## 段 1：第一性原理评审，与它落成的三件事（2026-10-27）

**评审方法**：回到 §0 的一句话（步步可验证、同能力不重教、机制强制去重）与两条派生原则——
**判定的诚实性是产品**、**机制必须被真实负载检验，而不是被自己的测试检验**——逐机制对照。

**发现与处置**：

1. **补丁链是全仓最脆的产物类**（本 session 三起手改损坏）。处置：`kiln prepare` 子命令
   （只铺脚手架、不跑规格、不留记录——learner 的"给我开局状态"与维护工具共用）+
   `tools/rebuild-patches.py`（铺链 → 可选 fixes → rustfmt → 按已提交补丁的段标签/段序重生成 →
   拒绝删行的 scaffold），`--check` 模式验证"每份已提交补丁等于它定义的树所产出的 diff"，并已接进

   改写的行；fmt 门只判解题后的树，所以从未被抓到）；另外 3 份是工具自己的假漂移（`mailer` 的
   `.sqlx` 被树里的 `.gitignore` 排除，`git add` 改用 `-f` 后消失），`lakelet/4.18` 的补丁文件名与
   步骤 id 不一致（`4.18-cardinality.patch`）属元数据漂移，工具改为按声明路径读取。
2. **i18n 机制从未装过真翻译**——回退链、结构检查、漂移检测全是未负载检验的机制。处置：
   zh-Hans 首批三步（mailer 1.1–1.3），`kiln i18n status` 结构 0 error、`--lang zh-Hans` 时正文
   解析到 `course/docs/steps/zh-Hans/…`。机制给翻译定了两条硬规则，实测才显形：**标题行必须逐字

3. **门的作用域曾是隐式的**（`unsafe-budget` 收尾时的按步化是第一次显式化）。处置：规则写进
   [plan.md](plan.md) §10——"这一步的工作对不对"的门按本步补丁的作用域判，"项目合不合格"的门

**评审中顺带修掉的**：`MissingDependency` 的提示把 track id 重复了一遍（`jobq/jobq/3.1-…`）。

**明确不做的（记下理由）**：README 里易腐的计数（步数/题数）不做"文档断言"检查——`lint-caps-md.py`

CI 的 lakelet selftest 在 4.1 挂了一次（12 个测试并行时 3/4 复现）：`a_frame_that_is_not_one…` 等

## 段 4：子 agent 评审，以及它抓到的八条

按用户的请求拉了一个子 agent 评审段 1–3 的全部产物。它自己铺链、比对旧树与新树、逐条试错，
抓到的不是风格问题而是**真缺陷**（`git diff 6cc157b..86a548b` 是它的证据）：

1. **`--check` 对"补丁少了一个文件段"失明**（最重）。工具只重生成补丁自己列出的段，所以一份漏掉
   某文件改动的补丁会通过检查——正是工具要抓的那一类。**但根因比这更深**：树是补丁铺出来的，
   一份当初就写错的补丁，它的树也是错的。工具真正能抓的是"补丁与它定义的树脱节"（手改过的补丁、
   没格式化的交付物、链的不一致）；漏写只在**下一步**的脚手架里露出，因此一条 track 的**最后一步**
   没有这样的证人。工具的文档改为说清这件事（而不是声称"逐字节一致"——那句本来就不成立：比较是
   语义的，hunk 头与上下文宽度是差异器的自由度）。
2. **写模式会静默丢段**：两棵树都没有的文件（`Cargo.lock` 由构建生成、树里没有）的段会消失而无
   提示。现在保留原段。
3. **`--steps` 是不可能工作的**：过滤掉链的前面几步之后，第一步的脚手架没有可比较的前一棵树。
   现在 `--steps` 选的是**写哪些**，链照铺。
4. **工具的自我描述不实**（"逐字节一致"）、**plan 章节指针错**（§6 → §10）、**审计数字错**
   （8/10/3 → 4/10/3 = 17，另 3 份是工具自己的假漂移）、**xtask 的失败消息不指名真正的原因**。
5. **已跟踪的 `.pyc`**（`tools/__pycache__/…`）——删掉并加 gitignore。
6. 风险两条已修：用户的 git 配置（颜色/外部 diff/前缀）不再影响输出；rustfmt 现在格式化树里
   **所有** `.rs`（`xtask/src/main.rs` 也在内，而 `fmt` 门判的是整个项目）。

**工具因此有了自己的自测**（`--self-test`，CI 也跑）：四条保证各配一个合成用例——"补丁漏掉一个
被改动的文件会被发现"、"两棵树都没有的文件的段被保留"、"上下文宽度与 hunk 边界不是内容"、
"增删行变了就是内容变了"。第四条的样本一开始写错了（把改动写成了上下文，等于一个空补丁），
是自测自己抓到的。

**没有采纳的一条**：README 里易腐的散文计数仍然不做文档断言检查（理由同段 1）。

## 段 5：共享构建目录让 CI 说了一句关于课程的谎（第三个 flake 的根）

CI 的第二轮在 `mailer/1.6` 与 `1.7` 报 "BROKEN STEP: the spec passes on the scaffold"——而这两步
在别的每一轮里都是绿的。查下去是**机制**而不是内容：

* 规格用 `env!("CARGO_BIN_EXE_mailer")` 启动服务进程。cargo 把编译出的二进制**上提到**
  `<target>/debug/<name>`——每个包名一个路径——而 `CARGO_BIN_EXE_<name>` 指的就是它。
* `kiln selftest` 用的是**全机共享**的 target 目录。于是任何一次"另一个树里的同名包"的构建
  （另一次 selftest、或一次被杀掉的运行留下的 cargo）都会把那个文件换掉。
* 被换掉的那次构建带的是**参考解的**二进制（被杀掉的运行已经走过 1.6 的解），于是新沙箱的
  **脚手架**跑出了解的行为——判决说"这一步分不开两个状态"，而真相是"这次跑的二进制不是这棵树的"。

**修法**：`kiln selftest` 的构建目录改为**本次运行自己的**（沙箱目录下的 `target/`），而不是全机共享的。
代价是每条 track 每次运行要重编依赖（实测 mailer 冷目录约 +1 分钟），换来的是"另一次构建换不掉这次
要启动的二进制"这条性质——按目录而不是按包名隔离。

**运行器的判决也改了**：脚手架通过时，它现在把两种可能都说出来（这一步真的分不开两个状态 / 这次跑的
二进制不是这棵树的），并指出"单独跑这一步能分辨"。一个只说第一种可能的判决，会让下一次调查从错误的
方向开始。

**顺带的一条**：CI 那一轮还撞上一次 crates.io 索引停顿（"failed to transfer more than 10 bytes in
30s"），一步因此被判红。cargo 的默认是"三十秒内不到十字节就放弃、重试三次"——那是为笔记本上的咖啡馆
wifi 调的，不是为一台同时被一百个构建索取的机器。运行器现在给 cargo 三个更耐心的默认值
（`CARGO_NET_RETRY=10`、`CARGO_HTTP_TIMEOUT=120`、`CARGO_HTTP_LOW_SPEED_LIMIT=1`），而且**调用方自己
写的值优先**（学员想用 cargo 自己的行为、或 `CARGO_NET_OFFLINE=true`，都还是他的）。一个单测把这三个
默认值钉住。

## 段 7：术语表——一条规则指向了一个从未存在的文件

`authoring.md` §8 一直写着"术语查 `glossary.toml`；新术语先加进词表再翻译"，而**这个文件不存在**。
这是"规则写了、机制没装"的又一例（和 i18n 回退链、门作用域同族）。这一段把它装上，并且**让它被检查**——
一张没人读的词表和没人查的 lint 表是同一种装饰。

**词表**（`course/glossary.toml`，69 条）：一个英文词 + 每种语言约定的说法，可选 `note`（给译者）与
`except`（这个词在某个说法里是另一个意思，表不管——`probe` 既是本课程的探题，也是 Kubernetes 的探针）。

**检查**（`kiln i18n status`，以及 `kiln check` 的 `i18n` 门）：英文正文用了表里的词、而译文没用约定的
说法，就报一条漂移告警。它**只读散文**——代码片段、行内代码、链接文字都不算词汇：实测第一版把
`mailer/1.1-workspace`、`Argon2::default()` 当成了词，一轮就报了八条假阳性。中文词被换行拆开时
（「默」/「认」）也算说到了。

**裁决过程本身就是检查的价值**：它先报了 14 条，逐条看下来——
- `step` 的约定说法是「步」而不是「步骤」（中文说「第 N 步」「这一步」）；
- `default` 是「默认」而不是「默认值」（形容词的位置）；
- `workspace` 保持拉丁（Cargo 自己的词，`[workspace.lints]` 更是逐字节不动）；
- `app factory` 是「app 工厂」，与课程自己的 [t1-mailer.md](t1-mailer.md) §4 一致；
- 1.1–1.3 的「must 门」改成「must 闸门」，与词表和后来的译文一致。

**译文的覆盖面**：zh-Hans 从 3 步到 **10 步**（mailer 1.1–1.8 + 之前的三步复核），结构 0 error、漂移 0 warning。
两个翻译 agent 各自独立指出词表缺词与冲突（`probe` 与存活探针、`app factory`、缺 catch-all/fallback/extractor），
这些都补进了表里。

## 段 8：一个死了的 owner 能把 CI 搁置半小时

CI 这次挂在 `kiln` 自己的一个集成测试上（`coverage_measures_the_step_module_or_names_the_component_to_install`），
原因不是课程而是**锁**：`coverage` 门在共享缓存里建一个有锁的构建目录，锁文件记下 owner 的 pid 与时刻，
但**没人检查那个 pid 还活着没有**。我为了并行工作杀掉的 CI 留下的锁，让下一个运行等满 `CLAIM_STALE`
（三十分钟）——而那个 pid 早就死了。

修法：`claim_within` 在拿不到锁时读 pid，用 `ps -p <pid>` 问一句；问不到就立刻接管（与"文件比 `stale`
更老"的旧规则并存，那条仍是兜底）。`ps` 是这个仓库已经在用的 POSIX 工具（进程夹具的 `SIGTERM` 就是
它），`std` 里没有等价的问法。pid 会被复用，所以这个答案只是"大概不在了"——代价有界（锁被接管、两个
运行写同一个构建目录），所以只在紧接着又一次 `take` 时才动手，旧的时间规则照旧兜底。两个单测钉住
两侧：owner 死了要接管，owner 活着要等。

**同一段里的一句自省**：这次的失败是**我自己并行跑工作**撞出来的（CI 在跑 `cargo test` 时我在同一个
`XDG_CACHE_HOME` 下跑别的 kiln 命令）。这条也记在 [m4-t5-progress] 的记忆里：门之间共享的目录与锁，
是为了让并发的运行互相绊住——所以**验证 CI 时不要在同一份缓存上并行做别的 kiln 工作**。

## 段 9：耐心必须有界，判决必须点名网络

上一段给 cargo 加的"耐心"旋钮设错了量级：10 次重试 × 120 秒，而一步的死线是 300 秒。网络真的断掉时
（这台机器当时连不上 `index.crates.io`，curl 也超时），一个步骤把整条死线烧完，然后报告"timed out"——
一句把读者引向课程的错误的话。改成 3 × 30 秒：慢传输仍然不判红，而"没有路由"在死线之内失败。

并且让判决**说出真相**：`kiln selftest` 在两种情况下都改口——脚手架的规格"失败"、以及参考解的规格
"仍然失败"——只要 cargo 的输出里有注册表不可达的痕迹（`spurious network error`、`failed to get`、
`Couldn't connect to server` 等），判决就说"这次跑不成：crate registry 不可达——这是网络，不是这一步，
它对脚手架什么也没证明"。一个"规格在脚手架上失败"的判决如果是网络造成的，那是另一种假证据：规格根本
没跑过，什么都没证明。单测把这两条钉住。

**当时的 CI 状态**：`relay/2.1` 因为断网超时，这一轮没有绿——记在这里，等网络恢复后重跑。

## 段 10：翻译的边界被写下来，并被检查

用户指出了一条本来就该有、但仓库只在 plan.md 里写反了的原则：**只有课程内容需要翻译；运行器的报错、
提示、闸门名、规格失败文本都不翻。** plan.md §3 D5 原来写的是"`kiln` 自己的提示语也在 `ui.toml`，
所以切换接口同时覆盖课程正文与 CLI"——那句话把一个按政策不做的事说成了承诺，而 `i18n status` 每次还会
打印一行 `cli catalogue: none (built-in English is used)`，读起来像一个待填的缺口。

改了三处：
1. **plan.md §3 D5** 改成真正的边界：译文覆盖步骤正文（外加课程自己的两句招呼语），运行器其余输出保持英文，
   并写明理由——它们引用代码、路径、标识符与编译器输出（`error[E0308]`、`assertion left == right failed`），
   翻译后既不能复制粘贴，也会给每次消息改动多添一份译文；
2. **`i18n status`** 只在真的有目录时才打印那一行；
3. **检查（`glossary::translated_output`）**：译文把运行器的输出写成自己的散文时，报一条漂移告警。标记是
   `error[E`、`panicked at`、`test result:`、`must gate`、`spec tests pass` 等；代码片段里的引用不算
   （那是引文，允许的）。单测钉住两侧。

**顺带把上一段的"两档 CI"问题记在这里**：内容改动（译文）跑全量 CI 是三十分钟换十秒该做的事；仓库目前
没有"这次改了什么"的概念。可行的形状是内容档（links / i18n / lint-caps / 文档计数）与全量档（只有改动落在
`kiln/`、`xtask/`、`course/tracks/`、`course/probes/` 时才跑）。没有做，因为这一轮先把边界本身立住。

## 段 11：内容改动不再跑全量 CI（用户指示）

用户明确要求：**不要跑全量 CI**。这条把段 7 里那个"两档门"的问题按最省的方式定了下来——内容改动
（译文、术语表、文档）的判据是**内容档**：`kiln i18n status --lang zh-Hans`（结构 + 漂移 + 运行器输出
误译）、`kiln links`、`kiln lint-caps`；改到 `kiln/` 或 `xtask/` 的提交才跑 `cargo test -p kiln` 与
`cargo clippy`。全量 `cargo xtask ci`（五轨 selftest，约 35 分钟）留给改动落在 `course/tracks/`、
`course/probes/` 的提交，以及发布前的验收。

**诚实地说清楚代价**：这意味着这些内容提交的推送背后没有一次"五轨全绿"的记录。它们改动的是
`course/docs/steps/zh-Hans/**`、`course/glossary.toml` 与文档，不参与任何一步的规格或闸门；`selftest`
读的是英文正文与规格，而 i18n 门读的正是内容档跑的同一套检查。所以"没跑全量"在这里是一个有依据的取舍，
不是一个遗漏——**但它被记下来**，将来若有一步红，读到这里的人知道从哪查起。

## 段 12：标题也是散文——结构按形状判，文字随译者

用户指出两件事：译文要**信达雅**，不需要逐字节对齐。第一版把"标题必须与英文逐字一致"写进了检查，那是
我为了好写检查而定下的规则，代价是中文读者在中文正文里看到 `## WHY`。改成：

- **标题可以翻**。译文与英文按**形状**对齐：段数、层级、顺序一一对应（`i18n::heading_shape`），

## 段 15：`kiln new-track` 与那份指南（plan §11 的验收）

M5 的最后一块是"用指南在 1 小时内起一条 3 步的玩具 track"。做法是**先真的做一遍**：在课程副本里
从零生成一条 `toy` track，把每一次撞墙记下来——那些撞墙就是指南的内容。

**生成器写什么、不写什么**（这条边界是整个设计的要点）：机械的一半（目录、`track.toml`、学员项目
骨架、规格路径与命名、正文入口、门的阶梯起点、规格哈希清单）一次写完；要判断的一半（台账槽位、退出
能力、探题、规格与参考解的内容、正文）只列成清单。**替人决定了它的生成器，会产出一门过了自己的
检查、却什么都没教的课。**

**做一遍才知道的五件事**（都进了指南）：

1. **能力已经有主人了**。新 track 不能在同一深度重教已教过的能力（R1/R2）。生成器现在**创建时就读
   台账**并指名冲突与出路（教更深的深度，或声明 `reteach = "why"`；台账不动，`lint-caps` 把每次
   重教报出来）。作者第一次撞到的红，本该是生成器的一句话。
2. **生成的骨架必须会失败**。第一版给了个能用的 `version()`，于是作者写完规格后 `selftest` 报
   "BROKEN STEP: the spec passes on the scaffold"——空测正是它要抓的东西。现在骨架是 `todo!()`。
3. **门的阶梯不能一步给满**。第一版给第一步全套持久门，于是 `unsafe-budget@0` 与 `exit-code` 在
   学员项目还没 deny `unsafe_code`、二进制还没学会拒绝参数时就红了。规则是 plan §6 的"门由教它那一步
   引入"：第一步三条基础门 + `fmt`/`clippy@1`，第二步加 `no-todo`/`docs:public`/`exit-code`，第三步
   起加 `unsafe-budget@0`。
4. **规格清单也要生成**。少了 `spec/manifest.toml`，`spec-integrity` 会在第一步就红，而作者根本
   不知道有这样一个文件。
5. **生成的二进制要会拒绝参数**。`exit-code` 门问的是"程序以非零退出并点名它拒绝的旗标"。

**指南**在 [new-track.md](new-track.md)：机械的一半 vs 要判断的一半、生成命令、三处必撞的墙
（能力已有主人、规格必须失败、补丁的 hunk 头要数对）、剩下的清单、跑门的命令、以及一张"一小时的账"。

## 段 16：三步玩具 track 的验收跑完（3/3）

段 15 的指南承诺"照它能在 1 小时内起一条 3 步玩具 track，所有门是绿的"。这一段的全部内容就是**把
那个承诺跑一遍**：在课程副本里生成 `toy`，写三份规格、五份补丁、三段正文，`kiln selftest --track
toy` 最后报：

```
✓ toy/1.1-first-step     scaffold ✓ solution ✓ gates 5/5
✓ toy/1.2-second-step    scaffold ✓ solution ✓ gates 8/8
✓ toy/1.3-third-step     scaffold ✓ solution ✓ gates 9/9
3/3 step(s) hold the contract
```

**验收抓到的四处问题，全部改在工具或文档里，而不是绕过去**：

1. **生成的 `Cargo.toml` 没有 deny `unsafe_code`。** 第三步起带 `unsafe-budget@0`，这个门要的是
   项目**拒绝** `unsafe`，不是"今天恰好没有"。生成器现在写 `[lints.rust] unsafe_code = "deny"`
   （一个以后要教 `unsafe` 的 track 在那一版 scaffold 里删掉它）。
2. **规格文件不过 rustfmt，`fmt` 门在每一步都红。** 规格会被拷进学员项目的 `tests/`，所以它是项目
   代码。一条超长的 `assert_eq!` 就足够。指南 §2.4 现在写了这件事，以及换规格后要重钉清单。
3. **脚手架编译不过**：`Error` 没有 `Display`（规格用了 `to_string()`），桩的参数 `message` 没用上
   （警告即错误）。`selftest` 对这两种的提示都是"不在脚手架上通过 + 可能缺一个签名"，那句提示把
   人引向了错误的方向。authoring.md 新增 §5.6：**规格用到的每个名字都要有桩（含 trait 实现），
   未用参数按仓库惯例加下划线**；判据是单独 `cargo build` 一次。
4. **手写补丁三次、错三次**（hunk 头数错、scaffold 删行、上下文取错）。这不是新知识，是 §5.5 早
   就写过的事——但指南原来把它写成"§2.3 hunk 头要数对"，等于教人继续手写。§2.3 现在给的是树的
   配方：`t0 → t1 → t2s → t2f`，每一步两个 `diff -u`，先 `rustfmt` 再 diff。

**一句话的账**：机械部分（生成、跑门）如今几乎不花时间；花时间的全是"判断的那一半"里**看起来
机械、其实需要工具**的两处——补丁和脚手架。这两处现在都有专门的规则和命令，指南的验收标准
（1 小时、3 步、全绿）因此是可以复现的，而不是我在段 15 里碰巧做到的一次。

## 段 17：文档站（`kiln site`）

M5 的最后一件：让整门课有一个能发布出去的形状。结论先说：**251 页、两种语言、一个搜索索引、
零个站内死链**，一条命令生成。

**做法与三个决定**：

1. **它是课程的一个视图，不是第二份课程。** 每页都从 `kiln hint` 读的同一份步骤正文渲染，走同一
   条回退链：缺译文就显示英文并在页头说明，某一步哪儿都没有正文就直接报错（`NotAuthored`），
   不会出一页空白。
2. **没有服务器、没有索引库。** 输出是静态托管直接能吃的文件：HTML + 一个 `style.css` + 一个
   `search.json` + 二十行 JS。全站 3.7 MB。渲染用 `pulldown-cmark`（CommonMark + GFM 表格），
   这是 `kiln` 为这件事新增的唯一依赖。
3. **`--check` 进 CI，发布是同一个实现。** CI 把全站渲染到临时目录再删掉，并检查**生成页面的每个
   站内链接都落在写出来的文件上**——这一步是 `kiln links` 做不到的：它判 markdown，而站点里的
   `2.15-shutdown-leases.md` 已经被改写成 `.html`，改错了只有渲染后的树知道。

**渲染这一步抓到的真内容缺陷**（这就是"机制要被真实负载检验"的又一个实例）：`en/lakelet/
4.19-backup-restore` 有一个跨行的行内代码（`` `backup --store `` / 下一行以 `<DIR> --to <DIR>` 开头）。
CommonMark 把以 `<DIR>` 开头的行当成 HTML 块，于是段落断在半句、后半行**原样不转义地**进页面——页面
看起来只错一点点，是最难发现的那种。修法两件：正文重排到 98 列（`<` 不再落在行首），并且 `kiln site`
现在**拒绝任何以 `<` 开头的正文行**并指名文件与行号；英文改了就要重钉译文的 `source_hash`（这一步
顺手做了，`i18n status` 仍是 0 error / 0 drift）。

**验收数字**（这一次都是本机实测）：`kiln site` → `251 page(s) in en, zh-Hans`；`kiln site --check`
→ 同样 251 页、链接全通；所有页面标签配平（用 `python3` 的 `HTMLParser` 逐页核对，251/251）；
`cargo test -p kiln` → **369 + 21 + 1**（新增 12 个 site 测试：表格、代码块、链接改写、回退、缺正文、
守卫、链接检查）；`cargo clippy -p kiln --all-targets -- -D warnings` 干净——顺带修掉了
`new-track` 里两处 `needless_borrow`，那是上一轮在"不跑全量 CI"期间提交的代码，clippy 从没看过它。

**没做的**：没有做视觉走查（这台机器上没有 Chrome/Chromium，浏览器截图无从谈起）；做的是结构核对
（标签配平、每页有 `<h1>`、表格/代码块/链接全在）。发布形态也没接任何托管商——`site/` 是普通文件，
交给谁都能托管。

## 段 18：用 Moli 做视觉走查，改了六处

段 17 结尾写了"没有做视觉走查"。用户指出这台机器上有 Moli（无头浏览器），于是补上：`moli serve
--layout` 起 CDP（127.0.0.1:9222），`python3 -m http.server` 服务 `site/`，再用一个 30 行、零依赖的

track 页、步骤页（表格、代码、长列表）、语言选择页、搜索结果下拉、暗色、390px 手机、手机表格。

**看到的问题与处置**（六处，全部是"看"才能发现的）：

1. **`<details>` 在 Moli 里渲染成一个圆点，而且内容永远展开。** 中文首页把英文招呼语塞进

2. **搜索框永远没有结果。** JS 里 `new URL(row.url, "../../search.json")` 抛 `TypeError`——相对

3. **中文站点的家具是英文的**：`Tracks`、`step(s)`、`project`、`search…`、页脚。处置：接到已有的

4. **track 名在中文页面上是英文**（"Mailer — subscription microservice"）。处置：`track.toml`
