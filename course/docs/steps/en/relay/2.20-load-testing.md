# Load test the thing you built, and write down the capacity

## WHY

You have a queue with a bound, a retry budget, per-tenant fairness, a DLQ and a p99 in `/metrics`.
Every one of those numbers was *chosen* — `delivery.max_in_flight`, `delivery.max_backlog`,
`rate_limit.per_second` — and none of them was ever checked against the service those settings
produce. The first time a customer sends a hundred events a second, the person on call finds out
which of the choices was wrong, in production, from the queue depth.

A capacity answer is what turns those settings from guesses into decisions, and it has three parts
that only work together: **a load generator** nobody has to trust (it offers the same events every
time, so a run can be compared with the one before it), **statistics** that are computed rather than
estimated (a p99 that came from an interpolation between two observations nobody made is a number
that cannot be checked), and **a curve**: p99 *against* concurrency, with the backlog beside it,
because latency alone answers "is it slow" and never "is it keeping up".

Two neighbours, and this step is neither of them. `obs/metrics-slo@aware` (`mailer/1.20-metrics`,
`relay/2.18-delivery-metrics`) measures the service *while it serves whatever traffic it happens to
get* — that is an observation, and its whole value is that no test arranged it. `async/backpressure`
(`relay/2.14-backpressure`) is the bound this step measures *against*: the seats are the process's
limit on concurrent attempts, the backlog bound is the queue's refusal to take more, and the
question a load run asks is where both of them start to bite. What is new here is the deliberate,
repeatable, offline pressure — and the page that says what the answers were.

## TASK

The scaffold put three things in place: `src/loadtest.rs` (the arithmetic, with `todo!()` in it),
`tests/support/workload.rs` (the harness that applies the pressure) and `docs/capacity.md` (the page,
with placeholder links). One line is yours in `src/lib.rs`: the module the scaffold added is not part
of the crate until a crate root says so, and a module nothing declares is a file nothing compiles.

### `src/loadtest.rs` — the generator, the arithmetic, the record

- **`keys` / `keys_from`** — `count` idempotency keys, unique, in a fixed order, so the ledger a run
  leaves behind can be compared with the last one. The generator is a *function*: the same argument
  answers the same keys on every machine;
- **`percentile` / `Percentiles`** — nearest rank, not interpolation: with `n` samples sorted
  ascending, the `q` quantile is the `ceil(q * n)`-th of them, clamped at both ends, and an empty
  sample answers zero rather than panicking in a report. Everything this module reports is therefore
  an observation a reader can recompute from the sample;
- **`Point` and `Curve`** — one level of load: the concurrency it was offered at, the p99 it cost,
  and the queue depth it left behind. `is_monotone_within(jitter)` is the *shape* check (a curve that
  rises, a curve that is flat, or one that broke), and `render` writes the table the page quotes.

### `tests/support/workload.rs` — the pressure

It starts the service over its own database with `N` subscribers, and `offer(keys, concurrency)`
puts `concurrency` blocking producers on one queue of keys, each timing its own request around the
socket. Two rules are already written into it, and both matter: it does the HTTP round trip before it
lets a test read a table (the port is armed before the migrations run), and it counts what the
service *answered* (`201`, `200` for a replay, anything else) rather than what it arranged to send.

### The run

Four things the spec asks of it, and each one is a claim about your service rather than about the
harness:

1. **the ledger is the list.** The events the service holds are exactly the keys the generator
   offered, once each, however many producers offered them — and the same run offered a second time
   adds nothing (`relay/2.2-idempotent-ingest` is what makes "the set of keys" and "the set of
   events" the same set);
2. **the statistics are exact.** A sample of twenty observations has three answers a reader can
   compute by hand, and the spec computes them — this is the half of a load run that does not depend
   on the machine;
3. **the curve is a shape.** At least three concurrency levels, each inside a bound, each leaving a
   deeper queue than the one below it. The backlog is arithmetic; the p99 column is a measurement
   and is *recorded*, not asserted monotone — one level's largest observation moves further than the
   load does on a machine that is also compiling. The shape check is proved against a rising and a
   collapsing curve so that it is not decoration;
4. **the load is work the service finishes.** Everything accepted reaches `sent`, the count is the
   events times the subscribers, and the backlog ends at zero. A load test that measured only what
   it could push in would report a service that is fast at forgetting.

### `docs/capacity.md` — the page

Four sections, and the shape of each is the answer to a question somebody asks before a launch:
**Method** (how the numbers were produced — a number without its method is a rumour, and it must say
that these are a debug build against a container on this machine), **Measurements** (the table, at
least three levels), **The slope** (what the growth column means and where the curve stops being a
curve), **Workers and throughput** (what another worker buys, and what it costs). The `links` gate
runs over this file: every relative target has to exist, and a `TODO` where a target should be is a
failure.

## DONE WHEN

- `kiln run relay/2.20-load-testing` — the spec passes (six cases: the ledger, the percentiles, the
  shape check, the bounded run, the drain, and the page)
- `kiln check relay/2.20-load-testing` — every must gate is green, `links` included
- `cargo test -p relay --test spec_load -- --nocapture` finishes in seconds and prints the curve you
  are about to quote in the page
- with the service running by hand (`cargo run -p relay`), the same load through `hey` or `curl`
  moves `relay_backlog_depth` and `relay_delivery_duration_seconds` in `/metrics`
  (`relay/2.18-delivery-metrics`) — the numbers a load run produces are the numbers a dashboard shows
- `docs/capacity.md` names the command that repeats the run, and quotes numbers *this* machine
  produced rather than the ones above

## TRAP

1. **A generator seeded by the clock.** It looks more honest — "random load" — and it makes every
   run a different experiment: the ledger cannot be compared, a regression cannot be spotted, and
   the number in the page is a number nobody can check. Keys are data; `keys(200)` is the same 200
   every time.
2. **Interpolating a percentile.** `p99 = 0.99 × (last - first) + first`, or an average of the two
   neighbours, answers a number *between* two observations — one nobody observed. Nearest rank
   answers one of the samples, and the arithmetic is checkable by hand.
3. **A p99 with no concurrency beside it.** "p99 = 43 ms" is unfalsifiable: the same service at one
   producer may be 8 ms and at four 43 ms, and a capacity decision from one column of one run is a
   guess with more digits.
4. **Asserting the p99 trend.** The measured p99 is the machine's as much as the service's, and a
   spec that fails when a level's maximum moves will be "fixed" by deleting it. Assert what is
   arithmetic (the backlog) and the bound (no request past `SLOWEST`); prove the *shape check* on
   synthetic curves.
5. **Measuring the subscriber.** The fixture's subscriber answers immediately on purpose. Point a
   load run at something that takes 200 ms and you have measured *that*, and the queue — the part
   this service owns — disappears from the numbers.
6. **Throughput only.** A service that accepts 1100 events a second and delivers 200 of them is
   worse than one that accepts 200 and delivers 200. The drain count is the half of the report that
   says the service keeps its promise (`delivery/at-least-once`, `relay/2.6-at-least-once`).
7. **Reaching for a worker per core.** Measured above: the same eight seats drain 400 deliveries in
   363 ms in one worker, 551 ms in two, and 1.87 s in eight, because every worker pays the claim
   statement's fixed cost per turn. More workers is not more throughput until something other than
   the database is the bottleneck.
8. **A page with a number and no method.** Debug or release, container or `127.0.0.1`, one
   subscriber or ten — every one of those changes the answer by more than the code will this year.
   Write the method down beside the table.
