# Change the schema while both versions are running

## WHY

The step before this one established the window: during a rollout, two releases of this service are
running against the same database, and the *old* one does not know what the new one is about to do.
Everything that makes a schema change safe follows from taking that sentence seriously.

The naive deploy is one migration with everything in it:

```sql
-- the change somebody wants
alter table events add column payload_bytes integer not null;   -- ✗
update events set payload_bytes = octet_length(payload::text);  -- ✗
```

Two lines, and each is an outage. The `not null` column with no default means every `insert` the old
release makes fails — and the old release is *running right now*, serving traffic, so the failure is
not hypothetical: it is the whole instance, on the third line of a deploy, while all the tests were
green. The `update` touches every row in the table: it holds a write lock for as long as the update
takes, on a table the old release writes to, so its delivery workers block, their claims sit there,
and the queue grows behind a deploy that looked instantaneous.

The way out is not a better migration; it is **three deploys**, and the shape of each one is decided
by what the *previous* release knows:

1. **expand** — a migration adds the column, nullable, no default. It rewrites nothing, and an
   `insert` naming only the old columns keeps working, because a new column may be absent. The old
   release cannot tell that anything happened, which is the point;
2. **backfill** — the rows that predate the column are filled in *batches*, by a step somebody runs,
   while both releases serve. Batches because each one holds a lock for milliseconds; a step because
   it can be interrupted, resumed, and run twice;
3. **contract** — a *later* release makes the column `not null` and removes the read path's
   fallback. Later, because the thing it depends on ("no row is empty") is a fact about the whole
   table, and because rolling back a release is easy while rolling back a `not null` is not.

What the middle phase costs is the interesting part, and it is what this step is really about: **the
read path has to answer while the column is empty.** Between the expand and the contract there is a
window — days, if the rollout is slow, or forever, if the deploy that would have finished it is
cancelled — in which the code that reads the column is running against rows that have none. So the
read path carries a fallback (`coalesce(payload_bytes, octet_length(payload::text))`), and the
fallback is the *same expression* the backfill writes: the stored number and the computed number can
never disagree, because they are one expression in two places. A read path that answered `null`, or
an error, would make the expand phase a breaking change — which is exactly what it is supposed not
to be.

Where `db/migrations@apply` (`mailer/1.9-postgres`) ends and this begins: that step is "there is a
schema, and the process applies it before serving". This one is what a schema change costs when the
process applying it is not the only one running. `ops/rolling-upgrade@apply` (`relay/2.22`) is the
window; `db/unique-as-concurrency@apply` (`relay/2.2`, `mailer/1.11-signup`) is the same instinct,
one table down — let the database refuse what should not exist rather than checking for it in code.
`db/schema-online-evolution@aware` is the depth here, and the reason it is `aware` rather than
`apply`: what a reader has to be able to do is *decide* which of the three phases a change belongs
in and argue about the window, and there is no single artefact to grade for that.

## TASK

The scaffold put two things in place: `migrations/0011_events_payload_bytes.sql` — the expand phase,
finished and commented — and `src/backfill.rs`, the middle phase, with `todo!()`.

### Read `migrations/0011_events_payload_bytes.sql` first

It is the whole of phase one and it is four statements: `alter table events add column payload_bytes
integer` (nullable, no default, no rewrite), a partial index in the shape the backfill reads, and two
comments saying why there is no `update` in it. The migration *not* doing the backfill is the
decision; a migration that did would be the second half of the naive deploy above.

### `src/backfill.rs` — the middle phase

- **`bytes(pool, batch)`** — one statement, filling at most `batch` rows that have no value yet, in
  the order the partial index is in, and answering how many it wrote. One statement means a batch is
  atomic: either its rows are filled or none is. The predicate is *the value is absent* rather than a
  bookmark, and that single choice is what makes the whole phase re-runnable — a row that already
  has a value is never written twice, so the second run of a finished backfill does nothing, and a
  run that was interrupted can be resumed by anybody;
- **`run(pool, batch)`** — the loop a deployment runs: batches until one fills nothing, and a
  `Backfilled` saying how many batches and how many rows that took. It stops on *filling nothing*
  rather than on "filled less than a batch", because the first is the statement's own answer that
  there is no work left and it is still correct when rows are being written while it runs.

### The write path and the read path

- **`src/events.rs`** — `ingest` writes the column for the rows it accepts, and the value is computed
  by the database (`octet_length($5::jsonb::text)`) from the text it is storing. That is the one
  subtlety worth pausing on: computing it in Rust from the JSON this process has in hand would be a
  second implementation of "how big is this", and it would disagree with the first one about key
  order and spacing;
- **`src/pagination.rs`, `src/http.rs`, `src/openapi.rs`** — the page answers a `bytes` field per
  event, read with the `coalesce` fallback and declared as its own schema (`ListedEvent`) rather
  than reusing `Event`: the page really does answer a field the other route does not, and
  `relay/2.3-contract-first` is a standing rule — the document says what the answer is;
- **`src/config.rs`, `src/main.rs`, `src/lib.rs`** — `--backfill`: connect, migrate, run the batches,
  print how many rows, exit `0`. It is a *command* rather than something startup does, because the
  middle phase of a rollout is run while the previous release is serving, may be interrupted, and is
  free to run again — a process that did it on every boot would make every restart a write over
  somebody else's table.

### What the spec judges

| the test | the claim |
| --- | --- |
| `the_previous_release_still_writes_rows_this_one_serves` | an `insert` naming only the columns of `0003_events.sql` lands, the new column is empty on those rows, and the page still answers a size for them — computed the way the backfill would store it |
| `the_backfill_fills_what_is_missing_and_can_be_run_again` | five rows in, five rows filled, every value equal to `octet_length(payload::text)`, a second run fills zero, and an event accepted *now* arrives with its size already written |
| `the_backfill_takes_a_batch_at_a_time` | batches of three fill three, four times over, and the last one fills what is left; `run` stops after 3 batches for 7 rows and fills them all |
| `the_backfill_is_a_step_a_rollout_runs` | `relay --backfill` exits `0`, fills the rows, and says how many |
| `the_column_is_still_nullable_because_the_contract_phase_is_a_later_release` | the column is nullable in the catalog, the partial index is there, and the read path still has its fallback |

## DONE WHEN

- `kiln run relay/2.23-online-schema` — the spec passes (five cases above)
- `kiln check relay/2.23-online-schema` — every must gate is green
- against a database of your own with rows in it:
  `cargo run -p relay -- --backfill` prints `backfilled N row(s) in M batch(es)`, and running it
  again prints `backfilled 0 row(s) in 0 batch(es)`
- `psql -c "select count(*) from events where payload_bytes is null"` is `0` after the backfill and
  `psql -c "select count(*) from events where payload_bytes <> octet_length(payload::text)"` is `0`
  — the stored value and the computed one are the same number
- `psql -c "\d events"` shows the column as `integer` with no `not null`, and
  `curl -H 'Authorization: Bearer <key>' localhost:8080/events` answers a `bytes` field per event
- you can say out loud, without notes, which of the three phases each of these belongs to: adding a
  column, filling it, making it `not null`, dropping the old column, adding a default, renaming one

## TRAP

1. **`add column … not null`.** Postgres 11 and later can add a `not null` column *with* a default
   without rewriting the table, and it is still wrong here: the **old release's** `insert` names the
   columns it knows, and a column the database refuses to leave empty rejects that insert. The
   failure is in the code that is already running, on the third line of a deploy.
2. **Backfilling inside the migration.** One `update` over the whole table, in the same transaction
   as the DDL, holding a write lock while the old release's workers try to write. It is a pause in
   the delivery queue with a changelog entry, and on a large table it is a pause measured in
   minutes.
3. **A backfill that is not idempotent.** `where received_at < now() - interval '1 day'`, or a
   `backfill_state` table with a bookmark: the first run is fine and the second one has to be
   reasoned about, which means it will not be run twice, which means a run that dies halfway is a run
   nobody finishes. `where payload_bytes is null` is the whole fix.
4. **Reading the column without a fallback.** The window between expand and contract is where rows
   have no value, and a read path that assumes one answers `null` (or an error) for every row that
   predates the change. The fallback is what makes the expand phase invisible, and it is removed in
   the *contract* phase, once the backfill has finished everywhere.
5. **A different size in the stored column than in the fallback.** `payload.to_string()` in Rust
   against `payload::text` in Postgres: `jsonb` canonicalises key order and spacing, `serde_json`
   does not, so the two answers differ by a byte for some payloads and nobody can tell which one is
   right. Compute it where the value is stored.
6. **The contract phase in the same deploy as the expand.** It is the tempting one, because the
   expansion is right there and the backfill is one command away. It makes the two deploys one, which
   is what the whole step is about not doing — and it removes the ability to roll back the code
   without rolling back a schema.
7. **Forgetting the index the backfill reads.** Without one, every batch scans the table to find the
   rows that have no value, so a backfill of a large table is quadratic in the thing it is trying to
   be incremental about. Partial, on the predicate it selects by.
8. **Assuming the window is short.** It ends when somebody deploys the contract, which may be never:
   a rollout can be paused for a week, a release can be rolled back, and a tenant's data can sit
   unbackfilled for as long as nobody runs the command. Write the read path for the window, not for
   the happy path.
9. **A `ROLLBACK`-able migration that "fixes" a bad one.** Down-migrations feel like safety and they
   are the opposite here: the schema they would roll back to is one the *new* release may already
   be writing to. The way back from a bad migration in a rolling deployment is forward, with another
   additive one.
