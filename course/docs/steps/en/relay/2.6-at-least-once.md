# At-least-once: write down what the delivery guarantees, and test it

## WHY

The service has accepted an event and owes it to three subscribers. Now something goes wrong, and
the question is not "does it go wrong" but **what is still true afterwards**. That answer is a
delivery guarantee, and every service has one whether or not anybody wrote it down — the written
version is what a subscriber's author can build against, and the unwritten one is what they discover
during an incident.

The honest options are three. *At most once*: send, never retry, and a subscriber that restarts for
five seconds silently loses everything sent in those seconds. *Exactly once*: the property everybody
wants and nobody can have across a network, because it requires knowing that a stranger's HTTP
server stored what it accepted. *At least once*: retry until the subscriber takes it or the worker
gives up, and accept the consequence — between the moment the subscriber has taken a request and the
moment the row says so, the worker can die, and that delivery will be sent again.

That window is why this step has two deliverables rather than one. The code has to make the window
as small as it can be, and the **decision record** has to say that the window exists, what it costs,
and what the receiver is expected to do about it (deduplicate on the delivery id). A guarantee that
is not written down gets "fixed" by the next person who sees a duplicate in a log.

## TASK

The scaffold added `src/delivery.rs` — the port, the types, `tick` with a `todo!()`, and the
fixture the spec uses as a subscriber (`tests/support/sender.rs`). Two more pieces have no scaffold:
the fan-out, which is a change to a file you already own, and the decision record, which is prose.

### `src/lib.rs`

Declare the module: `pub mod delivery;`.

### `src/delivery.rs`

- `tick(pool, sender, worker)` — one turn of a worker: **claim** a batch (step
  `relay/2.5-atomic-claim`), **attempt** each claimed delivery through the sender, **record** what
  happened. One write per attempt, and the write follows the attempt: a delivery that was recorded
  before it was sent is a delivery that a crash loses, which is the guarantee you were not offering.
- The three outcomes: the subscriber took it → `mark_sent`; a failure that may pass →
  `mark_retry` with the next instant (so `attempts` grows and the row waits); a failure that cannot
  be fixed, or a failure budget that is spent → `mark_dead`. Give up after a small number of
  attempts and write that number down as a constant; a retry policy with no end has no failures,
  only deliveries that are never late.
- `SendRequest` carries the **delivery id** and the **attempt number** on every attempt. The id is
  the receiver's deduplication key and does not change; the attempt number is what lets a receiver
  (and a metric) tell a retry from a new event.
- `Tick` reports what the turn did, including `lost`: an attempt whose outcome could not be recorded
  because the row was no longer this worker's. A worker that quietly drops that case is a worker
  whose counters disagree with the mailbox.

### The fan-out

An accepted event is owed to every endpoint its tenant has, and that has to happen **in the same
transaction that accepts the event** (`events::ingest`): one delivery row per endpoint, written with
the event or not at all. An event that exists without its deliveries is an event nobody is ever told
about — the one failure this guarantee does not allow — and deliveries written for an event that was
rolled back are work for a subscriber that was never told anything happened.

The unique constraint from `relay/2.5-atomic-claim` is what keeps a fan-out that runs twice
harmless.

### `docs/adr/0001-at-least-once.md`

The decision record, in the project, next to the code it is about. Three sections, in the shape the
`links` gate can check:

- `## Decision` — what this service guarantees: a delivery is forgotten only when a subscriber has
  taken it (`sent`) or a worker has given up on it (`dead`); every attempt carries a stable delivery
  id, and a subscriber that receives one twice can tell.
- `## Alternatives` — at least the three that were on the table (exactly once, at most once, and the
  lock-per-delivery variant of exactly-once that only holds while the worker is alive), each with
  what it would have cost. A record without alternatives is a description, and a description cannot
  be argued with.
- `## Consequences` — what this buys and what it costs: duplicates are possible and allowed, the
  subscriber has to be idempotent, ordering is not promised (that is `relay/2.9-ordering`), retries
  are bounded, and "deliveries sent" is not "events delivered".

It has to name the duplicate window in those words, and it has to **link** the code it talks about
(`src/delivery.rs`, `src/claim.rs`, the migration) — a relative link from `docs/adr/` is
`../../src/delivery.rs`. The `links` gate reads every markdown page in the project, so a target that
does not exist is a red step.

- `kiln links app/relay` — every link in the project resolves (the same check the gate makes)
- `cargo test --test spec_at_least_once the_window_between_sending_and_recording_lets_a_duplicate_through`
  — the duplicate window is measured rather than assumed
- posting three events with two endpoints registered and then running the worker leaves nothing in
  `pending` or `claimed`: `psql -c "select state, count(*) from deliveries group by state"` shows
  `sent` for the subscriber that takes them and `dead` for one that refuses them

## TRAP

1. **Recording before sending.** `mark_sent` and then the attempt turns a crash between the two into
   a delivery nobody ever makes — at-most-once wearing at-least-once's clothes. It is invisible in
   every test that does not kill the process mid-flight, which is why the spec's last test kills it
   mid-flight.
2. **Recording best-effort.** `let _ = mark_sent(…)` (or ignoring a `false`) leaves a delivery that
   was taken in a claimable state: the subscriber receives it again, forever, and the counter in the
   `Tick` says it was sent. A `false` means the row was not this worker's to record; that is `lost`.
3. **A fan-out per request rather than per accepted event.** The replay path (`Idempotency-Key`
   already used) runs the fan-out again, and every subscriber receives everything twice — the
   duplicate the guarantee allows, appearing where it does not have to.
4. **The event and its deliveries in two commits.** The insert commits, the process dies, and the
   deliveries never exist: an event the tenant believes was accepted and no subscriber is ever told
   about. Nothing retries it, because nothing knows it is missing.
5. **A retry with no end.** `mark_retry` for every failure and never `mark_dead` gives a poison
   delivery an infinite life: it is claimed, sent, failed, and claimed again while the subscriber
   that is actually working starves behind it. The spec drives the fail-forever case and expects the
   row to stop.
6. **Retrying what cannot be fixed.** A `410 Gone`, a target this service is not allowed to talk to,
   a malformed request: another attempt cannot help, and the retry budget spent on it is the budget
   the *next* delivery no longer has. Permanent failures are dead on the first attempt.
7. **A delivery id that changes between attempts.** Generating the id per attempt (or using a fresh
   UUID in the body) means the receiver cannot tell "the same delivery, sent twice" from "two
   events", and the write-off of duplicates becomes a lie.
8. **A `Tick` that counts attempts as deliveries.** Two attempts of one delivery are two entries in
   a counter and one delivery in the database. The `Tick` counts *what this turn decided*, and
   metrics of "deliveries sent" belong on the row, not on the attempt (step
   `relay/2.18-delivery-metrics`).
9. **An ADR that promises exactly-once.** "No duplicates" is a sentence a subscriber's author will
   build on, and the service cannot keep it. Write the window down, name the id, and say what the
   receiver is expected to do; that is the difference between a guarantee and a wish.
10. **A decision record with no links.** Prose about a module that was renamed away is a document
    that misleads a reader in a year. The record links `src/delivery.rs` and the migration, and the
    `links` gate fails the step when they stop resolving.
