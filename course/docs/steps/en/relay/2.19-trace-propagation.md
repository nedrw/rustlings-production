# Carry the trace across the boundary: W3C traceparent

## RECALL

`obs/tracing-propagation@aware` — `mailer/1.6-logging`: one correlation id per run, and from `1.7`
onwards one per request, carried in the log lines of everything that request did. It answered "which
lines belong together" inside one process, and it was the caller's own header when the caller sent
one.

## DELTA

The id was real and its scope was one process. Here the request ends long before the work does:

```text
caller ──traceparent──▶ relay (POST /events) ──queue──▶ worker ──traceparent──▶ subscriber
          1 trace id                              1 trace id
          1 span id            the event and the deliveries are written in one commit
```

Three things change, and each one is a shape rather than a line of code:

- **the context travels with the work, not with the process.** The delivery is made minutes or hours
  later by a worker that never saw the request, so the trace id is *written down* — a column on the
  delivery rows, written in the same transaction that accepted the event — and read back by the
  adapter that talks to the subscriber. A task-local or a thread-local propagates beautifully in
  every test and loses the trace in every deployment;
- **each hop gets a span of its own, and only the trace id is shared.** The caller's span is the
  caller's hop; the delivery is another. Two attempts at one delivery are two spans, which is what
  makes a slow retry visible as a *retry* rather than as one long request. The sampling decision is
  not this service's to make: it propagates what arrived, because a hop with no sampler has no
  business overriding the sampler that started the trace;
- **the header is parsed and regenerated, never forwarded.** What goes out is a header this service
  built from the trace id it stored — `00-<trace>-<span>-<flags>`, all lower case, no all-zero ids,
  exactly four fields. Passing a caller's bytes through is how a service becomes a relay for
  whatever anybody sends, and how a broken trace id becomes a broken trace in somebody else's
  system. A header this service cannot read is not an error: the trace restarts and the delivery
  happens, because a lost parent link is a worse trace and a dropped event is a worse service.

The format is the [W3C's `trace-context`](https://www.w3.org/TR/trace-context/), and that is the
point of writing it by hand here: the subscriber is a system this service knows nothing about, and
the only thing that makes the trace survive it is that the ids mean the same thing to both sides.

Two neighbours: `obs/structured-logs@apply` (`relay/2.1`) is where the trace id ends up in a line an
operator can search, and the *request* id stays what it was — this service's own handle on one
request, which is not what a caller's tracing system shares with the next service. Both are in the
log line, and they answer different questions.

## TASK

The scaffold added `src/trace.rs` and a migration is yours to write. Everything else is in files you
already own.

### `migrations/0009_trace.sql`

`ls migrations` first — the next free number is the one you use. Two nullable columns on
`deliveries` (`trace_id`, `tracestate`) and a `check` that a trace id is 32 lower-case hex
characters. Nullable is a decision: a delivery accepted before this service carried traces has no
trace, and it goes out with no header rather than with one invented at delivery time. The columns
belong to the *delivery* rather than to the event because they are read where the delivery is
attempted.

### `src/trace.rs`

- `TraceId` / `SpanId` — parse (exactly 32 / 16 lower-case hex, never all zeroes) and generate;
- `Traceparent` — `parse`, `generate`, `child` (the same trace, a span of its own, the caller's
  sampling decision), `Display`, and the accessors;
- `Context` — what crosses the boundary: the trace, the sampling decision, the vendor state. It
  deliberately does *not* carry the span id — a span is one hop's, and the delivery is a different
  hop from the request;
- `Traces` — the port the adapter asks for "what is the trace of this delivery", and `DbTraces`,
  the implementation that reads the columns.

### `src/events.rs`, `src/delivery.rs`

`ingest` takes the request's context and `fan_out` writes it on every delivery row it creates — the
same transaction, for the reason the rows themselves are one commit: a delivery whose trace was
written separately is a delivery that is sometimes untraceable.

### `src/outbound.rs`

`HttpSender::with_traces(store)` — a builder, like `signing`'s — and, in `send`, the header this
attempt generates: `traceparent` from the stored trace with a **new** span id, and `tracestate` when
the caller sent one. A delivery with no stored trace goes out without a header. This is the second
port the adapter looks something up with, and the same argument covers both: the worker's request
type does not grow a field for what only the adapter writes.

### `src/http.rs`

A layer, outside the request log: read `traceparent` and `tracestate`, keep the trace when the header
is one this service can read, start a new one when it is not — and **drop the vendor state with it**
when it is not, because a `tracestate` only means anything beside the trace it arrived with. The
context goes into the request extensions, the log line gains a `trace_id` field, and `create_event`
hands the context to `ingest`.

### `src/openapi.rs`

`POST /events` declares the two optional headers. `relay/2.3-contract-first` is a standing rule: a
header a caller may send is part of what this service promises.

  `curl -X POST localhost:8080/events -H 'Authorization: Bearer <key>' -H 'Idempotency-Key: k' -H 'traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01' -d '{"kind":"a","payload":{}}'`
  and the line your subscriber prints carries the same trace id `4bf92f3577b34da6a3ce929d0e0e4736`
  with a span id of its own
- `psql -c "select trace_id, tracestate from deliveries"` shows the id on the row, and the log line
  for that POST shows the same one

## TRAP

1. **A task-local or a thread-local.** It works in the test that sends a request and watches the
   delivery happen right after — and the delivery does not happen right after. The worker is a
   different task in a different turn, often a different process. The trace has to be *stored*.
2. **Forwarding the caller's header.** It looks right, and it makes this service a relay: the bytes
   go to a subscriber that may parse them differently, and a caller with a broken trace id gets their
   brokenness reproduced in somebody else's collector. Parse it, keep the trace id, generate the
   header you send.
3. **Reusing the caller's span id.** The span is one hop, and reusing the parent's makes two hops look
   like one in the trace — a delivery that took four seconds looks like a request that took four
   seconds, and the queue between them disappears from the waterfall.
4. **One span for two attempts.** A retry is another hop: a new span id per *attempt*, not per
   delivery. Otherwise the second attempt is invisible, which is exactly the attempt worth looking
   at.
5. **A `tracestate` kept when the `traceparent` was not.** Vendor state is scoped to the trace it
   arrived with; keeping it while starting a new trace hands the next hop somebody else's baggage
   under this service's trace id.
6. **Refusing the request.** A 400 for a header the caller's framework malformed turns one caller's
   telemetry bug into an outage. Ignore the header, start a trace, deliver the event.
7. **Reading the trace per attempt with a database round trip and forgetting what that costs.** The
   lookup is per attempt, next to the signing secret's — two probes per delivery. It is a deliberate
   price (the alternative is a field on the request type that every layer then carries), and it is
   worth knowing you are paying it: an index on `deliveries (id)` is what makes it a probe.
8. **Uppercase hex.** The format is lower case, and a service that accepts `4BF9…` produces traces
   that do not match the same trace id as the caller's — two ids that are the same to a human and
   different to every index.
9. **An all-zero id.** `0000…` is reserved by the format for "there is no trace"; accepting it means
   every caller that sends it lands in one trace together, and that trace is nobody's.
10. **A migration that writes the column non-null.** Every delivery accepted before this step has no
    trace id, and a `not null` column makes the upgrade a data migration nobody wrote.
