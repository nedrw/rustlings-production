# Delivery observability: latency, backlog, and which tenant is slow

## RECALL

`obs/metrics-slo@aware` — `mailer/1.20-metrics`: a `/metrics` endpoint written by hand in the
Prometheus text format, counters per route, and a `deliveries_total{outcome}` counter that answered
"how much happened". The endpoint is the part that carries over exactly: the media type, the
`# HELP` and `# TYPE` lines, and the rule that the text is produced by a function rather than
assembled by whoever remembers to call it.

## DELTA

A count of what happened is not what an operator pages on, and three things are missing from it:

- **the distribution, not the average.** "Delivery takes 300 ms" and "99 % of deliveries take 12 ms
  and the rest take four seconds" are the same average and two different services. What makes the
  difference visible is a histogram — buckets, cumulative, `+Inf` at the end — and a histogram is
  also the only metric here whose *rising* value is a statement about work that has not finished
  yet;
- **the queue, not the throughput.** A latency spike and a subscriber that has stopped answering
  look identical in a counter and completely different against a backlog. The gauge has to be read
  from the queue at the moment it is scraped: a number remembered between turns is a number about
  the past, which is exactly the number that misses the incident;
- **per tenant, and bounded.** "Which tenant is slow" is the question a multi-tenant service is
  actually asked, and it is also the question that gets a metrics endpoint taken down: every label
  value is a series in every scraper and an index in the store behind it, so the label set has to be
  a set this service *chose* — the tenant names, which configuration bounds — and never an endpoint
  URL, an event id, or a path a caller invented. What cannot be named is folded into `unknown`
  rather than dropped or kept.

The window into the queue is also the one place where a scrape touches the database, and the
trade-off is real: an accurate gauge costs a query per scrape, and a cached one is free and lies.
This step chooses accurate, and says out loud what a deployment with a large table would do about it
(index the states, or cache on a timer and accept the staleness).

Two neighbours, and neither is what this step is: `obs/structured-logs@apply` (`relay/2.1`) is where
a *specific* delivery, request or failure is followed — a log line costs nothing per distinct value
and a metric costs a series, so "which event failed" belongs in the log and "how many are failing"
belongs here; and `obs/cardinality-cost@apply` (a later track) is the discipline of what a label
costs, which this step applies in one place rather than studies.

## TASK

The scaffold added `src/metrics.rs`. Everything else in this step is in files you already own.

### `src/metrics.rs`

- `Outcome` — three values, and no more: `sent`, `retried`, `dead`. The worker's report also has
  `lost` (an attempt it could not write down) and `shed` (an attempt it never made because the
  endpoint's breaker was open). Neither is a fact about a delivery, and a fourth label value that
  means "ask the log" is a series nobody can query;
- `BUCKETS` — the fixed bounds. Fixed rather than configurable: a bucket that moves between deploys
  is a dashboard that moves with it. The histogram is **cumulative** — an observation inside five
  milliseconds is inside every bucket above it — which is what makes the last bucket equal to the
  count;
- `Metrics::record(tenant, outcome, elapsed)` — `&self`, because a turn's attempts run as several
  tasks at once and a registry handed out mutably would serialise the deliveries it measures;
- `Metrics::render(backlog)` — the exposition text. One `# HELP` and one `# TYPE` per family, then a
  line per sample. Every family is present for every tenant label **from the first scrape**: a
  histogram that appears only after the first delivery is a dashboard query that has to cope with a
  missing series, and a counter that shows a spike is only readable against a baseline that was
  there before it;
- the label value is the tenant's **name**, and anything that is not a name this service could have
  written folds into `unknown` *when it is recorded*, not when it is printed: the point of the fold
  is the memory as much as the output.

### `src/claim.rs`

`Claimed` gains the tenant's **name**, brought back by the claim's own join. The claim already joins
the target and the event for exactly this reason (`relay/2.5-atomic-claim`): a metric that costs a
second round trip per attempt is a metric that slows down the thing it measures.

### `src/concurrency.rs`

`Worker::metered(registry)` — a builder, like `leasing` — and the clock read around the *attempt*:
the seat and the record are outside the measurement, because what the number is about is how long
the subscriber took. Two outcomes are not recorded, and the reason is in `outcome_of`.

### `src/http.rs`, `src/main.rs`, `src/authz.rs`, `src/openapi.rs`

- `AppState` owns the registry and hands it out; `main.rs` gives the *same* one to the worker, so the
  process exports what it measures;
- `GET /metrics` reads the backlog, renders the text, and answers `text/plain`. It is a route like
  any other: `relay/2.16-authz-audit` decides who may read it (a scraper holds a `tenant-admin`
  key — the label set is every tenant's name, which is not a reader's business), and
  `relay/2.3-contract-first` requires it in the document with every status it can answer.

## TRAP

1. **An endpoint URL, an event id or a path in a label.** The endpoint is the most natural thing in
   the world to label a delivery metric with, and it is the one that ends the service: a tenant with
   ten thousand endpoints is ten thousand series per metric per outcome, in every scraper, for ever.
   The spec asserts that no label value is anything but a tenant name or `unknown`.
2. **A histogram that is not cumulative.** Counting each observation into exactly one bucket is the
   intuitive implementation and it produces a series where `+Inf` is not the count and a quantile
   computed from it is smaller than the truth. The spec walks the buckets and compares the last one
   with `_count`.
3. **A gauge remembered between turns.** The backlog updated when a worker finishes a turn is a
   number that is stale exactly when the queue is growing — the moment the number exists for. Read
   it from the queue when it is asked for.
4. **A cached gauge that survives the outage it describes.** The other half of the same decision:
   when the database cannot be read, the honest answer is an error, not the last number this process
   happened to have. A `200` with a stale gauge in it is a number an operator will act on.
5. **A series that only exists after the first delivery.** A dashboard query written against a
   family that appears later is a query that shows "no data" during the quiet period, which is
   indistinguishable from the service being down. Emit every label's series from the start.
6. **A `sum` that is not the sum.** The `_sum` and the buckets have to come from the same
   observation: computing one from the histogram and the other from a second pass over the samples
   is how an average ends up outside the range of its own buckets.
7. **A worker with a registry of its own.** `Arc::new(Metrics::new())` inside `Worker::new` is
   tempting and gives a process that measures deliveries into a registry nothing can scrape. One
   process, one registry, handed to both halves.
8. **Reading the backlog per tenant with a loop.** One query per tenant turns a scrape into N round
   trips and makes the endpoint's cost a function of how many customers there are. It is one grouped
   query.
9. **Timing the claim, the seat or the record.** A histogram whose clock starts before the seat is
   taken measures how long the worker waited for a free seat — a real number, and not the one
   anybody asked for. The attempt is what takes time.
10. **A `403` where the label set is the answer.** The route's permission is a decision about
    *information*, not about rows: a reader may read its own deliveries, and the numbers are about
    the whole service.
