# Inject the failures you are afraid of: delay, reset, half-open

## WHY

Every step so far has added a promise about failure: a retry with a budget, a dead letter instead of
a loop, a lease that recovers a crashed worker. Those promises have been *tested*, and they have
been tested against failures somebody wrote into the test — a fake that returns `Retryable`, a
delivery parked by hand, a row aged with `UPDATE`. None of that exercises the thing that actually
happens in production: a socket that is open and silent, a connection that ends between the request
and the answer, a subscriber that answers in 200 ms on Tuesday and 40 seconds on Friday.

The failure you have not injected is the failure you are guessing about, and the guess is almost
always "the client will tell me". It will not. A read that returns `Ok(0)` means "closed"; it does
not mean "slow", and a subscriber that took the request and went quiet looks exactly like a
subscriber that is thinking. The difference between a delivery that comes back in thirty seconds and
one that never comes back is a deadline somebody chose, and the only way to know which one you have
is to make a subscriber go quiet and watch what happens.

## RECALL

`test/fake-external@apply` — `mailer/1.13-email-port` — and `relay/2.6-at-least-once`'s
`tests/support/sender.rs`: a port with a recording implementation is how this project tests
"something external failed". That is a *decision* fake: it answers `Retryable` because the test said
so. It cannot be half-open, it has no socket, and it has no deadline to run into — the failure is
whatever the fake was told, which is exactly the failure you already thought of.

## DELTA

Here the failure happens at the socket, to the real client. `HttpSender` — the adapter of
`relay/2.7-outbound-client` with three deadlines — is pointed at a proxy the test owns, the proxy
receives instructions, and the deadlines, the retry budget of `relay/2.8-retry-budget` and the queue
state are judged through a failure that was *produced*, not simulated in a return value. The agent
of the failure is a hundred lines of `std` in `tests/support/faults.rs`: a listener, a thread per
connection, and a fault.

That is also where this step departs from the tooling list in `docs/curriculum.md` §7, which names
`toxiproxy` for exactly this job. The reasons are in the fixture's own module docs, and they are
worth reading before you write a line: an image that has to be pulled is a spec that fails on a
machine with no registry; and a fault *rate* drawn from a random generator is a test that fails one
run in twenty, which is a test people learn to re-run instead of read. The classes of failure are
the same and they are all here — slow, reset, half-open, dropped — and the thing being judged is
the service's behaviour, not the injection mechanism.

## TASK

Write `tests/support/faults.rs`. The scaffold gives you the interface the spec uses (a `Fault` to
choose, a `Proxy` with a port of its own and the counters a test reads) and nothing else: the
implementation is the step.

### The four faults

| fault | what the client observes | the production failure it stands for |
| --- | --- | --- |
| `Fault::Delay(d)` | the answer arrives, `d` later | a subscriber that is slow, or a path that is |
| `Fault::Reset` | the connection ends at once, with `RST` | a crashed process, a firewall, a load balancer with no backend |
| `Fault::HalfOpen` | the request is delivered and no answer ever comes | a machine that is up and not answering — the failure only a deadline catches |
| `Fault::Loss { every }` | every `every`-th request never reaches the target | a connection that goes away between two attempts |

Notes that are decisions rather than details:

- **the reset has to be a real one.** An orderly close is a `FIN`, and a `FIN` is what a subscriber
  that finished answering sends. `RST` is what a process that died in the middle sends. On a plain
  socket there is one portable way to produce it: **close the socket with unread bytes in its
  receive buffer** — read the head, one byte at a time, and leave the body where it is;
- **half-open means delivered and silent.** Forward the request to the target and never pass the
  answer back: the subscriber had it, which is a different failure from a connection that never
  arrived, and the only thing that can end it is the client's own read deadline;
- **loss is a period, not a probability.** `every = 2` drops every second request, so the same run
  drops the same ones and a test can assert how many were dropped instead of hoping;
- **the period counts requests, not connections.** This service reuses a connection for the
  attempts that go to the same target (`relay/2.7-outbound-client`): a connection that is only
  sometimes dropped takes the reuse with it, and the fault fires once and then hides behind a live
  socket;
- **the fault in force is read when the connection is accepted**, not per byte: a test that heals a
  proxy while an attempt is in flight is testing that attempt, and changing the fault underneath it
  would make the outcome depend on the scheduler;
- **the counters are part of the interface**, and they are not decoration. A proxy that injected
  nothing makes every assertion in the spec vacuously true. `forwarded()`, `dropped()` and
  `connections()` are how each test says "the fault happened on the path the service uses".

### The fixture rules you already know

Detach the connection threads (a test that walks away from a connection must still be able to
finish), set a read deadline on every socket the fixture owns (a fixture that blocks for ever turns
a failure into a hang), bind port `0` (the kernel picks, the fixture announces), and never sleep to
synchronise — the spec polls `psql` for the state it wants.

### No production code

This step changes nothing under `src/`. Everything it needs — the deadlines, the budget, the lease,
the dead-letter table — was built by the steps before it, and that is the point: what is missing is
not code, it is *evidence*.

## DONE WHEN

- `kiln run relay/2.17-chaos-injection` — the spec passes
- `kiln check relay/2.17-chaos-injection` — every must gate is green
- `cargo test --test spec_chaos` — the seven cases:
  1. a delay the attempt outlives is absorbed — one attempt, one delivery, no retry
  2. a delay it does not outlive spends an attempt, writes the deadline's sentence on the row, and
     the delivery is owed again
  3. a reset connection is a delay: every delivery comes back, and the service heals when the fault
     stops, with no row left `claimed`
  4. a half-open connection is cut by the read deadline — the subscriber had the request, the row
     says nothing arrived for the deadline, and the turn *ended*
  5. loss is reproducible: four attempts under `every = 2`, exactly two dropped, and the other two
     delivered
  6. every fault class in the matrix ends with all deliveries delivered and none invisible
  7. a fault that never stops ends the delivery in the dead-letter queue with its reason written
     down, instead of retrying for ever
- `cargo test --test spec_chaos a_dropped_connection -- --exact` twice in a row, and the second run
  reports the same numbers as the first: the injection is reproducible

## TRAP

1. **A `read` that takes the body with it.** The proxy reads a chunk of the request to find the end
   of the head, and the buffer it read also holds the first bytes of the body. Throw them away and
   the proxy then waits for a body that has already arrived — and the symptom is not a proxy that
   hangs, it is a *service* that retries every delivery against a subscriber that answers in
   milliseconds. Read once, keep what you got, take what is missing.
2. **A loss rate from a generator.** `if rng.next() < 0.3` is a test that fails one run in twenty,
   and the first thing anybody does with it is run it again. A period is just as good at finding
   the bug and it can be asserted: *the same fault, the same counters, every time*.
3. **Using a `Sender` fake to test failures of the socket.** `tests/support/sender.rs` is the right
   tool for "what does the worker do with a `Retryable`" and the wrong tool for "what does a client
   do with a socket that goes quiet": the fake has no socket, so no deadline, no half-open, no
   connection reuse, and nothing to inject.
4. **A fixture socket with no read deadline.** The proxy blocks for ever on a peer that is waiting
   for the proxy, and the test does not fail — it hangs, and CI kills it an hour later with nothing
   in the log. Every read in the fixture gets a deadline; the *test's* deadline stays the service's
   business.
5. **Sleeping to synchronise.** `sleep(200ms)` after injecting, to "give the failure time", is a
   race with the machine's speed: fast here, flaky there. The spec polls the database for a state it
   can name, and every wait has a deadline with a message.
6. **Asserting only the end state.** "Everything is `sent` at the end" is true of a proxy that
   forwarded everything and injected nothing — the whole file passes and nothing was tested. The
   counters are what make the difference between "the service survived a fault" and "there was no
   fault".
7. **Letting the breaker hide the fault.** `relay/2.8-retry-budget` cuts an endpoint off after a few
   failures and *sheds* the attempts that follow, and a shed attempt never reaches the proxy. The
   spec turns the breaker off on purpose, because a counters assertion about attempts has to be an
   assertion about attempts.
8. **One connection per attempt.** Assume the client opens a connection per delivery and a
   connection-level fault fires on every attempt. It does not: the connection is reused, so a fault
   that only applies to *new* connections fires once and then everything after it succeeds — and the
   test passes for the wrong reason.
9. **Healing the fault and asserting immediately.** The rows the fault touched are still in the
   queue: "healed" is not "drained". Wait for `pending + retrying = 0`, and let the failure message
   show the states rather than a sleep.
10. **Forgetting `RELAY__DELIVERY__ALLOW_PRIVATE_TARGETS`.** The subscriber is on `127.0.0.1`, and
    since `relay/2.12-ssrf-defense` a service refuses to deliver to its own networks unless the
    deployment says otherwise: without the setting, registering the endpoint is a `422` and every
    test in the file fails with a message about a target, not about chaos.

## FURTHER

- [toxiproxy](https://github.com/Shopify/toxiproxy) — the tool this step replaces: read its list of
  toxics, because the list is the taxonomy of failures worth injecting, and compare it with the four
  this fixture has
- [`std::net::TcpStream::set_read_timeout`](https://doc.rust-lang.org/std/net/struct.TcpStream.html#method.set_read_timeout)
  — the deadline every socket in a fixture needs, and the `WouldBlock` it produces
- [RFC 9293: TCP](https://www.rfc-editor.org/rfc/rfc9293) §3.5 — what a `RST` is, when the kernel
  sends one instead of a `FIN` (unread data, a closed socket), and why a connection with a dead peer
  is not the same failure as one that was never opened
- [Principles of Chaos Engineering](https://principlesofchaos.org/) — steady state, a hypothesis,
  and the smallest possible blast radius: the discipline this file applies at the scale of one test
- [PostgreSQL: `FOR UPDATE SKIP LOCKED`](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)
  — the claim that makes "nothing was lost" a statement about the queue rather than about one lucky
  process
