# Cursor pagination that never skips or repeats a row

## WHY

A tenant's event table only grows, and the first thing every client does with it is read it. The
naive answer — `GET /events` returns everything, or `?offset=` — is wrong in three separate ways,
and all three are visible in production and invisible in a test fixture of ten rows:

- **the answer is unbounded.** A tenant that has ingested two million events gets two million rows
  in one response: the query holds them, the serialiser holds them, and the socket holds them;
- **an offset is a count, and the stream moves.** `LIMIT 25 OFFSET 25` means "skip the 25 newest
  rows" — but the *newest* is exactly where new events arrive. One event is accepted between page 1
  and page 2, and the row at the boundary is never seen by anybody. The same measurement with a
  page that was filled by a deletion instead repeats a row. A reader that cannot tell the two apart
  cannot reconcile anything;
- **both of them sort the tenant's whole table to answer.** The cost of a page grows with how much
  the tenant has ever sent, which is the opposite of what a page is for.

A cursor fixes all three by answering a different question: not "how many have I seen" but "where
was I". The caller sends back an opaque position, the service reads *after* it, and the page is a
bounded range scan whose cost does not depend on the tenant's history. The price is that the
position has to be a real position — and that is this step.

## TASK

The scaffold added `src/pagination.rs`: the constants, the types, and the three signatures. The
migration, the route, the query and the wiring are yours.

### `migrations/0004_events_cursor_index.sql`

One index, in the order a page is read: the tenant, then the instant descending, then the identity
descending. The `events` table from step `relay/2.2-idempotent-ingest` has no index in that order,
and without one every page sorts the tenant's whole table.

### `src/lib.rs`

Declare the module: `pub mod pagination;`.

### `src/pagination.rs`

- `Cursor::after(event)` — the position of one event, written down. **Encode the instant and the
  identity together**, and round-trip exactly: microseconds are what a `timestamptz` column holds,
  and a cursor that loses them points at the wrong row. Hex, base64, a delimiter — the encoding is
  your call and the body above argues for one; what is not a call is that the token has to *sort*
  with the rows and has to be checkable before it is used.
- `Cursor::parse(text)` — a caller's text back into a position, `400` when it is not one this service
  issued. It arrives from a stranger: validate before you query.
- `page(pool, tenant, query)` — one page. Validate `limit` (absent means `DEFAULT_LIMIT`, anything
  outside `1..=MAX_LIMIT` is a `400` naming the parameter), apply `kind` and the cursor **in one
  statement**, order by `received_at DESC, id DESC`, and ask for **one row more than the page
  holds** — that extra row is how "there is more" is answered without a second query.
  `Page::next` is `Some(cursor)` of the *last row of the page* when the extra row came back, and
  `None` at the end of the stream.
- The comparison is strict and about the **pair**: the next page is rows where
  `(received_at, id) < (cursor_at, cursor_id)`. `<` rather than `>` because the order is newest
  first; a pair because one instant can carry several events.

### `src/http.rs`

- `GET /events`, behind the authentication layer, with the query parameters `limit`, `cursor` and
  `kind`. Take them as text and let `pagination::page` decide what is usable — one place answers
  what a request means.
- The answer is `{"events": [ … ], "next": "…" | null}`, events newest first, each event the shape
  `POST /events` answers with minus `replayed`. `next` is present and `null` at the end of the
  stream — not absent, so a client can tell "no more" from "this field is not in my contract".

### `src/openapi.rs`

Add what you just built: an `Event` schema, a `Page` schema (`events`, `next`), and the `get`
operation on `/events` with its three query parameters and the statuses it can answer with. The
document is the API; a route that is not in it is a route clients cannot find.

- `kiln run relay/2.4-cursor-pagination` — the spec passes
- `kiln check relay/2.4-cursor-pagination` — every must gate is green
- `curl -sS "localhost:8080/events?limit=2" -H "authorization: Bearer <key>"` answers two events and

  visits every event exactly once
- `psql -c "select indexdef from pg_indexes where tablename = 'events'"` shows an index whose
  columns are `(tenant_id, received_at, id)`

## TRAP

1. **A cursor made of the instant alone.** `WHERE received_at < $1` looks like a position and is
   not one: everything happening in one transaction shares an instant, so the second page comes
   back **empty** and every one of those events is silently skipped. The spec's first test has three
   events at one instant and a page of one, which is exactly this symptom.
2. **`<=` instead of `<`.** With a pair, `(received_at, id) <= ($1, $2)` repeats the row the cursor
   points at on every page: the walk comes back with the same event twice and never ends.
3. **An offset dressed as a cursor.** `?cursor=25` or a cursor that counts rows reintroduces every
   problem a cursor was chosen over: the row that was inserted between two pages is skipped, and
   the position means nothing to anybody else.
4. **`limit + 1` forgotten.** Without the extra row, "is there more?" is either guessed (`next` is
   always set, and the caller's last page is empty) or asked in a second query that can disagree
   with the first — one page that claims to be the end while a row sits behind it is data loss.
5. **A cursor that is not validated.** `200` for a cursor this service never wrote is a page
   starting *anywhere* — including past the whole stream, which reads as "you are done" to a caller
   that is not.
6. **A `limit` that is silently clamped.** Answering `200` with 100 rows for `limit=100000` looks
   friendly and lies about what was asked: the caller cannot tell a bounded answer from a truncated
   one, and neither can its metrics. `400` says which it was.
7. **An index in the wrong order.** An index on `(tenant_id)` alone, or `(received_at)` without the
   tenant, leaves the database sorting a page out of the tenant's table: correct answers, cost that
   grows forever, and nothing in the tests notices — which is why this step's spec reads
   `pg_indexes`.
8. **Filtering after paging.** Applying `kind=` to the last page, or paging first and filtering the
   rows you got, gives pages that are short for no reason and a `next` that steps over rows that
   were never read. The filter and the cursor are one `WHERE` clause.
9. **Sorting by `received_at` alone.** Ordering by one column while comparing two is how a page
   ends up with a row missing from the middle: the `ORDER BY` has to be the same total order the
   cursor is a prefix of — `(received_at, id)` in both places, and in the index.
