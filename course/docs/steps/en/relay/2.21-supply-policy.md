# Supply chain policy: licence allowlist and a default-deny unsafe budget

## WHY

Everything this service ships is written by somebody else. `relay` has 202 entries in `Cargo.lock`
and one of them is this project; every other line is a crate that some person publishes, under a
licence some lawyer has an opinion about, from a source nobody in this repository chose. That is not
a problem to be solved — it is the deal — but it is a set of decisions, and a decision that is not
written down is a decision that gets made accidentally by whoever adds the next dependency at
11 p.m.

Two of those decisions are this step, and both are the same shape: **the default is deny, and the
exceptions are named**.

The first is a **licence allowlist**. The failure it prevents is not a lawsuit; it is the quiet one.
A crate arrives under a copyleft licence that this service cannot ship, everything compiles, the
tests pass, and the problem surfaces in a release review three months later — when the dependency is
load-bearing and the fix is a rewrite. A closed allowlist turns that into a build failure on the
commit that added it, which is the only moment at which the decision is cheap.

The second is the **`unsafe` budget**, and it is where `unsafe/budget@aware` sits: not "we never
write `unsafe`" as a promise in a coding guideline, but `#![forbid(unsafe_code)]` at the crate root,
so the compiler refuses it. The library and the binary are two crate roots, and an attribute in one
says nothing about the other — a budget that covers half the code is a budget with a hole in it. The
`aware` half is knowing what the attribute costs and where you would have to go if you needed the
exception: a dependency's `unsafe` is *not* covered by this (it is `forbid` for **this** crate), and
the way to spend the budget deliberately is a written justification, a measured need, and an
`#[allow]` that a reviewer can see — never a silent one.

Two neighbours, and neither is this step. `repo/toolchain-pinning@apply` (`mailer/1.2-toolchain`,
`relay/2.1-project-skeleton`) pins *what compiles* this project — the compiler, the edition, the
formatting, the lints. This pins *what goes into it*, and the pinning mechanisms are different in
kind: a toolchain file is about the machine, a policy file is about other people's code.
`ci/pipeline@apply` (`mailer/1.3-ci`) is where a policy like this one gets *run*, and the answer for
this step is deliberately smaller: a policy file is readable offline by anybody, so the step is
judged by reading it, and the tool that enforces the whole graph is a gate that stays a *should*
until it is installed everywhere.

## TASK

The scaffold put one file in place, and it is the deliverable: `deny.toml` — the policy, with every
value that is a decision left empty.

### `deny.toml`

Three sections, and each one answers a question that has an answer today and nobody's answer
tomorrow:

- **`[licenses] allow`** — the closed list of licences this project accepts, as SPDX *expressions*
  rather than words: `MIT OR Apache-2.0` is satisfiable by either, `A AND B` needs both, and
  `Apache-2.0 WITH LLVM-exception` is a licence in its own right. `confidence-threshold` is how sure
  the tool has to be that it read a licence file as that licence;
- **`[bans]`** — `wildcards = "deny"` (a `*` requirement is a dependency nobody can review),
  `multiple-versions = "warn"` (two versions of `syn` cost build time and change nothing about what
  this service ships), and `deny = [...]`: the crates that must not appear in this tree whatever
  brings them in. For this service they are the system-linked TLS stacks: the client is hand-written
  (`relay/2.7-outbound-client`) and has no TLS backend at all, so one arriving through a transitive
  dependency is a decision that should be made out loud;
- **`[sources]`** — `unknown-registry = "deny"`, `unknown-git = "deny"`, and
  `required-git-spec = "rev"`: a crate from a registry nobody named, or from a git URL nobody named,
  is a crate with no review process behind it, and a git dependency on `branch = "main"` is a
  dependency that changes under the build.

### `src/lib.rs` and `src/main.rs` — the `unsafe` budget

One attribute at each crate root: `#![forbid(unsafe_code)]`. This project has two crate roots, so it
needs both, and the spec checks both.

### What the spec judges, and what it deliberately does not

`cargo-deny` is not installed on every machine, and a gate that cannot run must never turn a good
step red — that is the `?deny` *should* gate of this step's metadata, and it stays a should-gate
until a later milestone. What the spec does instead is judge the policy **offline**, on the machine
that is running it:

1. the policy parses, the allowlist is not empty, `[sources]` denies, `[bans]` has a real ban list —
   a file whose values are `TODO`s says nothing;
2. **the allowlist covers the tree.** The spec reads `Cargo.lock`, finds each crate's manifest in the
   copy cargo extracted into its registry cache, and checks every declared licence against the
   allowlist using the same expression rules the tool uses (including `OR`/`AND`/`WITH` and the
   deprecated `/`). It refuses to accept a check that judged almost nothing, so a moved registry
   cache is a failure rather than a silent pass;
3. **the bans hold today**: a crate the policy bans is not in the lock file;
4. **the budget is stated and empty**: both crate roots carry the attribute, and the number of
   `unsafe` keywords under `src/` — comments and the attribute's own spelling taken out — is zero.

Where the spec measures a *structure* rather than a behaviour, it says why in the file
(authoring.md §6.6): a policy file is not something a running service can be asked about, and `spec/`
is read-only, so the alternatives — writing a deliberately unsound file into the learner's tree to
watch the compiler refuse it, or starting `cargo metadata` inside `cargo test` — cost more than the
check is worth.

## DONE WHEN

- `kiln run relay/2.21-supply-policy` — the spec passes (five cases: the policy's own shape, the tree
  against the licence allowlist, the bans against the lock file, the `unsafe` budget, and the
  expression reader itself)
- `kiln check relay/2.21-supply-policy` — every must gate is green; `?deny` reports itself as not
  runnable rather than as a failure, which is what a should-gate is for
- `kiln doctor` names `cargo install cargo-deny --locked` if the tool is missing (the install command
  belongs on that line, not in a paragraph)
- with `cargo-deny` installed: `cargo deny check licenses bans sources` is clean on this tree, and
  adding a dependency under a licence the allowlist does not name makes it fail — that is the
  mutation that proves the file is wired to anything
- `cargo check -p relay` fails with `unsafe_code` denied if you put an `unsafe { }` block anywhere
  under `src/`, and the failure names the crate root that forbade it

## TRAP

1. **An allowlist copied from a blog post.** A licence nobody in this project has read is an
   accidental permission: `allow = ["MIT", "Apache-2.0", "GPL-3.0"]` passes every check in this step's
   spec and is a decision nobody made. The list is short because each entry is an answer.
2. **`unknown-registry = "warn"`.** The default. It prints a note for a crate from a registry nobody
   named and exits zero — which is exactly the state a policy exists to end. `deny` or nothing.
3. **A ban that is already violated.** `deny = ["openssl-sys"]` while something pulls it in is a
   policy nobody read; the spec's third test is what catches it, and the answer is to remove the
   dependency or remove the ban, deliberately.
4. **`#![forbid(unsafe_code)]` in `lib.rs` only.** The binary is a second crate root, and the
   attribute does not reach it: `unsafe` in `main.rs` compiles happily while the library looks
   protected. Two roots, two attributes.
5. **Confusing this budget with a dependency's.** `forbid(unsafe_code)` is this crate's rule. `serde`
   contains `unsafe` blocks, will continue to, and is not what this attribute talks about — a supply
   chain answer to that question is a different one (auditing what you depend on), and pretending the
   attribute covers it is how a project ends up believing something untrue about its own build.
6. **`confidence-threshold` lowered to make a check pass.** It says how sure the tool has to be that
   a licence *file* is the licence it thinks: turning it down makes the check green by making it
   guess, and the guess is the thing the check was for.
7. **A licence expression read as a string.** `MIT OR Apache-2.0` under an allowlist holding `MIT` is
   *fine* — the project takes it under MIT. A check that greps for the whole expression fails on
   crates that are licensed more permissively than the policy, and the fix people reach for is to
   widen the allowlist until it means nothing.
8. **A git dependency added during an incident.** `git = "…"` with no specifier tracks the default
   branch: yesterday's build and today's are different code, and no reviewer saw the difference. If
   it must be a git source, pin the revision — which is what `required-git-spec` is for.
