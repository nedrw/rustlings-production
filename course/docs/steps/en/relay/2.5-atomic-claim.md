# Claim work atomically: FOR UPDATE SKIP LOCKED

## WHY

`mailer/1.15-idempotent-delivery` already claimed a row before sending it, and this step does not
re-explain that state machine — what it adds is the part that step could get away without: a claim
that eight workers can run at the same time. The queue there held one message at a time; here a
batch, taken by whoever gets to it first, with the row itself saying who holds it.

An accepted event is a debt: every endpoint its tenant registered is owed one delivery, and that
debt has to survive a restart. So the queue is a table, and the worker is a query. The obvious query
is two statements — read the rows that look free, then mark the ones you took — and it is wrong in a
way that only shows up when it matters:

- **two workers read the same rows.** Both see `pending`, both decide those rows are theirs, both
  send. The subscriber receives one business event twice, and it cannot tell a duplicate from a new
  event unless *it* deduplicates. During an incident, when extra workers have just been started, is
  exactly when this happens;
- **a lock taken too early stops everything.** `for update` without `skip locked` makes the second
  worker wait for the first one's transaction, so throughput is one worker no matter how many you
  run. A lock held for the length of an HTTP request is a lock held for seconds;
- **a worker that dies holds its rows forever.** A claim that is only a state change and not a
  *lease* means `kill -9` leaves rows in `claimed` with nobody to finish them: one subscriber stops
  receiving anything, and nothing in the table says why.

The claim is therefore one statement, and it is the whole step: the database picks the work, stamps
who holds it, and answers with what was taken — all before any worker gets an id it could act on.

## TASK

The scaffold added `src/claim.rs`: the constants, the types, and five signatures with `todo!()`
bodies. The table, the module declaration and the five implementations are yours.

This step has no HTTP surface and no worker loop on purpose: what a *claim* means is judged on its
own here, and `relay/2.6-at-least-once` is where a claim is sent to a subscriber. The spec writes its
own delivery rows for that reason — the fan-out that creates them is the next step's.

### `migrations/0005_deliveries.sql`

One table, `deliveries`, one row per unit of work, with the columns the claim and the state machine
need. The names below are the contract — the spec reads the table with `psql`:

- `id uuid primary key`;
- `event_id uuid not null references events (id) on delete cascade` and `endpoint_id uuid not null
  references endpoints (id) on delete cascade`: a delivery without its event or its subscriber is
  not work, it is an orphan;
- `state text not null default 'pending'`, one of `pending`, `claimed`, `sent`, `retrying`, `dead`;
- `attempts integer not null default 0`: how many attempts have already **failed**;
- `next_attempt_at timestamptz not null default now()`: the earliest instant this row may be taken;
- `locked_by text`, `locked_at timestamptz`, `lease_expires_at timestamptz`: who holds it and until
  when. All three are null when nobody does;
- `last_error text`: the last failure, for a person;
- `created_at timestamptz not null default now()`;
- **one unique constraint** on `(event_id, endpoint_id)`, and one index in the order a claim reads
  (`next_attempt_at`, then `id`). The order of the index is the order of the `order by`, or the
  database sorts every delivery the tenant has ever been owed, once per tick.

### `src/lib.rs`

Declare the module: `pub mod claim;`.

### `src/claim.rs`

- `claim(pool, worker, limit, lease)` — **one statement**. Take up to `limit` rows that are
  `pending` or `retrying` with a `next_attempt_at` that has passed, oldest first, and only rows
  nobody else holds; stamp `state = 'claimed'`, `locked_by`, `locked_at` and
  `lease_expires_at = now() + lease`; answer with the work. `select … for update skip locked` inside
  the `update` that stamps the rows is what makes the two halves one decision.
- The answer is a `Claimed` per row: the delivery id, `attempts`, the **target** and the **event**.
  Joining them into the claim's `returning` clause is one statement per tick instead of one query
  per row, and it removes the window in which the row could change between the two.
- `release(pool, delivery, worker)` — hand a claim back: the row is `pending` again, for whoever
  comes next. Only the worker named in `locked_by` can do it, and it answers whether a row moved.
- `mark_sent(pool, delivery)` — the subscriber took it: `sent`, and no locks left. Only a `claimed`
  row moves, so a late worker cannot resurrect a delivery somebody already finished.
- `mark_retry(pool, delivery, why, next_attempt_at)` — a failed attempt: `retrying`, `attempts + 1`,
  `last_error = why`, `next_attempt_at` as the caller says, no locks left. The instant is a
  parameter because *how long to wait* is a policy this step does not own (that is
  `relay/2.8-retry-budget`), and because a test that can pass it can also pass a past instant.
- `mark_dead(pool, delivery, why)` — give up: `dead`, with the reason kept. Terminal, like `sent`.
  The attempt that ended it counts like any other failure, so `attempts` answers "how many attempts
  this delivery failed" whichever state that left it in.
- Every write that moves a row belongs to this module. A second file that knows the column names is
  a second place to forget one.

## TRAP

1. **Read, then write.** `select id … where state = 'pending'`, then `update … where id = any($1)`,
   is two decisions with a gap between them, and every worker in that gap picks the same rows. The
   spec's eight workers are the reproduction: the same delivery comes back from two of them, and
   nothing in the service says so — the subscriber simply receives the event twice.
2. **`for update` without `skip locked`.** Correct, and serialised: the second worker waits on the
   first one's lock instead of taking the next row. The spec's union comes back short — the workers
   are queued behind each other, and a slow subscriber (an HTTP request inside the transaction)
   makes every worker as slow as the slowest one.
3. **A lock held across the delivery.** `begin; select … for update; … send the event …; commit;`
   holds row locks for the length of an HTTP request. The claim is one statement precisely so no
   lock outlives the claim itself.
4. **`next_attempt_at` ignored.** Taking a row whose instant has not arrived throws away the promise
   the service made to a subscriber that asked for room: it is hammered while it recovers, and the
   retry history stops meaning anything. The spec's not-due rows must stay `pending`.
5. **`retrying` left out of the claimable states.** Then a failure is a delivery that is never tried
   again — the row is not `claimed`, so it is not stuck in a worker, and it is not `pending`, so no
   claim ever sees it. Silently, from the first failure on.
6. **An outcome recorded without a claim.** `update deliveries set state = 'sent' where id = $1` with
   no `state = 'claimed'` guard lets a worker that lost its claim overwrite what its successor is
   doing — and lets a late answer move a row out of `sent` or `dead`. The spec calls `mark_sent` on a
   row nobody claimed and expects `false` and no change.
7. **`attempts` grown by the claim.** If the claim counts the attempt, a delivery that succeeds on
   the fifth try has burned the whole budget of a delivery that failed four times, and the retry cap
   starts burying deliveries that are only slow. `attempts` grows where a failure is recorded.
8. **No lease, or a lease nobody reads.** A worker killed between the claim and the answer leaves
   rows in `claimed` with no worker behind them: the subscriber stops receiving events, and the table
   gives no clue about who to blame. `lease_expires_at` is what makes the recovery possible at all —
   reclaiming an expired lease is `relay/2.15-shutdown-leases`.
9. **A fan-out that can run twice without noticing.** Every part of the claim can be right and the
   subscriber still receives one event twice, because two delivery rows exist for one `(event,
   endpoint)`. `unique (event_id, endpoint_id)` is what makes a retried fan-out a no-op — the spec
   inserts the duplicate and expects the database to refuse it.
10. **An index in the wrong order.** `(state)` alone, or `(id)`, leaves the claim sorting the
    customer's whole history once per tick: correct answers, a cost that grows with the tenant, and
    no test that would notice — which is why this step's spec reads `pg_indexes`.
