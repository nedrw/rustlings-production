# Ship it without dropping an event: probes and migration order

## WHY

Every step so far ends with one instance of this service running. A deployment is not that. A
deployment is *a sequence of instances*: the new one starts, becomes able to serve, the load balancer
starts sending it traffic, the old one is asked to stop, it finishes what it is holding and exits —
and for some window both of them are running against the same database, with the same schema, at the
same time. Nothing in twenty-one steps was about that window, and everything that goes wrong in it
goes wrong in one of two ways.

**The first is what "ready" means.** A process that answers `200` on `/readyz` because its database
answered *some* query is a process an orchestrator will send traffic to. If its schema is not in the
database — because the migration has not run, because it half-ran, because this instance was pointed
at the wrong database — every one of those requests fails, and the failure is an outage the
orchestrator caused with a green light. Liveness and readiness are two different questions and the
distinction only exists if readiness is about something the process can be *wrong* about:
`/healthz` is "this process is running" (and must never touch the database — a process restarted
because its database blipped loses the attempts it is holding, `relay/2.15-shutdown-leases`), and
`/readyz` is "the schema I was built for is here, so traffic to me is going to work".

**The second is the order, and the direction the compatibility has to run.** The new instance applies
the migration; the *old* instance is still serving while it does. So:

- **migrate before you say where you listen**, and say which schema you are on before you say where
  you listen. That single line in the log is the whole startup contract, and it is what makes
  `readyz` trustworthy rather than hopeful;
- **the migration must be compatible with the code that is already running**, not with the code that
  is about to run. The old binary does not know about the new column and must not need to; it writes
  the column list it was compiled with, and that write has to be legal against the new schema. A
  migration that renames a column, drops one, or adds one that is `not null` without a default is a
  migration that turns the dual-version window into an outage — in the window, the *old* code is the
  one that breaks, and it breaks on a database that looks fine;
- **a process must not refuse to start because the schema is from the future.** This is the one
  counter-intuitive rule here, and it is what makes a rolling upgrade possible at all: the moment the
  new instance migrates, the schema has a migration the old instance has never heard of. A binary
  that treats that as an error exits — every old instance dies the instant the new one starts, which
  is a worse outage than the one rolling upgrades exist to avoid. That is why `Db::migrate` sets
  `ignore_missing`, and why the safety is *not* in that flag: it is in the migrations being additive,
  which is `relay/2.23-online-schema`'s whole subject.

The three neighbours, and their boundaries: `release/container-image@apply` (`mailer/1.21-container`)
builds the thing that gets deployed and is where the probes are *wired* (a `HEALTHCHECK` and a
readiness probe in a manifest), while this step is about what they must answer. `db/migrations@apply`
(`mailer/1.9-postgres`, `relay/2.1-project-skeleton`) established "connect, migrate, then serve", and
this step is the part that lesson left out: *serve what, to whom, and who watches*. And
`ops/runbook-drill@apply` (`mailer/1.22-runbook`) is the drill you reach for when a rollout goes
wrong; the next step makes the schema change itself safe, and the step after that drills the modes
this service degrades into.

## TASK

The scaffold put two things in place: `migrations/0010_deliveries_endpoint_idx.sql` — the change this
rollout is rolling out — and `src/readiness.rs`, with the types and `todo!()`.

### `migrations/0010_deliveries_endpoint_idx.sql` — the change being deployed

Read it. It is the interesting half of the step even though it is finished, because it is the shape
every migration from here on has to have:

- **`-- no-transaction` on the first line**, and `create index concurrently` under it. A
  `CREATE INDEX CONCURRENTLY` cannot run inside a transaction (the spec asks the database to prove
  that), and `sqlx` runs a migration inside one unless the file's first line says otherwise. The pair
  is what makes the index build *online*: a plain `CREATE INDEX` takes an `ACCESS EXCLUSIVE` lock on
  `deliveries`, and every worker in every process — including the old instance that is still
  delivering during the window — stops writing until it finishes;
- **it only adds.** An index changes no column and no query's meaning, so the old binary keeps
  working against it, which is the property that makes the window safe;
- it is the index the per-tenant claim of `relay/2.14-backpressure` reads: the claim finds one
  tenant's claimable rows with a subquery on `endpoint_id`, and without an index in that shape the
  planner walks other tenants' floods before it finds them.

### `src/readiness.rs` — what "ready" means

`Schema` is what the database's own record says about the schema this binary needs: `Current`,
`Ahead` (a rollout in progress, and **ready**), `Behind` (**not** ready), `Unreachable`. The
`probe` function is yours: one query against `_sqlx_migrations` that answers all three questions —
is the database there, which version does it record, has it ever been migrated — and a `case` that
keeps "no schema yet" from looking like "no database". The distinction is the point: one of them
sends an operator to the wrong system.

`Display` is already written and it is the sentence that ends up in a log line and in a `503` body,
so both places say *which* version is applied and *which* one is needed. "Not ready" without those
numbers is a page nobody can act on.

### `src/db.rs`, `src/http.rs`, `src/logging.rs`, `src/main.rs`

- `Db::migrate` sets `ignore_missing` on the migrator: a migration the database records and this
  binary does not know about is a rollout in progress, not an error. The doc comment on the method
  says what makes that safe, because the flag on its own is not what makes it safe;
- `/readyz` asks `readiness::probe` on every request and answers `503` with the schema sentence in
  the body when the answer is not ready. It no longer asks only "does the database answer"; `Db::ready`
  is gone, and the question it asked is a strict subset of the one that replaced it;
- `logging::announce_schema` is one line, printed *before* the line that says where the process
  listens. `main.rs` calls it between building the state and serving;
- `src/lib.rs`: the module the scaffold added has to be declared.

### What the spec judges

| the test | the claim |
| --- | --- |
| `readiness_is_about_the_schema_not_about_the_database_answering` | one running process, moved through a half-applied schema, back to current, then to a schema from a *newer* release, then to a database that is gone: `503`, `200`, `200`, `200` (and a second process starts against it), `503` — with `/healthz` `200` throughout |
| `the_schema_is_announced_before_the_port_is` | the log line that names the schema version comes before the line that says where the process listens |
| `a_process_that_cannot_reach_its_schema_never_says_where_it_listens` | a process pointed at a database nobody is on exits `1`, names the database, and never announces a port |
| `the_second_instance_is_ready_while_the_first_one_serves` | two instances on one database, both ready, twelve events through either with no `5xx`, one migration row per embedded migration, the first instance stops with `0`, the second keeps serving |
| `the_previous_release_still_writes_rows_this_one_delivers` | an `insert` that names only the columns of `relay/2.5-atomic-claim` lands in the new schema, the columns this release added are `NULL` on it, and the worker picks it up and attempts it |
| `the_migration_that_grew_the_schema_was_applied_online` | the index is valid and keyed on the endpoint; `create index concurrently` inside a transaction is refused *by this server*; the newest migration file declares itself non-transactional and builds concurrently |

One honest limit, written into the spec as well: both instances are this binary, so the spec cannot
show two *releases* talking to one schema. What it can show is the half that a rolling upgrade turns
on — the schema changes under a running process, the process keeps serving, and a row written the way
the previous release wrote it still lands and still gets delivered.

  indexrelid = 'deliveries_endpoint_claimable_idx'::regclass` is `t`

## TRAP

1. **A readiness probe that only pings the database.** `select 1` is true on an empty database, on a
   half-migrated one, and on one migrated by a release from next year. The probe has to be about the
   schema, because the schema is the thing this process can be *wrong* about.
2. **Caching the probe's answer from startup.** It is the natural optimisation and it makes the probe
   report a database that no longer exists — a migration that is rolled back, a failover to a replica
   that is behind, a database that was restored from a backup. Ask on every probe; it is one query.
3. **A probe that fails *closed* on a transient error, with no numbers in the body.** "Not ready" with
   no version in it is a page an operator cannot act on: the difference between "the migration has not
   run" and "the database is gone" is exactly the `case` in `probe`.
4. **`/healthz` that checks the database.** It looks more thorough and it is the opposite: a database
   blip then restarts every instance, and every instance loses the deliveries it was holding
   (`relay/2.15-shutdown-leases`). Liveness answers "is this process running" and nothing else.
5. **Announcing the port before migrating.** The bind happens first because the kernel has to hand out
   the port before anything can be logged about it — but *serving* must come after the migrations, and
   the line that says where you listen must come after the line that says which schema you are on.
   Otherwise the log of a failed rollout is indistinguishable from the log of a successful one.
6. **A migration that renames or drops.** It is fine for the new code and it breaks the *old* code that
   is still serving: read the previous release's `insert` statements as a contract and add to the
   schema. `relay/2.23-online-schema` is where that gets its floor plan.
7. **A `CREATE INDEX` without `CONCURRENTLY`.** It looks harmless — it is only an index — and it takes
   an `ACCESS EXCLUSIVE` lock on the table: during the window, the old instance's workers block on
   every write until the build finishes, which on a large table is the outage. And `CONCURRENTLY`
   inside a transaction fails outright, which is why the `-- no-transaction` directive is not
   decoration.
8. **Refusing to start against a schema from the future.** This is the trap that feels like
   correctness: the new instance applied a migration the old binary does not know about, so the old
   binary exits — and exits on every replica at once, the moment the rollout begins. A migration may
   be added to; that is the compatibility rule, and `ignore_missing` is the code that trusts it.
9. **Stopping the old instance first.** "Drain, then start the new one" is a window with no process
   ready at all. The order that costs nothing is: start the new, wait for readiness, then stop the
   old — which is what the spec's window test does.
10. **Believing the window is short.** It is not one deployment, it is two: the schema change ships
    separately from the code that uses it (`relay/2.23-online-schema`), so the old release can be
    running against the new schema for as long as the rollout takes — or, if it is rolled back, for
    ever.
