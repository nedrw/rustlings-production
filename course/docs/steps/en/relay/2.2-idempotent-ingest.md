# Accept an event once, however many times it is posted

## WHY

Not the same problem as `delivery/idempotency@apply` (`mailer/1.15-idempotent-delivery`), and the
name is the only thing they share: there the service was the *sender* and had to avoid sending the
same mail twice; here it is the *receiver*, and the duplicate arrives whether it wants it or not.
Nothing about that step is re-explained — what this one adds is an ingest-side key, the uniqueness
that makes a replay answer with the first event, and the difference between a retry and a mistake.

Every sender of webhooks retries, and every one of those retries is a request this service has to
survive rather than a request it can refuse. The connection dropped after the request was handled
but before the answer arrived; a proxy timed out; the sender's process was restarted mid-send.
From the sender's side that is one event. From this side it is three POSTs, and one `INSERT` per
POST turns one business event into three deliveries to every subscriber: three invoices, three
emails, three charges.

The sender cannot repair this alone, and that is the point: it does not know whether the request
it is retrying was handled, which is *why* it is retrying. Only the sender knows which of its
requests are the same piece of news, so only the sender can name them. That name is
`Idempotency-Key`, and this service's half of the bargain is stronger than "do not store it
twice": a retry has to be *answered*, with the same answer the first request produced — a client
that gets an error for a retry either keeps retrying or gives up on an event that was accepted.

And the name belongs to a tenant. Two tenants both calling their first event `order-1` are two
events, which is why the promise is about a pair, not about a string.

## TASK

The scaffold added `src/events.rs`: the types, and the signature of `ingest`. The table, the route
and the module wiring are yours.

### `migrations/0003_events.sql`

One table, `events`: `id uuid primary key` (generated by this service, never by the caller),
`tenant_id uuid not null references tenants (id) on delete cascade`, `idempotency_key text not
null`, `kind text not null`, `payload jsonb not null`, `received_at timestamptz not null default
now()` — and the constraint that makes "one key, one event" enforceable rather than hopeful. The
spec asks the database directly (`select count(*) from events`, `select payload->>'amount' from
events`), so the names and the `jsonb` type are part of the contract; the constraint is not
written down here because choosing it is the step.

### `src/lib.rs`

Declare the module: `pub mod events;` — until you do, the file is not compiled at all, and
`clippy` cannot see the `todo!()` it still contains.

### `src/events.rs`

Implement `ingest`: `Ingested::Accepted(event)` for the request that stored the event, and
`Ingested::Replayed(event)` for a request that found this tenant's key already taken — where the
event in the replay is the row that is already there, with the `kind` and `payload` sent the first
time, not the ones in the request being answered now.

### `src/http.rs`

- `POST /events`, behind the authentication layer. The tenant comes from the API key; nothing in
the body says who is calling.
- Body: `{"kind": "<what happened>", "payload": {…}}`. `kind` must not be empty and `payload`
must be a JSON object; a body that is not JSON at all is a `400`, because that is the caller's
mistake and a panic here takes the process down with it.
- `Idempotency-Key` is required. Missing or empty is `400` — not `401`: this caller *has* a valid
API key, and the request is one this API cannot accept. The sentence names the header.
- The answer is `{"id": …, "kind": …, "payload": …, "received_at": …, "replayed": …}`:
  - `201` with `"replayed": false` when this request stored the event;
  - `200` with `"replayed": true` when this tenant had already sent that key, carrying the
    *stored* event.
- Nothing is written before the header and the body have been accepted: a request that is refused
leaves the table exactly as it was.

## DONE WHEN

- `kiln run relay/2.2-idempotent-ingest` — the spec passes
- `kiln check relay/2.2-idempotent-ingest` — every must gate is green
- posting one body twice with one key against a running service answers `201` and then `200` with
the same `id`, and
  `psql -c "select count(*) from events"` answers `1` — while the same key from a second tenant
  gives a second row and a second `id`

## TRAP

1. **Read, decide, write.** `select … where idempotency_key = $1`, and insert when the answer was
   empty, is a race with a window: two retries in flight both read nothing and both insert. The
   spec's row count is 2, and the duplicate is *silent* — nothing in the answer says the event is
   now on its way twice. Make the database the decider instead.
2. **`on conflict do update`.** Overwriting the row on conflict passes "no duplicate row" and
   breaks "the same answer": a client reusing a key for new content gets its old event silently
   replaced. The spec's second POST sends a different `kind` and asks for the stored one back.
3. **An error for a retry.** `409` (or `500`) when the key is taken breaks exactly the client that
   idempotency keys exist for: it will retry, get the same error, and give up on an event this
   service accepted. A replay is `200` with the event.
4. **`unique (idempotency_key)`.** The first tenant to use `order-1` blocks every other tenant's
   `order-1`, and the spec's second tenant gets a duplicate-key error for an event that is new.
   The pair is the key.
5. **`payload text` instead of `jsonb`.** The row then holds `"{\"id\":\"inv_1\"}"`, a
   payload that merely looks like JSON: `payload->>'amount'` fails, and every subscriber that
   filters events parses the payload again by hand. `jsonb` is what makes the column queryable —
   and `select payload->>'amount'` is what the spec asks it.
6. **Storing before validating.** A refused request that already wrote a row leaves behind an event
   no subscriber should ever receive. The spec sends five bodies that must be refused and then
   counts the rows: it expects none of them to have been stored.
7. **An empty `Idempotency-Key` treated as a key.** `Idempotency-Key:` with nothing after it is a
   client that meant to send one: accepting it makes every event of that tenant collide with its
   first.
8. **Deriving the event `id` from the key.** Hashing `(tenant, key)` into the id makes two tenants
   with one key share an identity and leaks the caller's naming scheme into this service's. The id
   is generated here; the key is only ever compared.
