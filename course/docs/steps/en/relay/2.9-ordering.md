# Order per subscriber, concurrency for everyone else

## WHY

A subscriber that is handed the events of one tenant's stream out of order has to sort them
itself, and most of them will not: an `invoice.paid` arriving after the `invoice.voided` that
cancelled it is a subscriber whose state is wrong until somebody notices. So there is a promise
worth making along the delivery route — *one subscriber, one event at a time, in the order the
queue accepted them* — and it is expensive in exactly one way: the moment a subscriber is slow, the
worker that is waiting for it is not delivering anything else.

The cheap versions of that promise are two, and both fail loudly in production:

- **one lock for the whole worker.** The promise is kept and the whole queue is serialized: one
  subscriber that takes four seconds per request makes every other subscriber's deliveries four
  seconds slower. The subscriber that is down does not just hold its own events, it holds
  everybody's;
- **no lock at all, one task per delivery.** The queue moves at full speed and the promise is gone:
  two attempts to the same endpoint are in flight together, and which arrives first is the
  scheduler's decision — which is the same as saying nobody's.

What this step builds is the middle: **a lane per endpoint**. Deliveries to one endpoint are
serialized (in queue order); deliveries to different endpoints run at the same time; and the whole
thing is a map of mutexes rather than one mutex, so the cost of a slow subscriber is paid by its own
endpoint and nobody else. The same mechanism happens to answer a second question — what a burst of
retries looks like from a subscriber that just came back — because a lane is held for the duration
of one attempt rather than one delivery: a hundred deliveries that became due at the same
instant are a *sequence* of requests at one endpoint, not a hundred simultaneous ones.

## RECALL

`outbound/http-client@apply` — `relay/2.7-outbound-client`: one attempt is one request with three
deadlines (connect, read, whole attempt) and a redirect policy; the delivery port
(`relay/2.6-at-least-once`'s `Sender`) is what holds the client, and a failed attempt is a
`SendError` in one of two categories.

`delivery/at-least-once@design` — `relay/2.6-at-least-once`: a delivery is forgotten only when the
subscriber has taken it or the worker has given up on it, and that record says out loud that
**ordering is not promised** — this step is where it becomes a promise, and only per endpoint.

`async/graceful-shutdown@apply` — `mailer/1.14-worker`: work in progress is a future somebody holds,
and dropping it drops the work in it. That is the reason a lane is a guard and not a flag: it is
released by the *drop* of the attempt's future, however that future ends.

## DELTA

Three things are different from the track where these came from, and each one is about the same
fact: a webhook endpoint is somebody else's server, and the queue is shared by tenants who have
never met.

- **the lane is keyed by *endpoint*, not by job.** `mailer/1.14-worker` had one queue and a fixed
  number of workers; here the unit that must not be asked twice at once is one HTTP target, and the
  number of targets is unbounded, so the lock has to be *looked up* rather than held. That is why
  this file is a map of mutexes with a lifetime — and why the map has to forget: a gate kept for
  every URL a worker has ever seen grows with its tenants' history, which is a memory leak with
  somebody else's traffic in it;
- **the breaker from the step before is asked *inside* the lane.** A half-open breaker promises
  "exactly one probe", and that promise is only exact because the lane makes the asks serial: two
  tasks that reached the breaker together would both be the one probe. The lane is taken before the
  breaker is asked, which is a sentence about the two modules that neither of them can say alone;
- **the claim's answer is a set, not a sequence.** `relay/2.5-atomic-claim`'s statement ends in
  `update … returning`, and a `RETURNING` clause has no order: the rows come back in whatever order
  the plan walked them in. A lane is fair — whoever asks first is served first — so the *asking*
  order is the subscriber's order, and this step is where it is restored from the queue's key.

The gates for this step are the same as the last one, but the spec is stricter than anything before
it: it asserts properties of *overlap*, which no earlier step in this track could.

## TASK

The scaffold added `src/ordering.rs` — `Lanes`, `Lane` and `spread` with `todo!()` bodies — and
`tests/support/lanes.rs`, a sender that counts. No new dependency: the lanes are
`tokio::sync::Mutex`es, which the crates already in this build graph enable.

### `src/lib.rs`

Declare the module: `pub mod ordering;`. There is no scaffold line for it (the file is yours), so
until you add it the spec does not compile — that is the failure this course expects here.

### `src/ordering.rs`

- **`Lanes::enter(&self, endpoint) -> Lane<'_>`** — find or create this endpoint's gate, *then* wait
  for it. The map is locked only long enough to clone the gate out of it: holding a map lock across
  a wait would serialize every endpoint in the process behind one attempt, which is the single thing
  this module is not allowed to do. `tokio::sync::Mutex::lock_owned` takes the gate by value, which
  is what lets `Lane` outlive the borrow of the set and hold the gate a waiter is queued on.
- **`Lanes::known()`** — the number of gates the set is keeping. It has to come back down: the
  `Drop` of the last lane is what removes the entry, and "last" has to be a *count*, not a flag —
  a delivery that is already waiting has a copy of the gate, and if the entry were removed under it
  the next arrival would create a second gate for the same endpoint and both would be in the lane.
  Three references is the number to look for: the set's, the lane's own, and the one the permit
  holds.
- **Take the lane before asking the breaker, and hold it until the record is written.** The lane is
  a guard over the whole attempt — the send, the answer, and the write — so it is released by
  `Drop` on every path out, including the ones that return early (a shed delivery) and the ones that
  never finish (a future that is cancelled). Nothing about a lane is a timeout: a lane is held as
  long as the attempt exists, and the attempt's own deadline (`relay/2.7-outbound-client`) is what
  bounds it.
- **`spread(pool, sender, worker, lanes, budget) -> Result<Tick, Error>`** — one turn across every
  endpoint at once: claim a batch, one task per claimed delivery, every task waiting for its own
  endpoint's lane. The sender is an `Arc` because a task owns what it uses; the budget is cloned per
  task on purpose, so the clones share one breaker; and every task is joined even after one of them
  fails, because a turn that walked away from its own attempts would report on rows that are still
  being written.
- **Put the batch back in queue order before spawning anything.** `claim::claim` now carries the
  row's `next_attempt_at` as `Claimed::due_at` (the claim's own `ORDER BY` key), and the batch is
  sorted by `(due_at, delivery)` first. Add the field to `Claimed` — that is a change to a file you
  own, and the claim's signature stays as it is.
- **`src/delivery.rs`**: the per-delivery work becomes the unit the lanes wrap
  (`pub(crate) async fn attempt(…, lanes: &Lanes, …)`, taking its lane first), and
  `tick_with_budget` — whose signature `relay/2.8-retry-budget` pinned — now calls `spread` with a
  fresh set of lanes. Say why in the doc: a turn with lanes of its own is right for a caller that
  runs one turn and waits for it, and wrong for a worker that runs several, because two of those
  would have two lane sets and could be in one endpoint at once.

### `tests/support/lanes.rs`

The fixture is the course's, not yours, and it is the measuring instrument: it counts, per endpoint,
how many attempts are in flight, the highest that count ever was, and the order the attempts
started in. An endpoint can be *held*, and `release` is a pulse — it lets the attempts parked right
now through and keeps holding what arrives next — so a test can walk a queue one attempt at a time
without sleeping.

## TRAP

1. **One mutex for the worker.** The promise is kept and the queue is a single lane: a subscriber
   that takes four seconds per request is four seconds of latency for every other tenant. The spec's
   third case is this exactly — a held endpoint and a fast one, where the fast one has to finish.
2. **A lane keyed by tenant, or by event.** Two endpoints of one tenant are two integrations, and
   one integration's slowness is not the other's problem; meanwhile two events of one endpoint *are*
   the stream that has to keep its order. Key by the target the request goes to.
3. **Holding the lane across the whole turn.** Taking the lock once per turn and running the batch
   under it is the same as one mutex for the worker, with extra steps: the lane has to be held for
   one attempt, released, and taken again.
4. **Taking the lane *after* the breaker.** A half-open breaker lets exactly one probe through, and
   two tasks that arrive together both look like the one probe if nothing serializes the asks. The
   lane is the thing that serializes them, so it is taken first — and the field that keeps it is
   held until the function returns, not dropped at the end of a block.
5. **A map that never forgets.** `gates: HashMap<String, …>` with an entry per endpoint ever seen
   is a leak a tenant can drive: register a new URL every hour and the worker's map grows without
   bound. Removing the entry on release needs a count (a waiter holds the gate too), and removing it
   while somebody waits hands the next arrival a *different* gate — two attempts in one lane.
6. **Holding `std::sync::Mutex` across an await.** The map is behind a `std` mutex because it is
   held for a few instructions, and the *gate* is a `tokio::sync::Mutex` because it is held across
   the whole attempt. Swapping them is either a compile error or a runtime panic — and a blocked
   runtime thread is a worker that delivers nothing at all.
7. **Spawning and not joining.** A turn that returns after the first task fails, or after a
   `select!` on one of them, reports a `Tick` for attempts that are still running: the counters
   disagree with the rows, and the sum of what the operator sees is not the sum of what happened.
   Join every task, then report.
8. **The claim's order, assumed.** `update … returning` has no `ORDER BY` and Postgres does not
   promise one; the batch comes back in plan order, which for a small table often *looks* like id
   order. A lane built on top of that is fair and meaningless: it serves whoever asked first, and
   the first to ask is the plan's choice. Sort the batch by the claim's own key before spawning.
9. **A lane per *delivery*.** Serializing a delivery's own attempts (which the claim already does
   by handing each row to one worker) is not the same as serializing an endpoint's deliveries, and
   a map keyed by delivery id gives every attempt its own lane: nothing is ordered and the map grows
   with the queue.
10. **A held lane with a deadlock in it.** An attempt that takes a second lane (the same endpoint's,
    or another endpoint's) inside its own is a deadlock the moment two attempts do it in opposite
    orders. One lane, taken once, for the duration of one attempt.
11. **Assuming the lane is a global lock.** The lanes live in one process: two workers delivering to
    the same endpoint do not see each other, and the ordering promise is *per worker*. Across
    processes it is a question of partitioning or of a lock in the database (that is
    `relay/2.15-shutdown-leases` and beyond), and a reader who assumes otherwise will be surprised
    by exactly the duplicate they were trying to avoid.
