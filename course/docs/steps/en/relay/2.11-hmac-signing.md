# Sign what you send: HMAC, a timestamp, and a constant-time check

## WHY

A webhook target is a URL, and a URL is not an identity. Anybody who learns one — from a log, a
screenshot, a proxy that logs headers, a repository with an example config in it — can post a body
to it, and the receiver's application has no way to tell that request from a real one. TLS does not
help: it proves what the *server* is and says nothing about who wrote the request. Neither does the
`x-relay-delivery` header, which is a string anybody can type.

The only thing that can is a secret both ends know and nobody else does, used as a **keyed MAC**: a
short tag over the exact bytes of the request, which only a holder of the key can produce. Three
things have to be true for that to be worth anything, and each one is a step somebody skips:

- **the tag has to cover the bytes that were sent.** Signing a re-serialisation of the event, or a
  parsed-and-rebuilt body, produces a signature the receiver cannot reproduce — JSON has many
  spellings for the same value, and the one that arrived is the one that matters;
- **the tag has to be bound to the request it is for.** A tag that proves only "somebody with the
  key sent this body" is a bearer token: it can be lifted from one request and replayed with
  another. The delivery id and the instant are inside the signed material for that reason — the
  instant so a signature *expires*, the delivery so a signature cannot be replayed for a different
  one;
- **the comparison has to be constant time.** A tag comparison that stops at the first byte that is
  wrong tells the other end how much of a guess was right, one byte at a time, and a signature is
  exactly the value an attacker gets to guess at with as many requests as they like. This is the
  one place in this service where `a == b` is the wrong line of code.

This step is also where the secret *comes from*. The worker's request type is
`relay/2.6-at-least-once`'s port, and the secret is looked up by the adapter that is about to send —
not carried through the queue — so that the one value which must never reach a log line stays in the
one component that needs it.

## TASK

The scaffold added `src/signing.rs` — `Secret`, `Window`, `Verified`, `SignatureError`, the
`Secrets` port, `sign`/`verify`/`tags_match` and `DbSecrets`, with the bodies this step is about
answering `todo!()` — and `tests/support/keys.rs`, a `Secrets` store a test fills in by hand. It
also added two dependencies to `Cargo.toml`: `hmac` and `subtle`.

### `src/lib.rs`

Declare the module: `pub mod signing;`.

### `src/signing.rs`

- **The format is one sentence, and the header is the contract.** The signing string is
  `v1.<timestamp>.<delivery-id>.<body bytes>`, the tag is the lower-case hex of `HMAC-SHA256` under
  the endpoint's secret, and the header is the same string with the body replaced by the tag. The
  spec pins a golden vector (the documented input and the exact header it produces), which is what
  lets a receiver in another language check its implementation without reading this one.
- **`sign(secret, timestamp, delivery, body)`** — deterministic, and over bytes: `body: &[u8]`,
  never a value. The instant is a parameter, not `Utc::now()` inside the function, for the same
  reason `relay/2.8-retry-budget`'s budget takes one: a function that reads a clock cannot be
  judged without one.
- **`verify(secret, headers, body, delivery, now, window)`** — the receiver's half, in the order a
  receiver reads its own log line: is this a version I know, is the instant inside the window, is
  the signature *for this delivery*, and only then the tag. Keeping the two instants (the
  `x-relay-timestamp` header and the one inside the signature) one value is part of it: a receiver
  that checked one and hashed the other has a hole exactly the size of a replay.
- **`tags_match(expected, provided)`** — the comparison, delegated to `subtle`'s `ConstantTimeEq`.
  Keep it public: it is the answer to "where does the constant-time bit live" for the next person
  reading this module, and the spec uses it to check that every one-character mutation of a tag
  fails the same way.
- **`Secrets`** — a boxed-future trait for the same reason
  [`crate::delivery::Sender`] is one: a trait's `async fn` is not dispatchable through `Arc<dyn …>`.
  `DbSecrets` is the production implementation: one indexed lookup per attempt on
  `unique (tenant_id, url)`, so a secret rotated in the table is picked up without a restart.
- **Never send what you cannot sign.** `Ok(None)` from a store is a real answer, and the adapter
  turns it into a *permanent* failure: an unsigned request is a request the receiver cannot tell
  from anybody else's, and optional signatures are not signatures. A store that could not be read is
  retryable — the endpoint may be perfectly fine.

### `src/outbound.rs`: the adapter signs

`HttpSender::signing(policy, secrets)` is the new constructor (`new(policy)` stays, and stays
unsigned). In `send`:

- look the secret up **after** building the body, and sign the *same bytes* that go on the wire: build
  `let payload = body.to_string();`, sign `payload.as_bytes()`, and put that string in the request.
  Don't re-serialise for the signature — that is the bug the spec's "another spelling of the same
  JSON" case is about;
- stamp `x-relay-timestamp` with `Utc::now().timestamp()` and `x-relay-signature` with
  `signing::sign(...)`;
- a delivery the sender cannot sign is a failed attempt, not a delivered one: `Permanent` when the
  endpoint has no secret, `Retryable` when the store could not be read.

### `tests/support/keys.rs`

The fixture is the course's: a `Secrets` store over a map, so the spec about the *format* does not
need a database to have a secret. The last test of the spec uses `DbSecrets` and the secret a tenant
was actually given, which is why that step declares `images` in `track.toml`.

  answers a `secret`, and a delivery to that endpoint carries a header that verifies with it

## TRAP

1. **Signing a re-serialised body.** The `serde_json::Value` is signed, then serialised; or the body
   is serialised twice with different writers. The receiver hashes the bytes that *arrived*, so the
   signature only matches while both sides agree on a spelling — which is a property of a JSON
   library's version, not of the protocol. `sign` takes `&[u8]`, and the adapter signs the string it
   sends.
2. **Signing `key || message` with a plain hash.** It looks like an HMAC and it is not one: a hash
   function with a secret prefixed to the input is open to length extension, so a tag for one body
   is a tag for another. Use `hmac` — the crate exists because rolling this by hand is a real
   mistake people make.
3. **Comparing tags with `==`.** It compiles, it is right every time, and it leaks where a guess
   diverged: the comparison stops at the first wrong byte, so the time it takes is a function of how
   much of the tag is correct. `subtle::ConstantTimeEq` is the line of code that fixes it, and the
   spec's shape check exists because a timing assertion would be a flaky test rather than a proof.
4. **A signature with no expiry.** Without the instant inside the signed material, a captured
   request is valid forever, and a receiver that logs it (or a proxy that caches it) hands out a
   bearer token that never expires. Sign the instant, and check it against a window — in both
   directions, because clocks disagree in both.
5. **Two instants, checked once.** The timestamp is in `x-relay-timestamp` *and* inside the
   signature string: a receiver that checks the header and hashes a different value has a hole. Make
   them one value — refuse the request when they disagree — rather than trusting the header.
6. **A tag that is not bound to the delivery.** Checking the tag and not the delivery id inside it
   turns the signature into a bearer token: any signed request for one delivery verifies as any
   other. This is the case the spec's "a signature is for one delivery" test is about.
7. **The secret in a log line.** `#[derive(Debug)]` on a type holding the secret prints it, and the
   line ends up in the log aggregator, the bug report and the screen share. `Secret`'s `Debug` is
   written by hand (`Secret(<redacted>)`) for exactly that reason — keep it that way.
8. **A secret in the request.** Carrying the key on the queue (`SendRequest`) would put key material
   in every structure that touches a delivery, in every `Debug` of one, and in the dead-letter
   table's reasons. The adapter looks it up where it is used, which is also what makes a rotation
   visible without a restart.
9. **Sending unsigned when the lookup fails.** `Ok(None)` means "this service has no secret for that
   endpoint", and sending anyway makes the signature optional — a receiver cannot distinguish the
   unsigned requests the service chose to send from the ones an attacker sent. Refuse, permanently.
10. **A window that refuses its own edges.** `now - timestamp > max_age` and `now - timestamp >=
    max_age` differ by one signature, and the one that is wrong is the one that refuses a request
    a receiver at the boundary would accept. Both edges belong inside, and the spec checks them.
11. **A version that is guessed.** A receiver that verifies `v2.…` against `v1`'s rules is a receiver
    that has already agreed to a scheme nobody specified. Refuse an unknown version, and keep the
    version in the signed material so it cannot be edited in transit.
