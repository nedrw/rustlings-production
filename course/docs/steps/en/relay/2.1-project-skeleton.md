# Rebuild the service shape: typed config, logs, migrations, middleware

## RECALL

`repo/workspace-layout@apply` — `mailer/1.1-workspace`: a library that owns the service and a
`main.rs` that is a shell. `cfg/layered-config@apply` — `mailer/1.4-config`: defaults < file <
environment < flags, `--check-config` that prints the effective settings, secrets reported as set and
never printed. `obs/structured-logs@apply` — `mailer/1.6-logging`: one correlation id per run, one
line per request, a format chosen by configuration. `db/migrations@apply` — `mailer/1.9-postgres`:
connect, migrate, then listen; `/healthz` and `/readyz` answer different questions.

## DELTA

This is the same service shape in a different project, and three things are new here:

* **the middleware has an order, and the order is the point.** In `mailer` the correlation id and the
  request log were applied to one route group and authentication was a check inside a handler. Here
  the id, the log, and authentication are *layers*, and the layers run outside the refusal: a request
  that is rejected for a missing key still carries the id it was given and still appears in the log
  with it. The first thing an operator cannot do in a service that got this wrong is follow the
  refused requests;
* **the schema is multi-tenant from the first migration.** `tenants`, `endpoints`, and the rule that
  a row belongs to exactly one tenant. You will not add `tenant_id` later: `mailer` taught the
  authorization boundary after the data model existed, and that is the version of it we are not
  repeating;
* **the gates are stricter and the hints are gone.** `clippy@2` is on from this step — no `unwrap`,
  no indexing, no `panic` outside tests, in every non-test target. There is no scaffold for the
  service code: the stubs are signatures, and what fills them is yours.

`relay` is not `mailer` with a new name. Events arrive by POST, they are stored before they are
answered, and the delivery machinery — retries, ordering, dead letters, signatures — is what the next
twenty-three steps build. This step is the foundation those steps will not have to revisit.

## TASK

- Split the crate the way `mailer/1.1` did: `src/lib.rs` owns the modules, `src/main.rs` only
  decides the order of startup and the exit code.
- Implement the configuration layers (defaults < file < environment < command line), the
  `--check-config` report, and the rule that a connection string is reported as `set`, never printed.
- Implement structured logging with one run id, both formats, and a startup line an operator (and a
  test) can read the bound address out of.
- Implement the database layer: one pool, migrations embedded in the binary, a ready probe, and the
  tenants this configuration names seeded at startup (idempotent — a rotated key must go live on the
  next restart).
- Implement the HTTP surface with its layers in this order: correlation id, request log,
  authentication, handler. `/healthz` and `/readyz` are public; `/endpoints` is not.
- Implement `POST /endpoints` (a URL in, an id and a *generated* signing secret out) and
  `GET /endpoints` (the caller's own endpoints, never a secret), with a 404 and a 405 that a client
  can read.

## DONE WHEN

- `kiln run relay/2.1-project-skeleton` — spec passes
- `kiln check relay/2.1-project-skeleton` — all must gates green
- `RELAY__DATABASE__URL=… RELAY__BOOTSTRAP__TENANTS=acme=… cargo run -- --check-config` — the
  effective settings are printed, the secret is `set`, and nothing binds

## TRAP

1. **Authenticating inside every handler.** It works, and it makes the log line for a refused
   request impossible: the layer that writes the line is *inside* the one that refuses, so a 401
   never reaches it. The spec sends a request with an id and looks for that id in the log.
2. **A secret that is validated in the route but a secret that is *stored* in the clear.** Compare
   hashes, always, and look the hash up: the key never needs to be recoverable, and storing it that
   way is what makes a leaked database a leaked set of credentials.
3. **`unwrap()` on the request body.** With `clippy@2` that is a gate failure rather than a review
   comment, but the reason it is a gate is the runtime: a malformed body from a stranger must be a
   400, not a panic that takes the process with it.
4. **Seeding tenants non-idempotently.** `INSERT` on every start turns a restart into a duplicate-key
   failure, which is exactly when a restart is least welcome.
