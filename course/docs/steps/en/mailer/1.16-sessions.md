# Sessions and authentication: cookies versus API keys

## WHY

Everything this service has answered so far was about an *address*: is it free, is it confirmed, has
it been told. None of those questions was about a person, and the moment one route is about somebody's
own data, the service needs a second idea: a credential it issued to somebody it already checked, and
which it can check again on every request.

A **session** is that credential. It is a random value the service hands out once, remembers the hash
of until it ends, and accepts in one of two places:

- `Set-Cookie: session=…` is the browser's transport. The attributes are the design: `HttpOnly` keeps
the value away from scripts, `SameSite` keeps it away from other sites' requests, `Path=/` says where
it is sent, and `Max-Age` says for how long;
- `Authorization: Bearer …` is a program's transport: one header, no browser semantics, the same
token, and the same lookup on the server.

Four decisions come with that, and each of them is a way to get it wrong:

1. **the token is random, and the database stores only its digest.** A session token is a secret, and
a secret in a database is a secret every backup, replica and support dump gets to keep. It is hashed
with **SHA-256**, not Argon2 — and the difference from step `mailer/1.11-signup` is the point: a
password is guessable and needs a slow hash, a token nobody can guess does not, and a slow hash on
every request would make authentication itself the bottleneck;
2. **a session ends, and the *statement* that reads it decides that.** `revoked_at IS NULL AND
expires_at > now()` travels with every lookup, exactly as the confirmation window does in step
`mailer/1.12-token`. The database's clock decides, one statement decides, and there is no window
between "reading whether this is still good" and "acting on it";
3. **a login opens a new session and adopts nothing.** The classic version of getting this wrong is
*session fixation*: a service that takes the cookie it was given and blesses it on login. The fix is
not a check, it is a direction — the token comes from the server, always;
4. **being confirmed is part of being allowed in.** A subscriber whose address was never proven is
not somebody the service can authenticate yet; letting them in turns confirmation into decoration.

## TASK

The scaffold added the pieces, and the hole is one function:

- `migrations/0003_sessions.sql` — the `sessions` table: `token_hash` (unique), `created_at`,
`expires_at`, `revoked_at`, and `subscriber_id` with `ON DELETE CASCADE`. A migration that has run
anywhere is never edited: this is 0003;
- `src/session.rs` — the token type, its digest, and the three operations (`open`, `authenticate`,
`revoke`). **`Token::issue` answers zero bytes every time**: every session this service ever opens
has the same token, and whoever learns it holds all of them. That is session fixation, and no amount
of reading the routes will show it — which is why the spec logs in twice;
- `tests/support/service.rs` — a harness for a *process* with a client that can send a `Cookie` or an
`Authorization` header and read `Set-Cookie` back. The previous fixture drives the service in
process, which is exactly the shape that cannot test a header;
- `sha2` in the dependencies (inside the `kiln:scaffold:begin` block): the digest above needs a hash,
and the course's first *fast* one.

### `src/session.rs`

`Token::issue` has to ask the system for randomness — `SESSION_BYTES` bytes, as lower-case hex, the
same spelling as a confirmation token — and report `Error::TokenGeneration` when it cannot. There is
no fallback on purpose: a token this service invented is a token an attacker can invent.

### `src/login.rs` (new)

`Credentials` — an email and a password, raw — and
`log_in(pool, credentials) -> Result<(Token, Email), Error>`, which:

1. parses the address and the password (step `mailer/1.10-domain-types`: the parses come first);
2. reads the subscriber's `id`, `password_hash` and `status` by address;
3. verifies the candidate against the stored PHC string with `Argon2` — never a string comparison,
   and the answer to "no such address" is the same `401` as "wrong password";
4. refuses a subscriber who is not `active` with a `403` — the password was right, the account is not
   usable yet;
5. opens a session (`session::open`) and answers the token and the address.

### `src/http.rs`

- three routes: `POST /login`, `POST /logout`, `GET /me`. `/login` answers with the cookie
  (`{SESSION_COOKIE}={token}; Path=/; HttpOnly; SameSite=Lax; Max-Age=…`) and the subscriber in the
  body; `/logout` revokes the row *and* clears the cookie (`Max-Age=0`); `/me` answers with the
  address the session belongs to;
- a `credential` helper that reads the token from `Authorization: Bearer …` or from the `Cookie`
  header — the cookie is a *list of `name=value` pairs*, not a string that happens to contain the
  token — and a well-formed-but-unknown token is a `401`, while something that is not a token at all
  is the `400` of step `mailer/1.12-token`;
- the status table gains `401` for no usable session, `401` for credentials that do not match, `403`
  for a subscriber who never confirmed; `/me` and `/logout` are `503` without a database, like the
  other routes that need one.

### What the spec judges

| the test | the claim |
| --- | --- |
| a login | `200`, a `Set-Cookie` carrying 64 hex characters with `HttpOnly`/`SameSite`/`Path=/`, and the address in the body |
| one token, two transports | the cookie and `Authorization: Bearer` both answer `200` on `/me`; nothing, and a well-formed token nobody was issued, answer `401` |
| a wrong password, an unknown address | `401`, and no cookie either time |
| a subscriber who never confirmed | `403`, and no cookie |
| a logout | `204`, a cookie that has expired, and the token answers `401` afterwards — with `revoked_at` set in the row |
| an expired session | the row's deadline moved into the past is enough: `401` |
| two logins, and a token the client brought | different tokens every time, the brought one never adopted, and no row whose `token_hash` is the token itself |

## DONE WHEN

- `kiln run mailer/1.16-sessions` — the spec passes
- `kiln check mailer/1.16-sessions` — every must gate is green
- logging in against a running service answers with a cookie you can send back to `/me` by hand
  (`curl -c jar -d '{"email":…,"password":…}' /login` then `curl -b jar /me`)
- `SELECT token_hash FROM sessions` shows a 64-character digest that is *not* the value the cookie
  carries, and two logins leave two rows
- a logout makes the same cookie answer `401`, and `revoked_at` is set on that row

## TRAP

1. **A token that is not random.** A counter, a timestamp, or a value derived from the subscriber's
   address is a token that can be guessed or predicted — and the scaffold's fixed value is the
   degenerate case: every session shares it. The spec's two logins are what catch it.
2. **Storing the token.** A `token_hash` column that holds the token makes every backup, replica and
   `SELECT *` in a support session a set of live sessions. The digest moves the value to a place only
   the client and the memory of one request ever see.
3. **Argon2 on every request.** Hashing the session token with the password hasher looks like the
   careful choice and makes every authenticated request pay tens of milliseconds of work — which is
   the whole reason a session is a token and not the password. Fast hash for high-entropy secrets,
   slow hash for guessable ones.
4. **Adopting what arrived.** Reading a session cookie *before* login and using that row for the
   session after it is session fixation: an attacker who plants a token in a victim's browser is
   logged in as the victim, because the victim's login promoted the attacker's token. A login always
   issues.
5. **Logging out only in the database.** Revoking the row leaves the value in the browser, where it
   is one accidental cache, log line or restore away from working again. The cookie has to be
   cleared with the same response that revokes it.
6. **Forgetting to check the status.** Authentication is "who is this", and *authorization* is "what
   may they do" — but a service that authenticates an unconfirmed subscriber has already answered
   the second question wrongly, because confirmation is the only proof the address is reachable.
7. **A cookie with the wrong attributes.** No `HttpOnly` is a session a cross-site scripting bug can
   read; no `SameSite` is a session another site's form POST can spend (a copy of the *signup* form on
   another origin is enough); no `Max-Age` is a session that lives until the browser closes, or
   longer. `Secure` cannot be set on this build (there is no TLS yet, and a `Secure` cookie that
   never arrives is a login that does not work) — it is the first thing to add in step
   `mailer/1.21-container`, and the TRAP here exists so the omission is a decision rather than an
   oversight.
8. **Leaking which half was wrong.** "No such address" and "wrong password" are one `401`, because
   the difference is a fact about who is registered. This service leaks *some* of that anyway — a
   duplicate signup is a `409` (step `mailer/1.11-signup`) and an unconfirmed login is a `403` — and
   the honest version of the rule is: decide which of those answers is worth the leak, write the
   decision down, and do not leak by accident.
9. **Putting the token in a log line.** A session token in a log file is a session anybody with the
   logs can use — the same rule step `mailer/1.13-email-port` applied to a confirmation link. `Token`
   has no `Display` and a redacting `Debug` so that this one is hard to do by accident.
