# Errors as part of the API

## WHY

A failure that is a `String` can only be printed. The caller cannot tell "the port is taken" from
"the file is missing", so every caller reinvents the same parsing of the same sentence — or, worse,
gives up and retries something that will never work. The error type is as much of an API as the
functions are: it is what other code (a test, a second binary, an HTTP layer in step 1.7) is allowed
to depend on.

Two properties make it worth writing down. A **cause chain**: "cannot read `mailer.toml`" without
the operating system's "No such file or directory" leaves the reader to guess which half is wrong.
And an **exit code**: the shell is a caller too, and a deploy script that cannot tell a typo from an
unreadable file either retries forever or pages someone at three in the morning.

## TASK

The scaffold added the two dependencies (`thiserror`, `anyhow`) and put the failure type in
`src/error.rs`: one variant per way this service can fail, with the source a setting's value came
from. It has no messages, no causes and no exit codes yet — that is this step:

- **Give every variant a message** (`thiserror`'s `#[error("…")]`) and keep the wording the
  previous step's spec already pins: a caller may print it, and the tests compare it.
- **Carry the causes.** The two configuration failures keep what actually happened — the
  `std::io::Error` that stopped the read, the `toml::de::Error` that refused the file — as their
  source, so `error.source()` walks a chain instead of the message flattening it into prose.
- **Rewrite the rest of the service onto this type.** `mailer::parse` and `Config::load` return it,
  the layers construct the right variant instead of a sentence, and `ConfigError`, `Source` and the
  hand-written `Display` implementations from the previous step are deleted.
- **Map the failures to exit codes** in `Error::exit_code`, and keep the table small and honest:
  `2` when the caller asked for something this service does not have (an unknown argument, a
  missing value, a setting value that cannot be used, an unknown setting); `1` when the
  configuration could not be read or parsed. A script that sees `2` knows not to retry.
- **`anyhow` only at the boundary.** `main.rs` may use it: the binary's job is to print and exit, so
  an opaque box of failures is exactly what it wants. The library may not: `anyhow::Error` cannot be
  matched on, so it cannot be the failure type of a service — code that wants to react needs the
  variants.
- **Document what the fallible API returns.** Every public function returning `Result` gets an
  `# Errors` section naming the variants a caller has to handle; `docs:public` is a must gate from
  this step on and it denies `missing_errors_doc`, so a documented signature is part of "done".

## DONE WHEN

- `kiln run mailer/1.5-errors` — the spec passes
- `kiln check mailer/1.5-errors` — every must gate is green (including `docs:public`)
- `cargo run -- --nope; echo $?` prints the unknown argument and the usage text, and exits 2
- `cargo run -- --config nope.toml --check-config; echo $?` names the file, keeps the operating
  system's reason, and exits 1
- `cargo doc --no-deps` shows an `# Errors` section on `parse` and on `Config::load`

## TRAP

1. **Flattening the cause into the message.** `InvalidConfig { path, message: error.to_string() }`
   compiles, prints almost the same thing — and `source()` returns `None`, so the spec's probe
   crate reports *"a failure that carries a cause has to expose it through `source()`"*. The chain
   is what a caller can walk; a `String` is not.
2. **One exit code for everything.** Returning 2 for a missing configuration file makes a deploy
   script treat an unreadable file as a typo: the spec fails with *"the two kinds of failure must
   not share a code"*.
3. **Letting `anyhow` into the library.** `anyhow::Result` in `Config::load` is the shortest path to
   make the compiler happy, and it deletes the API: nothing outside can match on the failure any
   more. The spec's probe crate then stops compiling, and that compile error *is* the step's
   requirement — `mailer::Error` has to be what `parse` and `Config::load` answer with.
4. **Renaming or reshaping the variants.** The names in `src/error.rs` are what a caller matches on;
   the probe crate compiles against them. If you need a new failure, add a variant — do not fold two
   kinds into one, or the exit-code table loses the distinction it exists for.
