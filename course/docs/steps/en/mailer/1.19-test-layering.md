# Test layering with a real mail server container

## WHY

Every test in this course so far has run against a fake sender, and that was a decision with a price
and a payoff. The payoff: a test can say *what the fake was given*, so "one email per subscriber" is a
claim about a value rather than about a mail server. The price, which this step pays: **the fake is
wrong about everything it does not implement.** SMTP, headers, encodings, the envelope addresses — and
the parts that break in production are exactly those.

So this step adds the top of the pyramid instead of replacing a layer of it:

| layer | what it is for | what it cannot see |
| --- | --- | --- |
| unit (in `src/`) | a policy that is about time (`backoff`, the retry count) | anything about the service |
| the fake (`tests/support/email.rs`) | *what* the service decided to send, and what happens when sending fails | whether a real mail server would accept it |
| the container (`tests/support/mailpit.rs`) | the protocol, the delivered bytes, and a dependency that can really fail | nothing much — which is why there is only one or two of these |

The rule that makes this a *layer* rather than a second way of testing everything: **the fake stays.**
Failure injection — a sender that refuses, a sender that never answers — is a thing a fake is better at
than a container, because it is deterministic and instant. The container earns its place for the three
things only it can do:

1. **the delivered message**, byte for byte: what a mail client would show, including the confirmation
   link a person is supposed to click;
2. **a dependency that is really there** — and, with the new adapter, really *absent*: a mail server
   that is away, and one that accepts a connection and never answers;
3. **the entry point**: the binary, configured the way a deployment configures it, not a state a test
   built by hand.

**Order independence** comes with the same fixture: each test starts its own container, on its own
ports, against its own database, and drops them when it ends. Nothing is shared, so nothing is
order-dependent — and the DONE WHEN below asks for the suite to be run more than once to make sure.

## TASK

The scaffold added the pieces, and the wiring is what is missing:

- `src/smtp.rs` — the adapter T1 ships with: `lettre`, plain SMTP (`builder_dangerous`, which is the
  crate's name for "no TLS on this connection"), a per-conversation deadline, and
  `no-reply@mailer.invalid` as the sender — an address RFC 2606 reserves so that it cannot be a
  working mailbox;
- `tests/support/mailpit.rs` — a mailpit container for one test: SMTP on one published port, an HTTP
  API on another, `messages()`, `text_of(id)`, and a `Drop` that takes the container away. It follows
  the three rules `tests/support/postgres.rs` set: the engine is probed, the image is looked up by
  repository path (a mirror caches it under its own prefix), and every command has a deadline this
  module enforces itself;
- `lettre` in the dependencies, inside the `kiln:scaffold:begin` block.

### `src/config.rs`: two settings

Two settings, built the way step `mailer/1.4-config` builds the others — defaults, file, environment,
report — and added to `--check-config` so a deployment can see them:

```toml
email.smtp_host = …        # a host turns the logging adapter into SMTP; unset keeps the log
email.smtp_port = …        # the port that host listens on
```

`MAILER__EMAIL__SMTP_HOST` and `MAILER__EMAIL__SMTP_PORT` are how a test or a deployment sets them, and
a variable the service does not know is still refused rather than ignored (that is step 1.4's rule, and
a typo in `MAILER__EMAIL__SMTP_HOTS` is exactly the case it exists for).

### `src/lib.rs`

Declare the module: `pub mod smtp;`.

### `src/http.rs`: one place decides

`AppState::start` picks the adapter from the configuration — SMTP when a host is set, the logging
adapter when it is not — and everything downstream is written against the port. That is the whole
payoff of step `mailer/1.13-email-port`: adding a real transport cost one function.

**No host configured is the default, not a mistake.** Every step before this one runs the binary
without a mail server, and their specs read `an email would be sent` out of the log; a service that
refused to start without a mail server would break all of them — and a laptop. The last test in the
spec is there to keep it that way.

### What the spec judges

| the test | the claim |
| --- | --- |
| a signup against a real mail server | the message arrives, to the stored address with a subject, its body carries `/confirm?token=<the token in the row>` — and following that link confirms the subscriber |
| a mail server that is away | `201`, then `confirmation_attempts` reaches 3, `confirmation_sent_at` stays empty, the subscriber stays `pending`, and the claim is released |
| a mail server that accepts and never answers | `SIGTERM` is answered in about ten seconds with exit code **1**, `did not drain before its deadline` in the log, and the send that was in flight named there too |
| no SMTP host configured | the logging adapter still writes `an email would be sent`, once, with the address — every earlier step's tests depend on it |

## DONE WHEN

- `kiln run mailer/1.19-test-layering` — the spec passes
- `kiln check mailer/1.19-test-layering` — every must gate is green (`images` included: it fails
  until the container image is in the local store)
- `cargo test -p mailer --test spec_integration` passes three times in a row, and once with
  `--test-threads=1`: every test owns its container, its port and its database, so the order is not
  part of the contract
- a signup against a running service logs `an email is being sent`, and the message can be read back
  from the mail server's own API — subject, recipient, and the link in the body
- stopping that service while it is talking to a mail server that never answers exits `1` within the
  drain deadline, instead of hanging until something kills it

## TRAP

1. **Deleting the fake.** "We have a real mail server now" is the wrong reading of this step: a
   container cannot be told to fail at the exact message the test cares about, and every failure test
   in the course would become slow and flaky. The fake stays for failure injection; the container is
   for the protocol.
2. **Testing everything through the container.** A layered suite is not "more realistic"; it is
   slower and less precise at the bottom. If a claim can be made against a fake, it belongs with the
   fake — and the top of the pyramid should be a handful of tests that would be meaningless anywhere
   else.
3. **A container the test does not own.** A fixed port, a fixed name or a shared database is how two
   tests pass alone and fail together, and it is also how a suite becomes order-dependent. `podman run
   -p 127.0.0.1::1025` (an ephemeral host port) plus a `Drop` that removes the container is the shape
   that makes order irrelevant — and the DONE WHEN asks for a second and third run because that is the
   only way to notice.
4. **Assuming the image is there.** `--pull=never` turns "the image is missing" into a sentence a
   learner can act on (`kiln images pull`) instead of a registry wait inside a test. A pull that hangs
   is a suite that hangs, and a suite that hangs is a bug report nobody can reproduce.
5. **TLS by accident, or TLS where it cannot work.** `builder_dangerous` is the honest spelling of
   "this connection is in the clear": a loopback test container is the case that is right for, and a
   deployment is not. The alternative mistake is enabling a TLS stack for a container that speaks
   plain SMTP — which fails as a handshake error that looks like a mail server problem.
6. **No deadline on the connection.** `lettre` waits forever by default, so the adapter sets a
   timeout on the transport: without one, a mail server that accepts and then says nothing holds the
   worker — and the drain behind it — until something kills the process. The third spec test is the
   observation, and it is also the first time step `mailer/1.14-worker`'s drain deadline is judged
   from outside the process.
7. **A sender address that could be real.** `no-reply@example.com` is somebody's domain, and
   `no-reply@localhost` is a hostname a mail server will refuse. RFC 2606's `.invalid` is the
   convention for "this address can never work", which is what a placeholder should be.
