# Runbook and the first failure drill

## WHY

Twenty-one steps have produced a service that logs, counts, retries, drains and ships as an image.
None of them produced the thing that decides what happens at three in the morning, when a subscriber
writes "I never got the link" and the person on call has to answer two questions: **is this us, and
what do we do?** That is a runbook — and it is not documentation. Documentation describes a system
that is working; a runbook is instructions for a system that is not, written by somebody who has
watched it fail.

Two decisions shape this step, and both are ways to write a runbook that is worse than none:

1. **a runbook you cannot replay is prose.** "Check that the mail server is reachable" is a sentence
   nobody can test. Every step in a runbook has to be something a person can *do* and then *look at*,
   and the promise at the top has to be checkable by a command — which is why this step's deliverable
   is a drill first and a page second. The command is the same one a responder runs during an
   incident, so the page and the evidence cannot drift apart;
2. **a drill that cannot fail is decoration.** The drill below replays an outage and reports whether
   mail was lost. Run against a mail server that comes back, it says *nothing was lost* — and a drill
   that says that about *every* world is a green light wired to nothing. So the drill has to be run
   twice: once with the outage ending, once with the mail server never coming back. The second run is
   what makes the first one evidence, and it is exactly the case a runbook exists for.

**What this step is honest about**: the drill replays the outage against the in-process adapter of
step `mailer/1.13-email-port`, not against a container. What that costs is the SMTP conversation —
step `mailer/1.19-test-layering` is where that is exercised — and what it buys is an incident that
replays on a laptop, in seconds, without a mail server, in the same command a responder types. The
queue, the claims, the retry budget and the database are the real ones, which is what the promise is
about.

## TASK

The scaffold put two files in place, and each one has a hole that the other cannot fill:

### `tests/support/drill.rs` — the drill

It already starts the service with a mail server that refuses every message (`Recording::fail_with`,
step `mailer/1.13-email-port`), signs a subscriber up and reports a `Report`. What it does not do is
ask the service anything: `replay(Recovery::Never)` answers exactly what `replay(Recovery::ComesBack)`
answers, because `Report` is decided in the file instead of measured from the service. The spec's
second test is the one that notices.

Turning it into a drill means four things, in this order:

1. **the outage has to be real before the recovery means anything.** Wait for the *first attempt to
   fail* — the message has been offered to the mail server and not taken — before you let the server
   come back. A recovery that beats the outage proves nothing about anything;
2. **the recovery follows the drill's argument**: `Recovery::ComesBack` lets the sender through again
   (`Recording::clear_failure`), `Recovery::Never` does not, and the same code path has to handle
   both. The service's retry budget is three attempts inside a few hundred milliseconds
   (`backoff`, step `mailer/1.14-worker`), so "never" is one second away from "back";
3. **the numbers come from the service.** `delivered` is what the mail server took; `given_up` is
   what the service stopped trying to send — a row with nothing in `confirmation_sent_at` and its
   attempts spent. Asking the database is the point: a drill that reports what it arranged to happen
   is a test of the drill;
4. **wait for a fact, not for a number of seconds.** The scaffold sleeps; a drill polls until the
   queue has moved or a deadline passes. A sleep is either too short on a loaded machine or wasted
   time on an idle one, and neither is a statement about the queue.

### `docs/runbook.md` — the page

The skeleton has the five sections an incident needs and the headings a responder reads in order:

- **Symptoms** — what is noticed first, from the outside;
- **Signals** — what to look at, and where. The one that matters here is
  `deliveries_total{outcome="given_up"}` (step `mailer/1.20-metrics`): the number that means *a
  subscriber will never hear from us*. `failed` moving is normal (retries); `given_up` is not;
- **Steps** — what to do, in order, including the one counter-intuitive instruction: *restarting this
  service does not help*, because the queue lives in the database and a claimed message is released
  for the next attempt;
- **Verification** — what "recovered" means, and the command that replays the drill;
- **Escalation** — what to do when the mail server is not coming back today. The queue is bounded, so
  mail *will* be given up on; the honest choice is to stop taking signups and say so.

The `links` gate runs over this page (and every other markdown file in the project): relative targets
have to exist, `#anchors` have to match a heading, and a `TODO` where a target should be is a
failure. **A runbook that points at a file nobody can open is a runbook that gets abandoned at the
first incident**, which is why the gate is structural and offline rather than a link checker that
goes to the network (plan §6).

### What the spec judges

| the test | the claim |
| --- | --- |
| `the_drill_reports_the_promise_kept_when_the_server_comes_back` | the replay accepts a message during the outage, the server comes back, and nothing was lost |
| `the_drill_reports_the_loss_when_the_server_never_comes_back` | the same replay, with the server away for good, reports the loss and counts what was given up — the drill can fail |
| `the_runbook_names_its_sections_the_drill_and_the_signal` | the page has Symptoms/Signals/Steps/Verification/Escalation, names `spec_runbook_drill`, and names the signal that means mail is being given up on |

## DONE WHEN

- `kiln run mailer/1.22-runbook` — the spec passes (both replays, plus the page's structure)
- `kiln check mailer/1.22-runbook` — every must gate is green, `links` included: no placeholder
  targets left, and every relative target resolves
- `cargo test --test spec_runbook_drill` is a command you would be willing to run during an incident,
  and it finishes in seconds
- the page tells a responder, in order: what they are looking at, where to look, what to do, how to
  know it worked, and who to wake up when it does not
- you have replayed the `Never` case once and read its report yourself

## TRAP

1. **A drill that always passes.** `replay` that answers `delivered == accepted, given_up == 0` for
   every world is the most common shape of a written drill, and it is worse than no drill: it turns
   an incident into "the drill is green, so it must be something else". Run the second case; the
   spec does, and it is only expensive the first time.
2. **Reporting what you arranged to happen.** A drill that asserts on the *sender's* record in the
   in-process adapter proves the adapter works. The promise is about the service's own records — the
   row, its attempts, whether it was sent — and that is what the report has to be measured from.
3. **A sleep instead of a wait.** `thread::sleep(500ms)` is the second most common shape. It is the
   fastest green run on an idle machine and a flake on a loaded one, and it teaches the reader that
   the service is a machine with timings rather than one with states.
4. **Writing the page from the implementation.** A runbook written by reading `src/` lists the
   settings and the code paths, which is exactly what the responder *cannot* use at three in the
   morning. Write it from the alert that would page you, then check that the alert exists.
5. **A page that points at things that are not there.** The `links` gate exists because runbooks rot:
   a file gets renamed, a section moves, a dashboard link is left as a `TODO`. The rule the gate
   enforces is the one to write by: **every target is a file in this project, or a URL somebody else
   maintains and you would re-check**.
6. **Escalation as an afterthought.** "Contact the team" is not escalation. What the next person
   needs is: what you already ruled out, what you saw, and what decision you are handing them —
   including the one nobody likes: stop accepting signups, because the queue is bounded.
7. **Believing the drill covers the real mail server.** It replays the queue, not SMTP. When the
   incident is in the protocol (TLS, authentication, rate limits), the drill will be green while
   nothing arrives — step `mailer/1.19-test-layering` is the layer that answers those, and trap 1 is
   the reason you would know the difference.
