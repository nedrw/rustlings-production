# Postgres and migrations: an empty database, up to date before serving

## WHY

Everything so far has been stateless: the configuration is read once, the logs are written, the
HTTP surface answers. The moment this service keeps anything, three questions appear at once, and
they are the subject of this step:

- **Where does the schema come from?** Not from a person with a `psql` prompt and a wiki page — a
  fresh database has to become the database the code expects, with nobody in the loop. That is what a
  *migration* is, and the schema is code: versioned, reviewed, and applied by the service itself.
- **Which artifact owns it?** `sqlx::migrate!` embeds `migrations/` into the binary at compile time
  (`macros` is a feature this step turns on for exactly that). The build that ships has the schema
  and the code that reads it in one file, so a container image cannot run the wrong pair.
- **In what order?** Connect, migrate, and only then bind the socket. A service that answers requests
  before its schema is there is a service answering some of them with a 500.

And one more question that only shows up on a bad day: **is "the process is up" the same as "this
service can serve"?** It is not. `/healthz` stays about the process; `/readyz` is about what a
request needs, and this step introduces the difference because this is the step where the service
first *has* a dependency that can be away while the process is fine.

The whole rest of the track starts here. Steps 1.10–1.18 add tables and queries on top of the schema
you write now, every test from here on gets a database of its own, and the way a database is
configured stays the same until the last step: `MAILER__DATABASE__URL`, or `database.url` in
`mailer.toml`.

## TASK

The scaffold added the `sqlx` dependency and three files, and no behaviour: `src/db.rs` with the
shape of a `Database` whose bodies prove nothing, `migrations/0001_subscribers.sql` with the naming
rule and nothing else, and `tests/support/postgres.rs` — a container-and-`psql` harness the specs
use.
Your job is the code and the schema between them.

### The schema: `migrations/0001_subscribers.sql`

Write one `CREATE TABLE` for the table steps 1.10–1.18 build on. Names and types are part of the
contract (the spec asks `information_schema` for these columns):

| column | type | notes |
| --- | --- | --- |
| `id` | `BIGSERIAL PRIMARY KEY` | |
| `email` | `TEXT NOT NULL UNIQUE` | step 1.11 races two signups on this constraint |
| `name` | `TEXT NOT NULL` | |
| `password_hash` | `TEXT NOT NULL` | never a password: step 1.11 hashes first |
| `status` | `TEXT NOT NULL DEFAULT 'pending'` | `CHECK (status IN ('pending', 'active', 'unsubscribed'))` |
| `confirmation_token` | `TEXT UNIQUE` | nullable: only a pending subscriber has one |
| `confirmation_expires_at` | `TIMESTAMPTZ` | nullable, for step 1.12 |
| `confirmed_at` | `TIMESTAMPTZ` | nullable |
| `subscribed_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | the service's own bookkeeping |

Plus one cross-column rule: `CHECK (status <> 'active' OR confirmed_at IS NOT NULL)` — nobody is
active without having confirmed. Read the TRAP section before you tighten it; the obvious-looking
version of this constraint breaks step 1.18.

The file name is the version: `sqlx` sorts `0001_`, `0002_`, … and records what it applied in
`_sqlx_migrations`. **A migration that has run anywhere is never edited** — the next file is how a
schema changes.

### `src/db.rs`: connect, migrate, be ready

- **`Database::connect(url)`** builds the pool (`MAX_CONNECTIONS`, `ACQUIRE_TIMEOUT`) and
  **establishes a connection before it returns**. `PgPoolOptions::connect_lazy` is the wrong one
  here, and the spec says so: a service that has not talked to its database cannot know it can serve.
- **`Database::migrate()`** runs `sqlx::migrate!("./migrations")` against the pool. It is safe to
  run on every start and from two processes at once — `sqlx` locks and records — and it is not
  optional: this is what makes an empty database the schema this build expects.
- **`Database::ready()`** asks the database a question that only the migrated schema can answer
  (`SELECT 1 FROM subscribers LIMIT 1` is one), **on every call**. It reports the failure as an
  error rather than a `false`, because the reason goes to the log while the probe answers with one
  sentence.
- **`Database::pool()`** hands the pool out for the queries later steps add.

### `src/error.rs`: two more failures

`Error::Database { operation, source }` ("the database could not `connect`/`readiness`") and
`Error::Migration { source }` ("the schema could not be brought up to date"). Both are the
deployment's to fix: exit code `1`, like a broken configuration, and for the same reason — the caller
did nothing wrong and retrying the same command will not help.

### `src/http.rs`: the state, the startup order, and readiness

- **The state carries the database**: `AppState { config, database: Option<Database> }`, built by
  **`AppState::start(config, id)`** — the one place the startup order lives (config → logging →
  connect → migrate → a state), used by the binary *and* by the test harness. `router` and
  `serve_on` take the state instead of the configuration alone.
- **A configured database has to work; a missing one is a choice.** If `database.url` is set and the
  connect or the migration fails, `AppState::start` returns the error and the process exits — before
  anything is bound. If it is not set, the service starts and says so at `warn`: steps 1.4–1.8 stay
true, and `/readyz` is what tells the truth about it.
- **`GET /readyz`**: `200` with a JSON body when the database answers, `503` when there is no
  database or it does not answer. The body stays a sentence a client can branch on — *why* is this
  deployment's business, and it goes to the log at `warn`. `/healthz` keeps answering `200`
  regardless: restarting a healthy process because its database is away is not a fix.

### `src/main.rs` and `tests/support/mod.rs`: the same order, twice

The binary builds the state after logging and serves it; the factory builds the same state in its
thread, *before* handing the listener to the runtime, so a state that cannot be built fails the test
with a refused connection and a sentence instead of a request that never answers. Both call
`AppState::start` — writing that sequence out twice is how the two drift apart.

### Running it for real

The spec starts its own containers, so pull the image once before the first run:

```sh
kiln images                 # what the steps need, and what is already here
kiln images pull            # fetch what is missing (mirror-aware: KILN_REGISTRY_MIRROR)
```

Then point a *manual* run at a database of your own — the point of the exercise is to watch the
migrations happen:

```sh
podman run -d --name pg -e POSTGRES_PASSWORD=postgres -p 127.0.0.1:5432:5432 postgres:17-alpine
MAILER__DATABASE__URL=postgres://postgres:postgres@127.0.0.1:5432/postgres cargo run -p mailer
# ... then, in another shell:
psql "postgres://postgres:postgres@127.0.0.1:5432/postgres" -c '\d subscribers'
```

## DONE WHEN

- `kiln run mailer/1.9-postgres` — the spec passes (start it with `kiln images` green, or the
  harness will tell you which command fetches the image)
- `kiln check mailer/1.9-postgres` — every must gate is green, including `images`
- a database that starts empty is the schema above after one start, and the second start changes
  nothing
- starting with `MAILER__DATABASE__URL` pointing at a port nothing listens on exits `1` within a few
  seconds, with a sentence naming the database, and never serves
- with no `MAILER__DATABASE__URL` at all the service starts, `/healthz` is `200`, `/readyz` is `503`
- `cargo build` works with no database anywhere: `migrate!` embeds the files at compile time and
  needs nothing to run

## TRAP

1. **`connect_lazy`.** The pool is described, not opened, so the service starts happily with the
   database gone — and the spec's *"the service was still running after 10s"* is that defect, seen
   from outside. `connect` is the one that proves it.
2. **Binding before migrating.** Serve first, migrate in a background task, and the first requests
   arrive before the schema exists. The order is the step: connect, migrate, *then* bind. The spec
   cannot see your ordering directly; it sees a service that says it is ready while `subscribers`
   does not exist yet.
3. **The obvious constraint.** `CHECK ((status = 'active') = (confirmed_at IS NOT NULL))` looks like
   the same rule and is stronger: it forbids unsubscribing anybody who was confirmed, which step
   `mailer/1.18-authz-boundary` has to do. `status <> 'active' OR confirmed_at IS NOT NULL` says
   only what this service means: active implies confirmed.
4. **Readiness remembered instead of asked.** A `ready` flag computed at startup, or a `OnceCell`
   around the first successful query, answers `200` about a database that left an hour ago. The
   spec's *"a service that lost its database is not ready"* is that.
5. **Answering readiness with the database's own words.** Pasting the driver's error — connection
   string included — into a probe body publishes a credential to whoever can reach `:8080`. The body
   says *not available*; the log says what happened.
6. **Editing `0001` after it ran.** `sqlx` checks the checksum of every applied migration: changing
   one fails the next start with *"was previously applied but has been modified"*, on every
   deployment that already has it. Add `0002_…` instead.
7. **`query!` without offline data.** The compile-time-checked macros (`sqlx::query!`,
   `query_scalar!`) need a live `DATABASE_URL` at *compile* time, or a `.sqlx/` directory generated
   by `cargo sqlx prepare`. This step deliberately uses the runtime API (`sqlx::query`,
   `fetch_optional`) so the crate keeps building with no database anywhere; the macros and their
   offline metadata arrive with the first query of step `mailer/1.11-signup`.
8. **A container the tests cannot reach and nobody can find.** Starting a container per test without
   a deadline means a hung `podman` hangs `cargo test`; starting one *shared* container means two
   tests see each other's rows. The harness in `tests/support/postgres.rs` does neither: one
   container per test, every command with a deadline of its own, `--pull=never` so a missing image
   is a sentence instead of a registry wait.
