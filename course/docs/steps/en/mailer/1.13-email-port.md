# Email port and a fake implementation

## WHY

A confirmation email is the first thing this service has to do that is not its own. Everything so far
was inside the process: an address it parsed, a row it wrote, a token it issued. Sending mail means
talking to something it does not control — and the usual way of talking to something you do not
control is to write the call at the place that needs it:

```rust
smtp::send(&config.smtp, &email, subject, body)?;   // wherever it is needed
```

That line is a decision about *testing* as much as about mail. Every test of signup now needs an SMTP
server, or a mocking framework that takes that call apart and answers `Ok(())` — and a test whose
passing depends on a stand-in being told what the real thing would do is a test that agrees with
itself. This step writes the dependency down as a port instead:

- **the service knows a trait, not a client**: `EmailSender` says *a message goes somewhere*, and
  nothing about SMTP, hosts, or credentials. The handler asks the state for *something that can send*
  and hands it a message;
- **an adapter is where the world lives**: `Logging` is what this build runs with — T1 has no mail
  server until step `mailer/1.19-test-layering`, so a message is a log line today, and the same port
  grows a real adapter there without a handler changing;
- **a fake is code you own, not a library you configure**: `tests/support/email.rs` records every
  message it was handed and can be told to fail. That is the whole fake — no expectation DSL, no
  "verify", and failure injection is a *constructor argument* rather than a mocking trick. When the
  fake is wrong, it is wrong in a file you can read.

And then the part that is easy to get wrong once the port exists: **a mail server that is away is not
a signup that failed**. The row is written, the address is good, the subscriber exists; what is
missing is one message. A service that answers `500` there has thrown away an address it already has,
and the person who typed it will try again and be told they are already subscribed. The failure is a
log line today, and step `mailer/1.14-worker` is where it becomes a retry — but the *policy* (the
subscriber stays, the send does not change the answer) is decided here.

## TASK

The scaffold added `src/email.rs` — the message type, the port, the log adapter and two constants —
and `tests/support/email.rs`, the recording fake the spec uses. What is missing is the seam, the
message, and the policy.

### `src/lib.rs`

Declare the module: `pub mod email;`.

### The message: `confirmation_message` in `src/signup.rs`

The port knows nothing about subscriptions, so the email that confirms one is built where the
subscriber is:

```rust
pub fn confirmation_message(to: Email, token: &Token) -> Message
```

The body has to carry the link, with the token that is **in the row**:

```text
{CONFIRMATION_BASE_URL}/confirm?token={token.as_str()}
```

The subject is `CONFIRMATION_SUBJECT` (both constants are in `src/email.rs`), and the recipient is the
parsed address — the same value the row holds, not the text the caller typed.

### The seam: `src/http.rs`

The state carries the port, not the adapter:

- `AppState` gains `sender: Arc<dyn EmailSender>`;
- `AppState::start(config, id)` keeps its signature and builds the state with `Logging` — the binary
  (`src/main.rs`) does not change at all;
- `AppState::start_with_sender(config, id, sender: Arc<dyn EmailSender>)` is the same startup order
  with the sender as an argument, and `start` is a one-line call to it;
- `AppState::sender()` hands a handler what it needs.

This constructor is public on purpose: the harness that wants a fake is a crate the library cannot
see, so an argument is the only honest way to let it in. It is not a test-only path — a deployment
with a second adapter picks it the same way.

### The send: `src/signup.rs`

`subscribe` takes the sender (`pool`, `sender`, `request` in that order) and, **only after a row came
back** (the insert won, so the address is this subscriber's):

1. build the message;
2. hand it to the sender;
3. if that fails, log it — with the reason, and with the address it was for — and **let the signup
   succeed anyway**.

The second signup for an address that is taken answers `409` and sends nothing: an email to somebody
who is already subscribed is a link that confirms nothing, and it is exactly the message a person who
is *not* the subscriber would report as a phishing attempt.

### What the spec judges

| the test | the claim |
| --- | --- |
| a signup | exactly one message, to the stored address, whose body carries `/confirm?token=<the token in the row>` |
| the same address again | `409`, and no second message |
| a sender that refuses | `201`, the row is still `pending`, one attempt, no delivery |
| a sender that recovers | the next signup is delivered, and the failed one is not retried by this step |
| every adapter | `Logging` and the fake both take a deliverable message; the fake can be made to refuse |

## DONE WHEN

- `kiln run mailer/1.13-email-port` — the spec passes
- `kiln check mailer/1.13-email-port` — every must gate is green
- a signup through the running service logs one `an email would be sent` line with the address and the
  subject — and not the body, which carries the token
- a signup while the sender is told to fail still answers `201` and leaves the subscriber `pending`
- `cargo test --lib` passes: the port, the adapter and the message still hold together

## TRAP

1. **Letting the send decide the answer.** `sender.send(...).await?` in `subscribe` (or in the
   handler) turns a mail server that is away into a `500` for a subscriber this service has *already
   written*. The spec's *"a mail server that is away is not a signup that failed"* is that failure,
   and the row is still there to prove it.
2. **Sending before the insert.** The link is what the new subscriber needs, so it is tempting to
   build and send it first — and then the second signup for a taken address emails a confirmation
   link to somebody who is already subscribed. The spec's *"the second signup must not email
   anybody"* shows it as two delivered messages.
3. **Storing the adapter.** `sender: Arc<Logging>` in `AppState` compiles, passes every test that
   does not inject, and quietly removes the seam: the next test that needs a failure has to reach for
   a mocking framework after all. The type of the field is the whole design.
4. **An `async fn` in the trait.** `fn send(&self, message: Message) -> impl Future<...>` is the
   modern spelling and cannot be called through `dyn EmailSender`, which is what the state holds. The
   signature in the scaffold boxes the future for that reason; one allocation per message is what a
   seam costs (and `async-trait` automates exactly this transformation if you would rather not write
   it out).
5. **Logging the message.** `info!(?message, …)` in the log adapter looks helpful and writes the
   confirmation link — the token — into a log line. The adapter logs the envelope (address and
   subject); the body is the secret's home.
6. **A base URL that is half a decision.** `CONFIRMATION_BASE_URL` is a constant in this step, and it
   is a *setting* the moment this service is deployed anywhere: a link to `localhost` in an email is a
   link nobody can click. Do not leave a comment saying "this should be config" next to a hardcoded
   link — either a constant you mean, as here, or a setting built the way step `mailer/1.4-config`
   builds the others.
7. **A fake that is not like the real thing.** The fake has to answer the same way the adapter does:
   `Ok(())` when the message was taken, `Err(SendError)` when it was not, and the same message type.
   A fake that returns something else, or that swallows failures, is a fake that will one day pass a
   test the real adapter fails. The last test in the spec runs one contract over every adapter for
   that reason.
8. **Forgetting that this is still in the request.** The send happens inside `POST /signup` today, so
   a slow mail server makes signup slow — deliberately, because a queue and a worker are step
   `mailer/1.14-worker`, and this step is about the seam they will use. Knowing which of the two you
   are looking at is the difference between a trade and a bug.
