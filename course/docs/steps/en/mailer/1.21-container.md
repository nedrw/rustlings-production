# Containerize and deploy: multi-stage image, probes, migration order

## WHY

Everything this track has built runs because *you* started it: a binary in a directory, a database URL
in your shell, a mail server you launched yourself. A deployment is the same service started by
somebody else's machinery, on a machine that never saw your laptop — and between those two worlds sits
one artifact: **the image**. What the image contains, what it listens on, what it does before it
serves traffic, and how big it is are all decisions this step makes, and all of them are the kind that
look fine on your machine and fail on the first real one.

Four decisions, and each of them is a way to be wrong:

1. **what is in the image is what is in the image.** A one-stage build leaves `cargo`, `rustc`, `cc`,
   the registry, the sources and every build script in the thing you ship. The toolchain is not
   payload, and an image with a compiler in it has a compiler's vulnerabilities, a compiler's size and
   a whole extra surface nobody audits. So there are two stages: one that has everything and
   disappears, one that has a binary, a trust store and a user;
2. **it has to be small**, and "small" is a number. Every image is `COPY`d across a network and stored
   on a node, and the difference between 16 MB and 900 MB is the difference between a deploy that
   finishes during a rolling update and one that does not. The size ceiling in this step's spec is not
   a style preference: it is the assertion that the *runtime* stage is a runtime, and the most common
   way to fail it is to leave the builder under the shipped image;
3. **it has to listen where a deploy can reach it.** `mailer/1.4-config` made the listening host a
   setting and defaulted it to `127.0.0.1` — right for a laptop, and a container that only listens on
   its own loopback is a container nothing can reach. A published port with nothing behind it looks
   exactly like a broken image while being a perfectly healthy process;
4. **it has to say when it is alive and when it is ready**, and those are two different questions
   (`mailer/1.9-postgres`): liveness is about this process staying up, readiness is about the schema
   being current. Their `Dockerfile` form is the same image answering two routes — what makes them
   real is that an orchestrator *uses* them, and what makes them honest is that they disagree when the
   database is away.

**And the claim this step is really about**: *the image runs the same binary you tested.* That is the
promise a container makes to everything you did in the twenty steps before it — so the step's gate
(`container-repro`) rebuilds the image from your tree and asks the binary inside it the same question
it asks the binary on your host, which is a comparison no green test on the host can substitute for.

## TASK

The scaffold put three files in place, and the first one is the hole:

- `Dockerfile` builds one stage: `FROM rust:1.98-alpine`, `COPY . .`,
  `RUN cargo build --release --locked`, `ENTRYPOINT` at the binary inside the image. It is a working
  image, and every claim in `tests/spec_image.rs` fails against it;
- `.dockerignore` — without it the *host's* `target/` (hundreds of megabytes) is sent as build
  context on every build, and `.git/` goes with it;
- `tests/support/container.rs` — the fixture the spec uses: it builds the image once per run, starts
  it with the ports published, asks it HTTP questions from outside, runs commands inside it and
  reports its size. It never pulls an image: a missing base image is a sentence pointing at
  `kiln images pull`. It also mounts a build cache and passes its path as `CARGO_TARGET_DIR` —
  offered, not imposed: a `Dockerfile` that ignores the argument builds normally, and one that opts
  in reuses what the previous build compiled (see TRAP 3 for what a mount does *not* do).

### the `Dockerfile`

Two stages, and the second one starts from nothing:

```dockerfile
FROM ${BUILDER} AS builder      # the toolchain: build-time only
  ... build the binary ...
FROM ${RUNTIME}                 # alpine + ca-certificates + one user
COPY --from=builder /src/mailer /usr/local/bin/mailer
USER mailer
ENV MAILER__LISTEN__HOST=0.0.0.0
ENTRYPOINT ["/usr/local/bin/mailer"]
```

- **the dependency layer comes first and alone**, with a stub `src/`: it changes only when
  `Cargo.toml`/`Cargo.lock` do, so a code change rebuilds one crate instead of the whole tree. The
  stub has to compile under this workspace's lints (`missing_docs = "deny"` is workspace-wide);
- **`COPY --from=builder`** is the line that makes the second stage small: what crosses over is the
  binary, not the workspace. The path it copies *from* has to be outside the build cache the fixture
  mounts (see TRAP 3);
- **`USER`** before the entry point: the process is pid 1 inside the container either way, and a
  service that needs no privileges should have none;
- **`MAILER__LISTEN__HOST=0.0.0.0`** as image configuration, because that default is a deployment's
  decision and this is a deployment. Nothing else is baked in: the database URL, the SMTP host and the
  log level arrive as environment variables, which is what `mailer/1.4-config`'s layering was for;
- the image **runs the migrations at start-up** (the binary does that, step `mailer/1.9-postgres`) —
  the image does not ship a migration tool, and `sqlx-cli` is not in it.

### the base images come from `kiln images pull`

This step declares two images, and they are build-time inputs: `rust:1.98-alpine` (the builder) and
`alpine:3.20` (the runtime). `kiln check mailer/1.21-container` runs the `images` gate before anything
builds, and it names the pull command when one is missing; a build never reaches the network for them
(`--pull=never`). Behind a registry mirror the same images live under a different name
(`docker.1ms.run/library/rust:1.98-alpine`), which is why the `Dockerfile` takes both names as build
arguments and the fixture passes the names this machine's engine actually has.

### the probes

Nothing to write — they have been there since `mailer/1.9-postgres`. The step's job is to make them
*reachable*: `/healthz` answers 200 from outside the container, `/readyz` answers 503 with
`no database is configured` when there is none, and `/readyz` turns 200 only once the schema is in
place. The spec checks all three from outside the process, which is the only place a probe can be
checked.

### What the spec judges

| the test | the claim |
| --- | --- |
| `the_image_runs_this_service_and_is_reachable` | `/healthz` answers 200 through the published port, `/readyz` answers 503 and names the missing database, an unknown path is the same 404 body the host binary answers, and the log says it is listening |
| `the_image_is_small_because_it_is_not_a_build_environment` | no `cargo`, no `rustc`, no `cc`, no `/src`, the binary is there — and the image is under 25 MB |
| `the_image_does_not_run_as_root` | `id -u` is not 0, and the user exists |
| `the_container_migrates_before_it_serves` | with a database, `/readyz` goes green and the schema is in the database |

## DONE WHEN

- `kiln run mailer/1.21-container` — the spec passes (the first build takes minutes: it compiles the
  dependency tree inside the builder; later builds are seconds)
- `kiln check mailer/1.21-container` — every must gate is green, `container-repro` included: it
  rebuilds the image from your tree, holds it to the size budget, and compares the configuration report
  the binary inside the image answers with the one the binary on your host answers
- `podman run --rm -p 8080:8080 mailer:dev` then `curl -i localhost:8080/healthz` answers 200 from
  your machine — not from inside the container
- `podman image inspect mailer:dev --format '{{.Size}}'` is tens of megabytes, not hundreds
- `podman run --rm mailer:dev id -u` prints a number that is not 0
- `podman run --rm mailer:dev sh -c 'command -v cargo'` fails: the toolchain did not ship

## TRAP

1. **Listening on the container's own loopback.** The image inherits `listen.host = 127.0.0.1` from
   `mailer/1.4-config`, publishes a port, and answers nobody. The symptom is the worst kind: the
   container is up, the log says `listening`, the health check inside the container passes, and the
   outside sees a connection that goes nowhere. `0.0.0.0` is what a container needs.
2. **The dependency-layer stub has to compile under this workspace's lints.** An empty `src/lib.rs`
   fails `missing_docs = "deny"`, and that failure happens *inside* the build — reported as one clipped
   line by the builder, after the whole dependency tree has been compiled. It is a two-line fix
   (`printf '//! Stub.\n' > src/lib.rs`) and an hour if you have not seen it before.
3. **A cache mount is not a layer.** The fixture mounts a build cache and passes its path as
   `CARGO_TARGET_DIR`, which is what makes the second build cheap — and means a binary left in
   `$CARGO_TARGET_DIR` is *not* in the image. So the builder's last step copies the binary out of the
   mounted path in the same `RUN`, and the runtime stage copies from there:
   `COPY --from=builder /src/target/release/mailer` builds fine when the target directory is the
   mount, and produces an image with nothing in it. This is the trap a CI cache mount sets for every
   Rust project; here you meet it on purpose.
4. **Mounting a cache over the toolchain.** `/usr/local/cargo` is where the image keeps `cargo`
   itself; mounting a registry cache there replaces it and the build dies with `cargo: not found`. The
   cache path is `/usr/local/cargo/registry`.
5. **The base image name that only exists on your machine.** `FROM rust:1.98-alpine` works where Docker
   Hub is reachable and fails behind a mirror, where the image is stored as
   `docker.1ms.run/library/rust:1.98-alpine`. Names of base images are deployment facts; the build
   arguments are where they belong. The same store can hold one repository path *twice* — once per
   architecture, if it was filled through more than one mirror — and the engine refuses the copy
   that is not this machine's with `image not known`, several stages into a build. (The fixture picks
   the architecture this engine runs, which is why the pull to trust is `kiln images pull`.)
6. **Rebuilding the image by hand and calling it verified.** A green `podman build` says the file
   parses; the four claims in the spec are about what the image *does*, and the two that fail most
   often (size, reachability) are invisible from the build output. Run the spec.
7. **Baking configuration into the image.** `ENV MAILER__DATABASE__URL=postgres://…:secret@…` puts a
   credential in every layer, in `podman history`, and in every registry it is pushed to. The image
   declares what is true of the *deployment shape* (listen host, port); everything secret arrives at
   run time.
8. **Shipping a migration tool instead of migrating.** The alternative design — bake `sqlx-cli` into
   the image and run `sqlx migrate run` in an entrypoint script — puts a second copy of the schema
   logic in the image and makes the start-up order something a shell script has to get right. The
   binary already migrates before it serves, and that is the ordering the spec checks.
