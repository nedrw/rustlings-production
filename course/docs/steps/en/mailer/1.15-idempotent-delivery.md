# Idempotent delivery: one confirmation email per subscriber

## WHY

Step `mailer/1.14-worker` moved the send off the request path. It did not make it *once*: the queue
retries, a process can be restarted, two workers can hold a job for one subscriber, and the same
signup can arrive twice. Every one of those is another chance for a second confirmation email — and a
mail server cannot help. It takes a message and sends it; deduplicating is nobody's job but this
service's, and the place a service can actually do it is the database.

"Exactly once" is two claims pulling in opposite directions, and the honest version of it is:

- **at least once** — a message this service owed has to be sent even if the first attempt failed,
  the process was restarted, or a subscriber asked again;
- **at most once** — the *side effect* happens once per intent, however many attempts, jobs or
  workers take part.

Three decisions make that possible, and each of them is a way to get it wrong:

1. **the key is the intent, not the message.** What must not happen twice is *telling this
   subscriber about their confirmation*. The state therefore hangs off the subscriber — it does not
   hash the message, and it does not deduplicate on the token. A rotated token is a different
   message and the same intent, which is exactly how a message-shaped key ends up deduplicating
   nothing;
2. **the claim is a conditional write, and its answer is the truth.** `claim` does not read the row
   and then decide. There is a window between the halves of a read-then-write (step
   `mailer/1.11-signup` used a unique constraint to close it; this step uses the same move with an
   `UPDATE ... RETURNING`): the statement carries its conditions, and the row it returns went to
   exactly one caller — the one that won the claim. Every other caller gets *nothing to do*;
3. **the record is written after the send, and given back when it fails.** `confirmation_sent_at` is
   set only once a mail server has taken the message; a failed send releases the claim, so the
   message stays owed and claimable instead of being stuck as "somebody is on it" forever. And
   because the *count* of attempts lives in the row too, "we gave up on this one" is a fact
   somebody can query rather than a line in a log that scrolled away.

**The part this step does not fix, said out loud**: a worker that dies between the claim and the
send leaves a subscriber claimed and unsent. Closing that needs either a reaper
(`claimed_at < now() - interval '…'` puts the row back) or an outbox that makes the database the only
queue — later work, and the reason T3 exists. What this step buys is that no number of retries,
restarts, duplicate requests or concurrent workers can send the same confirmation twice.

## TASK

The scaffold added two things, and the hole in both is the middle decision above:

- `migrations/0002_confirmation_delivery.sql` — `confirmation_claimed_at`, `confirmation_sent_at`
  and `confirmation_attempts` on `subscribers`. A migration that has run anywhere is never edited:
  this is 0002, and the next schema change is 0003;
- `src/deliveries.rs` — the state machine, whose `claim` is a **read**: it asks whether the
  subscriber is pending and not yet told, and answers `Some` to every caller that asks. Two callers
  both get the message, and the count that is supposed to make giving up visible stays at zero.

### `src/lib.rs`

Declare the module: `pub mod deliveries;`.

### `src/deliveries.rs`: the claim becomes a claim

- `claim(pool, subscriber) -> Result<Option<Delivery>, Error>` — one statement that **writes** and
  decides at the same time:

```sql
UPDATE subscribers
   SET confirmation_claimed_at = now(),
       confirmation_attempts = confirmation_attempts + 1
 WHERE id = $1
   AND status = 'pending'
   AND confirmation_sent_at IS NULL
   AND confirmation_claimed_at IS NULL
   AND confirmation_token IS NOT NULL
 RETURNING email, confirmation_token
```

  `None` is not an error: it means the confirmation has already been sent, or another worker has it
  right now. A claim *is* an attempt — the worker sends once per claim (see below) — so
  `confirmation_attempts` counts the times this message was really offered to a mail server, and the
  count survives a restart;
- `mark_sent` — `confirmation_sent_at = now()`, claim cleared. It is the write every later job runs
  into: with the stamp in place, `claim` answers `None` without sending anything;
- `release` — the claim cleared, nothing else. A send that failed leaves the message owed;
- `outstanding(pool, email) -> Result<Option<i64>, Error>` — the subscriber this address belongs to
  *if the service still owes them a confirmation*: `None` for an unknown address, a confirmed one,
  or one that has already been told. This is the question a second signup asks.

### `src/delivery.rs`: the job is an identity, not a message

`Job` stops carrying a `Message` and carries a `subscriber` instead, and `Queue::start` takes the
pool as well as the sender: what has to be sent is decided by the row, at the moment somebody claims
it, and never by whoever queued the job.

The worker's shape changes with it. The retry loop now goes **through** the database rather than
around the sender — claim, send once, record or release — so each attempt is a claim, the attempt
count is real, and a release is what makes the next attempt possible at all:

```rust
let Some(delivery) = deliveries::claim(pool, job.subscriber).await? else { /* nothing to do */ };
let message = confirmation_message(delivery.email.clone(), &delivery.token);
match sender.send(message).await {
    Ok(()) => { deliveries::mark_sent(pool, job.subscriber).await?; /* delivered */ }
    Err(error) => {
        deliveries::release(pool, job.subscriber).await?;
        // …backoff, then claim again; after MAX_ATTEMPTS, log it and move on
    }
}
```

The message is rebuilt from the row (`confirmation_message(email, &token)` is the function of step
`mailer/1.13-email-port`), which is also why the token never has to travel in a job.

### `src/http.rs` and `src/signup.rs`: who may ask for a delivery

- `AppState` carries `delivery: Option<Queue>`, and it is `None` exactly when there is no database:
  the delivery record lives in one, and a queue that cannot record what it did is a queue that sends
  twice. `delivery()` hands a handler `Option<&Queue>`;
- `/signup` needs both — `state.database()` **and** `state.delivery()` — and reserves a seat before
  the insert, as in step `mailer/1.14-worker`;
- `subscribe(pool, seat, request)` sends `Job { subscriber: id }` when the insert wins. When the
  insert **loses**, it asks `outstanding(pool, &email)`: if the service still owes this subscriber a
  confirmation, the seat is used to ask the worker to try again — and the answer to the caller stays
  `409`, because the address really is taken. A second signup is a second *request to deliver*, and
  whether it produces an email is the database's decision, not the handler's;
- nothing in the handler reads before it writes: the duplicate path's question is asked *after* the
  unique constraint has already decided, so there is no window to lose.

### `src/main.rs`

The queue is optional now, so the shutdown sequence drops the `Option` before draining — a process
with no database has nothing to drain, and the exit codes do not change.

### What the spec judges

| the test | the claim |
| --- | --- |
| one signup | one email, and the row says so: `confirmation_sent_at` set, `confirmation_attempts` at 1 |
| the same address again | `409` (twice, in two spellings), and still exactly one email |
| a send that keeps failing | `MAX_ATTEMPTS` attempts, the row back to unclaimed and unsent, and — once the sender works again and the subscriber asks again — the message goes out, once |
| callers racing for one address | one `201`, seven `409`s, and one confirmation: the jobs that the duplicates queued have to be deduplicated by the claim, not by luck |

  with one stamp, one null and one count — and one email in the log
- with the sender failing, `confirmation_attempts` reaches `MAX_ATTEMPTS`, `confirmation_sent_at`
  stays null, and a later signup for that address delivers it

## TRAP

1. **A read, then a send.** The scaffold's `claim` asks the row whether the message is still owed and
   answers yes to everybody: two jobs claim the same message and it goes out twice. The window is the
   same one step `mailer/1.11-signup` closed for signups, and the fix is the same shape: make the
   statement carry its conditions and believe its `RETURNING` row, not a previous `SELECT`.
2. **Deduplicating on the message.** Keying the delivery on the token, or hashing the body, looks
   tidier and breaks the first time a token is rotated: the message changes, the intent does not, and
   the subscriber gets two confirmations for one subscription.
3. **`sent_at` before the send.** Stamping the row and then sending makes the record a guess: a send
   that fails leaves a subscriber who can never be told, and nothing will ever try again. The stamp
   means *the mail server took it*.
4. **A claim nobody releases.** Without `release`, one failed send makes the message unclaimable
   forever — the row says "somebody is on it" and that somebody is gone. The same hole exists for a
   process that dies mid-send, which is the one this step documents instead of fixing.
5. **Losing the count.** `confirmation_attempts` costs one column and is the only durable answer to
   "how hard did we try?". A worker that keeps a private counter in memory loses it on restart, and
   a job that resets it makes a message that was given up on indistinguishable from a new one.
6. **The queue as the record.** A `Job` that carries the message, and a `sent` flag that lives in
   the worker's head, is the design this step exists to replace: kill the process and the answer to
   "did that email go out?" is gone with it. The job is a question; the row is the answer.
7. **Making the answer idempotent instead of the effect.** Returning `200` for a duplicate signup
   instead of `409` does not make anything happen once — the email is the side effect, and the status
   code has nothing to say about it. Step `mailer/1.11-signup` decided what a duplicate address
   answers; this step decides what it *does*, and the two are independent.
8. **Claiming in the handler and sending in the request.** It is tempting to settle "does this
   subscriber still need an email?" while the request is open — and then to send it right there,
   because the answer is already in hand. That is step `mailer/1.14-worker` undone: the caller waits
   for the mail server again, and the queue loses the only thing it was holding.
9. **Forgetting the reaper.** Every claim that is not released is a delivery that will never happen.
   Releasing on failure covers the failures this service sees, not the ones that kill it; on a real
   deployment the claimed rows need an expiry, and the prose above says so rather than leaving the
   reader to discover it in production.
