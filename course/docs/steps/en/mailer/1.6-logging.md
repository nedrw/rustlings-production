# Structured logs with a correlation id per run

## WHY

A log line that reads "starting mailer on 127.0.0.1:8080" is fine until somebody has to find it
again. Then it is a sentence: the host is a substring, the port is a substring, and a dashboard that
wants to group by port has to parse prose it did not write. A line with *fields* is data — a
collector indexes it, a query filters it, and a field you rename breaks the query, which is exactly
the feedback you want.

The second half is correlation. One process serves many requests, and one request touches many
lines; without an id in every line, "which of these 40 lines belong together?" is answered by
guessing from timestamps. The mechanism is a span: a unit of work with fields, whose events inherit
them. Today the unit is the run itself — step 1.7 will wrap each HTTP request in the same kind of
span, and nothing about the machinery changes.

## TASK

The scaffold added the dependencies and put the entry points in `src/logging.rs`: a working
`RunId`, and two functions that do nothing yet, `init` and `announce`. Fill those two in and wire
them into the binary:

- **`init` installs the subscriber** with two settings read from the configuration (step 1.4):
  the level from `log.level` (`error`, `warn`, `info`, `debug`, `trace`) and the format from
  `log.format` — `pretty` for a terminal, `json` for a collector.
- **`&str` fields, not sentences.** The announcement is one `info` event with the fields `host`,
  `port`, `log_format` and `database`, and the message `mailer is starting`. `database` says `set`
  or `unset` — whether a secret is configured is worth knowing; the secret is not (step 1.4's rule
  holds here too).
- **A second event at `debug`** so the level setting has something to unlock: `info` is the level a
  healthy service runs at, and a build that logs its internals there is a build nobody reads.
- **The run's span**: `announce` runs inside a span named `run` with the field `run.id` set to the
  run's id (`RunId::of_this_process()` — the scaffold's type; the span is what makes the id appear
  on every line of the run without repeating it).
- **`pretty` must not decorate a pipe.** A terminal gets colour; `stdout` that is a file, a pipe or
  a collector gets the plain line, because `host=127.0.0.1` has to be findable in what was captured.
- **Logging starts before anything else the service does**, and it starts *only* on the service
  path: `--help`, `--version` and `--check-config` answer without a subscriber, so a
  configuration report stays something a script can read.
- Wire it up: `pub mod logging;` in the library, and the binary initialising logging and announcing
  the run. A failure to install the subscriber is a configuration-shaped failure like any other:
  give it a variant in the error enum with its own `# Errors` section and exit code.

## DONE WHEN

- `kiln run mailer/1.6-logging` — the spec passes
- `kiln check mailer/1.6-logging` — every must gate is green
- `MAILER__LOG__FORMAT=json cargo run` prints one JSON object per line, with `fields.host`,
  `fields.port`, `fields.log_format`, `fields.database` and a `run` span in each
- `MAILER__LOG__FORMAT=pretty cargo run` prints the same facts for a human, with no escape
  sequences when stdout is not a terminal
- `MAILER__LOG__LEVEL=debug cargo run` adds the debug line; `MAILER__LOG__LEVEL=error cargo run`
  prints nothing
- `MAILER__DATABASE__URL=postgres://user:pw@localhost/db cargo run` says `database=set`, and the
  URL appears nowhere in the output

## TRAP

1. **Colour left on.** `fmt()` colours by default, and the captured line then contains
   `\x1b[2mhost\x1b[0m\x1b[2m=\x1b[0m127.0.0.1`: the spec fails with *"`host=127.0.0.1` is missing
   from: …"* while the terminal looked perfect. Ask for a terminal before decorating the output.
2. **Logging the configuration instead of fields about it.** `info!(?config, "…")`, or
   `#[instrument]` without `skip_all`, records every setting — including the database URL — into the
   line or the span. The spec fails with the URL in the output, and the URL has to be rotated.
3. **A formatted sentence instead of fields.** `info!("starting on {}:{}", host, port)` produces a
   line a human likes and a collector cannot index: the spec fails with *"this event has no field
   `host`"*.
4. **The level that never gets used.** Leaving the subscriber at its own default (`INFO`) while the
   configuration says `debug` means the debug line never appears: the spec fails with
   *"`MAILER__LOG__LEVEL=debug` has to unlock the debug lines this build has"*.
