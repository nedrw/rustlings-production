# Publish a newsletter: transactional write, background fan-out

## WHY

Every message so far was about one subscriber. An issue is about all of them at once, and that is a
different shape of work:

- the *write* is a fan-out: one issue, and one delivery row for every subscriber who is owed a copy;
- the *sending* is a batch of independent messages, each with its own attempts, its own failures and
  its own idempotency — step `mailer/1.15-idempotent-delivery` one table over;
- and the two must not be the same thing. An issue that exists with no delivery rows is an issue
  nobody will ever receive. Delivery rows for an issue that does not exist are worse: nothing knows
  what was meant to happen.

That is what a **transaction** is for, and this step is the first place in the course where one is
not optional:

```rust
let mut transaction = pool.begin().await?;
let issue = …insert the issue…;
let copies = …insert one row per subscriber who is owed it…;
transaction.commit().await?;
```

Three decisions come with that, and each of them is a way to get it wrong:

1. **the two writes are one write.** `BEGIN`…`COMMIT` around them, and `?` inside: a failure at any
point rolls the whole thing back, so the database never holds half a publish. "An issue with some of
its copies" is not a state any later step can repair — nothing records who the missing copies were;
2. **the fan-out happens after the commit.** Handing work to the delivery queue *inside* the
transaction would make a queue a participant in the write: a full queue would either block the
transaction or roll back a published issue. What is queued is work that is already recorded, so a
failure to queue it is `mailer/1.14-worker`'s backpressure — rows that are owed and not yet handed
over — and not a reason to lose the issue;
3. **who is owed a copy is a query, not a loop.** `INSERT … SELECT id FROM subscribers WHERE status =
'active'` is one statement, and the database decides who is in it: a subscriber whose address was
never confirmed has not proven it is theirs, and one who left asked not to be written to. A loop in
Rust over a list read a moment earlier has a window in which somebody confirms — and a loop is also
how a fan-out becomes a round trip per subscriber.

**What this step does not build**, said out loud: a relay. If the queue is full when the fan-out runs,
the copies it could not hand over are still rows — owed, recorded, and picked up by nothing until a
later track's claimer exists. That is the honest cost of not putting the queue in the transaction,
and the TRAPs below name the two ways of getting that wrong.

## TASK

The scaffold added the pieces, and two of them are wrong on purpose:

- `migrations/0004_newsletter.sql` — `issues` (with the two `CHECK`s that make an empty subject or an
empty body impossible) and `issue_deliveries`, whose `UNIQUE (issue_id, subscriber_id)` is the key
that says what a row is;
- `src/newsletter.rs` — the request, the two new domain types, `publish`, `fan_out` and the claim /
mark / release of one copy. **`publish` writes the issue and then writes the copies, with no
transaction around them**, and its fan-out hands a copy to *every* subscriber instead of the
confirmed ones. Both are visible from outside: an unconfirmed address receives an issue, and a
publish that fails in between leaves an issue nobody can ever receive;
- `sha2` is already in the dependencies from step `mailer/1.16-sessions`; nothing new is needed for
this step's writes.

### `src/newsletter.rs`: one write

Wrap the two statements in a transaction: `pool.begin()`, both statements against `&mut *transaction`,
and `transaction.commit()`. Then let the database answer the audience question — `WHERE status =
'active'` — instead of iterating over subscribers in Rust.

### `src/delivery.rs`: a second kind of job

`Job` becomes an enum: `Job::confirmation(subscriber)` and `Job::issue(delivery)`, each naming a row
rather than a message (step `mailer/1.15-idempotent-delivery` made that call for the first kind). The
worker dispatches on it: the confirmation path claims a subscriber's confirmation, the issue path
claims one delivery row. Both retry the same way — one attempt per claim, `backoff` between them,
`MAX_ATTEMPTS` of them, and a release that puts the row back — which is why the two loops look alike;
write the second one out rather than inventing an abstraction for three lines of policy.

### `src/http.rs`: `POST /newsletter`

- authenticated: it is an act by a subscriber, so it reads the session of step `mailer/1.16-sessions`
and answers `401` without one;
- `202 Accepted`, not `201 Created`: the *issue* was created and is there when the response is
written, while the *sending* has been accepted and has not happened;
- the body says what happened: the issue's id and how many copies it is owed to;
- after `publish` commits, `fan_out` hands the copies to the queue, and a failure there is a line in
the log — not a failed publish, because the publish is the part that must not be undone.

### What the spec judges

| the test | the claim |
| --- | --- |
| a publish | `202` with the number of copies, one issue, one row per *confirmed* subscriber, and none for the unconfirmed one |
| a publish with no session, or with a token nobody was issued | `401`, and nothing written |
| a publish with an empty subject | `400` naming the field, and neither an issue nor a copy in the database |
| two confirmed subscribers | each receives exactly one copy of the issue (the log), each copy is recorded as sent, and each was claimed exactly once |

## DONE WHEN

- `kiln run mailer/1.17-newsletter` — the spec passes
- `kiln check mailer/1.17-newsletter` — every must gate is green
- publishing against a running service answers `202` with a count, and that count matches
  `SELECT count(*) FROM subscribers WHERE status = 'active'`
- `SELECT count(*) FROM issues` and `SELECT count(*) FROM issue_deliveries` move together: no issue
  without its copies, no copies without their issue
- the service's log shows one `an email would be sent` line per confirmed subscriber, with the
  issue's subject, and none for an address that never confirmed

## TRAP

1. **Two statements pretending to be one.** The scaffold's shape: insert the issue, then insert the
copies, and hope. A failure between them is an issue with no recipients — and because the issue is
*the record*, there is nothing left to repair it from. A transaction is not a performance decision
here; it is the difference between two states the system can be in.
2. **The queue inside the transaction.** `let mut transaction = …` followed by `queue.reserve()?` and
a `?` on failure looks tidy and turns backpressure into data loss: a full queue rolls back an issue
that was ready to go out. Worse, the window between the commit and the enqueue is exactly where a
crash must *not* cost anything — and putting the enqueue earlier does not remove the window, it just
makes the failure mode a rolled-back publish instead.
3. **A loop where a query belongs.** Iterating over subscribers read a moment ago means a window in
which somebody confirms or unsubscribes, a round trip per subscriber, and a partial fan-out if the
process dies in the middle. `INSERT … SELECT` is one statement, one plan, one list — and the list is
the database's answer, not the application's guess.
4. **Counting what you inserted.** `INSERT … SELECT` does not answer with the rows it inserted
unless you ask (`rows_affected`); a fan-out that reports the length of the *input* list is how a
publish answers "three copies" when one subscriber had already been removed by `ON DELETE CASCADE`.
5. **The audience that only looks right.** Sending to every row in `subscribers` is the mistake the
scaffold makes, and it is invisible unless somebody in the database is *not* an active subscriber —
which is exactly the state the spec's fixture is in. Confirmation is what makes an address
somebody's; a newsletter sent past it is a newsletter that teaches people not to subscribe.
6. **Forgetting the fan-out altogether.** A publish that returns `202` and queues nothing looks
perfect from the outside — the issue exists, the copies are recorded — and no email is ever sent.
The spec's log assertion is the observation, and a relay (T3) is what makes the gap survivable in
production.
7. **Treating the issue as the delivery.** One row per subscriber is what makes this table worth
having: a single "the issue was sent" flag has no place to record which subscriber's copy failed,
and no way to retry it without sending it to everybody again.
