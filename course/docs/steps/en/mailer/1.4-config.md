# Typed configuration with a documented override order

## WHY

A service reads its settings from four places at once: the defaults in the code, a file next to the
binary, the environment of whatever started it, and the flags a person typed. Every incident that
starts with "it works on my machine" is a disagreement about which of the four won. The order is not
a detail to discover later: it is the contract, and a service that cannot say what it is configured
with is a service nobody can operate.

There is a second reason to write it down. A setting no source mentions has one obvious answer
*only* if you already know it — so a typo, `MAILER__LISTEN__PROT`, has to be refused out loud, not
silently replaced by port 8080. And a secret with a default in the repository is not a secret: it is
a password with a longer life than the deployment that leaked it.

## TASK

The scaffold put `src/config.rs` in place: the settings and their defaults as types, the error type
with its messages, and two stubs (`Config::load`, `Config::report`) that do nothing yet. It also
added the two dependencies the file needs. Everything else in this step is yours:

- **The order is the contract**: defaults < the file < the environment < the flags. Each source
  changes only the settings it mentions; a setting a later source does not mention keeps the value
  an earlier one gave it.
- **The file** is `mailer.toml` in the working directory, or the path `--config <path>` names — in
  which case the default file is *not* read. Every setting is optional; a setting the service does
  not know is an error, not a default. A missing default file is normal; a file named on the command
  line has to exist.
- **The environment**: `MAILER__LISTEN__HOST`, `MAILER__LISTEN__PORT`, `MAILER__LOG__LEVEL`,
  `MAILER__LOG__FORMAT`, `MAILER__DATABASE__URL` — the prefix `MAILER__`, and `__` between the
  parts of a setting's name. A variable with that prefix that names no setting is refused, by name.
- **The flags**: `--listen-port <port>`, plus `--config <path>` for the file layer, plus
  `--check-config`. There is deliberately no flag for the database URL: a secret typed on a command
  line ends up in the process list and in every shell history.
- **A value that cannot be used** is refused with the setting, the value, and where it came from:
  `log.format = "xml"` says `log.format`, `xml`, and the file or the variable. Exit non-zero, always
  — a rejected configuration must not be rounded down to the default.
- **`--check-config`** prints the effective configuration and exits successfully: `database.url`,
  `listen.host`, `listen.port`, `log.format`, `log.level`, one `key = value` line each, sorted by
  key.
- **Secrets are shown, never printed**: `database.url` is `<unset>` when no source set it and
  `<redacted>` when one did — a configuration report is what people paste into issues.
- **The configuration is loaded before anything else happens**, so a bad one stops the service even
  when it was started without `--check-config`. `--help` and `--version` are the exception: a
  question about the binary should not depend on the state of a service.
- **What you commit** is `mailer.toml.example` with placeholder values; the file with the real ones
  goes into `.gitignore`.

## DONE WHEN

- `kiln run mailer/1.4-config` — the spec passes
- `kiln check mailer/1.4-config` — every must gate is green
- `cargo run -- --check-config` prints the five settings and exits 0
- `MAILER__LISTEN__PORT=9111 cargo run -- --check-config` shows port 9111
- `MAILER__LISTEN__PROT=9111 cargo run -- --check-config` names the variable and exits non-zero
- `MAILER__DATABASE__URL=postgres://user:pw@localhost/db cargo run -- --check-config` prints
  `<redacted>` and the password does not appear anywhere in the output

## TRAP

1. **Swallowing the file error.** `read_to_string(path).ok()` turns "the path you gave me is wrong"
   into "I used the defaults", and the service starts with another host's settings. The spec fails
   with *"the report must mention \"absent.toml\""* — the file you named is what the report has
   to say.
2. **Applying the layers in the order they are read rather than the order they win.** If the
   environment is applied after the flags, `--listen-port 9222` loses to a `MAILER__LISTEN__PORT`
   that the deployment happens to set, and the port in `--check-config` is not the port the person
   asked for.
3. **Printing the secret.** `database.url` in a `--check-config` dump looks helpful until it is
   pasted into an issue. The spec fails with *"the report must mention ..."* or with the raw URL in
   the output, and the URL has to be rotated.
4. **Letting an unknown variable through.** A `match` with a catch-all arm that ignores
   `MAILER__LISTEN__PROT` starts the service on the default port; the deployment looks fine and
   nothing works.

  the attribute behind "a setting this service does not know is an error"

  a deployment gets to change, and files are for development
- [`figment`](https://docs.rs/figment/latest/figment/) — the same layering as a provider stack, for
  when "four sources" becomes "a profile, a secret store and a feature flag service"
