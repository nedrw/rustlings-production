# One command for every check, wired into CI

## WHY

Every project ends up with two lists of checks: the ones a human runs before pushing, and the ones
the pipeline runs. They drift, and the drift is always the same shape — the pipeline is greenable
and the local list has a step nobody remembers, so a commit passes locally and fails in CI. The fix
is not discipline, it is one entry point: the checks live in code inside the repository, CI calls
that code, and a human calls exactly the same thing.

There is a second, quieter reason. A *task runner* in Rust is ordinary code: it fails in the middle
of the list and exits non-zero, it can be run with a different working directory, and it can be
tested. Shell glue in a YAML file is none of those things, and it is invisible to `cargo test`.

## TASK

The scaffold put the shape in place: an `xtask` crate, a `[alias] xtask` in `.cargo/config.toml` so
`cargo xtask <task>` works, and a stub whose `ci` task prints "not implemented yet".

- Fill in the `ci` task: it runs `cargo fmt --all --check`, then `cargo clippy --workspace
  --all-targets -- -D warnings`, then `cargo test --workspace`, and it fails with the exit code of
the first check that fails. Order matters: fail fastest first.
- Print progress to stderr, so a task that later prints a result stays scriptable.
- Add `.github/workflows/ci.yml`, calling `cargo xtask ci` — and nothing else. The workflow checks
  out the repository and calls the task; it does not list `fmt`, `clippy` or `test` itself, because
  a second list is what drifts.
- Do not pin the Rust version in the workflow: `rust-toolchain.toml` already decides it.

The spec **runs** your task twice. First on the clean tree, which has to be green. Then with a file
in `tests/` that is unformatted, contains a `todo!()` and fails a test, which has to be red —
whichever check your task runs first. It also reads the workflow and objects to any `cargo fmt`,
`cargo clippy` or `cargo test` line in it.

One detail the spec has to handle, and so do you: `cargo xtask ci` runs `cargo test`, which runs
this spec, which would run `cargo xtask ci` again. The spec sets `KILN_CI_NESTED=1` when it starts
the task and returns immediately when it sees it. A check that calls itself is a hang, and a task
runner is exactly where that bites.

## DONE WHEN

- `kiln run mailer/1.3-ci` — the spec passes
- `kiln check mailer/1.3-ci` — every must gate is green
- `cargo xtask ci` in `app/mailer` prints one line per check and ends with `every check passed`
- break formatting on purpose (a stray line break in `src/lib.rs`) and watch `cargo xtask ci` fail
  with the exit code of the `fmt` check

## TRAP

1. **Listing the checks in the workflow as well.** It looks harmless and it is the whole problem: the
   YAML list and the task list diverge, and the spec fails with *"no workflow runs `cargo xtask ci`"*
   or names the line that re-implements a check.
2. **Letting `cargo test` recursion run.** Without the nested guard, the second invocation of the
   task starts a third, and the run does not end — you see the same four lines printed again and
   again until you kill it.
3. **Returning success from `ci` regardless of what failed.** `Command::status()` gives you a
   `Result`, and `.ok()` throws away whether the check passed; the spec's broken-tree half then
   fails with *"`cargo xtask ci` stayed green with a file that is unformatted, unfinished and fails
   a test"*, which is the sentence that should have been the task's own exit code.
