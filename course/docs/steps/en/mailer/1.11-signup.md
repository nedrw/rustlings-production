# Signup: password hashing and a unique constraint as a concurrency primitive

## WHY

A signup endpoint looks like the easiest handler in the service: check the values, hash the password,
insert a row. Both halves of that sentence hide a decision, and both of them are the difference
between a service that works and one that works *once*.

**Who decides that an address is already subscribed?** The obvious answer is the application: read
the row, and if it is there, answer `409`. That answer is wrong, and not in a style sense — it is
wrong in the way arithmetic is wrong:

```text
A: SELECT ... WHERE email = 'ada@example.com'   -> no row
B: SELECT ... WHERE email = 'ada@example.com'   -> no row        <- both callers are inside the
A: INSERT ...                                   -> commits          window at the same time
B: INSERT ...                                   -> ERROR: duplicate key value violates unique
                                                   constraint "subscribers_email_key"
```

There is no application-level fix that is worth having. A `Mutex` serialises one process and does
nothing across two replicas — and the two replicas are the reason the address is unique in the
first place. A `SELECT ... FOR UPDATE` takes a row lock *on a row that does not exist yet*, which is
the one thing a row lock cannot do. The only thing that can decide a race between two processes is
the thing they both talk to, and it already has the answer: `subscribers.email` is `UNIQUE` (step
`mailer/1.9-postgres`). So this step hands the decision to the constraint:

```sql
INSERT INTO subscribers (email, name, password_hash) VALUES ($1, $2, $3) ON CONFLICT (email) DO NOTHING RETURNING id
```

`ON CONFLICT (email) DO NOTHING` turns “somebody already has this address” from an error into *no
row inserted*, and `RETURNING id` makes that visible: the winner gets its row back, the loser gets
nothing, and neither of them had to read anything first.

**What is stored in `password_hash`?** Not the password. A table of passwords is a table that
cannot be backed up, dumped for a migration, or read by a support engineer without becoming an
incident. What goes in is a PHC string (`$argon2id$…`): the algorithm, its parameters, a salt
*generated for this one subscriber*, and the digest. The salt is what stops one stolen table from
being a lookup for every subscriber at once, and the parameters are what make each guess expensive.
Verification — the caller for that is login, step `mailer/1.16-sessions` — hashes the candidate and
compares, so the original is needed nowhere after this function returns.

Two smaller decisions ride along, and both of them are about the boundary rather than about
crypto: a refusal has to say *which* field was wrong and **never** repeat the value (step
`mailer/1.10-domain-types` — a value may be a password, and a message ends up in a log), and a
failure the caller can act on has to come back as a 4xx while a failure only the deployment can act
on comes back as a 5xx with no explanation in it.

## TASK

The scaffold added `src/signup.rs` with the request shape and one function that is deliberately
wrong. The route is yours to write, and so are the two error variants it needs.

### `src/lib.rs`

Declare the module: `pub mod signup;`. (The scaffold's file is not compiled until you do — the spec
sees a service with no `/signup` route until then.)

### `src/error.rs`

Two variants, and both of them in the exit-code table:

| variant | message | exit code | HTTP |
| --- | --- | --- | --- |
| `AlreadySubscribed { email: String }` | `` `ada@example.com` is already subscribed `` | `2` | 409 |
| `PasswordHash { source: argon2::password_hash::Error }` | `the password could not be hashed` | `1` | 500 |

The address **is** part of `AlreadySubscribed` (unlike `InvalidInput`): the caller has to be told
which address is taken, and it is a value they already sent. The source of the hashing failure is
kept so the chain of `source()` stays intact (step `mailer/1.5-errors`), and a hashing failure is
the deployment's problem — it is not something a caller can fix by sending something else.

### `src/signup.rs`

`hash` is the one in the scaffold and it answers the password itself. Make it a real hash:

- `argon2` is already a dependency (the scaffold put it in `Cargo.toml`). `Argon2::default()` is
  Argon2id with the crate's recommended parameters;
- the salt is generated per call and travels inside the string that comes back — with the 0.6 API
  the hasher does that for you, so the code is two lines and there is no way to pass a fixed salt by
  accident;
- what comes back is the PHC string (`hash.to_string()`), which is what the column holds.

Then write the pipeline the whole step is about. Its shape, which is what the route will call:

```rust
pub async fn subscribe(pool: &PgPool, request: SignupRequest) -> Result<Email, Error>
```

1. **parse first**: `Email::parse`, `SubscriberName::parse`, `Password::parse` (step
   `mailer/1.10-domain-types`). Before the hash, not after: the parser's length cap is the only thing
   standing between a stranger and a request that hashes a gigabyte, and a refused value has to end
   as a 400 with **no row written**, not as a row nobody can use;
2. hash the password;
3. insert, with this statement and **this text**:

   ```sql
   INSERT INTO subscribers (email, name, password_hash) VALUES ($1, $2, $3) ON CONFLICT (email) DO NOTHING RETURNING id
   ```

   Bind the three values in that order, and ask for the row as something optional
   (`fetch_optional`) rather than as something that must exist (`fetch_one`) — “no row” is an
   ordinary answer here, not a failure. The Rust literal may be wrapped across lines; what matters is
   the *value* of the string, because that is what `sqlx` hashes (see TRAP 4);
4. a row back means this call inserted it — answer the parsed `Email`. No row means somebody else
   was already there, and that is `Error::AlreadySubscribed` with the address as it was stored
   (normalised, so the answer names the same thing the table holds).

### `src/http.rs`

One route, `POST /signup`, and one table that maps a failure to an answer. The contract the spec
judges:

| request | answer |
| --- | --- |
| a signup with three usable values | `201` and `{"status":"pending","email":"<as it was stored>"}` — no password, no hash |
| the same address again | `409`, one sentence naming the address |
| a value the domain refuses | `400`, one sentence naming the field and not the value |
| a body that is not a signup (missing field, not JSON, not an object) | `400`, one sentence about the body — and nothing quoted back from it |
| a valid signup with no database configured | `503` — the process is alive, this route is not ready (step `mailer/1.9-postgres`) |

Three details decide it:

- **the extractor has to be fallible**: take the body as `Result<Json<SignupRequest>, JsonRejection>`
  instead of a plain `Json<SignupRequest>`. A plain extractor answers with its own rejection, which
  is not this service's sentence, and the step's refusal may not quote the body;
- **one table, one rule**: write a `fn status_of(&Error) -> StatusCode` next to the handler that
  mirrors `Error::exit_code` — what the caller can fix is a 4xx, what only the deployment can fix is
  a 5xx. A 4xx repeats the failure's own sentence; a 5xx does not (the reason goes to the log, the
  caller gets a sentence that says nothing about this service's insides);
- **`Body` has to grow**: it is the JSON body of every answer that is not a success, and from this
  step it carries a sentence built from the failure, so its `status` field is a `String` rather than
  a `&'static str`.

Status codes are not decoration here: the spec's race test asks for one `201` and the rest `409`, so
an address that is taken must not come back as a 500 with the database's complaint.

## DONE WHEN

- `kiln run mailer/1.11-signup` — the spec passes (it starts a Postgres container, so the first run
  of the file takes a few seconds more than the ones before it)
- `kiln check mailer/1.11-signup` — every must gate is green
- a signup for ` Ada@Example.COM ` answers `201` with `"email":"ada@example.com"`, and the row
  holds the normalised name and `status = 'pending'`
- the same address again answers `409` and the table still holds one row
- `SELECT password_hash FROM subscribers` holds a value starting with `$argon2id$` that is not the
  password, and two subscribers who chose the same password have two different values
- a body the route cannot use answers `400` without quoting it back
- `cargo build` succeeds with no `DATABASE_URL` and no database running: the offline metadata in
  `.sqlx/` is what makes that true, and it is the reason the query is written as a macro

## TRAP

1. **`SELECT` and then `INSERT`.** The scaffold's `hash` is the loud trap; this one is the quiet one,
   and it is the reason the step exists. It passes every sequential test — the two callers in a
   manual test never overlap — and loses exactly one request the first time two people sign up in
   the same millisecond: the spec's *"concurrent signups for one address have to be decided by the
   unique constraint"* shows it as `[201, 500, 500, 500]`. No application-level lock fixes it; the
   constraint is the decision, `fetch_optional` is how you read it.
2. **Storing the password.** The scaffold's `hash` returns what it was given, so a step that only
   writes the route has a working signup endpoint and a table full of passwords. The spec's
   *"the password was stored as it was typed"* is that failure, seen from outside.
3. **One salt for everything.** A salt hard-coded, taken from the configuration, or derived from the
   address looks like a salt and is not one: identical passwords produce identical digests, which is
   the thing a salt exists to prevent. Generate it per call — the spec checks that two subscribers
   with the same password are two different values.
4. **Rewriting the statement.** `.sqlx/query-<hash>.json` is keyed by a SHA-256 of the query text the
   macro is given, and the scaffold ships the entry for the statement above and for nothing else. A
   reworded statement — a column list removed, `ON CONFLICT ON CONSTRAINT subscribers_email_key`,
   `"email"` in quotes — is a different key, and the build then stops with *set `DATABASE_URL` to use
   query macros online, or run `cargo sqlx prepare`*. Either write the statement as given, or run
   `cargo sqlx prepare` against a migrated database (the container of step `mailer/1.9-postgres` and
   `sqlx migrate run` are enough), and commit what it rewrites.
5. **`fetch_one` on an insert that may conflict.** `ON CONFLICT DO NOTHING` returning no row is a
   normal answer here, and `fetch_one` turns it into a `RowNotFound` error — a 500 for the ordinary
   case that the caller signed up second.
6. **A 500 where a 409 belongs.** Letting the unique violation reach the boundary as a database
   error passes a manual test (the log says *duplicate key*) and fails the spec: two concurrent
   signups must end as one `201` and one `409`, and a caller told “the service cannot answer this
   request” has nothing to act on.
7. **The password in the error path.** `Error::InvalidInput { value, … }` (or a 500 body that carries
   the database's complaint, which for a bad row can name a column and a value) puts a secret in a
   log line. The spec checks that a refusal does not repeat the value it refused, and TRAP 4 of step
   `mailer/1.10-domain-types` is the same rule on the parser's side.
8. **Hashing before parsing.** `Password::parse` is what caps the input at 128 characters; hash first
   and the cap protects nothing but the response time of a request that has already done the
   expensive thing. Parse, then hash, then insert.
