# HTTP skeleton: routes, extractors, honest 404 and 405

## WHY

This is the step where the service becomes something a network can talk to, and the first surface is
the one everything later is measured against. Two decisions here are hard to change later.

The first is what an *unanswered* request looks like. A service that answers every unknown path with
200 and an HTML page, or with an empty body, makes every client parse prose to find out what
happened. A 404 that says which routes exist, and a 405 that names the method that would have worked,
turn an integration bug into a five-second read.

The second is what `/healthz` means. It answers for the *process*, not for its dependencies: a
liveness probe that goes red because the database is away restarts a service that was doing exactly
what it should — and step 1.9 adds a readiness answer for the parts that can be away.

## TASK

The scaffold added `axum` and `tokio`, and put `src/http.rs` in place with two stubs: `router()` and
`serve()`. Fill them in and wire them into the binary:

- **`router()` returns the whole surface as a value.** No socket, no runtime: a test builds it and
  sends one request through it (step 1.8's app factory is built on exactly this).
- **`GET /healthz`** answers `200` with `{"status":"ok"}`, without touching anything but the process.
- **An unknown path is a `404`** with a JSON body that says so — not an empty body, and not a
  catch-all route that pretends to be a 404 handler.
- **A known path with the wrong method is a `405`** with that same JSON shape *and* the `Allow`
  header. The router knows which methods a route has; a catch-all cannot, which is why the fallback
  decorates the router's own answer instead of replacing it.
- **`HEAD /healthz`** answers `200` with no body — that is what `GET` means to the framework, and
  it should stay that way.
- **`serve(config, id)` binds the configured address**, logs the address **it actually bound** as a
  structured event (`address`), and serves until the process stops. Port `0` means "whatever is
  free", so the logged address is the only way a caller learns the port — a service that logs the
  configured `:0` is unreachable.
- **A bind that fails is a typed failure**, not a panic: the address in the message, its own
  variant in `Error`, its own row in the exit-code table, an `# Errors` section on `serve`.
- **The binary runs on a runtime** (`#[tokio::main]`), and its `Idle` path now serves instead of
  saying there is nothing to do.

## DONE WHEN

- `kiln run mailer/1.7-http` — the spec passes
- `kiln check mailer/1.7-http` — every must gate is green
- `MAILER__LOG__FORMAT=json cargo run -- --listen-port 0` prints a `listening` event with the bound
  address, and `curl -i <that address>/healthz` answers `200`
- `curl -i <address>/nope` answers `404` with a JSON body; `curl -i -X POST <address>/healthz`
  answers `405` with `allow: GET,HEAD`
- `cargo run -- --listen-port 1; echo $?` exits non-zero and names the address it could not bind

## TRAP

1. **A catch-all route instead of a fallback.** `Router::fallback` is the honest way; a
   `.route("/{*rest}", ...)` that returns 404 swallows every method too, so a `POST /healthz` answers
   *"no such route"* — the spec fails on the 405 assertion, because the router never got the chance
   to say which methods the route has.
2. **Logging the configured address.** With `--listen-port 0` the log says `127.0.0.1:0`, and every
   caller that reads it connects to nothing. The spec fails with *"the service has to log the
   address it bound … and it never did"*.
3. **Binding on a blocking socket inside `async`.** `std::net::TcpListener::accept` inside a Tokio
   task blocks the worker thread, so the first request is answered and the second one never is: the
   spec hangs until its deadline with *"the service to accept connections"*.
4. **An empty 404 body.** The status is right and a human sees nothing: the spec fails with *"a 404
   with an empty body tells a caller nothing"*.
