# Confirmation tokens: issue, verify, expire, single use

## WHY

A signup that writes a row is a signup that believes whoever typed the address. Nobody has proved
they can read mail at `ada@example.com` yet, so the row it wrote is a *claim*, and a confirmation
link is how the claim becomes a fact: the service sends one, the person who owns the mailbox clicks
it, and the row moves from `pending` to `active`. Every part of that is easy, and every way it goes
wrong is a way the token was never a token.

**Tampered.** A token nobody can guess is 32 bytes from the system's random number generator, and
it is *looked up* rather than checked. That is a design decision worth noticing: signing the token
(HMAC, JWT) instead would mean this service has to keep a secret, rotate it, and still look the row
up — because a signature says a token is *ours*, not that it is unused or unexpired. What it buys is
not needing storage at all, which is a trade this step does not need to make; what it costs is a key
that is worth stealing, which is a trade it does.

**Expired.** A confirmation link that works forever is a link in an inbox from 2019 — in a mailbox
that may have been forwarded, shared or leaked since. The window is stamped when the token is
issued, and the two clocks in this system (the application's and the database's) never have to agree
about anything: `now()` writes the expiry at the insert, and `now()` compares it at the update.
Both of those are the *database's* `now()`, which is the only clock that cannot drift from itself.

**Replayed.** This is the one that turns a token into a token: the statement that confirms the
subscriber also *refuses to act twice* — `status = 'pending'` is part of its condition, not
something read a moment earlier. Two clicks of one link, or two requests from the same mail client
prefetching it, arrive at the same row; the database decides which one changes it, and the other one
is told. Written the other way around — read the row, decide, then update — both requests read
`pending`, both update, both answer 200, and `confirmed_at` ends up being the time of the *second*
click. Step `mailer/1.11-signup` was the same lesson about inserts; this is it about updates.

What a caller gets told differs by case, and the difference is the point: a token nobody was given
is `404` (there is no such link), an expired one is `410` (that link is gone), an already confirmed
one is `409` (the link worked once, and the address is not waiting for anything), and text that is
not a token at all is `400`. A service that answers one status for all of them is a service whose
support queue is people asking what happened.

## TASK

The scaffold added `src/confirmation.rs` (the token type, the window, the parser, and an `issue`
that answers the same value for everybody) and `.sqlx/` metadata for the three statements below. The
work is the confirmation itself, plus a signup that hands out a token.

### `src/lib.rs`

Declare the module: `pub mod confirmation;`.

### `src/confirmation.rs`

`Token::issue` is the scaffold's placeholder, and a token that is the same for every subscriber is
not a token — `subscribers.confirmation_token` is `UNIQUE`, so the second subscriber collides. Make
it real: `TOKEN_BYTES` bytes from `getrandom::fill` (the dependency is already in `Cargo.toml`),
spelled with the `hex` helper that is already there. Asking the system and failing is the right
answer: a token this service makes up is a token an attacker can make up, so there is no fallback.

Then add the confirmation. Its shape, which the route will call:

```rust
pub async fn confirm(pool: &PgPool, token: &Token) -> Result<String, Error>
```

1. **one statement decides it**:

   ```sql
   UPDATE subscribers SET status = 'active', confirmed_at = now() WHERE confirmation_token = $1 AND status = 'pending' AND confirmation_expires_at > now() RETURNING email
   ```

   Ask for the row as something optional (`fetch_optional`): a row back means *this* call confirmed
the subscriber, and no row means it did not. Bind the token's text (`token.as_str()`); the text has
to match the statement byte for byte for the same reason it did in step `mailer/1.11-signup` (TRAP
4 there: `.sqlx` is keyed by the statement);
2. **only then find out why**, with a second statement that turns "no" into a sentence:

   ```sql
   SELECT email, status FROM subscribers WHERE confirmation_token = $1
   ```

   No row → `Error::TokenUnknown`. A row whose `status` is not `pending` → `Error::AlreadyConfirmed`
with that address. A row that *is* still `pending` → `Error::TokenExpired`, and that inference is
sound: the update's condition was exactly `pending AND not expired`, so a pending row it refused can
only have been refused by the expiry. The address comes back as a `String`: it came out of the table
(which only holds addresses that went through the parser on their way in), and there is nothing left
to check.

### `src/signup.rs`

The insert grows a token and an expiry, so a subscriber is never a row nobody can confirm. This
exact text:

```sql
INSERT INTO subscribers (email, name, password_hash, confirmation_token, confirmation_expires_at) VALUES ($1, $2, $3, $4, now() + make_interval(secs => $5)) ON CONFLICT (email) DO NOTHING RETURNING id
```

Bind the address, the name, the hash, the token's text, and `CONFIRMATION_WINDOW_SECS` — in that
order. Issue the token before the insert and answer it to nobody: the 201 body is what it was in
step 1.11, and the token is the thing that goes to the *mailbox*, not to the caller.

### `src/error.rs`

Four variants, all in the exit-code table (and the exit codes say the same thing the statuses do):

| variant | message | exit code | HTTP |
| --- | --- | --- | --- |
| `TokenUnknown` | `no subscriber has that confirmation token` | `2` | 404 |
| `TokenExpired` | `that confirmation token has expired` | `2` | 410 |
| `AlreadyConfirmed { email }` | `` `ada@example.com` is already confirmed `` | `2` | 409 |
| `TokenGeneration { source: getrandom::Error }` | `a confirmation token could not be issued` | `1` | 500 |

None of the three failure variants carries the token, for the reason `InvalidInput` carries no value:
a token is a secret, and a failure message ends up in a log line.

### `src/http.rs`

`GET /confirm?token=…`, and the status table grows three entries. The contract:

| request | answer |
| --- | --- |
| a token that confirms a pending subscriber | `200` and `{"status":"active","email":"<as it was stored>"}` |
| the same token again | `409`, naming the address |
| a token past its expiry | `410` |
| a well-formed token nobody was given (including one character changed) | `404` |
| text that is not a token | `400` |
| no `token` parameter at all | `400` |
| a confirmation with no database configured | `503` |

Three details:

- **the query string is parsed too**: take it as `Result<Query<ConfirmQuery>, QueryRejection>` (the
  same shape as the body in step 1.11) and run the token through `Token::parse` before anything
  else. "You sent something that is not a link" and "that link is not good" are two different
  answers for two different mistakes;
- **the 200 body is the same shape as the 201 body**: rename `SignedUp` to `SubscriberState` — it is
  no longer about signing up, it is about the state a route just changed;
- **the status table stays one rule**: `status_of` gains the three cases and the 5xx arm does not
  change. `TokenGeneration` is a 500 whose reason goes to the log.

The 201 body of step 1.11 grows nothing. A token in a signup response would be a token anybody who
can see that response can use, which is exactly the person the confirmation is meant to be
independent of.

## DONE WHEN

- `kiln run mailer/1.12-token` — the spec passes (it starts a Postgres container)
- `kiln check mailer/1.12-token` — every must gate is green
- a fresh signup leaves a 64-character hex token in the row, `confirmed_at IS NULL`, and an expiry
  about a day away, and the 201 body does not contain the token
- `GET /confirm?token=…` with that token answers `200`, and with it again answers `409` without
  moving `confirmed_at`
- moving `confirmation_expires_at` into the past (one `UPDATE` through `psql`) makes the confirm
  answer `410` and leaves the row `pending`
- two confirmations of one token arriving together end as one `200` and one `409`
- `cargo test --lib` passes: the token round-trips through its own text, two tokens differ, and
  `{:?}` does not print one

## TRAP

1. **Read, decide, update.** The same trap as 1.11 in the shape an update wears. It passes every
   sequential test and loses the first honest race: the spec's *"two confirmations of one token have
   to be decided by the database"* shows it as `[200, 200]` — both requests read `pending`, both
   answer success, and the second one moves `confirmed_at` to a time nobody clicked anything.
2. **A window that the application computes.** `Utc::now() + Duration::days(1)` bound into the
   insert, and `Utc::now()` compared at the update: two clocks, and the app's is the one that drifts
   across a fleet. The spec's window assertion (*between 23 and 25 hours from now*) is about the
   database's `now()`, and both `now()`s in the statements are the same clock.
3. **One status for every failure.** `404` for expired, `409` for tampered, `400` for everything:
   the spec checks each of them, and the reason to keep them apart is not pedantry — it is what tells
   a person who clicked an old link apart from a person who typed a broken one apart from somebody
   probing for tokens.
4. **The token in the answer, or in the error.** It is a secret exactly as much as a password is:
   the spec asserts the 201 body has no token and that no refusal echoes one. The same is true of
   log lines — the type has no `Display` on purpose, so `%token` does not compile and `?token` prints
   `<redacted>`.
5. **A cookie-cutter random token.** A counter (guessable by arithmetic), a timestamp (guessable by
   date), a UUIDv1 (a timestamp with a MAC address), `format!("{:x}", std::process::id())`: each of
   them is a token an attacker can *compute*. `getrandom::fill` is the only thing in this step that
   knows something the caller does not.
6. **Clearing the token on use, and losing the answer.** `SET … confirmation_token = NULL` looks like
   the tidy way to make a token single-use; it also makes a replayed link indistinguishable from a
   forged one, because nothing holds the value any more. What makes it single-use here is the
   `status = 'pending'` in the condition — the row *stays* the record of what happened.
7. **`fetch_one` instead of `fetch_optional`.** No row back is the *normal* answer for every failure
   this route has; `fetch_one` turns each of them into a `RowNotFound` and a 500.
8. **Trusting the second statement.** The diagnostic `SELECT` is not the decision — if it is written
   as the decision (read the status, then update), the race is back. It runs *after* the update said
   no, and it only picks the sentence. The same is true of its branch order: expired and not-pending
   are separate answers, and a row that is both gets the one that describes the state it is in.
