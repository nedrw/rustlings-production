# Authorization boundary: a subscriber only reads their own data

## WHY

Authentication answers *who is this*. It says nothing about *what may they see*, and the gap between
the two is where most real-world data leaks live: a route that authenticates properly and then
serves whatever id it was handed.

This step adds one route — `GET /subscribers/{id}/deliveries`, the messages one subscriber was owed —
and the whole of it is that boundary:

- **the id in the path is not the identity.** The session says who is asking, and the path says what
they are asking for; a handler that trusts the path has handed the decision to whoever wrote the
request. The comparison is one line, and it belongs *before* anything is read;
- **a resource somebody else owns does not exist for this caller.** The answer is `404`, not `403`. A
`403` says "this is here and it is not yours", which is a fact about somebody else's data — and a
route that says it is a route that enumerates ids for whoever asks. Making the two answers
*identical* is the point, so this step's spec checks the bodies too;
- **the query is scoped as well.** The handler's comparison is a fact about that handler; the `WHERE
subscriber_id = $1` is a fact about the statement. Both, because the second is what a later route
cannot forget: an unscoped query plus a missed check is the leak, and an unscoped query alone is one
review away from it.

There is a second reason the `WHERE` matters here, and it is the one that shows up in production: a
list built by fetching everything and filtering in Rust is a list that *was* in the process's memory
— in a log line, a panic message, a metrics dimension, or the next refactor's response body. The
database is the only place the boundary can be enforced once.

## TASK

No scaffold this time: a route, a query and one error variant, with step `mailer/1.16-sessions` and
step `mailer/1.17-newsletter` showing every shape involved. The spec is the contract.

### `src/newsletter.rs`: the read

`history(pool, subscriber) -> Result<Vec<DeliveryRecord>, Error>`: the copies of the issues one
subscriber was owed, newest first, as a list of `{issue, subject, sent_at, attempts}`. Two details
are worth copying from this step's reference solution rather than rediscovering:

- the statement is `INSERT`-free and `JOIN`s `issues` for the subject, and its only parameter is the
  subscriber (which comes from the session, never from the path);
- `sent_at` is selected as `sent_at::text`. This service reads clocks in SQL (`now()`), and a
  `TIMESTAMPTZ` read into Rust is a dependency on a time crate that nothing else here needs.

### `src/http.rs`: the route

`GET /subscribers/{id}/deliveries`, authenticated:

1. the usual readiness check (a database, and for this route nothing else) and `identity()` from the
   `Cookie` or `Authorization` header — `401` without a session;
2. compare `identity.subscriber` with the `id` from the path; if they differ, answer `Error::NotFound
{ what: "subscriber" }` — and log which id was asked for, because that is the interesting event;
3. otherwise answer `Json(history)`.

### `src/error.rs`

`Error::NotFound { what: &'static str }` — exit code `2`, status `404`, and one variant for "it is
not yours" and "it was never there" on purpose.

### What the spec judges

| the test | the claim |
| --- | --- |
| a subscriber asking for their own id | `200`, the issue's subject, and a `sent_at` for a message that was delivered |
| somebody else's id, and an id nobody has | `404` both times, with the same body — the two are indistinguishable |
| no session, and a token nobody was issued | `401` both times: being nobody is not being somebody else |
| two subscribers, two published issues | each history is the caller's own list — a query that forgot its `WHERE` would be visible as the other subscriber's rows |

## DONE WHEN

- `kiln run mailer/1.18-authz-boundary` — the spec passes
- `kiln check mailer/1.18-authz-boundary` — every must gate is green
- against a running service, `GET /subscribers/<your own id>/deliveries` answers `200` with a JSON
  list, and the same request with a *different* id answers `404` — same status and same body as an id
  that does not exist
- the service logs the refused attempt with both ids, so the boundary is observable without being
  exploitable

## TRAP

1. **Trusting the path.** `SELECT … WHERE subscriber_id = $path_id` is the leak in one statement: any
   authenticated caller reads any subscriber's history by typing a number. The session's id is the
   only id a handler may use.
2. **Filtering after the fetch.** Reading every row and then retaining the caller's is invisible in
   a test and wrong in production: the other rows were in memory, and memory is where logs, traces
   and the next refactor read from. The boundary belongs in the statement.
3. **`403` for somebody else's resource.** It reads as the polite answer and it is the leak: `403`
   confirms that the id exists, which turns a protected route into an enumeration oracle. `404` for
   both cases — and the same body, which is why this spec compares bodies.
4. **Comparing after reading.** Doing the work and then checking whose it was leaks through timing,
   through side effects (a write is harder to take back than a read), and through every log line
   written in between. The check goes first, or the query is scoped — ideally both.
5. **A route that authenticates and stops there.** The most common shape of this bug in reviews:
   `identity()` is called, the id from the path is used, and the session's subscriber is never
   mentioned again. Authentication at the top of a handler is not authorization; it is the input to
   it.
6. **Scoping by the wrong key.** Scoping by something the caller controls — an email address in a
   query string, a "tenant" header, an id in a body — is the same bug with extra steps. The one
   value a request cannot forge is the one the session resolved.
