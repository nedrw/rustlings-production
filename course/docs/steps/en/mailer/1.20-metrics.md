# Metrics and an SLO baseline

## WHY

Step `mailer/1.6-logging` gave this service a way to say what happened: one JSON line per event, with
fields. Logs answer *what happened to this request*, one request at a time, and they are the wrong
tool for the other question a service has to answer about itself: **how is this service doing, right
now?** For that you need numbers that are cheap to add up, fixed in shape, and exportable to
something that draws graphs and pages a person at three in the morning. That is what metrics are.

Three decisions come with them, and each of them is a way to get it wrong:

1. **the names and the labels are an API.** A dashboard, an alert rule and a runbook are all written
   against `http_requests_total{route,status}`. Renaming a label does not break the build; it breaks
   the graph that somebody is staring at during an incident, which is the worst possible time to
   find out. So the vocabulary lives in one file (this step's `src/metrics.rs`), and the spec pins
   it as a *snapshot*: a rename is a red build, not a silent silence;
2. **cardinality is bounded.** This is the one that costs money and takes experience to see. A label
   whose value comes from the request — a path with an id in it, an address, an error message —
   turns one series into thousands, and a metric store into an expensive accident. So `route` is the
   route the *router matched* (`/subscribers/{id}/deliveries` for every subscriber, `/signup` for
   every signup), and a path nobody routed is the pattern it matched, `/{*rest}`, not the string a
   stranger sent. That is also why this step turned the 404 handler into a route: **something you
   cannot match is something you cannot count**;
3. **a delivery's three endings are three numbers.** Step
   `mailer/1.15-idempotent-delivery` made them three — a message that was taken, an attempt that
   failed and will be retried, a message nobody will send — and one "errors" counter would make a
   message that was retried and delivered indistinguishable from one that was given up on. The
   `deliveries_total{outcome}` label is the difference between an alert that says *the mail server is
   unwell* and one that says *a subscriber will never hear from us*.

**And the part this step is honest about not having**: an SLO. A metric is an ingredient; an SLO is an
agreement about a number, and an agreement needs somebody to agree. The step's DONE WHEN asks for a
first draft — an indicator, a target, a window — but the enforcement belongs in a deployment
(`alertmanager`, a dashboard, a review), not in a course repository. What is here is the part a
machine can check.

## TASK

The scaffold added `src/metrics.rs`, and the hole is the part a scraper actually reads:

- the registry is there — counters by `(route, status)`, a histogram by route, counters by delivery
  outcome — and `record_request`/`record_delivery` are written;
- `render()` writes the `# HELP` and `# TYPE` line of every family and **no samples at all**: what
  this process has counted is invisible until the step writes the lines.

### `src/metrics.rs`: the exposition

Write the samples: one line per series, `name{labels} value`, sorted (by name, then by label), so two
scrapes of the same state are the same bytes — which is what makes the spec's snapshot a test rather
than a coin toss. For a histogram that means the buckets in growing order, a `+Inf` bucket, and the
`_sum` and `_count` of the family.

### `src/lib.rs` and `src/http.rs`

- declare the module (`pub mod metrics;`);
- `AppState` holds one `Metrics` for the process, built in `start_with_sender` and shared with the
  delivery queue, with `metrics()` handing it to the endpoint;
- `GET /metrics` answers with `state.metrics().render()` as `text/plain; version=0.0.4` — the
  content type every scraper understands;
- **one middleware counts every request**: `middleware::from_fn_with_state(state.clone(), measure)`,
  wrapped around the whole router. Two details are the step:
  - `MatchedPath` is the route *pattern*, never the concrete path (that is decision 2 above);
  - the layer must be the **last** call on the router, because a router layer wraps the routes that
    exist when it is applied — a route declared after it is a route nobody counts. (The spec catches
    exactly that: `/metrics` itself would count, and `/confirm` would not.)
- the 404 handler becomes a route: `.route("/{*rest}", get(not_found))` instead of `.fallback(…)`,
  because a fallback is not layered and would be the one answer this service does not count.

### `src/delivery.rs`

The worker is the only thing that knows how a message ended, so it is what counts: `Sent` on the
send that worked, `Failed` on every attempt that did not (retries included — it is the number that
says the mail server is unwell), and `GivenUp` when the attempts ran out. `Queue::start` takes the
registry along with the sender and the pool.

### What the spec judges

| the test | the claim |
| --- | --- |
| two requests, two routes | `http_requests_total{route="/healthz",status="200"}` and `{route="/signup",status="400"}` are counted separately |
| two paths nobody routed | *one* series for both, and the paths themselves appear nowhere in the exposition |
| the vocabulary | the set of `# HELP` families is exactly the three this service declares — the snapshot that fails on a rename — plus a histogram whose `+Inf` bucket equals its count |
| a delivered message | `deliveries_total{outcome="sent"} 1`, and no `failed` at all |
| a mail server that is away | `failed` counts every attempt, `given_up` counts the message once: three and one, from the same signup |

## DONE WHEN

- `kiln run mailer/1.20-metrics` — the spec passes
- `kiln check mailer/1.20-metrics` — every must gate is green
- against a running service, `curl /metrics` shows one line per series, and two `curl`s a second
  apart show a counter that moved
- a request for a path nobody routed adds exactly one series, called `/{*rest}` — and the path you
  asked for is nowhere in the output
- a draft SLO exists somewhere a person will read it: one sentence naming the indicator
  (`http_request_duration_seconds` at `POST /signup`), the target (e.g. *99% under 250 ms*) and the
  window (e.g. *28 days*). Nothing enforces it — that is the next deployment's job — and writing it
  down is what makes the next alert rule a derivation rather than a guess

## TRAP

1. **A label that comes from the request.** `route=path` looks helpful and is how one metric becomes
   one series per URL a scanner tries; the same mistake with `email`, `token` or an error message is
   worse, because those values are unbounded *and* sensitive. Labels are a fixed vocabulary, and
   values that arrive from outside are bucketed into it or dropped.
2. **A layer in the wrong place.** `Router::layer` wraps the routes that exist *when it is applied*.
   Put it in the middle of the chain (as this step's first attempt did) and every route declared
   after it — `/confirm`, `/newsletter`, the 404 catch-all — is invisible to the metric: the
   dashboard is not wrong, it is *missing*, which is harder to notice. The spec's second test is the
   observation.
3. **A metric that resets.** A counter built per request is a counter that always reads 1, and a
   registry cloned per handler is a number nothing shares. The registry belongs to the process, and
   everything that counts gets a clone of *that* `Arc`.
4. **Counting what you can, not what matters.** Requests are easy to count and rarely the question;
   the delivery outcomes — the thing a subscriber notices — are the step's real content. A service
   with a beautiful request histogram and no idea how many messages are stuck is a service with
   dashboards and no alerts.
5. **Averages.** `_sum`/`_count` invites an average, and an average latency is a number no user
   ever experienced: one slow request in a thousand disappears into it. Percentiles from buckets
   (`histogram_quantile` in PromQL, or a quantile over a window) are what the SLO should be written
   against.
6. **Forgetting that this endpoint is public.** `/metrics` is unauthenticated, which is the common
   shape (a scraper is not a subscriber) and a leak in the common misconfiguration (a process whose
   listener is the internet). It belongs on an interface nothing else can reach — step
   `mailer/1.21-container` is where that becomes a real decision — and what must never happen is a
   label that carries a secret, which is why trap 1 is the first one.
