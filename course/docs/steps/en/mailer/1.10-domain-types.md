# Domain types: parse, don't validate

## WHY

A service that takes text from strangers spends its life deciding whether that text is usable. The
usual shape of that is a `String` that travels everywhere and a `validate_email` call somebody makes
at the edge — and then a second call in the handler that reads from the queue, because the first one
wasn't enough, and a third that nobody remembers to add. Nothing in the type says an address was
checked, so nothing can be trusted, so everything is checked again.

This step replaces that with two things:

- **a type that only the parser can build**: `Email`, `SubscriberName` and `Password` all hold a
  private `String`, have no public constructor, and answer `parse` or nothing. A function that takes
  an `Email` has been *told* that the address was checked — by the compiler, not by a comment.
- **a parser that answers a value, not a verdict**: the result is not "valid" but the canonical form
  the service stores. That is where normalisation belongs: `Ada@Example.com` and `ada@example.com`
  are one subscriber, and step `mailer/1.9-postgres`'s `UNIQUE (email)` compares bytes. Deciding that
  here, once, is what keeps step `mailer/1.11-signup` from having to think about it.

There is a third decision, smaller and easier to get wrong: **a password is a secret, and a secret is
not a `String`**. It is not trimmed (spaces are part of it), it does not come out of `{:?}`, and no
failure message quotes it back — messages end up in log lines (step `mailer/1.6-logging`), and a
password in a log is a password that has to be rotated.

## TASK

The scaffold added `src/domain.rs` with the three types, the limits and no checks at all: every
`parse` keeps what it was given, and `Password` carries the derived `Debug`. Turn them into parsers,
and put the types where the rest of the code can reach them.

### The rules, and the limits

The values are part of the contract — the spec asks about exactly these numbers:

| type | accepts | refuses |
| --- | --- | --- |
| `Email` | at most `MAX_EMAIL_LENGTH` (254) bytes; exactly one `@`; a local part of 1–64 bytes of letters, digits, `.`, `_`, `+`, `-` with no dot at either end and no `..`; a domain of labels separated by dots, each label of letters, digits and `-` with no `-` at either end | no `@` or more than one, an empty local part or domain, a domain without a dot or with an empty label, anything outside the sets above (which includes spaces, control characters and non-ASCII, quoted local parts and IP-literal domains) |
| `SubscriberName` | 1–100 characters after trimming; single spaces between words; any letters, including non-ASCII | empty or only spaces, control characters (including `\n` and `\t`), more than 100 characters |
| `Password` | 12–128 characters, **exactly as typed** | fewer than 12, more than 128, control characters |

What the parsers produce is *canonical*:

- `Email`: trimmed, lower-cased — the whole address, because the database has to see one spelling.
- `SubscriberName`: trimmed, and runs of spaces collapsed to one.
- `Password`: unchanged. `as_str()` returns exactly what the caller typed, spaces and all.

Canonical means the parser is a fixed point: parsing what it produced is a no-op. The spec checks
that property over a generated set of addresses, not just over a handful of samples.

### The refusal

Add one variant to `src/error.rs`, and use it from all three parsers:

```rust
Error::InvalidInput { field: &'static str, expected: &'static str }
```

`field` is `"email"`, `"name"` or `"password"`; `expected` is what the value would have had to be,
phrased for a message (the table above is the source; the spec asserts a fragment of each). The
message reads `` the email is not an address with exactly one `@` ``.

The value that was refused is deliberately **not** in the variant: it may be a password. Add the
variant to the exit-code table too — a value the caller sent is the caller's to fix, which is code
`2` (and the answer a 400 will be made of in step `mailer/1.11-signup`).

### Where they live

`pub mod domain;` in `src/lib.rs`, because the rest of the service is about to start taking these
types. Nothing else changes yet: no route takes an `Email`, no handler returns one — this step is
about the values themselves, and the spec judges them from *outside* the crate, through a probe that
depends on your project by path (the same trick step `mailer/1.5-errors` uses for the error enum).

### What the spec does not test, and why

That no *other* constructor exists is not a runtime fact: it is the shape of the code, and the way to
check it is to read `src/domain.rs` for public fields, `pub fn new`, `From<&str>` and `Deserialize`
impls. The spec instead pins what a wrong constructor would break — normalisation, idempotence, the
refusals, and the redaction — and the TRAP section lists the escape hatches to keep closed.

## DONE WHEN

- `kiln run mailer/1.10-domain-types` — the spec passes (it compiles and runs a probe crate, so the
  first run takes a little longer than the later ones)
- `kiln check mailer/1.10-domain-types` — every must gate is green
- `Email::parse("Ada@Example.COM").unwrap().as_str()` is `"ada@example.com"`, and parsing it again
  gives the same value
- every sample in the spec's refusal table is refused, and the message names the field and what it
  expected — never the value
- `format!("{:?}", Password::parse("correct horse battery staple").unwrap())` does not contain the
  password
- `cargo doc --no-deps -p mailer` builds: a type whose rules are only in the step's body is a rule
  the next reader cannot find

## TRAP

1. **A derived `Debug` on `Password`.** The scaffold has it, and it is exactly what puts a password
   into a log line, a panic message or a `tracing` field the day somebody writes `info!(?password, …)`.
   The spec's *"`Debug` reaches log lines and panics"* is that failure, seen from outside. Write the
   impl by hand and say only that there is a secret in there — not even how long it is.
2. **Trimming a password.** `value.trim()` reads like tidying up and breaks real logins: a password
   with a leading space is a password. The spec's *"a password is not trimmed, collapsed or
   lower-cased"* is what a learner sees after making that change.
3. **Quoting the value in the failure.** `Error::InvalidInput { value, .. }` looks helpful — until a
   password is refused and the message lands in a log. The spec checks the message for the refused
   text.
4. **A second door.** `pub struct Email(pub String)`, `impl From<&str> for Email`, `#[derive(Deserialize)]`
   on the type, or a `Default` — each of them is a way to get an `Email` that was never parsed, and
   the whole point of the type is that there is none. If a value has to come from JSON (step
   `mailer/1.11-signup`), deserialise a raw string *and parse it*: the door is a function that goes
   through `parse`.
5. **Normalising in the wrong place.** Lower-casing at the point of insertion, or in the handler, or
   in the query (“`WHERE lower(email) = lower($1)`”) means two spellings live in the table, the unique
   constraint never fires, and step 1.11's race has two winners. Normalise in the parser, once.
6. **A parser that accepts too much.** An empty string is not an address, `ada@example` is not one,
   and `ada@-example.com` is not one. Every one of them is in the spec's refusal table, and each of
   them is a row a real service has had a bug about.
7. **A regex crate for this.** A pattern is unreadable, unmaintainable, and — for email — famously
   wrong in both directions. The rules above are thirty lines of code that say what this service
   accepts, which is a *smaller* claim than what RFC 5322 allows, and the honest one.
