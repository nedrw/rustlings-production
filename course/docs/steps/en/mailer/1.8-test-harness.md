# End-to-end test harness: an app factory on a random port

## WHY

The first test that needs a running service is also the first test that can be flaky. A fixed port
means two tests cannot run at once — and `cargo test` runs them at once, which is why the failure
shows up in whichever test happened to run second. A `static` app started once means one test's
state is the next test's starting condition. A harness that rebuilds the router by hand means the
tests pass against something the binary does not serve.

This step pays for all of that once. Every test after it — and there are many, from signup to
newsletter to shutdown — starts its own service, on a port the operating system picked, built out of
the same pieces `main.rs` builds, and stops it at the end. That is the whole value of a harness: the
tests stay short because the boring part is somewhere else, and they stay honest because the boring
part is the real thing.

## TASK

The scaffold put `tests/support/mod.rs` in place with the shape of a `TestApp` and no behaviour.
That file is plain project code — cargo does not treat anything under `tests/support/` as a test
target, so the specs pull it in with `mod support;` and both the specs and your own tests use the
same factory. Fill it in:

- **`TestApp::start(config)`** binds `127.0.0.1:0`, asks the socket which port it got, and serves the
  application on a listener of its own. The port in `config` is ignored: a test that could choose its
  port would choose one another test is using.
- **Serve the app the binary serves.** That needs one change in the library: split `http::serve` into
  "bind, then serve on the listener" so the harness can take the second half (`serve_on`), which is
  also what makes the port knowable before the first request.
- **Run the service in a thread of its own**, with its own Tokio runtime. A test is then an ordinary
  blocking `#[test]`, and the harness owns the runtime it will never nest inside another.
- **A tiny HTTP client** (`get`, `post`, `request`) speaking HTTP/1.1 over `std::net`, so a test is
  three lines: start, request, assert. `Connection: close` keeps every answer finite.
- **`stop` and `Drop`** shut the app down and join its thread — a stopped app must stop *accepting*,
  and a test that forgets to call `stop` must still not leak a thread.
- **No coordination with any other test**: no fixed port, no shared file, no `static`. The spec runs
  three apps at once and stops one in the middle to make sure of it.

## DONE WHEN

- `kiln run mailer/1.8-test-harness` — the spec passes
- `kiln check mailer/1.8-test-harness` — every must gate is green
- adding a throwaway `#[test]` that starts a `TestApp` and asserts `GET /healthz` is `200`, then
  running `cargo test` twice in a row, passes both times
- `cargo test -p mailer -- --test-threads=1` and `--test-threads=8` give the same result

## TRAP

1. **A fixed port.** It works alone and fails in company: the second test panics with *"Address
   already in use"* from the harness, or — worse — the two tests take turns answering each other's
   requests. The spec's *"three apps share one port"* failure is the same defect seen from the
   inside.
2. **One app for the whole binary.** A `static`/`OnceLock` app, or a port kept in a global, makes
   every test a continuation of the last one. The spec fails with *"stopping one app stopped
   another"*: the promise is one app per test, and only the harness can keep it.
3. **A router built in the harness.** Assembling just the routes a test needs is the shortest path
   to a green suite that says nothing about the service: the spec fails on the 404/405 assertions
   with *"the factory has to serve the same fallbacks as the binary, not a router of its own"*.
4. **A runtime inside a runtime.** Building a Tokio runtime inside the test's own async runtime, or
   calling `block_on` from one, panics with *"Cannot start a runtime from within a runtime"*. The
   harness owns one runtime, in its own thread; the test only sends requests.
