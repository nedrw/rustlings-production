# Pin the toolchain, formatting and lint policy

## WHY

"It compiles on my machine" is a version number nobody wrote down. A service built with `stable`
compiles with a different compiler next month, and a lint that is a warning today is an error in a
later toolchain — so the build breaks for whoever runs it next, in a commit that changed nothing.
The same goes the other way: a public service without an MSRV line accepts a dependency bump that
quietly raises the compiler a user needs, and the breakage shows up in their build, not yours.

Formatting and lint levels belong in the repository for the same reason: every review spends time on
whitespace, or on the one `unwrap` that reviewer A cares about and reviewer B does not, and none of
that is a decision anyone can look up later. Written down, they are a property of the project that a
tool enforces.

## TASK

Add three files' worth of policy to `app/mailer`. Nothing here is scaffolded: these are decisions,
and a decision someone else made for you is not a decision.

- `rust-toolchain.toml` pins `channel` to a concrete three-part version (not `stable`), and lists
  `rustfmt` and `clippy` as components, because the next step's task runs both.
- `rustfmt.toml` moves the style settings out of review: at least `edition` and `max_width`. The
  course repository's own `rustfmt.toml` is a working example, and `cargo fmt --all --check` is the
  gate that holds you to yours.
- `Cargo.toml` declares `rust-version` (the minimum a user needs) and `[lints] workspace = true`,
  and the `[workspace.lints]` tables deny what every target must respect:

```toml
[workspace.lints.rust]
missing_docs = "deny"
unsafe_code = "forbid"

[workspace.lints.clippy]
dbg_macro = "deny"
todo = "deny"
unimplemented = "deny"
```

Only lints that hold for *every* target belong in that table. Tests may `unwrap`, and a binary may
print; those belong to the ladder's rungs, which the gates pass on the command line (step 3 wires
them into one command). Putting `unwrap_used` or `print_stdout` in the workspace table is a mistake
with a specific symptom: the first test that asserts something fails to compile.

The spec checks that the pin is real — the compiler running the test reports the pinned version —
that the declared MSRV is satisfied by the pin, and that the policy bites. It proves the last one by
writing a small file into `tests/`, compiling it with `cargo clippy`, and requiring the build to
fail. A lint table that nothing ever observes is decoration.

## DONE WHEN

- `kiln run mailer/1.2-toolchain` — the spec passes
- `kiln check mailer/1.2-toolchain` — every must gate is green, including `fmt` and `clippy@1`
- `rustup show` in `app/mailer` reports the pinned toolchain

## TRAP

1. **Declaring the lints but not inheriting them.** `[workspace.lints]` is inert until the package
   opts in with `[lints] workspace = true`; without it the fixture compiles cleanly, `clippy` says
   nothing, and the spec fails with *"the lint policy does not bite"* rather than a lint error —
   which is exactly the confusing half hour this assertion exists to prevent.
2. **Putting `unwrap_used` in the workspace table.** It then applies to test targets too, and
   `cargo clippy` fails on the first `assert_eq!(x.unwrap(), y)` in a test. Rung 2 of the ladder
   denies it for production targets only, and the gates know the difference; the workspace table
   does not.
3. **Writing `channel = "stable"`.** Nothing fails today and everything fails later: the build
   picks up whatever rustup has at that moment, and `rustc --version` stops matching the file. The
   spec compares the two, so this one is caught immediately.
