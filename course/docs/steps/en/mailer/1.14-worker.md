# Background delivery worker: bounded queue, drain on shutdown

## WHY

Step `mailer/1.13-email-port` made "send an email" a value the service can hand to somebody else — and
handed it over *inside the request*. This step takes that trade back:

```rust
// src/signup.rs, as step 1.13 left it
if let Err(error) = sender.send(message).await {
    warn!(%error, to = %email, "the confirmation email could not be sent");
}
```

Three things are wrong with those two lines, and only the first one is about speed:

- **the caller pays for the mail server**: `POST /signup` now takes as long as SMTP takes, and a mail
  server that has stopped answering makes the *signup* path stop answering;
- **there is no bound**: nothing says how much of this work the process has taken on. A burst of
  signups, a slow server, a retry storm — they all pile up in the request path, and the place they
  pile up in is the one place that has to stay fast;
- **a failure has nowhere to go**: one attempt, one log line. The subscriber exists and the
  confirmation email does not, and nothing in the service knows the difference.

So the message goes into a **queue** and the request answers; one worker task behind the queue does
the sending. Four decisions come with that, and every one of them is a way to get it wrong:

1. **the queue is bounded** (`QUEUE_CAPACITY`). An unbounded queue is not a queue, it is a promise to
   run out of memory later. The bound is what turns "we have taken on more than we have finished"
   into an answer a caller can act on: a `503`, which says *come back*, rather than a `500`, which
   says *something here is broken*;
2. **capacity is taken before the work it is for**. The handler reserves a seat *before* the insert
   and sends on it after the row is written. A signup refused because the queue is full has therefore
   written nothing, so a client that retries gets a fresh chance. A signup that wrote the row and
   *then* learned the queue was full created a subscriber nobody can ever confirm, and its retry is
   answered `409` by that very row — a dead end built out of a `503`;
3. **a failed send is retried, with jitter**. `MAX_ATTEMPTS` attempts, each waiting a random delay in
   `[0, min(cap, base · 2ⁿ))`. The randomness is not decoration: when one mail server comes back,
   every worker in the fleet is holding the same failure, and they must not arrive at the same
   moment;
4. **stopping is a sequence**. A process that is asked to stop — a container being replaced, a
   deploy, a person at a terminal — should stop *taking* work, finish the work already taken, and
   only then exit. And it must do that inside a deadline (`DRAIN_DEADLINE`), because whoever asked
   politely also has a `SIGKILL` for the process that will not stop, and being killed mid-send is how
   a message disappears.

**And the boundary that has to be said out loud**: this queue lives in memory, so it is *not* the
record of what still has to be delivered. Kill the process and whatever it held is gone; the rows are
the record of who still has to be told something. Guaranteed delivery — an outbox, a claim on each
row, a delivery state machine — is later work: step `mailer/1.15-idempotent-delivery` starts it by
making "this message has already gone out" a fact in the database. What this step buys is a request
path that does not depend on the mail server, and a process that can be stopped without throwing away
the work it accepted.

## TASK

The scaffold added `src/delivery.rs` as the shape of a first draft, and it is deliberately the shape a
first draft reaches for: a `Queue` that is not a queue (a task per message), a `Seat` that costs
nothing, a `backoff` that answers the base every time, a `drain` that answers `0` without waiting. Its
module doc is the list of the four decisions above. The task is to make each of them true and then to
use the queue from the request, the server, and the binary.

### `src/lib.rs`

Declare the module: `pub mod delivery;`.

### `src/delivery.rs`: one queue, one worker

- `Queue::start(sender: Arc<dyn EmailSender>) -> Self` creates the channel and **spawns one worker
  task** that owns the receiving half for its whole life: `while let Some(message) = rx.recv().await`,
  each message sent with the retry policy below. When the loop ends — the queue is closed and empty —
  the worker logs `the delivery queue drained` with the number it delivered, and answers it.
- the channel is `tokio::sync::mpsc::channel::<Message>(QUEUE_CAPACITY)`: bounded, because that is what
  makes a `503` possible. Tokio's own queue is the right primitive here — a third-party one (kanal,
  flume, crossbeam) wins microbenchmarks that have nothing to do with this step's bottleneck (a
  password hash, a mail server) and would bring its own cancellation semantics into the shutdown
  path;
- `Queue::reserve(&self) -> Result<Permit<'_, Message>, Error>` is `self.jobs.try_reserve()` mapped to
  `Error::QueueFull`. A `Permit` is the seat: *the room is already yours*, so the send that follows
  cannot fail and cannot wait. It is also the answer to a subtle bug — a `mpsc::Sender::send(…)`
  cancelled inside a `select!` loses the message (tokio's own documentation says so), a reserved
  permit does not. `permit.send(message)` is not `async`, and that is the point: the waiting happened
  before the caller had anything to lose;
- `Queue::drain(self, deadline) -> Result<usize, Error>` stops the worker from taking new work — a
  `watch` channel the worker selects on, or a `close()` plus dropping the sending half, whichever
  names "no new messages" most clearly — and then waits for the worker's `JoinHandle` under
  `tokio::time::timeout(deadline, …)`. The elapsed deadline is `Error::DrainTimeout`; a worker that
  was gone is `Error::WorkerLost`. Taking `self` is not decoration either: it is the only handle that
  may wait for the worker, so a second caller cannot race this one;
- the scaffold's `Seat` type disappears: the permit *is* the seat, and the scaffold's version was
  there to show where one goes;
- the worker retries: up to `MAX_ATTEMPTS` attempts, sleeping `backoff(attempt)` in between. A message
  that still fails on the last attempt is `error!`ed with its reason and its address, and the worker
  moves on to the next message — one unreachable address must not stop the queue;
- `backoff(attempt) -> Duration` is a **pure function**, and that is a decision: *full jitter* is
  `random(0, min(RETRY_CAP, RETRY_BASE · 2ⁿ))`, the randomness comes from `getrandom` (never from the
  clock — a test has to be able to run it with time paused, and a clock-seeded jitter is a value a
  test can never predict), and a generator that fails falls back to the ceiling rather than refusing
  to retry.

### `src/error.rs`

`Error::QueueFull` — the queue is full: the deployment's problem, exit code `1`, HTTP `503`.
`Error::DrainTimeout` and `Error::WorkerLost` — the drain did not finish. None of these is the
caller's to fix, which is why none of them is a `2`.

### `src/http.rs`

- `AppState` carries the `Queue` (`delivery: Queue`), built in `start_with_sender` from the sender the
  caller chose, with `delivery()` handing a handler the queue. `sender()` goes away: the state no
  longer has a sender to reach, and a handler that could send directly could bypass the queue — the
  type is the design;
- `/signup` reserves **first**: `let seat = state.delivery().reserve()` → `subscribe(pool, seat,
  request)`;
- `serve` and `serve_on` grow twins that take a shutdown future: `serve_with_shutdown(state, id,
  shutdown)` and `serve_on_with_shutdown(listener, state, id, shutdown)`, built on
  `axum::serve(…).with_graceful_shutdown(shutdown)`. The versions without it stay as one-line calls
  that pass `std::future::pending()`: the test harness stops this server by *dropping* the future, and
  nothing about the harness has to change;
- the status table gains one line: `Error::QueueFull` → `503 Service Unavailable`.

### `src/signup.rs`

`subscribe(pool: &PgPool, seat: Permit<'_, Message>, request: SignupRequest)` — the seat is an
argument, so "capacity before the work" is enforced by the type rather than by a comment. Nothing
else about the pipeline changes: parse, hash, insert. Then, on the arm where the insert won,
`seat.send(confirmation_message(email.clone(), &token))` — not awaited, because there is nothing left
to wait for. The arm where the address was already taken simply drops the seat: its room goes back to
the queue, because a signup that sends no message must not cost a slot.

### `src/main.rs`

The binary is where a *process* stops, so the sequence lives here:

1. wait for the signal — `SIGTERM` (`tokio::signal::unix::signal(SignalKind::terminate())`) or
   `ctrl_c`;
2. `serve_with_shutdown(state.clone(), &id, shutdown())`: stop accepting, and finish the requests
   that are already in flight;
3. keep the queue handle across that call, then `drop(state)` and `drain(DRAIN_DEADLINE)`;
4. exit `0` when the drain finished — the worker has already logged what it delivered — and `1` when
   it did not, with `error!` naming what was left behind.

None of this belongs in the library: a signal is a property of a process, and a test that drives the
library has no signals to wait for.

### The unit tests: `backoff` and the drain deadline

The claims that are *about time* belong in unit tests in `src/delivery.rs`, with
`#[tokio::test(start_paused = true)]` and a sender that fails on purpose: a retry happens exactly
`MAX_ATTEMPTS` times, a wait is bounded by the cap, jitter is not a constant, a drain gives up on its
deadline. That needs `tokio`'s `test-util` feature — add it to the `tokio` line inside the
`kiln:scaffold:begin` block of `Cargo.toml` — the region scaffolds may write into, and therefore
the region where a dependency may change. A test that waits for real seconds to watch a
backoff is a test that makes the whole suite slow and flaky; the paused clock is the injected clock
this course asks for (authoring.md §6.4).

### What the spec judges

| the test | the claim |
| --- | --- |
| a sender that never answers | `201` while the send is still outstanding — the answer is the queue's, not the sender's |
| the queue, filled by signups | at least one `503`, and `rows == accepted`: a refusal wrote nothing |
| a sender that refuses once | the message arrives by its *retry*: one refusal, one delivery, no second request |
| a sender that keeps failing | the first message is attempted `MAX_ATTEMPTS` times and the *next* message is served: the queue moved on instead of retrying forever |
| `SIGTERM` to the process | exit code `0`, `the delivery queue drained` in the log, and the queued confirmation email sent before the exit |

- `kiln run mailer/1.14-worker` — the spec passes
- `kiln check mailer/1.14-worker` — every must gate is green
- `cargo test --lib` passes, including the paused-clock tests of `backoff` and the drain deadline
- `cargo test -p mailer --test spec_worker` passes if you would rather watch the spec directly
- a signup through the running service logs the confirmation email *after* the `201`, and a
  `kill -TERM <pid>` on that process exits `0` with `the delivery queue drained` in its log
- filling the queue (a sender that hangs, signups until it refuses) answers `503` for the last one
  and leaves `SELECT count(*) FROM subscribers` where it was

## TRAP

1. **An unbounded queue, or a task per message.** The scaffold's `tokio::spawn` per message compiles,
   passes everything that does not push the service past its bound, and fails as memory growth under
   load. The spec's *"at least one `503`"* is the observation, and the row count is its other half:
   a queue that never fills never refuses, so the refusal has to be *reachable*.
2. **`try_send` and a lost message.** Refusing to wait is right; refusing to answer is not.
   `try_send` that returns `Err(Full)` while the handler logs a warning turns a full queue into
   silently lost signups. A seat is what lets the request be refused *before* it has anything to
   lose.
3. **Reserving after the insert.** Writing the row and then queueing the message moves the refusal
   onto a subscriber that already exists — the `503` a client acted on becomes a `409` it cannot fix.
   The scaffold's own shape is the same bug in another spelling: sending on the seat inside the
   request path, where the caller still waits for the mail server.
4. **`send()` where a permit is needed.** `sender.send(message)` inside a `select!`, or awaited right
   after checking that there is room, is cancel-unsafe for the message and races the shutdown. The
   shape that cannot lose anything is `try_reserve()` → do the work → `permit.send(message)`.
5. **A `500` for a full queue.** The status table has a default arm, and `Error::QueueFull` falling
   into it tells a client that could have retried that the service is broken. `503` is the one answer
   that says "not now".
6. **Draining before stopping.** Calling `drain` while the server still accepts requests closes the
   queue under the requests that are arriving: capacity is free and they are refused anyway, and a
   permit held by a request still in flight can outlive the worker that was supposed to send it. The
   order is: stop taking requests → drain → exit.
7. **A drain without a deadline.** `worker.await` instead of `timeout(deadline, worker)`: one mail
   server that never answers holds the process open until the orchestrator loses patience and kills
   it, and the messages that *could* have gone out are dropped with the process. The deadline turns
   "stuck" into an exit code somebody can alert on. No spec can see this one through the running
   service — this build's adapter never blocks — so the *unit test* on `drain` is the only thing
   standing between you and a process that has to be killed: `Hanging` sender, one message, a
   deadline of a few milliseconds, an assertion that the drain answers `Err` instead of waiting.
8. **Retrying in lockstep.** A fixed delay, or `base · 2ⁿ` with no jitter, brings the whole fleet
   back to a recovering mail server at the same instant, with the same backlog. No spec catches
   this one — the unit test on `backoff` is where it is decided, which is also why the randomness is
   an argument-free pure function and comes from `getrandom` rather than from the clock.
9. **Sleeping a real clock in a test.** `#[tokio::test] async fn a_retry_waits() { … sleep(300ms) …
   assert }` is slow, flaky, and asserts the wrong thing: `start_paused = true` moves the clock, so the
   delay becomes a value the test can read instead of a duration it has to survive.
10. **Forgetting what the queue is not.** An in-memory queue that is treated as the record of what
    must be delivered is a promise the process cannot keep — it is killed, and the record is gone.
    The rows are the record; this step only makes the request path independent of the mail server.
