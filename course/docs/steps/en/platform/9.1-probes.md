# Liveness is about the process, readiness is about serving

## WHY

A Kubernetes probe is one question asked on a timer, and the *consequence* of a wrong answer is
where the damage is:

- a **failed liveness** probe restarts the process — so a liveness probe that checks the database
  restarts a perfectly healthy service every time the database blinks, turning one dependency outage
  into a restart loop;
- a **failed readiness** probe only takes the pod out of the Service's endpoints — so readiness is
  where dependencies belong, and it must check something real, because a readiness probe that always
  passes lets traffic reach a pod that cannot serve.

The split is one sentence: **liveness answers "is this process alive", readiness answers "can it do
its job right now"**. Mailer 1.9 introduced the difference with `/healthz` and `/readyz`; this step is
the manifest side of the same decision.

## TASK

The scaffold put `src/lib.rs` in place with `Probes` and `Finding`; `audit` is the stub.

- **[`audit`]** — every problem with the wiring, sorted:
  [`Finding::LivenessChecksDependency`] for a liveness probe that reads a dependency,
  [`Finding::NoReadinessProbe`] when there is none, and [`Finding::ReadinessAlwaysPasses`] when the
  readiness probe exists and checks nothing.
- **A manifest with no readiness probe has no "always passes" problem** — the two are alternatives,
  not a list of everything missing.

## DONE WHEN

- `kiln run platform/9.1-probes` — the spec passes
- `kiln check platform/9.1-probes` — every must gate is green
- liveness on the process and readiness on serving is clean; a liveness probe that reads the database
  is not

## TRAP

1. **The same endpoint for both.** It is the most common wiring and it collapses the two questions:
   either a dependency fault restarts the process (liveness on `/readyz`) or a dead pod keeps
   receiving traffic (readiness on `/healthz`). The spec cannot see endpoints; the prose can.
2. **A liveness probe on `/readyz`.** The dependency blinks, every pod restarts, and the restart is
   the outage.
3. **No readiness probe at all.** Rolling updates then replace pods before the new ones can serve,
   and a rollout that looked green sends 502s.
4. **A readiness probe that only returns 200.** It is worse than none, because it looks like a check;
   the spec's *"a probe that says nothing"* is the finding.
