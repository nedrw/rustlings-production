# Exactly once is a table, not a promise

## WHY

The broker gives at-least-once. Exactly-once *processing* is built on top: make the effect idempotent
by recording the offset that produced it, and skip a record whose offset is already there. The
mechanism is a table keyed by `(partition, offset)`, checked before the effect and written after it —
in the same transaction, in a real database; in this project's model, in the same call.

Two consequences follow, and both are visible in the spec:

- **a replay is a no-op.** Reprocessing a range that already succeeded applies nothing, which is the
  difference between "exactly once" and "we did not see it twice yet";
- **a crash between the effect and the commit does not duplicate.** The record is delivered again,
  the table already has it, and the second delivery changes nothing. The reverse order — effect after
  a commit — loses instead, which is why the commit is not part of this module at all.

The table is the whole design. Where it lives (the same database as the effect, the same transaction)
is where the guarantee comes from; a table in a different store is a window where both copies are
half-written.

## TASK

The scaffold added `src/exactly_once.rs` and its `pub mod exactly_once;` line. `Sink` — the table and
the effects — and its `applied`/`apply`/`effects` are given; `process` is the stub.

- **[`process`]** — walk `[from, to)` of a partition in offset order, apply every record the sink has
  not applied, and answer how many effects this pass added.
- **The end is clamped to the log**, as everywhere else: a range past the end is not an error.

## DONE WHEN

- `kiln run broker/7.7-exactly-once` — the spec passes
- `kiln check broker/7.7-exactly-once` — every must gate is green
- processing `[0, 3)` twice applies three effects the first time and zero the second

## TRAP

1. **Applying without checking.** The straightforward loop works on the first pass and duplicates
   every effect on a replay; the spec's *"a record was applied twice"* is the assertion.
2. **Keying the table by payload.** Two records with the same payload — a retry, a re-send — are one
   entry, and the second is skipped although it is a different record; the offset is the identity.
3. **Committing before the effect.** In a real system that is data loss (the record is behind the
   commit and never processed), and this module's model shows the other side: the sink's table is
   written with the effect, so there is nothing to commit before it.
4. **Trusting the sink's `apply` to dedupe.** `apply` does ignore a repeated offset — that is why the
   table is the mechanism — but the exercise is the *call*: a version that applies everything and
   relies on the table still counts the record as new, and the spec's counts fail.
