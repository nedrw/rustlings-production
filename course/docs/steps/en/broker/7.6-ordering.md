# Order what must be ordered, and nothing else

## WHY

A topic has no global order. Anybody who needs one has a design problem, and the answer is a key: the
records that must stay in order share a partition, and everything else spreads. The interesting part
is *how coarse* the key should be.

Two failure modes bracket the answer:

- **one key for everything** — partition `0` gets the whole topic: perfect order and no parallelism;
- **one key per event** — every record lands in a different partition and nothing is ordered at all.

What is actually required is a key per *group* of events that must stay ordered relative to each
other — the connected components of the "must be ordered" graph. A chain `a → b → c` is one group
even though no rule names `a` and `c` together: ordering is transitive, and a key per rule is how
that transitivity gets lost.

## TASK

The scaffold added `src/ordering.rs` and its `pub mod ordering;` line.

- **[`plan`]** — a key per event: events connected by ordering rules share one key, events no rule
  connects keep their own, and a group's key is the smallest name in it (so the answer does not
  depend on the order the rules came in). A rule naming an event that is not in `events` is ignored.
- **Union-find is the natural implementation** — the components are exactly the groups — but any
  answer with the properties above passes.

## DONE WHEN

- `kiln run broker/7.6-ordering` — the spec passes
- `kiln check broker/7.6-ordering` — every must gate is green
- `a-b`, `b-c` is one group; `a-b` and `c-d` are two; no rules is four groups of one

## TRAP

1. **A key per rule.** `("a","b")` and `("b","c")` give two keys, `a` and `c` are not ordered, and
   the chain the product needs is broken. The spec's *"a chain becomes one group"* is this defect.
2. **One key for everything.** It passes every ordering test and serialises the topic: the cost the
   keys exist to avoid.
3. **The group's key depends on rule order.** Picking the key from the first rule's left side gives
   a different plan for the same graph, and two publishers that compute the plan separately disagree
   — a split brain with extra steps.
4. **Only the direct pairs.** Checking `must_order` at publish time ("is this pair ordered?") instead
   of planning keys: transitivity is not checked, and it is its own O(n) lookup per event.
