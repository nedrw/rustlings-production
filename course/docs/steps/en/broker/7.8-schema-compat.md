# Additive is compatible; subtraction is a breaking change

## WHY

An event is a contract in the same sense an HTTP body is (step `relay/2.3`), with one difference that
makes evolution harder: the consumer of yesterday's event is still reading the stream. The rule is
asymmetric, and all three breaking moves are the same move — taking information away:

- **a removed field** is information a consumer may be reading;
- **a changed type** is the same information in another shape: a consumer that parsed `status` as a
  string and now gets a number is broken, whatever the JSON schema says;
- **an added required field** is subtraction from the *producer's* side: the old writers do not send
  it, and a consumer that requires it rejects their events. An added *optional* field is the one
  compatible addition, because a consumer that did not know about it ignores it.

The direction matters: compatibility is judged from the consumer of the old schema, which is
everywhere, not from the new producer, which is one process.

## TASK

The scaffold added `src/schema.rs` and its `pub mod schema;` line.

- **[`compat`]** — every breaking difference between the old and new schema, sorted:
  [`Breaking::Removed`], [`Breaking::TypeChanged`], [`Breaking::RequiredAdded`].
- **An added optional field is not in the list.**
- **The answer is a list, not a boolean**: a change that removes one field and adds another is two
  facts, and the reviewer wants both.

## DONE WHEN

- `kiln run broker/7.8-schema-compat` — the spec passes
- `kiln check broker/7.8-schema-compat` — every must gate is green
- adding `trace` as optional is compatible; adding `tenant` as required is not; changing `status`
  from text to number is not

## TRAP

1. **Only checking the old direction.** `for field in old` finds removals and type changes and misses
   the required addition entirely — the new producer's problem is the other loop.
2. **Treating any added field as compatible.** On a JSON wire it parses; on the consumer's side it is
   required or it is not, and the flag is the whole question.
3. **A type change is compatible "because JSON".** `"1"` and `1` are different values to every
   typed consumer, and to the database column the consumer writes them into.
4. **Returning the first break.** The reviewer is fixing several things at once; the spec's sorted
   list is what a changelog entry needs.
