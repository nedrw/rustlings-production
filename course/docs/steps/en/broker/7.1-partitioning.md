# A key has one partition, and a partition has one order

## WHY

A log with one append point is simple and cannot be read in parallel. A topic with many partitions
is a log per partition, and the two promises that make it useful are both about *which* partition a
record lands in:

- **the same key lands in the same partition, every time.** That is what gives per-key ordering: a
  consumer reading one partition sees that tenant's records in the order they were published, which
  no global ordering could give at a useful rate;
- **an unkeyed record still spreads.** A producer that keys nothing should not put its whole
  throughput into partition zero — the partitions exist to be read in parallel.

Offsets are per partition, not per topic: `(partition, offset)` names one record, and neither half
means anything alone. This is why a consumer's position is a map and not a number, which is the next
step.

## TASK

The scaffold put `src/lib.rs` in place with the topic, its partitions and `partition_for` — a stable
FNV-1a hash, given because a hash is not the exercise. `Topic::append` is the stub.

- **A keyed record** goes to `partition_for(partitions, key)`, at the end of that partition, and
  `append` answers `(partition, offset)`.
- **An unkeyed record** goes to the next partition in rotation — across appends, not per call.
- **An offset is the record's index in its partition.** Two partitions both have an offset `0`.

## DONE WHEN

- `kiln run broker/7.1-partitioning` — the spec passes
- `kiln check broker/7.1-partitioning` — every must gate is green
- appending the same key three times leaves one partition with `end == 3`, and four unkeyed appends
  leave every partition with exactly one record

## TRAP

1. **A hash that changes between runs.** `RandomState` (the default `HashMap` hasher) is seeded per
   process: the same key lands in a different partition after a restart, and per-key ordering is
   gone. The given `partition_for` is stable for exactly this reason.
2. **Routing by payload.** Convenient for a demo, and it breaks the moment two records for one key
   have different payloads: their order is no longer one partition's order.
3. **Every unkeyed record in partition zero.** Correct for the spec's keyed tests and wrong for the
   unkeyed one: three of four partitions stay empty and the topic is not read in parallel.
4. **A global offset.** Counting records across the whole topic makes `(partition, offset)` ambiguous
   — two records with one name — and every consumer position in the next step off by more than one.
