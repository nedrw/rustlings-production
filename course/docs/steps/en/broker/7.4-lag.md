# Lag is the number that says who is behind

## WHY

A consumer group that is alive is not a group that is keeping up. The number that says so is **lag**:
per partition, the end offset minus the committed offset — how many records are waiting. Summed, it
is the backlog; per partition, it says which one is the problem.

Two boundary decisions make the number trustworthy:

- **a commit past the end is zero, not negative.** It is a caller's mistake, and a `u64` subtraction
  would panic in a debug build and wrap to a gigantic backlog in a release one. The log is the
  truth, and the answer saturates;
- **a partition with no commit is fully behind.** Missing from the map means "nobody has committed",
  not "not applicable" — the whole partition is waiting, and a lag report that omits it is a report
  that hides the worst partition.

"Behind" is a threshold, and the boundary matters: a partition exactly at the threshold is at the
threshold, not past it. The alert should fire when lag is *above* the number somebody chose.

## TASK

The scaffold added `src/lag.rs` and its `pub mod lag;` line. `backlog` and `behind` are given;
`lag` is the stub.

- **[`lag`]** — one entry per partition of the topic: `end.saturating_sub(committed)`, where a
  missing commit is `0` and a commit past the end saturates to a lag of `0`.

## DONE WHEN

- `kiln run broker/7.4-lag` — the spec passes
- `kiln check broker/7.4-lag` — every must gate is green
- a topic whose partitions end at `1, 0, 0` with no commits reports lag `1, 0, 0` — every partition
  appears, including the quiet ones

## TRAP

1. **Plain subtraction.** `end - committed` with a commit past the end panics in debug and wraps in
   release; the spec's *"a commit past the end went below zero"* is that defect.
2. **Only the partitions with commits.** `for (partition, committed) in committed` reports the
   partitions somebody already knows about and hides the one nobody has started: the worst one.
3. **`>=` for "behind".** A partition exactly at the threshold is at it, not past it; the boundary
   test fails, and the alert fires one partition early forever.
4. **Lag from the uncommitted position.** `next` (what this process has read) is not `committed`
   (what the group will resume from): after a restart they differ by everything the process was
   holding in memory, which is exactly when lag matters.
