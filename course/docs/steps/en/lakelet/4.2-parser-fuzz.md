# A parser is only as good as the corpus of things that broke it

## WHY

`lakelet/4.1-ingest-protocol` built a decoder whose whole job is to be handed bytes by somebody who
is not on your side. The spec for it has twelve hand-written cases, and every one of them is a
shape *somebody thought of*: a whole frame, a prefix of one, a length above the limit, a version
from the future. That is the shape of the problem. A parser's input space is every byte string a
peer could send, and the cases a person writes are the ones they already suspect. The bug that
ships is the one nobody suspected — a length that is off by a few bytes, a buffer that ends sooner
than the code expected it to, a value whose meaning changed in a build nobody is running yet.

Fuzzing is the cheapest way to look at inputs nobody thought of: take inputs that *work*, mutate
them a little, hand each one to the parser, and let the machine find the case that falls over. Two
properties are what make it worth anything, and both are on this page:

- **it is seeded and the seed is honoured.** A failure has to be a *case*: the same seed has to
  produce the same inputs in this process, in the next one and on another machine, or the finding is
  a story about a Tuesday rather than a bug somebody can reproduce. That is why the generator is a
  few lines written out here instead of a dependency's `ThreadRng`: a crate that changes its
  algorithm in a patch release silently changes what a seed means;
- **it leaves a corpus.** The value of a fuzzer is not that it ran, it is that it *found* something
  and that the finding is still replayed a year later. One input per line, in the repository, read
  by the harness and by the spec on every build — that is the difference between a regression test
  and a note about a bug that once happened.

This is also where the project stops being something you describe and starts being something an
incident review can use. The capture scanner that ships with this step (`src/protocol/sniff.rs`)
answers "which frames are in this file?" for a `tcpdump` dump, a log that caught half a connection,
or a store that lost its tail. It is new code, it parses bytes a stranger chose, and new code that
parses bytes a stranger chose has bugs in it. The walk below is how you find yours.

## TASK

- Write `src/protocol/mutate.rs`: `walk(seed, iterations, visit)`, which hands `visit` one mutated
  input at a time. It owes four things — the same seed walks the same inputs (in any process),
  another seed walks somewhere else, every mutation kind this format has is in the walk (truncation,
  byte flips, edits to the length field, inserted junk), and not everything it produces is rubbish:
  the walk starts from frames the decoder accepts and leaves some of them alone, because an input a
  parser *accepts* is how a refusal is told apart from a parser that has stopped working. Keep the
  generator hand-written and inside this module.
- Run the harness: `cargo test -p lakelet --test fuzz_protocol -- --nocapture`. It walks 60,000
  inputs under `KILN_FUZZ_SEED` (default `1`) through `frame::decode` and `sniff::ranges`, replays
  everything under `tests/corpus/**`, and prints the two counters at the end. When a walk falls over
  an input it prints that input in the corpus's own format before it lets the panic through.
- Expect the first run to find something. If it is green on the first try, your mutator is not
  reaching the edges of the format yet — a length that is a few bytes off, a capture that stops
  sooner than the parser expects, junk where a field should be.
- Put the input that broke the parser into `tests/corpus/parser/`, one hex input per line in a
  `.txt` file, with a `#` line saying which failure it stands for (the directory's `README.md` has
  the format). Minimise it first: the smallest input that still reaches the failure is the one worth
  keeping, and it is also the one that explains it.
- Fix the *parser*, not the test. Then run all three seeds from
  `course/tracks/lakelet/fuzz/4.2-parser-fuzz.toml` (`for seed in 1 7 20260101; do KILN_FUZZ_SEED=$seed
  cargo test -p lakelet --test fuzz_protocol -- --nocapture; done`), and `kiln check
  lakelet/4.2-parser-fuzz --slow`, which runs them again with a floor on how much each seed has to
  have searched and on how many corpus inputs were replayed.

## DONE WHEN

- `kiln run lakelet/4.2-parser-fuzz` — the seven spec cases pass: the walk is seed-stable, two seeds
differ, all three of the decoder's answers are reached, the scanner survives everything it is handed
and still finds a frame that junk surrounds, every corpus entry replays, and a corpus line that is
not hex is refused by naming its file and line.
- `cargo test -p lakelet --test fuzz_protocol -- --nocapture` — green under each of the three seeds,
printing `lakelet-fuzz iterations=<n>` and `lakelet-fuzz corpus_cases=<n>`.
- `kiln check lakelet/4.2-parser-fuzz --slow` — every must gate green, `slow:fuzz@3` among them: three
seeds ran, each made more than `iterations_min` inputs, and at least `corpus_cases` inputs were
replayed from the corpus.
- The corpus holds the input your walk found, and the comment above it says which failure it is.

## TRAP

- **A generator that is not seed-stable.** Something that reads the clock, an address, a `HashMap`'s
iteration order or a crate's thread-local generator makes the same seed walk differently in the next
run: the spec's same-seed case fails, and every seed named in a report stops meaning anything.
- **A mutator that only truncates.** It finds the frame that was cut short and nothing else: no
refusal (every strict prefix is `Incomplete`), no arithmetic on a length that lies. A mutator that
only flips bytes has the mirror-image hole — it never produces a capture that ends inside a frame.
The spec's three-answers case names which of the three you are missing.
- **A corpus that is not replayed.** An input in a note, in a comment, in a chat message or in a
file the loader does not read (it reads `.txt` below `tests/corpus/`) is not a regression test: the
harness counts what it replayed and the course-side file says how many it owes. The spec replays the
same entries, so a corpus that quietly emptied out fails twice.
- **"The fuzzer found it, so I changed the assertion."** The panic is in the parser; weakening the
spec is not a fix and does not last (`kiln spec restore` puts the course's copy back, and
`spec-integrity` fails a spec that was edited), and deleting the corpus entry deletes the only
evidence that the bug was ever there.
- **A walk that hides what it found.** A panic with no input named leaves you bisecting fifty
thousand inputs by hand. The harness prints the input in the corpus's format for exactly this
reason: a finding you cannot reproduce is a finding you cannot fix.
- **Fixing it only for the seed you ran.** A panic that happens under seed `1` and not under `7` is
a panic; run every seed the course-side file lists before believing a fix, which is what the gate
does.
- **Reaching for `cargo-fuzz` here.** It is what a production project uses — libFuzzer,
coverage-guided, with a minimiser and a corpus directory — and it needs a nightly toolchain and a
crate that is not installed on this machine (`kiln doctor` says so). The course's harness is the
substitute that a `must` gate can run offline: the same idea, a smaller search, and the counters are
the judgement.

## FURTHER

- Run a coverage-guided fuzzer once, somewhere you are allowed a nightly toolchain: `cargo fuzz
init` in a copy of this project, `cargo fuzz run ranges`, and watch it *choose* mutations by what
they cover instead of by what a generator says. The corpus format you just wrote is what that tool
would keep too.
- Read the mutation stages a production fuzzer runs (AFL's deterministic stage, libFuzzer's
dictionary and havoc): bit flips, byte flips, arithmetic on integer fields, insertions and
truncations, with a dictionary of the constants the format uses. The four kinds in `mutate.rs` are
the small version of that list, and the length-field edit is the one a length-prefixed format
cannot do without.
- `lakelet/4.4-wal-recovery` is the same idea without a fuzzer: every truncation point of a written
log has to recover to a prefix of what was acknowledged, because a torn tail is a capture that ends
in the middle of a record — the input this step's walk produced by cutting a frame short.
- Open `tests/corpus/` in a later step and try to say what each entry broke without reading its
comment. An entry nobody can explain is an entry to delete or to explain.
