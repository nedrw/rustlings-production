# Pruning is measurable: how many segments a query did not have to open

## WHY

A store that answers every question by opening every file is correct, and it is the thing a telemetry
store exists not to be. `lakelet/4.11-query-engine` gave you half of the fix: a segment's entry in the
manifest states the span of timestamps its records cover, so a query whose range cannot meet that span
does not open the file. Half, because the manifest states *counts* — how many bytes, how many records,
when the first and the last of them happened — and nothing about what the records **are**. Ask
`FROM cpu WHERE host = 'h20'` of a store of two hundred segments and nothing is skipped at all: every
segment's span meets the query's range, every file is opened, and one record in two hundred is
finally an answer.

That failure has a shape worth naming before you write a line of this step, because it is the one your
tests will not catch. The answers are right. There is no failing case to write, because *"this query
opened two hundred files to return thirty records"* is not a bug in any counter this store has:
`rows_answered` is 30, `segments_opened` is 200, and nothing says that 200 was wrong.
**Correct and slow has no red test.** What it has is a *number*, and the work of this step is to make
that number exist, make it move, and make a budget fail when it stops moving.

So a store gets an index beside each segment — a **sidecar**: a small file that says what the segment
holds, close enough to answer "can this file possibly contain what I am asking for?" and never so
precise that it has to open the segment to find out. And the whole design of that file follows from
one sentence: an index is **derived state**. Everything in it can be built again from the segment it
describes. A missing index, a damaged index and an index for a segment that no longer exists are all
the same kind of event — *this query opens a file it could have skipped* — and never a different
answer. A store that dropped its index directory answers exactly what it answered before, having read
more; a store whose index files were scribbled over does too. The counters say which of the two
happened (`index_missing`, `index_unusable`) instead of the answer changing, and that is the property
this step is shaped around.

## TASK

Three files are yours, the store is the thing they change, and the harness is the course's. The split
is deliberate: the index is the lesson, and a lane that printed your numbers is a device.

**`src/engine/index/zone.rs` — the bounds of a segment's two ordered columns.** For every record a
`Record` has a timestamp and a value, and both have an order, so a segment can state the smallest and
the largest of each. The type is a **value**: built from records, never changed afterwards, comparable,
encodable in a fixed thirty-three bytes, and answerable without a store. One rule runs through every
method in it and it is the rule a page has to say out loud:

- **a zone answers *may* and never *does*.** A false positive — "a record here might meet your range"
  about a segment that holds none — costs one file read. A false negative costs a **record**: a query
  that did not open a segment holding a record it asked about answers with a hole in it, and no count
  in this store would say so. So a bound nobody stated answers `true` to everything, a zone built from
  no records at all answers `true` as well, and a record whose value is a **NaN** makes the value pair
  *unstated* rather than bounding a set that quietly leaves it out — a NaN is not above or below
  anything, so there is no interval that contains it;
- **the units are the manifest's.** Milliseconds since the epoch, unsigned, a timestamp before it
  counted as zero: the zone and a segment's entry in the manifest are two statements about the same
  records, and a store where they disagreed would prune on one number and delete on another;
- **the range question is the half-open rule `lakelet/4.11-query-engine` already prunes with** — a
  segment is met when its earliest record is before `to` and its latest is at or after `from` — written
  over a zone's own bounds instead of over a manifest entry. Both comparisons are load-bearing in
  opposite directions, and the spec asks about both ends;
- **a union with an unstated zone is unstated.** A merge writes the union of its inputs' zones
  (`merge`, below), and one input whose bounds nobody wrote down is enough to make the merged zone say
  nothing: that is the same rule `lakelet/4.9-retention` states for a merged segment's time range.

**`src/engine/index/bloom.rs` — which series a segment may hold.** A filter over the segment's *series
vocabulary*, and the second thing a query asks. Its elements are **terms**: a series name, and each
`key=value` pair a name carries. A query names both shapes — `FROM cpu` names a metric, `WHERE host =
'h0'` names a pair — and what a segment has is whole names, which is why the names *and* their pairs go
in. Three decisions in that file are worth more than the code:

- **the metric is deliberately not a term.** A store could prune with it — a segment holding no record
  of metric `cpu` cannot answer `FROM cpu` — and doing so would quietly change an answer: `FROM mem`
  about a store that has never held `mem` is *refused* today, with `Refusal::Unknown` decided from the
  records a query read, and a metric probe would turn that refusal into an empty answer whenever every
  segment in the range got pruned. Whether a store has *ever* held a metric is a question about its
  whole history, and `lakelet/4.18-cardinality-cost` is the step that makes a store able to answer it;
- **the size is fixed, and the fixedness is the point.** Every filter this build writes is the same
  shape, and it states that shape in its own encoding so a decoder can refuse a foreign one. That is
  what makes a **union** possible at all: a merge writes the union of its inputs' vocabularies without
  reading a single series name, and two filters can only be ORed when their bits mean the same places.
  A size that followed how many names went into a filter would make that merge impossible, and hashing
  every name again is exactly the read the index exists to avoid;
- **a CRC is a checksum, not a hash.** The crate the project already has is `crc32fast`, and the low
  bits of a CRC are strongly related for messages that differ in their last byte — which is the part
  `% size` keeps. One `fmix32` avalanche step over the checksum is what turns it into a hash, and the
  difference is measurable rather than theoretical: with the size this build writes, a vocabulary of
  sixteen terms, the filter answered `yes` about **one term in thirty** it had never seen before that
  step was there, where the module's own table promises about one in seventy thousand. Read that
  paragraph before you write the hash.

**`src/engine/index/mod.rs` — the index as a file.** One value per segment, its encoding, where it
lives, and the two ways it is consulted.

- **it lives beside the segments, not among them**: `<store>/index/<ordinal>.lki`. The manifest is the
  store (`lakelet/4.8-compaction`), a segment counts exactly when the manifest names it, and everything
  else in `segments/` is an orphan the next open deletes — an index file in there would be deleted the
  moment it mattered, and two earlier steps count the files in that directory. So the index gets its
  own directory, its own magic, its own version byte and its own extension, and the two formats move
  independently;
- **the seal is what makes damage a refusal instead of a lie.** Every byte above the seal is covered by
  `wal::checksum`'s CRC — the same function the log and the segment use — so a flipped bit is a
  *damaged* hint (no pruning, one read) rather than a plausible wrong one. Derived state that lies is
  worse than derived state that is absent, because the absence is counted and the lie is not;
- **`load` has no error path, and that is the contract.** It answers `Found`, `Missing` or `Damaged`.
  A store to go and repair is not a question a reader refuses to answer: the query opens the segment,
  says `index_missing` (or `index_unusable`) in its counters, and returns the same answer it would have
  returned with a perfect index. Nothing about a caller's data is an error because a hint is gone.

**The writer side is the store's, and it is three small changes.** `Segments::seal` writes the new
segment's index *after* the file and *before* the manifest names the segment — the order every
installed thing in this store follows, so a crash between the two leaves an index nobody consults.
`Segments::merge` writes the merged segment's index as the **union of its inputs' indexes**: no series
name is read, exactly as no record is read to state the merged segment's time range. An input whose
index is missing or damaged makes the merged index state *nothing* — a filter with every bit set and a
zone with no bounds, which prunes nothing — because an index that claimed a vocabulary the merged file
does not have would hide records that are in it. `Segments::expire` needs no change at all: the expired
segments' index files stay behind as garbage, named by ordinals the manifest does not name any more,
and a reader only ever asks about the ordinals the manifest *does* name. Turning that garbage into a
number somebody manages is `lakelet/4.20-capacity-model`'s subject, not this step's.

**The reader side is the plan's.** `Plan::of` already prunes by the manifest, and now prunes a second
time: a segment whose stated span meets the range is still skipped when its zone cannot meet the range
or its filter cannot hold a tag pair the query named. A query that named no pair is not asked about its
vocabulary at all — a filter is not consulted with nothing to ask it. The two prunings are counted
apart, because they are different decisions by different parts of the store: `segments_pruned` stays
exactly what `lakelet/4.11-query-engine` made it, `blocks_pruned` is the index's share, and the three
counts together are the whole store — every segment is *opened*, *pruned by the manifest* or *pruned by
the index*, never in two of them and never in none. `EXPLAIN` grows the one key this page's
predecessor promised (`blocks_pruned`, beside `segments_pruned`) and the twelve keys it always had keep
their names, their order and their meanings. The executed counts grow four more — `bytes_read`,
`bytes_avoided`, and the two that say whether the store could prune at all, `index_missing` and
`index_unusable` — and `lakeletq query --json` prints all of them, because a script that asks "did the
pruning happen?" is asking about a run that happened.

**And `OR` is still not in the grammar, which is this step's argument to make.** `lakelet/4.11-query-engine`
declines a disjunction and says why: a record that satisfies either half of one cannot be ruled out by
a predicate that matches one half. The index changes the shape of that question, so here is the whole
argument. Pruning a **conjunction** is one rule: a segment is skipped when *any* pair the query named
cannot be in it, because a record matching all of them has to carry every one. A disjunction is the
dual — a segment can be skipped only when *every* branch cannot be in it — and a filter can answer that
too, so `OR` is not unprunable. What it costs is the *plan*: a predicate list becomes a tree, the
series name the plan prints stops being a name (`cpu,host=h0` cannot spell `h0 or h1`), and the two
pruning decisions become a walk that can open *more* segments than the same question written twice.
That is a step of its own — a grammar, a printer and a plan — and this step's job was to leave the
index able to answer it: a disjunction over terms is answered by the same filter, and a step that adds
`OR` inherits the pruning rule rather than needing an index of its own.

## TRAP

1. **Pruning on the metric.** It is the obvious second probe and it is the one that changes an answer:
   `FROM mem` about a store that has never held `mem` is refused today with `Refusal::Unknown`, decided
   from the records a query *read*. Add the metric as a term, and any query whose range happens to meet
   only segments that do not carry it is answered empty instead of refused — the case
   `a_selective_query_opens_one_segment_of_many_and_an_unselective_one_opens_them_all` is where that
   shape lives next to a *refusal* the spec of the step before it pins, and the two cannot both hold.
2. **A merge that writes an empty index for an input it could not read.** `Bloom::of([])` is a filter
   that may contain *nothing*, so a merge that started from an empty vocabulary and unioned only what
   it could read would write an index proving the merged file holds no series at all — and the query
   after it returns zero rows for a store full of records, silently. The union starts from an input, and
   an input with no readable index contributes `SegmentIndex::unstated()`.
3. **Consulting an ordinal the manifest does not name.** `merge` and `expire` leave index files behind,
   and the ordinals are never reused, so `<store>/index/` accumulates files for segments that are gone.
   A reader that walked the directory instead of the manifest would prune on a *stale* zone map and skip
   a segment that does exist. The rule is the manifest's order and the manifest's list: the index is
   asked about an ordinal the manifest names or it is not asked at all.
4. **A zone whose "no" is drawn on the wrong side.** `may_meet` is the half-open rule, and both ends
   have a case: a range that ends exactly where the segment's first record stands does **not** meet it
   (that record belongs to the next question), while a range that begins exactly at its last record
   does. Turning either comparison around costs a record and no count, which is why the spec asks both
   of them and why the unstated zone answers `true`.
5. **A bloom whose size follows its vocabulary.** It looks generous and it breaks the merge: two
   filters of different shapes cannot be ORed, and a merge that hashed every name again would read the
   records the index exists to avoid reading. The size is a constant of the build, the decoder refuses
   anything else, and the price of a fixed size — a vocabulary past what it can hold answers `yes` to
   everything — is stated in the module and asserted rather than hoped for.
6. **Reading the index as a second source of truth.** The moment a plan uses an index value to answer
   something the manifest also states, the two can disagree — and a *stale but valid* file, or one
   written by an older build, is then a wrong answer rather than a missing one. The index is asked
   *whether it can rule a segment out*, and nothing else.
7. **A budget that measures time.** `slow:bench-budget@10` compares counts, and a lane that measured
   milliseconds would be red on a loaded machine and green on an idle one — which is how a budget
   teaches people to re-run it instead of read it. Every metric in `tests/budget_pruning.rs` is a
   count, a byte total or a ratio of two counts.

## FURTHER

- `src/engine/index/mod.rs` — the layout, byte for byte, and the three answers `Index::load` gives.
  Read the section on why the sidecar is not in `segments/` before you move it there.
- `src/engine/compaction/mod.rs` — `seal` and `merge`: the order the two write a segment and its index,
  and the union the merged index is written from.
- `src/engine/query/plan.rs` — the two pruning decisions in one loop, and what the plan counts apart.
- `crate::engine::index::bloom`'s table — the false-positive rate of the size this build writes, and
  the vocabulary past which a filter stops saving reads.
- Apache Parquet's format specification, "Column Chunk" → *bloom filter* — the same sidecar idea in a
  file format you have probably read with a query engine, with the same tension between a fixed size
  and a growing cardinality.
- MurmurHash3's `fmix32` — the avalanche step in the module's hash, and the reason a checksum is not a
  hash.
- RocksDB's wiki, "Partitioned Index Filters" and "Bloom Filter" — an index beside a data file, with
  the partitioning that a store with millions of segments ends up needing.
- ClickHouse's *data skipping indexes* — `minmax` and `bloom_filter` as two *kinds* of skip index, which
  is exactly the pair this step builds by hand.
