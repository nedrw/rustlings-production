# Framing is the interface: a length-prefixed ingest protocol with a checksum

## DELTA

Four projects in, you know how a skeleton is shaped: a library, a binary, a configuration, a
subscriber installed once, and a fixture that starts the process and waits for it to say it is ready.
This step re-stands all of that — and the new part is what a **stream** is like when it comes from a
machine instead of a browser.

Every `Bytes`-typed body in the last three tracks arrived already framed: `axum` handed you a
`Json<T>` and somebody else had dealt with the boundaries. Here you write them. A TCP connection
hands you bytes, arbitrarily cut: a frame can arrive in two pieces, two frames in one, a peer can
send half a frame and go away, and a peer can lie about a length. The protocol on this page is four
fields long, and every one of the four exists because of one of those facts:

- a **length** so the reader knows how much more to read, before it has any payload;
- a **version** so a frame from a build that is not this one is refused *before* its payload is
  buffered;
- a **checksum** so a mangled payload is a refusal rather than a bad number in the store;
- a hard **limit** so a peer cannot choose how much memory this process holds — a four-gigabyte
  length is refused in the four bytes that carry it, not after the allocation.

The store behind it is deliberately dumb for now: one append-only file, one length-prefixed record
per accepted payload. That is not the design you are settling on — `4.3` decides how hard it is
flushed, `4.4` gives each record its own checksum so a torn tail is recognisable, `4.5` writes
batches, `4.7` replaces the files with columnar segments — but it is what makes *this* step's
question answerable: does the daemon store exactly what a client sent, and exactly once?

The daemon's part of the work is the loop around the decoder, and it has one rule worth writing down
before you write it: **a refusal ends that connection, not the process**. After bytes that are not a
frame, nothing that follows can be trusted to start at a boundary, so count the frame, log the
reason, drop the client — and keep serving.

## TASK

- Implement the frame codec in `src/protocol/frame.rs`: `Frame::encode` and `frame::decode`,
  answering `Decoded::Frame(frame, consumed)`, `Decoded::Incomplete { needed }` or
  `Decoded::Invalid { reason }` — and `frame::read_all`, which walks a buffer and answers the frames
  it holds plus how many bytes they used.
- Implement the payload codec in `src/protocol/batch.rs`: a count, then that many records, and a
  refusal that says which record was wrong when one is.
- Implement the write path in `src/engine/spool.rs`: `Spool::open` creates the store directory,
  `Spool::append` writes one length-prefixed record and answers only once it can be read back, and
  `Spool::records` reads them back in order — or refuses the file rather than guessing.
- Implement the accept loop in `src/service/ingest.rs`: accept, read into a buffer that keeps what did
  not fit, decode, store, count; refuse a bad frame with a `frame rejected` line; log
  `connection closed accepted=… rejected=… bytes=…` per connection and `stopped accepting` on
  shutdown; answer a port probe without growing a line per health check.
- Write `docs/protocol.md`: the layout, the three answers the decoder gives, and what a peer can do to
  us. It is part of the step, not a summary of it — a wire format nobody else can read is a wire
  format with a deadline.

## TRAP

- **`read` is not a message boundary.** A loop that decodes once per read and drops the rest of the
  buffer loses frames as soon as the client writes two in a row, and it is invisible on a fast local
  socket until the day the payloads get big. Keep the tail.
- **Allocating from a length you have not checked.** `Vec::with_capacity(length)` with `length` off
  the wire is a remote out-of-memory: the refusal has to come before the reservation, which is why
  the limit is checked in the same four bytes the length arrives in.
- **Waiting for the whole frame before checking the version.** If a frame from another version is
  buffered first and refused later, the version byte bought you nothing. Pin the check to the fifth
  byte — the spec sends five bytes and expects a refusal.
- **Treating a half frame as an error.** A client that disconnects mid-frame is normal traffic (a
  killed process, a lost network); it leaves no record, and it must not be logged as a fault or end
  the daemon.
- **A checksum over the header.** If the checksum covers the length too, a corrupted length is caught
  by arithmetic instead of the version and the limit that exist for it — and the sentence the reader
  gets points at the wrong field.
- **`todo!()` left in a code path the spec never runs.** `no-todo` is a gate: every stub this step
  brought has to be implemented, not just the ones with tests in front of them.

## FURTHER

- Read `docs/protocol.md` in a later track and try to write a client from it alone. Every place you
  had to guess is a place this page is wrong.
- `lakelet/4.2-parser-fuzz` attacks exactly this decoder with seeded mutations, and its corpus is the
  set of inputs that broke it. Writing the mutator before the corpus exists is the normal order.
- Production protocols of this shape: PostgreSQL's wire protocol (a length, a kind byte, then the
  body), Kafka's record batches (a length prefix, a CRC per batch), and Redis's RESP (a type byte,
  then a length). All three chose the same four fields for the same reasons.
