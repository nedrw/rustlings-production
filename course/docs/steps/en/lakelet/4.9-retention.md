# Retention deletes what nobody can still read — and proves it

## WHY

Every step so far has added to this store. `lakelet/4.7-columnar-segments` made a segment worth
keeping, `lakelet/4.8-compaction` made fewer of them worth more, and nothing in either one ever
gave a byte back. A store that only appends does not fill up in a year of tests; it fills up in a
week of ingest, and the operator's answer — "delete the old files" — is a shell script that cannot
tell a closed segment from a half-written one, that has no idea which reader is holding which file,
and that leaves an index naming files that are gone.

"Old data is gone" is the claim this step has to make true, and it has **two halves**:

- **everything older than the cutoff is unreachable.** No read answers a record below it, whether
the file holding that record was deleted or not;
- **nothing newer than the cutoff was touched.** The segments that stay are the segments that were:
same order, same byte lengths, same record counts, same time ranges.

The second half is the one that costs. Deleting a file is one line; the hard part is the file that
holds records on both sides of the cutoff. It cannot be deleted — that takes newer records with it
— and it cannot be rewritten, because rewriting it would pay exactly the write amplification the
last two steps spent their budgets measuring, for a pass whose entire job is to stop paying for
bytes. So a segment like that is left alone, keeps its old records on the disk, and those records
stop being *answers* through the read path instead. On this step's own budget workload one segment
of twenty-four is in that position — the file the pass can neither delete nor rewrite — and the
numbers that describe it are in the same place the last step's were:

- the pass expires **10 of 24 segments** and reclaims **3 904 bytes**, and the files in the segment
directory are **3 904 bytes shorter** afterwards, measured by `stat`, not by the store's own report;
- it writes **zero bytes** into files that already existed: the only thing a pass writes is a new
index;
- the store's index still *counts* **1 260 records** after the pass, while a read answers **1 200** —
and the sixty in between are exactly that straddling segment's records below the cutoff. Both
numbers are honest; they answer different questions;
- it does all of that at a cutoff that is a **bucket boundary** rather than an instant, so the same
policy at 00:59 and at 01:01 deletes the same thing.

The other half of the step is what the first half may not break: **a reader never sees the store
change under it.** `lakelet/4.8-compaction` promised that for a merge, and a retention pass that
deleted files at the moment it swapped the index would give a query that began before the pass a
file nobody names any more. The same deferral applies — the files leave when the last reader that
named them lets go — and it is the same `Set`, reused rather than reinvented.

## TASK

Five properties make up this step. Everything else is packaging.

- **A segment's age comes from the store's index.** Where does "how old is this file" live? In the
manifest, written when the segment was closed: an entry states the range of timestamps the segment
holds, so a policy can decide what is old without opening a file — the same reason the entry has
always stated a byte length and a record count. That is a second constructor beside the one this
store already has, and the pair is deliberately not the same function: `SegmentInfo::spanning(index,
bytes, records, first, last)` is what `seal`, a merge and a decoded manifest use, and
`SegmentInfo::new(index, bytes, records)` stays what it was — the value a caller builds by hand for
a decision about **size**, which 4.8's plans are made from, and which states no range at all. An
entry with no range says so (`u64::MAX` twice, a millisecond no record can have), and the rule for
such a segment is the conservative one: a plan **keeps it** and does not call it straddling, because
`None` means "nobody wrote down when these records happened", not "old". So the manifest's own
layout changes (a version 2: a floor in the header, five `u64`s per entry), and the version byte is
what makes an older index a **refusal** instead of a misreading: a version 1 manifest states no time
range at all, and a pass acting on numbers nobody wrote would delete data that is still an answer. A
merge has to keep this true — the segment it writes states the union of its inputs' ranges, or
states none when one of them states none — and so does `seal`.
- **The cutoff is a bucket boundary, not an instant.** `Policy::cutoff` is `now - keep`, snapped
*down* with `Partition`. A raw `now - keep` moves with the clock, so the same store and the same
policy would delete different things a minute apart, and a boundary an operator can say out loud
("the store keeps everything since the 11th hour") would depend on when the pass ran. The price is
coarse — data is kept for somewhere between `keep` and `keep + width` — and it is the price
`lakelet/4.10-downsampling` pays too, on the same arithmetic.
- **A segment expires exactly when its *last* timestamp is below the cutoff** — whole segments,
never a record inside one. The comparison is half-open: a record whose timestamp is exactly the
cutoff is kept. A retained segment whose *first* timestamp is below the cutoff **straddles**: it is
kept, it is reported as straddling, it is not rewritten, and its old records stop being answers.
- **The floor is durable and one-way.** The manifest states the millisecond the store has already
forgotten up to — the store's **floor** — and a pass acts at `policy.cutoff(now).max(floor)`,
never below it. That number survives a reopen (an index that forgot it would answer data the store
promised was gone), and a pass that has nothing to expire writes **nothing at all**: same epoch,
byte for byte the same index, no file touched.
- **A pass accounts for itself.** `segments_before - expired == segments_after`, `bytes_reclaimed`
is the expired segments' bytes, the retained segments keep the manifest's own values, and the
store's own report says what it cost. `tests/budget_retention.rs` and
`course/tracks/lakelet/budget/4.9-retention.toml` are where those counts are measured, and
`docs/format.md`'s neighbour — the layout table in `src/engine/compaction/mod.rs` — is where the
index's bytes are written down.

**What the course gives you, and what is yours.** The scaffold declares the shape, because the
spec, the harness and the next steps read it:

- `src/engine/retention/mod.rs` — `Policy` (with `DEFAULT` set to *keep everything*, which is the
value that cannot lose data), `Plan` and `ExpireReport`, with their accessors and the doc comments
that state the rule. The bodies of `Policy::cutoff`, `Policy::plan` and `ExpireReport::of` are the
work;
- `src/engine/retention/partition.rs` — `Partition`, the bucket arithmetic `Policy::cutoff` snaps
with. Every body is yours;
- `src/engine/compaction/{plan,mod,snapshot}.rs` — the store's half: the two timestamps on
`SegmentInfo`, the floor in `Manifest`, the version 2 layout, `Segments::expire`, `Segments::floor`
and the read path's filter. Nothing else in the project changes;
- `tests/budget_retention.rs` — the course's harness, which is what `slow:bench-budget@10` runs. It
is not yours to edit.

**This tree does not build yet, and that is the first thing to fix.** The spec and the harness read
a segment's time range out of the store's index (`SegmentInfo::first_millis`, `Segments::expire`,
`Segments::floor`), and none of those exist until you add them: `cargo test -p lakelet --test
spec_retention` fails to compile, pointing at the signature the step is about. That is the same
"the signatures are the course's, the semantics are yours" boundary as every other step, one level
up: here the *shape of the index* is part of the work.

The boundary holds here too: `src/engine/**` may not name the service layer, in code or in prose
(`lakelet/4.1-ingest-protocol` reads those files as text), and a retention pass is engine work — it
runs in a test, in a repair tool and in a load generator that has no configuration file at all.
`now` is a parameter for the same reason.

## TRAP

1. **Filtering by the wall clock at read time.** `records()` that drops everything older than
`now - keep` answers differently on two calls with no write in between, and a query plan computed
from one answer is wrong for the next. The floor is a number in the index for exactly this reason:
it moves when a pass moves it, and not one millisecond before.
2. **Dropping a straddling segment.** It is the one file that holds records on both sides of the
cutoff, so deleting it deletes records *newer* than the cutoff — the second half of the claim,
which is the half a user notices. `a_straddling_segment_is_kept_and_not_rewritten` is the case, and
the budget lane's `records_below_cutoff_max` is the count that has to stay zero.
3. **Rewriting a straddler "to make the count look better".** Folding its old records into a new
file removes bytes the store was going to keep anyway, pays a full read-and-write of the segment,
and turns a pass into a compaction with worse inputs. `bytes_rewritten_max` is zero, and it is
measured from the files that were on the disk.
4. **Letting the floor reset on reopen.** A floor that lives only in memory comes back as zero
after a restart, and the records the store said were gone become answers again — with the files
still on the disk. `the_floor_survives_the_open` writes the file a crash between the swap and the
deletion leaves behind and asserts that the next open deletes it instead of resurrecting it.
5. **`<=` where the rule is `<`.** A segment whose last record is *exactly* the cutoff expires
under `<=`, and so does the millisecond the policy meant to keep. The boundary is worth a case of
its own on both sides: `last == cutoff` is retained, `last == cutoff - 1` expires, and a record
whose timestamp is the cutoff is still an answer.
6. **Snapping the cutoff *up*, or not at all.** A cutoff that is not a boundary makes the pass
depend on when it ran, and one that rounds up deletes a bucket the policy did not name.
`a_cutoff_is_a_bucket_boundary_and_zero_keeps_everything` pins the direction: `now - keep` rounds
*down*, always.
7. **Writing an index when the plan is empty.** A pass that runs every minute and rewrites the
manifest every minute is a pass that keeps the disk busy to say what it already said, and — worse —
it moves the epoch, so every reader's snapshot looks stale.
`a_pass_that_expires_nothing_writes_nothing` compares the manifest's bytes before and after.
8. **Deleting the files at the swap.** Same bug as `lakelet/4.8-compaction`'s trap 1, in a new
place: a reader that took its snapshot before the pass gets whatever the operating system does to a
file nobody names. The pass retires what it expired to the set the readers named.
9. **Reading a segment's time range out of the file.** `merge` and `seal` state the new segment's
range from the index rather than from the records going through them: a merge that read eight files
to learn when they happened would pay for the decision it is making, and a store that has to read
every segment to answer "what is old" cannot run a retention pass at all.
10. **Keeping the version byte at 1.** A version 1 index read as a version 2 one states a floor out
of the epoch's bytes and gives every segment whatever the next eight bytes happen to be. The byte
is what makes that a refusal; `a_version_1_index_is_refused_rather_than_misread` is the case.
11. **Expiring while a merge is written and not installed.** A merge writes a segment nobody names
and an index swap is coming; a retention pass that replaced the index in between would leave the
merge installing answers into a store that no longer has the segments it took. `Segments::expire`
refuses while a `Merge` is in flight, with `Error::Invalid`.
12. **A `todo!()` left in either retention file.** `no-todo` runs over every target, and the two
files this step adds are where the gate will look first.

## FURTHER

- **Time partitioning, and who ships it.** TimescaleDB's [chunks and retention
policies](https://docs.tigerdata.com/use-timescale/latest/data-retention/) are the production
version of this rule: a chunk is the unit of deletion for the same reason a segment is here — you
can drop a whole one, and you cannot cheaply drop a row inside one. Its `drop_chunks` takes a
*cutoff*, not a duration, which is the same decision this step's `Policy::cutoff` makes.
- **Cutoffs on bucket boundaries, and the arithmetic that makes them agree.** Prometheus's
[staleness and lookback
deltas](https://prometheus.io/docs/prometheus/latest/querying/basics/#staleness) and
[`timestamp`/`start`/`end`
alignment](https://prometheus.io/docs/prometheus/latest/querying/api/#range-queries) are the same
`floor(ts / width) * width` this step's `Partition` computes, and the reason a windowed query and a
retention policy have to count in the same buckets. `lakelet/4.10-downsampling` is where that
becomes a query.
- **Tombstones, and why deleting a *record* is a different feature.** RocksDB's
[`DeleteRange`](https://github.com/facebook/rocksdb/wiki/DeleteRange) and its tombstone
compaction are what a store does when it must delete part of a file: the bytes stay until a merge
reaches them, and the space is only given back then. This step takes the other road deliberately —
whole segments, no tombstones — and the cost is the straddler.
- **Filesystems do not forget on request.** The deferral this step reuses (retire the file, delete
  it when the last reader lets go) is the same idea as Unix's
  [unlinked-but-open file](https://man7.org/linux/man-pages/man2/unlink.2.html) semantics, which
  `lakelet/4.8-compaction`'s FURTHER section already points at. What is worth reading here is the
  other half: `man 2 fsync` and the directory flush, because the pass's durability is a rename plus
  a directory flush, exactly like a merge's.
- **The reason "delete old data" is a product decision.** ClickHouse's
  [`TTL`](https://clickhouse.com/docs/en/engines/table-engines/mergetree-family/mergetree#mergetree-table-ttl),
  InfluxDB's [retention
  policies](https://docs.influxdata.com/influxdb/v2/admin/buckets/create-bucket/) and OpenTSDB's
  [`tsd.core.auto_create_metrics`-era retention configs](http://opentsdb.net/docs/build/html/user_guide/configuration.html)
  all make the window a *stored, named* number rather than a flag on a command — because the
  interesting question is never "how do I delete the files", it is "who decided how long we keep
  this, and can we prove it happened".
- **The next readers of all this.** `lakelet/4.10-downsampling` aligns its windows on the same
`Partition`, and a downsampled answer has to respect the same floor. `lakelet/4.11-query-engine` is
where `Snapshot::len` and `Snapshot::records` stop being the same number, and where a plan has to be
written against the difference. `lakelet/4.14-index-pruning` uses the same per-segment time range to skip
files in a query, and `lakelet/4.17-soak` is what says a pass that runs for a week does not drift.
