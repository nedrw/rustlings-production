# The same source, the same bytes: reproducible builds and the supply chain

## RECALL

- `release/container-image@apply — mailer/1.21`: two stages, a runtime that carries only the binary,
  and a 25 MB ceiling that asserts the shipped stage is a runtime rather than a build environment.
  That step's claim was *the image runs the same binary you tested*, and its gate asked the binary
  inside the image the same question it asks the host's. What this step keeps is the shape and that
  gate; what it deepens is *what the binary is made of* — the compiler, the directory it was built in,
  the crates it was built from — because an image built from a tree nobody can rebuild is a
  reproduction of a moment, not of a source.
- `repo/toolchain-pinning@apply — mailer/1.2`: the pin as a file with a concrete three-part channel
  and the components the gates run, plus the lesson that a pin only bites through rustup. There, the
  file stopped "it compiles on my machine". Here it is one of the three inputs of a comparison: two
  builds of one tree agree only if the compiler is one of the things they agree about, and a
  `channel = "stable"` makes every build a build of the day's Rust.
- `ci/pipeline@apply — mailer/1.3`: one list of checks rather than two, called from the workflow, with
  the nested-run guard that makes a task runner testable. This project has no `xtask` — it is a
  workspace of its own, and its pipeline is the workflow — so the lesson arrives at design depth: the
  commands live in one file, the *toolchain* is written down in one file, and a second copy of either
  is the drift that step argued against.
- `supply/deny-policy@apply — relay/2.21`: `deny.toml` with four sections and the sentence each one
  enforces, written by a project that was publishing something. Here the policy is a fourth project's
  and its lists are **read off this tree's own lockfile** rather than chosen: the licences the
  dependencies declare, the crates that appear twice, the registry they come from — so a policy that
  drifts from the tree is a failing case rather than a stale paragraph.
- `release/artifacts@apply — jobq/3.25`: an artifact is a named thing with a version, a checksum and a
  changelog entry — a release somebody can point at. This step is the other half of that: what makes
  the bytes *behind* such a name reproducible, and which differences are left when they are not.

## DELTA

Every step of this phase has measured something about the store, and the last three measured what it
costs (`lakelet/4.18-cardinality-cost`, `lakelet/4.19-backup-restore`, `lakelet/4.20-capacity-model`).
This step measures the thing all of them stand on and none of them checked: **the build**. Every number
in those pages — every digest, every counter, every byte — came out of a compiler, a dependency set, a
set of flags and a directory, and if two builds of this tree disagree then "the thing the page
measured" is not a thing at all, it is a Tuesday afternoon.

The claim this step can honestly make is *byte for byte, or the remaining differences are named and
explained*, and the shape of it is decided by what a machine can actually hold still:

- **the compiler is an input.** `rust-toolchain.toml` pins the channel and the components, and the
  reproducer refuses to build when the compiler answering is not the one the file names. This is
  `mailer/1.2`'s file in a project whose comparison depends on it;
- **the dependencies are inputs.** `Cargo.lock` is committed and every build passes `--locked`, so
  cargo builds the versions this tree was tested with or refuses. That is the whole reason a lockfile
  is a file rather than a build artifact;
- **the location is an input, and it is the interesting one.** A compiler writes the names of the
  files it read into what it produces, and the file it read that nobody thinks of is the *library it
  linked against* — which lives under the target directory. Two builds in two directories therefore
  produce two artifacts that record two places, and every length-sensitive thing after those names
  moves with them (an rlib's own member index counts bytes). The mechanism is
  `--remap-path-prefix`, passed to **both** builds over **the whole build location** — the copy of the
  tree and the target directory beside it, resolved to one spelling first, because on Darwin
  `/var/folders/…` and `/private/var/folders/…` are one directory under two names and a remap that
  names only one of them leaves a difference behind;
- **a timestamp is the difference that is left, and it is not in the bytes.** The copies'
  modification times differ and always will, which is why the comparison is over content and why the
  block says `difference_timestamp=mtimes_differ` rather than pretending the two copies are the same
  file. Nothing in these artifacts records a time: an rlib's archive members carry a zero modification
  time because rustc writes them that way, and `SOURCE_DATE_EPOCH` — the standard lever for the tools
  that do stamp time into their output — changes nothing here. Naming it is the difference between
  "considered" and "never heard of it".

The second half of the step is the supply chain, and it is the same question from the other end: a
reproducible build is reproducible *from what*. `deny.toml` states what this tree may be built from —
four questions, each with its sentence — and the lists in it are not invented, because they are read
off the tree's own `Cargo.lock`: the licence families its dependencies declare, the four crates that
appear twice and where each second copy comes from, the one registry every crate is fetched from. The
tool that would run that policy (`cargo-deny`) is not installed here and is not a component of the
pinned toolchain, and this step says so in three places rather than shipping a gate that pretends
otherwise: the file, `docs/supply-chain.md`, and the pipeline, which names the command in a comment
and does not run it.

And the pipeline is where all of it becomes one list: `cargo fmt --all --check`, then
`cargo clippy --workspace --all-targets --locked -- -D warnings`, then `cargo test --workspace
--locked`, then the reproducer — the same commands in the same order the course's own CI runs them,
with the toolchain written down in exactly one file.

## TASK

The scaffold put six files in place and left the seventh out on purpose. Every one of them fails the
step's spec as it stands, which is what a scaffold is for.

- `Dockerfile` — **one stage, and the shape is `mailer/1.21-container`'s first version**: the
  toolchain and the sources stay in the image that runs. This step declares two images
  (`rust:1.98-alpine` and `alpine:3.20`), and only one of them is in the file so far;
- `scripts/repro.sh` — a stub that states the plan and exits non-zero;
- `deny.toml` — the four sections, named and empty;
- `.github/workflows/ci.yml` — a checkout and the four commands in a comment;
- `docs/build.md`, `docs/supply-chain.md` — `[TODO](TODO)` stubs with the headings this step's pages
  have;
- and **no `rust-toolchain.toml`**, which is a decision rather than an oversight: a scaffold that
  shipped a channel this machine does not have would send `rustup` looking for a toolchain that is not
  installed, and a missing file is a failing case. The pin is yours to write.

Seven files, one job each.

**`scripts/repro.sh` is the step.** It builds this tree twice, from two directories of deliberately
different depth, with the pinned toolchain and the locked dependencies, and compares the library and
the three binaries a release build produces, byte for byte. Three things about it are the work:

1. **the two locations differ, and differ in width**, so that a difference which is *only* the path
   has to show up as a difference in bytes rather than being hidden by two paths of the same length;
2. **the build location is remapped before the two builds are compared** — in both, over everything
   that names it, resolved to one spelling. `liblakelet.rlib` is the artifact this matters for: the
   three binaries do not carry the location in a release build, the library's metadata does, and a
   project that compared only its binaries would have a green block and an unexplained difference in
   the file its dependencies were compiled against. The script **checks** this rather than asserting
   it: before it prints anything, it fails if an artifact still contains the directory it was built
   in;
3. **its output is the finding**, and its output is quotable. Print one `name=value` line per fact on
   **stdout** and nothing else there — progress, including both `cargo build` runs, goes to stderr —
   and put no digest, no path and no time in it: a digest makes the page that quotes it stale the next
   time a crate moves, and a time is a different number on every machine. The block carries which
   artifacts, how many were compared, how many are identical, how many differ, what happened to each
   of the two differences two builds of one tree can have, and a verdict. Exit non-zero when
   something differs that the block does not name.

The pipeline and the spec both run it as `sh scripts/repro.sh`, and that is not a detail: the file
carries a `#!/bin/sh` line, but the step's files arrive as a patch and this course's applier writes
content rather than mode bits, so the executable bit is never something a patch can deliver. Spelling
the interpreter out does the same thing with the bit and without it; `chmod +x` in your project makes
it a command you can run directly.

Two environment variables are part of the interface, because the step's spec uses them:
`LAKELET_REPRO_ROOT=<dir>` builds the two copies under `<dir>`, and `LAKELET_REPRO_KEEP=1` leaves them
there — which is how the spec looks inside the two trees at the artifacts the block says it compared.
A script that prints a verdict without comparing anything has to fail that, and it will.

**`Dockerfile` is two stages.** The builder is `${BUILDER}`, the runtime is `${RUNTIME}`, and both are
`ARG`s whose defaults are the two images this step declares — the convention `mailer/1.21-container`
established, and not decoration: behind a registry mirror the same image lives under another name, and
the `container-repro` gate resolves those defaults against the local image store and passes the names
this engine actually has back as build arguments. The runtime stage carries the binary, one
unprivileged user and **no configuration at all**: not even the listen address a container needs,
because the gate compares the configuration report the image answers with the one this host's binary
answers and passes the image's environment through only for `MAILER__` names — a leftover from the
gate being written for the first project. A `LAKELET_*` variable baked into the image is a difference
the gate reports as a failure, which is a sharper reason than taste for the deployment to own its
environment. `ENTRYPOINT` is `lakeletd`, which is what makes `docker run <tag> --check-config` answer
the configuration report the gate compares.

**`rust-toolchain.toml` is the pin.** A concrete three-part channel — the one the course pins, so that
the binary this machine builds and the binary the image builds come from one compiler — and the two
components the gates run (`rustfmt`, `clippy`), with a comment saying what a floating channel costs
*this* step's claim. The spec compares the file with the compiler that runs it, so a `channel` nobody
is running is a failing case.

**`deny.toml` is the policy as a file a tool could run**, and its four sections are the four questions:
`[advisories]` (a known advisory, a yanked release), `[licenses]` (the families this lockfile declares,
and anything that needs an exception with its reason next to it), `[bans]` (two versions of one crate,
a wildcard requirement), `[sources]` (one registry, no git). The lists are not yours to invent: read
them off the tree with `cargo metadata` and let the spec judge them, because a policy file whose
licence list does not admit its own dependencies is a policy nobody can run.

**`.github/workflows/ci.yml` is the pipeline**, in the order that fails cheapest first, and the
toolchain is not named in it — `rust-toolchain.toml` in the checkout is the one place the channel is
written down, and a second pin is a second answer. The spec reads this file **as text**: this project
has no YAML parser and must not grow one.

**`docs/build.md` is the run**, written from a run: the block the script prints (the spec re-runs the
script and compares it line for line), then each remaining difference named and explained, the pin, what
`--locked` and the lockfile buy, what the image changes, the drill that shows the image gate red, and
what this project does **not** achieve. **`docs/supply-chain.md` is the policy a reviewer reads**: what
is pinned and where, the four sections and the sentence each one enforces, what the pipeline runs, the
five changes that would make the policy a lie, and one paragraph on what `cargo-deny` would add if it
were installed. The spec reads both pages against `deny.toml`: a page that promises a policy the file
does not state, or a file that refuses something the page never mentions, is the drift that pair of
files exists to catch.

## DONE WHEN

  claim each: the pin is a file whose channel is the compiler answering, and a concrete version rather
  than a pointer
  (`the_pin_is_a_file_and_the_compiler_answering_is_the_one_it_names`); the pin is the *course's* pin
  rather than a second opinion about which Rust this project uses
  (`the_pin_is_this_course_pin_and_not_a_second_opinion`); the reproducer answers a run — `sh
  scripts/repro.sh` exits zero and prints a block of one `name=value` per fact

  files — every artifact the block names exists in **both** trees, the two copies are byte-identical,

  (`the_run_compared_files_that_exist_in_both_builds`); the image is two stages whose `ARG` defaults
  are the two images this step declares, and the runtime stage carries the binary rather than the
  builder or the sources
  (`the_dockerfile_is_two_stages_and_the_runtime_stage_is_not_the_builder`); the image's entry point

  (`the_image_answers_the_configuration_question_the_gate_asks`); the policy file has four non-empty

  (`the_policy_and_the_page_state_the_same_thing`); the workflow runs the course's four commands in
  the course's order, with `-D warnings` and `--locked` where they belong, and names no version
  (`the_workflow_runs_the_course_commands_in_the_course_order`); nothing this step's files *run* is a
  command the pinned toolchain does not provide
  (`no_file_of_this_step_names_a_command_this_project_does_not_have`); the lockfile pins every
  dependency the manifest declares
  (`the_lockfile_pins_every_dependency_the_manifest_declares`); the page names the differences the run
  had — and no third one
  (`the_page_names_the_differences_the_run_had`); the supply-chain page names the four sections and the
  pin (`the_supply_chain_page_names_the_four_sections_and_the_pin`); and nothing on this step's judged
  side reads a wall clock into a number, with each claim a page makes implemented by a file
  (`nothing_on_this_steps_judged_side_reads_a_wall_clock_into_a_number`).
- `kiln run lakelet/4.22-reproducible-build` — the spec passes; `kiln check
  lakelet/4.22-reproducible-build --slow` — every must gate green. Two of those gates are about the
  image and one of them is this step's whole point: `images` resolves the two declared base images
  against the local store, and `container-repro` **builds the image from this tree**, holds the
  runtime stage to 25 MB, and compares the configuration report the image answers with the one this
  host answers.
- **Then break it, which is the drill this step is graded by.** `container-repro` is the gate that
  catches a broken image, and the cheapest break is one line: point the runtime stage at the builder
  (`FROM ${BUILDER} AS runtime`) and rebuild. The gate answers with the size — a runtime stage that
  carries `cargo`, `rustc` and the sources is hundreds of megabytes, not tens. Put the line back and
  it is green again. On the machine this step was authored on the container engine cannot start a
  container at all (an overlay mount fails with an input/output error), so the gate reports **blocked**
  with the engine's own sentence rather than a verdict, and the same is true of the `--check-config`
  half of the comparison for a second reason worth knowing: the gate asks the *host* binary through
  `cargo run --package lakelet`, and this project has three binaries and no `default-run`, so cargo
  refuses to guess which one to run. Both are facts about the machine and the gate rather than about
  the seven files, and both are named here rather than smoothed over — a green line nobody can
  reproduce is worth less than a red one with a reason.

## TRAP

1. **Remapping the source root and not the target directory.** The difference that survives is in the
   library's metadata, which names the rlibs `cargo` linked against — and those live under the target
   directory. It is invisible in the binaries, so a project that compares only its binaries ships a
   green block over a library nobody can reproduce. Remap the whole build location, in both builds.
2. **A build location that can be spelled two ways.** On Darwin `/var/folders/…` and
   `/private/var/folders/…` are the same directory under two names, and `$TMPDIR` hands out the first
   spelling while a build records the second: the remap covers one and the artifacts differ. This is
   not hypothetical — it is what the first version of this step's own reproducer did, and it is why
   the script resolves its work root before it uses it. A path is not canonical because you typed it.
3. **Comparing metadata instead of content, or quoting a digest on the page.** The two copies'
   modification times differ and always will; a comparison over metadata is a comparison that fails on
   a working build. And a digest in the block makes the page stale the next time anything moves, which
   is the one thing a page of measurements must never be — the spec re-runs the command and compares
   the block line for line, so a block carrying a hash is a failing case on somebody else's machine.
4. **Baking configuration into the image.** `ENV LAKELET_LISTEN_ADDR=0.0.0.0:7000` is what every
   container guide says, and here it makes `container-repro` fail: the gate compares the image's
   configuration report with the host binary's and passes the image's environment through only for
   `MAILER__` names, so a `LAKELET_*` variable in the image is a difference between two binaries that
   are the same binary. The deployment owns its environment; the image owns the binary.
5. **A runtime stage that is really the builder.** `COPY --from=builder /src /src` instead of the
   binary, or a second `cargo build` in the runtime stage, and the image weighs hundreds of megabytes
   — the ceiling is the assertion that the shipped stage is a runtime. `COPY --from=builder` is the
   line that makes it true, and the path it copies *from* has to be outside the build cache the gate
   mounts (`/opt/kiln/target`), because a mount is not a layer.
6. **A policy file whose lists nobody checked.** `allow = []` refuses every dependency this tree has;
   a list copied from another project refuses three of them and admits one it should not. Read the
   licences off this tree (`cargo metadata`), name the exception you make with its reason beside it,
   and name the duplicates you tolerate — the spec judges the file against the lockfile, so a policy
   that does not fit its own tree is a red case rather than a paragraph.
7. **A workflow that runs a tool the pin does not install.** `cargo deny check` is the obvious step to
   add next to a policy file, and it is a check that passes on the machine that has `cargo-deny`
   installed and fails on the runner — the pinned toolchain's components are `rustfmt` and `clippy`.
   The command is named in the page and in a comment, and run nowhere. Say which tool is missing
   instead of shipping a step that has never run.
8. **`COPY . .` in a project with no `.dockerignore`.** The build context is the whole directory a
   deployment is standing in, including the host's own `target/` — hundreds of megabytes of *this*
   machine's artifacts, sent to the engine on every build, for a binary the image compiles itself.
   Naming the files the build reads (`Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `src/`) is one
   line more and one directory narrower.
9. **A lockfile that is not committed, or a build without `--locked`.** Either one turns the
   dependency half of "the same source" into whatever the registry answers with today, and the
   comparison on the page then measures two moments rather than two directories. The reproducer and
   the pipeline both pass `--locked` for the same reason.
10. **Reading the pipeline as a pipeline.** The spec reads `.github/workflows/ci.yml` as *text* and
    says so; nothing here parses YAML, and a course project that added a YAML parser to judge
    indentation would have added a dependency to the tree it is judging. What the text has to carry is
    the commands, in the order a reviewer argues about them.
