# Soak: what is still alive after ten thousand cycles

## WHY

Every performance number this track has produced so far is a *flow*: bytes written per payload byte,
work per query phase, blocks a plan did not read. Each one answers "how much did that cost", and not
one of them can answer the question a process that has been up for nine days raises — *what is still
there?* A store can be fast and honest about every count it keeps and still hand a client one file
descriptor per connection; the first symptom of that is not a number in a budget, it is a machine
that stops at the descriptor limit on day nine, in production, with no red build anywhere.

The instrument for that question is the cheapest one there is and the least often written: take the
cycle the service already does, run it ten thousand times against **one** store, and read what is
alive at the end. What makes it a discipline rather than a loop is that the counters are *livestock*
— counts of things that exist right now, charged where the thing is created and released where it
dies — and that the criterion is a **steady state**: every cycle writes a segment and retention
forgets one, so a store that is working has the same counters at the halfway mark and at the end,
and a counter that grew is a leak with a name on it.

## RECALL

`perf/profiling@operate` — `lakelet/4.16`: a sampler says where the process was, and the page that
resulted is the evidence a reader can reproduce. This step asks the same kind of question about the
process's *resources* rather than its time: a profile is what the process was doing, and a soak is
what it is still holding.

`async/backpressure@design` — `lakelet/4.6`: the ingest path is a bounded queue with a writer behind
it and a task per connection in front. The tasks are the service's, and the count this step adds is
what turns "a task nobody reaped" from a sentence in a review into a number in a run.

## DELTA

The counters are new, the honest part is not, and the trap is in the definition rather than the
code: a counter that counts *the disk* instead of *the store* passes every functional test and turns
the first soak into an argument with the wrong file. `store_files` here counts the files the manifest
names — what the store can still be asked about — and `lakelet/4.14-index-pruning` is explicit that
an expired ordinal's index file stays behind as deliberate garbage. A run that counted it would
report that garbage as a leak, once per expiry, for ever.

## TASK

The scaffold added two modules whose signatures are the contract this step's harness and spec are
written against: `src/engine/soak.rs` (the store's counters and the one report a caller asks for)
and `src/service/soak.rs` (the service's ledger of spawned tasks, and the accessor that answers it
from the queue). It also added `tests/soak.rs`, the course's harness, and `docs/soak.md`, the page's
skeleton. The bodies are yours.

**The store's half — every file it opens is charged to it.** `Open::at` answers *one* counter per
store directory, and that is the decision the rest follows from: a store is its directory, so the
log at its root and the segments beside it are one count, and two stores are two counts. A soak
cannot see a leak the counter does not charge, so the second half of this task is not in the new
file at all: **every open in `src/engine` goes through `Open`** — the log's append, the log's read,
the device wait, the manifest write, the segment write, the segment read, the index write and the
index read. `Open::of_file` exists for the calls that have a file and not a store; a codec handed a
temporary by a budget harness charges a counter nobody reads, which costs nothing and lies about
nothing.

An open is not a leak by itself. What a leak looks like is the *handle* — `Held` — kept past the
call that opened it, and the counter is what turns that into a number the run reads at the end.

**The report.** `Live::of(directory, manifest, open_tasks)` is the one place a caller asks, and it
answers the five counters in `Live::NAMES` order: `open_tasks` (handed in — the engine has no task
scheduler), `open_handles` (asked of the store's directory), `store_files` and `store_bytes` (the
files the store names, and what they cost), and `records` (the manifest's own count, which must keep
moving while the other four stay flat). Nothing in either module may read a clock: a counter that is
a duration is a counter that says something different on a loaded machine, and the spec's last case
reads the two files for exactly that.

**The service's half — what it spawned and has not reaped.** `Tasks::spawn` is the one place a
service task becomes one, and its rule is one sentence: a task is open from the moment the ledger
spawns it until the handle that owns it is awaited or dropped. Not "until it finishes" — that would
make the counter a race between a task's last instruction and the reader asking, and a soak whose
numbers depended on that would report two numbers for one run. Give each queue its own ledger
(`Queue::new` builds one; `Queue::tasks` answers it) and make the daemon's loop spawn through it
instead of calling `tokio::spawn` itself, so the tasks the service owns are the tasks it reports.

**`docs/soak.md` is the deliverable**, and it is written from a run and not from an intention: what
a cycle is, a row per counter with what its growth would mean, the steady-state rule and the
cycles/hours distinction, the two commands, and the numbers from the last run — the counters at the
halfway mark and at the end, the wall clock, and which number moved and by how much. If nothing
moved, say that and give the numbers; the run that finds nothing is the evidence.

## TRAP

1. **Starting a fresh store per cycle.** The natural way to keep a loop clean is to make each cycle
   self-contained, and a soak that does it cannot see a leak: every counter returns to where it
   started because everything was thrown away. One store, thousands of cycles.
2. **Judging minutes.** `time cargo test --test soak` is not a verdict, and neither is a test that
   asserts one: on a shared machine the same correct store takes twice as long and reports the same
   numbers, and a leak that happens during a quiet night passes. The clock is printed as evidence
   and never compared.
3. **Counting the disk instead of the store.** `store_files` is a count of the files the manifest
   names. Count what is lying in the directory and the garbage `lakelet/4.14-index-pruning` keeps on
   purpose — the index of an expired ordinal — reads as one leaked file per expiry, and the run
   blames the store for a later step's capacity number.
4. **Counting a leaked entry yourself.** The counter that keeps one `Arc` per store directory is a
   counter over a map, and a map that never drops its dead entries is a small leak in the
   instrument. A store that has been dropped must leave nothing behind.
5. **Releasing the count only when the task finishes.** "Open tasks" has to be a number two readers
   agree on. A ledger released from inside the spawned future makes the count a race against the
   scheduler, and a soak then reports whatever the machine happened to be doing.
6. **Holding handles in the accept loop.** The leak this step is built to find is one line long: keep
   each connection's `JoinHandle` in a `Vec` instead of letting it go, and `open_tasks` grows by one
   per client while every other counter is flat. The start path is not where a task leak lives — the
   loop is.
7. **Writing the page from an intention.** The measured paragraph is the reason the page exists: a
   number nobody ran is a claim about the code's author rather than about the code. Run the long
   form, paste what it printed.
