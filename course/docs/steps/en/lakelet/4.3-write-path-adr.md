# Durability is a decision: what fsync costs and which crashes you accept

## WHY

`lakelet/4.1-ingest-protocol` gave the store an append-only file and a rule that sounds like a
promise: `Spool::append` answers once the record can be read back. Read back *by whom* is the whole
of this step. A write lands in the operating system's page cache and `write` returns — the bytes are
in the machine's memory, not on its device — and `append` answered its client anyway. If the process
dies, that is fine: the kernel still has the bytes and the file is intact. If the *host* dies, the
page cache is gone and a client that was told "stored" is owed an explanation.

Making that window smaller costs one system call, and that call is not free:

- **waiting for the device is measured in milliseconds.** On the machine this step was authored on, a
  durable write costs **4.1 ms** (`File::sync_all`, which on macOS is `F_FULLFSYNC`, the call that
  actually waits for the flash cell). At 4.1 ms per record the store's ceiling is **about 240
  records/s**, no matter how many clients are connected and no matter how idle the disk is otherwise.
  A telemetry store that accepts 240 samples/s in total is not a store;
- **the cheap call is a trap.** Plain `fsync(2)` on that same machine costs **52 µs** — eighty times
  less — and on macOS it is allowed to return before the drive has the bytes. A store that measures
  `fsync` and calls the result "one device flush" has measured the wrong syscall, and will pick a
  number that is wrong in the direction that loses data;
- **what the window costs depends on which crash you are talking about.** A process that is killed
  loses nothing that was written; a machine that loses power loses everything the kernel had not
  flushed; a machine that dies *during* a write leaves a record whose tail is garbage; a file whose
  *name* was never synced can go away with its directory entry; and a device that fails its own flush
  turns "acknowledged" into a question. Those five are not the same failure and no single number
  covers them all.

So "just fsync every record" and "never fsync" are both wrong for a telemetry ingest, and each is
wrong for the same reason: nobody wrote down what it costs or what it gives up. The answer is **an
interval** — a duty cycle, chosen from a measurement, with a stated bound on how much of the write
window a machine death can take. Choosing that number is this step. Keeping it honest is the rest of
it: the decision is a **value in the code** (`Policy`, `Policy::DEFAULT`) and a **sentence in the
docs** (`docs/adr/0001-write-path.md`), and the two are checked against each other, because a
durability guarantee that lives in somebody's memory is a guarantee that changes when they leave.

The record is worth writing for a second reason. `lakelet/4.4-wal-recovery` is the other half of this
problem — it replays a prefix of the log and refuses the torn tail — and it can only do that if it
knows what the write path promised. The crash-point list you write here is that map: it says, point by
point, what is on the device after an append has answered, which every later step has to preserve.

## TASK

- Implement `src/engine/wal/policy.rs`. The decision is data:
  - `Policy` with the three answers — `PerRecord`, `Interval { millis }`, `Never` — each documented
    with **what it costs** (how often the store waits for the device) and **what it loses** (which
    acknowledged records a machine death takes with it);
  - `Policy::ALL` (every policy this build can be asked for), `Policy::DEFAULT` (what this build
    does), `Policy::name()` (the kind: a stable string, because documents name it),
    `Policy::describe()` (the whole policy, number included), `Policy::parse()` (read `describe()`'s
    spelling back, and refuse anything else with a sentence naming the forms that work, as
    `Error::Invalid` so a typo is a configuration error and not a store failure), `Policy::losses()`
    and `Policy::syncs_per_record()`;
  - `Losses` — `Nothing`, `BoundedBy { millis }`, `EverythingSinceTheLastFlush`: the machine-readable
    half of the crash-point table, so that the table and the flag can be compared by a machine.
- **Measure one durable write on your machine** before you choose a number. Write a throwaway program
  under `/private/tmp` with its own `CARGO_TARGET_DIR`, append a record to a file the way
  `Spool::append` does, and time the real call (`File::sync_all`), not `fsync(2)`. Also time the
  append without it, and `fsync(2)` alone. Record the command, the machine and the numbers in the
  ADR — the number is the reason the decision is what it is, and a decision record without one is a
  preference.
- Derive `DEFAULT` from that measurement. A rule that survives review: **the device may own at most a
  tenth of the wall clock**, so the interval is at least ten times what one flush costs, rounded to a
  number a human says out loud. `Policy::DEFAULT` must be an `Interval`; a store that waits per record
  cannot keep up and a store that never waits cannot be defended.
- Write `docs/adr/0001-write-path.md` in the house style this course uses (`relay/2.6-at-least-once` is
  the example): a `# 0001 — <title>` heading, a Status/Context block, `## Decision` (which policy, the
  measured number, the derivation), `## Alternatives` (each rejected answer and the reason it lost —
  per-record, never, and any mechanism you considered), `## Consequences`, and what would make this be
  revisited. It has to name `Policy::DEFAULT.describe()` — the spelling, not a paraphrase.
- Write `docs/crash-points.md`: at least five points, one `###` heading each, and **every** point says
  what is on the device, what recovery will see, which policies lose what, and what the operator
  observes. It must name every `Policy::name()` in the build, and it must link to the ADR and to the
  code it is about (the `links` gate resolves every target).
- Teach `Spool` what durability means, without changing what `4.1` promised. The signatures are
  already there: the scaffold declares `Spool::with_policy`, `Spool::policy`, `Spool::len`,
  `Spool::is_empty`, `Spool::durable_offset` and `Spool::sync` in `src/engine/spool/durable.rs`, the
  module beside the write path, each with a `todo!()` body — so the spec calls them from its first
  run, and **what you write is the semantics, not the shape**. `with_policy` opens the store with the
  policy it is handed, `durable_offset` is how many bytes of what this spool wrote are known to be on
  *the device*, `len` is how many it has written, `is_empty` is whether it has written any, `sync`
  makes the rest durable, and `append` consults the policy — `PerRecord` waits inside the call,
  `Interval` and `Never` do not. An interval policy may flush when its interval has passed (it reads
  the clock to decide that, and that is the only thing the clock is for here). `Spool::open` stays the
  same call and means `Spool::with_policy(directory, Policy::DEFAULT)`, because that path is what the
  daemon takes.
- Keep `durable_offset` **true**: it moves when a flush has succeeded and never before. It is the
  boundary `4.4` replays to, and a number that is hopeful instead of true is worse than no number.

## TRAP

- **A `durable_offset` that is just `len`.** It is the shortest path and it fails the case that
  matters: under `never` the two numbers have to differ after an append (`0 of 41 byte(s)`), so a
  value that answers "everything" makes the whole policy a decoration. The mirror image — a `sync`
  that moves the boundary without flushing, or after a failed flush — passes the happy case and lies
  to `4.4`.
- **`Spool::open` hard-wiring a policy.** `PerRecord` there is the tempting "safe" choice, and it
  fails the case that opens a spool without one: what `open` picks is what a deployment gets, and the
  ADR's sentence is about that value.
- **Measuring `fsync(2)` and calling it the cost of durability.** Where `fsync` does not wait for the
  device (macOS/APFS: **52 µs** against **4.1 ms** for `sync_all`), the duty-cycle rule then hands you
  an interval of about a millisecond — a per-record policy wearing an interval's name, with the worst
  of both: no throughput and a loss window you believe is bounded by a number you invented.
- **A `parse` that is more forgiving than `describe`.** `interval`, `interval(50)`, `interval(-1ms)`,
  `per_record` and the empty string all have to be refused, with a `kind()` of `invalid`; answering
  `Policy::DEFAULT` on a typo is how a store runs a durability policy nobody chose, and a refusal that
  does not name the forms that work fails the case that reads those names out of the message.
- **A crash-point list that is prose about crashes.** Five paragraphs that never say `per-record`,
  `interval` or `never` fail the per-point case, and so does a list whose right words sit in only
  some of its points. The point that names no policy is the point an operator reads during an
  incident.
- **A policy in the code that no document names, or a document naming a policy the code lost.**
  Adding an interval to `ALL` and forgetting `docs/crash-points.md` fails the names case; taking a
  policy out of `ALL` while the table still lists it fails it the same way, and that direction is
  worse, because the table is what somebody planned against.
- **An ADR that says "an interval" without the number.** The record has to hold the exact
  `describe()` spelling (`interval(50ms)`), and the three sections (`## Decision`, `## Alternatives`,
  `## Consequences`) are part of the shape: a decision without its rejected alternatives is a
  preference, and the next person re-litigates it from scratch.
- **`todo!()` left anywhere.** The scaffold's stubs are `no-todo`'s business, in every target,
  including the ones the spec never calls.
- **`len` without `is_empty`.** `clippy@4` denies warnings, and `clippy::len_without_is_empty` fires
  the moment a `Spool::len` exists without one: `struct Spool has a public len method, but no is_empty
  method`. The scaffold declares the pair, so the only way to meet this one is to lose half of it —
  and the answer is the same either way: the write path answers `is_empty` too, and for a spool that
  means the store holds no bytes yet.
- **A red spec read as a broken course.** The spec's first run fails thirteen of its fourteen cases,
  every one of them at a `todo!("step lakelet/4.3-write-path-adr")` in the scaffold
  (`src/engine/wal/policy.rs`, `src/engine/spool/durable.rs`), because the decision's *shape* arrives
  with the scaffold and its semantics do not. `test result: FAILED` there is this step's starting
  line, and the case still failing once every stub is gone is the one with something to say.

## FURTHER

- `lakelet/4.4-wal-recovery` is the next half: a log is replayed to a prefix, and that prefix is the
  boundary this step's `durable_offset` draws. The torn write in your crash-point list is 4.4's
  subject — a record needs a checksum before a reader can tell a short write from a whole one.
- `lakelet/4.5-batch-writes` is what a per-record policy cannot afford and what an interval policy
  makes possible: many records per flush, and a count of what that saves.
- Production references for the same three-way choice, in four systems: SQLite's `PRAGMA
  synchronous` (`FULL` is per record, `NORMAL` is an interval, `OFF` is never), MySQL's
  `innodb_flush_log_at_trx_commit` (`1`, `2`, `0` — the identical enum on the identical axis),
  PostgreSQL's `synchronous_commit` with `wal_writer_delay` (200 ms by default: this step's interval
  with a different number and a different argument), and any WAL where group commit batches one flush
  across many transactions. Read one of them and ask what their number measures.
- The calls themselves, in the man pages your machine ships: `fsync(2)`, `fdatasync(2)` (which skips
  metadata that does not matter for reading the data back, and is not the same thing as waiting) and
  macOS's `F_FULLFSYNC` (the one that waits). Rust's `File::sync_all` is the portable way to say what
  you mean, and its cost is a property of the device in front of you, so measure it rather than
  believing a number from 2015.
- Read the `docs/adr/` directory of a project you depend on. The good records are short, name the
  alternatives that lost, and are dated. This one is `0001`; when the decision is revisited the new
  record is `0002` and it links back here instead of editing this page.
