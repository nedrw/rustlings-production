# Rotation without a gap: two keys valid, one of them preferred

## RECALL

- `sec/secrets-management@apply — mailer/1.4`: secrets out of the repository, and the four layers a
  deployment reads them through — defaults, file, environment, command line. What this step keeps is
  the rule that the secret is a value somebody put somewhere on purpose; what it deepens is that the
  *set* of secrets changes while the service runs: there the question was "where does the value come
  from", here it is "which of these values is signing, and when may the one that is not leave".
- `sec/token-lifetime@apply — mailer/1.12`: a token is issued, verified, expires and is used once —
  and *a token that survives any of them was never a token*. That step's window is written into a
  row and compared by the database; here the window is written into the token and compared by the
  daemon, and the reason the token exists at all is the one thing that step deliberately did not
  need: a key. What this step adds is the consequence that step's own sentence implies — a token
  that lives for an hour is an hour during which the key behind it must still be there, which is
  what makes a rotation an arithmetic question rather than an edit.
- `sec/hmac-signing@apply — relay/2.11`: sign the exact bytes you send, put the timestamp and an id
  inside the signed material, and compare tags with `subtle` rather than `==`, because a comparison
  that stops at the first wrong byte tells the other end how much of its guess was right. That step
  added `subtle` and `hmac` to the relay tree; this one adds `subtle` to *this* tree and uses the
  same two crates for the same reason, with one difference that is the whole point here: the key the
  tag is computed under can change, and the old one has to keep verifying for a while.

## DELTA

Every other step of this project decided what happens to *bytes*: what a frame is, how a batch is
written, how a query is answered, how a copy is restored. This step decides who may send any — and
the interesting half of that is not the check. It is the day the check's key has to change, because
that is where a deployment that looked secure for a year breaks in one command: delete the old key
and every client still holding a token signed with it is refused at its next connection, mid-flight,
with no window in which to re-key them.

So the shape of this step is a **ring** rather than a key, and four decisions fall out of it:

- **the ring is a directory of files, and the directory is the switch.** No `keys` directory below
  the store means authentication is off; a directory with no key in it is a refusal. That is not a
  convenience for the tests — it is the honest statement of what a deployment without keys *is*, and
  it is what keeps every harness the earlier steps shipped (`lakelet/4.6-ingest-backpressure`'s
  overload scenario, `lakelet/4.17-soak`'s long run) working without a line changing in either: both
  connect to a store with no ring and send batches;
- **the key that signs is the newest one, and both verify while both are open.** The rule is one
  sentence — the open key with the latest `not_before` is the one that signs — and it makes a
  rotation an *edit to a file* rather than a moment in the daemon: there is no state to flip, no
  restart to schedule and nothing that can be half-done;
- **a key may only leave after the longest lifetime a client could still be holding has passed
  since something newer took the signing over.** A bound built from the lifetime most clients ask
  for is a bound that holds for every client except the one that asked for the longest token — which
  is exactly the client it strands. So the module answers one number
  (`earliest_safe_retirement`), `lakeletq rotate --retire` refuses to go under it, and the daemon
  refuses the tokens a hand-edited retirement strands. Retiring early is a refusal, not a warning;
- **the ring is read per connection, and nothing in it reads a clock.** Reading it per connection is
  what makes a rotation take effect on a *running* daemon; taking every instant as an argument is
  what makes "what does this ring do at this instant" a question a test answers with a number. The
  cost of the first is one directory read and a handful of file reads per client, and the page says
  so rather than pretending it is free.

The comparison is the one place this step's code looks like `relay/2.11`: the tag is an HMAC-SHA-256
over the exact bytes that travel, and it is compared with `subtle`, because `==` on a tag leaks
where a guess diverged.

## TASK

The scaffold creates four files and adds two lines. `src/service/keys.rs` is the ring — the key
vocabulary, the token, the five typed refusals (plus "this is not a token at all"), the window
arithmetic — with every body answering `todo!()`. `src/cli/rotate.rs` is the operator's command, with
one body answering `todo!()`. `tests/sim_rotation.rs` is **complete** and fails until both are
written. `docs/rotation.md` is a `[TODO](TODO)` stub with the headings the page has.

**`src/service/keys.rs` is the step.** It reads no clock and no environment, and everything below is
a decision about what that means:

- a key file is `name=value` lines, named `<id>.key`, with `id`, `secret` (hex, either case),
  `not_before_millis` and an *absent* `not_after_millis` while the key is open. The reader is strict
  and every refusal names the file and the line, because this file is edited by hand at three in the
  morning;
- `preferred` is a property of the *files*, not of the clock: the open key with the latest
  `not_before`, ties broken by id, so two machines reading the same directory agree. `issue` is where
  the clock enters, and it refuses to sign with a key whose window has not opened rather than minting
  a token its own reader would refuse;
- `verify` is the typed answer a page and a log can act on, checked in the order a reader would ask
  it: is this a key I have, is the tag *this* key's over *these* bytes, has the key been retired, is
  the token's own window still open. Retirement before expiry is deliberate: a client whose key is
  gone has to be re-keyed, and that is the fact an operator needs first;
- the token is a payload inside `lakelet/4.1-ingest-protocol`'s frame — **nothing in `src/protocol`
  changes** — and the tag covers the bytes before it, length prefixes and all. Sign what you send;
- and `earliest_safe_retirement` is the number the whole step exists for. The ring holds no record of
  *when* a key arrived, only the `not_before` each file states, so the last instant a key could have
  signed is the latest `not_before` among the keys newer than it, and its tokens are live until that
  instant plus `Window::MAX_TOKEN_LIFETIME_MILLIS`. `None` is the honest answer for the key nothing
  has taken the signing over from yet: it may still sign, so no instant after which its tokens are
  all gone is knowable from the ring.

**`src/cli/rotate.rs`** is the same contract `lakelet/4.10-downsampling` established and
`lakelet/4.19-backup-restore` re-stood, on three operations: `--add --id <ID> --secret <HEX>
[--from <MILLIS>]` writes one key file (the secret is the operator's — this build does not generate
keys, and the box that would is `openssl rand -hex 32`, not a seeded generator), `--retire <ID>
[--at <MILLIS>]` writes the key's end and refuses anything under the safe instant, and `--list`
answers the ring oldest first with each key's window, whether it signs, and the instant it may leave.
The dispatch arm, the `USAGE` lines and the class mapping in `src/cli/mod.rs` are yours, exactly as
`lakelet/4.19-backup-restore` did it for `backup`.

**The daemon's half is three edits in `src/service/ingest.rs`**, and the shape of them is the
lesson: read the ring **per connection** (that is what makes the rotation take effect on a running
daemon), take the **first payload as the token** when the ring is open, and **count a refusal** where
the other refusals are counted so a client that never got in shows up in the numbers a deployment
reads. Everything else in that loop is `lakelet/4.6-ingest-backpressure`'s and must not move.

**`docs/rotation.md` is the operator's page**, written from runs: the procedure in order, the ring as
`--list` prints it, the arithmetic of the window, what a gap costs and where the refusals are
counted, the `subtle` comparison in one sentence, what an empty ring means, and a list of what this
step deliberately does **not** do — no key generation, no HSM, no revocation list, no re-encryption,
and a ring read per connection rather than a watcher.

## TRAP

1. **Retiring the old key at the moment the new one arrives.** It reads like a rotation and it is a
   cut: the clients that connected a minute ago are holding tokens signed by a key that is now gone,
   and they are refused at their next connection — which, for a client that connects per batch, is
   immediately. `earliest_safe_retirement` is the number that says how long to wait, and the case
   the spec writes about it is one millisecond of arithmetic.
2. **A bound built from the usual lifetime.** "Our tokens live five minutes, so five minutes is the
   wait" is a bound that holds for every client except the one that asked for the longest token this
   deployment may issue — and `MAX_TOKEN_LIFETIME_MILLIS` exists precisely so that the number is
   stated once. `issue` refuses a lifetime above it for the same reason.
3. **Reading the ring once, at startup.** The rotation then needs a restart, which means a window in
   which the daemon is running the old key and the file on disk says the new one — and an operator
   who scheduled the restart after the retirement has locked everybody out. The ring is read per
   connection; the cost is one directory read per client and the page names it.
4. **An empty ring meaning "refuse everything".** A deployment that has not turned authentication on
   is a deployment with no keys, and a daemon that refused every connection until somebody wrote a
   key file would break every harness and every load generator it has — the two the earlier steps
   shipped included. The switch is the directory, and the *other* state (a directory with no key in
   it) is the refusal, because that one is a deployment that meant to authenticate.
5. **Failing open when the ring cannot be read.** A key file with a typo in it is not "no keys": it
   is a deployment that has authentication on and a ring the daemon cannot parse. Treating that as an
   empty ring lets everybody in — past the retirement the operator just wrote. The connection is
   refused, counted, and the warning names the file.
6. **Comparing tags with `==`.** It compiles, it is right every time, and it leaks where a guess
   diverged, because the comparison stops at the first wrong byte. `subtle::ConstantTimeEq` is the
   line of code that fixes it, and the spec's shape check exists because a timing assertion would be
   a flaky test rather than a proof.
7. **Signing a canonical re-encoding.** A tag computed over the fields rebuilt "the same way" is a
   tag over a second spelling of them: it works until one side writes a length differently or a
   string in another case. The tag covers the bytes that travel, and the bytes that travel are what
   the reader feeds back into the same function.
8. **A readiness probe counted as a refused client.** A daemon that logs a refusal for every
   connection that carries nothing turns every health check into a warning, and an operator stops
   reading the warnings. A connection with no traffic is logged at `debug`, exactly as it was before
   this step.
9. **A retirement written in place.** The daemon reads this directory per connection, so a key file
   that is being rewritten is a file that can be read half-written — and half a key file is a ring
   that refuses to load, which refuses clients. Write beside it and rename.
10. **Generating the key from the store's own randomness.** `lakelet/4.13-model-based-tests`'s
    generator is seeded on purpose: the same seed is the same keys on every machine, which is
    exactly wrong for key material. The operator supplies the secret, and the page says so next to
    the command.
