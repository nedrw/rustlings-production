# Compaction rewrites segments while readers keep reading

## WHY

A store that only ever appends files grows without bound, and a reader pays for every one of them.
`lakelet/4.7-columnar-segments` gave this store a file worth keeping — records by column, compressed,
sealed — and closed the question of what a flush *writes* while opening the one this step answers:
how many records a segment holds, and when a new one starts. The answer so far is "one segment per
flush", and that arithmetic is the step:

- **every flush is one more file a query opens.** A segment has to be read from its header before
the first record is visible, and a query that spans an hour spans every segment that hour produced.
Sixteen flushes into this step's own workload the store is 8 112 bytes in sixteen files; the same
2 048 records in one file are 5 700. The bytes are not the problem — the *opens* are, and at a flush
every five seconds a day of ingest is seventeen thousand files;
- **two segments that hold the same series share nothing.** Not a dictionary, not a run, not a `zstd`
frame: the case each one pays for at its own boundary is the case one bigger block gets for free. In
the same workload, sixteen separate segments cost `bytes_per_sample` about forty percent more than
the single file they merge into.

Compaction is what fixes that, and it costs bytes that were already written once. That price has a
name — **write amplification** — and this step measures it instead of arguing about it: on the budget
workload a pass over sixteen segments writes **12 029 bytes** and the store stops holding **2 412**,
so this build rewrites about **5 bytes for every byte it removes**. Merging two segments at a time
costs about **10**; merging the whole store on every call costs about **40**. The other direction is
cheaper to describe and worse to live in: a policy that never merges leaves the file count a reader
pays for exactly where it was. So the decision *which* segments to merge is not a match arm inside a
loop — it is a value, `Policy` and a `Plan` in `src/engine/compaction/plan.rs`, and it can be
judged without merging anything.

The second half of the step is what the first half may not break: **a reader never sees a
half-compacted store.** A merge that rewrote the segments a query was halfway through would answer a
record twice or answer neither copy of it, and no count would tell anybody. So a merge is visible in
exactly one step — write the new segment, make it durable, swap what readers look at, and only then
let the old segments go — and a read that begins before the swap and ends after it has to answer
exactly what a read that ran entirely before it answered: the same records, once each, in the same
order.

That is also where the storage layer's crash points get their second chapter. `docs/crash-points.md`
is about *the log*: a record is written, a machine dies, a replay proves a prefix and stops at the
first record it cannot. This step is the same rule one level up, where the thing that may be
half-done is the **set of files a store is made of** — and the reason a crash there still leaves one
of exactly two worlds is a decision that has to be made once and kept: **the manifest is the store.**
A segment counts when the manifest names it, in the order it is named, and everything else in the
segment directory is a leftover a crash left behind. That single rule turns five different crash
stages into one recovery: read the manifest, delete what it does not name.

## TASK

Five properties make up this step. Everything else is packaging.

- **The policy is a value, and a plan is data.** A **size-tiered** rule, in one sentence: *a plan
takes the oldest run of `width` consecutive segments whose sizes are all within a factor of `ratio`
of each other.* Consecutive because a merge writes one segment where its inputs were, so a run that
skipped a segment would move that segment's records behind records that came after them; the oldest
because those are the files a reader has been opening longest; both ends for the size comparison,
because a rule that only looked at one end would merge a tiny file into a large one. A plan takes
exactly `width` segments — never one (that rewrites bytes and removes none), never the whole tier (a
cost that follows how long the store has been running is a cost nobody can bound). This build ships
**four segments within a factor of two** — `Policy::DEFAULT`, and the baselines in the budget lane
are taken on it: four equal segments of `s` bytes merge into about `3.2 s`, which is outside the run
they came from, so the next merge works on the segments that arrive instead of rewriting what the
last one wrote, and the rewrite ratio stays in single digits on this workload (about five), where
merging pairs costs about ten.
- **A reader holds a snapshot, and a snapshot names a set.** `Segments::snapshot()` is what a query
takes when it starts: the segments that were the store at that moment, still readable however many
merges happen beside it, and still *on the disk* until the last reader that named them lets go. A
segment a merge wrote is the store when the manifest names it and not one instant earlier.
- **A merge is visible in one step, and the store is what the manifest names.** The new segment is
written and flushed *before* the manifest names it, so a crash cannot leave an index pointing at
bytes the device never kept; the manifest is written to a pending name, flushed, renamed onto its
own, and the directory flushed after the rename, so a reader of the manifest sees the old one or the
new one and never a half-written mix. The segments a merge replaced are *retired*: the last snapshot
that named them deletes them.
- **A kill at each stage of a merge leaves one of two worlds.** Name the stages in that order —
`planned` → `written` → `durable` → `swapped` → `retired` — and say what a crash at each one
leaves: nothing on the disk, an orphan file in whatever part the device committed, a whole orphan,
the new set (with the old segments still there if a reader held them), and the new set with nothing
left over. Never a gap, never a record twice; and `lakelet/4.4-wal-recovery`'s rule for the log is
unchanged, because a merge never writes to the log.
- **Rewriting is a number.** The counts live in `tests/budget_compaction.rs` and the baselines in
`course/tracks/lakelet/budget/4.8-compaction.toml`: how many merges, how many files are left, how
many bytes were written and how many the store stopped holding — and the ratio of the last two,
which is the one that says whether a policy is paying for itself. The relations are part of it: a
merge leaves **fewer files** than it found, removes **every record it took and nothing else**, and —
on records with structure to share — writes **fewer bytes than it read**.

**What the course gives you, and what is yours.** The scaffold declares the shape, because the
harness, the spec and the next steps read it:

- `src/engine/compaction/plan.rs` — `SegmentInfo`, `Policy` (with `DEFAULT` set to the tempting
value), `Plan`, and the doc comment that states the rule. `Policy::plan` is yours;
- `src/engine/compaction/mod.rs` — `Segments`, `Manifest`, `Merge`, `MergeReport`, the file-name
constants, `file_of`, and the module docs that state the layout and the five stages. The manifest's
own bytes are yours (nothing outside the store reads them), and so are `seal`, `plan`, `merge`,
`install`, `compact` and everything private;
- `src/engine/compaction/snapshot.rs` — `Snapshot` and the private set behind it, with the promise
in the docs and the retirement left to you;
- `tests/sim_compaction.rs` and `tests/budget_compaction.rs` — the course's harnesses, which are what
`slow:sim@3` and `slow:bench-budget@10` run. They are not yours to edit;
- nothing else in the project changes. The log (`4.1`–`4.4`), the batch boundary (`4.5`), the queue
(`4.6`) and the segment format (`4.7`) stay exactly as they are: this step adds a second artefact
next to the log and one new rule about what a reader may see.

The boundary holds here too: `src/engine/**` may not name the service layer, in code or in prose
(`lakelet/4.1-ingest-protocol` reads those files as text), and a merge is engine work — it runs in a
test, in a repair tool and in a load generator that has no configuration file at all.

## TRAP

1. **Letting the old segments go at the swap.** Deleting them when the manifest changes hands gives a
reader that began before it a file nobody names: the spec's
`a_reader_that_took_a_snapshot_before_the_swap_answers_the_same_after_it` fails on the records, and
the sim's `files=` count shows the replaced segments gone while a reader still named them.
2. **Swapping the manifest before the new segment is durable.** The crash between the two leaves an
index pointing at bytes the device may never have kept, and the store answers a *gap*: the sim's
`written` and `durable` stages go red, naming the record count that came back short.
3. **Writing the manifest in place.** Appending to it, or overwriting it in place instead of writing
a pending file and renaming, means a crash mid-write leaves a half index — and a half index read as
a store with fewer segments is a hole in every answer after it. The spec cuts a manifest in half on
purpose.
4. **Reading the newest file instead of what the manifest names.** A directory listing is not a
store: after a crash the newest file is exactly the orphan a merge never installed, and a reader
that lists the directory answers a world nobody wrote — with the records of that segment counted
twice. `a_store_ignores_what_its_manifest_does_not_name` is the case.
5. **Carrying out a stale plan.** A plan is a value taken at a moment. A merge that takes what the
plan names without asking the store again writes a segment holding records that are already merged,
and every one of them is answered twice — which is why `Segments::merge` refuses a plan whose
segments are gone, and why a stale plan is an `Error::Invalid` and not a repair.
6. **A policy that merges pairs (or everything, every time).** The counts move and the bound says
which: `merges` goes from five to fourteen, `bytes_rewritten_per_byte_removed_max` from about five to
about ten — and a policy that merges the whole store on every call rewrites it sixteen times and
removes nothing (`merges`, `bytes_rewritten_max`, `plan_left_max`).
7. **Deduplicating, or keeping "the newest value per key".** This store's records are events, not
values under a key: a merge that drops a record removes bytes and *data*, and the budget's
`records_lost_max` is a bound of zero for exactly that reason.
8. **Sizes compared as counts, or multiplied in `u64`.** A tier is about bytes — the cost of reading
and writing them — and record counts say nothing about that. And a comparison written as
`size * ratio` overflows on a store with large segments (`u64::MAX` is a legal size, and the spec
plans one): compare in `u128`, or divide.
9. **Trusting a number the index states.** A segment's record count and byte length are the store's
own claims about a file; reserving `Vec::with_capacity(stated)` or reading a file of the wrong length
as if it were whole is how a damaged store becomes a *shorter* answer instead of a refusal.
10. **A snapshot that holds paths instead of the set.** A list of path names survives a merge as a
list of files that no longer exist. What a reader holds has to be the set itself — that is what makes
the deletion happen after the last reader rather than at the swap.
11. **`write_manifest` before the segment's bytes.** The order is the crash point: segment bytes,
segment flush, manifest bytes, manifest flush, rename, directory flush. Moving the flush after the
rename is the same bug as trap 2 with more steps in between.
12. **A `todo!()` left in any of the three files.** `no-todo` runs over every target, including the
merge path the spec reaches only through the crash cases.

## FURTHER

- **The three compactions in the field, and which one this is.** Leveled compaction (LevelDB, RocksDB)
keeps non-overlapping runs per level and pays write amplification per level for a floor on read
amplification; [size-tiered
compaction](https://docs.datastax.com/en/cassandra-oss/3.x/cassandra/dml/dmlConfigStorageEngine.html)
(Cassandra's default, and this step's rule) merges same-sized runs and keeps the write cost low at the
price of a file count that is logarithmic rather than constant;
[the RocksDB compaction wiki](https://github.com/facebook/rocksdb/wiki/Compaction) describes the
hybrid ("universal" and "FIFO") and, importantly for a policy, its parameters:
`max_bytes_for_level_base`, `level0_file_num_compaction_trigger`, `max_background_compactions`.
Read the parameter names and then this step's `width` and `ratio`: the shapes are the same, the names
are the part that is RocksDB's.
- **The trade has a name and a paper.** Write, read and space amplification trade against each other
— the RUM conjecture ([Athanassoulis et al., VLDB 2016](https://arxiv.org/abs/1603.01398)) is the
formal version — and this step's numbers are one point in it: 5 bytes written per byte removed for
sixteen files becoming one, against a query that no longer opens sixteen of them.
- **Tombstones, and why retention is a different problem.** RocksDB deletes a key by writing a
*tombstone* and allows the key's bytes to disappear only when a compaction reaches the oldest level —
so "delete" is a merge that removes data, and the rule this step refuses to break ("a merge keeps
every record") is exactly the rule that has to be *given up carefully* once there is a tombstone.
This store has no keys to shadow, which is why every record it ever accepted is still there. What it
needs instead is time: `lakelet/4.9-retention` is where "remove" gets its second meaning and where a
pass deletes *whole segments by timestamp* rather than records inside one, with a reader-holds rule
like this step's and a proof that nothing newer than the cutoff moved.
- **What the industry calls the manifest.** RocksDB's `MANIFEST` is a log of `VersionEdit` records and
the "install" of a compaction is one of them — the same idea as this step's "write a whole manifest
and rename it", with a log where this build has one file. The other half of the idea is in
`DeleteObsoleteFiles`: a file that is replaced goes on a *list* and waits for the readers that
reference the version it belongs to, which is this step's retired set with more bookkeeping.
- **`sync`, `rename` and the directory.** The one write-ordering idiom this step uses — write a
pending file, flush it, rename, flush the directory — is what
[SQLite's atomic commit](https://sqlite.org/atomiccommit.html) is about at length, and what makes
`rename` the safe primitive is that it is atomic on POSIX filesystems while `write` is not. The
subtlety worth remembering is the *directory*: flushing a file's bytes does not make its name
durable, which is `docs/crash-points.md` point 4 and the reason the manifest swap flushes twice.
- **Time partitioning is the same shape.** TimescaleDB's chunks and its compression/retention
policies are this step's segments with a time dimension: a chunk is closed and compressed once it is
older than a policy's interval, and dropping old data means dropping a chunk rather than rewriting
one. `lakelet/4.9-retention` is that step, and it is why a merge here keeps every record: the file
that has to be cheap to *remove* is a whole segment, not a record inside one.
- **The next reader of all this.** `lakelet/4.11-query-engine` is what takes a `Snapshot` and walks
the segments it names, and it leans on the manifest's record counts to say what a query will read
before it reads anything. What this step owes that one is the promise it just made: the set a
snapshot names is whole, in order, and does not change under it.
