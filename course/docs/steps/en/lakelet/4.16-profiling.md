# A profile is evidence: sample the process, read it, and say what it means

## WHY

A counter reports what it was built to count, and the number that was never counted is the number
that decides the incident. A store whose query profile is green and whose throughput is a tenth of
what it should be is not a contradiction: it is a counter looking at one half of a process while the
other half waits for the device. The only way to find that out is to *look at the process* — and a
sampler is the instrument that looks, because it interrupts whatever is running instead of reporting
on what somebody remembered to instrument.

That is also why this step's deliverable is a **page**. A profile nobody wrote down is an anecdote:
the numbers are on one machine, in one terminal, from one build, and the next person reads them as
hearsay. A page that carries the invocation, the sampler's own output, and one sentence about what
to change is evidence somebody else can reproduce, argue with, and act on.

## TASK

The scaffold added the mode, the two lines that reach it, and the page's skeleton:
`src/bin/lakelet-load/profile.rs` is the whole of `--profile` with two `todo!()` bodies in it, the
loader declares it inside its marked block and dispatches to it before the ingest grammar reads a
word of the line, and `docs/profile.md` is a stub of TODOs.

**`cycle` — one cycle of the loop, and everything it is made of.** The workload you are given is
`simulate`'s records for one batch, in `src/bin/lakelet-load.rs`; `from` is the first timestamp this
run may write (the framing around you works that out). Your cycle has four steps, in the order a load
run does them: move the workload on to `from` and one window per cycle after it, put those records
through the protocol path (the frames a client would send, read back out of their own bytes, so the
store holds what the wire carried), seal them into the store, and ask the store **one question about
the span you just wrote**, counted by the phases `lakelet/4.15-budget-regression` established. The
first cycle's trace *is* the run's report and every later one is merged into it.

Two properties of that shape are what the spec checks, and they are the whole reason the loop is
written this way:

- **the records a cycle ingests are the records its query reads and answers.** `decode`, `filter`
  and `aggregate` come out equal to `records`, `blocks` and `decompress` equal to `cycles`, and
  `headers` is one manifest entry per segment per cycle. A question that reached further back would
  break the first of those, and the failure message says which phase met a segment it should not
  have;
- **nothing about a counted run depends on the machine.** No clock, no thread count, no wall time
  reaches those counters, so two `--cycles 8` runs print the same bytes. `--seconds` is the run a
  human samples and it is allowed to vary; nothing may depend on how many cycles it got.

**`lines` — the shape the mode prints.** One line per phase *in the order a query walks them*, then
`cycles=`, `records=` and `bytes=`, and `seconds=` last for a timed run. `USAGE` in the same file has
the format written out with the numbers a `--cycles 8` run prints, and the phases' names come from
`Phase::name` rather than from string literals: a profile is read by a script, so it is a shape and
not a sentence.

**One program leaves one class behind.** The mode's `exit_code` is that rule; ask it from the
loader's `main` as well, so a flag the *ingest* mode cannot read leaves `2` the way a flag in this
mode does. A deployment that answered `1` about its own command line would be lying about what went
wrong.

**`docs/profile.md` is the deliverable.** Write it from a run, never from an intention:

- **what was sampled** — the profiler situation `kiln doctor` reports on your machine, and the exact
  invocation: a release build, `--seconds 30`, the pid, and `sample <pid> <seconds> -file out.txt` on
  it;
- **the two symbols at the top**, as the report printed them, and what each is doing in this store;
  the call graph above that table is what says where they come from;
- **the change the numbers justify** — one sentence, tied to the phase counters, and then what would
  have to move in the counters for that change to be visible. If the answer is "nothing would", say
  so and say why that is the finding: a counter and a sampler are not two spellings of one number;
- **the machine-checkable table** — a fenced block whose lines are exactly the whole output of a
  `--profile --cycles <n>` you state in the sentence above it. The spec re-runs that command and
  compares line for line, which is how the page cannot drift from the code.

Do not touch `src/engine/trace/**`: the phase names and their meaning are
`lakelet/4.15-budget-regression`'s contract and four earlier specs assert them.

## TRAP

1. **Sampling `cargo run`.** `cargo run` starts the loader as a *child*: the pid you sample is
   cargo's, and the report is a report about cargo compiling and waiting. Run the binary out of
   `target/release/`, and sample its pid.
2. **Quoting a number you did not print.** The block on the page is compared against a live run, so
   a count edited by hand — even a plausible one — fails with both lists side by side. Edit the page
   from a run, and re-run it after any change to the loop.
3. **Charging the phases from the answer instead of from the run.** A loop that filled the trace
   from `records` after the fact would print the same numbers on this workload and be worth nothing:
   the point of a count per phase is that it was charged *where the work happened*. Ask the executor
   for its own trace and merge those.
4. **Asking about the whole store rather than about what the cycle wrote.** The natural thing to do
   with a growing store is to query all of it, and it breaks the conservation: `decode` becomes a
   sum over every cycle so far and stops being `records`. A cycle asks about the span it just wrote.
5. **Printing a refusal on standard output.** A run that answers `--profile --cycles` with half a
   profile and then a complaint is a run a script cannot pipe anywhere: the cases assert that
   standard output is empty whenever the exit code is not `0`, and `Lakeletq`'s rule is the same one
   (`lakelet/4.10-downsampling`).
6. **Profiling a debug build and believing it.** A debug build's samples are largely samples of
   unoptimized code, which is a fact about `cargo build` and not about this store. Say which build
   the page is about.
7. **Writing an assertion about a `--seconds` run.** How many cycles a timed run got is the
   machine's business, so a spec that pinned it would go red on a busy afternoon — the same failure
   `jobq/3.22-bench-budget` was written to avoid. The only thing a timed run is quoted for is that
   it ran.
8. **Promising a sampler this machine does not have.** `cargo-flamegraph` is installed and cannot
   run without root, and `samply` is not installed: a page that sends a reader to either one is a
   page whose first step fails. `kiln doctor` is what measures which sampler works, and the page
   says what it found.
