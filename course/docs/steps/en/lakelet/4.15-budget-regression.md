# From budget to blame: which phase moved, and by how much

## RECALL

- `perf/bench-budget@apply — jobq/3.22`: a budget built out of counts, a guard over the shape of their
  growth, and the names a harness prints so that a gate can compare them. The rule that step
  established is the one this step stands on: **a wall-clock threshold is a measurement of the
  machine**, red on a busy afternoon and green on a quiet one, and the numbers a loop leaves behind —
  cells examined, statements written — are the same in every process on every machine. This step is
  not a second budget; it is what to do *when the budget goes red*, because "something got slower" is
  a sentence no review can act on.
- `perf/load-testing@apply — relay/2.20`: deliberate, repeatable pressure on a whole service, and the
  curve a capacity answer is read from — p99 against concurrency, with the backlog beside it. That
  step measures a *service* from the outside and this one measures a *query* from the inside, and the
  two questions are neighbours: "is this keeping up" is a curve of runs, "which part of this run is
  slow" is a profile of one. What this step takes from it is the discipline of a run nobody has to
  trust: fixed inputs, statistics that were computed, and an answer two people can compare.

## DELTA

`lakelet/4.14-index-pruning` made one cost of this store a number. `pruning_rate` says how much of a
store a query did not have to open, and the counters beside it — `segments_pruned`, `blocks_pruned`,
`bytes_read`, `bytes_avoided` — say what that was worth. That is the *how much*. It is not the
*where*: a query whose prune decision stopped pruning, a segment format that got more expensive to
inflate, a predicate that keeps ten times as many records as it used to, and a `GROUP BY …, series`
that walks the records once per series are four different defects, and every one of them moves
`rows_scanned` or `rows_answered` — or nothing at all, because a query that reads two hundred files
to return thirty records answers correctly and slowly.

So this step counts the work **inside** a run and splits it by the part of the engine that paid. Seven
phases, in the order a query walks them: the plan that decided about the store (`headers`), the blocks
read (`blocks`), the blocks inflated (`decompress`), the records decoded (`decode`), the records the
predicates kept (`filter`), the values folded into windows (`aggregate`), and the buckets written into
the answer (`render`). The counts travel with the answer, the harness prints a profile of two queries
over one store, and the page says how a red budget is read into a phase.

Three things are deliberately **not** here, and they are the reasons this step is shaped the way it
is:

- **no time.** Not a duration, not a rate, not a start and an end. A profile that measured the machine
  would be a profile two machines disagree about, and `jobq/3.22-bench-budget` settled that argument
  already — this step applies it one level down, to the parts of a single run rather than to the whole
  of one;
- **no new plan key.** `EXPLAIN` prints what a query *would* do and is pinned by two earlier steps by
  name and in order; the executed counts and the profile belong to a run that happened, and they go in
  the outcome and in the answer's document. A step that added a line to the plan to say what the run
  cost would be a plan lying about itself;
- **no stored history.** A trace describes one run and is reported with it. Nothing here keeps a
  profile of a past query, because a store that remembered its own past costs would be a store whose
  numbers depend on when it was asked — and `lakelet/4.20-capacity-model` is where a cost that can be
  *predicted* from the store's shape is the subject, not measured from a run.

## TASK

The scaffold added a module, an instrument and a page: `src/engine/trace/mod.rs` and
`src/engine/trace/counters.rs` (the contract of the counter, with `todo!()` bodies), the course's
harness `tests/attribution.rs`, and `docs/perf.md` as a stub. `src/engine/mod.rs` declares the module
inside its marked block.

**`src/engine/trace/counters.rs` — a count per phase, as a value.** `Phase` is the seven phases in
the order a query walks them, with the one list (`Phase::ALL`) and the name each phase is spelled with
in a metric line and a JSON key. `Trace` is the run's account of itself: `charge` where the work
happens, `count` and `total` to read it back, `shares` as whole percent of the run, and `merge` so
that two runs can be reported as one pair. Four decisions in that file are worth more than the code:

- **a charge is a count of something that happened**, at the place it happened. Deriving a phase
  afterwards from another number is the one shape that makes a profile useless, because the derived
  count cannot say which phase it came from;
- **the phases are a pipeline, not seven tallies.** `decode >= filter >= aggregate >= render`,
  `headers >= blocks >= decompress`, and `headers` is the plan's own conservation identity —
  `segments_opened + segments_pruned + blocks_pruned`, the three lists `lakelet/4.14-index-pruning`
  counts, added up. A counter no case can falsify is worse than no counter;
- **`filter` is the predicate and `aggregate` is the range.** A record `WHERE` kept can still be
  outside the range, and that is the interesting case: it says the predicate got wider rather than the
  range;
- **`shares` adds up to 100.** Whole percent of a whole run leaves a remainder, and a profile that
  said 99 would be a profile somebody has to explain; the phases with the largest remainders take it.

**The executor charges it, and the outcome carries it.** `query::exec` is the only place that sees
all seven phases, so it is where the trace is charged and where `Outcome` grows a `trace()` beside the
counters `lakelet/4.11-query-engine` and `lakelet/4.14-index-pruning` added. The rules are the ones the
phase table states: one `headers` per segment the plan examined (the plan's three lists are the whole
store, which is what makes that count checkable), `blocks` and `decompress` around each read,
`decode` per record the read returned, `filter` where the predicate is asked, and `aggregate` and
`render` from the window pass's own account of itself — the values it folded in, and the buckets it
wrote. `Outcome`'s existing fields must not change: four earlier specs assert them.

**`lakeletq query --json` prints the profile.** The text form's document grows one key, `trace`,
holding one number per phase in the order the phases ran; the harness's lines and that document spell
the phases the same way, from the same list. The plan's `EXPLAIN` output and the flag form's array of
buckets do not change at all — `lakelet/4.10-downsampling`'s array is the shape a script already reads,
and a profile added to it would be a second answer to a question that form does not ask.

**`docs/perf.md` is the page, and it is the deliverable.** The phases and what each one counts, the
identities and what each would catch, the command that prints a profile, the walk from a red budget to
a phase, one worked example with the numbers this project's store actually printed, and the two ideas
the page stands on — a profiler's phase view and a counter compared across two runs. A claim with no
count behind it does not belong on it.

**The harness is the course's, and the baseline is content.** `tests/attribution.rs` is the
instrument: it seals a store, asks two queries, and prints the profile of each beside the difference
between them. Do not edit it to make a number nicer, and do not edit the course's baseline — the gate
reads the course's copy, and `kiln reset lakelet/4.15-budget-regression` puts the harness back.

## TRAP

1. **Charging `aggregate` for what the window pass was handed.** A `GROUP BY …, series` query hands
   the pass the records it read once per series, so a run that charged the slice would count the same
   record once per series: on the wide query that is `aggregate` 720 against `filter` 360, and the
   identity `filter >= aggregate` fails on the very store the lane asks about. What became part of a
   window is the honest count, and the pass already reports it.
2. **Charging `filter` for the range as well as the predicate.** The two are different questions and
   the profile is what keeps them apart: with the range folded into the filter, `filter` and
   `aggregate` are the same number on every run — the identity stops falsifying anything — and the
   half-hour case goes red, because it is exactly the case where a record the predicate kept is
   outside the range.
3. **Timing it.** A phase measured in milliseconds is a phase a loaded machine moves, and the gate
   that reads it goes red when somebody else's build was running. Nothing in the trace module may
   name a clock — the spec reads the sources to say so — and the reason is the one
   `jobq/3.22-bench-budget` settled.
4. **Adding a key to `EXPLAIN`.** The plan prints what a query *would* do; the profile is about a run
   that happened. `lakelet/4.11-query-engine`'s spec counts the plan's lines and
   `lakelet/4.14-index-pruning`'s asserts its thirteen keys by name and in order, so a fourteenth key
   turns two earlier steps red — and the numbers a red budget is read with are not the plan's.
5. **A counter derived after the fact.** `decode = rows_scanned` and `aggregate = rows_answered` are
   exactly the honest numbers on every run this lane measures, so a trace whose two phases came from
   the outcome's totals passes the whole spec — and it is still the failure this page argues against,
   because a count derived from another count cannot say which phase the work came from. The drill is
   what makes that visible: take the index out and `decode` moves while `filter` does not, and a trace
   that was assembled afterwards has no way to have measured that.
6. **A share that does not add up, or a phase left out of the profile.** Whole percent of a whole run
   leaves a remainder; a profile that prints 99, or that leaves a phase out because its share rounded
   to nothing, is a profile a reader has to reconstruct rather than read. The phases that ran are the
   rows, and the remainder goes to the largest ones.
7. **A metric that is zero in both runs.** A counter neither run charges is a line the gate compares
   and no defect can move: it makes a green gate look like evidence. A phase that is genuinely not
   part of a run belongs in the page's prose, not in the harness's output.
8. **Editing the harness or the baseline instead of the code.** `tests/attribution.rs` is the course's
   file and the baseline is the copy the gate reads: a metric that has been made to fit is a
   measurement that has stopped being one. `kiln reset lakelet/4.15-budget-regression` puts the
   harness back, and a red gate is the answer to a real change.
