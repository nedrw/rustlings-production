# A restricted query engine: parse, plan, and refuse what is not answerable

## WHY

There is a query interface, and there is a *language*. `lakeletq query --store … --from … --to …
--window … --agg …` is five flags and one shape: it answers exactly the question it can spell, and
every other question — "the mean of `cpu` on `h0` between these two times, per series, the three
noisiest" — has to be asked by a person with a shell loop. A store is queried by dashboards, alert
rules and other programs, and those are customers who cannot loop: they write one string and they
read one exit code. So the question gets a **grammar**, and the grammar is where a store decides
what it will not do.

That last part is the step. A query language that answers everything is a language that answers
questions it cannot afford: a `mean` over a year, an `OR` that no segment can be pruned by, a range
the retention pass has already deleted, a metric name nobody ever ingested. Each of those is cheap
to *accept* and expensive or impossible to answer, and each of them is a wrong answer waiting to
look right. `lakelet/4.11-query-engine` is where every one of them is a **typed refusal** with an
exit code, decided **before a store is opened** — and where the plan that would do the reading is
printed by `EXPLAIN` so a person can see what the query is about to cost. `lakelet/4.12`–`4.18`
then make that reading cheap; this step is what makes it *sayable*.

## TASK

The grammar is fixed and the page `docs/query.md` prints it; six things about it are decisions you
have to keep coherent rather than syntax you have to copy:

- **the time range is mandatory, and half-open.** `ts BETWEEN a AND b` is `[a, b)`: a record at `a`
  is in the answer, a record at `b` belongs to the next question. Every range in this store is
  half-open already (`Range`, `Partition`, a segment's stated span), and the *mandatory* half is
  the one that pays for itself: a telemetry query that reads all of time is an accident with a
  fleet behind it, and it is refused in a sentence rather than answered by a scan.
- **`FROM` names the metric, and `WHERE` names tag pairs, exactly.** A record's series is
  `metric,tag=value,…`; the ingest side accepts arbitrary bytes, so the query side may not assume
  well-formedness and may not fold case. `Series::of` is *total* — the metric is everything before
  the first comma, a pair with a key in front of its `=` is a tag, anything else is not a tag and
  never matches — and `Query::selects` is the one place `FROM` and `WHERE` mean something.
- **`AND` only.** Every predicate has to hold; `OR` is refused rather than implemented, because it
  is the one clause whose presence changes what a plan may prune (`lakelet/4.14-index-pruning`
  argues it in full).
- **`GROUP BY time(<window>)` is mandatory and the window is on the absolute grid.** A query that
  does not say how wide a bucket is has not said what it wants, and every bucket is
  `[n * width, (n + 1) * width)` counted from the Unix epoch — `lakelet/4.10-downsampling`'s
  alignment and not a second one, so a range that is not a whole number of windows long touches one
  window more than you may have counted.
- **`GROUP BY …, series` is what makes the answer per series.** Without it, one answer mixes every
  series the predicates select — right for the fleet, wrong for a host — and with it the answer is
  one bucket list per series, ordered by name, each line carrying the series it is about.
- **`LIMIT` bounds series, and needs `GROUP BY …, series`.** A limit on one mixed answer names
  nothing to bound; `LIMIT 0` is refused for the same reason an empty range is.

**The refusals are the other half of the grammar.** Each one is a variant that carries its own
class, and the class is the exit code `jobq/3.15-cli-contract` established: `2` when the call is
wrong (the text, an aggregate nobody has, an `OR`, a limit that bounds nothing, a range below the
store's floor), `3` when the thing asked about is not there (a metric this store has never held —
a typo must not look like a quiet fleet), `4` when the store could not answer, `1` when this
deployment is broken. Everything the caller got wrong is decided **before a store is opened**.

**What the course gives you, and what is yours.** The scaffold writes the contract, the spec
compiles against it, and the semantics are the step:

- `src/engine/query/series.rs`, `lex.rs`, `parse.rs`, `plan.rs`, `exec.rs` — the full public
  surface with the doc comments that state the rules above and `todo!()` bodies. Every body is
  yours, accessors included: the signatures are the interface, and the rules are the work.
- `src/engine/query/mod.rs` — the module tree, with the five declarations added inside its marker
  block.
- `src/cli/mod.rs` — **yours**, and this step adds the `--sql` half of it: the flag, the refusal
  with the form that was given beside it (the text *is* the whole question, so a flag that means
  the same thing cannot be given with it), the dispatch through `parse`/`Plan::of`/`execute`, the
  two answer shapes, and the `USAGE` text that names the form. `src/bin/lakeletq.rs` does not
  change.
- `src/engine/compaction/snapshot.rs` — **yours**, and it needs one method: `Snapshot::records()`
  reads every segment, and a query that prunes has to read only the ones the plan kept. Add
  `records_of(&SegmentInfo)` beside it, from the same three steps (read the file, check the
  manifest's count against what it holds, drop what is below the floor). Adding a method is not a
  regression; changing `records()`'s promise would be (`docs/handoff-m3.md` §1 rule 10).
- `docs/query.md` — **yours**: the page a reader of the refusal table opens. It has to print the
  grammar, the refusal table with each refusal's class, the keys `EXPLAIN` prints, and the pipeline
  the plan describes. `kiln check` fails the `links` gate until the page is written and every link
  in it resolves, so the placeholder links the scaffold leaves are the checklist.
- The rest of `src/engine/query/**` is `lakelet/4.10-downsampling`'s `downsample`, unchanged, and
  your executor calls it rather than reimplementing it: one `downsample` call per series, or one
  over the selected records. A second implementation of a `mean` is a dashboard that gets it wrong
  a year from now.

**The command line.** `lakeletq query` takes the question two ways and the two are mutually
exclusive; `--store` is a flag in both, because a query text names a metric and not a directory:

| call | stdout | code |
| --- | --- | --- |
| `query --store <dir> --from <ms> --to <ms> --window <d> --agg <name> [--series <s>]` | 4.10's lines | 0 |
| `query --store <dir> --sql 'SELECT mean(value) FROM cpu WHERE host = '"'"'a'"'"' AND ts BETWEEN <a> AND <b> GROUP BY time(5m), series LIMIT 3'` | `<series> <start> <count> <value>` per line | 0 |
| `query --store <dir> --sql 'EXPLAIN SELECT …'` | `key = value` lines | 0 |
| anything the caller got wrong (including a flag beside `--sql`, or a range that asks for more buckets than `MAX_WINDOWS`) | *empty* | 2 |
| a metric this store has never held | *empty* | 3 |
| a store that refused (a manifest or a segment this build cannot read) | *empty* | 4 |
| an environment that is broken | *empty* | 1 |

Without `GROUP BY …, series` the text shape is 4.10's three fields and the mixed answer, and with
it the series name is the first field. `--json` is a format in both: the flag form prints the array
it always printed, and the text form prints one object — the counts the query cost beside its
buckets. The flag form's output is byte-identical to what it was, and its spec is part of your
acceptance: this step adds a way to ask, not a new answer.

**What you see first.** `cargo test -p lakelet --test spec_query_engine` builds and then fails
eighteen times out of eighteen, each failure a `not yet implemented` panic from a `todo!()` — and
two of them are not panics at all: the binary is handed `--sql` by a caller who expects the text
form to exist, and `docs/query.md` is still a checklist. That is the normal shape.

## TRAP

1. **Pruning that is reported but not performed.** `Snapshot::records()` reads every segment; a
   query that says `segments_pruned = 6` and reads all eight anyway has a plan that lies about the
   one number a budget acts on. The spec overwrites a *pruned* segment's file with bytes of the
   same length: the plan still answers, the answer is unchanged, and a query that opened that file
   would exit `4` instead.
2. **`first_millis <= to` instead of `<`.** A segment whose earliest record stands at `to` holds
   nothing the question asked about, and opening it reads records that are then discarded — which
   the counts catch, because `segments_opened` is asserted against the manifest's spans.
3. **`last_millis > from` instead of `>=`.** The opposite end, and worse: the segment whose last
   record is exactly `from` is pruned, and the record at `from` — which the half-open rule says is
   *in* the answer — disappears. A query that silently drops a record the caller can see in the
   store is the failure a plan may not have.
4. **A second implementation of the window pass.** An executor that accumulates its own windows
   drifts from `lakelet/4.10-downsampling` within a release: the partial bucket at each end, the
   grid, and `mean = sum / count` are four decisions, and two copies of them are two answers. The
   spec compares the answer with `downsample` on the same records.
5. **Reading the store to decide whether a name exists.** The difference between a typo and a quiet
   fleet is worth a sentence, and it is decided from the segments the range touches: a range the
   store has no segment in is answered empty whatever `FROM` names, and the page says so rather than
   reading the whole store to be clever.
6. **`OR` accepted "for now".** It is not a syntax detail: a plan cannot rule a segment out by a
   predicate that only half of a disjunction matches, so the pruning story changes the day it is
   accepted. It is refused now, with 4.14 doing the arguing.
7. **A range below the floor answered with what is left.** `lakelet/4.10-downsampling` answers that
   way (and still does, its spec is your acceptance); a *grammar* refuses it, naming the floor,
   because a caller who wrote a range the store has forgotten wants to be told.
8. **An unknown metric answered as an empty answer.** That is the failure this class exists for: a
   dashboard that shows nothing and a fleet that reports nothing look identical, and only the store
   knows which it is.
9. **`LIMIT` that limits buckets.** It bounds how many *series* an answer covers; a limit on one
   mixed answer either does nothing or lies. The refusal is the grammar's, and `LIMIT 0` is one of
   them.
10. **`--json` as a second code path.** The JSON branch that "handles" a failure differently drifts
    within a month. The spec runs every failing call twice, with and without `--json`, and compares
    both the code and the diagnosis.
11. **The usage text left behind.** `USAGE` is the interface a script reads; a tool that answers
    `--sql` and does not say so sends every caller to the source. The spec asserts the text names
    the form.
12. **A `todo!()` left in any file.** `no-todo` runs over every target, and the five files this step
    adds are where the gate will look first.

## FURTHER

- **What a restricted dialect costs, and buys.** Prometheus's
  [PromQL](https://prometheus.io/docs/prometheus/latest/querying/basics/) and InfluxDB's
  [Flux](https://docs.influxdata.com/flux/v0/) are the two ends of this trade in the wild: one is a
  small language that composes range vectors, the other a full dataflow language with a standard
  library. `lakelet`'s grammar is deliberately nearer the first, and the reason is the one this step
  is about — a query a store cannot plan is a query a store cannot promise.
- **Plans, and printing them.** PostgreSQL's
  [`EXPLAIN`](https://www.postgresql.org/docs/current/sql-explain.html) documents both halves of
  what this step does: `EXPLAIN` (what it *would* do, and the only honest source of a plan) and
  `EXPLAIN ANALYZE` (what it did, and the counts that came out). The separation is why the plan here
  reports `segments_pruned` and the outcome reports `rows_scanned`.
- **Pruning by metadata, which is the whole point.** The
  [Parquet](https://parquet.apache.org/docs/file-format/) format's per-row-group statistics and
  [Iceberg](https://iceberg.apache.org/spec/)'s partition summaries are this step's `SegmentInfo`
  span at industrial scale, and `lakelet/4.14-index-pruning` is where a store starts keeping a
  second kind of summary (`blocks_pruned`, and a bloom filter over series names).
- **A grammar you can hand to someone else.** The [`sqlparser`](https://docs.rs/sqlparser) crate is
  the alternative this project declined (docs/m3-plan.md §3): a real SQL front end you do not write
  yourself. Reading its `Parser` for five minutes is the cheapest way to see what "restricted" saves
  you, and what it costs — no subqueries, no joins, no `OR` is a smaller language than SQL decides
  to be.
- **Why a typed refusal instead of a string.** `jobq/3.3-library-errors` argued the same rule for a
  library: a caller that branches on a message is a caller that breaks on a reword. Here the class
  is the exit code a script reads, and the sentence is only for the person who has to fix it.
