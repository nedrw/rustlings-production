# Cold data leaves the box: tiering behind a port, and the client that speaks S3

## RECALL

- `outbound/http-client@apply — relay/2.7`: one HTTP request you can reason about — a request line,
  headers, a body, and an answer whose body ends where its `content-length` says rather than at the
  close of a connection. That step's client is a *delivery* client: three deadlines, keep-alive, a
  redirect policy, and one classification (`success`, `retryable`, `permanent`) that the layer above
  acts on. What this step keeps is the shoe: HTTP/1.1 over `TcpStream`, written rather than
  delegated, because a dependency you did not write is a dependency you cannot read when a `403`
  arrives. What it adds is everything 2.7 did not need — 2.7 sends an unsigned POST to a stranger's
  webhook, and this step's client talks to a service that checks **who** is asking.
- `store/retention@apply — lakelet/4.9`: the pass that removes whole segments, and the vocabulary
  this step's policy is a sibling of rather than a second idea. A policy is a value, a cutoff is
  `now - window`, the comparison is half-open (`last < cutoff`, so a record *on* the boundary
  stays), a segment whose age nobody wrote down is never acted on, and a pass is applied at a `now`
  a caller hands in. Every one of those sentences is this step's too, with one word changed:
  retention removes, tiering *moves*.
- `sec/hmac-signing@apply — relay/2.11`: a keyed MAC over the exact bytes that leave the socket,
  computed over a tuple that includes what the request is *for*, with the result written into a
  header. The failure it argued against is this step's failure exactly: signing a re-serialisation
  of the payload instead of the payload is how you produce a signature nobody can verify.
- `store/compaction@design — lakelet/4.8` and `ops/backup-restore@apply — lakelet/4.19`: the two
  orderings this step stands on. 4.8 wrote the manifest after the bytes it names; 4.19 wrote a
  file's bytes and *then* the manifest entry that says they are complete, which is what makes a
  copy that was interrupted tell the truth about itself. This step's ordering is the third of the
  family, and it is the one that is judged by a case rather than by a paragraph.

## DELTA

Every step of this phase has measured the box: the write path counts its calls, a segment's bytes
are pinned, a run is attributed to the phase that paid, a soak watches five live counters, and
`lakelet/4.20-capacity-model` puts a price on all of it. This step is the first one that does
something about the bill, and the thing it does is the oldest trick in storage: **most of what a
telemetry store holds is never read again, and it does not have to be on the expensive machine**.
The segments that are cold go into a tier — a bucket, or a directory — and come back when something
asks for them.

Three decisions make that safe, and none of them is obvious:

- **the port is blobs, not segments.** `Objects` is `put`, `get`, `delete` and a listing that pages;
  nothing in it knows what a segment is. That is what lets the rule and the two passes be written
  once and run against two implementations — a directory, and an S3-shaped endpoint over the client
  this step also writes — and it is what `conformance.toml` at the project's root is for: the step's
  own suite is run once per backend, with `KILN_BACKEND` set to the name, and a step whose tier only
  works against a directory is a step that has not been tested;
- **the object lands first, the local file goes second.** A crash in the window leaves the segment
  in *both* places, and the two are the same bytes because the `put` is what put them there — so the
  store is readable with the tier and without it. The other order has a window in which the manifest
  names a segment whose bytes are in neither place, and that is not a cold store, it is a lost one.
  That is the ordering 4.19 argued for a copy and 4.8 for a merge, applied to the one operation that
  moves something off the box;
- **the tier keeps no manifest of its own.** What is in the tier is answered by asking it — `list`,
  paged — and nothing is written durably. A map from ordinal to key would be a second file that can
  disagree with the tier, and a store that trusted it would refuse to open for a reason nobody could
  see. The price is stated rather than hidden: a tier that lost its listing is a tier that holds
  nothing, which is a truth a caller can act on.

The other half of the step is `outbound/http-client` at **design** depth, and the difference between
apply and design is what the client is answerable for. 2.7's client sent bytes and classified an
answer. This one is asked for a request that is *signed*, and signing is where an HTTP client stops
being plumbing:

- **the canonical request is built from the request that is sent.** `http::Request` keeps the
  method, the path, the query as pairs, the headers and the body, renders the wire bytes from them,
  and computes the canonical request from the same fields. There is no second assembly of the same
  request anywhere, which is the only way "the string that is signed cannot disagree with the bytes
  that are sent" is a property instead of a hope — and a disagreement is a `403` whose message says
  the signature did not match and nothing about which of the fifteen lines differed;
- **the instant is a value.** `x-amz-date`, the credential scope's date stamp and the signature all
  come from the config a caller builds. Nothing in the tier reads a clock, which is what makes a
  pinned signature vector a test rather than a flake;
- **the key is the idempotency key.** A segment's object name is a function of its identity, so a
  `put` that was sent twice wrote one object — which is the argument that makes a retry safe, and it
  is a completely different argument from `relay/2.8-retry-budget`'s, where a retry needs a budget
  because a delivered webhook is delivered;
- **a status class is a value, and a retry is a count.** `2xx` answered, `404` absent (absence is a
  value: `get` answers `None`), every other `4xx` refused without a second attempt, `5xx` and
  transport failures retryable `ATTEMPTS` times. No deadline, no backoff, no jitter: a retry policy
  that reads a clock is a policy two machines disagree about, and this step's whole subject is
  bytes that are the same on both.

Three things are deliberately **not** here, and each is a decision rather than a gap:

- **the store's manifest does not change.** `lakelet/4.9-retention` pinned its layout and its version
  byte, and a step that bumped it to describe where a segment's bytes are would break an earlier
  step's spec and a learner's store. So the tier holds segments *beside* a manifest that names them,
  and hydration writes a segment's bytes back into the file the manifest already names;
- **the log and the sidecar indexes are not tiered.** The log is the file a crash's readability is
  defined by (4.4), and the sidecar is derived state that can be built again (4.14). What the tier
  holds is the one thing a store cannot rebuild: the segments;
- **nothing decides *when* a pass runs.** `sweep` and `hydrate` are one pass each, for a task that
  owns the schedule — the same shape `Segments::compact` and `Segments::expire` have.

What that leaves is a statement worth making out loud, because this page is where an operator
finds it — and it is the one part of this step that is a *consequence* rather than a feature:

- **a `sweep` of a live store is safe, and `hydrate` is a live-store facility in this build.** The
  process that owns the store holds its manifest in memory, so it can sweep, hydrate the segment it
  is about to read, and go on answering. Both passes take the store, and neither of them needs
  anything the store does not already have;
- **a store whose process has stopped with cold segments cannot be opened at all.** `Segments::open`
  refuses a segment the manifest names and the directory does not hold, and that refusal is the
  honest answer — a store that answered from a manifest naming files nobody has would answer a hole.
  And because `Segments::open` is the *only* door to a store (there is no read-only way to load a
  manifest in this build: `compaction::Manifest`'s decoder is private, and the open itself writes —
  it deletes orphans and the half-written `*.pending`, and syncs the directory), there is also
  nothing left to hand `hydrate`. **The way back is by hand**: the keys this step derives *are* the
  store's own paths, so putting such a store together again is one copy per segment, from the tier
  into `segments/<ordinal>.lks`. That is a `sync` rather than a translation, and it is safe for the
  same reason a `put` is — the open checks every file it finds against the length the manifest
  states, so a file that is not the segment is still refused rather than read;
- **the door this build does not have is the next step's work, and this page says so rather than
  papering over it.** A reader that fetched a cold segment *on demand* — inside the store's own open,
  or inside the read path — is what a deployment actually wants, and writing it means giving the
  engine a read-only way to load a manifest plus a hydrate that runs before the length check rather
  than after an open. It would change `lakelet/4.8-compaction`'s open, which `lakelet/4.19-backup-restore`'s
  spec is already pinned against, so it is deliberately not this step: `docs/handoff-m3.md` §5
  records the gap, and the case `a_stopped_store_whose_segments_are_cold_is_not_openable_at_all` is
  that gap written down as a fact about this build.

## TASK

The scaffold created four engine files, two course-owned test files, and one declaration:

- `src/engine/tier/mod.rs` — the port, the rule and the two passes, with `todo!()` bodies and the
  whole surface documented;
- `src/engine/tier/filesystem.rs` — a directory as a tier;
- `src/engine/tier/http.rs` — the client;
- `src/engine/tier/s3.rs` — the S3 shape (SigV4 over `http`);
- `tests/s3_stub.rs` — **complete**: an in-process S3-shaped endpoint, which the spec declares as a
  module;
- `tests/support/tier.rs` — **complete**: the one factory both backends are run through;
- `conformance.toml` — the declaration the gate reads, with **one** backend in it;
- and four insertions inside marker blocks: `pub mod tier;` in `src/engine/mod.rs`, `pub mod tier;`
  in `tests/support/mod.rs`, `sha2 = "0.10"` and `hmac = "0.12"` in `Cargo.toml`.

**`src/engine/tier/mod.rs` is the contract.** `Objects` is the port, and it says the four things a
tier can be asked: `put` (idempotent — the same key and the same bytes leave the same object), `get`
(absence is `None`, not an error), `delete` (idempotent, because a pass that deletes what is already
gone has reached the state it asked for) and `list(prefix, cursor)`, which answers **one page**. A
`Cursor` is a *key* and not an offset: an offset counts what a prefix held when the walk began, so a
key that arrives in the middle of a walk shifts every page after it. `listing` is the loop that
walks a port's pages, and it lives here rather than in a caller for two reasons: "the endpoint said
there is more" is a fact only the loop can act on, and an endpoint that answers the same cursor
twice is not making progress — a loop that took its word for it would ask forever, so it is a
transport refusal.

`Policy` is `cold_after_millis` and [`Policy::DEFAULT`] is a week, and the rule is 4.9's with one
word changed: **a segment is cold exactly when the last timestamp the manifest states for it is
below `now - cold_after_millis`**. The *segment's own* range decides it rather than the store's
floor, and the reason is what a segment is — one file, moved as one object, and the newest record in
it decides whether anybody reads that file again. A segment whose range nobody stated is never cold:
a pass does not move bytes on a number nobody wrote down.

`sweep(store, objects, policy, now)` carries the ordering out: for every segment the manifest names
that the policy calls cold, read the file, `put` the object, and only then remove the local file.
`hydrate(store, objects)` is the other half: for every segment whose local file is missing **or is
not the length the manifest states**, fetch the object, check its length against the manifest's
number *before* writing anything, and write it back. A complete store asks the tier nothing at all —
no listing, no request — which is what makes a hydrate cheap enough to run before every read. Both
answer a `Report`, and every counter in it is what the *manifest* says rather than what a directory
happens to hold.

**`src/engine/tier/filesystem.rs` is the boring implementation, and it exists on purpose.** A
directory as an object store is not a deployment — it is on the same box as the store, in the same
failure domain — and that is exactly what makes it the implementation that shows the port is not
shaped around S3. Three things in it are decisions: a key that is not a path below the root is
refused (a port whose keys could walk out of its root can be told to write anywhere); `put` waits for
the device *and* for the directory entry that names the object, because the object is what a sweep
removes a local file because of; and the listing is one prefix in key order, which is the order an
S3-shaped endpoint answers in — that is what lets one suite judge both.

**`src/engine/tier/http.rs` is where the client is at design depth.** The request and the answer are
values, `Class` is the four things a caller has to do something about, `ATTEMPTS` is a count, and
`Request::canonical_request` is built from the request's own fields — including `Request::payload_hash`,
which is what the `x-amz-content-sha256` header is set from *and* what the signature is computed
over, so the two cannot drift. `Client` owns the tokio runtime it blocks on (the port is
synchronous, and a port that had to be `async` would be an engine that cannot run in a test), opens
one connection per attempt, and reads a body to the length it promised. It does **not** do `https`,
chunked answers, or connection reuse, and it says so.

**`src/engine/tier/s3.rs` is the S3 shape: SigV4.** The canonical request, the signed-header list
(derived from the request's own headers — a list a caller maintains by hand stops matching the
request the day somebody adds a header), the credential scope, the string to sign, the four-MAC
signing key, and the `authorization` header. `PutObject`, `GetObject`, `DeleteObject` and
`ListObjectsV2`; a `404` on a `get` is `None`; a `403` is refused without a second attempt and its
message says the signature was refused and quotes the scope, because that is what an operator can
act on.

**`conformance.toml` is the step's own deliverable, and the scaffold gave you one backend.** Add the
second: `backends = ["local", "s3"]`, with a word next to it saying what the second entry means. The
`conformance@2` gate runs `cargo test -p lakelet --test spec_tiering` once per entry, with
`KILN_BACKEND` set to the name, and requires every run to pass — a step that lists one backend has
not done the work, and `["local", "local"]` is one implementation written twice.

Do not touch `tests/s3_stub.rs` or `tests/support/tier.rs`: they are the course's files, they are
complete, and the fixture is the only place `KILN_BACKEND` is read. The suite is one suite run twice
— do not write a backend-specific test file, and do not let the `local` cases skip work the `s3`
ones do. A gate would still pass; the suite would stop being a conformance suite, which is the thing
it is.
One detail of the fixture is worth knowing before you read the results, because it says what is
being judged where: `KILN_BACKEND` decides which implementation *the port cases* are run **through**
— a directory, or the endpoint — and the cases about the client (a signature, a payload hash, a
retry, a request's shape, a page token) build an S3-shaped port on **every** run, because what they
are about is the same question on both. The endpoint is in-process and costs nothing, and leaving
that half out of one run would leave it out of the mutation walk, which runs this suite once.

## TRAP

1. **Deleting the local file before the object is in the tier.** This is the one mistake this step
   is shaped around, and it is invisible until a machine dies at the wrong instruction: the window
   between the two writes is either "both places" or "neither place", and only one of those is a
   store you can read. A test cannot kill a machine at a chosen instruction, which is why the case
   uses a tier whose `put` *lands and does not answer* — the realistic version of the same state.
2. **Trusting the length of a page.** An endpoint may answer fewer keys than the `max-keys` it was
   asked for, and this course's stub does it on purpose: the client asks for a thousand, the endpoint
   answers two, and `IsTruncated` is the only field that says there is more. A client that stopped at
   the end of the first page would report a third of the tier as the whole of it — and every case
   about a sweep would pass, because a sweep writes and never reads.
3. **A cursor that is an offset.** An offset counts what the prefix held when the walk began, so a
   key that arrived in the middle of a walk makes the next page skip one and a key that left makes
   it repeat one. A cursor is a key: a position that means the same thing whatever else happened
   meanwhile — and the tier is exactly the thing that changes while somebody walks it.
4. **Hydrating before checking the length.** The tier's copy of a segment is a copy of something
   that has a stated length, and a copy that is not that length is not the segment. Writing it first
   and checking afterwards leaves a file the store's own open then refuses — for a reason nobody can
   trace to the tier, which is the worst kind of refusal to debug. The check comes before the write,
   and a file that was already wrong is removed rather than left.
5. **Deciding cold from the wrong number.** The store's floor is what it has *forgotten*, and the
   first record of a segment says nothing about whether the file will be read again: a segment is
   cold when its **last** record is old. Using the floor would tier segments that are still being
   queried, and using the first record would tier a segment whose newest record is five minutes old.
6. **Signing a request you did not send.** The failure has a name in every review of every SigV4
   implementation: the canonical request is assembled from values, then the request is written from
   the same values in a slightly different order, and the two agree until somebody adds a header or
   forgets to encode a `/`. The only structural answer is the one this module takes: one value, two
   renderings, and the signature computed from the value.
7. **A clock in the signature.** `x-amz-date` from `SystemTime::now()` makes every signature
   different and the pinned vector impossible; worse, it makes a `403` depend on how long a request
   waited, which is a bug that appears under load and never on a developer's machine. The instant is
   a value in the config, in this step, for the same reason 4.3 made the fsync policy one.
8. **Retrying a `4xx`.** A `403` is an answer: a second attempt gets the same one, and every attempt
   spent on it is an attempt the next request needs. The line between "the endpoint could not answer"
   (`5xx`, a socket that died, a timeout) and "the endpoint answered, and the answer is no" is the
   whole of `Class`, and it is the difference between a tier that is down and a tier that is
   misconfigured.
9. **A retry bound that is a deadline, or a bound that is not there.** This step's client retries a
   request `ATTEMPTS` times and reads no clock while doing it: no backoff, no jitter, no deadline. A
   deadline is a policy about *time*, and a deployment that wants one wraps the call site; a retry
   loop with no bound at all is a pass that never ends, and a pass that never ends holds the store's
   schedule. `relay/2.8-retry-budget` is where a budget with a clock in it belongs, for a service
   that talks to somebody else's server many times a minute.
10. **Expecting a swept store to open, and having nothing left to hydrate it with.** `Segments::open`
    refuses a segment the manifest names and the directory does not hold, and it should: the
    alternative is answering from a manifest naming files nobody has. But that same refusal is the
    door to every pass — `hydrate` takes a store, and there is no read-only way to load a manifest —
    so a store whose process stopped while its segments were cold has no way back except by hand. An
    operator who sweeps, stops the writer, and then starts a build of that store gets a refusal
    naming a file: a true statement about the store, and a deployment decision about who may sweep.
    The keys are the store's paths, so the repair is one copy per segment, and the open checks what
    was copied.
11. **Writing something durable to remember what is cold.** A map from ordinal to key beside the
    store is a second file that can disagree with the tier, and the day it does, the store either
    refuses to open for a reason nobody can see or opens and answers a hole. Nothing here is written
    durably; `list` is the authority, and losing it is a truth a caller can act on.
12. **Filling `conformance.toml` with one backend, or with two copies of one.** `conformance@2` is a
    failure and not a block when the declaration is too small, and `["local", "local"]` is one
    implementation written twice. The second entry is the work.
