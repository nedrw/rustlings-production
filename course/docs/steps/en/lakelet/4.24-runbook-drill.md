# The runbook is the procedure, and the drill is the proof

## RECALL

- `ops/runbook-drill@design — jobq/3.27`: **the rung this step is one past, and the shape it keeps.**
  There the page was parsed into *stages as data* (`src/engine/runbook.rs`), the drill walked the
  stages the page named, and the reader reported what a stage owed rather than panicking on it —
  `without(stage, part)` built a mutated page and the gaps were the evidence. This step keeps every
  one of those decisions and changes what does the walking: the instrument is the course's own file
  and it runs the commands **against a live store**, so the page is not compared with a script that
  describes it but with the deployment the procedure is for.
- `ops/runbook-drill@apply — mailer/1.22`: **the first drill and the first page.** One failure
  replayed end to end, a report that says whether anything was lost, and the promise checkable by a
  command; four sections of "what this tool does" are not a runbook, and the five questions an
  incident asks (Symptoms, Signals, Steps, Verification, Escalation) are the ones this page answers.
  That step wrote the page *from* the drill so the two could not drift; here the drift is what the
  instrument catches.
- `obs/metrics-slo@design — jobq/3.17`: **the number behind each stage.** A signal is a rule —
  signal, threshold, window, drill — and a page that watches a number nobody publishes is a page
  about an imagined deployment. What this step adds is the other direction: the SLO page names the
  stage that protects each number, and the runbook names the numbers its stages read.
- `ops/backup-restore@apply — lakelet/4.19`, `perf/soak@apply — lakelet/4.17`,
  `obs/cardinality-cost@apply — lakelet/4.18`, `ops/capacity-cost@design — lakelet/4.20`,
  `store/tiering@apply — lakelet/4.21` and `sec/secrets-management@design — lakelet/4.23` are not in
  `requires` as separate slots, but every stage of this page is one of them: the copy and the
  restore, the soak's counters, the cap and its ledger, the model's constants, the sweep and the way
  back, and the rotation window. This step is where they become a procedure — and the one place the
  tree disagrees with the obvious page is 4.21: **no command sweeps or hydrates**, so stage 7 says
  so, and names the way back the engine actually has.

## DELTA

Twenty-three steps produced acts, and each one shipped the page that explains its own act:
`docs/dr-drill.md` the copy and the restore, `docs/soak.md` the counters a long run is read by,
`docs/cardinality.md` the bill, `docs/capacity.md` the model, `docs/rotation.md` the ring,
`docs/perf.md` and `docs/format.md` the shape of the work. **Not one of them is the procedure.** Four
pages of *what this tool does* are not a runbook, and `jobq/3.27` proved that saying so is not
enough: it parsed the page into stages and walked them with a script, which is exactly one rung
below what an operator needs, because a script that *describes* the procedure cannot tell you
whether the commands on the page are commands this deployment has.

So this step changes who does the walking. The instrument is `tests/runbook_harness.rs`, the
course's own file, and it does three things no earlier page could:

- **it parses the page into stages, and it runs the commands.** `$LAKELET_STORE` is a store it built
  through the real write path, `$LAKELET_ADDR` is a daemon it started on it, and a stage whose
  command is not one of this deployment's programs is a **finding** — with the stage's number, the
  part and one sentence — rather than a crash or a shrug. A runbook naming `kubectl rollout restart`
  is a runbook for another deployment, and this is the instrument that says so out loud;
- **a stage's state is a check, not a sentence.** The page names one of the instrument's checks
  (`settings-print`, `copy-holds-the-store`, `restore-holds-the-records`, `drill-agrees`,
  `counters-flat`, `bill-adds-up`, `cold-span-answered`, `window-respected`), and the check is made
  *after* the command ran, against the store: the copy's own manifest is opened and every entry's
  length and crc32 are compared, the restored ledger is held against the store's, the load's frames
  are held against the daemon's own counters, the table is held against the log's records and bytes.
  "It looked fine" is what a stage says when nobody can check it;
- **the page carries the report.** The block in `## Verification` is the instrument's own output, the
  spec re-runs the instrument and compares it line for line (`lakelet/4.19`'s rule for its own page),
  and nothing in it is a wall clock or a path — so a page full of verdicts stays true, or goes red
  naming the stage that moved.

The two pages are one document read from both ends. `docs/runbook.md` is the procedure — eight
stages, each with the command, the signal to watch, the state that proves it, the rollback and who is
told — and `docs/slo.md` is the number the procedure protects, with the stage that protects each one
named beside it and the error budget in the units this deployment's failures are actually paid in:
**refusals counted, records lost, minutes to restore**. A number nobody's stage protects, and a stage
that protects nothing, are both failures, and the spec checks the two directions.

What this step deliberately does **not** do: it adds no command to the deployment (the acts are
4.6–4.23's, and 4.21's are not commands at all), it grades nothing ("the page is good" is not a
property a machine has), and it promises no wall clock (RTO is measured on a named machine and
quoted, never judged).

## TASK

The scaffold put three files in place and wired none of them: `tests/runbook_harness.rs` is
**complete** — it is the instrument, not yours, and `kiln reset lakelet/4.24-runbook-drill` puts it
back if you edit it — while `docs/runbook.md` and `docs/slo.md` are stubs with the headings and the
stage list the pages have. Both pages are yours, and this is the step where two pages are the whole
deliverable.

**Read the harness's module docs before you write a line of either page.** They are the contract: the
`### <number>. <title>` heading a stage is, the five parts ([`PARTS`], and which of them is a fenced
`sh` block), the four answers a page may give for a rollback (a command, `none`, `nothing was taken`
— and which stages may say which), the programs ([`PROGRAMS`]) a command may start with and the
grammar behind their verbs and flags, the variables ([`VARS`]) the instrument points at the world it
built, and the one numeral the page's opening has to get right.

### `docs/runbook.md` — the procedure

Eight stages are already named, in the order an operator takes them. Each one needs its five parts,
and the order is not decoration: a copy before the load, a restore into a directory that is not the
store, a rehearsal, and the arithmetic before the act that cannot be undone.

1. **finish the stages that are there.** Every command is one of `lakeletd`, `lakeletq` or
   `lakelet-load` with the flags that program declares — `lakeletq --help`, `lakeletd --help` and
   `lakelet-load --help` are the grammar, and the harness reads the same words out of the sources;
2. **name the signal you would actually watch**, in backticks, and make it one this project reports:
   the fields of the daemon's log lines (`queue drained`, `series ledger`, `store recovered`, `store
   write cost`), a number a page of this project states, or a counter a harness prints. The
   instrument holds every name to the project's own files, so a plausible-sounding counter that
   nothing prints is a finding;
3. **pick the state from the list**, and pick the one that belongs to the act: `bill-adds-up` beside
   `lakeletq inspect series`, `counters-flat` beside a load run. A check beside the wrong act proves
   nothing about the stage, and the reader says so;
4. **write the rollback column as the column it is.** Stage 5 puts records on the store and its way
   back is the copy stage 2 took; stage 8 writes a retirement and says `none`, because nothing
   unsays one; everything else reads, and says `nothing was taken`. The instrument judges that
   direction: an act that takes something cannot claim it took nothing;
5. **quote the report.** Run `cargo test -p lakelet --test runbook_harness -- --nocapture` and put
   the block it prints in `## Verification` — the spec re-runs it and compares it line for line, so a
   hand-edited number is a red case rather than a stale page.

### `docs/slo.md` — the numbers the procedure protects

- **one row per number**, with where it comes from (a file of this project, or the course's own
  baseline beside it), the runbook stage that protects it, and what breaks it. The spec holds the row
  to the stage: a number the stage does not name is a row pointing at the wrong stage;
- **the error budget in this course's units** — refusals counted, records lost, minutes to restore —
  and spent against the numbers the table already carries: a budget that mentions a number the page
  does not name is a promise nobody agreed to;
- **what happens when a budget is spent**, in acts rather than sentiments: which stage you run, which
  number you change, and what you refuse to change (raising a cap to stop the refusals is the one
  change that makes a number look better while the store keeps paying for it).

## DONE WHEN

- `cargo test -p lakelet --test runbook_harness -- --nocapture` in `app/lakelet` prints the report,
  and every line of it says `verdict=holds`
- `cargo test -p lakelet --test spec_runbook` — the fifteen cases pass: the fourteen below and the
  instrument's own test, which the spec reaches through `#[path]`
- `kiln run lakelet/4.24-runbook-drill` — the spec passes on your pages, and **fails on the stub**
  (`kiln selftest lakelet/4.24-runbook-drill --track lakelet` is that pair, run for you)
- `kiln check lakelet/4.24-runbook-drill` — the nine must gates are green: `spec-integrity`, `caps`,
  `i18n`, `fmt`, `clippy@4`, `no-todo`, `docs:public`, `exit-code` and `links`. There is no `sim`,
  `soak` or `mutants` gate on this step: the instrument *is* the evidence, and the spec is what runs
  it
- `lakeletq inspect series --store <your store>` by hand, once, on a store you built — the second
  command `## Verification` names, because a page is a claim about a box somebody is sitting at
- `grep -c '^### [0-9]' docs/runbook.md` is the number of stages the report says it ran, and the
  numeral in the page's opening line is the same number
- `kiln run lakelet/4.23-secret-rotation` — the ring this page's last stage retires a key on still
  answers the same way, byte for byte

### What the spec judges

Fourteen cases, one claim each:

| the case | the claim |
| --- | --- |
| `the_page_is_a_procedure_and_every_stage_names_its_parts` | no placeholder is left, the opening's count is the count of stages, and every stage answers all five parts |
| `every_command_the_page_names_is_one_of_this_deployments` | every command is a program this deployment ships, its verb is one the program declares and every flag is one it takes — a page naming `lakeletq tier sweep` is a finding, not a crash |
| `every_signal_the_page_names_is_one_this_project_reports` | every name a signal puts in backticks is a name some source or page of this project writes down |
| `every_rollback_is_a_command_or_says_why_it_cannot_be` | a command, `none`, or `nothing was taken` — and a stage that writes the store may not say the last |
| `the_instrument_runs_every_stage_of_the_page_and_nothing_is_owed` | the instrument runs every stage's command against a store it builds and every stage's check holds |
| `a_stage_that_does_not_name_one_of_its_parts_is_a_finding` | one case per part, on pages the spec writes: a reader that waves a page through fails here |
| `a_command_that_exits_non_zero_names_the_stage_that_failed` | the stage, what it printed, and `verdict=failed` — a drill that swallows a broken command is decoration |
| `the_page_carries_the_report_the_instrument_prints` | the block in `## Verification` is the instrument's output, re-run and compared line for line |
| `the_slo_page_names_each_number_and_where_it_comes_from` | every row names a number, and a file of this project each number comes from |
| `the_two_pages_cross_reference_each_other` | every number names its stage and every stage is named by a number, in both directions |
| `the_error_budget_is_counted_in_the_units_this_course_uses` | refusals, records lost, minutes to restore — and no number the table does not carry |
| `both_pages_link_to_each_other_and_their_targets_exist` | the two pages link to each other, and every relative target resolves in the project |
| `the_instrument_reads_no_wall_clock_and_runs_no_cargo` | no wall clock reaches the report, the instrument runs the project's own binaries rather than shelling out to `cargo`, and two drills of one page print the same bytes |
| `the_report_says_how_many_stages_ran_and_which_ones_roll_back` | the report's summary line states the counts, and every stage that rolls back with a command says so on its own line |

## TRAP

1. **A page that is prose with numbers in front of it.** A stage that says "look at the store" and
   never names a command, a number to watch, or what a good answer looks like is the shape of a
   runbook that is read once and abandoned. The instrument reports the stage and the part, and the
   spec's gap cases are the same complaint applied to pages the *spec* writes — so a reader that got
   lenient fails there even while the page passes.
2. **A signal nobody publishes.** `series_reported_total`, `queue_pressure`, `replication_lag`: they
   read like the numbers a telemetry store would have, and this deployment has none of them. The
   harness holds every backticked name against the project's own sources and pages, so the failure is
   a finding naming the stage and the name rather than an operator discovering it at three in the
   morning.
3. **A rollback column that says "try again".** A refused act wrote nothing, so the repair is the
   call; a stage that retries a call which will always be refused is a stage that teaches a responder
   the wrong reflex. And the columns are judged in both directions: a read may not invent a way back,
   and the act that writes records into the store may not claim it took nothing.
4. **A retirement nobody can undo, written as if it could be.** Stage 8 is the one act on this page
   that cannot be unsaid: a retirement is written once, the last token the key signed is already out
   there, and the ring has no command that reopens a key. Its rollback column says `none`, and saying
   that *before* the instant is the whole of the arithmetic the stage is about.
5. **The plausible command.** `lakeletq tier sweep --store …` is the command this page *wants*, and
   it does not exist: `sweep` and `hydrate` are the engine's, nothing under `src/cli` or `src/bin`
   calls them, and a runbook that names a command nobody has is a procedure about an imagined
   deployment. Stage 7 says what this deployment really offers — a read of the span that left, and
   `hydrate` before anything reads the store — which is what an operator can act on today.
6. **Shelling out from the instrument.** A harness that runs `cargo test` inside a test deadlocks on
   the target directory's lock: the suite holds it, the child waits for it, and the step hangs
   instead of failing. The instrument runs the project's own binaries (`CARGO_BIN_EXE_…`) and the
   spec reads its source to hold it to that — the same reason `lakelet/4.19-backup-restore`'s cases
   run `lakeletq` rather than the library behind it.
7. **A wall clock in the report.** A block a page quotes is compared line for line, so a duration in
   it makes the page's own numbers depend on the machine and the moment. RTO belongs in the prose
   with the machine named (that is what `docs/dr-drill.md` does with its 1.02 s), and the instrument
   reads no clock at all: two drills of one page print the same bytes.
8. **An SLO page that is a second runbook.** The SLO page is a table of numbers with a stage beside
   each one and a budget underneath, not a second procedure. A number the runbook's stages do not
   name is a row pointing at the wrong stage, and the spec checks both directions because a page
   nobody's procedure protects is a promise rather than an SLO.
9. **Writing the page from the implementation.** A runbook written by reading `src/` lists settings
   and code paths, which is exactly what the responder cannot use. Write it from the alert that would
   page you — "ingest is being refused", "the disk is filling", "a client says its token was
   refused" — and then check that each of those has a stage and a number behind it.
