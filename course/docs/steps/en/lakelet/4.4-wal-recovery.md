# A log is a prefix: checksummed records, torn writes, and the boundary that was acknowledged

## RECALL

- `store/wal-recovery@aware — lakelet/4.3-write-path-adr`: the write path decides when an append waits
  for the device, and `Spool::durable_offset` is the boundary that decision promises — the last byte a
  *machine* death cannot take. `docs/crash-points.md` is the map of what each failure leaves on the
  device, and its point 3, the torn write, is this step's input: a record nobody finished.
- `time/clock-injection@apply — jobq/3.8-clock-injection`: a decision that depends on time is handed
  the clock it may read. This step's concurrent half is a *simulation*, and there the clock is the
  simulator's: the store's flusher in `tests/sim_wal.rs` sleeps on simulated time because a flush
  that happened only because the author's machine was loaded is exactly the nondeterminism
  `slow:sim@3` exists to catch.
- `err/typed-errors@design — jobq/3.3-library-errors`: a failure names the layer that refused it, and
  a caller decides from the variant rather than from a string. Here that is the difference between a
  *refusal* (`Error::Protocol`: these bytes are not this store's log) and a *recovery* (a torn tail,
  which is not an error at all — it is the input this step exists for).

## DELTA

`4.3` decided how long an acknowledged record may sit in the page cache, and wrote the number down.
It never had to *read* the log back, so three things it promised were still only promises:

- **`durable_offset` was a counter, not a contract.** Nothing measured the bytes on the device
  against it. This step makes it enforceable: a store that has been killed is opened again, the log
  is replayed, and what a machine death left is compared with what the write path said it would
  leave. The boundary is now something a replay is judged against, once per start, on every start.
- **"stop accepting, flush, log `draining`" was false.** `bin/lakeletd.rs` and point 6 of
  `docs/crash-points.md` both described a stop path that flushes, and nothing in this project called
  `sync` outside an append. This step makes the sentence true instead of correcting it: the accept
  loop returns, the store is flushed whatever the policy is, and the daemon prints the two numbers
  that make the claim checkable (`written`, `durable` — a clean stop has them equal). Point 6 of the
  crash-point list is updated to match, because a page that still said "a clean stop does not flush
  by itself" would now be the only wrong document in the repository.
- **A restart said nothing about what it cost.** Recovery happens when a store is opened, and the
  operator's cheapest view of a crash is the line that says what opening had to discard. The daemon
  logs `store recovered records=… bytes=… discarded=…` at startup: one line per start, fields a
  collector can read and no prose, in the shape `obs/structured-logs@design` fixed
  (`bin/lakeletd.rs` and the connection counters already read that way). The store exposes the fact
  (`Spool::recovered`); the daemon is the layer that decides to say it out loud — the engine has no
  log format and no level, and giving it one would be the boundary `lakelet/4.1-ingest-protocol`
  drew.

What is deliberately **not** here, so a reader knows where the next step starts:

- **one record per append, one file per store.** Batching is `lakelet/4.5-batch-writes`, and it is
  what a per-record flush cannot afford and an interval makes possible;
- **one log, not many.** Segments, compaction and retention are `4.7` to `4.9`; when the store grows
  a second file, "which file does recovery start with" becomes the question this step leaves open;
- **no repair.** Recovery reads what the device has and cuts the tail. It never rewrites a record,
  never invents one, and never guesses at a length field that failed its seal.

## TASK

Four properties make up this step. Everything else is packaging, and the packaging is worth a
paragraph of its own because it is where the course stops and you start.

- **A record declares itself.** `segment` owns the bytes: a header that says which log this is (four
  bytes of magic and a version), and then records of `[length][payload][seal]`, each one its own
  length and its own checksum. The **seal covers the length as well as the payload**, and the reason
  is in `src/engine/wal/checksum.rs`: this reader finds where a record *ends* from the bytes in front
  of it, on a file a crash may have cut in the middle of one, so the length is part of what has to be
  proved. A seal over the payload alone would let a damaged length field move the end of a record
  somewhere the seal still covered — recovery would hand back a prefix of somebody else's bytes as a
  record. (`crate::protocol::frame` seals its payload alone and is right to: a stream's reader is
  handed a length before it needs the payload, and bytes that are not a frame end the connection.)
  And a file that is **not** this log is a typed `Error::Protocol`, never a store that silently holds
  no records: without the header, `hi!` and a log whose first write was cut after two bytes are the
  same bytes, and recovery would have to guess which of the two it was looking at.
- **Replay stops at the first thing it cannot prove.** Given a store directory, `replay::recover`
  answers the records whose seals verified, how many bytes of the log that is, how many bytes it threw
  away, and *why* it stopped (`Stop`: `End`, `Torn`, `Corrupt`). It never skips a bad record to find a
  later good one, never returns a record it did not verify, and never panics. Write the argument for
  that in `src/engine/wal/replay.rs` next to the code: a log is a prefix by construction, so "the
  record after a bad one" is an offset the bad record's length described — a conclusion drawn from
  bytes that have just been shown to be untrustworthy; a gap is worse than a short log, because a
  store that returns records 1–10, drops 11 and returns 12 has told every reader the series was
  continuous; and what follows a tear is not data, it is the middle of a record.
- **Opening a store is recovering it.** `Spool::with_policy` replays the log, cuts the bytes no append
  finished, and starts its counters at the recovered end, so the next append continues *there* —
  never over the records it kept, never behind a tail nobody can read. `Spool::recovered` hands back
  what that found. A store whose log was cut is still a store: refusing to start would lose the data
  and the service, and the discarded count is how the operator hears about the first one.
- **The boundary survives a machine death.** `durable_offset` is what the store promised, so
  truncating the file to it (this is the model `tests/sim_wal.rs` and the spec both use) has to leave
  exactly the flushed prefix — nothing more, and nothing that was never flushed.

The exhaustive half of the second property is the headline acceptance of this milestone, and it is a
plain spec case rather than a slow one: **every** truncation point of a written log, from zero bytes
to the whole file, recovers to a prefix of the records, each one intact, with no error and no panic.
Twenty records is a few thousand cheap calls — the case builds the log from the writer's own
`segment::encode`/`introduce` so it knows every offset, and says in its message that this is why it is
not a slow test. The mirror image is one case further down: a *flipped* byte is corruption rather
than truncation, and the seal catches it and ends the replay there instead of handing the bytes back
as a record. The same claim is made once more one level up, where it is a store rather than a walk:
`every_cut_point_of_a_store_opens_to_the_prefix_it_can_prove` cuts a store's file at every offset,
opens it, and asks for the records, the recovered end, the discarded bytes, the file's length after
opening and the store's own reader — because "opening a store recovers it" is only true if it holds
at the smallest torn tail there is, one byte past the last whole record.

**What the course gives you, and what is yours.** The scaffold declares the shape, because more than
this step reads it:

- `src/engine/wal/segment.rs` — the layout (the header, `[length][payload][seal]`) as documentation
  and as constants (`MAGIC`, `VERSION`, `HEADER`, `LENGTH`, `OVERHEAD`), plus the signatures
  `encode`, `introduce`, `scan` and `Stop::name`;
- `src/engine/wal/checksum.rs` — `seal`, `verifies` and `LEN`;
- `src/engine/wal/replay.rs` — `Recovered` (and its accessors), `recover`, `truncate`;
- `src/engine/spool/recover.rs` — `Spool::recovered`, the one signature this step adds to the write
  path (the file exists for the reason `spool/durable.rs` does: a stub the learner rewrites *in place*
  cannot be delivered by an insertion, `docs/authoring.md` §5 rule 6);
- `tests/sim_wal.rs` — the crash-scenario harness, which is the course's file (like `4.2`'s
  `tests/fuzz_protocol.rs`): `slow:sim@3` runs it once per seed and compares the `lakelet-sim` lines
  in the order they were printed. It dies four ways — the process (nothing lost), the machine at its
  flush boundary, the machine inside the write that was in flight, and a device that wrote the whole
  write with one byte changed — and the fourth is what makes *this* gate, and not only the spec,
  notice a replay that skips the record it cannot prove.

Every `todo!()` in those files is yours, and so is the wiring: `append` writes `segment`'s bytes
(a log that does not exist yet is declared by its first record), `records` reads them back, and
`with_policy` does the recovery above. Nothing about the *format* is left to a guess, because the
spec's offsets depend on it; everything about *behaviour* — what stopping means, what the boundary
is worth, what a caller may conclude — is this step's work.

## TRAP

1. **A seal over the payload alone.** It looks right and passes every case that flips a payload byte.
  Then one flipped byte in a length field moves where the record ends, the bytes that length points at
  are compared against a seal they were never covered by, and — one time in four billion — a record
  comes back that was never written. The case that catches it flips the length field on purpose, and
  it fails with `the record that changed is not handed back`.
2. **Skipping the record that failed and resynchronising.** "The next record starts four bytes past
  the length I just read" is a conclusion drawn from the bytes that just failed; the answer to the
  case `a_record_the_replay_cannot_prove_is_not_skipped_over` is `[record 0]` and not
  `[record 0, record 2, record 3, record 4]`.
3. **Recovering without cutting.** `recover` reads, `truncate` cuts, and a store that only reads
  leaves the refused bytes in the file: the next append lands behind them and every later replay
  stops there for good, so the store accepts records that no reader will ever see again.
  `tests/sim_wal.rs` fails this one at its `kind=torn` restart (`bytes + discarded != kept`), and it
  is the failure the `torn` death exists to produce.
4. **Moving `len` or not moving `durable_offset`.** The counters start at the recovered end, not at the
  file's size: a store that counts the bytes it refused reports a length nobody can read back, and
  one whose `durable_offset` is behind the recovered end tells the next crash it may take bytes that
  are already gone.
5. **A `records()` that answers the prefix instead of refusing.** `Spool::records` is the *strict*
  reader — a caller who opens a store gets the recovered prefix, but a caller who hands it a file that
  stopped mid-record gets `Error::Protocol`, not a shorter list. The two readers are deliberately not
  the same one, and the case that pins it is
  `a_reader_that_was_not_opened_since_the_cut_says_so_instead_of_answering_a_prefix`.
6. **A transcript with a wall clock in it.** `format!("{:?}", Instant::now())` puts the machine's
  real monotonic base into the transcript, so the same seed produces two different digests and
  `slow:sim@3` reports `the same seed produced two different transcripts`. Print
  `Instant::now() - started`, a *simulated* duration — the defect is measured in
  `docs/handoff-m3-log.md` 段 6, where one seed produced two transcripts for exactly this reason.
7. **A transcript that observes nothing, or that sorts its lines.** The gate compares the lines in the
  order they were printed, so sorting them throws the schedule away, and printing only a summary makes
  every seed look identical: `every seed produced the same transcript`. The seed has to decide the
  order the events happened in.
8. **`tokio::net::*` in the harness.** The real socket types need `enable_tokio_io()`, and from there
  the addresses become real: the measured answers are `AddrNotAvailable` for a simulated address and
  `AddrInUse` for a port two runs share. The harness binds `turmoil::net::TcpListener` and connects by
  host name, which is what the simulated DNS resolves.
9. **A clean stop that logs the flush without flushing.** The line's two numbers come from the store
  (`written` before the `sync`, `durable_offset` after it), so a stop that prints `written == durable`
  without having waited for the device is the *harder* lie: the check reads the pair, and the page and
  point 6 of the crash-point list would then describe a window nobody closes.
10. **A daemon that says nothing about what it recovered.** The line is not decoration: a restart that
  discarded 4 KiB and does not say so is an operator comparing query results with no explanation, and
  `discarded=0` on a clean stop is the cheapest proof that the stop path works.
11. **A `todo!()` left in any of the five files.** `no-todo` runs over every target, including the ones
  the spec never calls.
12. **A red spec read as a broken course.** The first `cargo test -p lakelet --test spec_wal_recovery`
  fails all fourteen cases at `todo!()` — in `segment`, `checksum`, `replay` and `spool/recover.rs`.
  That is this step's starting line, not a broken repository; the case that is *still* red once every
  stub is gone is the one with something to say.
13. **A model that is a story rather than a mechanism.** `tests/sim_wal.rs` says, in the file, what
  each death models and how it is done — a dropped `Spool` for a process, `set_len` at
  `durable_offset` for a machine, a cut *inside* a record for a write that was interrupted, one
  changed byte in the write that was in flight for a device that wrote something else. A scenario
  that says "the machine dies" without saying what it did to the file is a paragraph, and the next
  person cannot tell a passing run from a run that never killed anything.

## FURTHER

- The format this step's is a small version of: SQLite's WAL (a frame is a header, a page and two
  checksums, and a *salt* makes the frames of an older WAL invalid), LevelDB's `doc/log_format.md`
  (CRC per record, no file header at all — and `db/log_reader.cc`, which stops at the first bad
  record) and PostgreSQL's `xlogreader.c` (`ReadRecord`: a long header with a magic and a version,
  then `XLogReaderValidatePageHeader` per page). Three answers to the same question, and each one's
  recovery code is the interesting half.
- Kafka's log segment format — the CRC is per batch rather than per record, and a truncated batch at
  the end of a segment is the normal case its recovery expects; it is the same "the tail is not
  data" rule with a different unit.
- `crc32fast`'s documentation, and why a CRC and not a hash: an adversary who can write the file can
  write the checksum too, so honesty against a *draft* of bytes is a different problem from honesty
  against a forger. A log that needed the second one would need a MAC, and that decision belongs to a
  step that has an adversary.
- `turmoil`'s `Builder::rng_seed` and `enable_random_order` — the simulator this step's harness is
  built on, and the two knobs that make a schedule reproducible. `docs/handoff-m3-log.md` 段 6 is the
  measurement that says the seed reaches the transcript.
- `std::fs::File::set_len` and `truncate(2)`: what "cut the file to the recovered end" is, and why a
  store that recovers has to do it before it appends again.
- `lakelet/4.5-batch-writes` is what a per-record flush cannot afford; `lakelet/4.7-columnar-segments`
  and `lakelet/4.8-compaction` are where one log becomes many files and recovery has to know which
  one to start with.
