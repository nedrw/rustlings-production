# Everything that can break, on purpose, in a table the tests read

## WHY

`5.13` gave faults a vocabulary; `5.14` and `5.15` asserted two of them in depth. This step asks the
question a runbook asks: **for every fault, what is the expected behaviour?** — and writes the answer
down as a matrix.

The matrix is data, and it is checked from both sides: the code holds the cases, the project's page
holds the same table, and the spec compares them. That is `lakelet/4.3`'s trick (a decision is a value
and a sentence, and the spec checks the two agree) applied to a fault catalogue — and it matters for
the same reason: a page that drifts from the code is a page an operator trusts about behaviour nobody
implements.

Each row answers three questions, because a fault is only understood when all three are answered:

| column | question |
| --- | --- |
| fault | what is injected, in `5.13`'s vocabulary |
| client sees | the sentence a caller can act on |
| invariant | what the cluster must still hold, whatever the schedule |

## TASK

- `src/chaos.rs` — the module this step adds:
  - `Case { fault, client_sees, invariant }` and `MATRIX`, one row per fault;
  - `covers` and `case_for`: the vocabulary a runbook may use;
  - `check()`: the matrix must not name a fault twice, leave a cell empty, or say the same thing in
    both columns.
- `docs/chaos.md` — the page this step ships (`links` judges it): the same table, plus how to read a
  row and what adding a fault costs.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_chaos_matrix
```

is green, and in particular the case that reads the page: the code's matrix and the page's table
have to be the same rows, word for word.

## TRAP

- **The two columns are different in kind.** "Writes are refused while the node is down" is
  observable by a caller and useless as a post-facto assertion; "the node catches up from the log" is
  what a drill checks. A table with the same sentence in both columns has one column.
- **A fault outside the matrix has no expected behaviour.** Injecting it is an experiment, not a
  drill — which is why `covers` exists and the spec checks it.
- **The matrix is compared row by row with the page.** A row added on one side and not the other is
  a page (or a code path) that lies; the spec is the only thing that keeps them together.
- **A duplicate row is a forgotten fault.** `check()` refuses one, because a matrix that names a
  fault twice is a matrix with a hole in it.

## FURTHER

- `5.22`'s audit is the last row of the matrix made operational: after every fault, what the cluster
  committed is what every node ended up holding.
- `test/chaos-injection@apply — relay/2.17` injected faults at the HTTP boundary; this step is the
  same idea with the cluster's own vocabulary, and the matrix is what makes it a runbook rather than
  a list of experiments.
