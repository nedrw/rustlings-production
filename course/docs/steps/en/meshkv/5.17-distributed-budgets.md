# Latency and throughput against node count: the budget with three axes

## WHY

"Does it scale?" is not a question with a yes. It is a question with a **budget**: how many messages a
write costs, how many acknowledgements decide it, how much of that work each node does, and how many
round trips a caller waits for.

Three axes, and each one is arithmetic a reader can check:

- **the quorum** — `⌊n/2⌋ + 1`, the number that decides anything in this track, from membership
  changes (`5.5`) to partitions (`5.14`) to rolling restarts (`5.15`);
- **the fan-out** — `n − 1`, the messages the leader sends per write;
- **the acknowledgements** — `quorum − 1`, what the leader *waits* for. The fan-out and the
  acknowledgements are different numbers, and a budget that used one for the other would overstate
  either the network or the latency.

Every number here is a **count**, never a time: a count is the same on a busy machine as on an idle
one, which is why this step's gate is `bench-budget` and why the step's own arithmetic is the
baseline.

## TASK

- `src/budget.rs` — the module this step adds:
  - `cost(nodes)`: `Cost { nodes, quorum, messages, acks, write_hops, read_hops }` for one write and
    one linearizable read;
  - `workload(nodes, writes)` → `Counts { messages, acks, leader_messages, follower_messages, hops }`;
  - `Counts::per_node()`: the average messages per node — the number that *rises* with the cluster,
    because the leader's share grows with it and a follower's does not.
- `budget/5.17-distributed-budgets.toml` and `tests/budget_distributed.rs` are course content: the
  baseline and the harness the `bench-budget` gate reads.
- `docs/budgets.md` — the page this step ships (`links` judges it), with the table the model produces.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_distributed_budgets     # the five cases
cargo test -p meshkv --test budget_distributed -- --nocapture
```

The second prints the counts the gate compares: four thousand messages, two thousand
acknowledgements, four thousand leader messages, one thousand per follower, one hop.

## TRAP

- **Fan-out is not the decision.** The leader sends to every peer but waits for a majority; a budget
  that counted the sends as the wait would overstate latency, and one that counted the wait as the
  sends would understate the network.
- **Adding a node is not free.** The leader's work grows by one message per write per node; the
  redundancy is real and so is the cost, and the per-node average *rises* rather than falls.
- **Counts, never times.** The moment a budget is a duration, it is a budget that fails on a loaded
  machine and passes on an idle one — which teaches the wrong lesson about which changes are free.
- **The quorum is one number, used everywhere.** If this step's model and `5.15`'s rolling restart
  disagreed about the quorum, one of them would be wrong; they are the same `⌊n/2⌋ + 1` on purpose.

## FURTHER

- The same three axes are what a capacity model (`5.20`'s neighbour in T4, `lakelet/4.20`) turns into
  a predicted-versus-measured comparison; here they are the budget the gate holds the code to.
- `5.18` puts the cluster's *observed* latency next to this model's hop count, and the SLO is where
  the two meet.
