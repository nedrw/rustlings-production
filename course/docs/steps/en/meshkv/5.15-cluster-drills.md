# One node at a time: rolling restarts that never lose the majority

## WHY

`5.14` made a partition an assertion. This step is the operator's half: a rolling restart is
something the operator *does* to the cluster, and the rule is the same arithmetic applied to a
schedule instead of a fault.

> At every instant of the restart, a majority of the cluster has to be up.

A three-node cluster can lose one node; a five-node one can lose two. A plan that takes down the
second node before the first is back stops the cluster — and it looks perfectly reasonable in a
spreadsheet. That is the failure this step is about, and the answer is to make the plan a **value**
whose majority is checked before the first node is touched.

## TASK

- `src/restart.rs` — the module this step adds:
  - `Plan::new(members, order)`: the order is a permutation of the members, checked (no missing node,
    no stranger, no duplicate);
  - `Plan::majority()`: `⌊n/2⌋ + 1`;
  - `Plan::run(up)`: walk the order, taking each node down and back, and refuse the step that would
    leave fewer than a majority up. A node that is already down is brought back on its turn and
    counts as down for every step before it;
  - `Step { node, was_up, majority_kept }`: the timeline a runbook prints.
- `docs/restarts.md` — the page this step ships (`links` judges it).

## DONE WHEN

```sh
cargo test -p meshkv --test spec_cluster_drills
```

is green, and the six cases say: the plan is a permutation, a three-node cluster survives a rolling
restart, five nodes can lose two and three cannot, a down node is brought back on its turn, a plan
that would stop the cluster is refused, and an empty plan is refused.

## TRAP

- **The order is not the plan.** The plan's schedule is the operator's to choose; what makes it a
  plan is the majority check at every step, not the order somebody wrote down.
- **A node that is already down counts.** Its turn brings it back, but it is down for every step
  before that, and a plan that forgets it takes the cluster to two nodes when it thinks it has three.
- **A refusal is per step, and it names the step.** "The plan would stop the cluster" is a sentence
  with a node in it; the refusal carries the node, the number up, and the number needed.
- **A restart that changes nothing is a mistake.** Restarting the same node twice with no failure
  between is a plan that reports work it did not do; the permutation check refuses it.

## FURTHER

- The arithmetic is the quorum rule `5.5` used for membership changes: the old majority and the new
  majority have to intersect, and a rolling restart is the special case where the configuration does
  not change at all.
- `5.18` puts the restart on a dashboard: the cluster's availability budget is the same majority
  arithmetic, stated as an SLO.
