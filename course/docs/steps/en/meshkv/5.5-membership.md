# Nodes join, nodes leave, and no committed write falls out of the quorum

## WHY

Every cluster is temporary. A machine is replaced, a region is added, a node is drained for
maintenance — and the one thing that must not happen while that is going on is a committed write
falling out of the quorum, because a committed write that falls out can be overwritten, and an
overwritten decision is the failure a replicated log exists to prevent.

The dangerous shape is obvious once you write it down: if the configuration could change in one
step, there is an instant where the old voters and the new voters each believe they are the
cluster. Two majorities that do not overlap can then decide two different things at the same index,
and both are "committed" by their own set.

Raft's answer is **joint consensus**, and it is the shape this step implements:

1. the leader appends a configuration entry naming **both** sets. From that moment a decision needs
   a majority of the old set **and** a majority of the new one — the membership is *joint*;
2. when that entry commits, every node adopts the new configuration and forgets the old one.

Any majority of the old set and any majority of the new set intersect as long as the cluster is
healthy, so there is exactly one quorum at every instant — the window is closed by construction,
not by timing.

Two details make this a `apply`-level step rather than a paragraph:

- **the configuration is a log entry**, so it is ordered with respect to the writes it must not
  lose. A change that overtook a write in flight would be a change that lost it.
- **the change is only decided by both sets**, so a leader that starts a change cannot finish it
  with a majority of the cluster it is leaving, and cannot finish it before the cluster it is
  joining has the entry — which is the whole point.

## TASK

- `src/raft/membership.rs` — `Config` (the voters, parsed from `n1,n2,n3`, refusing an empty list
  and a duplicate name), `Membership::{Stable, Joint}` with `is_met`, `targeted`, `voters`,
  `is_joint`, and the two functions that carry a configuration in an entry's payload
  (`encode`/`decode`).
- `src/raft/state.rs`:
  - `membership()`: the configuration this node is on, and whether a change is in flight;
  - `decided`: a decision is the membership's — one majority when stable, both while joint;
  - `begin_membership(target)`: leader only, one at a time, appending the configuration entry and
    putting the node into the joint state;
  - `peers()` is the union of both sets while the change is in flight: the joining nodes have to
    receive the entries they will be voting on, and the leaving ones have to keep receiving them
    until the change commits;
  - when a committed entry is a configuration, both the leader and the followers adopt it — the
    second half of joint consensus. A configuration entry that is **not** committed changes
    nothing.
- `tests/sim_membership.rs` is course content (shipped by this step): it drives the state machines
  as a value-level cluster, with the seed deciding whose election timeout fires first and in which
  order the messages arrive.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_membership      # the nine cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_membership -- --nocapture
```

The second prints a transcript like

```text
meshkv-sim elect leader=n1
meshkv-sim write index=2 committed=1
meshkv-sim change voters=5 joint_before=1 joint_after=0
meshkv-sim write index=4 committed=1 joined=1
```

and another seed elects another leader — the cluster has to agree on the same answer whoever won.

## TRAP

- **A majority of the old set is not a decision while the change is in flight.** That is the
  failure the joint phase exists to prevent: it would let the departing cluster commit a write the
  arriving one can overwrite.
- **A majority of the new set is not a decision either, before the new nodes have the log.** They
  have the state machine, not the entries: a decision needs a majority of the new set *that has the
  entry*, and the count is of acknowledgements, not of names.
- **The configuration is an entry, and its position matters.** It goes through the same
  `prev`/`match` machinery as a write, which is what keeps a change from overtaking a write in
  flight.
- **The change does not end when it is appended.** It ends when the configuration entry is
  *committed* — and that commit is exactly what requires both majorities.
- **A node that leaves is not a peer any more, and its acknowledgement stops counting.** A cluster
  that kept asking the departed node would be a cluster that can deadlock on a node that has been
  powered off.
- **One change at a time.** Two configuration entries in flight is two windows, and the second one
  may be committed by a set the first one has not agreed on yet.

## FURTHER

- Raft's paper §6 ("Cluster membership changes") is this step, including the argument for the joint
  phase: the two sets have to overlap, and the only way to guarantee it is to require both
  majorities while the change is in flight.
- `openraft` calls the same pair `Membership::{Stable, Joint}`; the names and the two `is_met`
  branches are the same because the protocol is.
- `5.21` runs two *versions* of the cluster at once — the same window, but the two sets differ in
  what they speak rather than in who they are.
