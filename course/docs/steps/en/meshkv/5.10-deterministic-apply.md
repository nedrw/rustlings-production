# The state machine is a pure function of the log, and the tests can prove it

## WHY

Nine steps of this track have been moving entries around. None of them said what an entry *means*.
This step is where the log becomes a key-value store, and where the sentence that makes a replicated
store possible finally has to be true:

> **The state is a function of the entries, and of nothing else.**

Two nodes that applied the same entries in the same order hold the same state — byte for byte. That
is what makes a leader and a follower agree, what makes a restarted node catch up, and what makes
`5.4`'s snapshot a fact rather than an opinion. It is also the sentence a single careless line can
break, and the breakage is invisible until two replicas disagree while both insist they are right.

The usual suspects are boring:

- **iteration order over a hash map.** Two nodes insert the same keys and iterate them differently.
  If the state's serialised form depends on that order, the two replicas disagree about their own
  digest while holding the same data.
- **the clock.** A state machine that reads `now` applies a different function on every replay — and
  a follower replaying the log after a restart disagrees with the leader about what happened.
- **randomness** (no place in a replicated function) and **floating point** (agrees with itself only
  on the same platform and the same instruction set).

So the state is an **ordered** map, the digest walks it in key order, and the API has **no time
argument anywhere**. That last one is a type-level statement: this step's code has nowhere to put a
clock, which is stronger than a comment saying it does not read one.

## TASK

- `src/kv.rs` — the module this step adds:
  - `Command::{Set, Cas, Delete}`, parsed from an entry's payload (`set k v`, `cas k expect new`,
    `delete k`, values as hex) and encoded back to the same bytes. Parsing is strict: a malformed
    command is a refusal, not a guess.
  - `Kv`: a `BTreeMap` from keys to values plus the last index applied. `apply(index, payload)`
    refuses anything that is not exactly the next index — a state machine applies a *prefix* of the
    log, so a gap, a duplicate or a step backwards is refused rather than guessed at.
  - `Applied::{Written, Removed, Absent, Mismatch}`: what one entry did, including the two cases a
    compare-and-set needs (the value matched, or here is what it holds instead).
  - `digest()`: an FNV-1a over the keys in order and their values. Two nodes with the same data
    produce the same digest whatever order the map was built in.
- `tests/sim_kv.rs` is course content: two machines, one log, the same digest — the seed decides the
  log, and a different seed is a different log.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_kv          # the nine cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_kv -- --nocapture
```

The second prints the digest after the whole log, then the digest a *fresh* machine reached by
replaying the same entries — and the two are the same number.

## TRAP

- **A hash map's iteration order is the classic way to break determinism.** The state uses a
  `BTreeMap` and the digest walks it in key order; a `HashMap` here would be a correctness bug that
  only shows up under a seed.
- **No clock in the state machine.** Not "no clock for now" — none in the API, so there is nowhere
  to put one. Time is a property of the *request* (`5.8`'s window), not of the apply.
- **Apply in order, and refuse the rest.** A state machine that accepted a gap would be one whose
  state depends on which entries happened to arrive. `index != applied + 1` is a refusal.
- **A failed compare-and-set changes nothing.** It answers `Mismatch` with the value that *is*
  there, so the caller can decide; writing anyway would make the CAS a plain set with extra steps.
- **The digest is over contents, not history.** Two logs that wrote the same keys in different
  orders reach the same state and must reach the same digest — that is what makes it a digest of the
  state rather than of the log.
- **The payload is the command.** The consensus layer treats an entry as bytes (`5.3`); this is the
  first place bytes are interpreted, and the interpretation is the step's whole contract.

## FURTHER

- Raft's paper calls this the *state machine*: a deterministic application of the log to a state.
  The word "deterministic" is doing all the work, and §5.4.3 explains why a leader must not commit a
  state that its followers would reproduce differently.
- `5.13` runs this code under a simulated network with the segment boundaries in the log itself; a
  non-deterministic apply makes that harness flaky, which is how the rule stays enforced.
- `5.22`'s audit compares the state the cluster committed with the state every node holds — the same
  digest this step computes, over the whole cluster.
