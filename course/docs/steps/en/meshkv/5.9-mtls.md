# The peer across the wire is the node it claims: mTLS and the rotation window

## WHY

`5.1` gave a node a name and a one-line handshake. That is enough to route messages and nothing
else: any process that can open a socket can say `MESHKV/1 hello n1`, and a cluster that believes
it will replicate its log to whoever asks. In a cluster, that is not a routing bug — it is a
cluster that can be joined by anything on the network.

The fix is not "add TLS" as a checkbox. Three rules have to hold, and each one is a way a cluster is
compromised:

- **the issuer has to be trusted.** A certificate is a statement by somebody; the trust store is the
  list of somebodies this node believes. A certificate from a stranger is a stranger, however
  well-formed.
- **the window has to contain now.** Certificates expire, and that is the mechanism by which a
  compromised key stops being useful. A node that verifies without the window has a trust store that
  only grows.
- **the name in the certificate has to be the name that was claimed.** A valid certificate for `n2`
  proves the peer is `n2`; it proves nothing about a peer claiming `n3`.

And there is a fourth thing that is not a rule but an operation: **rotation**. It is the one moment
a cluster holds two truths at once — the old certificate and the new one — and a cluster that gets
it wrong has an outage every time a certificate is renewed, which is to say regularly.

The result of verification is an [`Identity`], and that type is the point of the step: it cannot be
built by hand, so any code that takes one has a proof in hand rather than a string somebody typed.
This is `domain/parse-dont-validate@apply` used for a security decision — the difference between a
check and a guarantee is whether the unchecked value can still reach the code that cares.

## TASK

- `src/security.rs` — the module this step adds:
  - `Certificate`: a subject, an issuer, and a half-open validity window (`not_before` inclusive,
    `not_after` exclusive). An empty or backwards window is refused when the certificate is built.
  - `TrustStore`: the issuers a node believes, with `trusts`.
  - `verify(certificate, store, now)`: the three rules, each refusal naming which one failed.
  - `authenticate(claimed, certificate, store, now)`: verify **and** check that the certificate's
    subject is the name that was claimed.
  - `Identity`: the verified name, with no public constructor — `verify` and `authenticate` are the
    only doors.
  - `Rotation`: a node's current and next certificate. `presented(now)` answers the one the node
    shows its peers (the new one from the instant it is valid), `accepts(peer, store, now)` answers
    whether a peer's certificate is accepted (either, while both are valid), and
    `earliest_safe_retirement(overlap)` is the arithmetic that keeps a rotation from becoming an
    outage.
- `docs/mtls.md` — the page this step ships (`links` judges it).
- `tests/sim_mtls.rs` — course content: the scenario the `slow:sim@3` gate runs, with the seed
  deciding the order the handshakes happen in.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_mtls        # the ten cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_mtls -- --nocapture
```

The second prints a transcript like

```text
meshkv-sim rotation overlap_start=200 overlap_end=500
meshkv-sim handshake peer=n2 phase=overlap verdict=accepted
meshkv-sim overlap_accepted=3
meshkv-sim handshake peer=n2 phase=retired old=refused new=accepted
meshkv-sim after_retirement_accepted=3
meshkv-sim safe_retirement=300
```

and another seed handshakes in another order with the same verdicts.

## TRAP

- **A certificate is not an identity until it is checked against the claim.** A handshake that
  verifies the chain and ignores the name has authenticated somebody, not this peer — and in a
  cluster "somebody" is exactly what an attacker is.
- **The window is half-open.** A certificate is invalid at the instant it expires, not one
  millisecond later; the safe side of the comparison is the one that refuses.
- **An expired certificate and an untrusted issuer have different fixes.** The refusals say which
  one it was, because "handshake failed" sends an operator to the wrong place.
- **Present the new certificate only when it is valid.** Presenting it early fails against every
  peer that has not been updated yet — a rotation that starts with a cluster-wide refusal.
- **Accept both while both are valid.** The overlap is not laxity; it is the only way a rotation has
  no gap. What makes it safe is that it ends.
- **Retire on arithmetic, not on nerves.** `earliest_safe_retirement` is the new certificate's start
  plus the distribution time; retiring before it is an outage with a schedule.
- **Time injected, never read.** Validity windows are exactly the kind of thing a test has to be
  able to sit on either side of (handoff M3, `5.6`).

## FURTHER

- Rustls's book, the chapter on client and server authentication, is the wire format this step's
  rules sit in front of. The step deliberately does not implement the handshake; it implements the
  decisions a handshake has to make.
- `sec/token-lifetime@apply — relay/2.21` is the same three rules for bearer tokens; the difference
  here is that a certificate is presented per connection rather than per request, which is what
  makes the rotation overlap a *cluster* problem rather than a client one.
- `5.21` runs two versions of the cluster at once; a version skew and a certificate rotation are the
  same shape of problem — a window in which two truths coexist, with an arithmetic answer to when it
  ends.
