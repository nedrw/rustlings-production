# The network as data: turmoil topologies, seeds, and the digest of a run

## WHY

Every step of this track has tested a *rule* — a vote, a commit, a redirect — by calling it. None of
them tested what happens when the rules meet a network that misbehaves: a node isolated from the
others, a crash in the middle of a write, a message that never arrives. Those are the failures a
distributed system is *for*, and they are also the hardest to test, because in production they happen
at a moment nobody chose.

This step's answer is the one every serious distributed system has arrived at: **make the failure an
input.** A scenario becomes a text file — a *playbook* — of faults and writes; a seed decides the
order events happen in; and the run is a function of `(seed, playbook)`.

Two properties fall out, and both are the point:

- **the same seed is the same run.** A bug found by a seed is a bug somebody else can reproduce,
  byte for byte. Without this, a failure under load is an anecdote.
- **another seed is another run.** One interleaving tests one interleaving. The scenarios the course
  ships run under several seeds, and the invariants have to hold under all of them.

Why this is possible at all is the design decision `5.3` made and every step since has kept: the
cluster's rules are a *pure* state machine. A playbook can only drive something that takes messages
and returns messages. A system that reached for the network inside its rules could not be driven by a
playbook — its failures could only be tested by waiting for them.

(The course also ships `turmoil`, which does the same thing at the level of real sockets and a
virtual clock, and `5.3`'s instrument uses it. This step is about the *shape* of the failure, not
about which simulator provides the clock: a playbook is data, and data outlives the tool that ran
it.)

## TASK

- `src/sim.rs` — the module this step adds:
  - `Fault::{Partition, Heal, Drop, Crash, Restart}`, parsed from one line each;
  - `Playbook`: the steps in order (`Step::Fault` and `Step::Write`), read from text with `#`
    comments, plus `check()` — a playbook that says nothing is refused (a node isolated from
    itself, a heal of a link that is not partitioned, a drop of zero, two crashes with no restart);
  - `run(seed, size, &playbook)`: the cluster as `size` state machines, the faults applied between
    the writes, every event recorded;
  - `Transcript`: the events in order and a digest of them (FNV-1a), so "the same run" is one
    comparison.
- `docs/simulation.md` — the page this step ships (`links` judges it).
- `tests/sim_playbook.rs` is course content: the scenario the `slow:sim@3` gate runs, from a string.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_deterministic_network      # the seven cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_playbook -- --nocapture
```

The second prints the playbook's shape, every event in order, and the digest; the same seed prints
the same digest, and another seed a different one over the same scenario.

## TRAP

- **A playbook that says nothing is refused.** `partition n1 n1`, `heal` without a partition, `drop
  0`, two crashes with no restart — each is a step that cannot change anything, and a scenario built
  from those proves nothing. The check runs before the run.
- **The same seed has to be the same run, or the tool is a rumour.** That is what the digest is for,
  and why every event is a name, a count or a verdict — a clock or a path in the transcript would
  destroy the property.
- **A different seed has to be a different run.** A harness that ignores the seed passes three times
  and proves nothing; `sim@3` requires at least two distinct transcripts.
- **Faults are between the writes, not around them.** A crash after the last write is a different
  scenario from a crash before it — the playbook's order *is* the scenario.
- **The vocabulary is small on purpose.** `Partition`, `Heal`, `Drop`, `Crash`, `Restart` are enough
  to express every failure this track needs; a fault vocabulary nobody can exhaust is one that hides
  bugs instead of finding them.

## FURTHER

- `turmoil` and `madsim` are the two Rust simulators this idea is usually built on; `5.3`'s
  instrument uses turmoil at the socket level, and this step's playbook is the same idea one level
  up — the faults as a file.
- `5.14` reads a partition out of a playbook and asserts what the minority did; `5.16` turns the
  vocabulary into a matrix with an expected behaviour per cell.
