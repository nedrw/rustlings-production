# The log cannot grow forever: a snapshot is the state at an index

## WHY

A replicated log is a perfect record and a terrible product. It has every write in order, it can
rebuild any state, and it grows without bound — which means a node that has been in the cluster
for a year has to replay a year of writes to start, ship a year of bytes to a node that fell
behind, and hold a year of entries in memory and on disk to answer a question about *now*.

The answer every replicated store arrives at is the same: **the state at some index is enough, and
the entries that produced it can go**. A snapshot is that state plus the two numbers that say where
it came from — the index and the term. Compaction is what uses it: everything at or below the
snapshot's index is dropped from the log, and the log keeps its place in the cluster's numbering.

This step is `design`-level because the decision is not "take a snapshot sometimes"; it is a set of
choices with consequences:

- **when** a snapshot may be taken (only of committed state — anything else may still change);
- **what** it is allowed to replace (the entries it covers, and nothing more: a log that compacts
  past its snapshot has lost the ability to catch up a follower by entries alone);
- **how** a node that is too far behind catches up (it cannot be sent entries the leader no longer
  has, so it is sent the state);
- **what happens when a late snapshot arrives** (it is refused: a snapshot older than what a node
  has applied would undo a state that is already there).

The payload stays opaque. What a state *is*, and the rule that applying the same entries on two
nodes produces the same bytes, is `5.10`'s subject; this step is about the bookkeeping that makes
that state transportable.

## TASK

- `src/raft/snapshot.rs` — `Snapshot`: the index and term it covers, and the bytes. Constructing one
  at index 0 is refused, and `covers(index)` answers whether a given position is inside it.
- `src/raft/mod.rs` — the log learns where it starts:
  - `base()`: the index of the last entry it no longer holds;
  - `compact_to(index)`: drop the entries at or below `index`, keep the place (the next entry is
    `index + 1`), and refuse an index the log does not hold;
  - `starting_at(index)`: the empty log a node has after it installs a snapshot;
  - `at()` and `append()` and `truncate_from()` now account for the base, so an index still means
    the same thing on every node.
- `src/raft/state.rs` — `Raft` learns to take, compact and install:
  - `take_snapshot(data)`: of the committed state only, refusing when nothing is committed;
  - `compact(snapshot)`: check the log against the snapshot (it must hold that index, with that
    term) and compact;
  - `install_snapshot(snapshot)`: replace the log with the state, moving the commit index; a
    snapshot older than what the node has applied is refused;
  - `needs_snapshot(peer)`: whether a peer is behind the snapshot — and `append_entries()` sends the
    snapshot instead of entries when it is;
  - the `InstallSnapshot` message, its encoding, and the follower's answer.
- `docs/snapshot.md` — the page the step ships (`links` judges it).
- `tests/budget_snapshot.rs` — the harness the `bench-budget` gate reads: it compacts a thousand-entry
  log to a snapshot at 600 and prints the counts.

## TRAP

- **A snapshot is of the committed state.** Snapshotting an entry that is not committed yet takes a
  picture of a state that may still change — and a node that installs it has applied something that
  may never have happened.
- **Compaction keeps the numbering.** After compacting to 600, the next entry belongs at 601, and
  position 600 is the last one this node remembers having applied. A log that renumbered itself
  would make every other node's `prev` disagree with it for ever.
- **An index below the base is not an entry.** `at(500)` on a log compacted to 600 answers `None`,
  exactly like an index in the future. Code that treats "missing" as "not yet" and retries waits
  for ever.
- **The peer that needs a snapshot is the one that is behind it.** If the position the leader would
  send a peer to is at or before the snapshot's index, the entries that lead there are gone — send
  the snapshot. Sending entries from a compacted position is how a follower is stuck behind for
  ever, silently.
- **A late snapshot is refused.** A snapshot older than the node's commit index would undo state
  that is already applied. The refusal is the correct answer, and it has to be explicit: a node that
  silently ignores it is a node that never learns it is behind.
- **The snapshot's term is checked against the log's.** Same index, different term means a different
  history: the snapshot is from a branch this node never had. Compacting to it would replace the
  wrong entries.

## FURTHER

- Raft's paper §7 ("Log compaction") names the same three problems: how much of the log to keep,
  when to take a snapshot, and how to catch up a follower that is behind the snapshot. The phrase
  the paper uses for the last one — "install snapshot" — is the message you just implemented.
- `openraft` calls the pair `(last_log_id, snapshot_meta)`; every implementation keeps the index and
  the term together for the reason this step's spec checks.
- `5.15` restarts a node that has been away long enough to need this path, and `5.22` audits that
  the state a snapshot carries is the state the cluster committed — the two steps that turn "it
  compiles" into "it survived".
