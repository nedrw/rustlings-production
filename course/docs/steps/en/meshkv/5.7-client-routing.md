# Any node answers, one node decides: routing and redirection

## WHY

A client of a replicated store does not know who the leader is, cannot be told in advance, and
often does not want to care: it knows an address — the one its service discovery gave it, the one
behind a load balancer, the one in a configuration file that was right last week. The cluster,
meanwhile, moves its leadership around: a node is replaced, a region is drained, an election runs.

So the client asks a node, and the node may not be the one that may serve the request. What happens
next is this step's whole subject, and it is more than "ask someone else":

- **the refusal has to name somebody.** "I am not the leader" without a name is a dead end. The
  node that answers a redirect it cannot resolve says *no leader* instead — which is the honest
  answer while an election is running — and the client stops and says so, rather than trying nodes
  at random until one happens to lead.
- **a redirect cycle must not spin.** Two nodes that each believe the other is the leader — which
  happens during a leadership change — would send a client round for ever. The client remembers
  where it has been, and a request that comes back to its starting point is a failure, not a retry.
- **the number of hops has to be bounded.** Even without a cycle, a chain of redirects must end, and
  the bound is a number the client can state and a test can check.
- **what the client learned is worth keeping.** A client that has just learned where the leader is
  should ask there first next time: one line, and the difference between one round trip and two.

The step is `apply`-level because the rules are simple and the ways to get them wrong are not: the
difference between a client that survives a leadership change and one that hangs is a handful of
sentences, and every one of them is a case a test can hold.

## TASK

- `src/client.rs` — the module this step adds:
  - `Answer::{Served, Redirect, NoLeader}`: what a node says;
  - `Transport`: the seam — how a client reaches a node. A routing rule that cannot be tested
    without a network is a routing rule nobody tests, so the trait is one method and the harness
    implements it with a table;
  - `Client`: `serve(node, request, transport)` asks the leader it remembers (if any) and then the
    node it was given, follows redirects, and stops on a cycle, on a node that knows no leader, or
    on more hops than `MAX_HOPS`;
  - `leader()` and `hops()`: what the client knows and what it cost.
- `src/error.rs` — a refusal that names the leader: `Error::NotLeader { leader }`, so a write
  proposed at a follower tells the client where to go.
- `src/raft/state.rs` — `propose` on a follower now refuses with that error, and the message names
  the leader this node knows.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_client_routing
```

is green, and the cases it holds are the four rules above: the leader serves it, a follower
redirects, a cycle stops, the hop count is bounded, a node that knows no leader says so, and a
remembered leader is tried first.

## TRAP

- **A node that is down and a node that is not the leader are different failures.** The first is
  worth retrying, the second is worth redirecting; a client that treats them the same either spins
  on a dead node or gives up on a live one. The transport is where the difference comes from, and
  the error type keeps them apart.
- **A redirect that names nobody is not a redirect.** It is a dead end with a friendly name.
- **The hop bound is a number, not a hope.** "The chain will end" is not a property a client can
  rely on; `MAX_HOPS` is, and the spec checks that the client stops there.
- **A remembered leader is a hint, not a guarantee.** The leader may have changed since; the client
  still has to handle being redirected again.
- **A refusal that does not name the leader throws away the only useful thing it knew.** The cost
  of a redirect is one extra round trip; the cost of not naming it is a client that has to guess.

## FURTHER

- `openraft`'s client is a `Client` trait with a `Leader` handle behind it — the same split: the
  client asks, the cluster answers with a leader or with "ask again later".
- `5.8` is the next thing a client needs: when the redirect itself is retried, the retry must not
  be a second write. This step's client knows where to send a request; the next one knows what to
  do when the same request arrives twice.
- `5.11` gives the client an SDK, and the SDK's error type is exactly this step's three answers
  plus the refusals — a client's API is mostly the shape of its failures.
