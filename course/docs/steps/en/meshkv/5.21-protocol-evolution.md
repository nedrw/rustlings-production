# New nodes, old nodes, one cluster: versioned protocol and rolling upgrade

## WHY

A rolling upgrade is the third "two truths at once" in this track: joint consensus (`5.5`) held two
memberships, certificate rotation (`5.9`) held two certificates, and this step holds two **builds**.
The rule is the same arithmetic in a different unit — every node has to understand every other node at
every instant — and two numbers make it checkable:

- **major** is the wire format: two builds with different majors cannot talk, so a rolling upgrade may
  never mix them. A major bump is stop-the-world, and the plan refuses to pretend otherwise;
- **minor** is compatible inside a major, and the compatibility is **asymmetric**: a build parses every
  minor up to its own and no further. The newer build is the one that holds back, because it is the one
  that could send a frame the older cannot read.

That asymmetry is the whole constraint: a node upgraded to `1.2` speaks `1.1` on the wire until the
last node is upgraded, and the plan's phases say so.

## TASK

- `src/protocol.rs` — the module this step adds:
  - `Protocol { major, minor }` with `parse`/`render` and `can_parse` (the asymmetric rule);
  - `Greeting { node, protocol }` and `accept(local, greeting)`: refusals that name both versions, and
    say whether it was the major or the minor that could not meet;
  - `Upgrade::new(order, from, to)`: refuses an empty order, a downgrade, and a major-crossing plan;
  - `Upgrade::phases()`: one `Phase::Compat { speaking, built }` per node until the last, which is
    `Phase::Native { version }` — the moment the cluster moves.
- `docs/protocol.md` — the page this step ships (`links` judges it): the two numbers, the asymmetry, and
  the deploy log an operator reads.
- `tests/sim_protocol.rs` is course content: the plan walked in the seed's order.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_protocol_evolution     # the six cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_protocol -- --nocapture
```

The second prints the plan's phases in the seed's order — all `compat` but the last, which is
`native` — and every seed reaches the same shape.

## TRAP

- **The compatibility rule is asymmetric.** A newer build reads an older one's frames; an older build
  cannot read a newer one's. A plan that assumed symmetry would leave the older nodes failing to parse
  what the newer ones send.
- **A major bump is not a rolling upgrade.** Two majors cannot be in one cluster, and a plan that
  crossed one would be a plan that stops the cluster; the refusal says so.
- **The refusal names both versions.** "Protocol mismatch" sends an operator to the wrong build;
  `1.2` and `1.1` in one sentence does not.
- **The last step is the move.** Until it, the upgraded nodes are new builds in compatibility mode —
  which is what a deploy log should say, and what a plan that "upgrades everything at once" cannot.
- **The plan is an order plus phases, and the order is the operator's.** The check does not care which
  node goes first; it cares that the cluster never mixes what cannot meet.

## FURTHER

- `5.9`'s rotation and `5.5`'s joint consensus are the same shape: a window where two truths coexist,
  an arithmetic bound on how long it lasts, and a check that runs before the change.
- `5.22`'s audit is the last step: after every change this track has planned, the state the cluster
  committed is the state every node holds.
