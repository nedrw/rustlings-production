# Consistency is a dial: what each level promises and what it costs

## WHY

`5.6` gave one answer for reads: the leader, with a lease, and it is linearizable. That is the
strongest promise and the most expensive one — every read needs the leader, and the leader is one
node out of three.

Most reads do not need it. A dashboard that refreshes every ten seconds does not care about the write
that landed a millisecond ago; a cache warmer can live with a second of staleness; an operator asking
"what does *this* node hold" wants a different question answered entirely. The dial is how a caller
says which of those it is asking, and the three levels here are the ones every replicated store
offers:

| level | promise | who may answer |
| --- | --- | --- |
| `linearizable` | correct as of a moment after the read began | the leader, with a confirmed lease |
| `bounded-stale:<n>` | at most `n` entries behind the cluster's commit | any node that can *show* it is within `n` |
| `local` | whatever this node applied | any node |

The interesting part is not the enum. It is that **each level has to be refused when it cannot be
honoured**. A follower asked for a linearizable read must say so rather than answer from its own
state; a node asked for bounded-stale must be able to *show* its lag rather than assume it. A level
that is silently downgraded is worse than one that is refused, because the caller never learns which
promise it got — and a caller that cannot tell is a caller that cannot reason about its own reads.

## TASK

- `src/consistency.rs` — the module this step adds:
  - `Level::{Linearizable, BoundedStale { max_lag }, Local}` with `parse`/`render`
    (`linearizable`, `bounded-stale:<n>`, `local`) and `is_linearizable`;
  - `Answer::{Served { index }, Refused { reason }}`;
  - `answer(level, is_leader, lease_index, applied, commit, leader)`: the whole policy as one pure
    function. Every fact it needs — including the lag — is an argument, so the boundary of a level
    can be tested without a cluster.
- The lag is not measured here: a node knows its applied index, and it learns the leader's commit
  index from the leader's messages (`5.3`). The caller passes both; the module stays free of time
  and of the network.
- `tests/sim_consistency.rs` is course content: three nodes at different lags, one read per node per
  level, the seed deciding the order and the lags.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_consistency_levels      # the eight cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_consistency -- --nocapture
```

The second prints the lag of the furthest-behind node and the verdict each level gave it; another
seed is another set of lags with the same rules.

## TRAP

- **A follower must not answer a linearizable read.** It has no idea how far behind it is; the
  honest answer names the leader, and the caller retries there.
- **A leader without a lease cannot answer one either.** It is *probably* still the leader, and
  "probably" is the class of answer this course keeps removing (`5.6`).
- **A bound with no leader to measure against is unprovable.** A node that has heard of no leader
  cannot show its lag, so it refuses rather than guesses — the refusal is the honest answer.
- **The answer names the index it is correct at.** For bounded and local reads that is the node's
  applied index; for a linearizable read it is the lease's index, not the newer commit — a caller
  told the newer one would believe a value committed after the round.
- **A node ahead of the commit it knows about is not "negative behind".** The lag is zero, and a
  bound of zero serves it.
- **A silently downgraded level is the bug.** The dial's value is that a caller can trust the
  promise it asked for; a level that degrades quietly has no value at all.

## FURTHER

- This is the same trade-off the industry argues about as "linearizable vs bounded-stale reads"; the
  arithmetic is what matters, and it is the arithmetic this step makes testable.
- `5.18` puts these levels on a dashboard: the cluster's SLO is stated per level, because a
  bounded-stale read and a linearizable one have different budgets.
