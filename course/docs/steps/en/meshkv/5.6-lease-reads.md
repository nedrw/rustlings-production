# A read is a question about now: linearizable reads and the lease that makes them cheap

## WHY

A replicated log answers "what happened". A read answers "what *is*", and those are different
questions: a follower can be a hundred entries behind and still answer confidently from a state the
cluster replaced two seconds ago. That is a stale read, and it is not a small problem — a read
followed by a write on a stale answer is a lost update, and the whole point of a consensus log was
to stop exactly that.

Every replicated store solves this the same way, and this step implements both halves of the
solution:

- **the read index.** A leader that wants to answer does not trust its own memory. It sends a
  heartbeat, waits for a majority of the cluster to acknowledge it *in the leader's own term*, and
  only then answers at the commit index it saw before the round. The majority is the proof: no other
  node could have been elected in that term without at least one of those acknowledgements.
- **the lease.** That proof does not have to be repeated for every read. If a majority acknowledged
  the leader at `t` and the election timeout is `T`, no other node can win an election before
  `t + T` — so the leader may answer locally until then. The window is the lease, and it is only
  safe because it is **strictly shorter** than the election timeout: a lease that outlived the
  timeout is a stale read with extra steps.

The step is `design` depth for one reason: the interesting part is not the code, it is the argument
about *time*. The correctness of the read path depends on a relationship between two durations, and
that relationship is the thing a reviewer has to be able to check. So the spec checks it:
`is_safe_lease(lease, timeout)` is the sentence, and the course's own constants have to satisfy it.

One design rule shapes every function here: **time is an argument, not a call.** A lease that read
`SystemTime::now()` itself could not be tested (the test would race the window) and could not be
simulated (`5.13` drives this code through a virtual clock). Every function that needs to know when
it is takes a `now` in milliseconds, and the caller — the daemon, the harness, the simulator —
decides what "now" means.

## TASK

- `src/raft/read.rs` — `Lease` (an expiry and the position it covers), `ReadAnswer` (`Served`,
  `NotLeader`, `NeedsQuorum`), `LEASE_MILLIS`, `ELECTION_TIMEOUT_MILLIS`, and `is_safe_lease`.
- `src/raft/state.rs`:
  - `confirm_read(now)`: leader only; remember the commit index as the read index and return the
    heartbeats that prove leadership;
  - `complete_read(acknowledged, now)`: a majority in this term grants the lease at the read index
    and answers `Served`; anything less answers `NeedsQuorum` and grants nothing;
  - `serve_read(now)`: a follower answers `NotLeader` (with the leader it knows, if it knows one); a
    leader answers `Served` only inside its lease, and `NeedsQuorum` outside it;
  - `read_index()` and `lease()`: what the node is currently holding;
  - and the lease is dropped whenever the node stops leading — a promise about being the leader
    cannot survive the leadership.

## TRAP

- **A follower cannot answer, and must not pretend it can.** It has no idea how far behind it is;
  the honest answer is the leader's name, and the client retries there.
- **A leader without a round is not a leader that may answer.** It is *probably* still the leader —
  and "probably" is the class of answer this course keeps removing. The round is what turns it into
  knowledge.
- **The lease answers the position the round proved, not the newest commit.** A value committed
  after the round may not be on a majority yet. Answering the newer position would be claiming a
  decision the round did not prove.
- **The lease dies with the leadership.** A node that steps down (a newer term, a competing leader)
  must forget its lease and its read index in the same breath as its role; otherwise it keeps
  answering for a term that ended.
- **A lease as long as the election timeout is already too long.** An election can start at the
  instant the lease would end, so the comparison has to be strict. `is_safe_lease` is that sentence.
- **Time injected, never read.** A function that calls the clock is a function the deterministic
  simulator cannot drive — and the read path is exactly the code the simulator has to drive, because
  the lease is a statement about time.

## FURTHER

- Raft's paper §8 ("Client interaction") describes the read index and the lease in these terms: the
  leader confirms with a heartbeat round, then either serves the read at the confirmed index or
  waits for the entry it needs.
- `openraft` exposes the same idea as `ReadPolicy::LinearizableRead`; its `Leader` handle answers
  reads only after the equivalent confirmation.
- `5.12` turns the single answer this step gives into a *dial*: bounded-stale reads, reads from a
  follower with a known lag, and the price of each.
