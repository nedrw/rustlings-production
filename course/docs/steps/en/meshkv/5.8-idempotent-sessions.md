# A retry is not a second write: sessions and the keys that make one

## WHY

`5.7` taught a client to find the leader. This step is about what happens after it does, because
the answer to that question is often *nothing at all*: the request times out, and the client cannot
tell whether the write committed or whether the request never arrived. Both look identical from the
outside, and the client's only safe move is to ask again — which is fine, as long as asking again
is not a second write.

The failure this prevents is not hypothetical and not subtle. A client retries a `Set` it already
sent, the leader applies it twice, and the value that was supposed to be incremented once is
incremented twice. The write "succeeded" every time; the accounting is wrong. In a payment system
that is money; in a job queue that is the same job run twice.

The mechanism has two halves, and both are needed:

- **the session.** A client that talks to a cluster needs an identity that survives a retry, and the
  session has to be bound to *one* leader at a time: a retry that crosses a leadership change is a
  request a different leader has to recognise.
- **the idempotency key.** The client puts a key on the write it means to make once. The leader
  remembers the keys it has applied, together with the answers it gave, and a request that carries a
  key it has seen is not applied again — it is *answered again*, with the same answer.

The second half is where the care goes, and it is what this step is about:

- a duplicate must return the **original** answer, not a fresh one — a client that asked twice must
  not see two different results for one write;
- the key has to be remembered for a **window** long enough to cover a client's patience, and the
  window has to be *bounded*, because it costs one entry per write.

## TASK

- `src/idempotency.rs` — the module this step adds:
  - `IdempotencyKey` and `Session`: a session with an id (an anonymous session is refused — it
    cannot be recognised on a retry), and `key_for(request)`, which derives the key of one intended
    write from the session and the request;
  - `Answers`: the remembered keys with their answers and the moment they were answered, with
    `expire(now)` dropping the ones outside the window;
  - `Ledger`: `apply(key, now, apply)` — the heart of the step. A key it remembers is *not* applied
    again; the closure that would apply a new write is not even called, and the original answer is
    returned as `Outcome::Duplicate`. A new key is applied and remembered as `Outcome::Applied`.
  - `default_window()`: the window the course ships, long enough for a client that retries for a
    minute.
- A write that **fails** must leave no remembered answer — a refused write is not a write, and
  remembering it would answer a later retry with a failure that never applied.

## DONE WHEN

```sh
cargo test -p meshkv --test spec_duplicates
```

is green, and the cases it holds are: the same request in the same session has the same key, a
retry is answered with the original answer and applied once, a key is remembered for the window and
forgotten after it, a failed write is not remembered, and the answers are bounded by the window
rather than by the number of writes.

## TRAP

- **A duplicate must be answered, not refused.** A client that retries wants the answer it never
  got; answering "already applied" is a second protocol the client has to know about.
- **The answer has to be the original one.** If the duplicate is answered freshly, the client sees
  two different results for one write and cannot tell which is the truth.
- **The closure that applies a write must not run for a duplicate.** The spec counts the calls:
  a ledger that calls the closure and then discards the result has applied the write twice.
- **A failed write leaves no key.** Remembering a failure would make the retry answer with a
  failure that never applied — and the client would give up on a write that could still succeed.
- **The window is a decision.** Too short and a slow client's retry becomes a second write; too long
  and the memory grows with every write. The spec checks the number the course ships.
- **A key identifies a write, not a request.** Two different requests in one session are two
  different writes, so the key has to depend on the request as well as the session — otherwise the
  second one is swallowed as a duplicate of the first.

## FURTHER

- The HTTP world calls this an *idempotency key* and the payment APIs call it a *deduplication
  key*; the window is the same decision in both, and both are the same lesson: a retry needs an
  identity that says "this is the same request, please".
- `relay/2.2` taught delivery idempotency on the *server* side (a delivery id the receiver
  remembers); this step is the *client* side of the same idea, and the two halves together are what
  makes at-least-once delivery safe to build on.
- `5.11` gives the client an SDK, and the SDK's write method is this step's `Session::key_for` plus
  a retry loop: the SDK's contract is "you may call this twice, and the store will apply it once".
