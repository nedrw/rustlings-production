# The wire is numbers, not names

## WHY

A protobuf message on the wire is a list of `(number, value)` pairs. The name exists in the `.proto`
file, in the generated code and in the documentation — never in the bytes. Once that is clear, what
a change means follows by itself:

- **renaming a field is compatible** — the wire never carried the name, and a client built against
  the old schema is reading the same number;
- **a new number is compatible** — an old reader skips a number it does not know;
- **removing a number breaks a client that still sends it**, and **reusing** a number with another
  type is worse: the old client's bytes are now parsed as the new type, silently, with no error
  anywhere.

This is why `.proto` files carry `reserved 3, 5;` — a retired number is not handed out again, and
the compatibility check is the tool that tells you when you tried.

## TASK

The scaffold put `src/lib.rs` in place with the message types; `wire` is the stub.

- **[`wire`]** — every breaking difference between the old and the new message, by number and
  sorted: [`Breaking::NumberRemoved`] for a number that is gone, [`Breaking::NumberReused`] for one
  whose type changed.
- **A number that moved is a removal.** The old number is gone (clients send it) and the new one is
  simply new; the pair is not a "rename".

## DONE WHEN

- `kiln run rpc/8.1-field-numbers` — the spec passes
- `kiln check rpc/8.1-field-numbers` — every must gate is green
- renaming `status` to `state` is compatible; changing `count` from number to text is not

## TRAP

1. **Comparing by name.** The intuitive diff (`old.name != new.name`) reports every rename as a
   break and misses a number that changed type under a stable name — both directions wrong, and the
   second one is the dangerous one.
2. **A moved number reported as a rename.** `(2, "status") → (9, "status")` is a removed number `2`
   and a new number `9`; calling it compatible leaves clients sending `2` into nothing.
3. **Comparing only the old side.** A new field on a *new* number is fine, but a new field on a
   *retired* number is not — the second loop (new numbers that collide with a removed one) is where
   `reserved` earns its keep.
4. **Returning a boolean.** "Is this compatible" hides which numbers broke; the reviewer is editing
   a `.proto` and needs the list.
