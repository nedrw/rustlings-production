# A stream has a window, not a buffer

## WHY

Server streaming reads like "produce the items" and is really "produce as many items as the client
has room for". The room is the flow-control window: items sent and not yet acknowledged are in
flight, and the sender stops at the window. A producer that keeps sending past it is not streaming,
it is buffering the consumer's memory on the producer's terms — the unbounded queue of step 2.14,
one layer down and harder to see, because the API looks like a `for` loop.

The window also makes the failure modes honest: a slow consumer is visible as a full window (and
the server waits), not as a growing heap and an eventual `OOM` that looks like a leak.

## TASK

The scaffold added `src/stream.rs` and its `pub mod stream;` line. `new`, `in_flight` and `ack` are
given; `send` is the stub.

- **[`Stream::send`]** — the next item when fewer than `window` items are in flight; `None` when the
  window is full or the items are exhausted.
- **A full window is backpressure, not the end**: the caller acknowledges and calls again.

## TRAP

1. **Ignoring the window.** `self.items.get(self.sent)` without the `in_flight` check sends
   everything and buffers the consumer's memory — the spec's *"the window was exceeded"* is the
   assertion.
2. **Treating `None` as the end of the stream.** The caller stops asking; the client has received a
   prefix and believes it is the whole answer. The window reopening is the same `send` call.
3. **Decrementing the window on send and never on ack.** The stream stalls after one window.
4. **An ack larger than what was sent.** Clamping is given (`ack` can exceed `sent` when a client
   acknowledges in batches); the exercise must not double-count it as in-flight.
