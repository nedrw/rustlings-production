# Time is a dependency: inject the clock and let the compiler refuse the rest

## WHY

Every decision this engine makes is a comparison against an instant. Is this job due? Has this lease
lapsed? Is that worker still alive? Today each of those questions is answered by reading the
operating system's wall clock — at seven call sites in one store and five in the other — and that is
exactly what makes the interesting half of this engine impossible to test and unreliable in
production.

The testing half is easy to see: a suite that cannot move time can only *wait* to watch a lease
expire or a job become due, so it is slow on a good day and flaky on a bad one, and the flakiness
lands on whoever runs it on a loaded machine.

The production half is worse. If two workers read two wall clocks, "the lease has expired" is an
opinion rather than a fact, and the difference between those clocks — a container with drift, a
virtual machine that was paused, a clock stepped by NTP — becomes duplicated work or a job stuck
until somebody notices. One process stamps the row; another decides it is abandoned; the only clock
they can both be talking about is one they were handed.

## TASK

- The engine gets a `Clock` port: one method, `now()`, answering a wall-clock instant in UTC, and a
  `SystemClock` implementation that is what a process uses when nobody says otherwise.
- Both stores take the clock they are built with (`MemoryStore::with_clock`, `PostgresStore::with_clock`),
  the way they already take their lease — the constructor is the injection point, so no signature the
  earlier steps pinned has to move.
- **No store may read the wall clock itself.** The project's `clippy.toml` refuses `chrono::Utc::now`,
  `chrono::Local::now` and `std::time::SystemTime::now` for library code, and `clippy@3` turns that
  into an error. `SystemClock` is the one place that carries an `#[allow]` with its reason.
- Keep the monotonic clock where it belongs: measuring how long something took is a different
  question (`std::time::Instant`), and the daemon's own shutdown deadline stays on it.

## DONE WHEN

- `kiln run jobq/3.8-clock-injection` — the five spec cases pass.
- `kiln check jobq/3.8-clock-injection` — every must gate is green, including `clippy@3` (which is
  what enforces the ban list) and `semver@baseline` (the public surface only gained names).
- `cargo clippy --lib -- -D clippy::disallowed_methods` in `app/jobq` — clean.

## TRAP

1. Injecting the clock only where the test needs it — the lease stamp in one store keeps calling
   `Utc::now()` and the suite still passes, because the case that would catch it (an expiry the clock
   has to reach) is the one nobody wrote. Both stores, every instant.
2. Replacing `std::time::Instant` with the new port for *durations* — the shutdown deadline then
   moves backwards whenever the wall clock does, and a process that is asked to stop takes an hour.
   Wall clock for instants, monotonic for intervals.
3. Passing `DateTime<Utc>` around as the injected clock ("now" as a value) — then every call site has
   to be handed a fresh instant, and the store's own comparisons drift apart within one operation.
   The port answers *when asked*.
4. Adding `#[allow(clippy::disallowed_methods)]` to a store module — the ban list is the enforcement
   mechanism, and an allow that is not `SystemClock` is the rule being deleted one file at a time.
5. Keeping the default clock implicit but *wrong*: `MemoryStore::new()` must keep working with no
   clock at all, because every earlier step builds one that way (`jobq/3.1-engine-boundary` and the
   conformance suite both do).

## FURTHER

- `chrono::DateTime<Utc>` versus `std::time::Instant` — the two kinds of time a program keeps, and
  why the standard library only offers one of them as a wall clock.
- `clippy::disallowed_methods` in the Clippy lints list — the configuration this step's `clippy.toml`
  writes, including how a path is spelled.
- `docs/authoring.md` §7.4 — why the ban applies to library targets (where the engine lives) and not
  to test targets.
- `jobq/3.7-leases-and-recovery` — the lease whose expiry this step moves onto the injected clock;
  without this step, that step's recovery promise is only as good as the clocks involved.
