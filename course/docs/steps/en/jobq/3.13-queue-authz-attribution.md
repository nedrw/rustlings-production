# Queues as tenants: quotas, attribution and the noisy neighbour

## RECALL

- `sec/authz-tenant-isolation@design` — `relay/2.16-authz-audit`: the permission model as *data*, one
  layer that asks the matrix instead of a check at the top of every handler, and three refusals with
  three different reasons — `401` for a name nobody issued, `403` for an action, and the same `404`
  a missing row gets for somebody else's row. The rule that sentence encodes is the one this step
  keeps: **a refusal is about an action, never about a row**, because a `403` for a row that exists
  has answered the question the caller was fishing for. What is new here is what the model is about:
  a queue is not a route, and it is a *thing with work in it* that somebody has to be answerable
  for.
- `sched/fairness@design` — `jobq/3.9-priority-fairness`: the claim is where a resource is taken,
  the policy is what decides how much one queue may hold, and work over the cap stays queued with
  its attempts untouched. That policy is the knob this step turns for a *tenant*; there is no second
  policy here, and the body says which knob it used and why.
- `obs/metrics-slo@apply` — `relay/2.18-delivery-metrics`: a service's numbers are per *tenant*,
  because "which tenant is slow" is the question a shared service is actually asked, and a metric is
  a decision about what somebody will act on. The numbers this step keeps are the raw counts that
  decision is made from — read through the engine, per queue and per tenant, rather than scraped
  out of a log.

## DELTA

**The matrix says whether, the counters say how much, and an operator needs the second to act.**
`relay/2.16` can answer "may this tenant do this" and it cannot answer "who consumed the worker
pool last night". Those are different questions, and the difference is what this step adds:

- **a queue belongs to a tenant, and the model says what everybody else may do with it.** An owner
  and a list of grants over three actions — `submit`, `claim`, `administer` — where a wider grant
  covers a narrower one. Two properties fall out of writing the model as data: a grant for *one
  tenant reading another tenant's queue* has nowhere to be expressed, and the queue a tenant may see
  is exactly the set of queues the model names it in.
- **a refusal is the same answer a queue nobody declared gives.** That is the T2 lesson, kept where
  it can actually be kept: the filter is in the *queries*, not in a check a caller has to remember.
  A tenant's handle is a value (`Store::scoped`) rather than an argument to every call, so there is
  no path in this engine that asks "who are you" of a request — and a job the handle may not see is
  answered like a job nobody wrote (`Ok(None)` from the port, `NotFound` from the engine).
- **the counters are written by the work, not reconstructed from it.** Five per queue — `submitted`,
  `claimed`, and the three ways an attempt ends (`succeeded`, `failed`, `reclaimed`) — moved in the
  **same transaction as the state change** (`jobq/3.6-transaction-isolation` is the pattern), so a
  write that did not happen cannot be counted. `running` is derived from them rather than stored:
  the jobs holding a worker right now, which is the "who consumed the pool" number, and the number
  the tenant cap is enforced against.
- **a privileged change is one commit with its row.** Declaring a queue and recording who moved it
  are one transaction, so a change that cannot be recorded is a change that does not happen — the
  access model is the one thing in this engine where a silent change is worse than a refusal.

**The quota is `Policy`'s, one level up.** `jobq/3.9-priority-fairness` caps one *queue*;
`Policy::with_tenant_cap` caps one *tenant*, counted over the queues that tenant owns, in the same
place and with the same rule: a claim that finds no room takes nothing, the work stays queued, and
its attempts are untouched. What makes it a knob on that policy rather than a second policy is that
it is the same number the counters publish, used as a ceiling — the operator reads `running` per
queue, and the tenant's `running` is what the cap holds down. The loud tenant is not one queue; it is
one *tenant with several of them*, and a pool shared between tenants needs the ceiling on the second.

## TASK

The scaffold added three modules — all of them inert until you declare them — and a stub for
`migrations/0005_queues_and_usage.sql`.

### `src/engine/tenant.rs`, `src/engine/authz.rs`, `src/engine/usage.rs`

- a **tenant** is a name the engine can write down, held to the same alphabet and bound a queue name
  is (`Tenant::parse`), and it is not a credential: nothing authenticates anybody here, and the
  caller is whoever built the handle;
- the **model** is a value: `QueueDeclaration` (a queue, an owner, grants) with the rule written as
  two functions — `visible_to` (is this queue a queue *for* this tenant) and `allows` (may it do
  this) — so that a store asks one thing rather than comparing owners itself. `QueueAudit` is one
  line of the trail;
- the **numbers** are `Usage` (five counts and the derived `running`) and `QueueUsage` (one line of
  a report).

### `src/engine/error.rs`

Two **new variants**, not fields on existing ones (`jobq/3.3-library-errors` pins the shapes this
enum already has): `NoQueue { queue }` — the answer for a queue nobody declared, and the same answer
for a queue this caller may not see — and `Forbidden { action }`, which names the action and nothing
else, because the same variant answers a case where naming the queue would leak what the caller may
not see. Give both a row in `exit_code`.

### `src/engine/policy.rs`

`with_tenant_cap` and `max_in_flight_per_tenant`, defaulting to `None`: a deployment asks for the
cap, exactly as it asks for the per-queue one.

### `src/engine/store/`

The four new port methods are where this step's decisions live, and their documentation is the
contract the spec reads:

- `declare_queue(&QueueDeclaration)` — a scoped handle declares a queue for its own tenant and keeps
  an existing queue's owner where it is (a transfer is the operator's door, not a delegate's); a
  queue that exists needs `Administer`; the model and its audit line commit together;
- `scoped(&Tenant) -> Box<dyn Store>` — the handle a tenant holds. The filter is in every statement
  a scoped store runs: `enqueue`/`claim` (which answer `NoQueue`/`Forbidden`), the job reads and
  settles (`Ok(None)`/`NotFound`), the trail, the maintenance calls (a scope renews, hands back and
  reclaims inside its own queues) and the two reports;
- `usage()` — the numbers, per queue, in queue order: a scoped store answers for the queues its
  tenant *owns* (zeros included, so a queue an operator just created is visible before it is used),
  an unscoped one for every queue it could be asked about;
- `audit(limit)` — the privileged decisions about the queues this handle can see, newest first.

`src/engine/scheduler.rs` gets the operator's three doors (`declare_queue`, `usage`, `audit`) and
`scoped`, which is what a deployment hands each tenant's worker: the worker already holds an
`Arc<dyn Store>` (`jobq/3.7-leases-and-recovery`), so one process per tenant is one worker with one
handle, and there is no path in the engine that reads an identity out of a request.

### `migrations/0005_queues_and_usage.sql`

The file is yours, and the stub names what it has to hold: ownership, the grants, the counters, and
the trail. Two of its decisions are worth the paragraphs the stub gives them: the grants table is
where the action alphabet is closed (a `check`, so a typo lands in the migration rather than in a
query that matches nothing), and the *rule* — owner holds everything, a grant holds what it names,
`administer` covers the narrower two — belongs in one place with a name (`queue_permissions`),
because every statement in the durable backend asks it. The counters have **no** foreign key to the
ownership table: they are a fact about traffic, and ownership is a fact about who is answerable.

### What deliberately does not change

`claim`'s signature, the order it hands jobs out in, and every promise `jobq/3.5`–`3.12` certified:
an unscoped store answers exactly as it did before this step (which is what lets the earlier specs,
and every project that never declares a queue, keep working), and `Engine`'s existing methods are
untouched.

## TRAP

1. **A `403` for somebody else's queue.** The friendly answer is to say "that is not yours"; the
   specification compares the bytes a tenant gets *before* the queue exists with the bytes it gets
   after, and a refusal that changed would have answered the existence question. The queue-level
   refusal is `NoQueue`, and it is the same variant with the same message a queue nobody declared
   gets.
2. **An ownership check in Rust on the durable backend.** Reading the owner and comparing in the
   caller looks the same until two writers race: the *row-level* filters have to be in the queries
   (`get`, the settles, the trail), because the check that produces `NotFound` for a foreign job is
   the query that would have found it. The permission questions a queue-level door asks are the one
   exception, and the port's documentation says why.
3. **A tenant as a parameter of the store's methods.** Tempting, and it is a tenant a caller can get
   wrong: `scoped` is a handle, so the filter cannot be forgotten by a call site — and a store whose
   methods took an identity would be a store whose access model depends on every caller passing the
   right one.
4. **A counter written outside the transaction that changed the row.** `complete` that commits and
   then bumps `succeeded` counts attempts that were refused: the scripted case completes a job twice
   and asserts the five numbers, and a counter on the refusal path fails it with one extra count.
   The same shape as the trail of `jobq/3.6-transaction-isolation`, and for the same reason.
5. **A counter that is counted in the engine instead of in the store.** A map in the worker looks
   equivalent until a second process runs: the numbers an operator reads have to be the store's,
   because the store is what survives the process that made them.
6. **`running` as a sixth column.** Storing it means a number that can disagree with the other five
   — and the only honest answer to "who consumed the pool" would then be two answers. It is derived
   (`claimed` minus the three ways an attempt can end), and the invariant is asserted in the
   workload case.
7. **An audit row written after the change.** The row is what makes a change explainable, so a
   change this backend cannot record must not happen: the case that drops the trail table and asks
   for a declaration expects the declaration to fail *and* the model to be where it was. Writing the
   row afterwards passes the first half and fails the second.
8. **A per-tenant quota invented beside the policy.** Then there are two places that decide how much
   one queue may run, they will disagree, and `jobq/3.9-priority-fairness`'s promise ("over the cap
   the work waits, its attempts untouched") is kept by one of them and not the other. The knob for a
   tenant is the same knob counted one level up.

## FURTHER

- `relay/2.16-authz-audit` — the matrix, the three refusals, and the trail written before the
  action: the design half of this step, for a service's routes.
- `jobq/3.9-priority-fairness` — the cap this step counts over a tenant rather than a queue, and the
  argument for why work over a cap waits rather than fails.
- [PostgreSQL: `CREATE VIEW`](https://www.postgresql.org/docs/17/sql-createview.html) — why the
  access rule is a view here: one place every statement can read, instead of a join five statements
  have to keep identical.
- [PostgreSQL: row security policies](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) — the
  mechanism this project did *not* choose, and what it buys (the database enforces the filter even
  for a query somebody writes by hand) over what a scoped handle buys (the engine cannot ask the
  wrong question at all).
- `jobq/3.17-error-budget-alerts` — where these counters become the rate an operator watches, and
  why a rate needs the counts rather than the other way round.
