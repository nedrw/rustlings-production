# Coverage as a policy: the branches that must be walked

## WHY

Every build can print a coverage percentage, and the number it prints is usually the wrong one: a
single figure over a whole crate, dominated by the modules nobody argues about — the wiring, the
adapters that exist so a type can be named, the `main` that turns settings into a store. Code like
that is genuinely covered, and it drowns the module the review is about.

What is left when the percentage is read properly is the half that costs money: the branches nothing
ever walks. An error arm no case triggers leaves every *line* of that function covered and half of
its decisions unexercised, and the compiler cannot tell the difference between that and a suite that
thought about it. Nobody finds out from a dashboard; they find out from a page nobody wrote, because
the work is deciding which places have to be walked and then saying so where it can be reviewed.

This step is that decision, written where the compiler can hold you to it: which places this
project's engine has, which of them a case has to walk, which of them nothing can, and why the
threshold is not a hundred.

## RECALL

- `test/mutation@apply` — `jobq/3.20-mutation-threshold`: what a suite *notices*. The two numbers
  are complements and neither replaces the other — a mutant survives because no case *notices* the
  change, and a branch stays uncovered because no case *reaches* it. A suite can reach every branch
  and notice nothing; it can also notice everything it reaches while a third of the queue's
  decisions were never exercised. **This step does not re-teach the score.** What is new is the
  claim about which places exist, and the threshold that claim is judged by.
- `err/typed-errors@design` — `jobq/3.3-library-errors`: the error branches are the ones the
  inventory is mostly about, because a typed error is a decision (`Err` arm after `Err` arm) and
  the arms nobody writes a case for are exactly the ones production meets first.

## DELTA

Four names, and each one answers a question a percentage cannot:

- **`Kind`** — a line and a branch are two different questions about the same code. Only the second
  describes the suite.
- **`Inventory`** — the claim. It is about *one module*, and it refuses a place from somewhere else
  rather than growing into a library-wide table. That refusal is the whole reason this step exists:
  a percentage over a library is a percentage about `main`.
- **`Exempt` and the ceiling** — some branches are there for a compiler or a panic path, and no case
  can take them. They stay in the inventory with the reason somebody wrote down, they never count
  against a run, and `Inventory::ceiling` is what a threshold has to fit under.
- **`Walked` and the share** — a run is a *set* of places, not a count of executions, and a run of
  one module measured against another module's inventory answers `Foreign` instead of a number.

The three verdicts are `jobq/3.20-mutation-threshold`'s, deliberately: met, missed, and *not
answerable*. Here the missing evidence is an inventory with nothing of that kind to walk, there it
was a run that judged too few mutants — and in both cases a two-valued gate would have to call "I
can't tell" a failure.

## TASK

The scaffold added one module and one page, and **nothing declares the module yet**: wiring
`src/engine/mod.rs` the way `jobq/3.19-property-invariants` wired `walk` is your first decision, and
until it is made the spec does not compile.

### `Site`, `Kind` and `Walked` — what a number counts

A place is a file, a line and which of the two questions that line answers; a run is the *set* of
places it reached. Visiting the same place twice is one place, because a loop is one branch taken a
thousand times and a share that counted executions would be a share about the test data. The line and
the branch on it are different places, which is why a suite reporting a single percentage has
answered the easier question.

### `Inventory` and `Foreign` — the claim, about one module

The inventory records the places a case has to walk and the places nothing can. Both recorders
refuse a place that is not under the inventory's scope, and a run (`Walked`) refuses it too: the
arithmetic below answers `Foreign` — not a percentage — the moment the two sides disagree about what
they describe. `src/engine` is a module, not a string prefix, so `src/engineers/queue.rs` is
somewhere else.

### `ceiling`, `share` and the threshold — the arithmetic of a decision

The denominator is *every* place of that kind the module has, exempt ones included; only the
walkable ones can be counted as covered. So a perfect run scores `ceiling` — the highest share the
inventory allows — and not a hundred, and `CoveragePolicy::is_satisfiable` is the review's question:
is the rule we wrote down one anybody can meet? It is deliberately separate from `judge`, because the
arithmetic is what a build does and this is what a person does once.

### `docs/coverage.md` — the page the policy is written down in

The stub names the scope and the shape and leaves the decisions blank. Fill it in: the threshold and
what it counts, one row per branch a case has to walk with the case that walks it, the branches no
case can reach with the reason for each, and how the number is measured. The spec reads this page and
compares it with `CoveragePolicy::standard()`, so a page that states another threshold is a page that
has stopped being true.

### What deliberately does not change

The engine's own rules, the store port and every earlier suite. What changes is what this project is
willing to say about them.

  both sides, a walk as a set, the share and its empty answer, the ceiling below a hundred, an
  exemption with its reason, the list still to walk, the threshold met at the boundary, and the page
  against the code.
- `kiln check jobq/3.21-coverage-policy` — every must gate is green, `links` included: the page is
  part of the deliverable, and its targets have to resolve.
- `kiln selftest jobq/3.21-coverage-policy --track jobq` — the slow path runs `slow:mutants@80`

  without the LLVM tools the coverage gate answers `⚠ blocked` with the install line
  (`rustup component add llvm-tools-preview`): that is the honest answer rather than a failure, and
  the mutants gate is the one that has to be green.

## TRAP

1. **A percentage over the library.** `cargo llvm-cov` with no argument reports one number about
   everything, and it will be a comfortable one: the modules nobody doubts are covered and they are
   most of the lines. `Inventory::add` refuses a place outside its scope, and `Walked::visit`
   refuses one too, so the arithmetic answers with a `Foreign` naming `src/main.rs` and `src/engine`
   rather than with 78%.
2. **Counting lines and calling them branches.** `if let Some(cap) = policy.max_in_flight_per_queue()
   { … }` with only the `Some` arm ever taken is two covered lines and one uncovered decision. A
   suite that reports the first number reports the half the compiler already told you about.
3. **A threshold of 100 on an inventory that has an exemption.** The ceiling is then whatever the
   walkable places allow — nine of ten branches is 90 — and a policy of 100 fails every run,
   including the perfect one, and the reflex is to argue with the number rather than with the rule.
   `is_satisfiable` is the method that says so before somebody spends a week on it.
4. **An exemption with no reason.** `Inventory::exempt` takes the reason as an argument, because
   the entry a reviewer has to argue with is the one written down; a page of places with no reasons
   starts with "this one was annoying" and ends when the threshold is lowered.
5. **A run of another module quoted as this module's number.** A `Walked` is created with the scope
   it measured, and `share`/`uncovered` refuse a walk of a module the inventory does not describe:
   the number that comes back would otherwise be about the union of two modules, which is the defect
   in 1 with extra steps.
6. **A share that counts executions.** A thousand iterations of a loop is one place. Counting
   *hits* makes a fully covered module look like 400% and makes the number depend on how big the
   test data was, which is how a coverage gate turns into a test of the fixtures.
7. **A page that drifts.** The scope, the threshold and the kind live in the code
   (`POLICY_SCOPE`, `CoveragePolicy::standard()`) and the page states them, so the two are read
   together: the spec compares them, and it is the only thing that can — a coverage tool knows
   nothing about a page.
