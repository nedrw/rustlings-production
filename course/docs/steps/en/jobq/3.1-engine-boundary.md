# Draw the engine boundary: a library the daemon depends on, never the other way

## RECALL

- `repo/workspace-layout@apply` — `mailer/1.1`: one project, one `[workspace]`, `cargo fmt` and
  `cargo clippy` wired before anything else.
- `cfg/layered-config@apply` — `mailer/1.4`: defaults underneath, a file next, the environment on
  top, flags last; `--check-config` prints what the process will actually do and never the secret.
- `obs/structured-logs@apply` — `mailer/1.6`: one subscriber installed once, a run id on the lines
  that matter.
- `http/service-skeleton@apply` and `http/middleware-layering@apply` — `mailer/1.7`, `relay/2.1`:
  this is the third time you build the skeleton of a service, and the first time it is not a service.

## DELTA

Everything you already know about a project skeleton is here, and the *shape of the dependency*
changes. `relay` was a service that happened to have a library; `jobq` is a **library that happens to
have a daemon**. The engine — queues, jobs, states, the store port — has to run with no server, no
config file and no process in the picture, because the thing it is for is somebody else's program:
`jobq` is the engine, `jobqd` is one shell around it, and a later track is allowed to put a
completely different shell around the same engine.

What that costs today is one rule you cannot get from the compiler inside a single package: **the
arrow only points one way**. `src/service/**` may use `crate::engine`; nothing under `src/engine`
may mention `crate::service` or `crate::cli`. The spec checks it by reading the sources, which is
weaker than a second crate would be — and the reason is written down in the spec itself, so a future
author who splits the package knows exactly what to delete.

This step also fixes the port's shape for everything that follows. Traits that the engine holds
behind a reference return boxed futures (`fn claim<'a>(&'a self, …) -> BoxFuture<'a, …>`), not
`async fn`: an `async fn` in a trait is not dyn-compatible (`E0038`), and a worker holds its store
through a reference, not through a type parameter it can name.

## TASK

- Parse a queue name (`1..=64` bytes of `[a-z0-9._-]`) and say what is wrong with the rest.
- Implement the in-memory store: enqueue validates the attempt budget and resolves `run_at`;
  `claim` takes due jobs in order (priority first, then the one due longest, then identity), marks
  them running and counts the attempt; `complete` only settles a job that is running; `fail` records
  the reason and chooses between `queued` and `failed` from the budget; `get` reads one job.
- Let `Engine` be the only door: `submit`, `claim`, `complete`, `fail`, `inspect`, each delegating to
  the store and turning "no row" into `Error::NotFound`.
- Implement the daemon's settings: `Flags::from_args`, and `Config::load` merging defaults, the
  `--config` file, `JOBQ__SECTION__KEY` variables and the flags, with `report()` printing the result
  and redacting the password.
- Install the log subscriber once, and make `serve` open the store, announce `draining`, wait for
  `SIGTERM`/`Ctrl-C` and stop. `jobqd --check-config` has to answer without opening anything.

## DONE WHEN

- `kiln check jobq/3.1-engine-boundary` — every must gate is green (including `clippy@2`, which

## TRAP

1. Counting the attempt when the job *finishes* instead of when it is claimed → a worker that dies
   holding a job returns it with `attempts` unchanged, so the budget never runs out and a poison
   payload loops forever. The spec asserts the count right after `claim`.
2. Returning the job's own copy from `claim` without flipping the stored state → the same job comes
   back to the next worker: the spec's two-worker case finds the duplicate by comparing identities.
3. Making `Queue` a bare `String` alias → `queue_typo` reaches the database. The name is a key in a
   dashboard, a label in a metric and a column in a table, so the constructor is the only door.
4. Putting the engine's logic in `src/service` because the daemon is the only caller today → the
   spec's source check fails, and the next shell (a CLI, another service, a test) has to copy the
   daemon to get a queue.
5. Printing the configuration with the connection string in it → an operator pastes the report into
   a ticket and the password goes with it. `report()` redacts; `mailer/1.4-layered-config` already
   made this promise and this step keeps it.
