# The CLI is an interface: subcommands, exit codes, machine-readable output

## WHY

A command line is an API with no types. Nothing a script does with `jobqc` is checked by the
compiler: the exit codes, which stream an answer goes to, the spelling of a flag, whether the
output is one JSON document or a log line that happens to contain JSON — all of it lives in a
convention that exists only in the head of whoever wrote the script. Get one of those subtly wrong
and nothing breaks today. What breaks is the *customer*: the cron job that retries a typo for ever,
the dashboard that silently reads zero, the deploy script that treats "already finished" as "the
store is down" and pages somebody at 03:00.

The failure mode is always the same shape, and it is why this step is a contract rather than a
feature: a tool that *looks* machine-readable is worse than one that plainly is not, because the
script built on it stops checking. `--json` that prints a warning first, a failure that exits `0`
after printing an error, a usage page on stdout — each of them turns a real problem into a parse
error three systems away.

## RECALL

- `err/typed-errors@design` — `jobq/3.3-library-errors`: **where the exit-code table came from.**
  That step gave `Error` the two classifiers a caller acts on, `is_retryable` and `exit_code`, and
  pinned the numbers the two binaries already used. This step inherits the table rather than
  inventing one: `jobqc` never computes a code, it asks the failure.
- `domain/state-machine@apply` — `jobq/3.14-job-state-machine`: the four state names, and the
  refusal `JobState::parse` gives for a name the model does not have. `--state failed` is only an
  honest filter because a typo is a usage error instead of a query that matches nothing and looks
  like good news.
- `sec/authz-tenant-isolation@operate` — `jobq/3.13-queue-authz-attribution`: the five counters per
  queue. They are why `usage` is a subcommand at all — the number an operator acts on has to be
  readable by a person *and* by the script that pages them, and before this step the only way to
  get it was to write a program against the library.
- `api/library-design@apply` — `jobq/3.2-public-api-baseline`: the library's surface is its
  re-exports, and the binary has no grammar of its own. That is the boundary
  `jobq/3.1-engine-boundary` drew, and this step is where a second binary has to keep it.

## DELTA

**Nothing here is about queueing.** The store, the leases, the schedule and the counters all
already work; what this step adds is that their answers get a *shape a program can consume*, and
the shape is four decisions:

- **stdout is the answer, stderr is the diagnosis.** On success stdout holds the answer and stderr
  is empty; on failure stdout is **empty** and stderr holds one sentence. The bytes are decided in
  one place — `Outcome` is the value the library answers with, and the binary only writes it —
  because "remember not to print that" is not a rule, it is a hope.
- **one exit code per failure class.** `0` answered, `2` the call was wrong, `3` the thing asked
  about is not there, `4` the store refused, `1` this deployment is broken. The classes come from
  `jobq/3.3`; what is new is that every *caller mistake* is answered before a store is opened, so
  `2` means the script's problem wherever the deployment happens to be.
- **`--json` is a format, not a second command.** It changes what the answer looks like and nothing
  else: the exit code and the diagnosis are identical with and without it, and an empty answer is
  `[]` rather than nothing at all.
- **nothing prompts.** Every input arrives as a flag or on standard input, a call that is missing
  one names what it is missing, and a command that was not asked to read standard input never
  touches it — a tool that blocked on a terminal would be a tool that hangs the pipeline it was
  meant to feed.

One thing the engine did not have, and it is the honest cost of the step: **`Store::list`**. A tool
that answers "what is in this queue" has to be able to *ask*, and the alternative — a command line
that builds its own query — is a command line that reaches past the engine into whatever backend
the deployment happens to run. The port gains one method, the order it answers in is the order
`claim` already documents, and the filter carries a limit because a queue has no natural end.

## TASK

The scaffold added `src/cli/mod.rs` (the usage text, the `Outcome` shape, and the `run` signature
with a `todo!()`) and `src/bin/jobqc.rs` (the shell, complete). **Nothing declares the module yet**:
`pub mod cli;` in `src/lib.rs` is your first line, and until it is there the spec does not compile —
which is the step saying what it wants.

### `src/cli/mod.rs` — the grammar and the two streams

Everything in the table below has to be true, and the spec runs the real binary to check it:

| command | stdout (text) | stdout (`--json`) | code |
| --- | --- | --- | --- |
| `jobqc`, `jobqc --help`, `jobqc -h`, `jobqc help` | the usage text | the usage text | 0 |
| `jobqc --version` | `jobqc <version>` | — | 0 |
| `jobqc submit --queue Q --payload P` | `queued <id>` | `{"id":"<id>"}` | 0 |
| `jobqc submit --queue Q --stdin` | `queued <id>` | `{"id":"<id>"}` | 0 |
| `jobqc inspect <ID>` | `<id> <queue> <state> <payload>` | `{"id":…,"queue":…,"state":…,"payload":…}` | 0 |
| `jobqc list [--queue Q] [--state S] [--limit N]` | one such line per job | `[{…},…]` | 0 |
| `jobqc usage` | `<queue> submitted=… claimed=… succeeded=… failed=… reclaimed=… running=…` | `[{"queue":…,…}]` | 0 |
| anything the caller got wrong | *empty* | *empty* | 2 |
| a job or a queue that is not there | *empty* | *empty* | 3 |
| a store that refused | *empty* | *empty* | 4 |
| an environment that is broken | *empty* | *empty* | 1 |

Four details in that table are the ones that get argued rather than typed:

- **the payload is a JSON value, not a string of JSON.** `jq '.payload.to'` has to work without
  `fromjson` first, and in the text shape the payload is compact JSON (`serde_json::Value`'s own
  `Display`) so that a payload containing a newline cannot turn one job into two lines;
- **the fields are in the order written above**, in both shapes. JSON does not define an order and a
  golden test that reorders its fields at every refactor is a test nobody reads;
- **an empty list is `[]`**, and `list --limit 1` is a page of one: a script that has to special-case
  "no output" is a script that gets it wrong once and stops trusting the tool;
- **`--json` may appear before or after the subcommand**, because scripts and people put it in
  different places, and a tool whose `--help` has to explain which is a tool with a worse interface
  than the one it replaced.

### `src/engine/store/` — one read, and one pointer

`Store::list(&JobFilter)` is the new port method: the jobs this handle can see, in the order
`claim` documents (priority, then the one due longest, then identity), bounded by the filter's
limit, with the jobs a scope may not see simply absent — the rule `get` and `events` already
follow. `JobFilter` is the three questions as one value (`--queue`, `--state`, `--limit`), with
`DEFAULT_LIST_LIMIT` as the page a caller who did not ask for one gets. Both backends implement it:
a predicate over the map in memory, a `where` clause plus `order by` in SQL.

`impl Store for Arc<T>` is the other half, and it is what the *shells* need: the daemon and `jobqc`
choose a backend at runtime and hold it as an `Arc<dyn Store>`, while `Engine<S>` is generic over
the port. One forwarding impl (and `Sealed` for the pointer) is the whole cost of choosing your
store from your configuration rather than from your source code.

### `src/service/mod.rs` — `open_store` becomes public

`jobqc` talks to the same queue the daemon drains, and the only way for that to be true rather than
intended is for both of them to build their store from the same settings in the same place. It also
does **not** migrate: a tool that wrote on every read would need a writable replica and would take
a lock to answer a question.

### What deliberately does not change

`jobqd`'s flags, its `--check-config` report and its `draining` line (`jobq/3.1`), the settle
refusals and their classes (`jobq/3.7`), every promise `jobq/3.5`–`3.14` certified, and the
signature of everything the port already had: a method is *added* to a sealed trait, which is the
one way a port may grow.

## TRAP

1. **The usage text on stdout after a bad argument.** It is the friendliest thing to print and it
   is what `$?`-blind scripts choke on: a pipeline that expected a document gets a usage page. Every
   failure in the spec asserts stdout is *empty*, not merely that stderr was used.
2. **`--json` as a second code path.** Two paths for one command drift, and the drift is always in
   the failure handling — the JSON branch that decides "I could not serialise it, exit 1". The spec
   runs every failing call twice, with and without `--json`, and compares both the code and the
   diagnosis.
3. **A payload escaped by hand.** `format!("{{\"payload\":\"{payload}\"}}")` is machine-readable
   until the first quote inside a payload, and then it is a parse error in somebody else's process.
   The end-to-end case submits a payload with quotes, backslashes and newlines and reads it back as
   a *value*.
4. **A tool that reads standard input when it was not asked to.** `submit` without `--stdin` that
   reads stdin blocks for ever on a terminal — and a hang is the one failure a CI script cannot
   see. The payload is read only for `--stdin`, and the spec gives every other run `/dev/null`.
5. **A second place that opens a database.** `PgPoolOptions::connect` in the binary works until the
   CLI's lease, policy or feature set differs from the daemon's, and then two processes are draining
   one queue with two sets of rules. The tool takes `open_store`'s answer.
6. **Migrating on every command.** A `list` that runs the migrations is a write on a read: it takes
   a lock, needs a writable replica, and turns a read-only deployment into a broken one. The
   end-to-end case prepares the schema through the library and expects `jobqc` to find it ready.
7. **A list with no bound.** `select * from jobs` behind `jobqc list` is a tool that works until the
   queue is deep, and then it is the outage. The filter carries a limit, the CLI's default page is
   100, and `--limit` is a number rather than a hope.
8. **A filter compared as text in the tool.** `--state Queued` read with a string comparison matches
   nothing and the answer is `[]` — which is exactly what "no failed jobs" looks like. The state is
   parsed by the model (`jobq/3.14`), so a name it does not have is a usage error naming the four it
   does.

## FURTHER

- [Command Line Interface Guidelines](https://clig.dev/) — the discipline this step argues, written
  down for humans: exit codes, the two streams, `--json`, and why a prompt is a bug.
- [POSIX: exit status](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) —
  why the codes stop at 125: everything above is a shell's own (`126`, `127`, `128+n`).
- `jobq/3.3-library-errors` — the table `jobqc` reads rather than recreates, and the reason
  `--json` cannot change a code.
- `jobq/3.26-dlq-cli` — where this grammar grows: the commands that act on a dead letter, under the
  same four rules.
- `jobq/3.13-queue-authz-attribution` — the counters `usage` prints, and the scoped handle a
  deployment hands each tenant: a command line reads the operator's door, and a flag that named a
  tenant would be an identity read out of a request.
