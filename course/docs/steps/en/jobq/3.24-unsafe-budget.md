# An unsafe budget: deny by default, document every exception

## RECALL

- `unsafe/budget@aware` — `relay/2.21-supply-policy`: the policy, and what it costs. That step wrote
  `#![forbid(unsafe_code)]` at **each** crate root, because an attribute in one crate says nothing
  about the other, and it named the two things the attribute does *not* cover: a dependency's
  `unsafe` is somebody else's code, and spending the budget deliberately costs a written reason and
  an `#[allow]` a reviewer can see. **This step is the `apply` half of that slot**, and the sentence
  it adds is the budget: a number, measured from inside the project, that a gate compares against the
  course's copy.
- `api/library-design@apply` — `jobq/3.2-public-api-baseline`: the engine's surface is what
  `src/engine/mod.rs` re-exports and nothing else, so a new module is not public until it is listed
  there. The audit below is part of that surface — a caller can run the crate's policy over any
  sources — and it is documented and tested like the rest of the engine.
- `perf/bench-budget@apply` — `jobq/3.22-bench-budget`: the shape of a budget built out of counts
  rather than clocks, and the one this step's harness follows. This step's counts are smaller and its
  baseline is three zeros, and the reason to build it the same way is the same reason: a number a
  loaded machine answers differently is a number nobody keeps.

## DELTA

Four decisions separate this from `relay/2.21`:

- **the budget is a number, and the project measures it itself.** `unsafe_occurrences`,
  `undocumented_max` and `unguarded_max` are the three facts `kiln`'s `unsafe-budget@0` gate reads
  from outside the crate — uses, reasons, policy — as the crate's own audit reports them. The gate
  holds them to the course's baseline (`course/tracks/jobq/budget/3.24-unsafe-budget.toml`), so zero
  is a decision somebody wrote down rather than a sentence in a review, and a tree that spends the
  budget is told how much it spent.
- **a comment is not a use, and neither is a literal.** The count is the *word* in code. That sounds
  like a detail until the module is written: the module below mentions the keyword fifteen times —
  every one of them in a comment or in the string that spells the word — and the crate's production
  code uses it zero times, so a scan that read whole lines would report the explanation of the rule as
  a use of it. The gate reads the source the same way (its lexer is careful about exactly this) and
  the compiler is the one that refuses the *next* block.
- **the policy comes from the manifest, not from attributes.** `relay/2.21` needed one `forbid` per
  crate root; cargo's lint table denies for every target of the package in one place, so the project
  here has one policy and it is in `Cargo.toml`. Both spellings of a level are cargo's
  (`unsafe_code = "deny"` and `{ level = "deny" }`), `forbid` counts and `warn` does not, and the
  workspace table counts too — a policy read by grepping the wrong one of those is a policy that is
  not there.
- **the refusal is a list, in the order a reader fixes them.** `check` answers the *first* thing
  wrong: the policy, then the reasons, then the number. A crate that does not deny cannot pass on the
  strength of its comments, a bare `// SAFETY:` is not a reason, and going over the budget names the
  count rather than saying "too many".

## TASK

The scaffold added a module and a harness. **Nothing declares the module yet**: wiring
`src/engine/mod.rs` is your first decision, and until it is made neither the spec nor the harness
compiles.

### `BUDGET`, `WINDOW` and the three names — the numbers as content

`BUDGET` is zero and `WINDOW` is three: how many uses the crate allows, and how far above a use its
reason may sit. The three metric names are what the harness prints and what the course's baseline is
written in, in one list (`UNSAFE_METRICS`) read from both sides. The lint the manifest denies is
`unsafe_code` — the lint, not the keyword, which is the difference between a policy and a use of it.

### `Occurrence` and `Audit` — what one file says about itself

An `Occurrence` is a line and whether it has a reason, with the reason carried: a report that only
said `documented: false` sends a reviewer to open the file. An `Audit` is a file, its uses, and the
crate's policy — the policy is the crate's, and it is carried per file because every use is judged
against it. Nothing outside the module can build either one: `audit` is the only constructor, so the
numbers a harness prints are always the numbers a scan produced.

### `audit(file, source, denies_by_default)` — the scan

Three rules, and each one is a case in the spec:

1. **the code of a line is what stands before a `//` and outside a `"…"`.** A comment reaches the
   end of the line; a literal ends at the next unescaped quote. A block comment or a raw string that
   spans lines is read a line at a time — the narrowing is stated in the module's documentation
   rather than hidden, and this crate writes neither;
2. **the count is the word, not the name.** `unsafe_code` is the lint; `unsafe` is the keyword. A
   crate root that carries `#![deny(unsafe_code)]` denies the lint and uses nothing;
3. **tests are not production code.** An item gated by `#[cfg(test)]` is skipped wherever it sits in
   the file and however deeply it nests, and the lines above and below it still count. A test that
   reaches for the keyword is a statement about the test, and a count that included it would push a
   project to write worse ones.

An occurrence is *documented* when the nearest `// SAFETY:` line above it is at most `WINDOW` lines
up **and carries a reason**. A bare marker is not a reason, it does not fall through to an older
comment, and a marker below the block is not above it. What the reason may not be is settled by the
review it is for: it says what would break if the use were wrong.

### `denies_unsafe_code(manifest)` — the policy, from the manifest's text

The lint table is read from a `Cargo.toml`'s text: `[lints.rust]` for the package and
`[workspace.lints.rust]` for the members it carries, each in both cargo spellings of a level, with
`deny` and `forbid` counting and `warn`/`allow` not. A manifest that does not parse answers `false`,
because the honest reading of a policy that cannot be read is that it is not there. The function
takes text rather than a path: reading files is the caller's business, which is what lets the spec
test the policy with fixtures and the harness with the project's own manifest.

### `check(audits, budget)` — the refusal, in the order a reader fixes them

**The policy first** (a crate that does not deny has no rule for the exceptions to be exceptions
*to*), **then the reasons** (a line somebody writes), **then the number** (a block to remove, or a
budget to raise on purpose). Each refusal names the file, and the one that has a line names the line:
"unsafe budget exceeded" sends a reader to grep.

### `counts(audits)` — the lines a harness prints

One line per metric, `jobq-budget <name>=<value>`, and **all three lines always**: the numbers are
the measurement and the refusal is what a reviewer reads, so a run that refuses still prints them.
A missing metric is `blocked` to the gate rather than a failure, and a gate that blocks says nothing
about the crate.

### `Cargo.toml` — where the policy lands

`[lints.rust]` has a marked block in the project's manifest and nothing in it: the deny belongs there
and covers the library and both binaries at once. `unsafe-budget@0` checks it, the spec's last-but-one
case checks the project's own manifest, and the compiler is what makes it a rule rather than a
habit — the next `unsafe { }` under `src/` fails to build until somebody writes an `#[allow]` on
purpose.

### `tests/unsafe_budget.rs` — the harness, which is the course's file

The harness walks the project's own `src/**/*.rs`, reads the project's own `Cargo.toml`, audits each
file and prints the three lines. It is the instrument: a learner editing it is a learner editing the
measurement, and `kiln reset jobq/3.24-unsafe-budget` puts it back. It also asserts that the walk
found something before printing anything, because three zeros from a walk that read no files are not
a measurement.

### What the spec judges

| the case | the claim |
| --- | --- |
| `the_count_is_the_word_in_the_code_and_not_the_text_around_it` | a file of comments, doc comments and literals has no uses; `#![deny(unsafe_code)]` denies the lint and is not a use; the reason text is carried |
| `a_reason_in_the_window_above_is_what_documents_a_use` | four uses at four distances: one line above is documented, `WINDOW` lines above is documented, a bare marker is not, one line too far up is not — and the count of undocumented uses is the number a budget is written in |
| `tests_are_not_production_code` | the two uses around a `#[cfg(test)]` module count and the two inside it (nested one included) do not; a test module does not reach the line above it |
| `the_budget_is_a_number_and_going_over_names_the_count` | `check` answers `Ok(count)` under the budget and `Refused::Over` with the count over it; `BUDGET` is zero; no files is no uses |
| `the_refusals_come_in_the_order_a_reader_fixes_them` | one tree that breaks all three rules is refused for the policy first, then for the reason, then for the number |
| `the_policy_is_the_manifest_and_both_spellings_say_it` | both spellings of the level, the workspace table, `forbid` counting, `warn`/`allow` not, and a manifest that does not parse |
| `the_crate_holds_its_own_budget` | the project's own manifest denies the lint, and its own production code has no use in it — the walk is over `src/`, and the file with the most to say about the keyword is this step's own module |
| `the_report_is_the_three_facts_a_harness_prints` | the three lines, the names in one list, an unguarded file counted by the third number, and all three lines printed for nothing at all |

## DONE WHEN

- `kiln run jobq/3.24-unsafe-budget` — the eight cases pass: the count in code rather than in text,
  the window, the tests, the budget, the refusal order, the two spellings of the policy, the crate's
  own numbers, and the lines a harness prints.
- `kiln check jobq/3.24-unsafe-budget` — every must gate is green. The one to read is
  `unsafe-budget@0`: `0 unsafe occurrence(s) in 37 production file(s), each with a // SAFETY: note,
  and unsafe_code is denied in .../Cargo.toml`. The gate asks for the marker and this module asks for
  the reason after it, which is the stricter of the two readings and the one that matters on a day the
  budget is not zero — a bare marker passes the gate's note check while the harness reports one
  undocumented use.
- `cargo test -p jobq --test unsafe_budget -- --nocapture` prints `jobq-budget
  unsafe_occurrences=0`, `jobq-budget undocumented_max=0` and `jobq-budget unguarded_max=0`.
- `kiln selftest jobq/3.24-unsafe-budget --track jobq` — the slow path. The lines to read are
  `3 metric(s) within ±10% of the course baseline: unsafe_occurrences 0, undocumented_max 0,
  unguarded_max 0`, and `slow:?coverage@80` answering `⚠ blocked` on a machine without
  `llvm-tools-preview` — the honest answer there, not a failure of this step.
- `cargo check -p jobq` fails if you put an `unsafe { }` block anywhere under `src/`, and the
  failure names the lint that refused it. Add the `#[allow]` a reviewer would ask for and the tree
  builds again — and the harness then prints `unsafe_occurrences=1`, which is the gate telling you
  how much you spent.

## TRAP

1. **Counting the file rather than the code.** This step's own module mentions the keyword fifteen
   times — fourteen of them in its documentation and one in the constant that spells the word it
   counts — and the crate's production code uses it zero times. A scan that reads whole lines reports
   fifteen uses in a crate that has none, and the first thing it flags is the file that explains the
   rule.
2. **A `//` cut without knowing what a literal is.** `let text = "unsafe // not a comment";` is a
   literal that contains a comment marker, and cutting the line at the first `//` is the shorter
   version of the same mistake in the other direction: it hides everything after the marker,
   including a use. The code of a line is what stands before a `//` *outside a literal*, and the
   spec's fixture has both halves.
3. **A bare `// SAFETY:`.** It looks like evidence and says nothing, and it is worse than no comment:
   a reviewer who greps for the marker finds it and stops looking. The same goes for one that borrows
   its reason from four lines up — the line a reader looks at first is the one immediately above the
   block.
4. **A note *below* the block.** `unsafe { … }` followed by `// SAFETY: …` is a comment about code
   that has already been written, and the answer for the next reader is `git log`. The window is
   above, and the gate reads the same three lines in the same direction.
5. **Counting the tests.** An `unsafe` in a `#[cfg(test)]` module is a different statement from one
   in the library, and a count that included it would push a project to write worse tests — the same
   split `clippy` makes when it decides what a lint applies to. The region starts where the gated
   item opens and ends where its block does, nested modules included.
6. **`unsafe_code` counted as a use.** The lint's name appears in the manifest, in the module's own
   metrics and in the attribute a crate root may carry (`#![deny(unsafe_code)]`); a policy that
   counted as the thing it forbids would never be satisfied.
7. **One attribute on one crate root.** The trap `relay/2.21` named stays a trap in principle and
   changes shape here: cargo's lint table denies for every target of the package, so the project has
   one policy — and a `lib.rs`-only `#![forbid]` in a project with two binaries is a budget with two
   holes in it. The project's answer is the manifest's table plus the crate's own audit reading it.
8. **A policy read by grepping.** `unsafe_code = "deny"` and `unsafe_code = { level = "deny" }` are
   both cargo, `forbid` is a denial and `warn` is not, and the workspace's table counts for the
   members it carries. A scan looking for one string finds none of the others, and the answer it
   gives is *not denied* — which is the right refusal for the wrong reason.
9. **A `_max` metric read as a target.** `undocumented_max` and `unguarded_max` are upper bounds: a
   file that stopped being unguarded passes, and nobody has to edit the baseline to say so. The
   first number is exact, and a tree that spends the budget moves it in the direction the gate
   reports with a count.
10. **Editing the harness or the baseline instead of the code.** `tests/unsafe_budget.rs` is the
    course's file and `course/tracks/jobq/budget/3.24-unsafe-budget.toml` is the copy the gate reads:
    editing either changes the instrument, not the crate it measures. `kiln reset
    jobq/3.24-unsafe-budget` puts the harness back.
