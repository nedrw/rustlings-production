# Serialisation conflicts and the uniqueness race: retry, or prevent

## RECALL

- `db/unique-as-concurrency@apply` — `mailer/1.11-signup`: a uniqueness rule that two callers can
  break at the same instant belongs in the database, because a check the application performs first
  is a window both of them pass through — and the fix is to *use* the refusal
  (`on conflict … do nothing returning id`) rather than to avoid it. That knowledge transfers
  whole. What is new is that the row being raced is not a user's identity but a line of the job's
  own history, and that the rule has to be expressible in one place before it can live in the
  index.
- `db/transactions@apply` — `mailer/1.17-newsletter`: two writes that must not be half-done go in
  one `begin`/`commit`, and the work that follows the commit happens after it — not inside it.
  Here the pair is a state change and the line that describes it, and the write you are asked to
  *not* put inside the transaction is the one to the network; the isolation level, however, is a
  decision neither of those steps had to make, and it is half of this one.

## DELTA

- **A settle is now two writes, and they are one commit.** `complete` and `fail` change the row
  *and* append a line to `job_events` in one transaction. That trail is what
  `jobq/3.16-dlq-tooling` lists and `jobq/3.17-error-budget-alerts` counts, so a trail that can
  disagree with the row it describes is worse than no trail: an operator reading "failed twice"
  next to a row that says `queued` has two answers and no way to choose.
- **The conflict is a class of its own.** `Error::Conflict` is what the durable backend raises when
  the database refuses a transaction for concurrency — `40001` (a snapshot that lost a row to a
  commit it never saw) and `40P01` (a deadlock the server broke) — and `Error::is_retryable` was
  written in `jobq/3.3-library-errors` precisely so that this step could put a class behind it.
  What is *not* new here is the decision to retry; what is new is that retrying becomes the correct
  response to a class the engine can name, instead of a guess about a message.
- **The isolation level is the decision, and it is not free.** At PostgreSQL's default level the
  loser of the race *waits*, re-reads the row, and either succeeds or finds nothing to do —
  silently, with no way for the engine to tell "somebody else settled it" from "the row was never
  running". At `repeatable read` the same write is a refusal the caller can act on. You are trading
  a wait for an answer you can read, and the price is that somebody has to handle the refusal.
- **The retry has a bound, and it reports what it cost.** `retry` is a small loop over a closure:
  the closure is the transaction (so the caller writes it once), the predicate is the engine's own
  classification, and the answer carries how many attempts it took. There is no backoff yet — a
  wait needs a clock this crate does not own until `jobq/3.8-clock-injection` gives it one — and
  the bound is therefore the whole of the policy.

## TASK

The scaffold added three files, and everything else is an edit to files you already own.

### `migrations/0002_job_events.sql`

One row per settle: `id`, `job_id`, `kind`, `attempt`, `detail`, `at` — one line of
`src/engine/events.rs` each. The file is yours; two things about it are decisions:

- a line's identity is `(job_id, kind, attempt)`, so the same settle appended twice must be the
  *same* line — and that has to be the database's decision rather than a read-then-write the caller
  performs, because a retried transaction is exactly a caller arriving twice;
- the durable backend's append is `insert … on conflict (job_id, kind, attempt) do nothing`, which
  PostgreSQL only accepts when a **unique** index matches those columns exactly.

The reference solution also adds the index an operator's question needs (`job_id` in `at` order);
nothing in the spec forces its shape, and a step that reads the whole trail for counters
(`jobq/3.17-error-budget-alerts`) can add its own.

### `src/engine/`

- declare the two new modules and re-export what a caller can name — `pub(crate) mod events;`,
  `pub(crate) mod retry;`, then `pub use events::{EventKind, JobEvent};` and
  `pub use retry::{DEFAULT_ATTEMPTS, Retried, retry};` in `src/engine/mod.rs`. Never `pub mod`
  (step `jobq/3.2-public-api-baseline` reads the declarations): the module stays the crate's, and
  the *names* are the surface.
- `Error::Conflict { source }` is a **new variant**, not a new field on `Error::Store` — 3.3's spec
  constructs the existing variants and pins their `Display`, so a variant that grew a field would
  be a breaking change rather than an addition. Add it, extend `is_retryable` (both `Store` and
  `Conflict`) and give it a row in `exit_code` (4, the store's: what a shell can act on is "the
  queue would not take it").
- implement `retry` in `src/engine/retry.rs`: call the closure, retry while
  `error.is_retryable()` and attempts remain, answer the value with the count it took — and hand the
  *last* failure back unchanged when the bound runs out.

### `src/engine/store/`

- add two methods to the port: `record(&self, &JobEvent) -> Result<bool>` (append a line, answer
  whether it was new) and `events(&self, &JobId) -> Result<Vec<JobEvent>>` (one job's trail, oldest
  first). The docs on both are the contract the suite reads: appending is idempotent **by the line's
  identity**, and a job nobody wrote has an empty trail rather than an error.
- the durable backend: make each settle a transaction at `repeatable read`
  (`pool.begin_with("begin isolation level repeatable read")`), take the attempt from the update's
  own `returning` clause, append the line, and commit once. Map the driver's `40001`/`40P01` to
  `Error::Conflict` **in one place** — the function every statement's failure already goes through —
  so that no other path has to remember.
- the in-memory backend: keep the same promise with what it has. One lock over the rows *and* the
  lines is the honest translation of "one transaction": a refusal returns before either write, and
  a committed settle writes both.

### What deliberately does not change

`claim` writes no line (an attempt that has been *started* is on the row), the five existing port
methods keep their signatures and their behaviour, and nothing in this step wraps a settle in a
retry on the learner's behalf: the store reports the class, and the caller — the spec here,
`jobq/3.7-leases-and-recovery`'s worker next — decides what to do with it.

## TRAP

1. **Appending outside the transaction.** A `store.fail(…)` that commits the row and then calls
   `record(…)` looks correct in every test that does not fail in between — and then a process that
   dies between the two writes leaves a job with no explanation of how it got there, which is the
   exact moment the trail was for. `a_refused_settle_leaves_nothing_behind` fails the other way
   round: an append on the refusal path leaves a line for a settle that never happened.
2. **An `on conflict` clause with no unique index behind it.** Removing `unique` from the index
   compiles, migrates, and then every settle fails with
   `there is no unique or exclusion constraint matching the ON CONFLICT specification` — at the
   first append, not at the migration that should have caught it.
   `the_same_line_appended_twice_is_one_line` is the case; the assertion is a second `record`
   answering `false`, and it cannot pass
   while the database is free to write the row twice.
3. **Staying at the default isolation level.** The settle then *waits* for the other writer and
   re-reads, so `a_transaction_the_database_refused_is_a_conflict_with_a_cause` fails with the
   settle answering `Ok(Queued)` — the race is still there and the caller is still not told about
   it. The spec's message points at the level for this reason: `nothing ever waited for the held
   row` and `the loser of the race is refused rather than quietly re-read` are two different bugs.
4. **Reading the attempt in a second statement.** `update … returning` hands the settle the attempt
   its line has to name; a `select attempts` before or after it can name an attempt that moved on in
   between, and the line then contradicts the row under exactly the concurrency this step is about.
5. **A wrapper that retries everything, or retries forever.** Retrying `Error::Invalid` turns one
   rejected payload into a loop that never ends;
   `the_wrapper_retries_what_is_worth_retrying_and_stops_at_its_bound` checks the first with a call
   count of 1 and the second with a call count equal to the bound. Retrying the *first* failure
   again but never reporting how many attempts it took fails the same case, because the count is the
   assertion.
6. **`Error::Conflict` folded into `Error::Store`.** The cheapest way to make the whole suite green
   except one case: the conflict cases read the source chain for `40001` and
   `matches!(error, Error::Conflict { .. })`. A `Store { detail: "could not serialize…" }` is a
   string a caller cannot branch on, which is the argument the variant exists to settle.
7. **The in-memory backend skipped "because the conflict cases need Postgres".** Two of the seven
   cases need a database and say so; the other five — the trail, its idempotence, the retry loop —
   run against both backends, and a store whose `record` always answers `true` fails them on
   `KILN_BACKEND=memory` before a container is ever started.
