# Job states as a type: transitions that cannot be written down wrong

## WHY

Every rule about a job's life is a rule somebody has to keep. "Only a running job can be
completed", "a job whose attempt budget is spent is finished", "a finished job is never handed out
again" — today each of them lives in the path that acts on it: two settle statements in the
durable backend, two `if`s in the in-memory one, a `case` expression in SQL. A rule spread over
five places is a rule that can be changed in four of them, and the fifth place is the one that
runs at 03:00.

There is a second cost, and it is the one that shows up in review. A rule that lives in an `if`
cannot be *asked* anything: there is no function to hand a property test, no way to say "the four
states and the five events, show me a pair that panics", and no place a new engineer can read the
life of a job from beginning to end. What cannot be asked cannot be checked, and a queue's
whole value is the promise that a job which finished never runs again.

## RECALL

- `db/transaction-isolation@design`, `db/atomic-claim@design` — `jobq/3.6-transaction-isolation`
  and `jobq/3.7-leases-and-recovery`: **this is where the transitions happen today.** The settle
  paths of both backends are the five places the WHY is about, and the claim is the one that
  starts an attempt. Nothing here changes what they do; what changes is where the rule lives.
- `domain/parse-dont-validate@apply` — `mailer/1.10-domain-types`: the other half of "make it a
  type". That step made a value the only way to *have* a valid e-mail address, so an invalid one is
  not something you handle — it is something you cannot build. **This step does not re-teach it.**
  What is new here is that the value is not the point: the *moves between* values are, and a
  transition function is a different shape from a constructor.
- `delivery/dlq@apply` — `relay/2.10-dlq`: where the two terminal states came from. A job that is
  out of attempts is not a job that is missing — it is a job that is *finished*, the queue stops
  handing it out, and a human decides what happens next. `succeeded` and `failed` are that decision
  written as states, and this step is where they are written as *absorbing* ones.
- `sched/delayed-timers@apply` — `jobq/3.11-delayed-timers`: the timer reaches a `queued` job and
  makes it due. It never moves a job between states, which is why the model below has no event for
  "the clock passed" — being due is a property of a queued row, not a state.

## DELTA

**The rules become one total function, and the column becomes its encoding.** Two things follow,
and both of them are checkable rather than argued:

- **`transition(state, event) -> Result<JobState, Illegal>` is total.** Every state against every
  event has an answer, the answer for a move that is not allowed is a *named refusal* — the state
  it was in, the event that arrived, and which of the three reasons it was — and nothing in the
  function can panic. A property test (`jobq/3.19-property-invariants`) can walk the whole thing,
  because the whole thing is a value: the states and the events are lists, and the answer is a
  call. That is the difference between a model and a paragraph.
- **The row's `state` column is the encoding of the model, never the model.** `as_str` and `parse`
  are the two directions of it, a name this build does not know is refused *by the text that was
  stored* rather than rounded down to `queued`, and the schema gets the same sentence one layer
  down: `migrations/0006_job_states.sql` closes the column with a named `check`, so a state the
  model does not have cannot be written by a store, a migration, or a person with `psql` open.

**What is *not* new is the behaviour.** A job still goes `queued → running → succeeded`, a failure
with budget left still goes back to the queue, a claim whose lease ran out still comes back with
its attempt counted. Both earlier steps' suites have to stay green, and they are the evidence that
the model did not change the engine — it only moved the rule. If a `DONE WHEN` line below fails,
the model and the stores disagree, and *that* is the bug this step is shaped to catch.

## TASK

The scaffold added one module and one stub migration. **Nothing declares them yet**: wiring
`src/engine/mod.rs` the way `jobq/3.13-queue-authz-attribution` wired `authz`, `tenant` and `usage`
is your first decision, and until it is made the spec does not compile — which is the step telling
you what it wants.

### `src/engine/state.rs` — the table

Six of the twenty-four pairs of a state and an event are moves. Write them as one function:

| from | event | to |
| --- | --- | --- |
| `queued` | `claim` | `running` |
| `running` | `complete` | `succeeded` |
| `running` | `fail`, budget left | `queued` — the job is owed another attempt |
| `running` | `fail`, budget spent | `failed` |
| `running` | `claim lapse`, budget left | `queued` |
| `running` | `claim lapse`, budget spent | `failed` |

Everything else is refused, and the refusal says which of three things went wrong: the job is
finished, the event needed it to be running, or the event needed it to be waiting. Three decisions
in that table are worth more than the code they produce:

- **`retryable` is the budget's answer, not the machine's.** The machine is about *where* a job is;
  how many tries it has had is the row's business, and the store that counted the attempts is the
  one that says whether another is allowed. That is why `Event` carries a flag instead of a count —
  and why the two events that carry one have the same destinations: a failure and a lapsed claim
  are two *stories* (different `last_error`, different trail line, different counter) with one
  state answer, and a model that merged them would have hidden which of the two happened.
- **`succeeded` and `failed` absorb.** Every event against them is the same refusal, and
  `JobState::is_terminal` — already in `domain.rs` — has to agree with the model rather than being a
  second opinion about it.
- **The encoding round-trips.** `as_str` is in `domain.rs` with the rest of the vocabulary; `parse`
  is here, because a name the model does not know is a *refusal*, and this module is where refusals
  live. The four names are an interface: the column stores them, `jobqc` (`jobq/3.15-cli-contract`)
  prints them, and a dashboard groups by them.

Write `transition`, `JobState::parse` and `Event::as_str`; everything else in the module is the
vocabulary the spec and the rest of the engine already speak.

### `src/engine/store/` — the model is the store's answer, not its second opinion

Both backends ask the model for every state they *write*:

- the in-memory store calls `transition` where it used to decide with an `if`: a claim, a
  completion, a failure, and the row a `release`/`reclaim_expired` hands back;
- the durable store **binds the destination names from the model** (`destination(from, event)`) and
  keeps only the *predicates* in SQL — `state = 'queued'`, `lease_owner = $2`, and the
  `attempts < max_attempts` that only the row knows the answer to. A predicate that matches nothing
  is a query with no answer; a destination invented in SQL is a row in a state nobody can name;
- `decode_state` becomes `JobState::parse`, so reading the column and writing it come from the same
  four names.

The refusals the *stores* give stay exactly as they are: a settle the model refuses is
`Error::Invalid`, which is the class `jobq/3.7-leases-and-recovery` pinned and the one a worker
reads the lease out of. The model's own refusal is `Illegal`, and `From<Illegal> for Error` maps it
into that class — one refusal, one vocabulary, no new exit code.

### `migrations/0006_job_states.sql`

The stub names what it has to hold: a named `check` on `jobs.state`, spelling the four names the
enum spells. Two of its decisions are worth the paragraphs in the stub — the constraint is *named*
(a refusal that says `jobs_state_known` is one an operator can look up), and it *validates* (a
constraint added `not valid` would leave exactly the rows it exists to find behind it).

### What deliberately does not change

`claim`'s signature and the order it hands jobs out in, the settle refusals and their class, the
memory store's semantics that `jobq/3.1`–`3.13` certified, and the port: no method is added, no
variant of `Error` moves, and the destinations that used to be written in five places are written
in one.

- `KILN_BACKEND=postgres kiln run jobq/3.14-job-state-machine` in `app/jobq` — the same cases

- `kiln check jobq/3.14-job-state-machine` — every must gate is green.
- `kiln check jobq/3.13-queue-authz-attribution` — the earlier suites still pass: this step moves
  where a rule lives, not what the rule is.

## TRAP

1. **A second table.** `transition` written, and then the settle path deciding with `if attempts <
   max_attempts` anyway — the two agree today and diverge the first time somebody changes one. The
   store case walks *every* event through the port and compares the row with the model's answer,
   so this is caught rather than reviewed.
2. **A total function that panics on a pair nobody thought about.** `unreachable!()` in the arm for
   `queued` + `complete` passes every other test in the suite: `succeeded` is what a *user* sees,
   and the refusal is what an operator sees. The spec calls all twenty-four pairs, and a panic on
   any of them is a red step.
3. **A refusal that says only "not allowed".** It is the friendliest message to write and the least
   useful at 03:00: the operator has the job id already and needs to know whether the job is
   finished or somebody else is running it. The spec asserts the message against the state's own
   name and the event's, because those are the two strings the caller has.
4. **Rounding an unknown state down.** `parse` with a `_ => Ok(JobState::Queued)` arm turns the one
   row that says "this deployment and this binary disagree" into a job that runs a second time. The
   refusal carries the text that was stored, because that text is the only clue about which version
   wrote it.
5. **A constraint that is not there — or is not named.** Without the migration the durable backend
   accepts `dead` and the engine meets it later as a store failure on a read; with an unnamed
   constraint the operator gets PostgreSQL's generated name, which points at nothing in this
   repository. Both are asserted through `psql`, which is the only way to have the *database*
   refuse rather than a caller.
6. **Binding the destination and forgetting the predicate.** The durable store's statements now take
   the state names as parameters, and a bind that is one position off is not a compile error: the
   claim's `$9`, the settle's `$4`–`$6` and the reclaim's `$6`/`$7` each answer a different
   question. `KILN_BACKEND=postgres` on this step *and* on `jobq/3.5`–`3.13` is what keeps them
   honest.
7. **Treating the model as documentation.** A `transition` that nothing calls passes the first
   three cases of the spec and none of the fourth: the point of the step is that both backends ask
   it, which is what makes the schema's constraint and the model one decision rather than two.
