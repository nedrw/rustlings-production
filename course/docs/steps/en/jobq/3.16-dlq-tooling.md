# Dead letters: what is stuck, why, and one more life

## RECALL

- `delivery/dlq@apply` — `relay/2.10-dlq`: **where this queue's dead letters come from.** That step
  decided when a delivery is finished rather than merely late — the attempts ran out, or the
  subscriber answered something no retry can change — and it made the row stay queryable instead of
  disappearing. A job is in the same place today: `failed` is a state, the budget is what writes it,
  and the row does not move on its own. **What that step does not settle is whose decision the way
  back is, and this step is about exactly that** — the count it reset on the way back is the one
  place the two queues have to answer differently, and the reason is below.
- `domain/state-machine@apply` — `jobq/3.14-job-state-machine`: **the model has no move here, on
  purpose.** `transition` is total, and `succeeded` and `failed` absorb every event: nothing happens
  to a job after the end of its life, whatever arrives. That is not an obstacle to a replay, it is
  the shape of one — an event is something that happens *inside* a life, and an operator's replay
  starts another. This step does not add a row to that table, and a `transition` that grew one would
  make "my job is finished" and "somebody gave it another go" the same answer.
- `db/transactions@design` — `jobq/3.6-transaction-isolation`: a settle changes the row and
  appends the line that describes it **in one transaction**, so an operator reconstructing an
  incident cannot meet a row and a trail that disagree. A replay is a settle of that shape: one
  transaction in the durable backend, one critical section in the in-memory one.
- `time/clock-injection@apply` — `jobq/3.8-clock-injection`: the store's clock is the only authority
  on "now". A replayed job becomes **due at the instant the store's clock reads**, and that instant
  is handed to the decision rather than read inside it — otherwise a deployment with a fixed clock
  replays non-deterministically, and the durable backend's `now()` becomes a second authority the
  step before this one exists to remove.
- `sec/authz-tenant-isolation@operate` — `jobq/3.13-queue-authz-attribution`: **the handle is the
  identity.** A scoped store answers for the queues its model names, and a job it may not see is
  answered like a job nobody wrote. A replay goes through that door like every other call: the
  question "whose dead letters may I put back" is answered by the handle a caller is holding, not by
  a parameter it passes.

## DELTA

**Everything an operator wants to *read* is already on the port; what is missing is the way back.**
A job the engine gave up on is a row in `failed`, and the three questions an operator asks about one
are answerable today: which rows (`Store::list` with a state filter, `jobq/3.15-cli-contract`), what
exactly died (`last_error`, the attempt counters), and how it got there (`Store::events`, the trail
of `jobq/3.6`). So there is no dead-letter *store* to build — there is a name for the view, one
decision about the move, and one method to carry it. Three things are new, and each of them is a
sentence a runbook can hold:

- **The dead-letter queue is a view, not a table.** A dead letter is a row in `failed` and nothing
  else, so the interface to the queue is *the same store* asked a narrower question. Copying dead
  letters into a collection of their own — the shape the name suggests and the one the first
  implementation reaches for — gives one job two rows: the copy's payload goes stale, a replay has
  to move both, and the operator reads a queue that is no longer the queue. `dead_letters()` is that
  view as a value, so a command, a dashboard and a test ask the same question instead of each
  writing `state = 'failed'` in its own dialect.
- **A replay is a second life, and the model says so by having no row for it.** `transition` refuses
  `claim` on a failed job (`jobq/3.14`), and it is right to: the move is not something that happens
  to a job, it is a decision about a dead one. That is why the arithmetic is a value,
  `revived(job, now)` — *what a replay writes* — rather than an event, a SQL statement or a branch in
  a command line. It is public for the same reason `transition` is: a rule a caller can *ask* is a
  rule that can be shown to be wrong, and a tool can answer "what would this replay do?" before it
  does anything.
- **The port gains one method, and it is the only writer.** `Store::replay(&JobId)` answers with the
  row the replay wrote. It is on the port rather than in a tool because two backends have to answer
  the same way about a replay — that is the whole reason the port exists (`jobq/3.5`) — and a tool
  that built its own `update` would be a second arithmetic that drifts the first time one of them is
  touched.

**What a replay writes, field by field.** A dead letter is a job whose count has caught up with its
ceiling, and a replay is "give it one more go". These six decisions are the step:

| field | after a replay | why |
| --- | --- | --- |
| `state` | `queued` | the state a job is *born* in: a second life starts where the first one did |
| `attempts` | **unchanged** | the count is the row's history, and a replay does not un-spend an attempt that happened |
| `max_attempts` | `attempts + 1` | the ceiling moves because the count is the fact and the ceiling is the policy: one more go, and exactly one |
| `run_at` | the store's clock | the operator wants it run, and the instant that decision was made at is the store's |
| `last_error` | **unchanged** | the answer to the operator's first question; what makes it stale is an attempt that *succeeds*, and clearing it is `complete`'s job |
| lease | cleared | "no second life inherits a claim" is a property of the replay rather than of where the job died |

Everything else on the row — its identity, its queue, its payload, its priority — is what it was. The
last one is worth a sentence: a job that was urgent when it was written is urgent again when it comes
back, and a replay that reset a priority would be a scheduling decision nobody made.

**The ceiling moves rather than the count being reset, and this is the one place `relay/2.10-dlq`
and this queue answer differently.** That step put `attempts` back to zero on the way back, and for
its table that was right: a delivery has a *lives* table, so its history survived as rows, and the
count was the current life's own. A job has one counter and one trail. Zeroing the counter would be a
lie in a column the engine reads — `may_retry`, the listing, the numbers a queue reports — and it
would also lose a line: a line's identity is `(job, kind, attempt)`, so a job replayed twice from a
count of zero would append the line the first replay already wrote, and the history would say it was
replayed once.

**Every replay leaves a line, and nothing else moves.** The trail of `jobq/3.6` was written knowing
this step would arrive — an event kind is `#[non_exhaustive]` because "a replay, a purge and a run
somebody cancelled are all events an operator has to be able to read" — so a replay appends
`EventKind::Replayed`, naming the attempt the job had spent when it was put back, in the same
transaction as the row. A *refused* replay appends nothing, because nothing happened: the line is
there so that "has this been replayed before?" has an answer, and a job that was only asked about is
the case the trail must not be made of. No counter moves either — the queue's report counts work
(submitted, claimed, succeeded, failed, reclaimed) and a replay is not work; the attempt that follows
is what a claim counts.

**What a replay refuses, and what it is refused by.** Only a dead letter has a second life. Anything
else comes back as `Error::Invalid` naming the state the job is in, because a `queued` or `running`
job is already owed an attempt — replaying one would put a second claim on work that has not finished
dying — and a `succeeded` job given another go is a duplicate nobody asked for. The other two
refusals are the port's own, and they are inherited rather than invented here: a job the handle
cannot see is answered like a job nobody wrote (`Error::NotFound`, `jobq/3.13`), and a queue the
handle may see but may not `claim` from is `Error::Forbidden` naming that action — putting work back
into a queue you may not take work out of is somebody else's decision.

## TASK

The scaffold added one module: `src/engine/dlq.rs`. **Nothing declares it yet.** Wiring
`src/engine/mod.rs` is your first decision — the shape `jobq/3.13` used for `authz`, `tenant` and
`usage` is the one to copy — and until it is made the spec does not compile, which is the step
telling you what it wants.

### `src/engine/dlq.rs` — the view and the decision

Two functions, and the module's own documentation is where the argument above is written down.

`dead_letters()` is the view as a value: a filter whose state is `failed`, so that "what is stuck"
is one rule with one spelling. Its limit is the listing's default page — a queue has no natural end,
and an operator who wants more asks for more.

`revived(job, now)` is the decision: the row a replay writes, or the refusal that says this job has
no second life. It takes the instant rather than reading a clock, and it answers `Error::Invalid`
whose message **names the state the job is in** — the operator has the identity already and needs to
know what it is, because "this job is `queued`" and "this job is `succeeded`" are two different
mistakes. It is the only place in this crate where the six fields of the table above are decided, and
both backends call it: the in-memory store has the row already and the durable one reads it under a
lock, and neither of them is allowed to have an opinion about what the answer is.

### `src/engine/store/` — one method, and its two promises

`Store::replay(&JobId) -> Result<Job, Error>` is the new port method, and its documentation is where
the two promises that make it a *port* method are written: **the row is read and decided on under a
lock** — `for update` in the durable backend, the store's own critical section in memory — so two
operators replaying at the same instant cannot both be told they moved a job, and **the state change
and its trail line are one transaction**, so the row and the line commit together or neither does.
Both backends implement it, `impl Store for Arc<T>` forwards it like the rest, and the trait's
sealed direction does not change: this is a method *added* to the port, which is the one way a port
may grow.

The durable implementation is the interesting one and its shape is `jobq/3.7`'s settle: read the row
under a lock, ask the engine (through `revived`) where it goes, write the row and the line, commit.
Both refusals are asked for in the order an operator would: a row this handle may not see is looked
for with the scope filter every other read carries, so it comes back "not there", and a row that is
not a dead letter is refused by `revived` *before* anything is written — one call, one message, and
no statement deciding something the engine did not. The write itself carries `state = 'failed'`,
which is the decision written as a predicate rather than as a message: the row is locked, so it
cannot match a row that moved underneath the decision, and a write that matched nothing at all is a
store failure rather than a caller's mistake.

### `EventKind::Replayed`

The new kind, its stored name (`replayed` — the string a migration, a query and a person's `grep` all
agree on, and the fourth name `src/engine/events.rs` spells), and the durable backend's decoding of
it. That last one is the half that is easy to forget, and the failure it produces is the one TRAP 5
is about.

### What deliberately does not change

Every promise `jobq/3.5`–`jobq/3.15` certified: the settle refusals and their classes, the claim
order, the in-memory semantics, `jobqd`'s configuration report and its `draining` line, the CLI's
grammar and exit codes, and the signature of everything the port already had. The model of
`jobq/3.14` does not grow a row, the schema does not grow a table (a dead letter is a row in `jobs`),
and the CLI does not grow a command: this step is the interface a tool is written *against*, and
`jobq/3.15-cli-contract`'s four rules are what a command built on it would have to keep.

## TRAP

1. **Resetting the count.** `attempts = 0` on a replay is the answer `relay/2.10-dlq` gives and the
   one this row must not: `may_retry` then says a job has attempts it never spent, the operator's
   counters stop adding up, and the *second* replay of the same job appends the line the first one
   already wrote — a history that says "replayed once" about a job that was replayed twice. The
   spec walks a replay twice and compares the attempt count and the trail's length.
2. **A replay that keeps its opinion to itself.** `max_attempts` untouched moves a job from `failed`
   straight back to `failed` on its next failure without running anything: a claim's `attempts >=
   max_attempts` is not a predicate the model can see, and the row is simply never handed out again.
   The spec claims the replayed job and asserts the attempt it is running is one past the count that
   killed it, and that a second failure spends the new budget.
3. **The second replay doing something.** A script that timed out and retried its own command must
   not start a second life. An *idempotent* replay here is not a silent success: the job is `queued`
   now, so the refusal names that state, and the row and the trail are exactly where the first
   replay left them. The spec calls it twice and compares the whole row, the whole trail and the
   queue's numbers.
4. **A predicate that is not there.** `update jobs set state = 'queued' where id = $1` moves a
   *succeeded* job back into the queue, and the only thing that refuses it is `and state = 'failed'`
   — a decision written as a predicate rather than as a message. The spec replays a queued, a
   running and a succeeded job and expects each of them to be refused by the state's own name.
5. **A line that can be written and not read back.** Adding the kind to the enum without adding it to
   the durable backend's decoding leaves a trail that reads fine until somebody replays something:
   then `events()` answers `store: replayed is not an event this engine knows` — on the one call an
   operator makes *after* an incident. The spec reads the trail back through the port, on both
   backends.
6. **The database's clock.** `run_at = now()` in SQL is the database's opinion about the present, and
   `jobq/3.8-clock-injection` exists because a second authority on time disagrees eventually. The
   spec injects a clock stopped at an instant no wall clock will reach and asserts the replayed row
   is due at *that* instant — and that a claim, which only sees rows whose `run_at` has passed, takes
   it at once.
7. **Reading the row and then writing it.** Two statements outside a transaction — a `select` to
   decide, then an `update` to write — is the shape that passes every test in this file and loses the
   race in production: between them a second operator's replay moves the row, and the first one's
   write puts a ceiling on it that was computed from a count that has already moved. The queue then
   hands out an attempt it does not owe — a claim takes any `queued` row that is due, and the budget
   is what the *settle* reads — and the job ends up `failed` having spent more attempts than the
   ceiling it was given. The lock is not decoration; it is what makes "I looked and then I wrote" one
   act.
8. **The line in a second transaction.** A row that moved and a line that did not is exactly the
   disagreement `jobq/3.6` built the trail to prevent, and it is invisible until somebody
   reconstructs an incident from the two. The durable backend appends through the transaction it is
   already holding, which is the pattern the settle paths use.
