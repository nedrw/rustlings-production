# Deduplicate: for how long, and what happens at the edge of the window

## RECALL

- `delivery/idempotency@apply` — `mailer/1.15-idempotent-delivery`: one confirmation per subscriber,
  kept by a write whose own `returning` row is the truth, and the row never expires. The half this
  step keeps is that the *store* answers and the answer is the first request's. What T1 never had
  to decide is when the answer stops: a subscriber is an identity that lasts, and a producer's
  retry is a request that does not.
- `db/unique-as-concurrency@design` — `jobq/3.6-transaction-isolation`: a uniqueness rule two
  callers can break at the same instant belongs in the database, `on conflict` names the arbiter
  that decides, and the loser is told rather than left to re-read. Here the arbiter is a pair —
  `(queue, key)` — and the loser's answer is a job rather than a refusal.
- `time/clock-injection@apply` — `jobq/3.8-clock-injection`: every instant this engine compares
  comes from the clock it was handed. That is what turns "the window has passed" into a case that
  runs in milliseconds, and it is why both instants the key table is compared against are that
  clock's rather than the database's.

Two neighbours are also called idempotency and neither is this one, so the boundary is worth
writing down. `api/idempotency-key@apply` (`relay/2.2-idempotent-ingest`) answers a *request* with
the row it already stored, keyed by tenant and never expiring. `delivery/idempotency@apply`
(`mailer/1.15`) answers a *subscriber* the same way. This step is where the remembering has an end,
and the end is part of the interface.

## DELTA

**The window is the decision, and it belongs to the request.** "Deduplicate" with no duration is
not a specification: it is either a table nobody may ever empty or a promise a caller cannot rely
on for longer than one process's memory. So the request says it — `with_dedup_window` beside
`with_dedup_key`, both additive on `SubmitRequest` — and the engine's answer is bounded by that.

Three consequences follow, and each of them is a sentence a caller can plan against:

- **inside the window, a repeat is answered, not refused.** `Engine::submit` hands back the
  identity of the job the key already produced, the same identity the first request got, and the
  duplicate's payload is never written. A producer that gets a *second* identity back cannot tell
  whether its retry queued another copy of the work it is retrying, which is the failure the whole
  mechanism exists to prevent.
- **at exactly `first + window` the key is new again**, and not one instant before. The window is
  half-open: a key taken at `t` answers while `now < t + window` and is gone at `t + window`. That
  line is written **once**, in `Dedup::expiry`/`Dedup::live`, and both stores read it from there —
  one backend off by one is a backend that deduplicates a legitimate repeat, or executes a
  duplicate, for exactly one instant.
- **what a caller may assume after it: nothing.** Two requests carrying the same key on either side
  of the boundary are two jobs, and that is correct rather than a leak: the window is the
  producer's own statement about how long its retries live, and the reading it promises is "one
  piece of work per window". A retry loop that outlives its own window is asking for a new job.

The window is also **not moved by a duplicate**. It is stamped from the first request and stays
there, so a retry that asks for a longer window than the first one — or a client that retries every
second for an hour — is answered by the window that was opened first. A window a caller could push
forward by retrying would be a window the caller controls.

**Why the store keeps a row to enforce it.** The window's boundary has to be decided *while the
write happens*, by the same statement that writes, or two producers racing on one key both read
"no key yet" and both write. So the row is the mechanism: it carries the instant the key stops
answering, and the statement that takes a key is

```sql
insert into dedup_keys (queue, key, job_id, expires_at) values (…)
on conflict (queue, key) do update
    set job_id = excluded.job_id, expires_at = excluded.expires_at
    where dedup_keys.expires_at <= $now
returning job_id
```

— a **reset** for a row whose window has passed, and nothing at all for a live one. A store that
*refused* a dead key instead of resetting it would make every key name one job for ever, which is
the same promise as no window at all. And because the live half writes nothing, the answer for a
repeat is a read of the row the key already names: the first job, as it is now.

**Expiry is not deletion.** A key whose window has passed is dead because of the instant it
carries, not because something swept it, so sweeping is housekeeping: a store that never removes an
expired row answers exactly the same way, and a sweep that removed a *live* row would let a
duplicate through. That is the difference between the two halves of this step's mechanism — the
statement is the promise, the sweep is the disk.

## TASK

The scaffold added `src/engine/dedup.rs` (inert until you declare the module) and a stub for
`migrations/0004_dedup_keys.sql`.

### `src/engine/dedup.rs`

`Dedup` is the value both stores ask, and the four decisions in its module documentation are the
ones you are asked to make: what a key may be (`Dedup::new`, fallible — read its `# Errors`),
which side of `first + window` is which (`expiry`, `live`), and what a window of zero means (it is
not a special case: it is a key that is dead the instant it is taken). Fill in the `todo!()`s.

### `src/engine/domain.rs`

`SubmitRequest` gains a key and a window, and a `pub(crate) dedup()` that turns the pair into the
`Option<Dedup>` a store wants. Three cases, and the third is a rule rather than an omission: no key
is `Ok(None)` (a window nobody named remembers nothing), a key with a window is `Ok(Some(..))`, and
a **key with no window is `Error::Invalid`** — the window is part of the question, and the engine
will not pick a duration on the producer's behalf.

### `src/engine/store/`

- the port: `Store::enqueue`'s documentation is where the promise lives, so it is where "the answer
  is the job that key already produced, while the key is inside its window" is written down for
  both backends;
- the durable backend: one statement for the whole decision, with the key table's half
  (`on conflict (queue, key) do update … where expires_at <= $now`) and the job row's half in it, so
  that a live key writes **nothing** and a racing producer is decided by the database rather than by
  a read that happened a moment earlier. A request with no key keeps the statement it already had;
- the in-memory backend: the same rule under the lock it already takes — a live key answers before
  either write, an expired one is reset. The lock is this store's transaction
  (`jobq/3.6-transaction-isolation`), so nothing here can half-apply.

### `migrations/0004_dedup_keys.sql`

The file is yours. Two of its decisions are the ones the stub names: the queue is part of the key,
and the row carries the expiry. The third is the one `on conflict` needs — a unique constraint or
index matching `(queue, key)`, or the migration runs and every keyed write fails at the first
statement with `there is no unique or exclusion constraint matching the ON CONFLICT specification`.

### What deliberately does not change

`Engine::submit` still answers a `JobId` (`jobq/3.2-public-api-baseline` pinned it): a producer that
needs to know whether *its* request was the first one is asking about the trail, not about the
queue, and a second answer here would be a second contract. `claim`, the leases and the worker are
untouched: a deduplicated job is an ordinary job.

## TRAP

1. **Refusing a key whose window has passed.** `insert … on conflict … do nothing` is the obvious
   spelling and it makes each key name one job *for ever*: the boundary case then fails one second
   past the window, a legitimate later request is answered with a job from an earlier window, and
   the table only grows. The expired row has to be **reset**, which is what the `do update … where`
   half is for.
2. **`where expires_at < $now` instead of `<=`.** One character, and the window is half-open on the
   wrong side: at exactly `first + window` the row is still "live", so
   `the_boundary_is_exactly_the_window_after_the_first_request` fails with a duplicate where a new
   job was required — and only at that one instant, which is why the case is written on it.
3. **Stamping the window from the request that arrived.** Writing `now + window` on every keyed
   request, including a duplicate, moves the end out with each retry: the repeat that asks for a
   ten-minute window passes the first assertion of the boundary case and then keeps the key live
   for ten minutes, so the case's `first + window` step fails. The window belongs to the key as it
   was first taken.
4. **Reading the key and then writing.** `select … where queue = $1 and key = $2`, then insert when
   it came back empty, is a window two producers both pass through: `callers_racing_for_one_key_get_one_job`
   either fails on the constraint (one racer's submit is refused) or finds two jobs in the queue.
   Make the database decide, in one statement.
5. **Answering a repeat with a copy taken when the key was written.** Storing the `Job` beside the
   key looks tidy and answers a settled job as `queued`: the case completes the first job and asks
   again, and the state it reads back is the one from the moment the key was taken. The key names a
   job; the row is where that job's state lives.
6. **A key with no window treated as "no deduplication".** The request carries a name, so the
   producer believes it named its work; a store that ignored the key answers two jobs and looks
   correct — the refusal case is what refuses to let that pass, and the engine's answer is
   `Error::Invalid` rather than a duration nobody asked for.
7. **Deduplicating for the whole table.** One `key` column with a unique index and no queue in it:
   `a_key_is_a_key_of_one_queue_and_one_window` fails, because the same string in another queue is
   a different piece of work (`relay/2.2-idempotent-ingest` made this call for tenants). Two
   producers that both call their first job `order-1` in different queues are not duplicates of
   each other.
8. **Checking the window in Rust against `self.clock.now()` after the row was written.** The
   comparison happens somewhere, and if it happens outside the statement then the row's instant and
   the engine's decision can come from two different readings of the clock: the fix is not a
   tighter comparison, it is asking the clock once and letting the statement compare it (`$now` is
   bound, not `now()`).
