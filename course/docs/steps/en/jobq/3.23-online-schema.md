# Expand, backfill, contract: changing the queue's own schema online

## RECALL

- `db/schema-online-evolution@aware` — `relay/2.23-online-schema`: the three deploys and the window
  between them. That step decided what a schema change costs when the process applying it is not the
  only one running — expand adds without rewriting, the backfill fills in batches and stops on *filled
  nothing*, and the **fallback is the same expression the backfill writes**, so the stored number and
  the computed one cannot disagree. It also decided where the middle phase lives there: a command, run
  by a person, because the service has no queue to put it in. **This step is the `apply` half of that
  slot**, and the one thing it does differently is that sentence.
- `db/migrations@apply` — `mailer/1.9-postgres`: there is a schema, the process applies it before it
  serves, and a migration that has already run changes nothing. Here the schema belongs to the queue
  itself, and every phase of the change is written as statements a deployment runs against a database
  that is serving.
- `db/port-conformance@apply` — `jobq/3.5-store-port-conformance`: one suite, every backend. It is why
  this step can be about a *procedure* rather than about one database's SQL, and why the spec below
  runs twice — the in-memory store answers `migrate()` with `Ok(())` because it has no schema, and the
  cases that are about the schema itself are the database's.
- `jobq/3.14-job-state-machine` — the migration that closed the state column added its `check`
  *validating* rather than `not valid`, and said why: "a check that skipped validation would leave
  exactly the rows it exists to find behind it, and this table is small in every deployment this
  track has taught for. The step with an answer for one that is not is the schema step."
  This is that step, and `not valid` is the answer.

## DELTA

Four decisions separate this from `relay/2.23`:

- **the table belongs to the queue, and the backfill is a job in it.** The middle phase is not a
  command somebody runs next to the service: it is work on a queue in the table being changed, so it
  goes through the same port, the same claims, the same workers, the same trail. Batched, because one
  statement per batch is what makes a batch atomic; paced by `run_at`, because a plan that submits
  every batch due now is a plan that confines the queue it is migrating; resumable, because the
  batch's predicate is *the value is absent* rather than a bookmark; cancellable, because a batch
  that never ran filled nothing and a batch that ran filled all of itself.
- **the port does not change.** Not one method is added to `Store`, and that is the design rather than
  an omission: what the engine owes this step is the *plan* — which phase is next, from what the
  catalog says, and what the middle phase costs and how it is spread — and the port already has
  everything a job needs. The consequence is worth reading twice: the in-memory backend passes the
  same suite by having no schema at all, and the phases a database can answer are asked of the
  database.
- **`not valid`, because the table is not small.** `add constraint … check (…) not valid` takes
  effect for every write immediately and tells the database to skip the rows that are already there;
  the contract's `validate constraint` is the later deploy that makes it check them. On a table of ten
  rows, validating in the expand is a rounding error and `mailer`/`jobq/3.6` were right to do it; on a
  table that is the deployment's whole queue, it is a full scan under a lock taken by a deploy.
- **every phase asks the catalog first.** `alter table add column` is not idempotent: the second run
  of an expand is an error, not a no-op. So the phase decides from what the database already answers
  (`Applied`) and answers *nothing to do* rather than re-running its statements. The one exception is
  the middle phase's own statement, whose predicate is the whole of its resumability.

## TASK

The scaffold added a module, a harness and a page. **Nothing declares the module yet**: wiring
`src/engine/mod.rs` is your first decision, and until it is made neither the spec nor the harness
compiles.

### `Change` — one column, one expression, one queue

`Change::new(table, column, computed, queue)` is the whole description: the table the queue lives
in, the column it is gaining, the SQL expression that computes the value, and the queue the backfill
jobs run on. `batch` and `per` are the two decisions that are the *rate*: how many rows one job
fills, and how far apart two jobs are scheduled. The constraint and the index names are derived from the column
(`<table>_<column>_known`, `<table>_unfilled_<column>`) rather than spelled again, because an operator
who finds one in the catalog should be able to find the other by the column it is about.

`fallback()` is the read path's answer while the column is empty: `coalesce(<column>, <computed>)`. It
is built from `computed()` rather than written out, because the stored value and the computed one have
to be *one expression in two places* — that is the whole of what makes the expand phase invisible, and
it is the thing `relay/2.23` argued and this step keeps.

### `Applied` and `Step` — what the database says, and what that means

`Applied` is the catalog's answer: is the column there, how many rows have no value, has the
constraint been validated. `Applied::before()`, `expanded(remaining)` and `contracted()` are the three
states a deployment moves through, and each phase takes one and answers a `Step`:

| `Step` | when |
| --- | --- |
| `Statements(Vec<String>)` | the phase has work: the statements a deployment runs, in order |
| `Jobs(Plan)` | the middle phase: the jobs to submit, one per batch |
| `Nothing(&str)` | the phase is already applied — and the reason, spelled out |
| `Blocked(&str)` | the phase before it has not finished, so this one would be refused |

The distinction that matters is the last two. `Nothing` is "this already happened", which is what makes
every phase safe to run twice; `Blocked` is "this would be refused", which is the contract answering a
`set not null` with rows that have no value — the database's own error, moved to where the plan is
made.

### `Plan` and `Batch` — the middle phase, as work the queue runs

A plan is the change plus the batches that are left: one per `batch` rows, `due_at` one `per` apart,
and `rows()` summing to exactly what is missing. `statement(batch)` is the one statement a batch
runs — a single `update … where … is null … limit <batch>` — and the `is null` is not a detail: it is
the predicate that makes a re-run fill nothing and a half-finished run finishable by anybody.
`requests()` turns the plan into `SubmitRequest`s for the queue being changed, each carrying the batch
it is (`migration.batch`, `migration.rows`), because the worker that claims one has to know what to
run.

### `METRICS`, the limits, and `report` — what the plan costs

The budget for an online change is not a stopwatch either: it is the jobs the plan submits, the rate it
keeps and what resuming costs against starting over. `burst()` is the most batches due in one interval
(the rate limit, written as a guard), and `report(whole, resume)` prints the three lines a harness
compares with the course's baseline for this step
(`course/tracks/jobq/budget/3.23-online-schema.toml`). A plan with no denominator prints no guard line
rather than a zero, because `0.0` would compare with a bound like any other ratio and report a *pass*
for a plan that measured nothing.

### `docs/migration.md` — the change, written down for whoever runs it

The stub names the three phases and the three metrics. Fill it in: what each metric counts, the
baseline the course ships, why the rate and the resume ratio are guards rather than targets, and what
to do about a run that died halfway. The spec reads this page and compares it with `METRICS`,
`BURST_LIMIT` and `RESUME_LIMIT`, the same way `jobq/3.22-bench-budget` compares its page with its own.

### What deliberately does not change

The harness (`tests/backfill_budget.rs`) is the course's instrument, and the port is untouched
(`Store` gains no method here). The table is the queue's own — `jobs` — and the column is
`payload_bytes`, an integer derived from the payload the row already carries: the fact the backfill
computes is already in every row, so this change is one no reader can get wrong and no writer has to
be told twice.

### What the spec judges

| the case | the claim |
| --- | --- |
| `the_expand_phase_adds_and_rewrites_nothing` | the column is nullable with no default, the constraint is `not valid`, the index is partial on the predicate the backfill reads, and there is no `update` anywhere in the phase |
| `the_read_path_answers_from_the_expression_the_backfill_writes` | `fallback()` is `coalesce(<column>, <computed>)`, the batch statement uses `<computed>`, and the expand has no fallback in it |
| `the_backfill_is_batched_paced_and_atomic` | `ceil(remaining / batch)` jobs, no batch larger than `batch`, the rows add up, the due instants are one `per` apart, and one batch is one statement |
| `the_guard_is_the_rate_and_the_plan_without_it` | `burst()` is 1 for a paced plan and the number of batches for a plan whose interval is zero — the defect the guard is for — against `BURST_LIMIT` |
| `the_plan_is_a_function_of_what_is_left` | half the rows left is half the jobs, `report` prints the three lines and the ratio against `RESUME_LIMIT`, and an empty plan prints no ratio |
| `running_a_phase_twice_changes_nothing` | the second expand, the second backfill of a filled table and the second contract answer `Nothing`, and the contract answers `Blocked` while rows are still empty |
| `the_backfill_jobs_are_jobs_in_the_queue_it_migrates` | the plan's requests are accepted by the port on both backends, claimed like any other work, carry the batch they are, and leave the queue serving the jobs that were already in it |
| `the_old_release_writes_rows_this_one_serves` | against the database: the expand applied to a serving database leaves the column nullable, a row written the way the *old* release writes one lands and is served through the fallback, a batch fills it with the same number, the contract makes the column `not null` — and running the contract twice is fine |

## TRAP

1. **`add column … not null`.** Postgres could add it with a default without rewriting, and it is still
   wrong: the **old release's** insert names the columns it knows, and a column the database refuses to
   leave empty rejects that insert — the failure lands in the code that is already running. Increment
   the schema in three deploys, not one.
2. **The backfill inside the migration.** One `update` over the whole table in the same transaction as
   the DDL holds a write lock on the table the workers claim from, so the queue stops for as long as it
   takes — a pause in the deployment's work with a changelog entry. The expand phase's statements
   contain no `update` at all, and the spec checks that.
3. **A plan with no pace.** Every batch due at `now` (`burst_max` equal to the number of jobs, against a
   limit of 1) is a plan that hands the migration's workers the whole table at once: the queue it is
   migrating is the queue whose capacity it consumes, and the expansion is then an outage with a
   different name. The interval is a decision; zero is a decision somebody makes by accident.
4. **Planning the whole table when half of it is done.** The plan is a function of what the catalog
   says is *left* — `resume_ratio_max` 1.0 against a bound of 0.6 says a run that was interrupted at
   the halfway mark plans to look at every row again. The count of rows already filled is a number a
   database answers in one query, so there is no reason to re-derive it by trying to fill them.
5. **A bookmark instead of "the value is absent".** `where id > $1` or a `backfill_state` table: the
   first run is fine and the second one has to be reasoned about, which means it will not be run
   twice, which means a run that died halfway is a run nobody finishes. The predicate is the whole of
   the resumability, and `limit`-ing a single `update` is what makes a batch atomic.
6. **A contract whose second run fails.** The phase answers `Nothing` from the catalog, and the
   statements are still written so that a *half*-applied run finishes: `validate constraint` and
   `set not null` may be run again, but `drop index` without `if exists` is an error the second time —
   the one statement in the contract whose deletion is not idempotent by nature. The spec runs the
   contract's statements twice to prove it.
7. **Contracting while rows are empty.** `alter table … set not null` is refused by the database with
   `column "payload_bytes" of relation "jobs" contains null values`, and the deploy that ran it is
   now half-applied in the middle of a rollout. That refusal is the contract running early, and the
   plan says `Blocked` before anybody reaches a database: `remaining > 0` is the check.
8. **Computing the value in Rust.** `payload.to_string()` against `payload::text`: `jsonb`
   canonicalises key order and spacing and `serde_json` does not, so the stored number and the
   fallback's disagree by a byte for some payloads and nobody can say which is right. The expression is
   the database's, written once, and both the write path and the fallback read it from `computed()`.
9. **A read path with no fallback.** A `select payload_bytes from jobs` with no `coalesce` answers
   `null` for every row that predates the change — the expand phase is supposed to be invisible, and
   nulls are how it becomes a breaking change. `fallback()` is built from `computed()`, so the two
   halves of the window are one expression.
10. **Editing the harness or the baseline instead of the plan.** `tests/backfill_budget.rs` is the
    course's file and `course/tracks/jobq/budget/3.23-online-schema.toml` is the copy the gate reads:
    editing either changes the instrument, not the plan it measures. `kiln reset jobq/3.23-online-schema`
    puts the harness back.

  expand phase can be applied to a table that is being written to.

  at the price of a build that can fail and has to be cleaned up by hand.

  levels a migration's statements take, and which of them queue behind a running query.
