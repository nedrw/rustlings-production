# One suite, two implementations: the store port and its conformance tests

## WHY

The engine's promises live on its port: a claim hands out due work in priority order and never hands
the same job to two workers, an attempt is counted when a worker takes a job, only work somebody is
running can be settled, and an identity nobody wrote is an empty answer rather than an error. Until
today one implementation kept those promises, and they held because there was nothing to disagree
with.

The durable backend turns them into a *contract*: two codebases, written at different times, against
the same five methods. The failure it invites is not a crash. It is drift — priority quietly stops
meaning anything on the new backend, a restart hands the same job out twice, a missing identity
starts coming back as an error instead of an empty answer — and none of it shows up until the queue
is the only copy of the work.

What catches drift is not care. It is a conformance suite: one file of assertions, run once per
backend. One spec file and one gate, not N test suites that answer differently; and the only artifact
in the project where "implementing this port" is written in a form a machine can disagree with.

## RECALL

- `db/migrations@apply` — `mailer/1.9-postgres`: forward-numbered files applied once, the applied set
  recorded in the database, and the schema brought up to date before the service serves — a start
  that is safe to repeat. This step does not re-teach it, and
  `migrations/0001_jobs.sql` is written the way that step left you writing migrations (`mailer` and
  `relay` number their own files; this project starts at `0001`). What changes is whose schema it is:
  not a service's private tables, but a table that is *one* implementation of a port whose other
  implementation is a map.
- `db/atomic-claim@apply` — `relay/2.5-atomic-claim`: a claim is one statement, with
  `for update skip locked` inside it, because choosing the rows and stamping them has to be one
  decision. That knowledge transfers whole. What is new is what it is measured against: in `relay`
  that statement was the service's only way to claim work, and here it is one of two implementations
  of one port, judged by a file that also runs against a store with no rows to lock at all.

## DELTA

- **The new artifact is the suite, not the backend.** One spec file, run once per backend: the fast
  run takes `memory` (the fixture's default), and the `conformance@2` gate re-runs the project's own
  `run.cmd` with `KILN_BACKEND` set for every name `conformance.toml` declares. Adding the next
  backend is adding a name and a variant in the fixture — not another spec.
- **A promise the suite asserts has to be written *in the port*.** The claim order is one: it is on
  `Store::claim` from this step on, because a promise only one backend's documentation makes is a
  promise the other backend cannot be held to, and the suite would be reading the implementation it
  was meant to be judging.
- **A disagreement is a bug in whichever implementation is wrong — including the one already
  shipped.** The in-memory store chose its due jobs while holding one lock and stamped them after
  letting it go, so two workers asking at the same instant could both be handed the same job. Nothing
  in the engine could see that; the suite sees it on the first run, and the fix is to make both halves
  of the decision one section.

## TASK

- Write `migrations/0001_jobs.sql`: the columns the port carries and nothing a caller cannot see —
  identity, queue, payload, state, priority, the instant it may run, the attempts it has spent, the
  budget it was given, the last reason it failed — plus an index for the predicate a claim runs
  against a table that is mostly not due.
- Implement the durable backend: `connect`, a `migrate` that is safe to run against a database that is
  already current, and the five port methods, each answering exactly what the in-memory store answers.
- Make `claim` **one statement**: choose the rows with `for update skip locked` inside the update that
  stamps them, count the attempt there, and answer in the port's order (priority, then the job that
  has been due longest, then identity) rather than in whatever order the rows come back from a table.
- Refuse what must be refused. `complete` and `fail` only touch a running job: `Error::Invalid` when
  the job is in some other state, `Error::NotFound` when there is no such row. `get` answers
  `Ok(None)` for an identity nobody wrote. A budget of zero attempts is `Error::Invalid` rather than a
  row nobody can run.
- Declare the module: `pub(crate) mod postgres;` in `src/engine/store/mod.rs`, the type re-exported
  through `jobq::engine` — never `pub mod`, which would make the module a path and break the surface
  `jobq/3.2-public-api-baseline` pinned — and declare the two new fixtures in `tests/support/mod.rs`
  so the spec can reach them.
- Keep the in-memory backend conformant as well. When a case fails against one of the two, the
  implementation that disagrees with the port is the one to change; relaxing the assertion moves the
  disagreement into the engine.

## DONE WHEN

- `kiln run jobq/3.5-store-port-conformance` — the whole suite is green against the in-memory store,
  which is what a fast run uses.
- `KILN_BACKEND=postgres kiln run jobq/3.5-store-port-conformance` in `app/jobq` — the same cases
  against a Postgres container of its own: exactly the run the `conformance@2` gate repeats once per
  backend in `conformance.toml`.
- `kiln check jobq/3.5-store-port-conformance` — every must gate is green, `images` and
  `semver@baseline` included.

## TRAP

1. **A claim that chooses the rows and then writes the decision down.** The suite answers with
   `two workers came back with the same job (4 of 16 claims were repeats)` — and it answers that
   against `KILN_BACKEND=memory` too, because the in-memory store shipped in exactly that shape:
   it read the due jobs under one lock and stamped them under the next. The fix is structural
   (select and stamp in one critical section) rather than a check afterwards.
2. **Assembling the statement with `format!`.** A shared column list looks like good hygiene and
   `sqlx` 0.9 refuses it: `error[E0277]: dynamic SQL strings should be audited for possible
   injections … the trait SqlSafeStr is not implemented for &String`. The driver takes a `&'static
   str` so that the SQL is visible at the call site; every value travels as a bind parameter, so
   there is nothing to assemble.
3. **A `migrate` that runs its own DDL.** Creating the table with a bare
   `execute("create table jobs …")` makes the *second* run fail with
   `42P07: relation "jobs" already exists`, and the second run is the one a daemon performs on every
   start. `the_schema_step_can_be_run_again` is the case that says so.
4. **Resolving `run_at` against the database's clock.** `now()` is a second authority next to the
   engine's clock, and the two drift: a container whose clock is a second behind makes
   `a_write_answers_with_the_row_and_the_instant_it_is_due` fail with the backend's own name in the
   message, while the same assertion passes against the in-memory store. One clock, bound into the
   statement, is what keeps the two backends answering the same question.
5. **`pub mod postgres;`.** It compiles, the suite goes green, and the next time
   `jobq/3.2-public-api-baseline` is judged the run fails with
   `every module under src/engine must be pub(crate)`: a module a caller can name is a module that
   moves under them in the next release.
6. **Forgetting the request that can never run.** `Store::enqueue` documents a budget of zero attempts
   as `Error::Invalid`; a backend that inserts the row anyway fails with `expected Error::Invalid,
   got …`, and the row it wrote is one no worker will ever finish — the in-memory store was already
   refusing it, which is why the assertion exists.
7. **The fixture directory's own dead code.** `clippy@3` is `-D warnings` on every target, tests
   included, and a fixture is a menu: `tests/support/postgres.rs` carries `query`, `execute` and
   `stop` for the steps that come after this one, so the first spec that does not call one of them
   fails the gate with `error: struct Postgres is never constructed`. The relaxation belongs where
   its reason is written down — one `#![allow(dead_code)]` at the top of `tests/support/mod.rs`,
   because a fixture nothing in *this* spec calls is a fixture another spec calls — rather than
   sprinkled over the functions that happen to be unused today.

- [PostgreSQL: the locking clause](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)
  — `FOR UPDATE`, and the `SKIP LOCKED` that turns a queued-up worker into a worker that takes the
  next free row.
- [`sqlx::postgres::PgPoolOptions`](https://docs.rs/sqlx/0.9.0/sqlx/postgres/struct.PgPoolOptions.html)
  — connecting, `acquire_timeout`, and what `connect` waits for that `connect_lazy` does not.
- [`sqlx::migrate!`](https://docs.rs/sqlx/0.9.0/sqlx/macro.migrate.html) — migrations embedded in the
  binary, and the table that records which of them have run.
- [`tokio::test`](https://docs.rs/tokio/1/tokio/attr.test.html) — the runtime flavour, which is what
  makes the concurrency case more than one claim after another.
- `relay/2.5-atomic-claim`'s `src/claim.rs`: the same statement written for one service, with the
  lease and the holder this port does not have yet (`jobq/3.7-leases-and-recovery`).
- The port itself — `src/engine/store/mod.rs` is the contract the suite reads, and
  `tests/support/store.rs` is the seam `KILN_BACKEND` goes through.
