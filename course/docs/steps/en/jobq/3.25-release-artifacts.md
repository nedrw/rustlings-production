# Ship it: versioned artifacts, checksums and a changelog nobody has to reconstruct

## WHY

Everything this project has been held to so far is asked of a process that is already running: a
claim, a lease, a transition, an alert. A **release** is the first thing the project hands to
somebody who is not here, and what travels is a file with a name, a version inside it, and — if
nobody decided otherwise — nothing that says whether the bytes arrived intact or what changed in
them.

Those failures are cheap to write down and expensive to meet. The binary on `PATH` is not what its
`--version` says, because a stale build was packaged and the tag names an intention rather than the
bytes. A mirror or a CI cache hands out the file that had this name last quarter, because a name
that does not carry the version is a cache key. A bug report says `0.4.0` and nobody can tell which
`0.4.0`: three tags moved, and the changelog was reconstructed from `git log` by whoever was on
call. A checksum file a human compares by eye is a checksum file nobody checks.

None of that is about queues. It is the difference between something you built and something
somebody can *use*, and it is why this step is a tool rather than a paragraph in a wiki.

## RECALL

- `ci/pipeline@apply` — `mailer/1.3-ci`: a pipeline is a sequence of commands that either produces
  a green result or fails, and that is the same bet this step makes one job later. The boundary:
  the pipeline runs *your code*, and this is the job at the end of it that publishes *a file*. The
  tool below runs no compiler and no test — it is handed what the build produced and decides
  whether that is the release the tag names. That is also why it can be rehearsed from a shell with
  no CI runner anywhere.
- `api/library-design@apply` — `jobq/3.2-public-api-baseline`: that step's witness file ends with a
  sentence this one makes true — a breaking change is allowed, but it costs a major version bump in
  `Cargo.toml` **and** a line in `CHANGELOG.md`. The semver gate reads the first half; the file this
  step writes is the second half, and the release tool refuses to publish a version whose section
  is missing, empty, or still sitting under `Unreleased`.
- `cli/contract@apply` — `jobq/3.15-cli-contract`: the third binary you add here is held to that
  step's table rather than to a new one — one exit code per failure class, the answer on stdout and
  the diagnosis on stderr, and an argument it does not understand is a usage error that names the
  argument. Codes are a promise a script branches on; the release tool's refusals come back as the
  classes `jobq/3.3-library-errors` wrote.

## TASK

The scaffold added a module, a binary, a harness, a page stub and a changelog stub. **Nothing
declares the module yet**: wiring `src/engine/mod.rs` is your first decision, and until it is made
neither the spec nor the harness compiles.

### `VERSION`, `TAG_PREFIX`, `CHECKSUMS` and `BINARIES` — the facts, once

`VERSION` is `CARGO_PKG_VERSION`, read at compile time: the manifest is the only place a version is
written in this project, and a second copy of the string is the copy that goes stale. `TAG_PREFIX`
is `v` and `BINARIES` is `jobqd` then `jobqc` — the order a release lists them in. `CHECKSUMS` is
`SHA256SUMS`, the name every tool that reads a checksum file already looks for.

### `digest(bytes)` — SHA-256, because the file is read by other people

A checksum file is an agreement with tools that already exist (`sha256sum -c`, a package manager, a
container registry), so the algorithm is not a choice: it is 64 lower-case hex characters of
SHA-256. The crate takes the `sha2` dependency the scaffold added for exactly this, and the
alternative — a hash written by hand in this module — is the kind of code that is wrong in a way
nobody notices until it matters. The spec pins the two published vectors (`digest(b"")` and
`digest(b"abc")`) so that "it hashes something" cannot pass for "it hashes with SHA-256".

### `Artifact` — a name and the bytes it is a promise about

One file of the release, built by `Artifact::of(name, bytes)` with the bytes in hand. `digest()` is
the file's own, `len()` is what it weighs, and nothing outside the module can build one out of a
name and an idea. The bytes live with it on purpose: verification is about what was downloaded, and
a type that carried a path instead would make every check a second filesystem read with its own
failure mode.

### `Release::of(tag, target)` — the tag is the version, and the name carries both facts

`Release::of("v0.1.0", "aarch64-apple-darwin")` answers a release: its `tag()`, its `version()`,
its `target()`, the `directory()` it is written into (`jobq-0.1.0-aarch64-apple-darwin`), the
`binaries()` it carries and the `checksums()` file it ships. Three refusals, in the order a reader
would say them out loud: a tag that does not start with `v` is not a tag of this project
(`refs/tags/v0.1.0` is a *ref*, not a tag), a tag whose version is not this crate's is a release of
something else (`v0.2.0` on a `0.1.0` tree), and neither is a name a call site may format by
itself — that is why the tool takes a tag and not a version.

The version in a release directory's name is not decoration: two builds of one version for two
targets are two files, and a name that carries one of the two facts is a name a mirror is free to
confuse with the other.

### `accepts(name, output)` — the binary has to say it is this release

Given the text a binary printed for `--version`, answer whether it is this release's version. The
version is the **last word of the first line** — `jobqd 0.1.0` — so a second line (a warning, a
build stamp) is not part of it, and a line with no version in it is a refusal rather than a match.
This is the check that catches the release assembled from a stale build, and it is why the tool
*runs* what it is about to ship instead of trusting the directory it was handed.

### `checksums(artifacts)` — a file, not a hash

One `<digest>  <name>` line per artifact, **two spaces**, sorted by name, every line ending in a
newline, and an empty set is an empty file rather than a broken one. Two spaces and the sort order
are the difference between a file `sha256sum -c` reads and a file a human reads: a tab is a file
`sha256sum -c` answers `no properly formatted checksum lines were found` for, an unsorted file makes
two runs over one release produce two different files, and a missing final newline makes `while
read` drop the last artifact. The checksum file is **not** an artifact of itself: a manifest that
covered itself could not be used to check anything.

### `verify(manifest, artifacts)` — both directions, or neither

Every artifact must have a line with its digest, **and** every line must name an artifact that is
here. The second half is the one that goes unnoticed: a manifest promising a file nobody built
looks like a manifest, and the machine that consumes the release fails much later, somewhere else.
A byte that changed is `ChecksumMismatch` carrying the file name and both digests — a report that
said "the release is corrupt" would send a reader to unpack it by hand. An artifact that is not in
the manifest is a file nobody checked, and an empty manifest is not evidence about anything.

### `changelog_ok(changelog, version)` — the account of itself

Three rules, in the order a reader would notice them: the version has a section of its own (`##
[0.4.0]`, or `## 0.4.0` with anything after it, and a `###` heading is not a section); the section
says something — at least one line that is not blank and not a comment, before the next heading; and
there are no notes left above it, because an `## [Unreleased]` heading that still *holds* entries
means the release did not promote them and the version it is publishing does not say what went out
with it. An empty `## [Unreleased]` at the top is exactly what a released tree keeps.

The rule is about the file's structure rather than about text: a version *mentioned* in a bullet
under `Unreleased` is not a section, and a checker that grepped for `0.1.0` would pass a changelog
that says nothing. This is also the half of `jobq/3.2-public-api-baseline`'s sentence that a gate
cannot read — "a breaking change costs a major bump and a line in `CHANGELOG.md`" is a promise to a
reader, and the line is this step's job.

### `Refusal` — the refusals, and the codes they leave behind

One enum for every way a release can be refused, with a `Display` that names the file, the line or
the version rather than saying "invalid release": the tag, the version, a binary that reports
something else, a missing or unreadable input, both directions of a checksum file, and the three
changelog refusals. It is called `Refusal` rather than `Refused` because `jobq/3.24-unsafe-budget`
already flattened a `Refused` into `jobq::engine` and two names cannot share one path; the probe for
this slot (`course/probes/release-artifacts.apply.rs`) spells its own standalone enum `Refused`,
which is a difference in the fixture rather than in the rule. `exit_code()` maps the variants onto
the classes `jobq/3.3-library-errors` wrote — `2` the call was wrong (a tag that is not this
project's, a tag of another version), `3` the thing asked about is not there (a binary that is not in
the directory the release is made from), `1` this deployment is broken (a binary that reports another
version or cannot be run, a manifest that does not match its files, a changelog that does not account
for the version).

### `src/bin/jobq-release.rs` — the tool

```text
jobq-release --tag v0.1.0 --target aarch64-apple-darwin --from target/release --out dist
```

Every flag is required except `--changelog`, which defaults to `CHANGELOG.md` and is resolved
against the working directory. What it does, in order: refuse a tag that is not this crate's
version; refuse a missing binary; run each binary with `--version` and refuse one that does not
report the release; refuse a changelog that does not account for the version; then write
`<out>/<directory>/` with the two binaries and `SHA256SUMS`, and print the checksum file's lines so
a pipeline log shows what was published. It does **not** build anything: the release build is
`cargo build --release` (or the pipeline's own step), and a tool that compiled would be a second
build with a second set of flags. `--target` is not guessed for the same reason the tag is not
typed twice: the name of the release is a decision, and a tool that inferred it would be the tool
that shipped the wrong one quietly.

### `CHANGELOG.md`, `docs/release.md` and `tests/release_harness.rs`

The changelog is the account of what went out: `## [Unreleased]` on top, then one section per
released version, newest first, each with what changed — the first release of this project is
`0.1.0`, and its section is the project as a user meets it rather than a list of commits. The page
is the procedure a person follows (`docs/release.md`): what a release is made of, the commands, how
a user checks what they downloaded, and where in a pipeline this job sits. The harness is the
course's instrument (`tests/release_harness.rs`): it runs the tool over the binaries this tree just
built, prints the counts below, and a learner who edits it is a learner editing the measurement —
`kiln reset jobq/3.25-release-artifacts` puts it back.

### What the spec judges

| the case | the claim |
| --- | --- |
| `the_tag_is_the_version_and_nothing_else` | `v0.1.0` is this project's tag, `0.1.0` is not a tag, `refs/tags/v0.1.0` is a ref, and a tag of another version is refused as such |
| `the_name_carries_the_version_and_the_target` | the directory names both facts, two versions or two targets do not collide, the two binaries are in the order a release lists them, and the checksum file is not one of them |
| `a_checksum_file_is_the_format_a_tool_reads` | two spaces, sorted, 64 lower-case hex, a trailing newline, empty for empty — and the two published SHA-256 vectors |
| `verification_is_both_directions` | a changed byte names the file and both digests, a manifest line with no file is an incomplete release, an unlisted file was never checked, and a reordered manifest still verifies |
| `a_binary_that_does_not_report_the_release_is_refused` | the last word of the first line is the version; a second line is not; nothing that looks like a version is a refusal |
| `the_changelog_has_to_account_for_the_version` | a missing section, an empty one, notes still under `Unreleased`, and a version mentioned in prose — against a promoted section that passes |
| `the_tool_writes_the_release_the_tag_names` | the real binaries, the real changelog: the directory, the three files, a manifest that verifies against the bytes that were copied, and the lines the tool printed |
| `a_from_directory_without_the_binaries_is_refused_and_named` | the missing file is named, the code is `3`, and nothing is written |
| `the_tool_wants_files_it_can_run` | a directory where a binary should be, and a file that reads fine and cannot be run: both are refused by name, with code `1` |
| `the_tool_refuses_what_it_cannot_release` | a usage error that names the argument, a missing flag, and a tag of another version — with the codes they leave behind |
| `a_release_that_cannot_be_written_is_this_machine_and_not_the_release` | an output directory that cannot be created is code `1` and a sentence saying what could not be done |
| `the_project_ships_a_changelog_that_accounts_for_this_version` | this tree's own `CHANGELOG.md` says what `0.1.0` is, with no placeholders left |
| `the_page_states_the_release_the_tool_produces` | `docs/release.md` names the two binaries, the checksum file, the changelog and the tag, and has no `TODO` left in it |

## DONE WHEN

- `kiln run jobq/3.25-release-artifacts` — the thirteen cases pass.
- `kiln check jobq/3.25-release-artifacts` — every must gate is green. The ones to read are
  `links` (the page and the changelog are project pages, and their targets have to resolve),
  `semver@baseline` (this step adds names to the surface and removes none) and `unsafe-budget@0`
  (`sha2` is safe code; the budget is still zero).
- `cargo build --release && cargo run --bin jobq-release -- --tag v0.1.0 --target <your target>
  --from target/release --out dist` — prints one `<digest>  <name>` line per binary and writes
  `dist/jobq-0.1.0-<target>/`. Then `cd dist/jobq-0.1.0-<target> && sha256sum -c SHA256SUMS` (macOS:
  `shasum -a 256 -c SHA256SUMS`) says OK twice, which is the whole point of the format.
- `cargo test -p jobq --test release_harness -- --nocapture` prints `jobq-budget artifacts=2`,
  `jobq-budget checksum_lines=2`, `jobq-budget unverified_max=0` and `jobq-budget extras_max=0`.
- `cargo run --bin jobq-release -- --tag v0.2.0 --target <your target> --from target/release
  --out dist` exits `2` and says which version this tree is — the refusal a release job is supposed
  to hit when the tag and the manifest disagree.

## TRAP

1. **A tag built at the call site.** `format!("v{version}")` in the tool, in the pipeline YAML and
   in the page is three copies of one string, and the copy that goes stale is the one in the tag.
   The version lives in `Cargo.toml`, `VERSION` reads it at compile time, and the tag is *checked*
   against it rather than composed from it.
2. **A checksum file with a tab.** `sha256sum` writes two spaces; an editor, a YAML block or a
   formatter often writes a tab, and `sha256sum -c` then answers `no properly formatted checksum
   lines were found`. The file is for other people's tools, not for reading.
3. **Verifying one direction.** Checking every file you have against the manifest passes a manifest
   with a line missing, and the missing line is the artifact somebody else is about to download.
   The manifest naming a file nobody built is the failure that reaches a user.
4. **Hashing the name instead of the bytes.** A digest taken over the path, the artifact's name, or
   the name plus the length is a checksum a rename changes and a corrupted download keeps. The
   digest is over the bytes that were read, and the spec's vectors are what says so.
5. **A manifest that lists itself.** `SHA256SUMS` inside `SHA256SUMS` cannot be checked by anything:
   the file's own digest changes when the line is written. Two files and one manifest is the shape.
6. **Reading `--version` with `starts_with`.** `jobqd --version` prints `jobqd 0.1.0`; a check for the
   *name* passes whatever version follows it, and a check for `contains("0.1.0")` passes a binary
   that reports `0.1.0-rc1-broken`. The version is the last word of the first line, and anything
   else is a refusal.
7. **The stale build.** `--from target/debug` after a `cargo build --release` packages yesterday's
   binary, and nothing in the file says so: the version check is the only thing between the tag and
   a file that lies about itself. It is also why the tool refuses a binary it cannot *run*.
8. **`Unreleased` promoted by editing the heading.** Writing `## [0.1.0]` above notes that were left
   under `## [Unreleased]` gives a release whose section is empty and whose notes are another
   release's: the tool checks the section, not the version string.
9. **A changelog checked by grepping.** `changelog_ok` looks for a section *heading*; a changelog
   that mentions the version in prose, or in a `###` subsection, has published a number without
   saying what is in it.
10. **Editing the harness or the baseline.** `tests/release_harness.rs` is the course's file and
    `course/tracks/jobq/budget/3.25-release-artifacts.toml` is the copy the gate reads: editing
    either changes the instrument, not the release. `kiln reset jobq/3.25-release-artifacts` puts
    the harness back.
11. **A page with the commands in it and none of the reasons.** `links` checks that the targets
    resolve and the spec checks that the names are the code's; neither can tell you whether the
    page explains *why* the tag and the manifest have to agree. Write the page for the person
    releasing at 3 a.m. with a failing job in front of them.
