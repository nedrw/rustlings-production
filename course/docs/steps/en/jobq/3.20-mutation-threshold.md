# Mutation testing: prove the specs are not decoration

## WHY

A green suite says that the cases you wrote pass. It says nothing about the cases you did not write,
and nothing about whether the cases you did write would fail if the rule under them changed. That is
the expensive half of testing, and it is invisible: a suite that asserts nothing has the same
green check as a suite that asserts everything, and a reviewer reading a diff sees the first one
only on the day it matters.

There is a way to ask, and it is the one thing in a build report that measures the *tests* rather
than the code: change the rule in one place — a comparison, a boolean, a constant — build it, and run
the suite. A changed rule that the suite fails on is a rule the suite is really watching. One it
shrugs at is a case nobody wrote, and the change is in the tree with every light green.

The number that comes out of that is only worth what its denominator is worth, and this step is as
much about the denominator as about the count: a share of three mutants is not the evidence of a
share of forty, a share of nothing is not a number at all, and a build that looked at nothing must
not be reported as a build that failed.

## RECALL

- `test/property-based@apply` — `jobq/3.19-property-invariants`: the machine that can answer *no*.
  This step is what happens to that answer: a mutation run is that walk pointed at rules somebody
  changed on purpose, and the score is the count of the ones it came back with.
- `test/integration-layering@apply` — `mailer/1.19-test-layering`: what the suite is made of. **This
  step does not re-teach it.** What is new is the verdict — which parts of that suite would notice a
  changed rule, and what to do about the ones that would not.

## DELTA

Two things arrive, and they are the two halves of the same decision: **the arithmetic a build is
held to**, and **the run that produces its inputs**.

- **The rule is a threshold and a floor.** A threshold on its own is met by a run that judged three
  mutants well, so the policy carries two numbers, and the verdict has three answers rather than
  two: `passed`, `failed` and — for a run below the floor — `unproven`. The third one is the
  decision this step is really about. "The suite is not good enough" and "there is not enough
  evidence to say" send a maintainer to different places, and a boolean gate has to fold one of them
  into the other, which is how a class of defect turns into an afternoon of the wrong work.
- **The score is a share of the judged.** A mutant whose site does not compile says nothing about
  the suite, so it is outside the fraction rather than inside it as a survivor; and an empty run has
  no percentage at all (`None`, not `0`), because a `0%` compares with a threshold like any other
  number and reports "looked at nothing" as "worst possible".

`caught` is where the two steps meet: the invariants of `jobq/3.19-property-invariants` are the
suite, a table of changed models is the mutants, and a mutant is killed when one invariant comes
back with a counter-example. One seed for the whole run, because two runs have to be comparable —
a suite whose score depends on the weather is a suite nobody can hold a threshold against.

## TASK

The scaffold added one module and **nothing declares it yet**: wiring `src/engine/mod.rs` the way
`jobq/3.19-property-invariants` wired `walk` is your first decision, and until it is made the spec
does not compile. Five pieces, and every one of them is a decision about what a number *means*.

### `Score` — how many, and out of what

The denominator is `killed + survived` and nothing else: it is what was *judged*. A mutant that did
not build or did not finish is in neither count, because counting it as a survivor would let a
project raise its score by making its own code unbuildable. `percent` answers `None` for an empty
run — `checked_div` is the whole of that decision, written where it happens — and it truncates,
because a threshold of 80 is a decision about whole percent and rounding up would let a run one
mutant short of it read as a pass.

### `MutationPolicy` — a threshold, a floor, and three answers

`judge` compares with `>=`, because a threshold of 80 is *met* by 80%; it answers `Unproven` below
the floor, and it raises the floor to one judged mutant whatever the configuration says: a run that
judged nothing has proven nothing, and that is not a setting. `is_satisfiable` is the review's half
— "nobody can meet this" has exactly two shapes, a threshold above 100 and a floor of zero — and the
two methods are deliberately separate: the arithmetic is what a build does, and the review is what a
person does.

### `Survivor` and `Report` — a score somebody can act on

A survivor carries the file, the line, the column and the rewrite that lived — the same four things
`kiln`'s own gate prints, so a report from the tool and a report from this project read the same.
The column is part of it: one line can hold two of the same operator, and a report that named only
the line would name the same place twice. `Report::of` takes the survivors rather than deriving them
from the count: the run knows which mutants lived, and a report that reconstructed them from a
number would hide the case where the two disagree.

### `caught` — the run itself

One walk per mutant, per invariant, with the `walk`/`Model`/`Invariant` machinery of
`jobq/3.19-property-invariants`, and a mutant is killed when one invariant comes back with a
counter-example. This is the whole of mutation testing, and it is three lines: everything a real
tool adds on top is bookkeeping — where to apply the change, whether it builds, how long to wait —
and the bookkeeping is why the tool is worth having.

### What deliberately does not change

The walk and its model (`jobq/3.19`), the engine's table, and every earlier suite. If a `DONE WHEN`
line below fails, this arithmetic and the walks it is fed disagree — and *that* is the defect this
step is shaped to catch.

## DONE WHEN

- `kiln run jobq/3.20-mutation-threshold` — the nine cases pass: the score and its empty run, the
  policy nobody can meet, the boundary where 80% meets 80, the three words, the survivor's place,
  the three shapes of a report line, a table of planted defects scored against the property from
  the step before, and the suite that cannot fail scoring zero.
- `kiln check jobq/3.20-mutation-threshold` — every must gate is green, including `clippy@4`.
- `kiln selftest jobq/3.20-mutation-threshold --track jobq` (or `kiln verify jobq --slow`) — the
  slow path runs `slow:mutants@80`, which mutates **this step's own module** and runs these cases
  against every mutant it takes: the line in the report is the score, and a survivor names the
  place and the missing assertion. A module whose rules can be changed without a case noticing is
  the defect that gate exists to report.

## TRAP

1. **`>` where `>=` belongs.** It is the whole difference between a threshold of 80 and a
   threshold of 81, and it passes every case that does not sit exactly on the line: a run that
   killed exactly 80% of what it judged is reported as a failure, and the fix somebody reaches for
   is to lower the threshold.
2. **A score of `0%` for a run that judged nothing.** The number is then a number a dashboard can
   chart, and it says "worst possible" about a build that never looked. `percent` answers `None`,
   and the report says which of the two problems it is.
3. **Two answers instead of three.** Folding "not enough evidence" into "failed" sends a maintainer
   to write a case for a mutant that was never judged — which is the opposite of what the report
   knows.
4. **A threshold with no floor.** Three mutants, all killed, is 100%, and the gate that accepts it
   is a gate a project passes by sampling less. The floor is what makes the percentage evidence
   rather than a ratio.
5. **A survivor with no place.** "1 of 6 survived" is a line nobody can act on. The report is the
   half of mutation testing that gets used, and it has to name the file, the line, the column and
   the rewrite that lived.
6. **Mutating the code inside the spec.** Writing a case that edits a file, rebuilds the crate and
   runs itself is a compiler inside a test: it is slow, it is flaky, and it is the bookkeeping that
   the gate (`kiln check … --slow`) and `cargo-mutants` in a real project already do.
7. **A mutant run that never finishes.** The gate runs this step's cases once per mutant, and a
   case that waits for a condition with no deadline turns one mutant into a timeout — for every
   mutant, on every machine, for everybody. Bounded loops and condition-with-deadline waits are
   `jobq/3.19`'s rule; they are also what keeps this step's own gate affordable.

  with a floor" rather than on a single number.

  against a table of planted defects.

  *model* rather than a text edit: a rule is a value in this crate.
