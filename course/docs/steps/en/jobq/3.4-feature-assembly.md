# Feature flags that assemble one engine, not one program per feature

## RECALL

- `cfg/layered-config@apply` — `mailer/1.4-config`: defaults underneath, a file next, the environment
  on top, flags last, and `--check-config` printing what the process actually decided. That is how
  one *binary* answers "which settings do I have?" at run time. A feature answers the same question
  one level up, and earlier: which code is in the binary at all.
- `api/library-design@apply` — `jobq/3.2-public-api-baseline`: the surface is what `jobq::engine`
  re-exports, the store port is sealed, and `jobq/3.3-library-errors` gave that surface an error type
  a caller can branch on. A feature changes what is *behind* that surface, which is the one thing
  the baseline cannot see: the same `Engine`, assembled with less in it.

## DELTA

A service solves "some deployments need the database and some do not" by reading a flag. A library
cannot: the database driver has to be *absent* from the build, or it is in the binary of every caller
that only ever wanted the in-memory queue. So the crate learns to be assembled, and the difference
from layered configuration is the direction of the decision:

- **the layer is chosen at compile time, by whoever depends on the crate.** `cfg` is not a runtime
  `if`. A caller that does not want the durable backend asks for it with
  `default-features = false`; a caller that wants it gets it by doing nothing. Nobody has to pass a
  setting through, and no deployment can forget one.
- **features are additive, and that is a design constraint rather than a slogan.** Nothing may be
  spelled "without": not "postgres off", not "metrics disabled". The rule exists so that two
  callers who want two different things get the union — `jobq` with `postgres`, and something else
  that also wants `metrics`, cannot end up in a build where one of them silently loses.
- **one crate, several assemblies.** The failure mode this step is against is the fork: a
  `jobq-memory` package and a `jobq-postgres` package that drift apart until their `Engine` types are
  not the same type. Every assembly here is the same crate, the same `Engine`, the same port — and
  the matrix of combinations is checked rather than trusted.
- **the in-memory engine is the floor.** Every assembly can run a job. That is what makes
  `--no-default-features` a *useful* build rather than a broken one, and it is the property the spec
  runs a caller against in each combination.

What the gate holds *today* is one seam, and it is small on purpose: the durable backend is not
written yet (`jobq/3.5-store-port-conformance` writes it), so what the feature decides is which
build the crate is — and the one thing such a build must never do is leave an operator guessing.
Adding a second feature now (`metrics`, `tracing`) would be a flag for code that does not exist: the
engine has no metrics to switch off and the daemon's logging is not optional (`mailer/1.6`), so the
honest number of features for this crate today is one.

## TASK

- Add a `[features]` table to `Cargo.toml`: `default = ["postgres"]` and `postgres` as a list.
  Default-on, because the plain `cargo build` — what a dependent, a `cargo install` and every later
  step of this track uses — has to be the whole engine.
- Write the table inside a `kiln:scaffold:begin` / `kiln:scaffold:end` block, and keep `postgres` as
  a list, one entry per line. That is not decoration: `jobq/3.5-store-port-conformance` wires the
  durable backend's dependency into that list, and a scaffold may only insert lines inside a marked
  region (docs/authoring.md §5).
- Put the `cfg` in the one place the durable backend is reached from: `open_store` hands a durable
  URL to a function whose body is the seam, and a `#[cfg(feature = "postgres")]` decides which
  answer this build gives when the backend is asked for.
- Make the answers say which build this is. A build without the feature has to refuse a durable
  store *by naming the missing feature* ("rebuild with `--features postgres`"), not by repeating the
  connection string back: an operator with a database is not helped by being told to use `memory`.
- Change nothing else for the feature: the in-memory engine, the port, the error type and both
  binaries are the same in every assembly, and `cargo build --no-default-features` has to produce a
  daemon that drains a memory queue.

## DONE WHEN

- `kiln run jobq/3.4-feature-assembly` — the spec passes: the manifest names the feature and turns it
  on, every assembly builds with its own unit tests, a caller runs a job in each one, and the
  assembly without the feature refuses a durable store by name.
- `kiln check jobq/3.4-feature-assembly` — every must gate is green, `clippy@3` and
  `semver@baseline` included (the surface of `jobq/3.2` is unchanged by this step, and the witness
  is what says so).
- `cargo build -p jobq --no-default-features` in `app/jobq` — the in-memory engine alone, then
  `cargo build -p jobq --all-features`.

## TRAP

1. **A `cfg` that is missing from one call site.** Gating the durable path in the library and
   leaving one reference in `src/bin/jobqd.rs` behind: `cargo build --no-default-features` fails with
   `error[E0433]: failed to resolve: use of undeclared crate or module`, and the build that breaks
   is the one nobody runs by hand — which is why the spec builds the daemon in every combination.
2. **Refusing a durable store in the terms of the *other* build.** Keeping the old message ("use
   `memory`, or wait for the durable backend") in a build with no feature looks like it names the
   problem — the connection string in it contains `postgres` — and the spec strips the URL out
   before it reads the message, then fails with *"the refusal has to name the missing feature
   (`postgres`) as a feature"*. What the operator needs is the flag to rebuild with, not their own
   connection string read back to them.
3. **A feature that only builds next to another one.** Gating the daemon's store factory on
   `postgres` while its *call site* assumes the feature is on makes
   `cargo build --no-default-features` fail with `error[E0425]: cannot find value … in this scope`,
   and `--no-default-features --features <one>` is worse: it compiles in the combination its author
   tried. That is why the spec builds every feature on its own line of the matrix, not only the
   three convenient ones.
4. **Pulling the driver in anyway.** Making `sqlx` a normal dependency ("it is simpler than an
   optional one") puts the database in the binary of every caller who wanted only the queue: the
   build is green and the feature means nothing.
5. **Assuming the default build.** Running `cargo test -p jobq` and stopping there proves one
   assembly. `cargo build --no-default-features` is the one that finds the missing `cfg`, and
   `--all-features` finds the `cfg` that was never exercised together with the others.
