# 供应链策略：许可证白名单，与默认拒绝的 unsafe 预算

## 为什么

这个服务发布出去的每一行代码都是别人写的。`relay` 在 `Cargo.lock` 里有 202 条记录，其中一条是这个项目；
其余每一条都是一个 crate，由某个人发布，带着某个律师有意见的许可证，来自这个仓库里没人选过的源。这不是
一个待解决的问题——这就是这笔交易——但它是一组决定，而一个没有写下来的决定，就是夜里十一点加下一个
依赖的人顺手替你做的决定。

这些决定里有两个就是这一步，而两者的形状一样：**默认是拒绝，例外要一个个点名**。

第一个是一份**许可证白名单**。它要防的失败不是一场官司，是安静的那一种：一个 crate 带着本服务发布不了的
copyleft 许可证进了树，编译一切正常，测试全过，三个月后问题在发布评审上冒出来——那时这个依赖已经
扛着要紧的活，修法就是重写。一份封闭的白名单，把它变成加进这个依赖的那个提交上的一次构建失败，而那
是这个决定唯一便宜的时刻。

第二个是 **`unsafe` 预算**，`unsafe/budget@aware` 就落在这里：不是把"我们从不写 `unsafe`"当成编码规范
里的一句承诺，而是在 crate 根上写 `#![forbid(unsafe_code)]`，让编译器来拒绝。库和二进制是两个 crate
根，写在一个根上的属性管不到另一个——只盖住一半代码的预算，是一份漏了个洞的预算。`aware` 的那一半，是
知道这个属性要付出什么，以及在真需要例外时你得走到哪儿去：依赖里的 `unsafe` *不*归它管（它 `forbid`
的是**这个** crate），而有意花掉这份预算的方式，是写下理由、说清一个掂量过的需求，再加一个评审者看得
见的 `#[allow]`——绝不是悄无声息的那一个。

两个邻居，都不是这一步。`repo/toolchain-pinning@apply`（`mailer/1.2-toolchain`、
`relay/2.1-project-skeleton`）钉住的是*用什么编译*这个项目——编译器、edition、格式化、lint。这里钉住的
是*进去的是什么*，而两种钉法在种类上就不同：工具链文件管的是机器，策略文件管的是别人的代码。
`ci/pipeline@apply`（`mailer/1.3-ci`）是这类策略被*执行*的地方，而这一步的答案故意小一些：策略文件谁
都能离线读，所以这一步靠读它来判，而管住整张依赖图的那个工具，是一道在各处都装上之前一直停在 *should*
的闸门。

## 任务

脚手架放好了一个文件，它就是交付物：`deny.toml`——策略本身，凡是一个决定的值都留空。

### `deny.toml`

三个小节，每一节都在回答一个今天有答案、明天就没人答得上来的问题：

- **`[licenses] allow`**——这个项目接受的许可证的封闭清单，写的是 SPDX *表达式*而不是单词：
  `MIT OR Apache-2.0` 满足其一即可，`A AND B` 两个都要，而 `Apache-2.0 WITH LLVM-exception` 本身就是
  一种许可证。`confidence-threshold` 是工具要把一个许可证文件读成那种许可证，得有多大把握；
- **`[bans]`**——`wildcards = "deny"`（一个 `*` 要求，就是一个人人无从评审的依赖），
  `multiple-versions = "warn"`（两个版本的 `syn` 花掉构建时间，却一点也改变不了这个服务发布的东西），
  以及 `deny = [...]`：那些无论谁带进来、都不许出现在这棵树里的 crate。对这个服务来说，它们是
  系统链接的 TLS 栈：客户端是手写的（`relay/2.7-outbound-client`），根本没有 TLS 后端，所以要有哪个
  经由传递依赖混进来，就该是一个被明说出来做的决定；
- **`[sources]`**——`unknown-registry = "deny"`、`unknown-git = "deny"`，以及
  `required-git-spec = "rev"`：来自没人点名的 registry、或来自没人点名的 git URL 的 crate，是一个
  背后没有评审流程的 crate，而依赖 `branch = "main"` 的 git 依赖，是一个会在构建过程中变掉的依赖。

### `src/lib.rs` 与 `src/main.rs`——`unsafe` 预算

每个 crate 根上一行属性：`#![forbid(unsafe_code)]`。这个项目有两个 crate 根，所以两处都要写，而规格
两处都查。

### 规格判什么，又故意不判什么

`cargo-deny` 不是每台机器上都装着，而一道跑不起来的闸门，绝不能把一个好端端的步骤判红——这就是这一步
元数据里那道 `?deny` *should* 闸门，它在后面某个里程碑之前一直是一道 should 闸门。规格换了一个做法：在
跑它的那台机器上**离线**判这份策略：

1. 策略能解析，白名单不为空，`[sources]` 是拒绝，`[bans]` 有一份真的禁用清单——一份值全是 `TODO` 的
   文件什么也没说；
2. **白名单覆盖得住这棵树。** 规格读 `Cargo.lock`，在 cargo 解到 registry 缓存里的那份拷贝中找到每个
   crate 的 manifest，再用和工具相同的那套表达式规则（包括 `OR`/`AND`/`WITH` 和已弃用的 `/`），把声明
   的每个许可证对照白名单查一遍。它拒绝接受一次几乎什么都没判到的检查，所以 registry 缓存挪了位置就是
   失败，不是一次无声的通过；
3. **禁用清单今天成立**：策略禁掉的 crate 不在 lock 文件里；
4. **预算写明了，而且是空的**：两个 crate 根都带着这个属性，而 `src/` 底下 `unsafe` 关键字的个数——
   去掉注释和属性自己那处拼写——是零。

凡是规格量的是*结构*而不是行为的地方，它都在文件里说明理由（authoring.md §6.6）：策略文件不是问一个
跑着的服务就能问出来的东西，而 `spec/` 是只读的，所以那些替代做法——往学习者的树里写一个故意不健全的
文件、看编译器拒它，或者在 `cargo test` 里起 `cargo metadata`——代价都超过这次检查本身的价值。

## 完成标准

- `kiln run relay/2.21-supply-policy` — 规格通过（五个用例：策略自身的形状、树对许可证白名单、禁用
  清单对 lock 文件、`unsafe` 预算，以及表达式读取器本身）
- `kiln check relay/2.21-supply-policy` — 每个 must 闸门都是绿的；`?deny` 报告自己跑不了，而不是报告
  失败，should 闸门就是干这个的
- 工具没装时，`kiln doctor` 会点名 `cargo install cargo-deny --locked`（安装命令该在那一行上，不在
  段落里）
- 装好 `cargo-deny` 之后：`cargo deny check licenses bans sources` 在这棵树上干净，而加一个许可证不在
  白名单里的依赖会让它失败——那是证明这个文件确实接上了什么东西的变异
- 你要是在 `src/` 底下任何地方放一个 `unsafe { }` 块，`cargo check -p relay` 会失败，因为
  `unsafe_code` 被拒；而失败信息会点名是哪个 crate 根禁掉了它

## 陷阱

1. **从博客文章里抄来的白名单。** 一个这个项目里没人读过的许可证，就是一次顺手给出的许可：
   `allow = ["MIT", "Apache-2.0", "GPL-3.0"]` 能通过这一步规格里的每一项检查，却是一个没人做过的
   决定。清单短，是因为每一条都是对一个问题的回答。
2. **`unknown-registry = "warn"`。** 这是默认值。它对一个来自没人点名的 registry 的 crate 打一行
   提示，然后以零退出——而一份策略存在的目的，正是终结这种状态。要么 `deny`，要么什么都不写。
3. **一条已经被违反的禁令。** `deny = ["openssl-sys"]` 摆着，而有东西已经把它拉进了树，这是一份没人
   读过的策略；规格的第三个测试就是抓它的，而答案是有意地移掉那个依赖，或者移掉那条禁令。
4. **`#![forbid(unsafe_code)]` 只写在 `lib.rs` 里。** 二进制是第二个 crate 根，这个属性够不到它：
   `main.rs` 里的 `unsafe` 照样编译通过，而库看上去受着保护。两个根，两行属性。
5. **把这份预算和依赖的预算搅在一起。** `forbid(unsafe_code)` 是这个 crate 的规矩。`serde` 里有
   `unsafe` 块，以后也还会有，而那不是这个属性在说的事——那个问题在供应链上的答案另有一个（审计你
   依赖的东西），硬说这个属性盖住了它，正是一个项目最后对自己的构建信了假话的方式。
6. **把 `confidence-threshold` 调低，好让检查通过。** 它说的是工具对一个许可证*文件*就是它以为的那个
   许可证要有多大把握：调低它，是让检查靠猜变绿，而猜正是这项检查要防的东西。
7. **把许可证表达式当字符串读。** 白名单里只有 `MIT` 时，`MIT OR Apache-2.0` 是*没问题*的——项目按
   MIT 收下它。拿整个表达式去 grep 的检查，会在那些许可比策略还宽松的 crate 上失败，而人们第一反应
   想到的修法，是把白名单放宽到一点意思都没有。
8. **事故里加上去的 git 依赖。** 不带 specifier 的 `git = "…"` 跟的是默认分支：昨天的构建和今天的
   构建是不同的代码，而没有任何评审者看见这个差别。如果非得是 git 源，就把修订钉住——
   `required-git-spec` 就是干这个的。

## 延伸阅读

- [cargo-deny: the book](https://embarkstudios.github.io/cargo-deny/) — 文件里的每个字段，以及每项
  检查实际在做什么
- [SPDX licence expressions](https://spdx.github.io/spdx-spec/v2.3/SPDX-license-expressions/) —
  `allow` 是按什么语法（`OR`、`AND`、`WITH`、括号）读的，以及为什么这不是一次字符串比较
- [SPDX licence list](https://spdx.org/licenses/) — 那些标识符，以及为什么 `MIT` 和 `MIT-0` 是
  两种不同的许可证
- [The Rust reference: `unsafe`](https://doc.rust-lang.org/reference/unsafe-keyword.html) — 这个
  关键字究竟允许什么，好让这份预算是一份预算，而不是一种迷信
- [Rust Secure Code WG: `unsafe` guidelines](https://rust-lang.github.io/unsafe-code-guidelines/) —
  一份要花这份预算的理由里必须有什么
- [Cargo book: source replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html)
  — `unknown-registry = "deny"` 真正管的是什么：一个镜像、一个 vendored 目录，以及你的构建所编译
  的东西来自哪个源
