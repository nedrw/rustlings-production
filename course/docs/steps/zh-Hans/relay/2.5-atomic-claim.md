# 原子地认领工作：FOR UPDATE SKIP LOCKED

## 为什么

`mailer/1.15-idempotent-delivery` 已经在发送之前认领了一行，这一步不重讲那台状态机——它加的是那
一步可以侥幸不做的部分：一次能让八个 worker 同时跑的认领。那里的队列一次只放一条消息；这里是一批，
谁先到谁取，而哪一行归谁，由行自己说出来。

一个被接受的事件是一笔债：它的租户注册的每个端点，都欠着一次投递，而这笔债必须挺过一次重启。于是
队列是一张表，worker 是一次查询。最直觉的查询是两条语句——先读出看着没人要的行，再把你取走的那些
标上——而它错的方式，只在真正要紧的时候才现形：

- **两个 worker 读到同一批行。** 两边都看到 `pending`，都认定这些行是自己的，都发出去。订阅者把
  一个业务事件收到了两遍，而除非*它*自己去重，否则分不清这是重复还是一个新事件。故障处理期间、刚
  把额外的 worker 起起来的那一刻，恰恰是这件事发生的时候；
- **锁取得太早，什么都停住。** 没有 `skip locked` 的 `for update` 会让第二个 worker 等第一个的
  事务，于是不管你起了多少个 worker，吞吐只有一个 worker。一个在整个 HTTP 请求期间都握着的锁，就
  是一个握了几秒的锁；
- **死掉的 worker 会永远攥着它的行。** 一次认领如果只是改状态、而不是一份*租约*，`kill -9` 之后
  留下的就是一些 `claimed` 的行，没人收尾：一个订阅者从此什么都收不到，而表里没有任何东西说明
  原因。

所以认领是一条语句，而它就是这一步的全部：数据库挑出工作、盖上谁持有它的章，再把取走了什么答复
回来——这一切都发生在任何一个 worker 拿到可以据以行动的 id 之前。

## 任务

脚手架加了 `src/claim.rs`：常量、类型，以及五个函数体是 `todo!()` 的签名。表、模块声明，还有这
五个实现，归你写。

这一步故意既没有 HTTP 表面，也没有 worker 循环：*认领*本身意味着什么，在这里单独评判；把一次认领
送到订阅者那里，是 `relay/2.6-at-least-once` 的事。规格之所以自己写投递行，原因也在这里——生成
这些行的扇出归下一步。

### `migrations/0005_deliveries.sql`

一张表 `deliveries`，每个工作单元一行，带上认领和状态机需要的列。下面这些名字就是契约——规格会用
`psql` 直接读这张表：

- `id uuid primary key`；
- `event_id uuid not null references events (id) on delete cascade` 和
  `endpoint_id uuid not null references endpoints (id) on delete cascade`：一次投递要是没有它的
  事件或它的订阅者，就不是工作，而是孤儿；
- `state text not null default 'pending'`，取值是 `pending`、`claimed`、`sent`、`retrying`、
  `dead` 之一；
- `attempts integer not null default 0`：已经有几次尝试**失败**了；
- `next_attempt_at timestamptz not null default now()`：这一行最早能被取走的时刻；
- `locked_by text`、`locked_at timestamptz`、`lease_expires_at timestamptz`：谁持有它，持有到
  什么时候。没人持有时，三个都是 null；
- `last_error text`：最近一次失败，给人看的；
- `created_at timestamptz not null default now()`；
- 在 `(event_id, endpoint_id)` 上的**一条唯一约束**，以及一个索引，顺序就是认领读取的顺序（先
  `next_attempt_at`，再 `id`）。索引的顺序就是 `order by` 的顺序——否则每个 tick，数据库都要把
  这个租户历史上欠过的每一次投递全排一遍。

### `src/lib.rs`

声明模块：`pub mod claim;`。

### `src/claim.rs`

- `claim(pool, worker, limit, lease)`——**一条语句**。取最多 `limit` 行——状态是 `pending` 或
  `retrying`、`next_attempt_at` 已经过去、最老的先取，而且只取没被别人持有的行；盖上
  `state = 'claimed'`、`locked_by`、`locked_at` 和 `lease_expires_at = now() + lease`；最后把
  工作答复回来。让两半变成同一个决定的，是那条给行盖章的 `update` 里面的
  `select … for update skip locked`。
- 答复是每行一个 `Claimed`：投递 id、`attempts`、**目标**和**事件**。把它们 join 进认领的
  `returning` 子句，每个 tick 就只要一条语句，而不是每行一次查询；同时这也消掉了那行可能在两次
  查询之间变掉的窗口。
- `release(pool, delivery, worker)`——把一次认领交回去：这一行重新变成 `pending`，留给下一个来取
  的人。只有 `locked_by` 里点名的那一个 worker 做得到，而它会回答有没有行被改动。
- `mark_sent(pool, delivery)`——订阅者收下了：变成 `sent`，锁全部清空。只有 `claimed` 的行会动，
  所以一个迟到的 worker 没法让一个别人已经做完的投递复活。
- `mark_retry(pool, delivery, why, next_attempt_at)`——一次失败的尝试：变成 `retrying`、
  `attempts + 1`、`last_error = why`、`next_attempt_at` 按调用方给的值，锁全部清空。时刻之所以是
  参数，是因为*等多久*是一项策略，不归这一步管（那是 `relay/2.8-retry-budget` 的事），也因为
  一个能传它的测试，也就同样能传一个已经过去的时刻。
- `mark_dead(pool, delivery, why)`——放弃：变成 `dead`，原因留着。跟 `sent` 一样是终态。把它终结
  的那次尝试和别的失败一样计数，所以不管最后停在哪个状态，`attempts` 回答的都是"这次投递失败了
  几次"。
- 所有会改动某一行的写入，都归这个模块。第二个知道这些列名的文件，就是第二个会漏掉某一列的地方。

## 完成标准

- `kiln run relay/2.5-atomic-claim` — 规格通过
- `kiln check relay/2.5-atomic-claim` — 每个 must 闸门都是绿的
- `cargo test --test spec_claim workers_claiming_at_the_same_time_never_hold_the_same_row`——同一个
  连接池上的八个 worker，各自拿回来的集合互不相交，而它们的并集正是所有到期的行
- `psql -c "select indexdef from pg_indexes where tablename = 'deliveries'"` 显示一个索引，列是
  `(next_attempt_at, id)`
- `psql -c "select state, count(*) from deliveries group by state"` 显示规格跑完之后没有一行留在
  `claimed`：测试做过的每一次认领都有回音

## 陷阱

1. **先读，再写。** `select id … where state = 'pending'`，然后 `update … where id = any($1)`，
   是两个决定，中间隔着一道缝；落在这道缝里的 worker，每一个都会挑到同一批行。规格的八个 worker
   就是复现：同一次投递从其中两个那里回来，而服务里没有任何东西说一声——订阅者只是把事件收了两遍。
2. **`for update` 不带 `skip locked`。** 结果正确，但串行化了：第二个 worker 去等第一个的锁，而
   不是去取下一行。规格算出来的并集是缺的——worker 们彼此排队，而一个慢订阅者（事务里的一个 HTTP
   请求）会让每个 worker 都和最慢的那个一样慢。
3. **锁跨过了投递。** `begin; select … for update; … send the event …; commit;` 会让行锁握满一个
   HTTP 请求那么久。认领做成一条语句，正是为了让任何锁都不会比认领本身活得更久。
4. **无视 `next_attempt_at`。** 取一行还没到时刻的，就丢掉了服务对一个请求过喘息空间的订阅者许下
   的承诺：它一边恢复一边被猛捶，而重试的历史从此不再说明任何问题。规格里那些还没到期的行，必须
   留在 `pending`。
5. **可认领的状态里漏了 `retrying`。** 于是一次失败就成了一次永不再试的投递——这一行不是
   `claimed`，所以它没卡在某个 worker 手里；也不是 `pending`，所以任何认领永远看不到它。从第一次
   失败起，无声无息。
6. **没认领就记结果。** 一条没有 `state = 'claimed'` 守卫的
   `update deliveries set state = 'sent' where id = $1`，会让一个丢了认领的 worker 覆盖它的继任
   者正在做的事——也会让一个迟到的答复把一行从 `sent` 或 `dead` 里挪出来。规格会对没人认领的行
   调用 `mark_sent`，期望它回 `false`、并且什么都没变。
7. **`attempts` 在认领时增长。** 如果认领把这次尝试也算进去，一个第五次才成功的投递就烧掉了一个
   失败了四次的投递的整份预算，于是重试上限开始埋葬那些只是慢的投递。`attempts` 只在记录失败的
   地方增长。
8. **没有租约，或者租约没人读。** 一个在认领和答复之间被杀的 worker，会留下一些后面没有 worker 的
   `claimed` 行：订阅者再也收不到事件，而表里没有任何线索能指出该怪谁。让恢复成为可能的，正是
   `lease_expires_at`——回收过期的租约是 `relay/2.15-shutdown-leases` 的事。
9. **扇出跑了两遍，谁都没发现。** 认领的每一部分都可以是对的，订阅者照样会收到同一个事件两次，因为
   一个 `(event, endpoint)` 有了两条投递行。让重跑一遍的扇出变成空操作的，是
   `unique (event_id, endpoint_id)`——规格会插入那条重复行，并期望数据库拒绝它。
10. **索引顺序不对。** 只有 `(state)`，或者只有 `(id)`，会让认领每个 tick 都把客户的全部历史排一
    遍：答案是对的，代价随租户增长，而没有一个测试会察觉——所以这一步的规格要去读 `pg_indexes`。
