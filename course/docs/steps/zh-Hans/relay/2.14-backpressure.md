# 有界并发：队列有个底

## 为什么

事件照来，不管有没有人能被够到。这就是这个服务许下的承诺——现在接受，稍后投递——而在负载之下，它
产生了一个直到为时已晚才有人问的问题：

> 这些活里，有多少在*这个*进程里？

三个不同的数字都能回答它，而一个服务会死于把它们混为一谈：

- **没人投递的那些行。** `deliveries` 就是队列，它的深度是运维读得到的一个数字。它允许增长：整个设计就
  是让它增长，因为一个停了一小时机的订阅者，不该拦住它后面的事件被接受。它不可以做的是*永远*长下去——过
  了某个界，对下一个事件的诚实回答是 `503`，*再回来*，而不是再加一行没人会去处理的行；
- **这个 worker 认领的那些行。** 一次认领把行挪到 `claimed`，而一行 `claimed` 在租约到期之前对别的每一
  个 worker 都不可见。那是"一次一个尝试"的正确机制，却是一个不该变大的数字：一个认领了五千行、然后挨个
  尝试的 worker，用五千个任务在内存里攥着五千行谁也碰不了的行；
- **真正在途的那些尝试。** 这是决定进程生死的那个数字。每一次在途尝试都是一个 socket、一个缓冲、一个任
  务；一千次就是一个内存画像，而它在队列指标里*看不见*，因为那些行看起来只是还没处理完——worker 健康的
  时候，它们看起来也一模一样。

这一步叫背压，但机制是一道界，而有用的形状是：**一个 worker 认领多少行，就是它能让多少尝试在途**。每
次尝试一张许可，每一轮认领的规模由许可数决定，而负载之下长大的是 `deliveries` 里的行数——它就该长在那
儿，因为数据库生来就是拿来装队列的，进程不是。

同一形状里还有第二道界，在上一层：未投递的事件超过 `max_backlog`，入口路径就回 `503`。这里要紧的是那
次迁移——`async/backpressure@aware`，第 `mailer/1.14-worker` 步，用一个有界的内存通道和满时的 `503`
讲的正是这件事，而带出那句话的是"容量先于它要装的工作被占下"。这里的机制不一样，因为队列不在内存里：
它是 `deliveries` 表，数量向数据库要，而检查发生在*写这份工作的那个事务里面*——于是被拒绝的事件一个字
节都不写，而重试的调用方拿到的是一次新的机会，不是一份只被接受了一半的承诺。

**还有一条必须说出口的边界**，因为现在有三步都带着一道限制：

- `delivery/ordering@apply`——`relay/2.9-ordering`——讲的是*哪些*尝试可以重叠：每个端点一次一个，因为一
  个订阅者的事件有先后。那条车道是在尝试内部取的，这一步不碰它。这一步讲的是**总共**可以有多少个重叠；
- `http/rate-limit@apply`——`relay/2.13-rate-limit`——讲的是一个*调用方*可以要多少，它在门口拒绝。这一步
  讲的是这个服务可以*拿住*多少，不管是谁送来的：一个在配额以内的租户，只要没人投递，照样能把队列塞满；
- `delivery/retry-budget@design`——`relay/2.8-retry-budget`——讲的是这个服务在一个正在失败的订阅者身上花
  多少。一个有界的 worker 让那份预算有了意义：界在那儿，一个停机的订阅者把行留在表里，而不是把进程吃掉。

这一步还讲另一件事，而它根本不是一道界：被拿走的是**谁的**工作。`claim::claim` 拿的是最老的行，这没
错，也意味着一个租户灌洪水时，最老的行永远是那个租户的。一个严格按队列顺序认领的 worker，会一直服务
这场洪水直到它结束——只有 `max_in_flight` 个座位时，十万个事件就是好几个小时，期间其他每个租户的投递
都在等。所以公平也是这道界的一部分：座位在有活的租户之间，一轮一轮地分。

## 任务

脚手架加了 `src/concurrency.rs`（类型和函数体为 `todo!()` 的签名）和 `tests/support/load.rs`——一个会
数有多少尝试在途、并且可以被*按住*的订阅者，规格就是这样观察一道界的，而不是去量时钟。

### `src/lib.rs` 与 `src/concurrency.rs`

- `Limits::new(in_flight, backlog)`——两个数字，任一为零则回 `Error::Config`：一个没有座位的服务什么都
  投不出去，一个零的积压上限拒绝每一个事件。
- `has_room(executor, limits)`——把未投递的工作（`pending`、`retrying`、`claimed`）有多少，和那道界比一比。
  它收的是 **sqlx executor**，不是 pool，因为它是在入口事务里被问的；它是一条策略而不是一把锁，所以队列
  最后可能超出一道界、多出一行，而这一点没有任何东西观察得到。
- `Gate`——由 `Arc<Semaphore>` 支撑的座位，`limit()`、`in_flight()`、`enter()`（一张 **owned** 的许可，
  于是尝试一次投递的任务能在整个尝试期间一直拿着它），以及 `quiesce(deadline)`：等到没有东西在途，或者
  等到截止时间过去。等的是许可本身——一次把所有座位都拿走，只有在没人占着座位时才可能成功——而不是一个被
  轮询的计数器。
- `Worker::new(pool, sender, gate, lanes, budget, limits, name)`——部署实际跑的那个值。gate 和 lane 都
  是 `Arc`：一个进程里的两个 worker 共用一道界和一组车道，而每个 worker 一个 gate，就是每个 worker 一
  道界。
- `Worker::turn()`——用 `claim_fair` 最多认领 `limits.in_flight()` 行，每次尝试开始*之前*拿一个座位，一
  直拿到记录写下去为止，然后 join 每一个任务。
- `Worker::work(turns)`——上面这件事，做 `turns` 次。
- `claim_fair(pool, worker, limit, lease)`——把座位在有活的租户之间发出去，等得最久的租户先来，对每个租
  户调 `claim::for_tenant`。活比自己那份少的租户，用掉自己有的；剩下的下一轮再认领。

### `src/claim.rs`

`for_tenant(pool, worker, tenant, limit, lease)`——`relay/2.5-atomic-claim` 的那次认领，收窄到一个租
户：同一条语句，同一个租约，多一个条件。它住在这儿，挨着它所收窄的那个认领，因为这个模块拥有那些行和
列名。把行映射（`returning` 的元组到 `Claimed`）抽出来，让两个认领共用。

### `src/config.rs`、`src/events.rs`、`src/openapi.rs`

- `delivery.max_in_flight`（默认 4）和 `delivery.max_backlog`（默认 10000），存成
  `delivery.limits: concurrency::Limits`——限流器自己的类型，于是零存不进去。两个都在 `--check-config`
  里报告。
- `events::ingest` 收下这些界，并且**在接受事件的那个事务里面**，当它将要拿住的工作已经超过这道界时拒
  绝：回滚，回 `Error::Unavailable`。重放永远走不到那个分支——一个对不确定的请求做重试的调用方，必须被
  告知"你已经发过这个了"，而不是"再回来"——这是检查落在*哪儿*的属性。
- 文档为 `POST /events` 加上 `503`（调用方现在可能拿到的答案），别的都不变：`429` 是调用方的限制，
  `503` 是服务的。

## 完成标准

- `kiln run relay/2.14-backpressure` — 规格通过
- `kiln check relay/2.14-backpressure` — 每个 must 闸门都是绿的
- `cargo test --test spec_backpressure`——六个用例：两个 worker 共用一个 gate、积压在表里长大、安静的租
  户、被封顶的认领、配置，以及 `503`
- `RELAY__DELIVERY__MAX_IN_FLIGHT=2 RELAY__DELIVERY__MAX_BACKLOG=50 … cargo run` 在你自己生成的负载下
  跑，然后 `psql -c "select state, count(*) from deliveries group by state"`：行数往上爬，`claimed` 停
  在 2，而进程里没有任何东西跟着它长
- `RELAY__DELIVERY__MAX_BACKLOG=1 … cargo run`，然后拿两个不同的 `Idempotency-Key` 发两个事件：第二个
  回 `503`，而拿*第一个*键再发一次仍然是 `200`

## 陷阱

1. **认领的一批比座位还多。** `claim(pool, worker, 1000, lease)`，然后一个循环挨个尝试，是每个人最先写
   出来的形状：它管用，队列会排干，而进程攥着一千行和一千个任务。碰上一个慢订阅者，它每一轮都让进程更大
   一点——而且，因为那些行是 `claimed`，也是别的 worker 拿不走的工作。认领就是那道界，否则那道界是假的。
2. **每个 worker 一个 gate。** 在 worker 的循环里 `Gate::new(limits)`，等于给每个 worker 一份自己的
   `in_flight`——四个 worker，四倍的界，而且进程自己的限制没有一个写得下来的地方。gate 是 worker 共用的
   一个 `Arc`，每个进程只创建一次。
3. **在 spawn 出来的任务里拿一张借来的许可。** `SemaphorePermit<'_>` 活不过 spawn 它的那一轮，于是那次
   尝试根本没法挪进 `tokio::spawn`——修法是*owned* 的许可（`acquire_owned`），理由就是座位存在的理由：它
   要被拿着走完一个 HTTP 请求的长度，而那是这一轮的栈所没有的生命周期。
4. **靠轮询计数器实现 `quiesce`。** `while gate.in_flight() > 0 { sleep(10ms) }` 是那种能跑、却总差一点
   点的版本：它在最后一个尝试早就结束之后还要睡一个固定间隔，还把一个"有没有东西在途"的问题，变成了关于
   机器调度器的问题。一次把所有座位拿走*本身就是*那个问题，而运行时来回答它。
5. **一次按租户数量做除法的认领。** 没有租户在等时，`limit / 0` 是 worker 循环里的一次 panic——在库里，
   在生产里，在顺利路径上（队列本来是空的）。两个守卫（`limit <= 0`，以及没人在等）都该是普通答案，而不
   是错误。
6. **把整批都发给一个租户。** 不看份额的 `claim_fair`，就是一个代码更多、同样饥饿的 `claim::claim`：洪
   水的下一千行，比谁的都老。座位是按租户的，剩下的给等得最久的那些租户。
7. **选错了检查的地点。** 在 insert *之前*问 `has_room`，说的是"刚才还有地方"；在提交*之后*问，它什么都
   拒绝不了。放在事务里面，是唯一一种拒绝什么都不写的版本，而正是这一点让 `503` 对客户端来说可以安全重
   试。
8. **拒绝一次重放。** 一个对没拿到答复的请求做了重试的调用方，必须被告知"你已经发过这个了"——同一个键，
   同一个事件，`200`。如果界在幂等查询之前就检查，这个调用方会为一个本服务早已接受的事件拿到 `503`，然
   后客户端会试第三次。
9. **每次入口都数一遍积压，还说这是免费的。** 那条查询是对队列表的一次扫描：一万行时它什么都不是，一千
   万行时它就是入口路径的成本。那个量级的部署会维护一个计数器（一个触发器，或者 worker 维护的一个 gauge），
   而不是去问真相；这门课留着那条不会漂移的查询，并且把这件事说出来。
10. **相信那道界是一把锁。** 两次入口可以都发现有地方、都写进去，于是队列可能超出一道界、多一行——和
    `mailer/1.14` 在精确的界与"队列前面的队列"之间做的那笔交易一样。要精确的界，就得每次入口一把锁，而那
    把锁本身就是瓶颈。

## 延伸阅读

- [`tokio::sync::Semaphore`](https://docs.rs/tokio/1.53.1/tokio/sync/struct.Semaphore.html) ——
  `acquire`、`acquire_owned`、`acquire_many`，以及等待者队列的公平性
- [`tokio::task::JoinHandle`](https://docs.rs/tokio/1.53.1/tokio/task/struct.JoinHandle.html) ——丢掉一
  个会怎样（它*不*取消任务），这也是一轮要 join 它 spawn 出来的东西的原因
- [Little's law](https://en.wikipedia.org/wiki/Little%27s_law) ——为什么并发的界就是延迟乘以吞吐的界，
  而这就是 `max_in_flight` 背后的算术
- [PostgreSQL: `FOR UPDATE SKIP LOCKED`](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)
  ——`relay/2.5-atomic-claim` 的那次认领就建在它上面，以及没法与它合用的窗口函数（这就是 `claim_fair` 是每个
  租户一条语句、而不是带 rank 的一条的原因）
- [Kubernetes: resource requests and limits](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)
  ——同一个问题上移一层：一个进程可以拿住多少，而不是它拿这些做什么
