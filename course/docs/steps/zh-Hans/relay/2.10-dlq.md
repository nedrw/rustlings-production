# 毒丸不堵队列：放弃、隔离、重放

## 为什么

一条只有万事顺利时才排干的队列，会在第一个不配合的订阅者那里停住。两种投递会这样收场，而它们是同一行上不同的
失败：一个答 `410 Gone`（或者 `400`，或者一个本服务不允许对话的目标）的订阅者，问它多少次都不会收下这个事
件；一个*在努力*却办不到的订阅者，会烧光整份尝试预算而哪儿也没到。两种都是终结性的，而
`relay/2.6-at-least-once` 已经把它们的下场写下来了：行停在 `dead`。

一行没人看得见的 `dead`，比一个重试循环好不了多少。队列在动，运维的仪表盘变绿——而那些没有到达的事件是隐形
的：没有列表，没有原因，没有让它们再来一次的办法。"放弃"而没有"这是我们放弃了什么"，一个投递服务就是这样在
一个周二弄丢一张发票，过一个月才知道。

所以这一步交付剩下的四分之三：

- **终态可查询。** 每个租户一条路由，列出这个服务放弃过的每一次投递：它要去哪儿、订阅者说了什么、花了多少次
  尝试、什么时候；
- **失败被隔离。** 一次有毒的投递只花*一次*尝试，然后它就出了队列，于是正常工作的订阅者不会被那个不工作的拖
  慢。这是队列版的 `relay/2.9-ordering` 承诺，往上挪了一层；
- **有一条回来的路。** 一个宕了一小时的订阅者回来了，而这一小时里死掉的投递，正是它的用户在等的那些。
  `POST /dlq/{id}/replay` 把一条放回队列：同一次投递（接收方按 id 去重）、一份全新的预算，以及刚刚结束的那
  段生命的历史，留在一个有人能读到的地方。

有意思的是最后那条的*边界*，它占掉这一步的一半，原因也在此：重放复活的是一封死信，别的什么也不复活。订阅者
已经收下的投递不复活（再发一次是没人要的重复），已经重新欠着的投递不会被复活两次，而不属于你的投递根本不存在。

## 任务

脚手架加了 `migrations/0006_dead_letters.sql`（一次投递丢掉的每一段生命一行，外加列表要读的那个部分索引）
和 `src/dlq.rs`——`DeadLetter`、`Life`、`Replay`，以及函数体是 `todo!()` 的 `list` 和 `replay`。没有新依
赖。路由和契约文档归你。

### `src/lib.rs`

声明模块：`pub mod dlq;`。

### `src/dlq.rs`

- **`list(pool, tenant, limit)`**——一个租户的死信，最近一次死亡排在最前，每一封带着它完整的履历：`lives`，
  最老的在前，被某次重放撤销的那几段生命上设着 `replayed_at`。列表按租户划分，因为一封死信点名一个端点和一个
  事件，而它们属于同一个租户：按*事件的*租户过滤，不是按端点的，否则一个被删掉的端点会连它的死信一起丢掉。
- **`replay(pool, tenant, delivery) -> Option<Replay>`**——三次必须一致的写入，所以一个事务：*用
  `for update`*读那次投递，做决定，然后挪动这一行（`pending`、没有尝试、现在到期），并给还没关的历史行盖
  上已重放的戳。`None` 是"这个租户没有这次投递"，对别人的投递也是这个答案——调用方必须分不清两者，所以路由
  回 `404` 而不是 `403`。
- **`Replay::NotDead`**——边界：一次重新欠着的投递，或者一次已经送达的投递，都不是死信，而一次硬要重置它的
  重放会发出一个重复。回 `200`，带 `replayed: false` 和它当前的状态。问一下不是错误，而一个重试重放的调用
  方（因为它自己的请求超时了）必须得到和第一次调用一样的答案。
- **重放*不*做的事**：它不改投递的 id（接收方的去重键），不删履历，也不清 `last_error`——这一行留着它死掉
  的原因，直到一次投递成功（清掉它的是 `mark_sent`）。

### `src/claim.rs`：`mark_dead` 写下死信

状态和履历不能有机会对不上：`mark_dead` 变成一条语句，把行挪到 `dead`，并在同一口气里插入
`dead_letters` 那一行。`where state = 'claimed'` 的守卫必须在这次重构里活下来——不归这个 worker 的行写不
出信——而答复是写下的信的数量，所以它的签名和含义都不变。

### 路由（`src/http.rs`）

- `GET /dlq`——调用方租户的死信，`?limit=` 有界（默认 50，最多 200，别的都是 `400`）。放在和 `/events`
  同一个认证层后面：失败列表不是公开的。
- `POST /dlq/{id}/replay`——`200` 带 `{id, replayed, replays, state}`（不管有没有重放都是同样四个字段，
  客户端只解析一种形状）；不是投递 id 的东西回 `400`；这个租户看不见的投递回 `404`。

### `src/openapi.rs`

两条路由都进 `document()`，带上它们能回的每一个状态，以及每个 body 的 schema——包括那个 `404` 和那个
`400`，因为 `relay/2.3-contract-first` 的规格检查的就是"调用方能得到的每一个答复都必须在契约里"。schema
是封闭的（`additionalProperties: false`），并点名自己的 `required` 字段。

## 完成标准

- `kiln run relay/2.10-dlq` — 规格通过
- `kiln check relay/2.10-dlq` — 每个 must 闸门都是绿的（`relay/2.3` 的契约规格也会对着这棵树跑：
  `kiln selftest relay/2.3 --track relay`）
- `cargo test --test spec_dlq` — 六个用例：有毒的订阅者在第一次尝试时就被埋葬，也不碰其他订阅者；列表点名什
  么死了、死在哪儿、为什么；花完的预算也是一封死信；一次重放是一段新的生命，旧的留着；重放对一次没死的投递
  什么也不做；另一个租户既看不见也重放不了
- `curl -s -H "Authorization: Bearer $KEY" localhost:8080/dlq | jq` 显示一个带履历的死信数组，而
  `curl -X POST .../dlq/<id>/replay` 把一封挪出去

## 陷阱

1. **一封没人读得到的死信。** 行在 `dead` 里，队列干净，事件没了，没有列表也没有原因。`attempts` 和
   `last_error` 从 `relay/2.6` 起就在那儿了；让它们能回答问题的是这一步。
2. **所有租户共用一个列表。** 没有租户过滤的 `GET /dlq`，是一处附带审计轨迹的跨租户泄漏：每封死信都点名一
   个事件 id、一个 `kind` 和另一个租户的端点 URL。按事件的租户过滤（事件是租户的；端点可能已经被删了，而它
   的死信仍然是这个租户的事）。
3. **复制投递的重放。** 插入一条*新*行、给它一个新 id，是诱人的形状，而它破坏了接收方唯一的去重键：订阅者
   看到第二个事件，分不清它和真事件。id 不变；复活的是那一行。
4. **保留尝试次数的重放。** 重置状态却不重置 `attempts`，等于给这次投递一份它已经花掉的预算：它被认领、被
   尝试，要么在第一次失败时就死，要么烧掉一个没人解释得清的计数。尝试次数归零，旧的计数留在履历里。
5. **抹掉履历的重放。** 覆盖行上的 `last_error`（或者删掉那些信），毁掉的是"这事以前发生过吗"的答案，而那是
   运维在第二次重放之后问的第一个问题。每一段生命是一行；重放只盖一个 `replayed_at`。
6. **没有边界的重放。** 调用方点什么就复活什么——一次 `sent` 的投递、一次已经 `pending` 的投递——会把一个
   修 bug 的工具变成重复生成器，把一个 id 的两次重放变成它的两段生命。只有 `dead` 会动，而答复会说明实际发
   生了什么。
7. **两次写入，没有事务。** 挪动这一行、给履历盖章，分成两条语句，夹在中间的崩溃会留下一次重新欠着的投递，而
   履历说没人重放过它——同一个 id 的两次并发重放，也可能都看到 `dead`，都把它复活。一个事务，并且
   `for update` 读那一行。
8. **对另一个租户的投递回 `403`。** 那是诚实的状态码，也是错误的答案：它告诉调用方这个 id 存在。对"没了"和
   "不是你的"都回 `404`，是 `mailer/1.18-authz-boundary` 用过的同一条规则。
9. **对一次没死的投递回 `400`。** 重放一行已送达的投递，是调用方的错误——或者是一个客户端在重试自己的请求。
   回错误，就让重试和错误分不开；`200` 加 `replayed: false`，让两者都变成一次读。
10. **没有上界的列表。** 把一个租户丢过的一切都答回来的 `GET /dlq`，是一条恰好在最要紧时变慢的查询，也是
    一个运维读不完的响应。给它上界，把上界写进文档，并在 body 里说明一个非常大的 DLQ 想要的是
    `relay/2.4-cursor-pagination` 的游标。
11. **不在文档里的路由。** 客户端在 `/openapi.json` 里找不到的路由，是只有这个服务自己知道的路由，而代码和
    文档不一致时，`relay/2.3-contract-first` 的规格会让这一步整体失败——包括你加了却忘了描述的那些状态。
