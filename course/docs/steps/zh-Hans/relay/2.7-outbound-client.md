# 一个行为说得清的出站客户端：截止时间、keep-alive、重定向

## 为什么

一次投递就是发给别人服务器的 HTTP 请求，而那个请求的每一种失败，都是*时间*上的失败。一个接下连接却什么也不答
的订阅者，会把 worker 永远占住。一个四十秒才答的订阅者，占它四十秒——而服务器默认"根本没有读超时"时，少数几个
这样的订阅者就能占住所有 worker，队列不再往前走，日志里没有一句话说明为什么。事件堆在一个甚至没有宕机的目标后
面。

所以这一步讲的是截止时间，有三个，因为它们回答三个不同的问题：

- **connect**——握手可以花多久。被过滤的主机、只在理论上可路由的主机，或者干脆没了的主机；
- **read**——在字节到达之前，*一次*读可以花多久。一个接下了连接就沉默的目标；
- **一次尝试**——所有事情加在一起可以花多久，重定向也算在内。没有它，一条四跳的链条即便每一跳都在自己的读
  截止时间内作答，也完全没有上界：读截止时间是每次读的，而一次尝试是唯一的总量。

客户端还带着两个决定，两个都关于连接，而不是载荷：连接会被**复用**（一个每次投递都开一个 socket——还要付一次
TLS 握手的钱，不管握在哪儿发生——的 worker，花在连接上的时间比投递还多），而**重定向**由一项数跳数、拒绝环路
的策略来跟，而不是目标说什么就跟到哪儿。

最后，客户端不是决定失败之后怎么办的组件：它把答复归类成投递层据以行动的那三个词，由投递层来做决定。一个自己
重试的客户端，是没人看得见的第二套重试策略。

### `src/outbound.rs`

- `Client::attempt(&self, request)`——一次尝试，三个截止时间各就各位：整件事在 `deadline` 之内，每次连接在
  `connect` 之内，每次读在 `read` 之内。到期的截止时间是 `Retryable`：什么都还没投出去，订阅者身上也没有
  任何迹象表明不是这样。
- **线路上发出去的请求**：请求行、`host`、调用方的头部、`content-length`、body。`connection`、
  `keep-alive`、`te`、`trailer`、`transfer-encoding`、`upgrade` 和 `proxy-*` 这一组是**逐跳的**：它们
  描述的是一条连接，而客户端拥有它即将使用的连接，所以这些头被丢掉，而不是转发。别的都原样透传。
- **答复**：一个状态行、头部，以及一个用两种方式之一结束的 body——在答复承诺的 `content-length` 处结束，
  或者在它什么也没承诺时随连接关闭而结束。两种在野外都有；只读第一种，会丢掉一个边流边关的目标发来的每一个
  body。提前停下的答复是*没写完*，不是短：它是可重试的。
- **Keep-alive**：一条没有关闭连接的答复，会让连接保持可复用，客户端把它留给同一个 authority（`Client`
  以 `&self` 共享，所以连接池藏在一把锁后面）。一条写着 `connection: close` 的答复会结束那条连接，下一次
  尝试另开一条。没有 `content-length` 的 body 随连接关闭结束，所以永远不可复用。
- **重定向**：跟一个 `Location`——绝对的或相对的——最多 `Policy::redirects` 跳；拒绝这次尝试已经访问过的
  URL（一个环路），拒绝没有 `Location` 的一跳，拒绝这个客户端说不来的一跳（https）。`303` 变成不带 body
  的 `GET`；webhook 前面的 `301`/`302` 意思是"把同样的东西发到这儿来"，所以方法和 body 都保留。
- **归类**（`Outcome`）：`2xx` 成功；`408` 和 `429` 可重试（订阅者在请求再试一次）；其他每个 `4xx` 按永久
  处理；`5xx` 可重试；这个客户端看不懂的一切，以及重定向策略的每一次拒绝，也算永久。永久的答复不会再得到一
  次尝试——花在 `410` 上的重试预算，正是下一次投递需要的预算。
- `HttpSender`——`relay/2.6-at-least-once` 的端口，架在客户端之上：一次尝试就是向端点的 URL 发一个 POST，
  body 是 API 答复里那个事件，`x-relay-delivery` 带着投递 id；这个 id 在多次尝试之间稳定，接收方正是按它
  去重。

这个客户端故意**不做**的事，每一件都是一句说明，而不是沉默：

- **`https`。** 投递目标可能是 `https`，而这个客户端带着理由拒绝它（`Permanent`，因为重试不会长出一个 TLS
  实现来）。TLS 该在哪儿——在客户端里用 `rustls`，还是在进程前面放一个终止器——是一个部署决定，决定它的不是
  这一步。
- **分块传输编码。** 用 chunked 作答的订阅者不被理解：body 被当成帧字符读出来。这是一次*撒谎的*答复，而不是
  缺了个特性，修法是在这个文件里放一个解码器，不是把截止时间放宽。
- **临时的 `1xx` 响应**（`Expect: 100-continue`）：一行 `100 Continue` 会被当成答复来读。这个服务发出去
  的东西从不要求它。
- **authority 里的 userinfo 和 IPv6 字面量**（`http://user@host/`、`http://[::1]/`）：
  `relay/2.1-project-skeleton` 步的 URL 解析器接受它们，而这里"host:port 或 host"的拆法不接受。拒绝它们比
  支持它们是更小的改动，而这个服务注册的订阅者 URL 都是租户自己的。

## 陷阱

1. **只有一个截止时间。** `tokio::time::timeout(30s, whole_attempt)` 是人人都会写的那版，它把"订阅者安静
   了十秒"和"订阅者四跳每一跳都花十秒才答"之间的区别藏了起来。没有*每次读*的截止时间，一个每秒发一个字节的
   目标，从头到尾都待在尝试截止时间之内；没有尝试的截止时间，一条链就没有总量。
2. **把 body 读到 EOF。** 在一个带有 `content-length` 的 HTTP/1.1 连接上，`read_to_end` 直到目标关闭才
   返回——而 keep-alive 的目标不会关闭。每次成功投递，worker 都要等到读截止时间，而且连接还在被读，没法复用。
   `content-length` 才是 body 的结尾；连接关闭是回退处理，不是规则。
3. **相信一个短 body。** `content-length: 100`，线路上只有五个字节，这是一条从未写完的答复。把这五个字节存
   下来，投出去的就是半个载荷，还被记成已送达——至少一次承诺不会有的那种失败，由客户端而不是队列制造出来。
   规格的最后一个用例就是这个答复。
4. **转发逐跳头部。** 把调用方的 `connection: close`、`transfer-encoding` 或 `te` 抄到下一跳，描述的是一
   条已经不存在的连接：`transfer-encoding: chunked` 让目标按这个客户端根本没写的 body 帧去读，而
   `connection: close` 把客户端打算复用的连接，变成目标会在它脚下关掉的那条。
5. **每次投递都开新连接。** 正确，且慢：每次投递都要付一次握手的钱，订阅者看到的是一大串新连接而不是一条事件
   流，负载一高，连接队列（和文件描述符）就是瓶颈。按 authority 复用，并且把 `connection: close` 当成字面
   意思来听。
6. **池子里一条已经死掉的连接。** 目标关掉一条空闲连接之后，留下的 socket 会在第一次写入时失败。它可重试，
   不是致命错误——这也是为什么在一次*复用*连接上失败的尝试，不能把那条连接放回池子。
7. **永远跟重定向，或者一个都不跟。** `Location` 是陌生人的指令：没有上界地跟，就是一次投递在别人的负载均衡
   器上到处走，而环路是同样的事情没有尽头。陷阱的另一半是一个把*每一个*重定向都拒绝的客户端：订阅者会搬家，
   跟不了一次搬家的服务会无声地失去它们。
8. **在 `302` 上把 webhook 的 POST 变成 GET。** 浏览器就是这么干的，而这意味着载荷永远到不了——目标收到一个
   空请求，回 `200`，投递被记成已送达。`303` 的意思是 `GET`；`301`/`302` 是"同样的东西，在那边"。
9. **客户端自作主张地重试。** 一个内部重试 5xx 的客户端，把这次尝试从重试预算（第 `relay/2.8-retry-budget`
   步）、从指标（`relay/2.18-delivery-metrics`），以及从正在读那一行上的 `attempts` 的运维人员眼前藏了起
   来。一次尝试就是一个请求，决定属于上面一层。
10. **一个替*投递*决定状态码含义的客户端。** 这里的归类是关于这次尝试的：`410` *对这次投递*是永久的，因为
    订阅者这么说了；`400` 是永久的，因为重试它只会得到同一个 `400`。对一次被永久拒绝的投递该怎么办，是
    `mark_dead`，那是 worker 的决定，不是客户端的。

  `429 Too Many Requests`，两个请求再试一次的 4xx

  把它变成 `GET` 的那句话

  — keep-alive、池化，以及为什么服务器可以在任何时候关掉一条空闲连接

  `write_all`，以及 `read` 返回 `0` 意味着什么

  为什么一次被取消的*写*可能已经把半个请求发出去了（之后连接不可复用，所以超时的尝试会把它丢掉）
- [`hyper`](https://docs.rs/hyper/latest/hyper/) — 这个文件如果交给它来写会是什么样：先自己写一个，再读连
  接、连接池和超时这三层，然后比较接口
