# 游标分页：一行都不跳过，一行都不重复

## 为什么

租户的事件表只会变大，而每个客户端拿到它做的第一件事就是读它。最直觉的答案——`GET /events` 返回
全部，或者用 `?offset=`——错在三个彼此独立的地方，而这三处都在生产环境里看得见，在十行的测试夹具
里看不见：

- **答复没有上界。** 一个已经收了两百万个事件的租户，会在一次响应里拿到两百万行：查询把它们攥在
  手里，序列化器把它们攥在手里，socket 也把它们攥在手里；
- **偏移量是一个计数，而流在动。** `LIMIT 25 OFFSET 25` 的意思是"跳过最新的 25 行"——可*最新*
  的地方，正是新事件到达的地方。第 1 页和第 2 页之间有一个事件被接受，边界上的那一行就永远没人看
  得见。同样的测量，如果那一页的空位是被删除腾出来的，重复的就是某一行。分不清这两者的读取者，什么
  账都核对不了；
- **两者都得把租户整张表排一遍才能回答。** 一页的代价随租户历史上发过多少东西一起涨，这跟一页存在
  的意义正好相反。

游标把这三个问题一起解决，靠的是换一个问题来答：不问"我已经看过多少"，而问"我刚才在哪儿"。调用方
把一个不透明的位置送回来，服务从它*之后*开始读，一页就成了一次有界的范围扫描，代价不随租户的历史
变化。代价是：这个位置必须真的是一个位置——而这一步讲的就是这件事。

## 任务

脚手架加了 `src/pagination.rs`：常量、类型，以及三个签名。迁移、路由、查询和接线，归你写。

### `migrations/0004_events_cursor_index.sql`

一个索引，顺序就是读一页的顺序：先租户，再按时刻倒序，最后按标识倒序。`relay/2.2-idempotent-ingest`
步建出的 `events` 表没有这个顺序的索引，少了它，每一页都要把租户整张表排序。

### `src/lib.rs`

声明模块：`pub mod pagination;`。

### `src/pagination.rs`

- `Cursor::after(event)`——把一个事件的位置写下来。**把时刻和标识一起编码**，并保证精确往返：微秒
  正是 `timestamptz` 列里存的东西，丢掉微秒的游标，指向的就是错行。十六进制、base64、分隔符——
  编码怎么选由你定，上面的正文也为其中一种给了理由；不由你定的是：这个 token 必须能和行一起*排序*，
  而且必须能在被使用之前先做校验。
- `Cursor::parse(text)`——把调用方送来的文本还原成位置；不是本服务发出的位置，回 `400`。它是从
  陌生人那里来的：查询之前先校验。
- `page(pool, tenant, query)`——一页。校验 `limit`（不传就是 `DEFAULT_LIMIT`，落在
  `1..=MAX_LIMIT` 之外的一律 `400`，并点名这个参数），把 `kind` 和游标**在同一条语句里**应用，
  按 `received_at DESC, id DESC` 排序，并**比一页多要一行**——多出来的那一行，就是不必再发一次
  查询也能回答"还有没有"的办法。多要的那行确实回来时，`Page::next` 是这一页*最后一行*的
  `Some(cursor)`；到流末尾则是 `None`。
- 比较是严格的，而且比的是**一对值**：下一页是满足 `(received_at, id) < (cursor_at, cursor_id)`
  的那些行。用 `<` 而不是 `>`，因为顺序是最新在前；用一对值，因为同一个时刻可能承载好几个事件。

### `src/http.rs`

- `GET /events`，放在认证层后面，查询参数是 `limit`、`cursor` 和 `kind`。把它们都当文本收下，
  让 `pagination::page` 决定哪些能用——一个请求是什么意思，只由一个地方回答。
- 答复是 `{"events": [ … ], "next": "…" | null}`，事件最新在前，每个事件的形状和 `POST /events`
  的答复一样，只少一个 `replayed`。到流末尾时，`next` 仍然在，值为 `null`——不是缺失，这样客户端
  才分得清"没有了"和"我的契约里没有这个字段"。

### `src/openapi.rs`

把刚建起来的东西补进去：一个 `Event` schema、一个 `Page` schema（`events`、`next`），以及
`/events` 上的 `get` 操作，带上它的三个查询参数和它能回的状态码。文档就是 API；不在文档里的路由，
客户端就找不到。

## 完成标准

- `kiln run relay/2.4-cursor-pagination` — 规格通过
- `kiln check relay/2.4-cursor-pagination` — 每个 must 闸门都是绿的
- `curl -sS "localhost:8080/events?limit=2" -H "authorization: Bearer <key>"` 回两个事件和一个
  `next`；把那个 `next` 当作 `cursor=` 送回去，回的是*接下来*两个；一路翻到末尾，每个事件恰好被
  访问一次
- `psql -c "select indexdef from pg_indexes where tablename = 'events'"` 显示一个索引，列是
  `(tenant_id, received_at, id)`

## 陷阱

1. **游标只有时刻。** `WHERE received_at < $1` 看起来像个位置，其实不是：同一个事务里发生的所有事
   共享同一个时刻，于是第二页回来是**空的**，那些事件被悄悄跳过。规格的第一个测试在同一个时刻放了
   三个事件、页大小为 1，正是这个症状。
2. **用 `<=` 而不是 `<`。** 比一对值时，`(received_at, id) <= ($1, $2)` 会让游标指向的那一行在
   每一页重复出现：这一趟走下来，同一个事件回来两次，而且永远走不完。
3. **把偏移量装扮成游标。** `?cursor=25`，或者一个只是数行数的游标，会把当初选游标就是为了绕开的
   每一个问题重新引进来：两页之间插入的那一行被跳过，而这个位置对别人毫无意义。
4. **忘了 `limit + 1`。** 没有这一行，问"还有没有"就只能靠猜（`next` 永远非空，调用方的最后一页
   永远是空的），或者另发一次查询、而它可能给出跟第一次不一样的答案——某一页自称是末尾、后面却还
   坐着一行，那就是数据丢失。
5. **不校验游标。** 对本服务从未写下过的游标回 `200`，就是让一页从*任意位置*开始——包括整个流的
   末端之后；而在一个其实还没读完的调用方眼里，那读起来就是"你读完了"。
6. **悄悄给 `limit` 封顶。** 对 `limit=100000` 回 `200` 加 100 行，看着友好，却在对"你要了什么"
   这件事上撒谎：调用方分不清一个本来就有界的答复和一个被截断的答复，它的指标也分不清。`400` 才能
   说清是哪一种。
7. **索引顺序不对。** 只有 `(tenant_id)` 的索引，或者没有租户的 `(received_at)`，会让数据库为了拼
   出一页去排租户的表：答案是对的，代价永远在涨，而测试一点都没察觉——所以这一步的规格要去读
   `pg_indexes`。
8. **先分页再过滤。** 把 `kind=` 用到最后一页上，或者先翻页、再过滤拿到的行，会得到毫无理由地短的
   一页，以及一个跨过从未读过的行的 `next`。过滤条件和游标属于同一个 `WHERE` 子句。
9. **只按 `received_at` 排序。** 排一列、却比两列，一页就会从中间漏掉一行：`ORDER BY` 必须是游标
   作为其前缀的那同一个全序——两处都是 `(received_at, id)`，索引里也是。
