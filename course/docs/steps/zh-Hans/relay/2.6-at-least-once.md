# 至少一次：把投递的保证写下来，并测试它

## 为什么

前面有两步讲的是相邻的问题，这两步在这里都不重开。`delivery/idempotency@apply`（`mailer/1.15-idempotent-delivery`）
讲的是别把同一封确认信发两遍——一个靠键实现的*去重*保证。`db/atomic-claim@apply`
（`relay/2.5-atomic-claim`）讲的是干活的时候谁持有那一行。这一步讲的是，两者之间发生一次崩溃之后，还有什么是
成立的，而它故意选了更弱、也更诚实的那个保证：一条都不丢，允许重复。

服务接受了一个事件，就欠着它的三个订阅者各一次投递。这时出了岔子，而问题不是"会不会出岔子"，而是**事后还有
什么仍然成立**。那个答案就是一条投递保证，而每个服务都有这么一条，不管有没有人把它写下来——写下来的那版，是
订阅者的作者可以据此开发的东西；没写的那版，是他们在事故里才发现的。

诚实的选项有三个。*至多一次*：发出去，绝不重试，一个重启五秒的订阅者会无声地丢掉这五秒里发给它的一切。
*恰好一次*：人人都想要、却没人能在网络上拿到的性质，因为它要求你知道一个陌生人的 HTTP 服务器确实存下了它收下
的东西。*至少一次*：一直重试，直到订阅者收下或者 worker 放弃，并接受后果——从订阅者收下一个请求，到行里记下
这件事之间，worker 可能死掉，而那次投递会被再发一遍。

正因为这个窗口，这一步有两件交付物，而不是一件。代码要把窗口压到能压的最小，而**决策记录**要说明这个窗口存在、
代价是什么、接收方该拿它怎么办（按投递 id 去重）。没写下来的保证，会被下一个在日志里看见重复的人"修掉"。

## 任务

脚手架加了 `src/delivery.rs`——端口、类型、带 `todo!()` 的 `tick`，以及规格拿来当订阅者用的夹具
（`tests/support/sender.rs`）。还有两件东西没有脚手架：扇出，它是对一个你已经拥有的文件的改动；以及决策记录，
它是文章。

### `src/lib.rs`

声明模块：`pub mod delivery;`。

### `src/delivery.rs`

- `tick(pool, sender, worker)`——worker 的一轮：**认领**一批（第 `relay/2.5-atomic-claim` 步），把认领到的
  每次投递**尝试**一遍，经由 sender 发出去，再**记录**发生了什么。每次尝试一次写入，而且写入在尝试之后：一次在
  发送之前就记下的投递，是崩溃会丢掉的那次投递——而你提供的并不是这个保证。
- 三种结果：订阅者收下了 → `mark_sent`；一次也许能过去的失败 → `mark_retry` 带上下一次的时刻（于是
  `attempts` 增长，行等着）；一次修不好的失败，或者一份已经花完的失败预算 → `mark_dead`。尝试到一个小数目就
  放弃，并把那个数写成常量；一个没有终点的重试策略里不存在失败，只有永远不算迟的投递。
- `SendRequest` 在每次尝试里都带着**投递 id** 和**尝试序号**。id 是接收方的去重键，不会变；尝试序号让接收方
  （和一项指标）分得清一次重试和一个新事件。
- `Tick` 报告这一轮做了什么，包括 `lost`：一次尝试的结果没能记下，因为那一行已经不归这个 worker 了。把这种
  情况悄悄吞掉的 worker，计数器会和邮箱对不上。

### 扇出

一个被接受的事件，欠着它的租户所拥有的每一个端点各一次投递，而这必须**在接受这个事件的同一个事务里**发生
（`events::ingest`）：每个端点一行投递，和事件一起写下，或者一行都不写。一个存在却没有投递的事件，是一个永远
不会有人被告知的事件——这是这个保证唯一不允许的失败；而为一个已经回滚的事件写下的投递，是派给一个从未被告知
出过任何事的订阅者的活。

让跑了两次的扇出变得无害的，是 `relay/2.5-atomic-claim` 的那条唯一约束。

### `docs/adr/0001-at-least-once.md`

决策记录，放在项目里，挨着它讲的代码。三节，形状要能被 `links` 闸门检查：

- `## Decision`——这个服务保证什么：一次投递只有在订阅者收下了它（`sent`）、或者某个 worker 放弃了它
  （`dead`）之后才会被忘掉；每次尝试都带着一个稳定的投递 id，重复收到它的订阅者能认出来。
- `## Alternatives`——至少写上桌过的三个（恰好一次、至多一次，以及恰好一次那种"每次投递一把锁、只在 worker
  活着时成立"的变体），每个都要写清它原本的代价。没有备选的记录只是描述，而描述没法拿来争论。
- `## Consequences`——它买到了什么、代价是什么：重复是可能的，也是允许的；订阅者必须幂等；顺序不作承诺
  （那是 `relay/2.9-ordering`）；重试有上界；"发出的投递"不等于"送达的事件"。

它必须原样写出"重复窗口"这几个字，还必须**链接**它讲到的代码（`src/delivery.rs`、`src/claim.rs`、那个迁移）
——从 `docs/adr/` 出发的相对链接是 `../../src/delivery.rs`。`links` 闸门会读项目里的每一个 markdown 页面，
所以一个不存在的目标就是一步红。

## 完成标准

- `kiln run relay/2.6-at-least-once` — 规格通过
- `kiln check relay/2.6-at-least-once` — 每个 must 闸门都是绿的，包括 `links` 闸门
- `kiln links app/relay` — 项目里的每个链接都能解析（闸门做的也是同一个检查）
- `cargo test --test spec_at_least_once the_window_between_sending_and_recording_lets_a_duplicate_through`
  — 重复窗口是被测量出来的，不是假设出来的
- 注册两个端点、投三个事件，再跑一轮 worker，`pending` 和 `claimed` 里什么都不剩：
  `psql -c "select state, count(*) from deliveries group by state"` 显示收下它们的订阅者是 `sent`，
  拒绝它们的那一个是 `dead`

## 陷阱

1. **先记录后发送。** 先 `mark_sent` 再尝试，会把两者之间的一次崩溃变成一次谁也不会再发的投递——穿着至少一次
   外衣的至多一次。在每个不会在半途杀掉进程的测试里，它都看不见，所以规格的最后一个测试就在半途杀掉它。
2. **尽力而为地记录。** `let _ = mark_sent(…)`（或者无视一个 `false`）会让一次已经被收下的投递留在可认领的
   状态：订阅者会一遍又一遍地收到它，而 `Tick` 里的计数器说它已经发过了。`false` 的意思是那一行不归这个
   worker 记录；那就是 `lost`。
3. **按请求扇出，而不是按已接受的事件扇出。** 重放路径（`Idempotency-Key` 已经用过）会把扇出再跑一遍，每个
   订阅者于是什么都收到两遍——保证允许的那种重复，出现在根本不必出现的地方。
4. **事件和它的投递分两次提交。** 插入提交了，进程死了，投递从未存在：租户相信事件已被接受，却没有任何订阅者
   被告知。什么都不会重试它，因为没有任何东西知道它缺了。
5. **没有终点的重试。** 每次失败都 `mark_retry`、从不 `mark_dead`，会让一次有毒的投递活到永远：它被认领、被
   发送、失败，又被认领，而真正在干活的订阅者排在它后面饿死。规格会驱动那个永远失败的场景，并期望这一行停
   下来。
6. **重试修不好的东西。** 一个 `410 Gone`、一个本服务不允许对话的目标、一个畸形的请求：再试一次也无济于事，
   而花在它上面的重试预算，就是*下一次*投递不再拥有的预算。永久失败在第一次尝试时就死掉。
7. **每次尝试之间会变的投递 id。** 每次尝试现生成 id（或者在 body 里用一个新 UUID），接收方就分不清"同一次
   投递发了两次"和"两个事件"了，而"重复可以容忍"这句话也就成了谎话。
8. **把尝试当投递计数的 `Tick`。** 一次投递的两次尝试，是计数器里的两个条目、数据库里的一次投递。`Tick` 数的
   是*这一轮决定了什么*，而"发出了多少投递"的指标属于行，不属于尝试（第 `relay/2.18-delivery-metrics` 步）。
9. **承诺恰好一次的 ADR。** "不会有重复"是一句订阅者的作者会拿来做依据的话，而这个服务守不住它。把窗口写下
   来，点名那个 id，说清接收方该做什么；保证和愿望的区别就在这里。
10. **没有链接的决策记录。** 讲一个后来被改名的模块的文章，是一年后会误导读者的文档。记录要链接
    `src/delivery.rs` 和那个迁移，而当它们不再能解析时，`links` 闸门会让这一步失败。
