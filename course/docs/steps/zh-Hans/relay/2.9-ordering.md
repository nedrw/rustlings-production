# 每个订阅者各自保序，其余部分并发

## 为什么

一个订阅者拿到的某个租户事件流要是乱序的，就得自己把它排好，而大多数订阅者不会：一个 `invoice.paid` 在取消
它的 `invoice.voided` 之后到达，这个订阅者的状态就是错的，直到有人发现。所以沿投递这条路由，有一条值得许下的
承诺——*一个订阅者，一次一个事件，按队列接受它们的顺序*——而它的代价恰好只有一种：订阅者一慢，等它的 worker
就什么别的都不投了。

这条承诺的廉价版本有两个，两个都会在生产环境里出大问题：

- **整个 worker 一把锁。** 承诺守住了，整个队列却被串行化：一个每个请求花四秒的订阅者，让其他每一个订阅者的
  投递都慢四秒。宕掉的那个订阅者不只是攥着自己的事件，它攥着所有人的；
- **根本不上锁，每次投递一个任务。** 队列全速前进，承诺没了：对同一个端点的两次尝试同时在途，谁先到是调度器
  的决定——等于说谁的决定都不是。

这一步造的是中间那个：**每个端点一条车道**。发往同一个端点的投递被串行化（按队列顺序）；发往不同端点的投递
同时跑；而整件事是一张互斥锁的地图，不是一把互斥锁，所以一个慢订阅者的代价由它自己的端点付，不牵连别人。
同一个机制顺带回答了第二个问题——一个刚回来的订阅者看到的一波重试长什么样——因为一条车道持有的时长是一次
尝试，而不是一次投递：一百次同一瞬间到期的投递，在一个端点上是一*串*请求，不是一百个同时的请求。

## 回顾

`outbound/http-client@apply`——`relay/2.7-outbound-client`：一次尝试是一个请求，带三个截止时间（connect、
read、整个尝试）和一条重定向策略；持有客户端的是投递端口（`relay/2.6-at-least-once` 的 `Sender`），而一次
失败的尝试是一个 `SendError`，属于两类之一。

`delivery/at-least-once@design`——`relay/2.6-at-least-once`：一次投递只有在订阅者收下了它、或者 worker 放
弃了它之后才会被忘掉，而那份记录明说**顺序不作承诺**——这一步是它变成承诺的地方，而且只在每个端点之内。

`async/graceful-shutdown@apply`——`mailer/1.14-worker`：正在进行的工作是一个有人持有的 future，丢掉它就把里
面的工作也丢了。这正是车道是一个守卫而不是一个旗标的原因：它由那次尝试的 future 被*丢弃*时释放，不管那个
future 怎么结束。

## 变化

有三件事和这些来源所在的 track 不同，而每一件都关于同一个事实：webhook 端点是他人的服务器，而队列由素未谋面
的租户共享。

- **车道的键是*端点*，不是作业。** `mailer/1.14-worker` 只有一条队列和固定数量的 worker；这里不能同时被问
  两次的单位是一个 HTTP 目标，而目标的数量没有上界，所以锁必须是*查出来的*，不是常握在手里的。所以这个文件
  是一张带生命周期的互斥锁地图——也是这张地图必须学会忘事的原因：给 worker 见过的每个 URL 都留一扇门，会随
  租户的历史增长，那是一处装着别人流量的内存泄漏；
- **前一步的熔断器是在车道*里面*问的。** 半开的熔断器承诺"恰好一个探针"，而这个承诺之所以精确，只因为车道
  让询问串行：两个一起走到熔断器跟前的任务，会双双成为那一个探针。先拿车道，再问熔断器——这是关于两个模块的
  一句话，两个模块谁单独都说不出来；
- **认领的答复是集合，不是序列。** `relay/2.5-atomic-claim` 的语句以 `update … returning` 收尾，而
  `RETURNING` 子句没有顺序：行按计划走过的顺序回来。车道是公平的——谁先问谁先被服务——所以*询问*的顺序就是
  订阅者的顺序，而这一步就是它从队列的键里被恢复的地方。

这一步的闸门和上一步一样，但规格比之前任何一步都严：它断言*重叠*的性质，这是这个 track 里之前任何一步都做
不到的。

## 任务

脚手架加了 `src/ordering.rs`——`Lanes`、`Lane`，以及函数体是 `todo!()` 的 `spread`——还加了
`tests/support/lanes.rs`，一个做计数的 sender。没有新依赖：车道是 `tokio::sync::Mutex`，这个构建图里已有
的 crate 已经把它启用了。

### `src/lib.rs`

声明模块：`pub mod ordering;`。没有一行脚手架替它准备（这个文件是你的），所以在加上它之前规格编译不过——
这正是课程在这里预期的失败。

### `src/ordering.rs`

- **`Lanes::enter(&self, endpoint) -> Lane<'_>`**——找到或造出这个端点的闸门，*然后*等它。地图只锁到把闸
  门克隆出来为止：握着地图锁去等，会让进程里的每个端点都排在一次尝试后面，而这是这个模块唯一不被允许做的事。
  `tokio::sync::Mutex::lock_owned` 按值拿走闸门，正因如此 `Lane` 才能比集合的借用活得久，并握住一个等待
  者所排的那扇闸门。
- **`Lanes::known()`**——集合正在留着的闸门数量。它必须降回来：最后一条车道的 `Drop` 才是删掉那个条目的东
  西，而"最后"必须是一个*计数*，不是一个旗标——一个已经在等的投递手里有一份闸门的副本，如果条目在它脚下被删
  掉，下一个来的人会为同一个端点造出第二扇闸门，两个就都在车道里了。要找的数字是三个引用：集合的、车道自己
  的，以及许可持有的那一个。
- **先拿车道，再问熔断器，并一直握到记录写完。** 车道是守着整次尝试的守卫——发送、答复和写入——所以它在每
  一条出去的路上都由 `Drop` 释放，包括提前返回的那些（一次被 shed 的投递）和永远不结束的那些（一个被取消的
  future）。车道没有任何超时：尝试存在多久，车道就握多久，约束它的是这次尝试自己的截止时间
  （`relay/2.7-outbound-client`）。
- **`spread(pool, sender, worker, lanes, budget) -> Result<Tick, Error>`**——一轮同时铺到每个端点上：认领
  一批，每次被认领的投递一个任务，每个任务都等它自己端点的车道。sender 是 `Arc`，因为任务拥有它用的东西；
  预算故意按任务克隆，好让这些克隆共享一个熔断器；即使其中一个失败，每个任务也都会 join，因为一轮要是从自己
  的尝试旁边走开，报告的就会是还在被写的行。
- **在 spawn 任何东西之前，把这一批恢复成队列顺序。** `claim::claim` 现在把行的 `next_attempt_at` 作为
  `Claimed::due_at` 带着（认领自己的 `ORDER BY` 键），而这一批先按 `(due_at, delivery)` 排序。把这个字
  段加进 `Claimed`——那是对一个你拥有的文件的改动，认领的签名不动。
- **`src/delivery.rs`**：每次投递的工作变成车道包住的那个单位
  （`pub(crate) async fn attempt(…, lanes: &Lanes, …)`，先拿自己的车道），而 `tick_with_budget`——它的
  签名被 `relay/2.8-retry-budget` 钉住了——现在带着一套新的车道调用 `spread`。在文档里说明为什么：一轮自
  带车道，适合跑一轮就等它的调用方，不适合跑好几轮的 worker，因为其中两个会各自有两套车道，可能同时待在同一个
  端点里。

### `tests/support/lanes.rs`

这个夹具是课程的，不是你的，而它是量具：它逐个端点数，有多少次尝试在途、那个计数最高到过多少，以及尝试开始
的顺序。一个端点可以被*按住*，而 `release` 是一个脉冲——它放行此刻停着的尝试，继续按住接下来到的那些——所
以测试可以不用睡眠，一次一个尝试地走完一条队列。

## 完成标准

- `kiln run relay/2.9-ordering` — 规格通过
- `kiln check relay/2.9-ordering` — 每个 must 闸门都是绿的
- `cargo test --test spec_ordering` — 五个用例：一个端点一条车道，一次一个尝试地走；被按住的端点不拖住一个
  快的；队列的顺序就是订阅者的顺序；每个端点都轮到一次之后，才有端点轮第二次；没人握着的车道会被忘掉
- 把 worker 指向你自己的一个目标（`python3 -m http.server` 什么都答），看它的访问日志，一个端点是一次一个
  请求，两个端点是并行的请求

## 陷阱

1. **整个 worker 一把互斥锁。** 承诺守住了，队列却成了单车道：一个每个请求花四秒的订阅者，就是其他每个租户
   四秒的延迟。规格的第三个用例正是这个——一个被按住的端点和一个快的端点，而快的那个必须跑完。
2. **按租户、或者按事件给车道定键。** 一个租户的两个端点是两个集成，一个集成慢不是另一个的问题；而同一个端
   点的两个事件*正是*必须保序的那条流。定键要用请求去的那个目标。
3. **一条车道握过整轮。** 每轮拿一次锁、在锁下跑完这一批，和整个 worker 一把互斥锁是一回事，只是多了几步：
   车道必须握一次尝试，放开，再拿。
4. **在熔断器*之后*拿车道。** 半开的熔断器只放一个探针过去，而如果没有什么把询问串行化，两个一起到达的任务
   看起来都像那一个探针。串行化它们的是车道，所以先拿它——而保存它的那个字段要握到函数返回，不是在代码块末
   尾就丢掉。
5. **一张永不忘事的地图。** 每个见过的端点一个条目的 `gates: HashMap<String, …>`，是租户能驱动的泄漏：每
   小时注册一个新 URL，worker 的地图就无界地长。在释放时删条目需要一个计数（一个等待者也握着闸门），而在有
   人等着的时候删掉它，会把一扇*不同的*闸门交给下一个来的人——两次尝试进了同一条车道。
6. **跨 await 握着 `std::sync::Mutex`。** 地图藏在一把 `std` 互斥锁后面，因为它只被握几条指令；而*闸门*是
   一个 `tokio::sync::Mutex`，因为它跨整次尝试被握着。把两者对调，要么编译错误，要么运行时 panic——而一条
   被堵住的运行时线程，就是一个什么也不投的 worker。
7. **spawn 了却不 join。** 在第一个任务失败之后就返回、或者对其中一个做 `select!` 之后就返回的一轮，会为还
   在跑的尝试报告一个 `Tick`：计数器和行对不上，运维看到的总和不是实际发生的总和。join 每个任务，再报告。
8. **假设认领有顺序。** `update … returning` 没有 `ORDER BY`，Postgres 也不承诺有；这一批按计划顺序回来，
   对一张小表来说，那常常*看起来*像 id 顺序。建在这上面的车道公平而无意义：谁先问就先服务谁，而谁先问是计划
   的选择。spawn 之前，按认领自己的键把这一批排好。
9. **每次*投递*一条车道。** 把一次投递自己的尝试串行化（认领已经通过把每一行交给一个 worker 做到了），和把
   一个端点的投递串行化不是一回事；而按投递 id 定键的地图，会让每次尝试都有自己的车道：什么都没保序，地图还
   随队列增长。
10. **一条握着的车道里藏着死锁。** 一次尝试在自己的车道里又去拿第二条（同一个端点的，或者别的端点的），一旦
    两次尝试以相反的顺序这么做，就是死锁。一条车道，拿一次，握一次尝试那么久。
11. **以为车道是全局锁。** 车道住在一个进程里：两个 worker 往同一个端点投递时互相看不见，保序承诺是*每个
    worker* 的。跨进程就是一个分区问题，或者数据库里一把锁的问题（那是 `relay/2.15-shutdown-leases` 及
    之后的事），而假设不是这样的读者，会恰好撞上他们想避免的那个重复。
