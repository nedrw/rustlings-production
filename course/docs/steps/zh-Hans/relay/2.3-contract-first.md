# 把 API 写成契约：生成的文档、快照与兼容性

## 为什么

这个服务正在长出第二个客户端——合作方的集成、内部的仪表盘、客户的脚本——而它们每一个都是照着猜写
出来的。猜的材料是他们能翻到的一切：两个版本之前的 README、只跑过一次的 `curl`、某次答复里冒出来
却从没被承诺过的字段。头一次有字段改名，这个猜就要用一串支持工单来还，而答案永远是"那本来就不在
API 里"——这话是真的，也毫无用处，因为没有任何地方这么说过。

所以 API 被写下来，用一种客户端*读得懂*的格式，再由服务发布出去。这就是 `GET /openapi.json`。但
一份只是存在的文档比没有更糟：它是一个没人核对的承诺，一个字段一个字段地漂走。让它成为契约的，是
测试套件拿它跟服务做比对——文档声明的路由，要真的接进路由里、有人服务；文档称作必填的字段，处理
函数就得真的要求；文档里的 schema，要对得上实际回来的 JSON。快照是评审者在 pull request 里读的
东西：文档的 diff 就是 API 的 diff，而 API 的 diff 就是一场关于"这次改动该不该发生"的讨论。

## 任务

脚手架加了 `src/openapi.rs`，里面只有一个函数 `document()`。文档本身、发布它的路由，以及各处接线，
归你写。

### `src/lib.rs`

声明模块：`pub mod openapi;`。

### `src/openapi.rs`

以 `serde_json::Value` 返回 OpenAPI 文档。形状必须是客户端期待的样子：

- 顶层要有 `openapi` 版本（一个 `3.x` 字符串），以及 `title` 非空的 `info`；
- `paths`：每条路由一个条目，键是小写的方法名。这个服务提供的每条路由都必须在里面——`/healthz`、
  `/readyz`、`/endpoints`（两个方法都要）、`/events`——而且文档要把 `idempotency-key` 写成
  `POST /events` 的**必填头部参数**，因为 body 并不等于整个请求；
- 收 body 的路由要有 `requestBody` schema；每条路由能用哪些状态码作答，就要有对应的 `responses`——
  包括调用方会遇到的 `400` 和 `401`，以及 `POST /events` 会回的 `200` **和** `201`；
- `components.schemas`：每个 schema 都要声明自己的 `type`；一条记录要声明 `required`，并用
  `additionalProperties: false` 把自己封闭起来；自由形态的 `payload` 就是没有字段的
  `{"type": "object"}`——文档用这个形状说"调用方发来什么就是什么"；
- 每个 `$ref` 都要指向文档自己声明过的 schema。文档要从数据搭出来——每种重复出现的形状一个辅助
  函数——而不是把同一份字段清单写两遍：第二份拷贝的下场，就是 TRAP 讲的事。

文档必须**可复现**：每次调用，字节都一样。不能读时钟，不能让 `HashMap` 的迭代顺序进来，也不能有
自己会动的版本号。

### `src/http.rs`

- 把它发出去：`GET /openapi.json`，**公开**——客户端要在手上有 key 之前，先读到这个服务承诺了
  什么，而一份需要 key 才能拿到的契约，就是没人会去取的契约。
- 处理函数以 JSON 返回文档。它故意做得只有薄薄一层：文档建在 `src/openapi.rs` 里，测试才调得到
  它。
- body 得跟文档对得上，而有一样东西*不会*自动跟上，就是 `additionalProperties: false`：除非你
  另作声明，`serde` 会忽略不认识的字段，所以请求结构体要加上 `#[serde(deny_unknown_fields)]`。
  文档向调用方承诺：拼错的字段是 `400`，不是一次悄悄的空操作——而这个承诺要么在代码里是真的，要
  么就是谎话。

## 完成标准

- `kiln run relay/2.3-contract-first` — 规格通过
- `kiln check relay/2.3-contract-first` — 每个 must 闸门都是绿的
- `curl -sS localhost:8080/openapi.json | jq '.paths | keys'` 列出服务提供的路由，而且跑两次，
  输出逐字节相同
- 把 `document()`（或者某个响应结构体）里的一个字段改名，规格就会变红：pull request 里的快照，
  靠的就是这道检查

## 陷阱

1. **一份没人比对的文档。** 把文档写完就收手，是默认的结果：写的那天路由是对的，两步之后就不对
   了。规格的第一个问题就是：文档里的每个路径和方法，答的是不是 `404`/`405` 以外的东西——所以一条
   加进了 `router()`、却在这里被忘掉的路由，会让这一步失败。
2. **写了 `required`，代码却不认。** 一个列成必填、处理函数却当它可选的字段，写下来的是意图，不是
   行为：客户端漏掉它，一切照常；而等哪天处理函数*开始*在意它，所有这样的客户端会一起坏掉。规格会
   照文档自己的 `required` 清单拼一个 body，再把字段一个一个删掉。
3. **文档说对象是封闭的，代码却留着口。** `additionalProperties: false` 和
   `#[serde(deny_unknown_fields)]` 是同一项主张写在两个地方；只有前一个的话，把 `payload` 拼错的
   调用方会拿到一个 `201`，以及一个里面没有载荷的事件。
4. **同一份字段清单写了三遍。** 请求一个 schema、答复一个、数据库行再一个，就是三个要改 `.kind`
   的地方，和两个会忘掉的地方。形状只搭一次（`answer`、`event_schema`），让各处路径通过名字引用
   它们。
5. **文档里带着钟。** 从环境里读来的 `version`、一个 `info.generated_at`，或者按哈希顺序遍历的
   map，都会让生成器每跑一次就产出一份不同的文档：快照的 diff 变成噪声，评审者不再读它——而快照
   存在的唯一用处，就是被读。
6. **`$ref` 指向虚空。** 一个 `{"$ref": "#/components/schemas/Event"}`，下面却没有 `Event`：
   这种文档会让生成器崩溃，而人看过去却像是一切正常。规格会把文档里的每一个引用走一遍。
7. **把文档藏在认证后面。** 看起来更整齐——文档讲的是 API，而 API 要 key——可这等于每个客户端都
   得先被配置好，才能知道该怎么被配置。`GET /openapi.json` 是公开的。
8. **文档卖着一条路由，服务却回 `404`。** 一个在文档里、却不在路由里的路径，比缺一条条目更糟：
   客户端的代码是照着它写的，而它做的第一件事就是失败。文档和路由是同一张表的两个视图。

## 延伸阅读

- [OpenAPI Specification 3.1](https://spec.openapis.org/oas/v3.1.0.html) — 这份文档所用的
  `paths`、`components.schemas`、`required` 和 `additionalProperties` 都出自这里
- [`additionalProperties`](https://json-schema.org/understanding-json-schema/reference/object.html#additional-properties)
  — 为什么封闭一个对象是一份兼容性承诺，而不是抠字眼
- [serde: `deny_unknown_fields`](https://serde.rs/container-attrs.html#deny_unknown_fields) — 让
  这个承诺在处理函数那里成真的那个属性
- [Stripe: versioning](https://docs.stripe.com/api/versioning) 与
  [Zalando's API guidelines](https://opensource.zalando.com/restful-api-guidelines/#api-versioning)
  — 对"什么算破坏性变更"两个论证充分的回答，而这个正是快照逼你回答的问题
- [json-schema: the `$ref` keyword](https://json-schema.org/understanding-json-schema/structuring#dollarref)
  — 文档如何在多条路径之间共用同一个形状，而不必复制它
- [utoipa](https://docs.rs/utoipa/latest/utoipa/) — 从处理函数*反向*生成这份文档的 crate；这一步
  之后再读它，那时你已经看得出它会替你生成什么
