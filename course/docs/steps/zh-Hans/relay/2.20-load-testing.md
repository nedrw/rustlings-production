# 对你自己造的东西做负载测试，并把容量写下来

## 为什么

你有一个带上限的队列、一份重试预算、按租户的公平、一个死信队列，以及 `/metrics` 里的一个 p99。这些
数字每一个都是*选*出来的——`delivery.max_in_flight`、`delivery.max_backlog`、
`rate_limit.per_second`——而没有哪一个被放到这些设置项产出的服务上验证过。客户第一次每秒发一百个
事件的时候，值班的人会从队列深度上得知，哪一个选择是错的，而且是在生产里。

一个容量上的答案，才是把那些设置项从猜测变成决定的东西，而它由三个部分构成，缺一不可：
**一个不需要谁去信任的负载生成器**（它每次都提供同样的事件，所以一次运行能跟上一次比），
**算出来而不是估出来的统计**（一个 p99，如果来自两次谁都没做过的观测之间的插值，就是一个无法核对的
数字），以及**一条曲线**：p99 *相对于*并发，旁边放着积压，因为单看延迟只能回答"它慢不慢"，永远回答
不了"它跟不跟得上"。

两个邻居，而这一步不是它们中的任何一个。`obs/metrics-slo@aware`（`mailer/1.20-metrics`、
`relay/2.18-delivery-metrics`）测的是服务*在应付碰巧到来的流量时*的样子——那是一次观察，而它的全部
价值在于没有测试安排过它。`async/backpressure`（`relay/2.14-backpressure`）是这一步*对着*量的那个
上限：座位是进程对并发尝试的限制，积压上限是队列拒绝再收，而一次负载运行问的问题是这两个从哪里开始
咬人。这里新的是那种刻意的、可重复的、离线的压力——以及那页把答案写下来的文档。

## 任务

脚手架放好了三样东西：`src/loadtest.rs`（算术，里面是 `todo!()`）、`tests/support/workload.rs`
（施加压力的装置）和 `docs/capacity.md`（那一页，链接是占位的）。`src/lib.rs` 里有一行归你：脚手架
加的模块，要等 crate 根声明它，才算这个 crate 的一部分，而一个没人声明的模块，就是一个什么都没编进去
的文件。

### `src/loadtest.rs`——生成器、算术与记录

- **`keys` / `keys_from`**——`count` 个幂等键，唯一，顺序固定，于是运行留下的台账能跟上一本比。生成
  器是一个*函数*：同样的参数，在每台机器上答出同样的键；
- **`percentile` / `Percentiles`**——最近秩，不是插值：`n` 个样本升序排好，`q` 分位数就是其中第
  `ceil(q * n)` 个，两端夹紧，而空样本答零，而不是在一份报告里 panic。于是这个模块报告的每一样东西，
  都是读者能从样本里重算出来的观测；
- **`Point` 和 `Curve`**——一级负载：它被施加时的并发、它换来的 p99，以及它留下的队列深度。
  `is_monotone_within(jitter)` 是*形状*检查（一条在涨的曲线、一条平的曲线，或者一条断掉的），而
  `render` 写出那一页引用的表。

### `tests/support/workload.rs`——压力

它用自己的数据库、带着 `N` 个订阅者把服务起起来，而 `offer(keys, concurrency)` 把 `concurrency` 个
阻塞的生产者放到同一个键队列上，每个都在自己的 socket 上给自己的请求计时。有两条规则已经写在它里面，
两条都要紧：它先完成 HTTP 往返，才让测试去读表（端口在 migration 跑之前就绑好了），而且它数的是服务
*答*了什么（`201`、重放时的 `200`、别的任何东西），而不是它安排发出了什么。

### 这次运行

规格对它提四件事，每一件都是关于你的服务的主张，而不是关于装置的：

1. **台账就是那份清单。** 服务握着的事件，正好是生成器提供的那些键，每个一次，不管有多少个生产者提
   供了它们——而同一次运行再提供一遍，什么也不加（`relay/2.2-idempotent-ingest` 就是让"键的集合"
   和"事件的集合"变成同一个集合的东西）；
2. **统计是精确的。** 二十个观测的样本有三个读者能手算的答案，而规格把它们算出来——这是负载运行里不
   依赖机器的那一半；
3. **曲线是一个形状。** 至少三级并发，每一级都在一个界限之内，每一级留下的队列都比它下面那一级深。积压是
   算术；p99 那一列是测量，是被*记录*的，而不是被断言单调——在一台还同时在编译的机器上，某一级最大
   的那个观测动得比负载还多。形状检查拿一条上升的曲线和一条崩塌的曲线来验证，这样它才不是装饰；
4. **负载是服务做得完的活。** 被接受的一切都到达 `sent`，总数是事件数乘订阅者数，而积压最后归零。
   一个只测量自己能塞进去多少的负载测试，报告的会是一个很擅长遗忘的服务。

### `docs/capacity.md`——那一页

四节，每一节的形状都是发布之前有人会问的一个问题的答案：**方法**（数字是怎么产出的——一个没有方法的
数字是传言，而且它必须说明，这是 debug 构建、跑的是这台机器上的一个容器）、**测量**（那张表，至少
三级）、**斜率**（增长那一列是什么意思，以及曲线从哪里开始不再是曲线）、**worker 与吞吐**（多一个
worker 换来什么，又付出什么）。`links` 闸门会跑在这个文件上：每个相对目标都必须存在，而本该是一个
目标的地方写成 `TODO`，就是失败。

## 完成标准

- `kiln run relay/2.20-load-testing` — 规格通过（六个用例：台账、分位数、形状检查、有界的运行、
  排干，以及那一页）
- `kiln check relay/2.20-load-testing` — 每个 must 闸门都是绿的，`links` 也在内
- `cargo test -p relay --test spec_load -- --nocapture` 几秒内跑完，打印出你马上要在那一页里引用的
  曲线
- 手工把服务跑起来（`cargo run -p relay`），同样的负载透过 `hey` 或 `curl` 打过去，会推动
  `/metrics`（`relay/2.18-delivery-metrics`）里的 `relay_backlog_depth` 和
  `relay_delivery_duration_seconds`——负载运行产出的数字，就是仪表盘显示的数字
- `docs/capacity.md` 写明重复这次运行的命令，引用的是*这台*机器产出的数字，而不是上面那些

## 陷阱

1. **用时钟做种子的生成器。** 它看起来更诚实——"随机负载"——而它让每次运行都成了另一个实验：台账没
   法比，回归没法发现，而那一页里的数字是一个谁都没法核对的数字。键是数据；`keys(200)` 每次都是同样
   的 200 个。
2. **给分位数做插值。** `p99 = 0.99 × (last - first) + first`，或者对两个邻居取平均，答出的是一个
   *介于*两个观测之间的数——一个谁都没观测到的数。最近秩答出的是样本里的一个，而那个算术可以手算
   核对。
3. **一个旁边没有并发的 p99。** "p99 = 43 ms"无法被证伪：同一个服务在一个生产者时可能是 8 毫秒，四
   个时是 43 毫秒，而从一次运行的一列里做出来的容量决定，是一个位数更多的猜测。
4. **断言 p99 的趋势。** 测出来的 p99 有多少属于机器，就有多少属于服务，而一个在某一级的最大值移动
   时就失败的规格，会被"修"成删掉它。断言算术能算的东西（积压）和界限（没有请求超过 `SLOWEST`）；
   把*形状检查*放在合成的曲线上证明。
5. **把订阅者测了进去。** 夹具的订阅者是故意立刻作答的。把负载运行指向一个要 200 毫秒的东西，你测的
   就是*那个*，而队列——这个服务自己拥有的那部分——从数字里消失了。
6. **只看吞吐。** 一个每秒接受 1100 个事件、只投递 200 个的服务，比一个接受 200、投递 200 的更差。
   排干数是报告里说明服务守住了承诺的那一半（`delivery/at-least-once`、`relay/2.6-at-least-once`）。
7. **每个核配一个 worker。** 上面已经量过：同样的八个座位，一个 worker 363 毫秒排干 400 次投递，两个
   worker 551 毫秒，八个 1.87 秒，因为每个 worker 每一轮都要付认领语句的固定成本。在数据库之外的
   东西成为瓶颈之前，更多的 worker 不是更多的吞吐。
8. **一页只有数字、没有方法。** debug 还是 release、容器还是 `127.0.0.1`、一个订阅者还是十个——其中
   每一样对答案的改变，都比今年代码会带来的改变更大。把方法写在表旁边。

## 延伸阅读

- [`tokio::task::JoinSet`](https://docs.rs/tokio/latest/tokio/task/struct.JoinSet.html)——一个 worker
  *本来会*用来托住许多尝试的东西；这一个用的是闸门加一个句柄向量（`relay/2.14-backpressure`），这个
  差别值得读一读
- [Prometheus: histograms and summaries](https://prometheus.io/docs/practices/histograms/)——为什么从
  桶里算出来的 p99 不是观测的 p99，以及 `histogram_quantile` 实际做了什么
- [Gil Tene: how NOT to measure latency](https://www.youtube.com/watch?v=lJ8ydIuPFeU)——协调遗漏，
  以及为什么一个等每个答案的负载生成器，能报出一个没有任何用户见过的 p99
- [Google SRE book: handling overload](https://sre.google/sre-book/handling-overload/)——有界队列是
  为了什么，以及卸掉负载和丢掉负载的区别
- [PostgreSQL: `EXPLAIN`](https://www.postgresql.org/docs/current/using-explain.html)——"这个 p99 是
  从哪来的"之后的下一个问题：哪个执行计划，它走了多少行
