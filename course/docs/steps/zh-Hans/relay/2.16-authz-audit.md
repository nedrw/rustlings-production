# 授权矩阵，以及它背后的审计轨迹

## 回顾

`sec/authz-tenant-isolation@apply`——`mailer/1.18-authz-boundary`：订阅者来要自己的投递，查询里带着
`subscriber_id = $1`，而属于别人的那一行回 `404`——跟一行不存在的记录得到的是同一个答案。一个路由，
一处检查，就写在那个能回答它的处理函数里。

## 变化

那是资源层面的归属：*这一行*、*这个调用方*、一个路由。这里变的是：问题不再按路由逐个问，答案也不再
是事情的全部：

- **权限模型是数据，路由也是数据。** 一张（角色、动作、范围）的表装着每一条授权，一张路由表说明每个
  路由是哪个动作，再由一个层拿路由表去问权限表。现在加一个路由却没加权限，是一处看得见的遗漏，而不是某个
  忘了加守卫的处理函数——而一个格子的*缺席*，是评审者读得出来的决定：整张表里没有任何一个格子，把
  一个租户的行授给另一个租户；
- **一次拒绝有三个理由，不是一个。** "我不认识你"是 `401`，"我认识你，但你不可以"是 `403`，"那不是
  你的"是 `404`——而第三个，就是一行不存在的记录得到的那个 `404`。`mailer/1.18` 有最后一个。它没有
  另外两个，也没有在它们之间做决定的那条规则：**`403` 说的是动作，永远不是行。** 对别人的行回
  `403`，是服务在确认那一行确实在那儿，而这正是猜的人在钓的信息；
- **特权决定先写下来，再执行，而这份轨迹是可读的。** 日志行写给正在看这个进程的人；轨迹则是服务自己
  数据库里的一张表，跟别的东西一样按同一条租户规则过滤，几个月后它还能回答"是谁动了这个，我们当时
  怎么决定的"。这意味着决定是在处理函数运行*之前*写下的：一个执行到一半死掉的特权操作，必须已经留下
  一行，说明它正要去做。这也意味着拒绝本身也是一行——而且，一条写不进去的轨迹，会拒绝这个动作。

层的位置是 `relay/2.1-project-skeleton` 教过的，这里不动：关联 id、日志、配额，然后是**身份**，现在
再加一个位于身份之后的层，它唯一的职责就是去问矩阵。最后两层之间的拆分是新东西，而且是故意的：身份层
回答的是*谁*（一个没有 key 的请求，和一个拿着谁都没签发过的 key 的请求，都是匿名的，把它们区分开，
就是在替猜测分类），而关于*可以做什么*的东西，除了矩阵，哪儿都不写。

## 任务

### `migrations/0008_audit.sql`

先 `ls migrations`：下一个空号就是你要用的号，而两个编号相同的 migration 会让 `sqlx` 把它们全部
拒绝。里面放两样东西：

- **角色挂在租户上。** `tenants.role`（`text not null default 'tenant-admin'`，配一个 `check`，
  列出这个服务有的角色）是这个服务的简化，值得明说：这里的租户恰好只有一把 API key，所以"一份凭据
  一个角色"和"一个租户一个角色"是同一件事。每人一把、每台笔记本一把、每个 CI runner 一把 key，才是
  通用的答案，而那是一张以凭据为键的表，不是一列；
- **轨迹。** 一个特权决定一行：租户、它执行时用的角色、动作、动作针对的东西、决定本身、请求的关联 id，
  以及时间。凭据不是一列，也永远不会是：这张表比它所记录的那把 key 活得久，而一条引用了 key 的轨迹，
  就是那份 key 的第二份副本，只是保留期更长。给这张表唯一的那条查询加上它需要的索引——一个租户的
  行，最新的在前。

### `src/authz.rs`

脚手架给了类型和一个空矩阵。用数据把它填上：

| 角色 | 可以做什么 | 作用于 |
| --- | --- | --- |
| anonymous | 读健康检查、就绪检查和契约 | 进程本身 |
| tenant-reader | 上面三项，加上读端点、事件、死信 | 自己的租户 |
| tenant-admin | reader 能做的一切，加上注册端点、接受事件、重放死信、读轨迹、读指标 | 自己的租户 |

- `GRANTS`——每一个格子，每个都是 `Scope::Own`。脚手架的形状让"给另一个租户的行授权"根本写不出来，
  而这正是要点；
- `granted(role, action)`——某个角色对某个动作拥有的最宽范围；
- `decide(role, action, scope)`——一个*处处有定义*的函数。一条授权覆盖它自己的范围以及所有更窄的范围；够不到所问
  范围的授权是 `Deny(NotVisible)`；压根没有授权时，匿名调用方拿到 `Deny(Unauthenticated)`，已知调用方
  拿到 `Deny(NotPermitted)`；
- `ROUTES`——路由表作为数据：方法、**axum 匹配时看到的**路径（`/dlq/{id}/replay`，占位符什么的都在），
  以及动作。这个服务提供的每个路由都在里面，`/audit` 也在，否则下面那一层永远不会拿它去问矩阵；
- `Action::is_privileged`——会改变东西、因此会留下一行的动作；
- `Action::is_metered`——花*租户*配额的动作。三个进程路由不计入配额：一个忙着的服务，如果它的就绪探针
  回 `429`，编排器就会把它重启。

### `src/audit.rs`

- `record(pool, entry)`——一条插入，在动作之前。`decision` 是 `Decision::as_str` 产出的那个 token：
  `allow`，或者原因。
- `list(pool, tenant, limit)`——调用方自己的行，最新的在前，租户条件写在 `where` 里。在 limit *之后*
  再过滤，就是一份会在第一页把别人的行发出去的列表。

### `src/http.rs`

- `identify` 取代了原来那个会拒绝的层：它查一把 key，有的话就把 `Principal` 插进请求。没有 key 的
  请求、以及 key 不属于任何人的请求，都继续以*匿名*身份走下去；
- `authorize` 在它之后运行。它读出匹配到的路由（axum 把*匹配到的*路径放进请求，叫 `MatchedPath`），
  去问 `authz::decide(role, action, Scope::Own)`，然后要么运行处理函数，要么用拒绝对应的状态码作答。
  没有路由匹配得上的请求，或者路由没有对应方法的请求，留给路由器：那里 axum 自己的 `404` 和 `405` 才是
  诚实的答案，不是 `403`；
- 特权动作在 `next.run(request)` **之前**写下它那一行，而一条写不进去的轨迹会结束这个请求。记下的目
  标是*路由*（`POST /events`），永远不是调用方敲出来的路径：审计列里一旦引用调用方输入，这一列装的就是
  调用方随手发来的东西；
- `/audit` 和别的读一样是读，所以读它不会给自己添一行；
- 限流器在花掉一个桶之前，拿匹配到的路由去问 `Action::is_metered`，而不是去查第二份"受限制的路由"
  清单；
- 现在路由器是**一个**。没有"公开"子路由器：`/healthz` 不带 key 也能访问，是因为矩阵这么说的，不是
  因为路由怎么拼装。

### `src/config.rs`, `src/db.rs`, `src/auth.rs`

租户条目写成 `name=key` 或 `name:role=key`——角色挂在*名字*上，因为 key 是一个不透明的密钥，可能包含
任何字符，而租户名允许哪些字符是明确限定的。没写角色的条目是管理员，所以这一步之前写好的配置继续能用。
`seed_tenants` 写入角色，`auth.rs` 里的查询在同一条语句里连名字一起把它读出来：角色是找到那把 key 的
那一行自带的属性，而这次查询之后，*请求*里说什么都改不了它。

### `src/error.rs`

一个新变体：`Forbidden(String)`，`403`，稳定 token 是 `forbidden`。它的消息点名被拒绝的动作，别的不
说。

### `src/openapi.rs`

`GET /audit` 和它的 schema，带上它能回的每一个状态。`relay/2.3-contract-first` 是一条常设规则，不是
一次性的：不在文档里的路由，就是一个没人对它的答复达成过一致的路由，而文档是拿运行中的服务来校验的。

## 完成标准

- `kiln run relay/2.16-authz-audit` — 规格通过
- `kiln check relay/2.16-authz-audit` — 每个 must 闸门都是绿的
- `cargo test --test spec_authz`——十一个用例：路由 × 角色矩阵、拒绝的三个理由、别人的行对不存在的
  行、reader 在矩阵里的整行、矩阵作为数据、每个特权决定一行且可追溯、被拒绝的写留在轨迹里而读不留、
  轨迹按租户过滤、没有任何头部或设置项能改变身份、轨迹里没有凭据，以及角色长在租户行上
- `RELAY__BOOTSTRAP__TENANTS='acme=key-acme-5f3d,reports:tenant-reader=key-reports-2c4f' cargo run`
  然后用 `curl`：
  `curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8080/events -H 'Authorization: Bearer key-reports-2c4f' -H 'Idempotency-Key: k' -d '{"kind":"a","payload":{}}'`
  打印 `403`，而同一条命令加上 `-H 'X-Role: tenant-admin'` 也打印 `403`
- `psql -c "select role, action, target, decision, request_id from audit_log order by at"`——每个
  特权请求一行，被拒绝的也在内

## 陷阱

1. **把矩阵写进处理函数里。** 每个路由都在函数体开头调一次 `decide`，跑得挺好，直到有人加了一个路由。
   然后那个路由对任何拿着 key 的人都有求必应，而它被加进去的那个文件里，看不出任何不对。规格的路由表
   就是从外面写的，正因为这个：一个从没问过矩阵的路由，就是一个对矩阵拒绝的调用方也回 `200` 的路由。
2. **对别人的行回 `403`。** `GET /dlq/{id}` 拿着另一个租户的 id 回一句"禁止访问"，等于回答了调用方
   本来无权问的问题：那一行存在。对那一行唯一安全的答案，跟一行不存在的记录得到的答案逐字节相同，这
   意味着产出它的检查是*查询的*，不是矩阵的。
3. **相信头部。** `X-Role: tenant-admin`、`X-Tenant-Id`、`X-Forwarded-Tenant`，body 里的一个 `role`
   键：每一个都是某人敲进去的文本，而一个会读其中任何一个的服务，它的授权模型网络上的任何人都能改。
   规格以 reader 的身份把它们全发一遍，每次都期望同一个 `403`。
4. **动作之后才写轨迹。** 有意思的行，正是进程死在中间的那些。先写行，再动手：这个服务说不清的动作，
   就是它不做的动作，于是失败路径是一次拒绝，而不是一行没人看的日志。
5. **把每一次读都记进轨迹。** 每个请求一行听着很周全，其实是一张比它所描述的流量长得还快的表，而且长
   在这个服务正努力服务的数据库里。特权的意思是"改变了我们欠什么，或者谁够得着它"。
6. **凭据进了轨迹。** 不在列里，不在 target 里，也不在一个攻击者挑的 `request_id` 里：在这个服务判定
   它靠谱之前，request id 就是调用方输入，而读轨迹的人，可能并没有权限看那把 key。要断言这件事：规格
   会拿 key 和签名密钥把整张表 grep 一遍。
7. **角色只在启动时校验，数据库不校验。** 配置会拒绝这个服务没有的角色，然后有人凌晨三点跑一句
   `update tenants set role = 'owner'`：check 约束才是给那些不是这段代码写下的行准备的答案，而查角色时
   必须在一个它不认识的角色上大声失败，而不是悄悄默认成别的。
8. **该回 `403` 的地方回 `401`。** 两者不能互换：运维会把 `401` 读成"调用方的 key 有问题"，把 `403`
   读成"调用方的 key 没问题，是请求不对"。对一个无权写的 reader 回 `401`，会让人去轮换一把其实好端端
   的 key——而一个在 `401` 上重试的客户端（刷新 token），会永远重试下去。
9. **文档里缺了一个路由。** `/audit` 是一个新路由，带一个新状态（`403`），而文档要拿运行中的服务来
   校验：它必须声明这个路径，也必须描述服务真正回的那个状态。
10. **给进程路由计配额。** 配额以调用方为键，而就绪探针没有 key：把限流器放到 `/readyz` 前面，一个忙
    着的服务就会被编排器用来判断它健不健康的那同一个探针回 `429`。租户的配额该落在为租户工作的那些
    路由上。
11. **记录一个没有租户做过的决定。** 匿名请求没有租户，所以来自它的*特权*请求回 `401`，也不留行——
    没有东西可以挂上去。这是一条值得知道的边界，而不是一个该糊上的缺口：未认证的尝试，是在日志行里
    看得见的。

## 延伸阅读

- [OWASP: Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)
  ——默认拒绝、把检查集中到一处，以及 DELTA 里那个 `404` 所针对的 IDOR
- [PortSwigger: access control vulnerabilities](https://portswigger.net/web-security/access-control)
  ——这一步的矩阵正是照着这些错误塑造的，包括一个 reader 的 `403` 所对应的纵向越权
- [PostgreSQL: row security policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
  ——这条规则还能落在的另一个地方：由数据库为每条语句强制 `tenant_id`，以及运维它的代价
- [`axum::extract::MatchedPath`](https://docs.rs/axum/0.8.9/axum/extract/struct.MatchedPath.html) —
  为什么处理函数前面的层能看到路由的*模板*，而不是调用方敲出来的路径
- [NIST: role-based access control](https://csrc.nist.gov/projects/role-based-access-control) —（角色、
  动作、范围）这张表的来历，以及带继承的模型长什么样
