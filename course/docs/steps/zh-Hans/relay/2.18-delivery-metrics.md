# 投递可观测性：延迟、积压，以及哪个租户慢

## 回顾

`obs/metrics-slo@aware`——`mailer/1.20-metrics`：一个手工写出来的 `/metrics` 端点，用 Prometheus 文本
格式，每个路由一组计数器，还有一个 `deliveries_total{outcome}` 计数器回答"发生了多少"。原样带过来
的，是这个端点：媒体类型、`# HELP` 和 `# TYPE` 行，以及那条规则——文本由一个函数产出，而不是由记得去
调它的那个人手工拼起来。

## 变化

一个"发生了多少"的计数，并不是运维会为它触发告警的东西，而它缺三样东西：

- **要分布，不要平均值。** "投递耗时 300 毫秒"和"99% 的投递耗时 12 毫秒，其余的要四秒"是同一个平均
  值，却是两个不同的服务。让这个差别看得见的，是直方图——分桶、累积、最后一个是 `+Inf`——而直方图
  也是这里唯一一个*往上涨*意味着还有没做完的活的指标；
- **要队列，不要吞吐。** 一次延迟尖峰和一个停止作答的订阅者，在计数器里长得一模一样，对着积压看却
  截然不同。这个 gauge 必须在被抓取的那一刻从队列里读：一个在轮次之间记着的数字，是关于过去的数字，
  而那恰恰是会错过事故的那个数字；
- **按租户，而且有界。** "哪个租户慢"是一个多租户服务真正会被问到的问题，也是会让一个指标端点被拿下
  的问题：每个 label 值都是每个 scraper 里的一条序列、背后存储里的一个索引，所以 label 集合必须是一
  个这个服务*自己选的*集合——配置能限定的那些租户名——而绝不能是一个端点 URL、一个事件 id，或者一个
  调用方编出来的路径。不在名单里的，折进 `unknown`，而不是丢掉或者留着。

窥视队列的那个窗口，也是抓取唯一会碰到数据库的地方，而这里的取舍是真的：一个准确的 gauge 每次抓取要
花一条查询，一个缓存的 gauge 不要钱，还会撒谎。这一步选准确，并且明说一个有张大表的部署会怎么处理它（给
状态建索引，或者按定时器缓存，接受它过期）。

两个邻居，而这一步不是它们中的任何一个：`obs/structured-logs@apply`（`relay/2.1`）是跟进
*某一次具体的*投递、请求或失败的地方——日志行对每个不同的值都不花钱，而指标要花一条序列，所以"哪个事件
失败了"归日志，"多少在失败"归这里；`obs/cardinality-cost@apply`（后面某个 track）是关于 label 有多
大代价的学问，这一步只在一个地方用它，而不去研究它。

## 任务

脚手架加了 `src/metrics.rs`。这一步其余的一切，都在你已经拥有的文件里。

### `src/metrics.rs`

- `Outcome`——三个值，不能再多：`sent`、`retried`、`dead`。worker 的报告里还有 `lost`（一次它没能
  记下来的尝试）和 `shed`（一次它压根没做的尝试，因为端点的熔断器开着）。两者都不是关于一次投递的
  事实，而第四个 label 值如果意思是"去问日志"，那就是一条谁都没法查询的序列；
- `BUCKETS`——固定的边界。固定，而不是可配置：一个在两次部署之间会移动的桶，就是一个跟着它移动的
  仪表盘。直方图是**累积的**——落在五毫秒以内的观测，也在它之上的每一个桶里——正是这一点让最后一个
  桶等于总数；
- `Metrics::record(tenant, outcome, elapsed)`——`&self`，因为一轮里的尝试是几个任务同时跑的，而一个
  可变地发出去的 registry 会把它正在测量的投递串行化；
- `Metrics::render(backlog)`——导出的文本。每个 family 一条 `# HELP`、一条 `# TYPE`，然后每个样本一
  行。每个 family 对每个租户 label **从第一次抓取起**就在了：一个要等到第一次投递之后才冒出来的直方
  图，是一个得应付序列缺失的仪表盘查询；而一个显示尖峰的计数器，只有对着在它之前就在的基线才读得懂；
- label 值是租户的**名字**，而任何不可能是这个服务写出来的名字，都在*记录的时候*折进 `unknown`，不是
  在打印的时候：折进去这件事，一半是为了内存，一半是为了输出。

### `src/claim.rs`

`Claimed` 多了租户的**名字**，由认领自己的 join 带回来。认领本来就把目标和事件 join 进来了，原因正是
这个（`relay/2.5-atomic-claim`）：一个每次尝试都要多一个往返的指标，就是一个会把它所测量的东西拖慢的
指标。

### `src/concurrency.rs`

`Worker::metered(registry)`——一个 builder，跟 `leasing` 一样——以及围绕*尝试*读的时钟：座位和记录都
在测量之外，因为这个数字说的是订阅者花了多久。有两种结果不记录，原因在 `outcome_of` 里。

### `src/http.rs`, `src/main.rs`, `src/authz.rs`, `src/openapi.rs`

- `AppState` 拥有 registry 并把它发出去；`main.rs` 把*同一个*交给 worker，于是进程导出的就是它测量
  的；
- `GET /metrics` 读积压、渲染文本，回 `text/plain`。它跟别的路由一样：`relay/2.16-authz-audit` 决定
  谁能读它（scraper 拿一把 `tenant-admin` 的 key——label 集合是每个租户的名字，那不是 reader 该知道
  的事），而 `relay/2.3-contract-first` 要求它出现在文档里，带上它能回的每一个状态。

## 完成标准

- `kiln run relay/2.18-delivery-metrics` — 规格通过
- `kiln check relay/2.18-delivery-metrics` — 每个 must 闸门都是绿的
- `cargo test --test spec_metrics`——八个用例：端点及其 family、谁能抓取、一个慢租户对一个快租户、
  每个租户的积压、累积直方图、有界的 label 集合、一次死掉的投递，以及契约里的这个路由
- 服务跑着的时候，
  `curl -s localhost:8080/metrics -H 'Authorization: Bearer <a tenant-admin key>' | grep -E 'relay_(backlog_depth|deliveries_total)'`
  显示每个租户、每种结果一行，而
  `psql -c "select state, count(*) from deliveries group by state"` 与 `relay_backlog_depth` 一致
- `curl -s localhost:8080/metrics -H 'Authorization: Bearer <a reader key>'` 回 `403`，而不带 key 的
  同一个请求回 `401`

## 陷阱

1. **label 里放端点 URL、事件 id 或者路径。** 端点是最自然不过的投递指标 label，而它也是会让这个服务
   完蛋的那个：一个有上万个端点的租户，就是每个指标、每种结果上万条序列，在每个 scraper 里，永远。规
   格会断言没有任何 label 值不是租户名或 `unknown`。
2. **不累积的直方图。** 把每个观测恰好数进一个桶，是最直觉的实现，而它产出的序列里 `+Inf` 不等于总
   数，由它算出来的分位数比真值小。规格会走一遍各个桶，拿最后一个跟 `_count` 比。
3. **在轮次之间记着的 gauge。** 一轮跑完时才更新的积压，是一个在队列正增长时恰好过期的数字——而那个
   时刻正是它存在的理由。要的时候，从队列里读。
4. **一个熬过了它所描述的那次故障的缓存 gauge。** 同一个决定的另一半：数据库读不了的时候，诚实的答案
   是报错，不是这个进程碰巧记得的上一个数。一个装着过期 gauge 的 `200`，是运维会照着行动的数字。
5. **一条只在第一次投递之后才存在的序列。** 对着一个后来才出现的 family 写的仪表盘查询，在安静时段
   显示"没有数据"，而这跟服务挂了分不出来。从一开始就导出每个 label 的序列。
6. **一个不是总和的 `sum`。** `_sum` 和桶必须来自同一份观测：一个由直方图算、另一个把样本再扫一遍
   算，平均值就越出它自己那些桶的范围了。
7. **worker 自带一个 registry。** `Worker::new` 里写 `Arc::new(Metrics::new())` 很诱人，它给出的进程
   把投递测量进一个谁都没法抓取的 registry。一个进程，一个 registry，交给两半。
8. **用循环逐个租户读积压。** 每个租户一条查询，把一次抓取变成 N 个往返，也让端点的代价成了有多少
   客户的函数。它是一条分组查询。
9. **把认领、座位或记录也算进时间。** 一个在拿到座位之前就启动计时的直方图，测的是 worker 等了
   多久的空位——一个真实的数字，但不是任何人要的那个。花时间的是尝试。
10. **在答案就是 label 集合的地方回 `403`。** 这个路由的权限是关于*信息*的决定，不是关于行的：
    reader 可以读自己的投递，而这些数字是关于整个服务的。
