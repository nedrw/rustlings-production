# 不管投几次，事件只被接受一次

## 为什么

这跟 `delivery/idempotency@apply`（`mailer/1.15-idempotent-delivery`）不是同一个问题，两者只共享一个名字：
那里服务是*发送方*，要避免同一封信发两遍；这里它是*接收方*，重复请求来不来由不得它。那一步的东西不重讲——
这一步加的是入口侧的键、让重放用第一个事件作答的那种唯一性，以及"重试"和"犯错"之间的区别。

凡是发 webhook 的都会重试，而每一次重试都是这个服务必须挺过去的请求，不是它能拒绝的请求。请求处理完了、答复
还没送到，连接断了；代理超时了；发送方的进程在发送中途被重启了。从发送方看，那是一个事件；从这边看，是三个
POST，而每个 POST 一次 `INSERT`，就把一个业务事件变成给每个订阅者的三次投递：三张发票、三封邮件、三次扣款。

发送方自己修不了这件事，而这正是要点：它不知道自己正在重试的那个请求处理了没有——它也正是*因为不知道*才重试的。
只有发送方知道它哪些请求是同一件事，所以只有发送方能给它们起名。那个名字就是 `Idempotency-Key`，而本服务这一
半的承诺比"别存两遍"更强：重试必须被*答复*，且答案与第一次请求产出的一样——一个重试却拿到错误的客户端，要么
一直重试下去，要么放弃一个已经被接受的事件。

名字还归属于租户。两个租户都把自己的第一个事件叫做 `order-1`，那是两个事件——所以这个承诺说的是一对值，
不是一个字符串。

## 任务

脚手架加了 `src/events.rs`：类型，以及 `ingest` 的签名。表、路由和模块接线归你。

### `migrations/0003_events.sql`

一张表 `events`：`id uuid primary key`（由本服务生成，绝不由调用方生成）、
`tenant_id uuid not null references tenants (id) on delete cascade`、`idempotency_key text not null`、
`kind text not null`、`payload jsonb not null`、`received_at timestamptz not null default now()`——再加上一条
让"一个键一个事件"可执行而不是可期待的约束。规格直接问数据库（`select count(*) from events`、
`select payload->>'amount' from events`），所以那些名字和 `jsonb` 类型都是契约的一部分；约束这里没写出来，
因为选哪一条正是这一步的内容。

### `src/lib.rs`

声明模块：`pub mod events;`——在你这么做之前，这个文件根本不参与编译，`clippy` 也看不见它里面的 `todo!()`。

### `src/events.rs`

实现 `ingest`：存下了事件的请求回 `Ingested::Accepted(event)`；发现这个租户的键已被占用的请求回
`Ingested::Replayed(event)`——重放里的那个事件是表里已有的那一行，带着第一次发来的 `kind` 与 `payload`，
不是眼下这个请求里的。

### `src/http.rs`

- `POST /events`，在认证层后面。租户来自 API key；body 里没有任何东西说明谁在调用。
- body：`{"kind": "<what happened>", "payload": {…}}`。`kind` 不能为空，`payload` 必须是 JSON 对象；
  压根不是 JSON 的 body 是 `400`，因为那是调用方的错，而这里一个 panic 会把进程一起带走。
- `Idempotency-Key` 必需。缺失或为空是 `400`——不是 `401`：这个调用方*确实*拿着有效的 API key，而是这个请求
  本 API 收不了。那句话要点名这个头部。
- 答复是 `{"id": …, "kind": …, "payload": …, "received_at": …, "replayed": …}`：
  - 这次请求存下了事件：`201`，`"replayed": false`；
  - 这个租户早就发过那个键：`200`，`"replayed": true`，带着*存下来的*事件。
- 在头部与 body 都被接受之前，什么都不写：被拒绝的请求让表保持原样。

## 完成标准

- `kiln run relay/2.2-idempotent-ingest` — 规格通过
- `kiln check relay/2.2-idempotent-ingest` — 每个 must 闸门都是绿的
- 对运行中的服务用一个键把同一个 body 投两次，先回 `201`、再回 `200`，`id` 相同，而
  `psql -c "select count(*) from events"` 答 `1`——同一个键从第二个租户发出，则得到第二行、第二个 `id`

## 陷阱

1. **读、判断、写。** `select … where idempotency_key = $1`，查到空就插入，是一次带窗口的竞态：两个在途的重试
   都读到空，都插入。规格数出的行数是 2，而重复是*无声的*——答复里没有任何东西说这个事件正在往两边走。让数据库
   来做裁决。
2. **`on conflict do update`。** 冲突时覆盖那一行能通过"没有重复行"，却破坏了"同一个答案"：客户端拿同一个键
   发来新内容，会把自己旧的事件悄悄换掉。规格第二次 POST 发的是不同的 `kind`，要回的却是存下来的那个。
3. **给重试回一个错误。** 键被占时回 `409`（或 `500`），恰好打断了幂等键为之存在的那类客户端：它会重试、拿到同一个
   错误，然后放弃一个本服务已经接受的事件。重放该是 `200` 加那个事件。
4. **`unique (idempotency_key)`。** 第一个用 `order-1` 的租户，把其他所有租户的 `order-1` 都堵死了，规格里第二个
   租户会为一个全新的事件拿到主键冲突。键是那一对。
5. **`payload text` 而不是 `jsonb`。** 行里于是装着 `"{\"id\":\"inv_1\"}"`——一个看起来像 JSON 的载荷：
   `payload->>'amount'` 会失败，而每个要按事件过滤的订阅者都得自己再解析一遍。`jsonb` 才让这一列可查询——
   而 `select payload->>'amount'` 正是规格要问的。
6. **先存后校验。** 一个已经被拒绝、却已经写了行的请求，会在表里留下一个任何订阅者都不该收到的事件。规格会发五个
   必须被拒的 body，然后数行：它期望一个都没被存下。
7. **把空的 `Idempotency-Key` 当成键。** `Idempotency-Key:` 后面什么都没有，是一个本想发送却漏了值的客户端：
   接受它，会让这个租户的每个事件都和第一个撞上。
8. **从键推出事件 `id`。** 把 `(tenant, key)` 哈希成 id，会让两个租户共用一个键时共享同一个身份，还把调用方的命名
   习惯泄漏进这个服务。id 在这里生成；键只用来比较。
