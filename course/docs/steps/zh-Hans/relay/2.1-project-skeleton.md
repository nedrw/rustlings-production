# 重建服务骨架：类型化配置、日志、迁移、中间件

## 回顾

`repo/workspace-layout@apply`——`mailer/1.1-workspace`：库拥有这个服务，`main.rs` 只是一层壳。
`cfg/layered-config@apply`——`mailer/1.4-config`：默认值 < 文件 < 环境 < 旗标，`--check-config` 打印
生效的设置，密钥只报告"已设置"、从不打印。`obs/structured-logs@apply`——`mailer/1.6-logging`：每次运行
一个关联 id，每个请求一行日志，格式由配置决定。`db/migrations@apply`——`mailer/1.9-postgres`：连接、
迁移、然后才监听；`/healthz` 与 `/readyz` 回答的是不同问题。

## 变化

同样的服务骨架，换一个项目，但有三处是新的：

* **中间件有顺序，而顺序就是要点。** 在 `mailer` 里，关联 id 和请求日志挂在同一个路由组上，认证则是处理函数
  内部的一次检查。这里，id、日志、认证都是*层*，而层跑在拒绝之外：一个因为缺 key 被拒的请求，照样带着它被
  赋予的那个 id，照样带着这个 id 出现在日志里。一个把这件事做错的服务，运维第一件做不到的事，就是追查那些被
  拒绝的请求；
* **schema 从第一份迁移起就是多租户的。** `tenants`、`endpoints`，以及"一行只属于一个租户"这条规则。你不会
  以后再加 `tenant_id`：`mailer` 是在数据模型立起来之后才讲授权边界的，而那一版我们不重演；
* **闸门更严，提示没了。** 从这一步起就是 `clippy@2`——每个非测试目标里都不许 `unwrap`、不许下标、不许
  `panic`。服务代码没有脚手架：桩就是签名，填什么是你的事。

`relay` 不是换了个名字的 `mailer`。事件经 POST 进来，先存下来再答复，而投递那一整套机制——重试、顺序、死信、
签名——是接下来二十三步要建的东西。这一步是它们不必回头再补的地基。

## 任务

- 照 `mailer/1.1` 的方式拆 crate：`src/lib.rs` 拥有模块，`src/main.rs` 只决定启动顺序和退出码。
- 实现配置分层（默认值 < 文件 < 环境 < 命令行）、`--check-config` 报告，以及"连接串只报 `set`、绝不打印"
  这条规则。
- 实现结构化日志：一个运行 id、两种格式，以及一行能让运维（和测试）读出绑定地址的启动日志。
- 实现数据库层：一个连接池、编进二进制的迁移、就绪探针，以及这份配置点名的租户在启动时被播种（要幂等——轮换的
  密钥必须在下次重启时生效）。
- 实现 HTTP 表面，层按这个顺序：关联 id、请求日志、认证、处理函数。`/healthz` 与 `/readyz` 公开，`/endpoints`
  不公开。
- 实现 `POST /endpoints`（收一个 URL，给出一个 id 和一个*生成的*签名密钥）与 `GET /endpoints`（调用方自己的
  端点，绝不带密钥），外加客户端读得懂的 404 与 405。

## 完成标准

- `kiln run relay/2.1-project-skeleton` — 规格通过
- `kiln check relay/2.1-project-skeleton` — 所有 must 闸门都是绿的
- `RELAY__DATABASE__URL=… RELAY__BOOTSTRAP__TENANTS=acme=… cargo run -- --check-config` ——生效的设置被打印，
  密钥显示 `set`，而且不绑定任何端口

## 陷阱

1. **在每个处理函数里做认证。** 它能用，却让被拒请求的日志行成为不可能：写那行的层在拒绝它的层*里面*，所以 401
   永远到不了它。规格会发一个带 id 的请求，并在日志里找那个 id。
2. **路由里校验的是密钥，存下来的却是明文。** 永远比哈希，并且按哈希去查：密钥从来不需要可还原，而用明文存它，
   就是让一次数据库泄露变成一整组凭据泄露的原因。
3. **对请求体 `unwrap()`。** 有了 `clippy@2`，这是闸门失败而不是评审意见，但它成为闸门的原因是运行时：陌生人送来的
   畸形请求体必须是 400，不能是一个把进程一起带走的 panic。
4. **非幂等地播种租户。** 每次启动都 `INSERT`，就把重启变成主键冲突——而那恰恰是最不欢迎出错的时候。
