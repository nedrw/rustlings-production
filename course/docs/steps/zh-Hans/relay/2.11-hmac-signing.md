# 发出什么就签什么：HMAC、时间戳，与恒定时间的比较

## 为什么

webhook 目标是一个 URL，而 URL 不是身份。任何人只要知道了它——从日志、截图、一个记录头部的代理里、
一个放着示例配置的仓库里——就能往它 POST 一个 body，而接收方的应用没有任何办法把那个请求和真的请求分
开。TLS 帮不上忙：它证明的是*服务器*是谁，对请求出自谁手一字不提。`x-relay-delivery` 头部也不行，那
是一个谁都能敲进去的字符串。

唯一能做到这件事的，是一个两端知道、别人都不知道的密钥，把它当作**带密钥的 MAC** 来用：在请求的精确字节之
上算出的一小段标签，只有拿着密钥的人才算得出来。要让这件事有价值，得有三件事同时成立，而每一件都是有
人会跳过的一步：

- **标签必须覆盖真正发出去的那些字节。** 签一个事件重新序列化之后的结果，或者签一个解析完又重建的 body，
  产出的签名接收方复现不了——同一个 JSON 值有很多种写法，而到了对面的是哪一种，就按哪一种算；
- **标签必须绑在它所属的那个请求上。** 一个只能证明"某个拿着密钥的人发过这个 body"的标签，就是一个
  bearer 令牌：可以从一个请求上揭下来，配着另一个请求重放。投递 id 与时刻因此才进了签名材料——时刻让签
  名*会过期*，投递 id 让签名不能被搬去给另一次投递重放；
- **比较必须是恒定时间的。** 一个在第一个不对的字节处就停下的标签比较，等于一个字节一个字节地告诉对面
  猜对了多少，而签名恰恰是攻击者可以拿任意多个请求去猜的那种值。这是这个服务里唯一一个写 `a == b` 就错
  了的地方。

密钥*从哪儿来*也归这一步。worker 的请求类型是 `relay/2.6-at-least-once` 的那个端口，而密钥由即将发送
的那个适配器现查——不跟着队列走——这样，那个绝不能进日志行的值，就只留在唯一需要它的组件里。

## 任务

脚手架加了 `src/signing.rs`——`Secret`、`Window`、`Verified`、`SignatureError`、`Secrets` 端口、
`sign`/`verify`/`tags_match` 和 `DbSecrets`，而这一步要回答的正是里面那些 `todo!()` 的函数体——以及
`tests/support/keys.rs`，一个由测试手工填值的 `Secrets` 存储。它还往 `Cargo.toml` 里加了两个依赖：
`hmac` 与 `subtle`。

### `src/lib.rs`

声明模块：`pub mod signing;`。

### `src/signing.rs`

- **格式就一句话，而头部就是契约。** 签名串是 `v1.<timestamp>.<delivery-id>.<body bytes>`，标签是用该
  端点的密钥对 `HMAC-SHA256` 求值后的小写十六进制，而签名头部就是同一个串，只是 body 那一段换成了标签。
  规格钉住了一组黄金向量（写明的输入，以及它产出的那个精确头部），有了它，另一个语言写的接收方不必读这
  份实现，也能核对自己的实现。
- **`sign(secret, timestamp, delivery, body)`**——确定性的，而且作用在字节上：`body: &[u8]`，绝不是一个
  值。时刻是参数，不是函数内部的 `Utc::now()`，理由和 `relay/2.8-retry-budget` 的预算也要收一个时刻一
  样：一个自己读时钟的函数，没有时钟就判不了。
- **`verify(secret, headers, body, delivery, now, window)`**——接收方的那一半，顺序就是接收方读自己那行
  日志的顺序：这是我认识的版本吗，时刻在窗口里吗，这个签名*是不是这次投递的*，最后才轮到标签。让两个时
  刻（`x-relay-timestamp` 头部里的那个，与签名里的那个）是同一个值，也是它的一部分：查了其中一个、却哈
  希了另一个的接收方，漏洞正好有一个重放那么大。
- **`tags_match(expected, provided)`**——那次比较，交给 `subtle` 的 `ConstantTimeEq`。让它保持 public：
  对下一个读这个模块的人来说，"恒定时间的那一位住在哪儿"的答案就是它，而规格也用它来查：标签上的每一次单字符
  变异，都以同样的方式失败。
- **`Secrets`**——一个返回 boxed future 的 trait，理由是 [`crate::delivery::Sender`] 也是这样一个 trait：
  trait 的 `async fn` 没法通过 `Arc<dyn …>` 分发。`DbSecrets` 是生产实现：每次尝试都在
  `unique (tenant_id, url)` 上做一次走索引的查询，于是表里轮换过的密钥不用重启就能拿到。
- **签不了的东西就别发。** 存储返回的 `Ok(None)` 是一个真实答案，适配器把它变成*永久*失败：一个没签名
  的请求，接收方分不清它和别人发来的请求，而可选的签名不叫签名。存储读不出来则是可重试的——端点本身可能
  一点毛病都没有。

### `src/outbound.rs`：适配器来签名

`HttpSender::signing(policy, secrets)` 是新的构造函数（`new(policy)` 还在，也仍然不签名）。在 `send`
里：

- 在 body 拼好**之后**再查密钥，签的是*上线的同一批字节*：先 `let payload = body.to_string();`，再签
  `payload.as_bytes()`，然后把那个字符串放进请求。别为了签名再序列化一遍——规格的 *"another spelling of
  the same JSON"* 用例说的就是这个 bug；
- 用 `Utc::now().timestamp()` 盖上 `x-relay-timestamp`，用 `signing::sign(...)` 盖上
  `x-relay-signature`；
- 发送方签不了的投递是一次失败的尝试，不是一次已投递：端点没有密钥是 `Permanent`，存储读不出来是
  `Retryable`。

### `tests/support/keys.rs`

夹具是课程给的：一个架在 map 上的 `Secrets` 存储，这样关于*格式*的规格不需要数据库也能拥有一个密钥。
规格的最后一个测试用的是 `DbSecrets` 和某个租户实际拿到的那把密钥，这也正是那一步要在 `track.toml`
里声明 `images` 的原因。

## 完成标准

- `kiln run relay/2.11-hmac-signing` — 规格通过
- `kiln check relay/2.11-hmac-signing` — 每个 must 闸门都是绿的
- `cargo test --test spec_signing`——九个用例：黄金向量、确定性、被改过的 body、同一份 JSON 换了写法的
  body、为另一次投递签的签名、窗口的两条边界以及边界的两侧、未知版本和每一种畸形头部、六十四个错误标签统一的失
  败方式，以及经由 `HttpSender` 的两个端到端用例
- 接收方可以手工核对：
  `printf '%s' 'v1.1760000000.<delivery>.<body>' | openssl dgst -sha256 -hmac whsec_…` 就是规格黄金向
  量所期待的那个标签
- `curl -H "Authorization: Bearer $KEY" -d '{"url":"https://example.test/hook"}' localhost:8080/endpoints`
  会答复一个 `secret`，而发往那个端点的一次投递带着一个能用它验过的头部

## 陷阱

1. **签的是重新序列化的 body。** 先签 `serde_json::Value`、再序列化；或者用两个不同的 writer 序列化两次。
   接收方哈希的是*到达*的那批字节，所以签名只在两边对写法意见一致时才匹配——而那是 JSON 库版本的属性，不
   是协议的属性。`sign` 收 `&[u8]`，适配器签它要发出去的那个字符串。
2. **用一个普通哈希签 `key || message`。** 它看起来像 HMAC，其实不是：把密钥拼在输入前面的哈希函数经不
   起长度扩展，于是给一个 body 的标签，也是给另一个 body 的标签。用 `hmac`——这个 crate 存在，就是因为手
   工卷这个是人们真会犯的错。
3. **用 `==` 比较标签。** 它编得过，每次都对，还泄漏出猜测是从哪个字节开始偏的：比较在第一个错字节处停
   下，于是花的时间是"标签对了多少"的函数。修它的是 `subtle::ConstantTimeEq` 这一行，而规格里之所以有那
   个形状检查，是因为一条计时的断言只会是一个时灵时不灵的测试，不是证明。
4. **签名没有过期时间。** 签名材料里没有时刻，被截获的请求就永远有效，而一个把它记进日志的接收方（或者
   一个缓存它的代理）派发的是一张永不过期的 bearer 令牌。把时刻签进去，再拿窗口查它——两个方向都查，因为
   时钟在两边都可能不一致。
5. **两个时刻，只查了一个。** 时间戳既在 `x-relay-timestamp` 里，*也*在签名串里：一个查了头部、却哈希了
   另一个值的接收方，有一个洞。让它们是同一个值——不一致就拒绝这个请求——而不是信任头部。
6. **标签没有绑到投递上。** 只查标签、不查标签里的投递 id，签名就变成了 bearer 令牌：为一次投递签的请求，
   放到任何别的投递上也能验过。规格的 *"a signature is for one delivery"* 测试说的就是这个。
7. **密钥进了日志行。** 持有密钥的类型上一个 `#[derive(Debug)]` 就会把它打印出来，而那行最后会出现在日
   志聚合器里、bug 报告里和屏幕共享里。`Secret` 的 `Debug` 是手写的（`Secret(<redacted>)`），为的就是这
   个——保持原样。
8. **密钥进了请求。** 让密钥跟着队列走（`SendRequest`），就会把密钥材料塞进每一个碰到投递的结构里、每一
   个这样的结构的 `Debug` 里，以及死信表的理由里。适配器在用它的地方现查，这也正是轮换不用重启就看得见
   的原因。
9. **查不到密钥还照发。** `Ok(None)` 的意思是"这个服务在那个端点上没有密钥"，照样发出去，就把签名变成了
   可选的——接收方分不清哪些没签名的请求是这个服务自己选择发的，哪些是攻击者发的。拒绝，而且永久拒绝。
10. **窗口拒绝自己的边界。** `now - timestamp > max_age` 和 `now - timestamp >= max_age` 只差一个签名，而错
    的那一个，会拒绝一个恰好落在边界上的接收方本来会接受的请求。两条边都该在窗口里面，规格会查它们。
11. **版本靠猜。** 一个拿 `v1` 的规则去验 `v2.…` 的接收方，等于已经同意了一套没人规定过的方案。拒绝未知
    的版本，并且把版本留在签名材料里，让它没法在途中被改。

  服务来核对自己实现的接收方

  crate，以及 `Mac` trait，它的 `new_from_slice` 接受任意长度的密钥
- [`subtle`](https://docs.rs/subtle/2.6.1/subtle/trait.ConstantTimeEq.html) ——`ConstantTimeEq`，以及那
  份讲清它能承诺什么、不能承诺什么的文档
- [Stripe: webhook signatures](https://docs.stripe.com/webhooks#verify-manually) ——生产环境里的同一种
  格式（`t=`、`v1=`、一份签过名的载荷），包括容差窗口

  ——另一个接收方对"签名材料里必须有什么"的看法
- [Coda Hale: how to safely compare two strings](https://codahale.com/a-lesson-in-timing-attacks/) ——
  这一步的比较所针对的计时攻击，带数字
