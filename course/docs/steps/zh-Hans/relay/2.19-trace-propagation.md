# 把 trace 带过边界：W3C traceparent

## 回顾

`obs/tracing-propagation@aware`——`mailer/1.6-logging`：每次运行一个关联 id，从 `1.7` 起每个请求一
个，跟着这个请求做过的每一件事的日志行往下走。它在一个进程内部回答"哪些行是一起的"，而当调用方自己
发来一个头部时，它就是调用方的那个头部。

## 变化

那个 id 是真的，而它的作用域是一个进程。这里，请求早在活干完之前就结束了：

```text
caller ──traceparent──▶ relay (POST /events) ──queue──▶ worker ──traceparent──▶ subscriber
          1 trace id                              1 trace id
          1 span id            the event and the deliveries are written in one commit
```

变的是三件事，每一件都是形状，而不是一行代码：

- **上下文跟着活走，不跟着进程走。** 投递是几分钟、几小时之后由一个从没见过这个请求的 worker 做的，
  所以 trace id 被*写下来*——投递行上的一列，在接收事件的那个事务里一起写——再由跟订阅者说话的那个
  适配器读回来。task-local 或者 thread-local 在每个测试里都传播得漂漂亮亮，在每个部署里都把 trace
  弄丢；
- **每一跳有自己的 span，共享的只有 trace id。** 调用方的 span 是调用方那一跳；投递是另一跳。一次
  投递的两次尝试是两个 span，正是这一点让一次慢重试以*重试*的样子出现，而不是一次很长的请求。采样
  决定不归这个服务做：它传播到达时的那个，因为一个没有采样器的跳，没有资格推翻开启这条 trace 的那个
  采样器；
- **头部是解析出来再重新生成的，永远不是转发。** 发出去的是这个服务用存下的 trace id 自己拼的头部
  ——`00-<trace>-<span>-<flags>`，全小写，没有全零的 id，正好四个字段。把调用方的字节透传过去，是
  一个服务变成谁发什么都转的转发器的方式，也是一个坏掉的 trace id 在别人的系统里变成一条坏 trace 的
  方式。这个服务读不懂的头部不是错误：trace 重新开始，投递照做，因为丢了一个父链接是差一点的 trace，
  丢了一个事件是差一点的服务。

格式是 [W3C's `trace-context`](https://www.w3.org/TR/trace-context/)，而在这里亲手写它的意义就在于
此：订阅者是一个这个服务一无所知的系统，唯一能让 trace 穿过它的，是这些 id 在两边意思相同。

两个邻居：`obs/structured-logs@apply`（`relay/2.1`）是 trace id 最后落进一行运维能搜的日志的地方，而
*请求* id 保持原样——它是这个服务自己对一个请求的抓手，不是调用方的追踪系统跟下一个服务共享的东西。
两个都在日志行里，回答的是不同的问题。

## 任务

脚手架加了 `src/trace.rs`，还有一个 migration 归你写。其余的一切都在你已经拥有的文件里。

### `migrations/0009_trace.sql`

先 `ls migrations`——下一个空号就是你要用的号。`deliveries` 上加两个可空的列（`trace_id`、
`tracestate`），再加一个 `check`，要求 trace id 是 32 个小写十六进制字符。可空是一个决定：在这个
服务携带 trace 之前被接受的投递没有 trace，它发出去时不带任何头部，而不是带一个在投递时编出来的头部。这
两列属于*投递*而不是事件，因为它们是在尝试投递的地方被读的。

### `src/trace.rs`

- `TraceId` / `SpanId`——解析（正好 32 / 16 个小写十六进制，从不全零）和生成；
- `Traceparent`——`parse`、`generate`、`child`（同一条 trace、它自己的 span、调用方的采样决定）、
  `Display`，以及各个访问器；
- `Context`——穿过边界的东西：trace、采样决定、厂商状态。它故意*不*带 span id——span 属于某一跳，
  而投递跟请求是不同的跳；
- `Traces`——适配器问"这次投递的 trace 是什么"的那个端口，以及 `DbTraces`，读那些列的实现。

### `src/events.rs`, `src/delivery.rs`

`ingest` 接收请求的上下文，`fan_out` 把它写到它创建的每一行投递上——同一个事务，理由和那些行本身是
一个提交一样：投递的 trace 如果分开写，这条投递就会有时无法追踪。

### `src/outbound.rs`

`HttpSender::with_traces(store)`——一个 builder，跟 `signing` 的一样——以及在 `send` 里，这次尝试
生成的头部：用存下的 trace 配一个**新的** span id 生成 `traceparent`，调用方发过 `tracestate` 时也
带上它。没有存下 trace 的投递发出去不带头部。这是适配器用来查东西的第二个端口，同一个论证覆盖两者：
worker 的请求类型不会为只有适配器写的东西多长一个字段。

### `src/http.rs`

一个层，在请求日志之外：读 `traceparent` 和 `tracestate`，头部是这个服务读得懂的就保留它的 trace，
读不懂就开一条新的——读不懂的时候，**把厂商状态也一起丢掉**，因为 `tracestate` 只有跟它一道来的那条
trace 放在一起才有意义。上下文进请求的 extensions，日志行多一个 `trace_id` 字段，`create_event` 把
上下文交给 `ingest`。

### `src/openapi.rs`

`POST /events` 声明那两个可选头部。`relay/2.3-contract-first` 是一条常设规则：调用方可以发的头部，
是这个服务所承诺的东西的一部分。

## 完成标准

- `kiln run relay/2.19-trace-propagation` — 规格通过
- `kiln check relay/2.19-trace-propagation` — 每个 must 闸门都是绿的
- `cargo test --test spec_tracing`——七个用例：调用方的 trace 穿过队列到达订阅者、没有 trace 的请求
  自己开一条、十个读不懂的头部被忽略、两个端点拿到同一条 trace 的两个 span、厂商状态原样传递、真实
  进程日志行里的 trace id，以及作为矩阵的头部语法
- 用你自己的订阅者（`nc -l 9000` 就行）、服务跑着：
  `curl -X POST localhost:8080/events -H 'Authorization: Bearer <key>' -H 'Idempotency-Key: k' -H 'traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01' -d '{"kind":"a","payload":{}}'`
  而你的订阅者打印出来的那一行，带着同一个 trace id `4bf92f3577b34da6a3ce929d0e0e4736`，配一个它
  自己的 span id
- `psql -c "select trace_id, tracestate from deliveries"` 行上显示这个 id，而那次 POST 的日志行显示
  同一个

## 陷阱

1. **用 task-local 或 thread-local。** 在"发一个请求、看着投递紧接着发生"的那个测试里，它管用——而
   投递不会紧接着发生。worker 是另一轮里的另一个任务，常常是另一个进程。trace 必须被*存下来*。
2. **转发调用方的头部。** 它看着对，却把这个服务变成了转发器：那些字节去了一个可能用不同方式解析它
   们的订阅者那里，而一个 trace id 坏掉的调用方，把自己的坏处复制进了别人的 collector。解析它，留下
   trace id，生成你要发的头部。
3. **复用调用方的 span id。** span 是一跳的，复用父的会让两跳在 trace 里看起来像一跳——一次花了四秒
   的投递看起来像一次花了四秒的请求，而它们之间的队列从瀑布图上消失了。
4. **两次尝试一个 span。** 重试是另一跳：新的 span id 是每次*尝试*一个，不是每次投递一个。否则第二
   次尝试就隐形了，而那恰恰是值得看的那次尝试。
5. **`traceparent` 没保留，`tracestate` 却留了下来。** 厂商状态的作用域是它随来的那条 trace；开着
   一条新 trace 还留着它，就是把别人的行李挂在这个服务的 trace id 下递给下一跳。
6. **拒绝这个请求。** 因为调用方框架弄坏的一个头部回 400，把一个人的遥测 bug 变成了一次故障。忽略这
   个头部，开一条 trace，把事件投出去。
7. **每次尝试都用一个数据库往返去读 trace，还忘了这要花什么。** 这次查询是每次尝试一次，挨着签名
   密钥那次——每次投递两次查询。这是一笔故意的价钱（另一种做法是请求类型上多一个字段，然后每一层都
   背着它），而知道自己正在付这笔钱是有价值的：`deliveries (id)` 上的索引，才让它成为一次探针式
   查找。
8. **大写的十六进制。** 格式是小写，而一个接受 `4BF9…` 的服务，产出的 trace 会跟调用方的同一个
   trace id 对不上——两个对人来说相同、对每个索引来说都不同的 id。
9. **全零的 id。** `0000…` 是格式保留给"没有 trace"的；接受它，意味着每个发它的调用方都一起落进同
   一条 trace，而那条 trace 不属于任何人。
10. **migration 把这一列写成非空。** 这一步之前被接受的每一次投递都没有 trace id，而一个 `not null`
    的列，会让升级变成一次没人写过的数据迁移。

- [W3C: trace context](https://www.w3.org/TR/trace-context/)——`traceparent` 的语法、保留的全零 id、
  版本规则，以及 `tracestate` 是干什么的
- [OpenTelemetry: context propagation](https://opentelemetry.io/docs/concepts/context-propagation/)——
  同一个想法做成库，包括对队列来说"载体"意味着什么：这里那一行就是载体
- [OpenTelemetry: semantic conventions](https://opentelemetry.io/docs/specs/semconv/)——一个叫
  "deliver webhook" 的 span 应该怎么命名，以及它会带哪些属性
- [`sqlx::PgPool`](https://docs.rs/sqlx/0.9.0/sqlx/struct.PgPool.html)——store 持有的句柄，以及为什么
  一个持有连接池的端口克隆起来便宜、用错了代价高
- [Google Dapper](https://research.google/pubs/pub36356/)——整个想法来自哪篇论文，以及为什么 id 是
  在源头采样，而不是每一跳都采
