# 按租户限流，谁也不会饿着谁

## 为什么

收下一个事件是这个服务最便宜的动作，也是最值得灌洪水的动作：一个请求写一行，而每一行随后都欠着该租户
注册的每一个端点。一个生产端里有循环的租户——一次不带退避的重试、一次队列重放、一个每次页面浏览都触发
的 bug——一分钟能发十万个事件，而代价不会停在他自己的账上：

- **worker 是共用的。** 每一个被接受的事件都变成一次要尝试的投递，而队列只有一条：下一个租户的发票，要
  等洪水被处理完才到得了；
- **数据库是共用的。** 每个事件都是事务里的一个行加一次扇出，而连接池是所有人共用的八个连接；
- **而失败的不是洪水。** 闯祸的租户没事——他的请求正被*接受*。没被服务到的是那些投递迟到的租户，而任何
  人问的第一个问题都是"这个服务是不是慢了"，这恰恰是一个限流能变成具体答案的那个问题。

所以入口路径需要一道限制。有意思的部分是*谁的*限制：

- **所有人共用一个桶**，就是同呼吸共命运。有循环的那个租户花掉其他每个租户的配额，而客户问"为什么拒绝
  我"时，服务的回答是"别人在忙"——这话是真的，也无法接受；
- **匿名者没有桶**是个洞。每个不带凭据的请求在被拒绝之前仍然要花一次数据库查询，而那次查询正是攻击者一
  分钟能要十万次的便宜东西；
- **拒绝却不带"什么时候"**，把限制变成一场重试风暴。只被告知"429"的客户端立刻就回来，于是限制本身成了负载。

形状是**每个调用方一个令牌桶**：`burst` 个请求立刻可用，按 `per_second` 补充，桶空了就回 `429` 加一
个 `Retry-After`。调用方由它出示的凭据来标识——凭据做过哈希，于是限流器不用查任何东西就能决定——而每一
个什么都没出示的请求共用一个桶，因为源地址是网络做出的一个主张，不是身份。

**还有一条必须说出口的边界**：这是*准入*控制，对的是调用方。`delivery/retry-budget@design`——第
`relay/2.8-retry-budget` 步——有一个重试预算和一个熔断器，而它们对的是**下游**：预算决定的是，面对一
个正在失败的订阅者，这个服务做什么。两者不是一回事，也不能互相顶替：一个桶从不发送任何东西（它只拒绝），
一个熔断器从不拒绝任何东西（它只是不再尝试）。调用方的配额保护不了订阅者不被慢队列拖住，熔断器也保护
不了这个服务不被一个每秒发一万个事件的调用方压垮。`relay/2.14` 是这个三角形的第三条边——这个进程同一
时刻拿着多少活，不管是谁送来的。

## 任务

脚手架加了 `src/ratelimit.rs`：`Quota`、`Clock`、`Bucket`、`Verdict`、`Limiter` 和 `bucket_of`，函数
体是 `todo!()`。它不引入任何 crate：这里的算术大约三十行，得在一个测试自己拥有的时钟下保持确定性，
而 `governor`（或任何别的限流 crate）只会是一份为了逃避写一次减法而买来的依赖。

### `src/lib.rs` 与 `src/ratelimit.rs`

- `Quota::new(burst, per_second)`——一个配额，任一数字为零则回 `Error::Config`。一个空的桶，或者一个永
  不补充的桶，会永远拒绝每一个请求：那是一次部署用一个笔误把自己的服务弄下线，所以在读它的地方就拒绝。
- `Bucket` 和它的两个操作：`refill` 加上 `elapsed × per_second`，封顶在 `burst`（闲置一小时是一个
  burst，不是一小时的请求量）；`is_full` 是没人花过的桶所处的状态。
- `Limiter::check(caller) -> Verdict`——先补调用方的桶，然后花掉一个请求，或者回
  `Verdict::Refused { retry_after }`，值是 `(1 - left) / per_second`。一把锁盖住读、补和减：分成两步就
  会放进来比桶里装得下的更多请求。
- `Limiter::known()`——持有多少个桶。这张 map 是有界的：一旦它大过 `SWEEP_AT`，那些*又满了*的桶会被丢掉，
  因为一个满的桶和一个没有的桶表现完全一样。没有这一条，限流器就会跟着攻击者编出来的凭据数量一起长。
- `Clock`——那个端口（`now() -> Duration`，单调，只有差值有意义），部署用的 `System` 建在 `Instant` 上。
- `bucket_of(Option<&str>) -> String`——桶：凭据，**做过哈希**（一把在 map 里活过一次运行的密钥，就是一
  把躺在 core dump 里的密钥），没有凭据时是 `ANONYMOUS`。

### `src/config.rs`

加一个 `rate_limit` 段，类型是 `ratelimit::Quota`（限流器自己的类型，于是零根本不可能存在，也就无从
被误读——`Quota::new` 是唯一的构造函数），来源是 `rate_limit.burst` / `rate_limit.per_second` 或
`RELAY__RATE_LIMIT__BURST` / `RELAY__RATE_LIMIT__PER_SECOND`，默认 `32` 和 `16`。不是整数的值是一次
配置错误。两行都在 `--check-config` 里报告。

### `src/error.rs` 与 `src/http.rs`

- `Error::RateLimited { retry_after }`——状态码 **429**，kind `"rate_limited"`，`retryable: true`。
  `Error` 的 `IntoResponse` 还在错误带着等待时间时写上 `Retry-After`（整秒，绝不为零），于是这个头部跟
  着拒绝一起走，不管拒绝是在哪儿产生的。
- `AppState` 为整个进程持有一个 `Limiter`，由配置建在 `System` 之上。
- 一层 `limit_calls`，挂在租户路由上：先 `bucket_of(bearer_token(headers).as_deref())`，再 `check`。
  **它挂在认证*外面*。**最后应用的 `.layer()` 是最外层——于是超配额的请求，在被那次会识别出它的查询之前
  就被拒绝，而匿名的洪水根本不碰数据库就被拒绝。

### `src/openapi.rs`

租户的每一条路由现在都可能回 `429`，所以每一条都要把它写进描述（`relay/2.3` 的规则：调用方拿得到的状
态码，必须在契约里）。这个头部要写进描述里。

## 完成标准

- `kiln run relay/2.13-rate-limit` — 规格通过
- `kiln check relay/2.13-rate-limit` — 每个 must 闸门都是绿的
- `RELAY__RATE_LIMIT__BURST=3 RELAY__RATE_LIMIT__PER_SECOND=1 … cargo run`，然后拿一把键发四个事件，回
  `201, 201, 201, 429`，第四个带着 `Retry-After: 1`
- `cargo test --test spec_ratelimit`——七个用例：对着一个测试拨动的时钟验补充算术、每个调用方一个桶、八
  个线程打一个桶、清扫、配置，以及两个真正走网络的用例
- `RELAY__DATABASE__URL=… cargo run -- --check-config | grep rate_limit`——两个数字

## 陷阱

1. **整个服务一个桶。** 算术是对的，策略是错的：一个租户的循环拒绝了所有人，而那个本来能显示出来的指标
   （"refused, per tenant"）根本不存在。规格的第一个测试就是这个：acme 超配额被拒，而 globex 的下一个请
   求是 `201`。
2. **靠查密钥来决定桶。** 那么一个请求是先被认证、再被限流，而带着编出来的密钥的请求涌进来，在被拒绝之
   前每一个都要花一次数据库往返——你想卸掉的那份负载，正是你在付钱的那份。改成把凭据做哈希，那就完全不需
   要查询。
3. **在锁外面计数。** `if bucket.left >= 1.0 { … }`，减在别处；或者 `Mutex` 在读和写之间被放掉，都会放
   进来比桶里装得下的更多请求：八个线程可以每个都读到"还剩一个"。规格拿一个冻结的时钟跑的正是这个。
4. **补充超过 burst。** 加 elapsed × rate 而不封顶，等于给一个闲置了一小时的调用方一个装着三千个请求的
   桶——他等来的那个 burst，在一个瞬间里全部到手，而这跟桶的用处正好相反。
5. **把小数部分的令牌抹掉。** 每次检查都 `left.floor()`，意味着半秒的补充什么也没挣到，还被*忘掉*了：有
   效速率变成每请求 `1 / ceil(1/rate)` 秒，比设置项慢，而且取决于调用方问得多勤。
6. **靠定时器驱动补充。** 每个调用方一个任务，或者一个全局 ticker，都是会泄漏、会漂移、还要关掉的东西，
   而且它让限流器的行为取决于运行时的调度，而不是流逝的时间。在读取时补充：`bucket.refill(now)`，别的什
   么都不做。
7. **只增不减的桶 map。** 键是调用方出示的任何凭据，而攻击者每个请求编一个：一张没有淘汰的 map，就是一
   次按攻击者的时间表发生的内存泄漏。满的桶，就是没人正在花的那些。
8. **`Retry-After: 0`。** 把等待截断成整秒，一秒以下的都变成 `0`，等于告诉客户端立刻重试——正是这个头部
   存在要防的那场风暴。绝不少于一秒，而且永远是整数，因为头部的意思就是这个。
9. **用一个没人能据以行动的 body 拒绝。** 一个空 body 的光秃秃 `429`，让客户端无从解析，让运维无从 grep。
   body 和其他每一种拒绝是同一个 `Error` 形状，带着 `error: "rate_limited"` 和 `retryable: true`。
10. **把限流器放到认证里面，还说是一回事。** 于是匿名的洪水在查过一次之后才拿到 401，而"便宜的拒绝"并不
    便宜。层落在哪儿*就是*行为本身：在认证外面，挂在租户路由上，带着共享的匿名桶。

## 延伸阅读

- [RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) ——`429 Too Many Requests`，以及
  它本该带的 `Retry-After`
- [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3) ——`Retry-After`：秒数
  或者一个 HTTP 日期，以及客户端被允许假定什么
- [Stripe: rate limits](https://stripe.com/docs/rate-limits) ——一个公开 API 对"哪个桶，桶空了怎么办"的
  回答，包括按账户加按端点的划分
- [`governor`](https://docs.rs/governor/) ——这一步有意不用的那个 crate：先读接口，再拿它和 `SWEEP_AT`、
  和测试拨动的 `Clock` 比一比
- [Cloudflare: how we built rate limiting](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/)
  ——为什么令牌桶和滑动窗口对不上，以及计数应该挪到哪儿去
- [Rust: `Instant`](https://doc.rust-lang.org/std/time/struct.Instant.html) ——定义上就是单调的，这正是
  它适合给桶当时钟、不适合给时间戳当时钟的原因
