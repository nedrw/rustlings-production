# 注入你害怕的故障：延迟、重置、半开

## 为什么

到目前为止的每一步，都加了一个关于失败的承诺：带预算的重试、用死信代替死循环、把死掉的 worker 找回来
的租约。这些承诺都被*测过*，而且测的时候，失败是某人写进测试里的——一个返回 `Retryable` 的假实现、
一次手工停在那里的投递、一行用 `UPDATE` 做旧的数据。这些都没有碰过生产里真正发生的事：一个开着却
一声不吭的 socket、一条在请求和答案之间断掉的连接、一个周二 200 毫秒、周五 40 秒才回的订阅者。

你没有注入过的失败，就是你正在猜的失败，而猜的内容几乎总是"客户端会告诉我"。它不会。一次返回
`Ok(0)` 的读，意思是"关了"，不是"慢"，而一个收下请求就没声了的订阅者，看起来跟一个正在思考的订阅者
一模一样。一次三十秒才回来的投递，和一次永远不回来的投递，区别在于某个人选的截止时间；而想知道自己
面对的是哪一种，唯一的办法就是让一个订阅者安静下来，看会发生什么。

## 回顾

`test/fake-external@apply`——`mailer/1.13-email-port`——以及 `relay/2.6-at-least-once` 的
`tests/support/sender.rs`：一个带记录实现的端口，是这个项目测试"外部的东西失败了"的方式。那是*奉命行事*
的假实现：它回 `Retryable`，因为测试这么说了。它半开不了，没有 socket，也没有能撞上的截止时间——失败
就是假实现被告知的那个，而那恰好是你早就想到的那个失败。

## 变化

这里，失败发生在 socket 上，落到真正的客户端身上。`HttpSender`——`relay/2.7-outbound-client` 那个
带三个截止时间的适配器——指向一个测试自己的代理，代理接收指令，而截止时间、`relay/2.8-retry-budget`
的重试预算和队列状态，都透过一个*被制造出来*的失败来评判，而不是一个在返回值里模拟出来的失败。制造
失败的是 `tests/support/faults.rs` 里一百来行 `std` 代码：一个监听器、每条连接一个线程，外加一种故障。

这一步也从 `docs/curriculum.md` 第 7 节那份工具清单里偏了出来，那份清单正是为这件事点名了 `toxiproxy`。
理由就在夹具自己的模块文档里，值得你在动手写一行之前读一读：一个得先拉下来的镜像，是一个在没有
registry 的机器上会失败的规格；而一个从随机数生成器里抽出来的故障*率*，是一个二十次里失败一次的
测试——这种测试，人们会学会重跑它，而不是读它。失败的类别是一样的，而且都在这里——慢、重置、半开、
丢弃——而被评判的是服务的行为，不是注入的机制。

## 任务

写 `tests/support/faults.rs`。脚手架给了你规格会用的接口（一个用来选故障的 `Fault`，一个有自己的
端口、还带着测试要读的计数器的 `Proxy`），别的什么都没有：实现才是这一步的内容。

### 四种故障

| 故障 | 客户端观察到什么 | 它代表的生产故障 |
| --- | --- | --- |
| `Fault::Delay(d)` | 答案在 `d` 之后到达 | 一个慢的订阅者，或者一条慢的路径 |
| `Fault::Reset` | 连接立刻结束，带 `RST` | 崩掉的进程、防火墙、没有后端的负载均衡器 |
| `Fault::HalfOpen` | 请求送达了，而答案永远不来 | 一台机器活着却不作答——只有截止时间才抓得到的失败 |
| `Fault::Loss { every }` | 每第 `every` 个请求永远到不了目标 | 在两次尝试之间消失的连接 |

下面是决定，不是细节：

- **重置必须是真重置。** 有序关闭是一个 `FIN`，而 `FIN` 是答完了的订阅者发的东西。`RST` 是执行到
  一半死掉的进程发的东西。在裸 socket 上，有一种可移植的办法造出它：
  **在接收缓冲区里还有未读字节的时候关掉 socket**——一次一个字节地把头部读完，把 body 原样留下；
- **半开意味着送达了，然后没声了。** 把请求转发给目标，然后永远不把答案传回来：订阅者已经拿到了，这跟一条
  从未到达的连接是两种失败，而唯一能终结它的，是客户端自己的读截止时间；
- **丢弃是周期，不是概率。** `every = 2` 每第二个请求丢一个，所以同一次运行丢的是同样那几个，测试
  可以断言丢了多少个，而不是指望；
- **周期数的是请求，不是连接。** 这个服务把发往同一个目标的尝试复用一条连接
  （`relay/2.7-outbound-client`）：一条只是偶尔被丢的连接会把复用一起带走，于是故障触发一次，就躲到
  一条活着的 socket 后面去了；
- **生效中的故障是在连接被接受时读的**，不是逐字节：一个在尝试进行中把代理治好的测试，测的是那次
  尝试，在它底下换故障，会让结果取决于调度器；
- **计数器是接口的一部分**，不是装饰。一个什么都没注入的代理，会让规格里的每一条断言都空洞地成立。
  `forwarded()`、`dropped()` 和 `connections()` 就是每个测试说"故障发生在服务真正走的那条路径上"的
  方式。

### 你已经熟悉的夹具规则

把连接线程 detach 掉（一个甩手不管连接的测试，也必须还能跑完），给夹具拥有的每个 socket 设一个读
截止时间（永远阻塞的夹具，会把一次失败变成一次挂起），绑端口 `0`（内核挑，夹具公布），永远不要用
sleep 来同步——规格会轮询 `psql`，等它想要的状态。

### 不碰生产代码

这一步不改 `src/` 下的任何东西。它需要的一切——截止时间、预算、租约、死信表——都是前面几步建好的，
而这正是要点：缺的不是代码，是*证据*。

## 完成标准

- `kiln run relay/2.17-chaos-injection` — 规格通过
- `kiln check relay/2.17-chaos-injection` — 每个 must 闸门都是绿的
- `cargo test --test spec_chaos`——七个用例：
  1. 一次尝试熬过去的延迟被吸收——一次尝试、一次投递、不重试
  2. 一次熬不过去的延迟花掉一次尝试，把截止时间的那句话写在行上，而这次投递又欠着了
  3. 被重置的连接就是一次延迟：每个投递都回来，故障一停服务就自愈，没有一行留在 `claimed`
  4. 半开的连接被读截止时间切断——订阅者拿到了请求，行上说截止时间之前什么都没到，
     而这一轮*结束了*
  5. 丢弃可复现：`every = 2` 下四次尝试，正好丢两次，另外两次送达
  6. 矩阵里的每一类故障最后都以所有投递送达、没有一次隐形收场
  7. 一个永不停止的故障，让这次投递带着写下的原因终结在死信队列里，而不是永远重试下去
- `cargo test --test spec_chaos a_dropped_connection -- --exact` 连续跑两次，第二次报的数字和第一次
  一样：注入是可复现的

## 陷阱

1. **一次把 body 也带走的 `read`。** 代理读一块请求，想找到头部的结尾，而它读进来的缓冲区里还有
   body 的头几个字节。把它们丢掉，代理就会去等一个早就到了的 body——而症状不是代理挂住，是*服务*对着
   一个毫秒级就回的订阅者，把每次投递都重试一遍。读一次，把手里的留着，缺的再补。
2. **从生成器里抽丢弃率。** `if rng.next() < 0.3` 是一个二十次里失败一次的测试，而任何人拿到它的
   第一件事就是再跑一遍。周期找 bug 一样管用，而且可以断言：*同样的故障，同样的计数器，每一次*。
3. **用 `Sender` 假实现来测 socket 的失败。** `tests/support/sender.rs` 是回答"worker 拿到一个
   `Retryable` 会怎么样"的正确工具，也是回答"客户端面对一条安静下来的 socket 会怎么样"的错误工具：
   假实现没有 socket，于是没有截止时间、没有半开、没有连接复用，也没有任何东西可注入。
4. **夹具里的 socket 没有读截止时间。** 代理在一个等着代理的对端上永远阻塞，而测试不是失败——是挂
   住，CI 一小时后把它杀掉，日志里什么都没有。夹具里的每一次读都要有截止时间；*测试的*截止时间，
   仍然是服务自己的事。
5. **用 sleep 来同步。** 注入之后 `sleep(200ms)`，"给失败一点时间"，是在跟机器的速度赛跑：这里快，
   那里抖。规格会轮询数据库，等一个它能叫出名字的状态，而每一次等待都有截止时间和一条消息。
6. **只断言结束状态。** "最后全部是 `sent`"这句话，对一个什么都转发了、什么都没注入的代理同样
   成立——整个文件通过，而什么都没测。计数器才是"服务挺过了一次故障"和"压根没有故障"之间的区别。
7. **让熔断器把故障藏起来。** `relay/2.8-retry-budget` 在几次失败之后把一个端点切断，并*卸掉*随后
   的尝试，而被卸掉的尝试永远到不了代理。规格故意把熔断器关掉，因为一条关于尝试次数的计数器断言，
   必须真的是关于尝试次数的断言。
8. **以为每次尝试一条连接。** 假设客户端每次投递都开一条连接，那么连接级的故障每次尝试都会触发。事实
   不是这样：连接是复用的，于是只对*新*连接生效的故障触发一次，之后全都成功——而测试通过的理由是
   错的。
9. **治好故障就立刻断言。** 故障碰过的行还在队列里："治好了"不等于"排干了"。等
   `pending + retrying = 0`，让失败消息把各个状态显示出来，而不是 sleep 一下。
10. **忘了 `RELAY__DELIVERY__ALLOW_PRIVATE_TARGETS`。** 订阅者在 `127.0.0.1` 上，而从
    `relay/2.12-ssrf-defense` 起，除非部署方说有，服务拒绝向自己的网络投递：不设这个设置项，注册
    端点就是 `422`，文件里的每个测试都会以一条关于目标的报错失败，而不是关于混沌的报错。

## 延伸阅读

- [toxiproxy](https://github.com/Shopify/toxiproxy)——这一步取代的工具：读一读它的 toxic 清单，
  因为那份清单就是值得注入的故障分类学，再拿它跟这个夹具的四种比一比
- [`std::net::TcpStream::set_read_timeout`](https://doc.rust-lang.org/std/net/struct.TcpStream.html#method.set_read_timeout)
  ——夹具里每个 socket 都需要的那个截止时间，以及它产生的 `WouldBlock`
- [RFC 9293: TCP](https://www.rfc-editor.org/rfc/rfc9293) §3.5——`RST` 是什么，内核什么时候发它而不是
  `FIN`（还有未读数据、socket 已关闭），以及一条对端已死的连接，为什么跟一条从未打开过的连接不是同
  一种失败
- [Principles of Chaos Engineering](https://principlesofchaos.org/)——稳态、假设，以及尽可能小的爆炸
  半径：这个文件把这条纪律用在了一个测试的尺度上
- [PostgreSQL: `FOR UPDATE SKIP LOCKED`](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)
  ——正是这个认领，让"什么都没丢"成为关于队列的陈述，而不是关于某个走运的进程
