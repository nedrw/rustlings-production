# 带着在途租约停机：恢复，且不留下卡住的行

## 回顾

`async/graceful-shutdown@apply`——`mailer/1.14-worker`：一个被要求停下的进程停止*接收*工作，把已经收
下的工作做完，并在一个截止时间之内退出，因为那个客气地提出要求的人，手里还为不肯停的进程攥着一个
`SIGKILL`。在那里，工作是一条内存队列里的消息，而截止时间决定它会不会丢。

## 变化

顺序是一样的，而搞错的代价换了形状。这个服务不把工作拿在内存里：一次在途的投递是 `claimed` 里的一行，
带着持有它的 worker 的 id，以及一个时刻——过了这个时刻，这行就被视为已遗弃。这改变了三件事，而每一
件都是这一步必须做出的决定：

- **丢掉一个任务不再丢掉那次投递。** 一次被取消的尝试，留下的是被一个已经不存在的进程认领着的一行，所
  以投递没有丢——它变成**在租约的长度之内不可见**。于是你选的截止时间不是"排干可以花多久"，而是"我愿意
  让这次投递、以及这个 worker 拿过的其他每一行，多久没人接手"，而决定谁赢的那只钟不是你的。在租约之
  内回来的 worker，是一次重复；在租约之后回来的，是给一个从没被告知第一次的订阅者的第二次投递；
- **`kill -9` 根本没法处理，而这里就是"这不再是脚注"的地方。** 它没有处理函数、没有日志行，也没有把任
  何东西还回去的机会。唯一能把那些行恢复过来的，是写在它们上面的那个时刻，所以总得有人去*读*它：一个从
  不看过期租约的 worker，就是一个让它们永远不可见的 worker。那就是 `reclaim_expired`，它让一次崩溃变成
  一次延迟，而不是一次丢失；
- **一次干净的停机不必等那个时刻。** 一个正在停的 worker 知道自己正在停，也知道自己拿着哪些行——于是它
  现在就把它们还回去，一次发布花的是秒，不是一个租约。一次看起来像故障的部署，和一次没人注意到的部署，
  差别就是这一条语句。

值得说出口的后果：**是两个数字，不是一个。** `delivery.drain_seconds` 决定这个进程停机时放弃多少工作，
`delivery.lease_seconds` 决定队列把一个没有主动停机的进程造成的损害藏多久。一个比部署愿意等的最慢尝
试还短的租约（`Policy::deadline`，`relay/2.7`），就是一个在持有它的 worker 身下过期的租约，同一次投
递随后被两个 worker 同时尝试——那道界管的是*认领*，而行里没有任何东西说"这次尝试还活着"。

## 任务

脚手架加了 `src/lease.rs`：三个函数体为 `todo!()` 的签名。这一步其他的东西都在你已经拥有的文件里，而"
什么该放在哪儿"这件事本身就是这一步：队列的行归 `src/claim.rs`（`relay/2.5`），跑起来的 worker 归
`src/concurrency.rs`（`relay/2.14`），而*停机*是什么意思，归新模块。

### `migrations/0007_lease_reclaim.sql`

恢复过期租约，是对既处于 `claimed` *又*过期的那批行的一次 `update`，每个 worker 每一轮跑一次。按完全
相同的形状加一个部分索引——`on deliveries (lease_expires_at) where state = 'claimed'`——因为没有它，这
条语句会走遍这个服务曾经欠过的每一次投递，而从一次崩溃里恢复的代价，会随着租户的历史一起长。下一个空
闲的迁移编号是 `0007`（`ls migrations`）。

### `src/lease.rs`

- `reclaim_expired(pool)`——每一行租约已经到期的记录都回到 `pending`，此刻到期，没有持有者、没有租约，
  **并且它的尝试被计入**。没有人观察到那次尝试发生了什么：订阅者可能被告知了，也可能没有。不计入它，就
  是一个 worker 反复死掉的投递被永远重试的方式，因为失败计数是唯一能结束一次投递的东西——而那些该去的地
  方是 `relay/2.10-dlq`，也就是说，它们得被计入才能到那儿。
- `release_held(pool, worker)`——这个 worker 还拿着的每一行都回到 `pending`，保留它的失败计数和它的时刻
  （它没有任何地方失败）。过滤条件是 `locked_by = $1`，而这个条件就是全部的安全属性：一个能放掉任何人
  租约的 worker，能顺手把另一个 worker 的在途尝试交给第三个。
- `serve(worker, drain, shutdown)`——顺序如下：
  1. **信号结束认领。** 正在跑的那一轮并不是*被*信号取消的——循环在信号*和*这一轮上 select，信号赢了就丢掉
     这一轮的 future（它的任务会继续跑；见陷阱 1）——而且不再有新一轮开始；
  2. **在途的尝试得到 `drain` 这段时间。** `worker.gate().quiesce(drain)` 等座位回来，那恰好就是"还有没有
     东西在途"，而在截止时间之内作答的尝试，它的投递被记成已投递——这正是这段顺序唯一的用途；
  3. **剩下的全部还回去**：`release_held`，于是一次停机花的是秒，不是一个租约；
  4. **空队列不会被立刻再问一遍**：什么都没认领到的一轮之后，跟一段短短的等待，否则一个没活干的 worker 会
     把一个核花在发问上。
  轮与轮之间是 `reclaim_expired`——一条在没有东西可回收时什么都不写的语句——于是一个在崩溃之后启动的
  worker，会把崩溃那个留下的捡起来。

### `src/concurrency.rs`

worker 的两个新部件：一个 `lease` 字段（默认 `claim::LEASE`，用 `Worker::leasing` 改它——认领时长原来
是 `relay/2.5` 的一个常量，现在变成这个部署的决定），以及 `Worker::pool()`，因为这个 worker 还回去的
租约是*它自己的*数据库里的行。`Report` 的两个构造函数改成 `pub(crate)`，好让 `serve` 数它跑了多少轮。

### `src/config.rs`、`src/main.rs`

- `delivery.lease_seconds`（默认 60）和 `delivery.drain_seconds`（默认 10），为零都拒绝，两个都由
  `--check-config` 报告。
- `main.rs` 在 HTTP 状态用的同一个 pool 上跑**一个 worker**，`HttpSender::signing` 建在
  `Policy::of(&config)` 和 `DbSecrets` 上，名字取自 run id（名字就是认领时被盖上去的那个东西，两个进程
  共用一个名字，就会互相放掉对方的行）。信号停掉两半，而**两半都要 await**：单用 `select!` 会在先完成
  的那一半一结束时就返回，丢掉另一半的 future，一次在途投递就是这样一声不响地从日志里消失的——
  `mailer/1.14-worker` 点名的那个陷阱。

## 完成标准

- `kiln run relay/2.15-shutdown-leases` — 规格通过
- `kiln check relay/2.15-shutdown-leases` — 每个 must 闸门都是绿的
- `cargo test --test spec_leases`——八个用例：一个过期的租约、一个活的租约、一个 worker 自己的行、排干
  超时、排干完成、`kill -9` 与恢复、一次干净停机，以及配置
- `RELAY__DELIVERY__LEASE_SECONDS=600 … cargo run`，然后 `kill -TERM <pid>`：进程在
  `delivery.drain_seconds` 之内退出，而 `psql -c "select state, locked_by from deliveries"` 显示它当时
  正在处理的那一行回到了 `pending`——立刻，而租约上还剩十分钟，没人等过它
- 换成 `kill -9 <pid>`，然后重新启动服务：那一行在租约到期之后被恢复，而订阅者被问了两次

## 陷阱

1. **在信号上 `select!`，把另一个分支丢掉。** 信号到达时正在跑的那一轮已经 spawn 了任务；丢掉它的
   future 会把这些任务*脱挂*（一个被丢掉的 `JoinHandle` 不取消任何东西），于是它们继续跑，而停机路径却
   认定那些行空出来了——那一行被一个 worker 已经不再记账的任务投递出去。那次尝试必须被*等到*（`quiesce`），
   或者它的行被还回去，两者之间的差别就是排干截止时间。`main.rs` 里同样的错误，会在排干还跑着的时候结束
   进程，于是 `release_held` 永远不会发生，租约成了唯一的恢复手段。
2. **一个从不读过期租约的 worker。** 于是 `kill -9` 留下一行永久卡死的记录：没有东西把它记下来，也没有
   别的 worker 会看它一眼——队列干脆不再把那次投递算进来，而订阅者永远不会知道。轮与轮之间的
   `reclaim_expired` 只有两行，而它就是整个崩溃故事。
3. **等租约，而不是还回去。** 一个排干之后不带 `release_held` 就退出的 `serve` 是对的，*而且*慢：每一次
   发布都让在途的投递整整一个租约不可见。"工作最后总会回来"和"我一停，工作就回来"不是同一个承诺。
4. **放掉自己没拿着的行。** 不带 `locked_by = $1` 条件的 `release_held`，把*每一行* claimed 的记录都放回
   队列——包括另一个 worker 的在途尝试，它们随后被别人认领、第二次尝试。两次尝试，一次投递，还怪不到任何
   人头上。
5. **忘了排干截断的是尝试，不是投递。** 一次尝试被截止时间截断的行，保留它的失败计数，因为它没有任何地
   方失败——而那次投递会被再尝试一次，可能投出一个重复。把它算成一次失败，会让一次发布看着像订阅者的问题；
   不算它则没问题，*因为*接收方按投递 id 去重（`relay/2.11-hmac-signing` 签的是那个 id，
   `relay/2.6-at-least-once` 承诺的是那个 id）。
6. **租约比尝试的截止时间还短。** `lease_seconds = 1` 配 `Policy::deadline = 30s`，意味着 worker 自己的
   行在它还在等答复的时候就过期了：队列把同一次投递交给另一个 worker，于是现在两个 worker 在跟一个订阅
   者说话。租约必须比一次部署愿意等的最慢尝试更长，而这两个数字住在配置的不同段里，它们恰恰就是这样被各
   自设出来的。
7. **两个进程共用一个 worker 名字。** 整个机队都是 `locked_by = 'relay'`，意味着一个正在停机的 worker
   会放掉另一个活着的 worker 此刻正在尝试的行。名字来自 run id，理由和陷阱 4 里的那个条件一样。
8. **排干的时候还在认领。** 一个等排干时继续转轮次的 `serve`，是一个揽下自己做不完的工作的 worker——和
   `mailer/1.14-worker` 用一个有界队列许下的承诺正好相反。信号结束的是*循环*，不只是这一轮。
9. **一个空转的闲 worker。** 一个 `claim → nothing → claim` 的循环，是一个把核（还有一次数据库往返）花
   在证明队列是空的上的进程，每个 worker 一份，每个副本都有。空轮之后的那段等待，是让一个空闲服务便宜的
   东西，而它必须能被信号打断——否则 `SIGTERM` 要等完这个空闲间隔。
10. **信报告，不信行。** 信号到达时正在跑的那一轮被丢掉了，于是它的计数永远到不了 `serve` 返回的那个
    `Report`：它做完的投递在数据库里，那才是它们重要的地方。运维在停机那行日志里读到 "0 sent"、在表里读
    到 "3 sent" 时，读的是一份关于*轮次*的报告，不是关于工作的报告。
