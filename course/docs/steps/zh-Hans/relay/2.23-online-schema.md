# 两个版本都在跑的时候改 schema

## 为什么

上一步立下了那个窗口：一次发布期间，这个服务的两个版本跑在同一个数据库上，而*旧*的那个并不知道新的那个
接下来要干什么。凡是让 schema 变更安全的做法，都是从认真对待这句话推出来的。

天真的部署，是一个把什么都塞进去的迁移：

```sql
-- the change somebody wants
alter table events add column payload_bytes integer not null;   -- ✗
update events set payload_bytes = octet_length(payload::text);  -- ✗
```

两行代码，每一行都是一次故障。没有默认值的 `not null` 列，意味着旧版本做的每一个 `insert` 都会失败——
而旧版本*此刻就在跑*，正在对外服务，所以这个失败不是假设：它是一次部署的第三行上、整个实例的失败，而
当时所有测试都是绿的。`update` 触碰表里的每一行：它在整场更新期间一直握着写锁，而这还是一张旧版本正在
写的表，于是它的投递 worker 卡住，认领就搁在那儿不动，队列在一场看起来瞬间完成的部署背后越积越长。

出路不是写一个更好的迁移，而是**三次部署**，而每一次的形状，由*上一个*版本知道什么来决定：

1. **扩展（expand）**——一个迁移加上这一列，可空、无默认值。它不重写任何东西，而只点名旧列的 `insert`
   照旧能用，因为新列可以缺着。旧版本看不出任何事情发生过，这正是要点；
2. **回填（backfill）**——在列出现之前就有的那些行，*分批*填上，由某个步骤来跑，两个版本同时服务。
   分批，是因为每一批只握锁几毫秒；做成一个步骤，是因为它可以被打断、被接着跑、被跑两遍；
3. **收缩（contract）**——一个*更晚*的版本把这一列变成 `not null`，并去掉读路径上的回退处理。更晚，
   是因为它依赖的那件事（"没有一行是空的"）是关于整张表的事实，也因为回滚一个版本容易，回滚一个
   `not null` 不容易。

中间那一段的代价才是有意思的部分，也正是这一步真正在讲的东西：**列还空着的时候，读路径也得答得出来。**
扩展和收缩之间有一段窗口——发布慢的话是几天，如果那个本该收尾的部署被取消，就是永远——在这段窗口里，
读这一列的代码跑在还没有值的行上。所以读路径带着一个回退处理
（`coalesce(payload_bytes, octet_length(payload::text))`），而这个回退处理就是回填所写的*同一个表达式*：
存下来的数字和算出来的数字永远不会打架，因为它们是分处两地的同一个表达式。一条回 `null`、或者报错的
读路径，会让扩展阶段变成一次破坏性变更——而那正是它不该是的东西。

`db/migrations@apply`（`mailer/1.9-postgres`）到哪儿为止、这里从哪儿开始：那一步是"有一个 schema，
进程在服务之前把它应用上去"。这一步讲的是，应用它的那个进程不是唯一在跑的进程时，一次 schema 变更要付
多少代价。`ops/rolling-upgrade@apply`（`relay/2.22`）是那个窗口；`db/unique-as-concurrency@apply`
（`relay/2.2`、`mailer/1.11-signup`）是同一种直觉，往下挪了一张表——该不存在的东西，让数据库去拒绝，
而不是在代码里查一查。`db/schema-online-evolution@aware` 是这里的深度，以及为什么它是 `aware` 而不是
`apply`：读者要做到的事，是*判断*一次变更属于那三个阶段里的哪一个、并就窗口争论，而这件事没有单一的
产物可以拿来打分。

## 任务

脚手架放好了两样东西：`migrations/0011_events_payload_bytes.sql`——扩展阶段，已经写完、带注释——以及
`src/backfill.rs`，中间那个阶段，带着 `todo!()`。

### 先读 `migrations/0011_events_payload_bytes.sql`

阶段一的全部就是它，四条语句：`alter table events add column payload_bytes
integer`（可空、无默认值、不重写表）、一个回填所要读的形状上的部分索引，以及两行注释说明为什么里面没有
`update`。迁移*不*做回填，就是那个决定；一个做了回填的迁移，就会是上面那个天真部署的后半段。

### `src/backfill.rs`——中间那个阶段

- **`bytes(pool, batch)`**——一条语句，最多填 `batch` 条还没有值的行，顺序就是部分索引的顺序，并答复
  它写了多少行。一条语句，意味着一个批次是原子的：它的行要么全填上，要么一行没填。谓词是*值不存在*，
  而不是一个书签，而正是这一个选择让整个阶段可以重跑——已经有值的行绝不会被写第二遍，所以一次跑完的
  回填再跑第二遍什么都不做，而一次被打断的运行，谁都能接着跑完；
- **`run(pool, batch)`**——部署跑的那个循环：一批接一批，直到某一批什么都没填，最后回一个 `Backfilled`，
  说明花了几批、几行。它停在*什么都没填*上，而不是停在"填不满一批"上，因为前者是语句自己给出的答案
  ——没有活剩下了；而且在它跑着的时候有新行写进来，这个答案照样对。

### 写路径和读路径

- **`src/events.rs`**——`ingest` 为它接受的那些行写这一列，而值由数据库从它正在存的文本算出来
  （`octet_length($5::jsonb::text)`）。这是唯一值得停一下的微妙之处：在 Rust 里用这个进程手上那份
  JSON 来算，会是"这有多大"的第二份实现，而它会在键的顺序和空白上和第一份打架；
- **`src/pagination.rs`、`src/http.rs`、`src/openapi.rs`**——一页给每个事件答一个 `bytes` 字段，用
  `coalesce` 那个回退处理来读，并声明成它自己的 schema（`ListedEvent`），而不是复用 `Event`：这一页
  确实答了另一条路由不答的字段，而 `relay/2.3-contract-first` 是一条常设规矩——文档说什么，答案就是
  什么；
- **`src/config.rs`、`src/main.rs`、`src/lib.rs`**——`--backfill`：连接、迁移、跑批次、打印多少行、
  以 `0` 退出。它是*一条命令*，而不是启动时顺手做的事，因为发布的中间阶段是在上一个版本还在服务时跑的、
  可能被打断、也尽可以再跑——一个每次启动都做这件事的进程，会让每次重启都变成往别人的表上写。

- `kiln run relay/2.23-online-schema` — 规格通过（上面五个用例）
- `kiln check relay/2.23-online-schema` — 每个 must 闸门都是绿的
- 对着你自己一个有数据的数据库：`cargo run -p relay -- --backfill` 打印
  `backfilled N row(s) in M batch(es)`，再跑一遍打印 `backfilled 0 row(s) in 0 batch(es)`
- 回填之后 `psql -c "select count(*) from events where payload_bytes is null"` 是 `0`，而
  `psql -c "select count(*) from events where payload_bytes <> octet_length(payload::text)"` 是 `0`

- `psql -c "\d events"` 显示这一列是 `integer`，没有 `not null`，而
  `curl -H 'Authorization: Bearer <key>' localhost:8080/events` 给每个事件答一个 `bytes` 字段

  删掉旧列、加一个默认值、重命名一列

## 陷阱

1. **`add column … not null`。** Postgres 11 及以后可以*带着*默认值加一个 `not null` 列而不重写表，
   可在这里它仍然是错的：**旧版本**的 `insert` 点名的是它知道的那几列，而一个数据库不允许留空的列会
   拒掉那条 insert。失败发生在已经在跑的代码里，在一次部署的第三行上。
2. **在迁移里做回填。** 一条覆盖整张表的 `update`，和 DDL 在同一个事务里，旧版本的 worker 想写的时候
   它正握着写锁。那是一段带着一条 changelog 记录的投递队列暂停；在大表上，这段暂停以分钟计。
3. **不幂等的回填。** `where received_at < now() - interval '1 day'`，或者一张带书签的
   `backfill_state` 表：第一遍没问题，第二遍就得先想清楚，而那意味着它不会被跑第二遍，也就意味着一次
   死在半路的运行，是没人会去收尾的运行。`where payload_bytes is null` 就是全部的修法。
4. **读这一列却不带回退处理。** 扩展和收缩之间的窗口，就是行的值还空着的地方；一条假定有值的读路径，
   会对每一行早于这次变更的行答 `null`（或者一个错误）。让扩展阶段看不见的正是这个回退处理，而它是
   在*收缩*阶段摘掉的，等回填在各处都跑完以后。
5. **存进列里的大小和回退处理算出的大小不一样。** Rust 里的 `payload.to_string()` 对上 Postgres 里的
   `payload::text`：`jsonb` 会规范化键的顺序和空白，`serde_json` 不会，于是某些载荷上两个答案差一个
   字节，而没人说得清哪个是对的。在值被存下的地方算它。
6. **收缩阶段和扩展同一次部署。** 这个很诱人，因为扩展就在手边，回填也只是一条命令的事。它把两次部署
   变成一次，而这一步通篇讲的就是别这么干——它还拿掉了"不回滚 schema 也能回滚代码"的能力。
7. **忘了回填要读的那个索引。** 没有它，每一批都要扫全表去找没有值的行，于是一场大表的回填，在它想
   做成增量的那件事上是平方级的。部分索引，建在它据以选取的谓词上。
8. **假定窗口很短。** 它要等到有人部署收缩才结束，而那可能永远不会来：一次发布可以停一周，一个版本
   可以被回滚，而一个租户的数据可以一直没人回填，只要没人去跑那条命令。读路径要照着窗口写，不是照着
   顺利路径写。
9. **一个能 `ROLLBACK` 回去、"修好"一个坏迁移的迁移。** 向下迁移感觉像安全网，在这里恰恰相反：它要
   回滚到的那个 schema，*新*版本可能已经在往里写了。滚动部署里从一次坏迁移退回来的路是往前走的，
   再发一个只做加法的迁移。
