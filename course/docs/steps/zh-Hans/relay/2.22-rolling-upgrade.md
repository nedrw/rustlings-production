# 发布时不丢一个事件：探针与迁移顺序

## 为什么

到目前为止，每一步的结尾都是这个服务的一个实例在跑。一次部署不是那样。一次部署是*一串实例*：新的起来、
变得能服务，负载均衡器开始往它送流量，旧的被要求停下、把手里的东西做完再退出——而在一段窗口里，两个
实例同时跑在同一个数据库上，schema 也一样。二十一步里没有一步讲这个窗口，而在这个窗口里出的事，不出在
两种方式之外。

**第一个是"就绪"是什么意思。** 一个进程在 `/readyz` 上回 `200`，只因为它的数据库答出了*某个*查询——
这样的进程，编排器就会往它送流量。如果它的 schema 不在数据库里——因为迁移没跑、因为迁到一半、因为这个
实例被指到了错的数据库——那些请求就一个接一个地失败，而这个失败，是编排器打着绿灯造成的一次故障。存活
与就绪是两个不同的问题，而这个区分只有在就绪问的是某件进程*可能搞错*的事时才成立：`/healthz` 说的是
"这个进程在跑"（而且绝不能碰数据库——一个因为数据库打了个嗝就被重启的进程，会丢掉它正握着的尝试，
`relay/2.15-shutdown-leases`），而 `/readyz` 说的是"我这份代码要的 schema 在这儿，所以发给我的流量能正常
工作"。

**第二个是顺序，以及兼容性得朝哪个方向跑。** 新实例应用迁移；它做这件事的时候，*旧*实例还在服务。所以：

- **先迁移，再说自己在哪儿监听**，而且在说自己在哪儿监听之前，先说自己站在哪个 schema 上。日志里的
  那一行就是整份启动契约，正是它让 `readyz` 可信，而不只是往好处想；
- **迁移必须和已经在跑的代码兼容**，而不是和即将跑的代码兼容。旧二进制不知道新列，也不该需要知道；它
  写的是它编译时那份列清单，而那次写在新 schema 下必须合法。一个重命名一列、删掉一列、或者加一个
  没有默认值的 `not null` 列的迁移，就是把双版本窗口变成一次故障的迁移——在窗口里，坏掉的是*旧*代码，
  而且它是在一个看起来好好的数据库上坏掉的；
- **进程不能因为 schema 来自未来就拒绝启动。** 这是这一步里唯一一条反直觉的规矩，也正是它让滚动升级根本
  成为可能：新实例一迁移，schema 里就有了一条旧实例从没听说过的迁移。一个把这件事当错误的二进制，就
  会退出——新的刚一起来，每个旧实例当场死掉，那比滚动升级本来要避免的那次故障还糟。这就是 `Db::migrate`
  设 `ignore_missing` 的原因，也是为什么安全性*不在*那个旗标里：它在迁移都是增量的，而那正是
  `relay/2.23-online-schema` 的全部主题。

三个邻居，和它们各自的地界：`release/container-image@apply`（`mailer/1.21-container`）造的是被部署的
那个东西，也是把探针*接上*的地方（manifest 里的一个 `HEALTHCHECK` 和一个就绪探针），而这一步讲的是
它们必须答出什么。`db/migrations@apply`（`mailer/1.9-postgres`、`relay/2.1-project-skeleton`）立下的
是"连接、迁移，然后才服务"，而这一步是那课漏掉的部分：*服务什么、给谁，以及谁在看*。
`ops/runbook-drill@apply`（`mailer/1.22-runbook`）是发布出岔子时你会去跑的那次演练；下一步让 schema
变更本身变安全，再下一步演练这个服务会退化成的那些模式。

## 任务

脚手架放好了两样东西：`migrations/0010_deliveries_endpoint_idx.sql`——这次发布要发出去的那个变更——
以及 `src/readiness.rs`，带着类型和 `todo!()`。

### `migrations/0010_deliveries_endpoint_idx.sql`——正在被部署的那个变更

读一读它。它虽然已经写完了，却是这一步有意思的那一半，因为从这里往后每个迁移都得是这个形状：

- **第一行是 `-- no-transaction`**，下面才是 `create index concurrently`。`CREATE INDEX CONCURRENTLY`
  不能在事务里跑（规格会让数据库自己证明这一点），而 `sqlx` 除非文件第一行另有说明，否则会把迁移放在
  一个事务里跑。这一对放在一起，才让建索引这件事是*在线*的：普通的 `CREATE INDEX` 会给 `deliveries`
  加一把 `ACCESS EXCLUSIVE` 锁，而每个进程里的每个 worker——包括窗口里还在投递的旧实例——都会停写，
  直到它建完；
- **它只做加法。** 索引不改任何列，也不改任何查询的意思，所以旧二进制对着它照样能跑，而正是这条性质让
  窗口是安全的；
- 它正是 `relay/2.14-backpressure` 里按租户认领所读的那个索引：认领用一个按 `endpoint_id` 的子查询
  找出某个租户可认领的行，而没有这个形状的索引，查询规划器得先趟过别的租户的洪水，才找得到它们。

### `src/readiness.rs`——"就绪"是什么意思

`Schema` 是数据库自己的记录对"这个二进制要的 schema"的回答：`Current`、`Ahead`（一次发布正在
进行，而且**就绪**）、`Behind`（**不**就绪）、`Unreachable`。`probe` 函数归你写：一条查
`_sqlx_migrations` 的语句，同时回答三个问题——数据库在不在、它记着哪个版本、它到底有没有被迁移过——
再加一个 `case`，让"还没有 schema"不像"没有数据库"。这个区分就是要点：两者之中有一个，会把运维送去修
错的那个系统。

`Display` 已经写好了，它就是最后落进一行日志和一段 `503` body 里的那句话，所以两处都会说清应用的是
*哪个*版本、需要的是*哪个*版本。没有那两个数字的"未就绪"，是一条没人能处置的告警。

### `src/db.rs`、`src/http.rs`、`src/logging.rs`、`src/main.rs`

- `Db::migrate` 在 migrator 上设 `ignore_missing`：数据库记着、而这个二进制不认识的迁移，是一次正在
  进行的发布，不是错误。这个方法上的文档注释说清了是什么让这件事安全，因为单靠那个旗标并不安全；
- `/readyz` 每个请求都问一次 `readiness::probe`，答案不是就绪时回 `503`，body 里带着那句 schema 说明。
  它不再只问"数据库答不答"；`Db::ready` 没了，而它问的那个问题，是取代它的那个问题的严格子集；
- `logging::announce_schema` 只有一行，打印在说进程在哪儿监听的那行*之前*。`main.rs` 在把状态建好
  之后、开始服务之前调它；
- `src/lib.rs`：脚手架加的模块得声明出来。

### 规格判什么

| the test | the claim |
| --- | --- |
| `readiness_is_about_the_schema_not_about_the_database_answering` | 一个跑着的进程，依次被挪到迁了一半的 schema、再回到最新、再到一个来自*更新*版本的 schema、最后到一个已经不存在的数据库：`503`、`200`、`200`、`200`（并且第二个进程能对着它起来）、`503`——全程 `/healthz` 都是 `200` |
| `the_schema_is_announced_before_the_port_is` | 点名 schema 版本的那行日志，出现在说进程在哪儿监听的那行之前 |
| `a_process_that_cannot_reach_its_schema_never_says_where_it_listens` | 一个被指到没人用的数据库上的进程以 `1` 退出，点名那个数据库，并且从来不宣告端口 |
| `the_second_instance_is_ready_while_the_first_one_serves` | 同一个数据库上两个实例，都就绪，往任何一个送十二个事件都没有 `5xx`，每个内嵌迁移对应一行迁移记录，第一个实例以 `0` 停下，第二个继续服务 |
| `the_previous_release_still_writes_rows_this_one_delivers` | 一条只点名 `relay/2.5-atomic-claim` 那些列的 `insert` 落得进新 schema，这次发布新加的列在它上面是 `NULL`，而 worker 把它捡起来并尝试投递 |
| `the_migration_that_grew_the_schema_was_applied_online` | 索引有效，而且建在端点上；事务里的 `create index concurrently` 被*这台服务器*拒绝；最新的迁移文件声明自己不走事务，并且并发地建索引 |

一个诚实的限度，规格里也写明了：两个实例都是这个二进制，所以规格没法展示两个*发布版本*对着同一个
schema 说话。它能展示的是滚动升级所依赖的那一半——schema 在一个跑着的进程底下变了，进程照旧服务，而
一行按上一个发布版本的写法写进去的行，照样能落下、照样能被投递。

## 完成标准

- `kiln run relay/2.22-rolling-upgrade` — 规格通过（上面六个用例）
- `kiln check relay/2.22-rolling-upgrade` — 每个 must 闸门都是绿的
- 对着你自己的数据库跑 `cargo run -p relay`，然后在另一个终端里：`curl -i localhost:8080/healthz` 和
  `curl -i localhost:8080/readyz` 都是 `200`，而
  `psql -c "update _sqlx_migrations set success = false where version = (select max(version) from _sqlx_migrations)"`
  会**不重启**就把 `/readyz` 变成 `503`，同时 `/healthz` 仍是 `200`
- `psql -c "select max(version), count(*) from _sqlx_migrations"` 答出这个进程所在的 schema，而对着
  启动日志 `grep 'the schema is in place'` 显示同样的数字
- `psql -c "\d deliveries"` 显示出 `0010` 建的那个索引，而
  `select indisvalid from pg_index where
  indexrelid = 'deliveries_endpoint_claimable_idx'::regclass` 是 `t`

## 陷阱

1. **一个只 ping 数据库的就绪探针。** `select 1` 在一个空数据库上为真，在迁了一半的上也为真，在被
   明年某个发布版本迁过的上也一样。探针必须问 schema，因为 schema 才是这个进程可能*搞错*的东西。
2. **把探针的答案从启动时缓存下来。** 这是最自然的优化，而它会让探针报告一个已经不存在的数据库——
   迁移被回滚了、故障切换到了一个落后的副本、数据库是从备份恢复的。每次探针都问一遍；那只是一条查询。
3. **一个碰到瞬时错误就*失败关闭*、body 里又没有任何数字的探针。** 不写版本的"未就绪"，是一条运维
   无从处置的告警："迁移还没跑"和"数据库没了"之间的区别，恰恰就是 `probe` 里那个 `case`。
4. **去查数据库的 `/healthz`。** 它看起来更周全，其实正相反：数据库打个嗝，每个实例就都被重启，而
   每个实例都会丢掉它正握着的投递（`relay/2.15-shutdown-leases`）。存活回答的是"这个进程在不在跑"，
   别的不答。
5. **迁移之前就宣告端口。** 绑定先发生，是因为内核得先把端口发下来，之后才有东西可记进日志——但*服务*
   必须在迁移之后，而说你在哪儿监听的那行，必须在说你在哪个 schema 上的那行之后。否则一次失败的发布，
   日志和一次成功的发布分不出来。
6. **一个重命名或者删列的迁移。** 它对新代码没问题，却会打断还在服务的*旧*代码：把上一个发布版本的
   `insert` 语句当成契约来读，只往 schema 上加东西。`relay/2.23-online-schema` 就是给这件事出图纸的
   那一步。
7. **不带 `CONCURRENTLY` 的 `CREATE INDEX`。** 它看着无害——不过是个索引——却会在表上取一把
   `ACCESS EXCLUSIVE` 锁：窗口期间，旧实例的 worker 每次写都会被挡住，直到建完；在大表上，这就是那次
   故障。而事务里的 `CONCURRENTLY` 会直接失败，所以 `-- no-transaction` 那条指示不是装饰。
8. **面对来自未来的 schema 拒绝启动。** 这个陷阱看上去像是在坚持正确性：新实例应用了一条旧二进制不
   认识的迁移，于是旧二进制退出——而且在发布开始的那一刻，每个副本一起退出。schema 只可以往上加，
   这就是兼容规则，而 `ignore_missing` 就是信任这条规则的那行代码。
9. **先停旧实例。** "排干，再起新的"是一段一个就绪进程都没有的窗口。不花任何代价的顺序是：起新的、
   等它就绪、再停旧的——规格里那个窗口测试就是这么做的。
10. **以为窗口很短。** 它不是一次部署，是两次：schema 变更和用它的代码分开发布
    （`relay/2.23-online-schema`），所以旧版本可以在整个发布期间都跑在新 schema 上——或者，如果它被
    回滚，就永远跑在新 schema 上。
