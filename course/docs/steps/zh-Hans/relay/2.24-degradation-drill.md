# Runbook v2，和把它变成证据的那些演练

## 回顾

`ops/runbook-drill@apply`——`mailer/1.22-runbook`：一次故障，从头到尾重放一遍。邮件服务器走了，服务照旧
接受注册，重试预算用尽，演练报告有没有东西丢了——一遍服务器回来了，一遍服务器再也没回来。是第二遍让
第一遍成为证据，而那一页（Symptoms、Signals、Steps、Verification、Escalation）是照着演练写的，好让
两者不会各走各的。

## 变化

那次演练是**一个只有一份后台任务的服务里的单次故障**：邮件服务器不在，队列在数据库里，而事故的答案
只有一句话——"队列兜着它，被放弃的是这些"。这个 track 的服务，出问题的方式比能看的地方还多，而要命的
事故，是那个没人诊断出来的：

- **失败是一个模式，不是一个东西。**"数据库不在了"和"那个订阅者不再应答"不是同一次事故，"一个租户在
  往队列里灌水"也不是。每一个都有自己的特征（`relay/2.18-delivery-metrics`）、自己的爆炸半径（一个
  worker 的租约、一个订阅者的投递、一个租户的积压），还有——这才是要点——自己*正确*的答案。响应者
  如果伸手去抓一个配错了模式的答案，事故只会更长：把座位调多能修好一个慢订阅者，却会让一场风暴更糟；
- **演练要覆盖的是*服务*退化的方式**，而不是某一个依赖退化的方式。每次演练提出的主张都一样，而且是
  这个服务自己的主张：每一个被接受的投递，都以 `sent` 或 `dead` 收场，没有东西留在 `pending`、
  `claimed` 或 `retrying` 里。三个场景，一个承诺，而每次演练都是一条有人会敲两遍的命令；
- **交付物是一个矩阵。** `mailer/1.22` 只有一次重放和一页纸。这里是
  `Scenario::{DatabaseAway, SlowSubscriber, TenantStorm} × Recovery::{ComesBack, Never}`——六个
  世界，其中三个是承诺、三个是证伪——再加上一页纸，为那三个各点名一条命令，因为一本 runbook，如果它
  的演练没法按事故分别执行，那就是事故里没人会翻开的那本。

夹在邻居之间，它站的位置是：`ops/rolling-upgrade@apply`（`relay/2.22`）是*安全地改动*那个服务的演练，
而 `db/schema-online-evolution@aware`（`relay/2.23`）是它的 schema 那一半；这一步讲的是什么都没在
部署、却仍然有地方不对的时候。而 `delivery/dlq@apply`（`relay/2.10`）不是退化：DLQ 里的投递是*故意*
被放弃的，`Report::nothing_was_lost` 把它算作一个结局，而不是一次损失——这些演练讲的是还欠着的那些
投递，而那是一个没人注意到的状态。

## 任务

脚手架放好了两个文件，每个都带着一个另一个填不上的洞：`tests/support/drill.rs` 摆出三次演练，报告
一个它*决定*的 `Report`，而不是它量出来的；`docs/runbook.md` 有事故需要的那些小节，以及占位的目标。

### `tests/support/drill.rs`——演练

`Scenario` 挑故障，`Recovery` 挑坏掉的东西回不回来，而 `run` / `run_with` 已经接好了：它们起一个夹具
（一个数据库、一个它自己的服务、两个租户），接受事件，然后从服务的记录里读出报告。错的是中间那一段
——三个场景函数归你写。每一个都有同样的四件事要做：

1. **让故障成真。** `DatabaseAway`：worker 自己的连接池认领每一次投递，然后在它底下被*关掉*——那些行
   身上盖着一个永远不会应答的持有者的章。`SlowSubscriber`：夹具的订阅者接过每次尝试，然后把它搁在
   那儿不动（`tests/support/load.rs`），于是一整套尝试都在路上、没有一个被应答——注意一个订阅者就是
   一条*车道*（`relay/2.9-ordering`），所以想要四个尝试同时在路上的演练，得注册四个端点。
   `TenantStorm`：一个租户的洪水排进了队列，另一个租户那一个事件就排在它后面；
2. **等故障变得可观察**，而不是等多少秒。演练先断言*服务的*行说出了故障做了什么——全都认领了、每条
   车道都占满了——然后才对恢复做任何决定。抢在故障发生之前到来的恢复，对两个世界都证明不了什么；
3. **服从 `Recovery`。** `ComesBack` 让坏掉的东西重新工作，演练就等队列动起来（一个新的 worker 回收
   死掉的那个持有的东西；停住的尝试被放行；风暴结束，座位把它排干）。`Never` 让它继续坏着，演练就
   报告*还欠着*什么——对风暴来说，这意味着洪水到达得比座位排干得更快，演练在有限圈数之后停下，而不是
   假装自己赢得了；
4. **从行里读数字**——`sent`、`dead`，以及三个意思是"还欠着"的状态。`Report::nothing_was_lost` 就是
   最后那个计数为零，而它就是整个承诺：被放弃的投递是一个结局（它在 DLQ 里，记进 `dead` 那个计数），
   而一切都恢复之后还留在 `claimed` 的投递，是一个再也不会有人尝试的投递。

有一件事值得有意为之：夹具里的两个 `Panics` 是特性。`Counted` 会让一次等了半天、尝试却从没开始的演练
失败，而演练自己的 `assert_eq!` 在故障并不真实时会判它失败——于是一次散架的演练，散架时带着一句说明
它在等什么的话，而不是报一个绿色的空。

### `docs/runbook.md`——那一页

`mailer/1.22` 的那五个小节已经在那儿了，而且正是对的五个：**Symptoms**（最先被注意到的东西，从外面
看）、**Signals**（看什么，以及*在哪儿*看——那个指标、那条查询、那行日志）、**Steps**（做什么，包括
那些反直觉的）、**Verification**（"恢复了"是什么意思，用数字说）、**Escalation**（叫醒谁，交给他
什么）。这一版要加的是那个矩阵：响应者得能从*信号*上把三种退化分开，而每一节都得为三种各说一句不同的
话。

`links` 闸门会跑这一页，以及项目里其他每一个 markdown 文件：相对目标必须存在、`#anchors` 必须对得上
一个标题、本该是目标的 `TODO` 算失败。规格查的是闸门查不了的：这一页为三次演练各点名了确切的命令，
以及那些命令是对着哪些信号读的。

### 规格判什么

| the test | the claim |
| --- | --- |
| `the_database_away_drill_keeps_the_promise_and_can_be_replayed` | worker 的连接池在握着每一次投递时死掉，租约把它们带回来，队列排干——两遍，在两个数据库上 |
| `the_slow_subscriber_drill_keeps_the_promise_and_can_be_replayed` | 每次尝试都在路上、没有一个被应答；它们被放行，每一次投递都发出去——两遍 |
| `the_tenant_storm_drill_keeps_the_promise_and_can_be_replayed` | 洪水结束，队列排干，而那个安静的租户——它那一个事件比洪水里的每一行都*新*——被服务到了 |
| `the_{database_away,slow_subscriber,tenant_storm}_drill_reports_the_loss_when_nothing_recovers` | 同样三次演练，坏掉的东西再也不回来，各自在*服务的*行里报告还没做完的工作：演练是会失败的，而正是这让那些绿色的运行有了意义 |
| `the_runbook_names_its_sections_its_drills_and_the_signals_they_are_read_against` | 五个小节、三条确切的演练命令、`relay_backlog_depth` 与 `relay_deliveries_total{outcome="dead"}`，而且没有占位符 |

## 完成标准

- `kiln run relay/2.24-degradation-drill` — 规格通过（上面七个用例），一分钟之内
- `kiln check relay/2.24-degradation-drill` — 每个 must 闸门都是绿的，包括 `links`
- 下面每一条都是你亲手跑过的命令，而且其中至少有一次的 `Never` 报告你读过了：

```sh
cargo test -p relay --test spec_degradation_drill the_database_away_drill
cargo test -p relay --test spec_degradation_drill the_slow_subscriber_drill
cargo test -p relay --test spec_degradation_drill the_tenant_storm_drill
```

- 这一页按顺序告诉响应者：他在看什么、去哪儿看、做什么、怎么知道起作用了、不起作用时叫醒谁——**而且**
  在做任何一件之前，怎么把三种退化分开
- 你能张口说出为什么 `dead` 里的投递不是一次丢失的投递，而 `claimed` 里的是，以及演练讲的是这两者中
  的哪一个

## 陷阱

1. **一个永远通过的演练。** 对每个世界都说 `delivered == accepted, outstanding == 0` 的 `Report`——
   脚手架一上来正是这样——是书面演练最常见的形状，而且比没有更糟：它把一次事故变成"演练是绿的，那
   大概是别的地方"。`Never` 那几种情况就是用来让它失败的；去跑它们。
2. **抢在故障之前的恢复。** 在尝试被停住之前就放行它们，或者在认领被握住之前就让数据库回来，会造出
   两个看起来一样的世界，和一次对两者都证明不了什么的演练。等*行*说出故障已经发生。
3. **从演练的意图里读报告。** `delivered = accepted` 是一个演练不问任何人就知道的数字。服务自己的
   记录才是答案唯一住着的地方——三个算作"还欠着"的状态，见 `Report::nothing_was_lost`。
4. **用 sleep 代替等待。** `thread::sleep(2s)` 是第二常见的形状：在空闲机器上是最快的一次绿灯，在
   负载机器上是一次 flake。这些演练里的每一次等待都是带截止时间的条件（`Counted` 失败时把它的计数
   写进消息里），而*租约*那一种，是靠把租约做旧来处理的，不是靠等它过期。
5. **四个尝试共用一个订阅者。** `relay/2.9-ordering` 让每个端点各有一条车道，所以发往一个订阅者的
   尝试是*故意*串行的：一个端点的慢订阅者演练，看到一个尝试在路上、"什么都没丢"，而这理由和故障毫无
   关系。
6. **以为"什么都没丢"就是"每个人什么都收到了"。** 用完了重试预算的投递是 `dead`：服务放弃了它，它在
   DLQ 里，硬装作不是这样，会让演练变成关于订阅者的，而不是关于这个服务的承诺的。承诺是没有任何东西
   *看不见*——而 `dead` 正是看不见的反面。
7. **照着实现写出来的 runbook。** 读着 `src/` 写出来的一页，会罗列设置项和代码路径，而那正是响应者
   在凌晨三点用不上的东西。从会把你叫起来的告警写起，然后去确认那条告警存在——如果它不存在，那是一条
   关于服务的发现，不是关于这一页的。
8. **一页纸的命令只有一条。** "去跑演练"算不上一个能按事故分别执行的验证步骤。三条命令不同，因为三种
   失败不同，而规格会检查三条都在页面上。
9. **把升级当成补丁。** "联系团队"不是升级。下一个人需要的是：你已经排除了什么、你看到了什么、你把
   哪个决定交给他——包括那两个没人喜欢的：停止为某个租户接收事件，以及告诉一个客户，他们的事件正在
   被放弃。

- [PagerDuty: being on-call](https://response.pagerduty.com/oncall/being_oncall/) — 一次呼叫该花掉
  一个人多少注意力，这也是 Symptoms 那一节照着告警来写的原因
- [PagerDuty: during an incident](https://response.pagerduty.com/during/during_an_incident/) — 演练
  的形状和它周围的分工，Verification 与 Escalation 两节就是照它写的
- [Google SRE book: managing incidents](https://sre.google/sre-book/managing-incidents/) — 升级路径
  所用的词汇，以及为什么"队列很大"不算一次交接
- [Google SRE workbook: alerting on SLOs](https://sre.google/workbook/alerting-on-slos/) — 一条告警
  应该建在哪些信号上，以及症状和原因的区别
- [Chaos engineering principles](https://principlesofchaos.org/) — 为什么要在故障自己到来之前，先在
  一个能恢复的世界里故意把它注入进去
- [the lease of `relay/2.15-shutdown-leases`](2.15-shutdown-leases.md) — 数据库演练所倚靠的机制：
  一次认领就是一份租约，而截止时间正是把一个死掉的 worker 变成可恢复工作的东西
