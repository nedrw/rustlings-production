# 带预算的重试：抖动、上限和熔断器

## 为什么

`relay/2.6-at-least-once` 决定了失败的尝试让投递继续欠着，并写下一个常量：五次尝试，然后停下。那个常量就是
策略该在的地方。这两者之间隔着的东西，决定了一个服务是能从失败里恢复，还是把自己的故障越弄越糟。

那套策略有三种失败值得点名，因为每一种都是事故报告里的一页。

**回来的订阅者被所有东西同时砸中。** 它不在时失败的每一次投递，都按同一个时间表重试，于是所有 worker 在同一
毫秒醒来，而刚启动完的订阅者一下子收到全部积压。这就是惊群，修法不是"再等久一点"——总负载大致是对的——而是把
重试*摊开*：同样的总量，在不同的时刻到达。

**消失的订阅者会吞掉队列。** 对一个大部分时间在线的端点，每次投递重试五次没问题。对一个宕掉的端点，队列里的
每一次投递都会花光整份预算：一轮认领十六行，往一堵不会应答的墙上发十六个请求，而它们后面的投递在等一轮又一轮
什么也不产出的工作。这里的活不是重试；这里的活是知道这个端点已经宕了，知道一次，然后停下。

**没人说得清的重试策略，是没人调试得了的重试策略。** 运维员从"由随机数发生器抽出来的抖动"那里得到的话是：
"大概在三十秒到一小时之间的某个地方，我想。"一次投递的下次尝试时刻就在行上，所以它最好是一个 worker 算两遍
能得到同一个答案的函数。

所以这一步就是这套策略：指数级增长的等待，确定性地摊开，有上限，尝试次数有界，外加一个熔断器，在队列被一个
端点耗光之前停止跟它说话。这是一个 `design` 步，所以它还要交付一份为那些数字辩护的记录——预算是一组取舍，而
没有写成文字的取舍，会被下一个在日志里看见一次缓慢重试的人"修掉"。

### `src/backoff.rs`

- **`Budget::delay(delivery, attempt)`**——在 `attempt` 次失败之后的那次尝试之前要等多久。窗口是 `base`
  每失败一次翻一倍，封顶在 `cap`；投递*在*窗口里的位置，来自 `(delivery id, attempt)` 的哈希。
- **在窗口的哪里，以及为什么不用整个窗口。** 教科书答案是*全抖动*：在 `[0, window]` 上均匀抽一个数。它的
  去相关效果和这一样好，却在底部有一个几乎为零的等待——一次重试和它正在重试的失败落在同一毫秒，那是穿着退避
  外衣的自旋。它还破坏了前一步：`spec/2.6` 在失败*之后立刻*向 worker 要第二轮，并期望这次投递还在等，所以
  等待必须有个下限。摊在窗口的**上半部分**（`[base/2, base]`），并在记录里说明全抖动为什么输了。
- **用哈希，不用发生器。** `Uuid::as_u64_pair()` 给你 id 的 128 位；用一个 splitmix64 风格的收尾器把它们
  和尝试序号混在一起，取最高的 53 位，作 `[0, 1)` 里的 `f64`。没有 `rand`，没有状态，每个 worker、每次重跑
  都得到同一个等待。相邻的 id 必须在窗口里落得很开——"去相关"说的就是这个——所以要混，不要 `% 100`。
- **翻倍必须停下来。** `1u32 << 40` 在 debug 构建里 panic，而绕回来的等待只有几毫秒。把翻倍的次数夹住，用
  `saturating_mul`，再 `.min(cap)`。
- **`Budget::gives_up(attempt)`**——尝试预算，也就是 `relay/2.6` 的 `MAX_ATTEMPTS` 有了个名字。默认预算
  保留 5 次尝试、30 秒的基数和 6 小时的上限：那些是给定的，这一步加的是形状。
- **熔断器。** 每个*端点*一个 `BreakerPolicy { failures, cooldown }`，答案是 `Admission`：`Try`、半开时的
  `Probe`，或者 `Shed`。数**连续的可重试失败**，成功时清零，冷却之后发生的事当作一次探针：只放一次尝试出
  去，它的答复决定熔断器是合上（成功）还是再开一个全新的冷却期（失败）。一个从未被汇报的探针——拿着它的
  worker 死了——必须在又一个冷却期之后被认定为丢失，否则一个死掉的进程就把一个端点永久切断了。
- **时间是参数，不是从环境里随手读的。** `delay` 收下投递，`admit` 收下时刻。另一个选择——
  `tokio::time::pause()` 配 `#[tokio::test(start_paused = true)]`，`mailer/1.14-worker` 的 worker
  循环用的就是它——在这里是错的工具，理由有三条：`test-util` 在这个构建图里不是 `tokio` 的特性，脚手架不能
  改写 `Cargo.toml` 里的 `tokio` 那一行，而一个读时钟的*策略*，是没有时钟就没法评判的策略。时钟归 worker
  循环（`relay/2.9-ordering` 和 `relay/2.15-shutdown-leases`）；策略收下别人告诉它的东西。
- **`Clone` 共享熔断器。** 状态住在 `Arc<Mutex<…>>` 后面：worker 把它跑的每一轮都交给同一个预算，于是端点
  跨轮保持切断。每轮重建的熔断器，是只保护一轮的熔断器。

### `src/delivery.rs`

- **`tick_with_budget(pool, sender, worker, budget)`**——带着它所用策略的那一轮，也是这一步加进来的接缝：
  `pub async fn tick_with_budget(pool: &PgPool, sender: Arc<dyn Sender>, worker: &str, budget: &Budget) -> Result<Tick, Error>`。
  sender 是 `Arc`，因为一轮可以拥有它并发跑的东西（那是 `relay/2.9-ordering`）；budget 是策略。`tick`——
  `relay/2.6` 钉住的签名——留着，继续用默认策略，也继续只跑一轮。
- **把预算接进去。** `mark_retry` 写 `now + budget.delay(delivery, attempt)`，最后一次尝试由
  `budget.gives_up(attempt)` 判定，而不是一个常量。把常量从这个文件里搬走，别在策略旁边留下一份副本。
- **在尝试之前问熔断器，并记下它的答复。** 被 shed 的投递**不做尝试**：用 `claim::release` 把行交回队列，
  并在 `Tick::shed` 里计数。它的 `attempts` 不动，`next_attempt_at` 也不动——那是熔断器许下的承诺，而一
  行被 shed 之后留在 `claimed`，就是直到租约到期都没人看一眼的投递。
- **永久失败不是端点的健康状况。** 一个 `410 Gone` 说的是某一次投递；熔断器数的是重试会再撞上的那些失败。
  把这一点写进记录：正因如此，有毒端点上的投递仍然一个一个地死掉，而不是一起被 shed（它们落在
  `relay/2.10-dlq`）。
- **默认熔断器不能在一次投递花完自己的尝试之前打开。** `failures` 至少得是 `max_attempts`，因为
  `spec/2.6` 数的是*轮数*：在一个投递还剩几次尝试时打开的熔断器，会把本该埋葬它的那几轮 shed 掉，而前一步
  就红了。默认值（5 和 5）就是这条约束变成了数字。

  的投递被摊开、熔断器会打开、合上、半开、一个丢失的探针不会把端点永久切断、默认策略仍然在 `relay/2.6` 量过

## 陷阱

1. **字面照做的全抖动。** 在 `[0, window]` 上均匀抽数，会足够频繁地给出几乎为零的等待，重试和失败在同一毫秒
   开火，而 `spec/2.6` 那句 "asked again when the retry is due, not before" 在最终的树上失败。摊到上
   半部分，或者任何有下限的窗口。
2. **用 `rand` 做抖动。** 它去了相关，也毁掉了可复现性：两个 worker 为同一次投递算出不同的等待，说下次尝试
   在何时的日志行没法核对，一个想断言等待的测试只能接受一个区间。`(id, attempt)` 的哈希跨进程、跨重跑都稳
   定，那正是这一步花钱买来的性质。
3. **`1u32 << attempt`。** 四百次翻倍在 debug 里是 panic，在 release 里是回绕，而一次已经失败了四十次的投
   递，绕回来的等待只有几毫秒。夹住翻倍次数，用 `saturating_mul`，再 `.min(cap)`。
4. **恒定不变的抖动。** `attempt * base + (id % 2)` 什么也没去相关，任何范围跟窗口比起来只是个舍入误差的表
   达式也一样。六十次一起失败的投递必须落在六十个不同的地方；规格会检查它们确实如此。
5. **shed 了却不交回。** 行被认领了，尝试跳过了，worker 走了：这次投递在租约到期之前一直是 `claimed`
   （六十秒的隐身），之后的那一轮又认领它、又 shed 它、又写回去。把它交回去，并计数。
6. **为它拒绝的那次尝试收费的熔断器。** 如果一次被 shed 的投递仍然走 `mark_retry`，它的 `attempts` 就会
   增长，等到端点恢复时预算已经没了——当时是端点宕了，受罚的却是这次投递。规格的最后一个测试正是这个。
7. **第一次失败就打开、或者任何失败都打开的熔断器。** 一次小故障不是宕机，一个永久的 `410` 也不是关于端点的
   证据：数*连续的可重试*失败，并在成功时清零。
8. **半开的熔断器没有回头路。** 一个探针放了出去，拿着它的 worker 死了，端点就被永久切断，因为永远没有人汇
   报这个探针。给探针一个自己的窗口，窗口用尽就把它当作丢失。
9. **把熔断器放进 `static`。** 进程级的捷径让熔断器跨轮存活，也让它在*测试*之间存活：一个弄坏端点的规格，
   会让同一个二进制里的每个测试都面对一个坏掉的端点，而失败看起来像策略不稳定，而不是共享状态。该共享的东西
   是预算，而它是传进来的。
10. **常量的第二份副本。** 策略回答了同一个问题，却在 `delivery.rs` 里留着 `MAX_ATTEMPTS`（或者旁边再放
    一个 `BACKOFF`），两个上界就是这样分家的：行上说一套，worker 做另一套，而差别表现为"attempts"永远
    到不了运维人员被告知的那个数。
11. **一套成了另一种策略的默认预算。** 默认值是值，而没人论证过的值，是没人辩护得了的值。5 次尝试、30
    秒、6 小时和一个 5 次失败的熔断器，就是 `relay/2.6` 的常量有了形状——改了它们，记录得跟着改，
    `spec/2.6` 还得照样通过。

## 延伸阅读

- [AWS: exponential backoff and jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)
  — "full" 和 "equal" 抖动被命名、被测量的地方，以及为它们辩护的那个模拟
- [Marc Brooker: jitter, sleeping and the thundering herd](https://brooker.co.za/blog/2015/03/21/backoff.html)
  — 同一个论证，出自替我们把它写成文章的人，并给出等抖动的公式
- [Martin Fowler: circuit breaker](https://martinfowler.com/bliki/CircuitBreaker.html) — 三个状态、探针，
  以及为什么熔断器该放在它所保护的那次调用旁边
- [Nygard: release it! — stability patterns](https://pragprog.com/titles/mnee2/release-it-second-edition/)
  — `Circuit Breaker`、`Bulkhead` 和 `Fail Fast`——这个模式就出自那本书
- [splitmix64](https://prng.di.unimi.it/splitmix64.c) — 这一步的哈希所用的收尾器，六行，没有状态
- [`tokio::time::pause`](https://docs.rs/tokio/1.53.1/tokio/time/fn.pause.html) — 暂停的时钟，它对
  `Instant::now()` 和定时器做了什么，以及它需要的 `test-util` 特性（所以这里的策略改成收一个时刻）
- [`chrono::DateTime`](https://docs.rs/chrono/0.4.42/chrono/struct.DateTime.html) — 时刻上的算术，以及不会
  panic 的 `Duration` 转换
- [RFC 9110 §15.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.5) — 带 `Retry-After` 的
  `503 Service Unavailable`：订阅者用这个状态，按它自己的条件要的正是这套策略
