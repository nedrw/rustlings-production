# 每个分区恰好有一个主人

## 为什么

一个消费者组是几个进程假扮一个读者。这个假扮只有在每一刻**每个分区恰好分配给一个成员**时才成立：
两个主人就重复处理，没有主人就卡住，而一个分区中途换手，就是所有人都在抱怨的那次再平衡。

这一步的分配规则是范围分配器——最简单的那个，也是让性质看得见的那个：

- **连续区间。** 成员 `a` 拿 `0..k`，`b` 拿 `k..m`：一个成员的分区是一段区间而不是一把散沙，
  它的读就是顺序的；
- **每个分区恰好一次。** 分配结果的并集就是分区表，没有重复；
- **余数给更早的成员。** 分不匀时总得把多余的放个地方；"成员排序、余数在前"是让分配具有确定性的那条规则；
- **成员比分区多就有成员空手。** 这是一个诚实的答案而不是错误：组开大了，多出来的成员会在有人离开时
  接管分区。

## 任务

脚手架加上了 `src/assignment.rs` 和它的 `pub mod assignment;` 那一行。

- **[`assign`]**——每个成员拥有的分区，从成员名到一段连续列表：成员排序，每人
  `partitions / members` 个，余数给前几个，没有分区的成员拿到空列表。
- **没有成员**就是一张空表；**没有分区**则每个成员都拿到空列表。

## 完成标准

- `kiln run broker/7.3-rebalance` —— 规格通过
- `kiln check broker/7.3-rebalance` —— 每个 must 闸门都是绿的
- 六个分区两个成员是 `[0,1,2]` 与 `[3,4,5]`；五个分区两个成员是 `[0,1,2]` 与 `[3,4]`

## 陷阱

1. **轮转分配。** `partition % members` 分得均匀，也分得散：成员 `a` 拿到 `0,2,4`，它对日志的读在
   到处跳。规格里连续性的断言就是证人。
2. **区间重叠。** 切分处差一（`next..=next + count`）会让分区 `k` 同时属于两个成员；"每个分区恰好
   一次"那条测试会抓住它。
3. **余数给最后一个成员。** 那依然是一个合法的分区集合，却和其他消费者期待的分配器不一致；分不匀那条
   测试钉住了规则。
4. **成员不排序。** 分配就取决于调用方传进来的顺序，两个成员从同一个集合算出来的结果可以不一致——
   那是换了副面孔的脑裂。
