# 做完再提交，重启从这里继续

## 为什么

已提交的偏移是消费者组留给下一世的唯一遗产。重启之后的行为全由一个约定和一个习惯决定：

- **提交的是下一个要读的偏移**，不是刚读过的那个。处理完偏移 `0` 的记录之后 `commit(1)`，意思是
  "从 1 重新开始"。提交刚读过的那个偏移，那条记录会被永远重投——这是每个消费者起步时都有的差一；
- **做完再提交**，不是先提交。先提交是一句进程还没兑现的承诺：提交之后崩溃，这条记录永远不会被处理；
  做完之后、提交之前崩溃，记录会再投一次——这就是*至少一次*的含义，也是为什么那件工作必须幂等。

日志是"有什么"的唯一真相，所以提交不能主张日志里没有的东西：越过末尾的偏移会被夹到末尾，而 topic
并不存在的分区根本不是一个位置。

## 任务

脚手架加上了 `src/consumer.rs` 和它的 `pub mod consumer;` 那一行。`poll`、`resume`、`committed`
和构造函数是现成的；`commit` 是桩。

- **[`Consumer::commit`]**——记录这个组在某个分区的位置：
  - topic 没有的分区：忽略；
  - 越过 `topic.end(partition)` 的偏移：夹到末尾；
  - 其余：原样记录。
- **重启从提交处继续**——`resume` 是现成的；规格里"至少一次"那条测试读的是未提交的情形：那些记录
  会再投一次。

## 完成标准

- `kiln run broker/7.2-consumer-offsets` —— 规格通过
- `kiln check broker/7.2-consumer-offsets` —— 每个 must 闸门都是绿的
- 处理两条记录并提交 `2` 之后，用 `resume({0: 2})` 构造的消费者从第三条开始

## 陷阱

1. **提交刚读过的偏移。** 读完偏移 `0` 之后 `commit(&topic, 0, 0)`，重启又从 `0` 开始，那条记录
   被永远重投；规格里*"从停下的地方继续"*会失败。
2. **先提交再做。** 规格看不见两条语句的先后，但"未提交"那条测试是同一个算术的另一面：没有提交的
   进展会被重投，而那正是让至少一次诚实的代价。
3. **记录一个越过末尾的提交。** 重启读不到东西（没问题），而下一步的 lag 会变成负数——规格把它夹在
   末尾。
4. **为不存在的分区提交。** 看起来无害，实际上掩盖了一个在说错 topic 的调用方；规格里"忽略"那条
   让这张表保持诚实。
