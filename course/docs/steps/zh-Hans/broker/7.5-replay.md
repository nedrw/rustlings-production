# 重放是一个区间，不是一个位置

## 为什么

迟早有人要再看一遍昨天的事件：下游那张表错了、某个投影要重建、审计要看那段区间。这些都不是*消费*
——消费者组已提交的偏移是关于"服务处理到哪"的承诺，重放不能移动它，否则在线消费者会从审计停下的
地方重新开始。

把两者分开的形状，是一个覆盖半开区间的重放对象：它从 `from` 往后读、在 `to` 之前停下，不持有任何
提交。`to` 是开区间，和这门课里每一个区间一样——`[from, to)`——也正因为如此，"把出错的那段重放
一遍"才能不带差一地写出来。

## 任务

脚手架加上了 `src/replay.rs` 和它的 `pub mod replay;` 那一行。`new`（把 `to` 夹到日志末尾）与
`remaining` 是现成的；`next_record` 是桩。

- **[`Replay::next_record`]**——重放下一个偏移上的记录并前进；区间走完、或日志在区间内结束时返回
  `None`。
- **重放从不碰消费者。** 规格围绕一次重放对一个在线消费者做 poll 与 commit，并要求它的位置不变。

## 完成标准

- `kiln run broker/7.5-replay` —— 规格通过
- `kiln check broker/7.5-replay` —— 每个 must 闸门都是绿的
- 对三条记录重放 `[1, 3)` 得到第二条和第三条，而在线消费者接下来读到的仍然是第二条

## 陷阱

1. **从重放里提交。** "它就是一个更早的消费者"这个自然的想法，会让在线组从审计的位置恢复。规格的
   *"重放提交了东西"* 会失败。
2. **把 `to` 当成闭区间。** `[1, 3)` 读出 1、2、3，相邻两个窗口就会把一条记录处理两次——每个区间
   bug 都是这个算术。
3. **从 `from - 1` 开始。** 反方向的差一：每次重放的第一条记录被应用两次，而幂等的效果会把它藏到
   藏不住的那天。
4. **让区间跑过日志。** 对越过末尾的 `to`，`next_record` 应当回答 `None` 而不是 panic；夹取在
   `new` 里，读取返回的 `Option` 是第二道防线。
