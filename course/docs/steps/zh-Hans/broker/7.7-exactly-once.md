# 恰好一次是一张表，不是一句承诺

## 为什么

broker 给的是至少一次。恰好一次**处理**是在它之上搭出来的：把效果做成幂等——记下产出它的偏移，
偏移已经在表里的记录就跳过。机制就是一张以 `(分区, 偏移)` 为键的表，在效果之前检查、在效果之后
写入——真实系统里在同一个事务里，这个项目的模型里在同一次调用里。

两个后果随之而来，规格里都看得见：

- **重放是空操作。** 重新处理一段已经成功的区间，什么都不应用，这就是"恰好一次"与"还没看到第二次"
  的区别；
- **效果与提交之间崩溃不会重复。** 记录会再投一次，表里已经有了它，第二次投递什么都不改变。反过来
  ——提交在效果之前——会丢，这也是为什么这一步里根本没有提交这件事。

表就是整个设计。它放在哪里（与效果同一个数据库、同一个事务），就是这个保证的来源；放在另一个存储
里的表，是两个副本都只写了一半的那个窗口。

## 任务

脚手架加上了 `src/exactly_once.rs` 和它的 `pub mod exactly_once;` 那一行。`Sink`——那张表与效果
——以及它的 `applied`/`apply`/`effects` 是现成的；`process` 是桩。

- **[`process`]**——按偏移顺序走某个分区的 `[from, to)`，把 sink 还没应用过的每一条应用掉，回答这一
  遍新增了几个效果。
- **末尾夹到日志**，和别处一样：越过末尾的区间不是错误。

## 完成标准

- `kiln run broker/7.7-exactly-once` —— 规格通过
- `kiln check broker/7.7-exactly-once` —— 每个 must 闸门都是绿的
- 对 `[0, 3)` 处理两次：第一次应用三个效果，第二次零个

## 陷阱

1. **不检查就应用。** 最直白的循环第一遍正确，重放时把每个效果都复制一遍；规格里*"一条记录被应用了
   两次"*就是这条断言。
2. **用载荷当表的键。** 两条载荷相同的记录——一次重试、一次重发——会被当成同一项，第二条被跳过，
   尽管它是另一条记录；偏移才是身份。
3. **提交在效果之前。** 在真实系统里那是数据丢失（记录落在提交之后、永远不被处理），而这一步的模型
   露出的是另一面：表与效果一起写，因此没有东西可以在它之前提交。
4. **指望 `apply` 自己去重。** `apply` 确实会忽略重复的偏移——表之所以是机制，正因为如此——但题在
   *调用*上：一个应用一切、依赖表去重的版本仍然把那条记录算成新的，规格的计数会失败。
