# 该排序的排序，其余并行

## 为什么

topic 没有全局顺序。需要全局顺序的人有一个设计问题，答案是键：必须保持顺序的那些记录共用一个分区，
其余的分开。有意思的地方在于键**要多粗**。

两个失败模式夹住了答案：

- **一切都用同一个键**——分区 `0` 拿到整个 topic：顺序完美，并行度为零；
- **每个事件一个键**——每条记录落到不同分区，什么都没有顺序。

真正需要的，是*必须相互保序的一组事件*共用一个键——"必须保序"这张图的连通分量。链 `a → b → c` 是
一组，即使没有任何规则同时点名 `a` 和 `c`：顺序是传递的，而"每条规则一个键"正是把这层传递性丢掉
的方式。

## 任务

脚手架加上了 `src/ordering.rs` 和它的 `pub mod ordering;` 那一行。

- **[`plan`]**——每个事件一个键：被规则连在一起的事件共用一个键，没有规则相连的事件各自一个，而一组
  的键取组里最小的名字（这样答案不取决于规则的先后）。规则里点名了 `events` 之外的事件就忽略。
- **并查集是自然的实现**——连通分量就是那些组——但任何满足上述性质的答案都能过。

## 完成标准

- `kiln run broker/7.6-ordering` —— 规格通过
- `kiln check broker/7.6-ordering` —— 每个 must 闸门都是绿的
- `a-b`、`b-c` 是一组；`a-b` 与 `c-d` 是两组；没有规则就是四个单元素组

## 陷阱

1. **每条规则一个键。** `("a","b")` 和 `("b","c")` 给出两个键，`a` 与 `c` 没有顺序，产品需要的
   那条链断了。规格里*"一条链变成一组"*就是这个缺陷。
2. **一切都用同一个键。** 它过掉所有顺序测试，并把整个 topic 串行化：正是键存在的意义要避免的代价。
3. **组的键取决于规则的顺序。** 取第一条规则左边那个名字，同一张图会得到不同的计划，两个各自计算的
   发布方从此不一致——换了副面孔的脑裂。
4. **只看直接配对。** 发布时检查 `must_order`（"这一对有序吗？"）而不是先规划键：传递性没有检查，
   而且它本身就是每条事件一次 O(n) 的查找。
