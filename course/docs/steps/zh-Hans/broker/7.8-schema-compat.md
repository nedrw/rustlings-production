# 加法兼容，减法破坏

## 为什么

一个事件是一份契约，意义与第 `relay/2.3` 步的 HTTP 正文相同，只多一件让演进更难的事：昨天的那个事件的
消费者还在读这条流。规则是不对称的，而三种破坏其实是同一件事——**把信息拿走**：

- **删掉一个字段**，是消费者可能正在读的信息；
- **改变类型**，是同一份信息换了形状：把 `status` 当字符串解析的消费者，现在收到数字，就是坏了，
  不管 JSON schema 怎么说；
- **新增一个必填字段**，是从*生产者*那一侧做减法：旧写入方不发送它，而要求它的消费者会拒掉它们
  的事件。新增**可选**字段是唯一兼容的加法，因为不知道它的消费者会忽略它。

方向很重要：兼容性是站在旧 schema 的消费者那边判断的——它无处不在；不是站在新生产者那边——它只是
一个进程。

## 任务

脚手架加上了 `src/schema.rs` 和它的 `pub mod schema;` 那一行。

- **[`compat`]**——旧 schema 与新 schema 之间每一处破坏性差异，排序返回：
  [`Breaking::Removed`]、[`Breaking::TypeChanged`]、[`Breaking::RequiredAdded`]。
- **新增可选字段不在列表里。**
- **答案是一个列表，不是一个布尔值**：一处删字段、一处加字段是两个事实，评审者两个都要看。

## 完成标准

- `kiln run broker/7.8-schema-compat` —— 规格通过
- `kiln check broker/7.8-schema-compat` —— 每个 must 闸门都是绿的
- 新增可选的 `trace` 兼容；新增必填的 `tenant` 不兼容；把 `status` 从文本改成数字不兼容

## 陷阱

1. **只查旧的那一向。** `for field in old` 找得到删除与类型变化，完全漏掉必填新增——新生产者那一侧
   的问题是另一个循环。
2. **把任何新增字段都当兼容。** 在 JSON 线上它能解析；在消费者那一侧，它要么必填要么不必填，那个
   标志才是整个问题。
3. **"因为是 JSON"，所以类型变化兼容。** 对每个有类型的消费者、对它写入的数据库列，`"1"` 和 `1`
   都是不同的值。
4. **只返回第一处破坏。** 评审者同时在改好几处；规格要的是排好序的完整列表，changelog 也需要。
