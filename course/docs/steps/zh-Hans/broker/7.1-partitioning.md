# 一个键一个分区，一个分区一个顺序

## 为什么

只有一个追加点的日志简单，但没法并行读。一个 topic 有很多分区，就是每个分区一条日志，而让这件事
有用的两条承诺，说的都是记录落在**哪个**分区：

- **同一个键每次都落在同一个分区。** 这正是按键有序的来源：只读一个分区的消费者，看到的是那个租户
  的记录按发布顺序排列——全局有序在有用的吞吐下给不了这个；
- **没有键的记录也要分散。** 一个从不给记录设键的生产者，不该把全部吞吐压进分区零：分区存在的
  意义就是可以被并行读。

偏移是每个分区各算各的，不是整个 topic 一个：`(分区, 偏移)` 才唯一指名一条记录，两半单独都没有
意义。所以消费者的位置是一张表而不是一个数字——那是下一步。

## 任务

脚手架放好了 `src/lib.rs`：topic、它的分区和 `partition_for`（一个稳定的 FNV-1a 哈希，作为给定项，
因为哈希不是题）。`Topic::append` 是桩。

- **带键的记录**去 `partition_for(partitions, key)` 那个分区的末尾，`append` 回答 `(分区, 偏移)`。
- **没有键的记录**去轮转到的下一个分区——是跨多次追加轮转，不是每次调用都从头。
- **偏移就是记录在它那个分区里的下标。** 两个分区都有偏移 `0`。

## 完成标准

- `kiln run broker/7.1-partitioning` —— 规格通过
- `kiln check broker/7.1-partitioning` —— 每个 must 闸门都是绿的
- 同一个键追加三次之后，有一个分区的 `end == 3`；四条无键记录之后，每个分区恰好一条

## 陷阱

1. **哈希在两次运行之间会变。** `RandomState`（`HashMap` 默认的 hasher）按进程播种：同一个键重启
   之后落到另一个分区，按键有序就没了。给好的 `partition_for` 是稳定的，正是为此。
2. **按载荷路由。** 做演示很方便，可一旦同一个键的两条记录载荷不同就坏了：它们的顺序不再是某一个
   分区的顺序。
3. **所有无键记录都进分区零。** 对规格里带键的测试都对，对无键那条是错的：四个分区里三个永远是空的，
   topic 没有被并行读。
4. **全局偏移。** 在整个 topic 上数记录，会让 `(分区, 偏移)` 变得不唯一——两条记录同一个名字——下一
   步里每个消费者的位置都会差得不止一个。
