# lag 是那个说清谁在落后的数字

## 为什么

活着的消费者组，不等于跟得上的消费者组。说清这件事的数字是 **lag**：每个分区上，末尾偏移减去
已提交的偏移——还有多少条记录在排队。加起来是积压（backlog）；分区分开看，就知道哪个分区是问题所在。

两个边界决定让这个数字可信：

- **提交越过末尾就是零，不是负数。** 那是调用方的错，而 `u64` 的减法在 debug 构建里会 panic、
  在 release 构建里回绕成一个巨大的 backlog。日志是真相，答案饱和；
- **没有提交的分区是完全落后。** 表里没有它，意思是"还没人提交"，不是"不适用"——整个分区都在等，
  而一份漏掉它的 lag 报告，是一份把最差分区藏起来的报告。

"落后"是一个阈值，而边界是有意义的：恰好落在阈值上的分区在阈值上，没有越过它。告警应当在 lag
**高于**某个选定的数字时响。

## 任务

脚手架加上了 `src/lag.rs` 和它的 `pub mod lag;` 那一行。`backlog` 与 `behind` 是现成的；`lag`
是桩。

- **[`lag`]**——topic 的每个分区一项：`end.saturating_sub(committed)`，其中缺失的提交按 `0` 算，
  越过末尾的提交饱和成 lag `0`。

## 完成标准

- `kiln run broker/7.4-lag` —— 规格通过
- `kiln check broker/7.4-lag` —— 每个 must 闸门都是绿的
- 一个末尾为 `1, 0, 0`、没有任何提交的 topic 报出 lag `1, 0, 0`——每个分区都在，包括安静的那些

## 陷阱

1. **直接相减。** `end - committed` 在提交越过末尾时 debug 构建 panic、release 构建回绕；规格里
   *"越过末尾的提交掉到了零以下"* 就是这个缺陷。
2. **只算有提交的分区。** `for (partition, committed) in committed` 报出的都是已经有人知道的分区，
   藏起那个还没人开始的分区：最差的那个。
3. **"落后"用 `>=`。** 恰好落在阈值上的分区在阈值上、没有越过；边界测试会失败，而告警永远早一个分区
   响。
4. **用未提交的位置算 lag。** `next`（这个进程读到了哪里）不是 `committed`（这个组会从哪里恢复）：
   重启之后两者相差的就是进程内存里那份进度，而那恰恰是 lag 要紧的时候。
