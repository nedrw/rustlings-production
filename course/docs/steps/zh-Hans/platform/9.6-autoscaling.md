# 快上、慢下，加一条止抖动的带

## 为什么

自动伸缩器是一个公式加两个习惯。公式是 `desired = ceil(current × metric / target)`；让公式可用的
是那两个习惯：

- **一条容差带。** 在目标值 10% 以内的指标算"够近了"。没有这条带，围着目标值波动的指标会每个窗口
  要一个副本、再要少一个副本，永不停歇——集群把时间都花在启动和杀掉从未服务过任何请求的 Pod 上；
- **不对称。** 扩容发生在第一个窗口，因为队列*现在*在长。缩容要等目标值以下的若干个窗口，因为短暂
  回落是一次暂停，而为一次暂停撤走容量，就是让下一次尖峰遇到一个更小的服务。

这个不对称是值得在评审里为之辩护的设计决定。对称的自动伸缩器更好描述，两个方向都更糟：吸收突发慢，
丢弃容量快。

## 任务

脚手架加上了 `src/autoscaling.rs` 和它的 `pub mod autoscaling;` 那一行。

- **[`desired`]**——公式，夹在 `[min, max]` 里，而指标落在目标值 `TOLERANCE_PERCENT` 以内时保持
  当前数量不动。
- **[`Stabilizer::observe`]**——实际应用的副本数：上升立刻生效并重置计数；下降要等 `down_after` 个
  连续窗口都落在当前数量或以下。

## 完成标准

- `kiln run platform/9.6-autoscaling` —— 规格通过
- `kiln check platform/9.6-autoscaling` —— 每个 must 闸门都是绿的
- 三个 Pod 在目标值 200% 时要求六个；95% 时保持三个；缩容窗口为三时，第三个低窗口之后才降

## 陷阱

1. **没有容差带。** 只有公式就会围着目标值振荡；规格里*"带内保持数量不变"*就是失败的那条断言。
2. **对称窗口。** 扩容之前也等，就是把一次突发变成一次事故：稳定器在数数的时候，队列在长。
3. **用浮点比较算容差带。** `metric as f64 / target as f64` 用一个舍入规则决定集群的行为；整数写法
   （`metric × 100` 对 `target × 90/110`）是精确的。
4. **夹取夹错了方向。** `max` 是上限、`min` 是下限，而 `min > max` 是配置错误，夹取要能扛住它而
   不是 panic。
