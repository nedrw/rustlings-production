# 发布的每一步，而不只是结尾

## 为什么

一次发布可以以完全正确的规模收尾，同时在中途把服务打挂过。结尾是第二天早上仪表盘上显示的东西；
中途是用户看到的东西。所以演练要**逐个观测步骤**核对两个预算——上限（`replicas + max_surge`）与
下限（`replicas - max_unavailable`）——报告的是破了预算的那些步骤，不是一个结论。

这和 runbook 演练（mailer 1.22）是同一个形状：彩排只有在它有地方能失败时才算证据，而"部署是绿的"
不是证据——"没有一步超过 surge、没有一步低于下限"才是。

## 任务

脚手架加上了 `src/drill.rs` 和它的 `pub mod drill;` 那一行。

- **[`drill`]**——对每一个观测步骤，按顺序：`total` 高于上限是 [`Violation::TooManyPods`]，`ready`
  低于下限是 [`Violation::TooFewReady`]；两个可以同时成立，且都报出来。恰好落在预算上是允许的。

## 完成标准

- `kiln run platform/9.7-rollout-drill` —— 规格通过
- `kiln check platform/9.7-rollout-drill` —— 每个 must 闸门都是绿的
- 三个副本、surge 一、不可用预算一：同一步里四个总数、两个就绪是允许的；五个总数或一个就绪都是违规

## 陷阱

1. **只查最后一步。** 结尾是绿的、中途是事故；规格里*"每一步都查，不只是最后一步"*就是这条断言。
2. **每步只报一个违规。** 两个预算可以同时破，而评审者在修两件事；只报第一个会把第二个藏起来。
3. **严格的上限。** 四个总数*在*上限上，不在它之上；比较写成 `>=` 时边界测试失败。
4. **忽略下限。** `maxUnavailable: 1` 允许三个里有两个就绪，所以两个就绪的一步是干净的一步——要求
   三个全就绪的实现会挂在干净发布上。
