# 存活说进程，就绪说能不能服务

## 为什么

Kubernetes 的探针由定时器驱动，定时问一个问题，而**答错的后果**才是伤害所在：

- **存活**探针失败会重启进程——一个查数据库的存活探针，会在数据库每次眨眼时重启一个完全健康的
  服务，把一次依赖故障变成重启循环；
- **就绪**探针失败只是把这个 Pod 从 Service 的端点里摘出去——所以依赖属于就绪：它必须真的检查
  点什么，因为永远返回通过的就绪探针，会让流量到达一个根本不能服务的 Pod。

这条分界就是一句话：**存活回答"这个进程活着吗"，就绪回答"它现在能做自己的事吗"**。mailer 1.9 用
`/healthz` 与 `/readyz` 引入了这个区别；这一步是同一个决定的清单侧。

## 任务

脚手架放好了 `src/lib.rs`：`Probes` 与 `Finding` 在里面；`audit` 是桩。

- **[`audit`]**——接线上的每个问题，排序返回：[`Finding::LivenessChecksDependency`] 是存活探针读了
  依赖，[`Finding::NoReadinessProbe`] 是没有就绪探针，[`Finding::ReadinessAlwaysPasses`] 是就绪探针
  存在却什么都不检查。
- **没有就绪探针的清单没有"永远通过"的问题**——两者是两个选择，不是一份"缺了什么"的清单。

## 完成标准

- `kiln run platform/9.1-probes` —— 规格通过
- `kiln check platform/9.1-probes` —— 每个 must 闸门都是绿的
- 存活查进程、就绪查服务是干净的；存活探针去查数据库不是

## 陷阱

1. **两个探针用同一个端点。** 这是最常见的接线，也是把两个问题合成一个：要么依赖故障会重启进程
   （存活探针指向 `/readyz`），要么一个死掉的 Pod 继续收到流量（就绪探针指向 `/healthz`）。规格
   看不见端点，正文看得见。
2. **存活探针指向 `/readyz`。** 数据库一闪，所有 Pod 重启，而那次重启就是事故。
3. **根本没有就绪探针。** 滚动发布于是会在新 Pod 能服务之前换掉旧 Pod，看起来全绿的发布发出 502。
4. **只返回 200 的就绪探针。** 它比没有更糟，因为它看起来像一项检查；规格里*"什么都没说的探针"*
   就是这个发现。
