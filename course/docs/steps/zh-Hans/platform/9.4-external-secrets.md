# secret 是引用，不是产物

## 为什么

烤进镜像的密钥（secret），就是每个仓库副本、每层缓存、每台拉过它的笔记本里都有一份的密钥。平台原生的
答案是**引用**：清单里写密钥管理器（secret manager）中的一个路径与一个键，工作负载启动时解析它，而镜像里只有引用，
别的什么都没有。轮换于是变成一次重启（或一次重载），而不是重新构建。

两个判断撑起这个设计，第二个是评审最容易漏掉的：

- **解析是严格的。** 路径或键不存在时，是一个点名它的错误——从来不是一个空字符串，让服务带着空密码
  启动，然后在别的地方、以另一种样子失败成一个认证 bug；
- **产物是干净的。** 清单里出现密钥的值就是泄漏，注释里也算：清单会被提交、评审、发布，而注释
  就是文件里的一行。

## 任务

脚手架加上了 `src/secrets.rs` 和它的 `pub mod secrets;` 那一行。`resolve` 与 `leaks` 是两个桩；
类型是现成的。

- **[`resolve`]**——每个引用解析成它的值，或 [`SecretError::Missing`] 点名第一个不存在的路径与键。
  解析失败时不返回任何部分结果。
- **[`leaks`]**——清单里含有任何一个密钥值的非空行。

## 完成标准

- `kiln run platform/9.4-external-secrets` —— 规格通过
- `kiln check platform/9.4-external-secrets` —— 每个 must 闸门都是绿的
- 指向存在的路径与键的引用能解析；缺键会点名路径；注释里的值会被找到

## 陷阱

1. **查询上 `unwrap_or_default()`。** 缺失的键变成一个空密码，失败会在另一个服务里以登录 bug 的形式
   浮现。规格里*"是一个错误，不是一个空值"*就是这个缺陷。
2. **返回引用而不是值。** 一个返回 `env → path` 的"解析器"把取密钥的活留给调用方，等于把管理器
   的 API 塞进每个工作负载。
3. **只审 `value:` 行。** 注释、标签或注解里的密钥仍然在会发布出去的那份文件里；规格里注释那条
   用例是最便宜的版本。
4. **空密钥匹配一切。** `leaks` 的扫描必须跳过空值——空字符串被每一行包含。
