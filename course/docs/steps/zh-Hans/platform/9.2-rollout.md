# 两个预算决定发布的每一步

## 为什么

滚动发布是两个数字的算术，而每一个发布 bug 都是其中一个被忽略了：

- **`maxSurge`** 限定可以多存在几个 Pod——只要 `total < replicas + surge` 就允许创建；
- **`maxUnavailable`** 限定可以比期望数量少几个就绪——只有在 `ready - 1 >= replicas - unavailable`
  时才允许一个 Pod 离开。

这两个一起解释了为什么 `maxUnavailable: 0` 需要 surge：没有多余 Pod，就没有东西能在第一个旧 Pod
离开之前变就绪，发布会在满容量处永远等下去。它也解释了相反的失败：一个副本、`maxSurge: 0` +
`maxUnavailable: 1`，会在换手期间把服务打挂，因为唯一能走掉的 Pod 就是仅有的那个。

## 任务

脚手架加上了 `src/rollout.rs` 和它的 `pub mod rollout;` 那一行。`available_floor` 与 `may_create`
是现成的；`may_terminate` 是桩。

- **[`may_terminate`]**——现在能否再走一个旧 Pod：这个 Pod 必须存在，而且它离开之后仍要有至少
  `available_floor(replicas, max_unavailable)` 个就绪。

## 完成标准

- `kiln run platform/9.2-rollout` —— 规格通过
- `kiln check platform/9.2-rollout` —— 每个 must 闸门都是绿的
- `maxUnavailable: 0` 时三个 Pod 会一直是三个，直到第四个就绪；`maxUnavailable: 1` 时立刻可以走一个

## 陷阱

1. **忽略就绪。** 因为 Pod 存在就算它可用：新 Pod 被创建、旧 Pod 离开，而新 Pod 还没通过就绪探针
   ——这道算术本该禁止的缺口。
2. **下限用 `>=` 的反面。** 结果**等于**下限时就可以走，而不是要求停在下限之上：三个副本、
   `maxUnavailable: 1` 可以以两个就绪运行，而要求三个会把发布卡在第一步。
3. **创建越过 surge。** `may_create` 是另一个预算；只检查下限的循环会一直开 Pod，直到集群拒绝。
4. **比工作负载还大的预算。** 三个副本上的 `maxUnavailable: 9` 不意味着可以逐出九个；上限是存在的
   Pod 数。
