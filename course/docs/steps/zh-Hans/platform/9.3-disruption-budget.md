# 预算为零是告警，不是安全

## 为什么

PodDisruptionBudget 是工作负载在集群做*自愿*工作（节点排干、升级、自动伸缩的合并）时对自己的承诺。
同一个数字有两种写法——`minAvailable`（至少留这么多）与 `maxUnavailable`（最多走这么多）——两个方向
的算术是一样的。

有意思的是边界：

- **允许零次逐出的预算会挡住每一次排干。** 它不是安全措施，是一个永远排不掉的节点，而告警应该在
  有人升级时才发现它之前就响起来；
- **比工作负载还大的预算变不出 Pod。** 三个副本上的 `maxUnavailable: 9` 只允许三个，因为只有三个；
- **下限不能低于零。** `minAvailable` 大于副本数是配置错误；答案是零次允许，不是负数。

## 任务

脚手架加上了 `src/budget.rs` 和它的 `pub mod budget;` 那一行。

- **[`allowed`]**——一次能逐出几个 Pod：第一种写法是 `replicas - minAvailable`，第二种是
  `maxUnavailable`，两者都以 `replicas` 封顶，且永远不低于零。

## 完成标准

- `kiln run platform/9.3-disruption-budget` —— 规格通过
- `kiln check platform/9.3-disruption-budget` —— 每个 must 闸门都是绿的
- 五个副本的 `minAvailable: 2` 允许三个；`minAvailable: 5` 允许零个；两个副本的 `maxUnavailable: 9`
  允许两个

## 陷阱

1. **同时写 `minAvailable` 与 `maxUnavailable`。** Kubernetes 会拒绝这份清单，而这里的模型只有一个
   预算：API 的回答是"选一种写法"，不是"加起来"。
2. **负的下限。** 无符号整数上的 `replicas - minAvailable` 会回绕：算术必须饱和，否则一个配置错误
   变成"逐出一切"。
3. **把零当成安全。** 零次允许逐出意味着排干会挂住；这个数字是一个信号，而这一步的职责是把它正确
   地算出来，让告警能据此行动。
4. **封顶封错了对象。** 上限是副本数，不是缩容之后的期望数：预算说的是现在存在的 Pod。
