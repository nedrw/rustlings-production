# Runbook 与第一次故障演练

## 为什么

二十一步造出了一个会记日志、会计数、会重试、会排干、还能打成镜像的服务。但没有一步造出那样东西——它决定凌晨
三点发生什么：订阅者写信说"我从没收到链接"，值班的人必须回答两个问题：**这是我们这边的事吗，该怎么办？**
那就是 runbook——而它不是文档。文档描述一个正常运转的系统；runbook 是写给一个不正常系统的操作说明，作者是看着
它出过故障的人。

两个决定塑造了这一步，而两者都能把 runbook 写得比没有还糟：

1. **不能重放的 runbook 只是散文。** "检查邮件服务器是否可达"是一句没人能测的话。runbook 里每一步都得是人能
   *做*、然后能*看*到结果的东西，而开头那句承诺必须能被一条命令检查——所以这一步的交付物先是演练，然后才是页面。
   那条命令就是事故中响应者会敲的同一条，于是页面和证据不会各走各的；
2. **不会失败的演练只是装饰。** 下面的演练重放一次故障，并报告有没有邮件丢失。对着"会恢复"的邮件服务器跑，它
   说*什么都没丢*——而一个对*任何*世界都这么说的演练，是一盏接在空处的绿灯。所以演练必须跑两遍：一遍故障结束，
   一遍邮件服务器再也不回来。第二遍才让第一遍成为证据，而它恰恰就是 runbook 存在的那个场景。

**这一步坦承的地方**：演练是对着 `mailer/1.13-email-port` 步的进程内适配器重放故障，不是对着容器。代价是少了
SMTP 那段对话——`mailer/1.19-test-layering` 步才是练它的地方——换来的是：一次故障在笔记本上、几秒钟内回放完，
不需要邮件服务器，用的还是响应者会敲的那条命令。队列、认领、重试预算和数据库都是真的，而这句承诺正是关于这些的。

## 任务

脚手架放了两个文件，每个都带着一个另一个填不上的洞：

### `tests/support/drill.rs`——演练

它已经会用一个拒绝每条消息的邮件服务器启动服务（`Recording::fail_with`，`mailer/1.13-email-port` 步），注册
一个订阅者，并给出一个 `Report`。它不做的是向服务问任何东西：`replay(Recovery::Never)` 的回答和
`replay(Recovery::ComesBack)` 一模一样，因为 `Report` 是在文件里定死的，不是从服务量出来的。规格里第二个测试
就是察觉这件事的那个。

把它变成演练，要按顺序做四件事：

1. **恢复有意义之前，故障得是真的。** 等到*第一次尝试失败*——消息已经递给邮件服务器、没被收下——再让服务器
   回来。抢在故障之前的恢复，什么也证明不了；
2. **恢复服从演练的参数**：`Recovery::ComesBack` 让发送器重新放行（`Recording::clear_failure`），
   `Recovery::Never` 不放行，而同一条代码路径要能处理两者。服务的重试预算是几百毫秒内的三次尝试
   （`backoff`，`mailer/1.14-worker` 步），所以"永不"离"回来"只有一秒；
3. **数字来自服务。** `delivered` 是邮件服务器收下的；`given_up` 是服务放弃发送的——那一行 `confirmation_sent_at`
   仍旧空着，尝试次数已耗尽。问数据库才是重点：一个报告"我安排发生了什么"的演练，测的是演练自己；
4. **等一个事实，而不是等若干秒。** 脚手架在 sleep；演练要轮询，直到队列动了或者死线到了。sleep 在负载机器上
   太短，在空闲机器上是白等，两者都不是关于队列的陈述。

### `docs/runbook.md`——那一页

骨架里有事故需要的五个小节，也是响应者按顺序读的标题：

- **症状**——最先被注意到的、从外面看到的东西；
- **信号**——看什么、在哪儿看。这里要紧的是 `deliveries_total{outcome="given_up"}`（`mailer/1.20-metrics`
  步）：那个数字意味着*有个订阅者再也收不到我们的信*。`failed` 在动是正常的（重试）；`given_up` 不是；
- **步骤**——按顺序做什么，包括那条反直觉的指示：*重启这个服务没有用*，因为队列住在数据库里，被认领的消息会
  释放给下一次尝试；
- **验证**——"恢复了"是什么意思，以及重放演练的那条命令；
- **升级**——邮件服务器今天不会回来时怎么办。队列有界，所以邮件*确实会*被放弃；诚实的选择是停止接收注册，并且
  说清楚。

`links` 闸门会跑这一页（以及项目里其他每一个 markdown 文件）：相对目标必须存在、`#锚点` 必须对得上一个标题、
本该是目标的 `TODO` 算失败。**一个指向谁也打不开的文件的 runbook，是在第一次事故里就会被放弃的 runbook**——
所以这道闸门是结构性的、离线的，而不是一个要上网的链接检查器（plan §6）。

### 规格判什么

| the test | the claim |
| --- | --- |
| `the_drill_reports_the_promise_kept_when_the_server_comes_back` | 重放期间消息被接受、服务器回来了、什么都没丢 |
| `the_drill_reports_the_loss_when_the_server_never_comes_back` | 同一次重放，服务器永远不在，报告损失并数出放弃了什么——演练是会失败的 |
| `the_runbook_names_its_sections_the_drill_and_the_signal` | 页面有 Symptoms/Signals/Steps/Verification/Escalation，点名 `spec_runbook_drill`，并点名那个"邮件正在被放弃"的信号 |

## 完成标准

- `kiln run mailer/1.22-runbook` — 规格通过（两次重放，加上页面的结构）
- `kiln check mailer/1.22-runbook` — 每个 must 闸门都是绿的，含 `links`：没有遗留的占位目标，每个相对目标都能
  解析
- `cargo test --test spec_runbook_drill` 是一条你愿意在事故中执行的命令，而且几秒内跑完
- 页面按顺序告诉响应者：他在看什么、去哪儿看、做什么、怎么知道起作用了、不起作用时叫醒谁
- 你自己重放过一次 `Never`，并且亲自读过它的报告

## 陷阱

1. **一个永远通过的演练。** 对任何世界都回答 `delivered == accepted, given_up == 0` 的 `replay`，是书面演练最
   常见的形状，而且比没有演练更糟：它把一次事故变成"演练是绿的，那大概是别的地方"。去跑第二种情况；规格就在跑，
   而它只在第一次显得昂贵。
2. **报告你安排发生的事。** 一个断言*发送器*记录的演练，证明的是适配器能工作。承诺是关于服务自己的记录的——
   那一行、它的尝试次数、它有没有发出去——报告必须从那里量。
3. **用 sleep 代替等待。** `thread::sleep(500ms)` 是第二常见的形状。它在空闲机器上是最快的一次绿灯，在负载机器上
   是 flake，而且它教会读者：这个服务是一台有时间的机器，而不是一个有状态的机器。
4. **照着实现写页面。** 读着 `src/` 写出来的 runbook，会罗列设置项和代码路径，而那恰恰是凌晨三点响应者*用不上*
   的东西。从会把你叫起来的告警写起，然后去确认那条告警存在。
5. **指向不存在之物的页面。** `links` 闸门存在，是因为 runbook 会腐烂：文件改名、小节搬走、看板链接留成
   `TODO`。闸门执行的规则，正是该照着写的规则：**每个目标要么是本项目里的文件，要么是别人维护、而你会定期复查的
   URL**。
6. **把升级当成补丁。** "联系团队"不是升级。下一个人需要的是：你已经排除了什么、你看到了什么、你把哪个决定交给
   他——包括那个没人喜欢的：停止接收注册，因为队列有界。
7. **以为演练覆盖了真的邮件服务器。** 它重放的是队列，不是 SMTP。当事故出在协议层（TLS、认证、限流），演练照样
   绿着，而信一封都不到——`mailer/1.19-test-layering` 步是回答这些问题的那一层，而陷阱 1 是你分辨这两者的理由。
