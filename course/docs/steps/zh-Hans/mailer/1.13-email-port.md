# 邮件端口与一个假实现

## 为什么

确认邮件是这个服务第一件不是它自己说了算的事。此前的一切都在进程里：解析一个地址、写一行数据、签发一个
令牌。而发信要跟一个自己控制不了的东西打交道——跟这种东西打交道，通常的写法就是哪儿要就在哪儿调用：

```rust
smtp::send(&config.smtp, &email, subject, body)?;   // wherever it is needed
```

这一行看似只是发信，其实也决定了*测试*怎么写。从此每个注册测试要么需要一台 SMTP 服务器，要么需要一个
把这次调用拆开、回 `Ok(())` 的 mocking 框架——而一个"通过与否全看某个替身被安排成什么样"的测试，说到底是
自己跟自己点头。这一步换个写法，把依赖写成一个**端口**：

- **服务认的是 trait，不是客户端**：`EmailSender` 只说明*一条消息要送到某处*，跟 SMTP、主机、凭据都无关。
  处理函数向状态要*一个能发东西的东西*，把消息交给它；
- **适配器才是世界所在的地方**：`Logging` 是这次构建跑的那个——T1 到第 `mailer/1.19-test-layering`
  步才有邮件服务器，所以今天一条消息就是一行日志，而同一个端口之后会长出一个真的适配器，处理函数不用改；
- **假实现是你自己的代码，不是一个要配置的库**：`tests/support/email.rs` 记下收到的每条消息，也能被要求
  失败。整个假实现就这么多——没有期望 DSL、没有 "verify"，要它失败只是*构造时传个参数*，不是什么 mocking
  戏法。它真出错时，错在一个你读得到的文件里。

端口一立起来，还有个地方特别容易做错：**邮件服务器掉线，不等于注册失败**。行已经写了，地址是好的，订阅者
就在库里，缺的只是一封信。此时回 `500`，等于扔掉一个已经到手的地址；而敲下它的人会再试一次，然后被告知
"你已经订阅过了"。这个失败今天只落一行日志，到 `mailer/1.14-worker` 步才变成重试——但*策略*（订阅者留下，
发送不改变答案）是在这一步定的。

## 任务

脚手架加了 `src/email.rs`（消息类型、端口、日志适配器、两个常量），还有 `tests/support/email.rs`——规格
用的记录型假实现。缺的是接缝、那条消息，以及那条策略。

### `src/lib.rs`

声明模块：`pub mod email;`。

### 消息：`src/signup.rs` 里的 `confirmation_message`

端口对"订阅"一无所知，所以那封确认信要在订阅者这边构造：

```rust
pub fn confirmation_message(to: Email, token: &Token) -> Message
```

正文必须带上链接，而令牌必须是**表里存的那个**：

```text
{CONFIRMATION_BASE_URL}/confirm?token={token.as_str()}
```

主题取 `CONFIRMATION_SUBJECT`（两个常量都在 `src/email.rs`），收件人是解析过的地址——表里存的那个，不是
调用方敲进来的文本。

### 接缝：`src/http.rs`

状态里放的是端口，不是适配器：

- `AppState` 增加 `sender: Arc<dyn EmailSender>`；
- `AppState::start(config, id)` 签名不动，内部用 `Logging` 造状态——二进制（`src/main.rs`）一行都不用改；
- `AppState::start_with_sender(config, id, sender: Arc<dyn EmailSender>)` 是同样的启动顺序，把发送器当作
  参数，而 `start` 是对它的一行调用；
- `AppState::sender()` 把处理函数需要的东西交给它。

这个构造函数故意公开：想要假实现的测试装置是库看不见的 crate，用参数把它递进来是唯一诚实的办法。它也不是
"仅供测试"的路径——接了第二个适配器的部署，同样用它来选。

### 发送：`src/signup.rs`

`subscribe` 多收一个发送器（顺序是 `pool`、`sender`、`request`），并且**只有在取回一行之后**才发（插入
赢了，这个地址就归这个订阅者）：

1. 构造消息；
2. 交给发送器；
3. 发不出去就记日志——写清原因和收件人——然后**让注册照常成功**。

对已被占用地址的第二次注册回 `409`，并且一封都不发：给已订阅的人再发信，等于递过去一个什么都不确认的
链接——而在*不是*订阅者的人眼里，那正好是要当钓鱼举报的东西。

### 规格判什么

| the test | the claim |
| --- | --- |
| 一次注册 | 恰好一条消息，发给存储的地址，body 带着 `/confirm?token=<行里的那个令牌>` |
| 同一个地址再来 | `409`，没有第二条消息 |
| 一个拒绝的发送器 | `201`，行仍然是 `pending`，一次尝试，没有投递 |
| 一个恢复的发送器 | 下一次注册被投递，而失败的那一次不会被这一步重试 |
| 每一个适配器 | `Logging` 与假实现都能收下一条可投递的消息；假实现可以被弄成拒绝 |

## 完成标准

- `kiln run mailer/1.13-email-port` — 规格通过
- `kiln check mailer/1.13-email-port` — 每个 must 闸门都是绿的
- 通过运行中的服务做一次注册，记下一条 `an email would be sent` 日志行，带地址和主题——不带 body，因为
  它带着令牌
- 在发送器被告知要失败时的一次注册仍然回 `201`，并把订阅者留在 `pending`
- `cargo test --lib` 通过：端口、适配器与消息仍然彼此吻合

## 陷阱

1. **让发送决定答案。** 在 `subscribe`（或处理函数）里写 `sender.send(...).await?`，等于把邮件服务器离线变
   成 `500`——可对这个订阅者，服务*已经*写下一行了。规格那句 *"a mail server that is away is not a signup
   that failed"* 说的就是这个，而那一行还摆在那儿当证据。
2. **先发信后插入。** 链接正是新订阅者要的，于是很容易先把信构造好发出去——然后对已被占用地址的第二次注册，
   就把确认链接寄给了一个已经订阅的人。规格那句 *"the second signup must not email anybody"* 会显示成两条
   已投递的消息。
3. **把适配器存进去。** `AppState` 里的 `sender: Arc<Logging>` 能编译，通过每一个没有注入的测试，并悄悄
   地把接缝去掉：下一个需要失败的测试终究得去拿一个 mocking 框架。这个字段的类型就是整个设计。
4. **trait 里写 `async fn`。** `fn send(&self, message: Message) -> impl Future<...>` 是现代写法，可它没
   法通过 `dyn EmailSender` 调用，而状态持有的正是后者。脚手架里的签名因此把 future 装箱——每条消息一次
   分配，这就是接缝的代价（不想手写的话，`async-trait` 自动做这个变换）。
5. **把整条消息记进日志。** 日志适配器里写 `info!(?message, …)` 看着挺方便，可它把确认链接——也就是令牌
   ——写进了日志行。适配器只记信封（收件人和主题）；密钥该住在 body 里。
6. **base URL 只做了一半的决定。** `CONFIRMATION_BASE_URL` 在这一步是个常量，可这服务只要部署到任何地方，
   它就是个*设置项*：邮件里指向 `localhost` 的链接，没人点得动。别在硬编码的链接旁边留一句"以后该做成
   配置"——要么是你想清楚了的常量（像这里），要么就照 `mailer/1.4-config` 步造其他设置项的方式，把它造成
   设置项。
7. **假实现不像真货。** 假实现必须跟适配器答得一样：收下消息 `Ok(())`，没收下 `Err(SendError)`，消息类型
   也相同。回别的东西、或者把失败吞掉的假实现，早晚会让一个真适配器过不了的测试通过。规格最后那个测试对
   每个适配器跑同一份契约，就是为这个。
8. **忘了它还在请求里。** 今天发送就发生在 `POST /signup` 当中，所以邮件服务器一慢，注册就慢——这是故意的：
   队列和 worker 是 `mailer/1.14-worker` 步的事，而这一步做的是它们要用的那个接缝。分清眼前是哪一个，
   就是"一个取舍"和"一个 bug"的差别。

## 延伸阅读

- [Alistair Cockburn: hexagonal architecture](https://alistair.cockburn.us/hexagonal-architecture/) —
  这一步是它一个实例的那张"端口与适配器"图，出自给它起名的人
- [Martin Fowler: test doubles](https://martinfowler.com/bliki/TestDouble.html) — 假实现坐在 stub、spy
  与 mock 之间的哪个位置，以及为什么"fake"是那个不检查你调用的
- [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html) 与
  [`Pin`](https://doc.rust-lang.org/std/pin/index.html) — 为什么一个返回 `impl Future` 的 trait 方法
  过不了 `dyn`，以及装箱它的代价
- [`async-trait`](https://docs.rs/async-trait/latest/async_trait/) — 替你写下装箱签名的那个宏，以及它
  所做的转换（即使这一步手写，也值得读一遍）
- [`axum::extract::State`](https://docs.rs/axum/latest/axum/extract/struct.State.html) — 为什么状态必须是
  一个具体类型，而那正是把 trait object 逼出来的原因
- [tracing](https://docs.rs/tracing/latest/tracing/) — 字段里的 `?value` 对 `%value`，以及"记录信封"
  与"记录密钥"的区别在实践中是怎么做出来的
