# 邮件端口与一个假实现

## 为什么

一封确认邮件是这个服务第一件不是它自己的事。到目前为止一切都在进程内部：一个它解析的地址、一行它写的
数据、一个它签发的令牌。发信意味着和一个它不控制的东西说话——而和一个你不控制的东西说话，通常的写法是
在需要它的地方写下那次调用：

```rust
smtp::send(&config.smtp, &email, subject, body)?;   // wherever it is needed
```

那一行既是一个关于*测试*的决定，也是一个关于邮件的决定。现在每一个注册的测试都需要一个 SMTP 服务器，
或者一个把那次调用拆开、回答 `Ok(())` 的 mocking 框架——而一个"通过与否取决于某个替身被告知真货会
怎么做"的测试，是一个自己同意自己的测试。这一步把依赖写成一个**端口**：

- **服务认识的是一个 trait，不是一个客户端**：`EmailSender` 说的是*一条消息去某个地方*，与 SMTP、主机、
  凭据都无关。处理函数向状态要*一个能发东西的东西*，并交给它一条消息；
- **适配器才是世界所在的地方**：`Logging` 是这次构建跑的那个——T1 到第 `mailer/1.19-test-layering`
  步才有邮件服务器，所以今天一条消息就是一行日志，而同一个端口之后会长出一个真的适配器，处理函数不用改；
- **假实现是你拥有的代码，不是你要配置的库**：`tests/support/email.rs` 记下它收到的每一条消息，并且能被
  告知去失败。这就是全部的假实现——没有期望 DSL、没有 "verify"，失败注入是一个*构造参数*而不是某种
  mocking 把戏。假实现错的时候，它错在一个你能读的文件里。

然后是端口一旦存在就容易做错的那部分：**一个离线的邮件服务器不是一个失败的注册**。行写下了、地址是好的、
订阅者存在了；缺的是一条消息。在这里回 `500` 的服务，扔掉了它已经拿到的一个地址，而输入它的人会再试一次，
然后被告知自己已经订阅过了。这个失败今天是一行日志，第 `mailer/1.14-worker` 步才是它变成一次重试的地方
——但*策略*（订阅者留下，发送不改变答案）在这里决定。

## 任务

脚手架加了 `src/email.rs`——消息类型、端口、日志适配器和两个常量——以及 `tests/support/email.rs`，规格用的
记录型假实现。缺的是那个接缝、那条消息，以及那条策略。

### `src/lib.rs`

声明模块：`pub mod email;`。

### 消息：`src/signup.rs` 里的 `confirmation_message`

端口对订阅一无所知，所以确认一封订阅的邮件在订阅者所在的地方构造：

```rust
pub fn confirmation_message(to: Email, token: &Token) -> Message
```

body 必须带上链接，而令牌必须是**行里那个**：

```text
{CONFIRMATION_BASE_URL}/confirm?token={token.as_str()}
```

主题是 `CONFIRMATION_SUBJECT`（两个常量都在 `src/email.rs` 里），收件人是解析过的地址——行里存的那个值，
不是调用方输入的文本。

### 接缝：`src/http.rs`

状态携带的是端口，不是适配器：

- `AppState` 增加 `sender: Arc<dyn EmailSender>`；
- `AppState::start(config, id)` 保持签名，用 `Logging` 构造状态——二进制（`src/main.rs`）完全不用改；
- `AppState::start_with_sender(config, id, sender: Arc<dyn EmailSender>)` 是同样的启动顺序，把发送器当作
  参数，而 `start` 是对它的一行调用；
- `AppState::sender()` 把处理函数需要的东西交给它。

这个构造函数有意是公开的：想要假实现的装置是一个库看不见的 crate，所以参数是唯一诚实的引进方式。它不是一条
仅供测试的路径——带第二个适配器的部署用同样的方式挑它。

### 发送：`src/signup.rs`

`subscribe` 收发送器（按 `pool`、`sender`、`request` 的顺序），并且**只在拿回一行之后**（插入赢了，所以
这个地址属于这个订阅者）：

1. 构造消息；
2. 交给发送器；
3. 如果它失败，记日志——带上原因，带上它是发给谁的——然后**让注册照常成功**。

对一个已被占用的地址的第二次注册回 `409` 并且什么都不发：发给一个已经订阅的人的邮件，是一个什么都不确认
的链接，而它恰恰是*不是*订阅者的那个人会当作钓鱼来举报的那种消息。

### 规格判什么

| the test | the claim |
| --- | --- |
| 一次注册 | 恰好一条消息，发给存储的地址，body 带着 `/confirm?token=<行里的那个令牌>` |
| 同一个地址再来 | `409`，没有第二条消息 |
| 一个拒绝的发送器 | `201`，行仍然是 `pending`，一次尝试，没有投递 |
| 一个恢复的发送器 | 下一次注册被投递，而失败的那一次不会被这一步重试 |
| 每一个适配器 | `Logging` 与假实现都能收下一条可投递的消息；假实现可以被弄成拒绝 |

## 完成标准

- `kiln run mailer/1.13-email-port` — 规格通过
- `kiln check mailer/1.13-email-port` — 每个 must 闸门都是绿的
- 通过运行中的服务做一次注册，记下一条 `an email would be sent` 日志行，带地址和主题——不带 body，因为
  它带着令牌
- 在发送器被告知要失败时的一次注册仍然回 `201`，并把订阅者留在 `pending`
- `cargo test --lib` 通过：端口、适配器与消息仍然彼此吻合

## 陷阱

1. **让发送决定答案。** 在 `subscribe`（或处理函数）里写 `sender.send(...).await?`，会把一个离线的邮件
   服务器变成一个 `500`——而对这个订阅者，这个服务*已经*写下了一行。规格的 *"a mail server that is away
   is not a signup that failed"* 就是那个失败，而那一行还在那里作为证据。
2. **在插入之前发送。** 链接正是新订阅者需要的，所以先构造并发送很诱人——然后对已被占用地址的第二次注册，
   就给一个已经订阅的人发了确认链接。规格的 *"the second signup must not email anybody"* 把它显示成两条
   已投递的消息。
3. **把适配器存进去。** `AppState` 里的 `sender: Arc<Logging>` 能编译，通过每一个没有注入的测试，并悄悄
   地把接缝去掉：下一个需要失败的测试终究得去拿一个 mocking 框架。这个字段的类型就是整个设计。
4. **trait 里的 `async fn`。** `fn send(&self, message: Message) -> impl Future<...>` 是现代写法，却
   没法通过 `dyn EmailSender` 调用，而状态持有的正是后者。脚手架里的签名因此把 future 装箱；每条消息一次
   分配就是接缝的代价（而 `async-trait` 恰好自动做这个转换，如果你不想手写）。
5. **把消息记进日志。** 日志适配器里的 `info!(?message, …)` 看起来有用，却把确认链接——令牌——写进了一行
   日志。适配器记信封（地址与主题）；body 才是密钥的家。
6. **一个只做了一半决定的 base URL。** `CONFIRMATION_BASE_URL` 在这一步是一个常量，而这个服务一旦部署到
   任何地方，它就是一个*设置项*：邮件里指向 `localhost` 的链接是没人能点的链接。不要在一个硬编码的链接
   旁边留一句"这里该做成配置"——要么是一个你认真的常量，像这里；要么是一个按第 `mailer/1.4-config` 步
   构造其他设置项的方式构造出来的设置项。
7. **一个不像真货的假实现。** 假实现必须与适配器回答得一样：消息被收下时 `Ok(())`，没有被收下时
   `Err(SendError)`，同一个消息类型。返回别的东西、或者吞掉失败的假实现，是一个终有一天会在真适配器失败的
   测试上通过的假实现。规格里最后那个测试对每一个适配器跑同一份契约，正是为此。
8. **忘了这仍然在请求里。** 发送今天发生在 `POST /signup` 内部，所以一个慢的邮件服务器会让注册变慢——
   这是有意的，因为队列与 worker 是第 `mailer/1.14-worker` 步，而这一步是它们将使用的那个接缝。分清你正
   看着的是这两者中的哪一个，是"一个取舍"与"一个 bug"之间的区别。

## 延伸阅读

- [Alistair Cockburn: hexagonal architecture](https://alistair.cockburn.us/hexagonal-architecture/) —
  这一步是它一个实例的那张"端口与适配器"图，出自给它起名的人
- [Martin Fowler: test doubles](https://martinfowler.com/bliki/TestDouble.html) — 假实现坐在 stub、spy
  与 mock 之间的哪个位置，以及为什么"fake"是那个不检查你调用的
- [`Future`](https://doc.rust-lang.org/std/future/trait.Future.html) 与
  [`Pin`](https://doc.rust-lang.org/std/pin/index.html) — 为什么一个返回 `impl Future` 的 trait 方法
  过不了 `dyn`，以及装箱它的代价
- [`async-trait`](https://docs.rs/async-trait/latest/async_trait/) — 替你写下装箱签名的那个宏，以及它
  所做的转换（即使这一步手写，也值得读一遍）
- [`axum::extract::State`](https://docs.rs/axum/latest/axum/extract/struct.State.html) — 为什么状态必须是
  一个具体类型，而那正是把 trait object 逼出来的原因
- [tracing](https://docs.rs/tracing/latest/tracing/) — 字段里的 `?value` 对 `%value`，以及"记录信封"
  与"记录密钥"的区别在实践中是怎么做出来的
