# Postgres 与迁移：一个空数据库，在开始服务之前先跟上版本

## 为什么

到这一步为止，服务还是无状态的：读一次配置，写写日志，HTTP 接口应答完就结束。一旦它开始留住任何
东西，三个问题会同时冒出来——它们就是这一步的内容：

- **schema 从哪来？** 别指望某个守着 `psql` 窗口、旁边还摊着一页 wiki 的人——一个空数据库得自己变成
  代码期望的样子，全程没人插手。这就是*迁移*：schema 也是代码，有版本、要评审、由服务自己应用。
- **哪个产物拥有它？** `sqlx::migrate!` 在编译期把 `migrations/` 嵌进二进制（这一步打开 `macros`
  特性正是为了它）。交付的构建把 schema 和读它的代码放在同一个文件里，于是容器镜像不可能跑错那一对。
- **先做哪一步？** 连接、迁移，最后才绑定套接字。schema 还没到位就开始接请求的服务，等于用 500 应答
  其中一部分人。

还有第四个问题，只在出事那天才被想起：**"进程还活着"等于"服务还能用"吗？** 不等于。`/healthz` 回答的
是进程，`/readyz` 回答的是一个请求需要的东西——而这一步之所以引入这个区别，是因为服务第一次*有了*一个
可能进程还在、它却先掉了的依赖。

本 track 余下的全部从这里开始。1.10–1.18 在你现在写的 schema 上增加表和查询，从这里往后的每个测试
都有自己的数据库，而数据库的配置方式一直不变，直到最后一步：`MAILER__DATABASE__URL`，或者
`mailer.toml` 里的 `database.url`。

## 任务

脚手架加了 `sqlx` 依赖和三个文件，没有任何行为：`src/db.rs` 只有 `Database` 的形状，函数体什么都证明
不了；`migrations/0001_subscribers.sql` 只有命名规则和别的什么都没有；`tests/support/postgres.rs` 是
规格用的容器加 `psql` 装置。你的工作是它们之间的代码与 schema。

### schema：`migrations/0001_subscribers.sql`

为 1.10–1.18 要建立其上的那张表写一条 `CREATE TABLE`。名字与类型是契约的一部分（规格会向
`information_schema` 询问这些列）：

| column | type | notes |
| --- | --- | --- |
| `id` | `BIGSERIAL PRIMARY KEY` | |
| `email` | `TEXT NOT NULL UNIQUE` | 第 1.11 步会在这条约束上让两次注册相撞 |
| `name` | `TEXT NOT NULL` | |
| `password_hash` | `TEXT NOT NULL` | 永远不是密码本身：第 1.11 步先做哈希 |
| `status` | `TEXT NOT NULL DEFAULT 'pending'` | `CHECK (status IN ('pending', 'active', 'unsubscribed'))` |
| `confirmation_token` | `TEXT UNIQUE` | 可空：只有等待确认的订阅者才有 |
| `confirmation_expires_at` | `TIMESTAMPTZ` | 可空，供第 1.12 步 |
| `confirmed_at` | `TIMESTAMPTZ` | 可空 |
| `subscribed_at` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | 服务自己的记账 |

再加一条跨列规则：`CHECK (status <> 'active' OR confirmed_at IS NOT NULL)`——没有人未经确认就是激活
状态。在收紧它之前先读 TRAP 一节；这条约束那个看起来显然的写法会弄坏第 1.18 步。

文件名就是版本：`sqlx` 按 `0001_`、`0002_`……排序，并把它应用过的东西记在 `_sqlx_migrations` 里。
**一条在任何地方跑过的迁移永远不再修改**——改 schema 的方式是加下一个文件。

### `src/db.rs`：连接、迁移、就绪

- **`Database::connect(url)`** 建连接池（`MAX_CONNECTIONS`、`ACQUIRE_TIMEOUT`），并且**在返回之前
  真的建立一条连接**。这里用 `PgPoolOptions::connect_lazy` 是错的，规格也是这么说的：一个还没和它
  的数据库说过话的服务，没法知道自己能不能服务。
- **`Database::migrate()`** 对池跑 `sqlx::migrate!("./migrations")`。每次启动都跑、两个进程同时跑
  都是安全的——`sqlx` 会加锁并记录——而且它不是可选的：正是它让一个空数据库变成这次构建期望的 schema。
- **`Database::ready()`** 向数据库问一个只有迁移后的 schema 才能回答的问题（`SELECT 1 FROM
  subscribers LIMIT 1` 就是一个），**每次调用都问**。它把失败作为错误报告而不是一个 `false`，因为
  原因要进日志，而探针只回一句话。
- **`Database::pool()`** 把池交出去，供后面的步骤加查询。

### `src/error.rs`：两个新的失败

`Error::Database { operation, source }`（"数据库无法 `connect`/`readiness`"）与
`Error::Migration { source }`（"schema 无法被带到最新"）。两个都是部署方要修的：退出码 `1`，和配置
坏掉时一样，理由也一样——调用方没有做错什么，重跑同一条命令也不会好。

### `src/http.rs`：状态、启动顺序与就绪

- **状态带着数据库**：`AppState { config, database: Option<Database> }`，由 **`AppState::start(config,
  id)`** 构造——启动顺序只住在一个地方（配置 → 日志 → 连接 → 迁移 → 一个状态），二进制*和*测试装置
  都用它。`router` 与 `serve_on` 收状态而不是只收配置。
- **配了数据库就必须能用；没有数据库是一种选择。** 如果 `database.url` 设了而连接或迁移失败，
  `AppState::start` 返回错误、进程退出——在绑定任何东西之前。如果没设，服务照常启动并在 `warn`
  级别说出来：1.4–1.8 依然成立，而 `/readyz` 是说出真相的那一个。
- **`GET /readyz`**：数据库能应答时 `200` 带一个 JSON 体；没有数据库或不应答时 `503`。体里始终是
  客户端可以据以分支的一句话——*为什么*是这次部署自己的事，它进日志、级别 `warn`。`/healthz` 无论如何
  都继续回 `200`：因为数据库离线就重启一个健康的进程，不是修法。

### `src/main.rs` 与 `tests/support/mod.rs`：同一个顺序，写两遍

二进制在日志之后构造状态并服务它；工厂在它自己的线程里构造同一个状态，**在**把 listener 交给运行时
*之前*，于是一个构造不出来的状态会让测试以"连接被拒"和一句话失败，而不是一个永远不应答的请求。两者都
调用 `AppState::start`——把这个序列写两遍，正是两者分头漂移的方式。

### 真的跑一遍

规格会起它自己的容器，所以第一次运行之前先把镜像拉一次：

```sh
kiln images                 # what the steps need, and what is already here
kiln images pull            # fetch what is missing (mirror-aware: KILN_REGISTRY_MIRROR)
```

然后把一次*手动*运行指向你自己的数据库——这个练习的重点就是看迁移真的发生：

```sh
podman run -d --name pg -e POSTGRES_PASSWORD=postgres -p 127.0.0.1:5432:5432 postgres:17-alpine
MAILER__DATABASE__URL=postgres://postgres:postgres@127.0.0.1:5432/postgres cargo run -p mailer
# ... then, in another shell:
psql "postgres://postgres:postgres@127.0.0.1:5432/postgres" -c '\d subscribers'
```

## 完成标准

- `kiln run mailer/1.9-postgres` — 规格通过（先让 `kiln images` 绿，否则装置会告诉你哪条命令用来拉
  镜像）
- `kiln check mailer/1.9-postgres` — 每个 must 闸门都是绿的，包括 `images`
- 一个空着启动的数据库，在一次启动之后就是上面的 schema，而第二次启动什么都不改
- 把 `MAILER__DATABASE__URL` 指向一个没人监听的端口启动，几秒内以 `1` 退出，附一句点名数据库的话，
  且从不开始服务
- 完全没有 `MAILER__DATABASE__URL` 时服务启动，`/healthz` 是 `200`，`/readyz` 是 `503`
- 任何地方都没有数据库时 `cargo build` 也能过：`migrate!` 在编译期把文件嵌进去，运行时什么都不需要

## 陷阱

1. **`connect_lazy`。** 连接池只是被描述、没有被打开，于是数据库没了服务也能高高兴兴地启动——而规格
   的 *"the service was still running after 10s"* 就是这个缺陷从外面看到的样子。证明它的是 `connect`。
2. **在迁移之前绑定。** 先服务、把迁移放进后台任务，第一批请求就会在 schema 存在之前到达。顺序就是
   这一步：连接、迁移，*然后*绑定。规格看不见你的顺序；它看见的是一个在 `subscribers` 还不存在时就说
   自己就绪的服务。
3. **那个显然的约束。** `CHECK ((status = 'active') = (confirmed_at IS NOT NULL))` 看起来是同一条规则，
   其实更强：它禁止把任何确认过的人退订，而第 `mailer/1.18-authz-boundary` 步必须做这件事。
   `status <> 'active' OR confirmed_at IS NOT NULL` 只说了这个服务的意思：激活意味着已确认。
4. **把就绪记下来而不是问出来。** 启动时算一个 `ready` 标志，或者用一个 `OnceCell` 包住第一次成功的
   查询，就会对一个一小时前就离开的数据库回答 `200`。规格的 *"a service that lost its database is not
   ready"* 说的就是这个。
5. **用数据库自己的话回答就绪。** 把驱动的错误——连连接串一起——粘进探针的响应体，等于把一份凭据公开
   给任何能访问 `:8080` 的人。体里说 *not available*；发生的事在日志里。
6. **在 `0001` 跑过之后改它。** `sqlx` 会校验每一条已应用迁移的校验和：改一条会让下一次启动以
   *"was previously applied but has been modified"* 失败，而且在每个已经拥有它的部署上。改为加
   `0002_…`。
7. **离线数据缺失时用 `query!`。** 编译期检查的宏（`sqlx::query!`、`query_scalar!`）在*编译*时需要
   活的 `DATABASE_URL`，或者一个由 `cargo sqlx prepare` 生成的 `.sqlx/` 目录。这一步有意用运行时 API
   （`sqlx::query`、`fetch_optional`），这样 crate 在任何地方都没有数据库时也能构建；宏和它们的离线
   元数据随第 `mailer/1.11-signup` 步的第一个查询一起到来。
8. **一个测试够不着、也没人找得到的容器。** 每个测试起一个容器却不设死线，意味着一个卡住的 `podman`
   会挂住 `cargo test`；起一个*共享*容器，意味着两个测试看见彼此的行。`tests/support/postgres.rs` 里的
   装置两个都不做：每个测试一个容器，每条命令都有自己的死线，`--pull=never`，于是缺失的镜像是一句话，
   而不是一次 registry 等待。
