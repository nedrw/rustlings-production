# 发布通讯：事务内写入，事务外扇出

## 为什么

此前每一条消息都只关系到一个订阅者。一期通讯却一下子关系到所有人，那是另一种形状的活：

- *写入*是一次扇出：一期内容，加上每个"欠着一份"的订阅者各一行投递记录；
- *发送*是一批彼此独立的消息，各有各的尝试、各有各的失败、各有各的幂等——`mailer/1.15-idempotent-delivery`
  步的那套，换张表再来一遍；
- 而这两件事绝不能是同一件事。一期通讯存在、却没有任何投递行，就是一期谁也收不到的通讯。反过来更糟：投递行
  指向一期根本不存在的通讯，那就没人知道原本要发生什么。

**事务**就是为这个准备的，而这也是全程第一次，事务不是可选项：

```rust
let mut transaction = pool.begin().await?;
let issue = …insert the issue…;
let copies = …insert one row per subscriber who is owed it…;
transaction.commit().await?;
```

随之而来三个决定，每个都有做错的方式：

1. **两次写就是一次写。** 在它们外面套 `BEGIN`…`COMMIT`，里面用 `?`：任何一步失败，整个回滚，数据库里绝不会
   留下"发布了一半"。而"一期只带着部分副本"这种状态，后面的步骤也修不了——没有任何东西记下缺的是哪些人；
2. **扇出发生在提交之后。** 在事务*里面*把活儿交给投递队列，等于让队列成了这次写的一方：队列一满，要么阻塞
   事务，要么把一期已经发布的通讯回滚掉。入队的应该是已经记录在案的工作，所以入队失败属于
   `mailer/1.14-worker` 步的背压——有行欠着、还没交出去——而不是丢掉这期内容的理由；
3. **谁欠一份是个查询，不是一个循环。** `INSERT … SELECT id FROM subscribers WHERE status = 'active'` 是
   一条语句，由数据库决定名单：地址从未确认过的订阅者还没证明它是自己的，而已经退订的人明确说过别再发给他。
   在 Rust 里对着一份刚读出来的列表循环，中间有个窗口，有人正好在这期间完成了确认；循环还意味着扇出变成了
   每个订阅者一次往返。

**这一步不建的东西**，也说清楚：中继（relay）。如果扇出时队列满了，那些没交出去的副本仍然是行——欠着、
记着、并且没有被任何东西捡起来，直到后面某个 track 的认领器出现。这就是不让队列参与事务的诚实代价，下面
的陷阱会点名两种把它做错的方式。

## 任务

脚手架把零件放好了，其中两处是故意写错的：

- `migrations/0004_newsletter.sql`——`issues`（带两条 `CHECK`，让空主题和空正文不可能存在）与
  `issue_deliveries`，后者的 `UNIQUE (issue_id, subscriber_id)` 就是"一行是什么"的键；
- `src/newsletter.rs`——请求、两个新的领域类型、`publish`、`fan_out`，以及单份副本的 claim / mark / release。
  **`publish` 先写通讯再写副本，外面没有事务**，而它的扇出把副本交给*每一个*订阅者，而不是已确认的那些。
  两处都从外面看得见：未确认的地址也会收到通讯；而中途失败的发布，会留下一期永远没人能收到的通讯；
- `sha2` 从 `mailer/1.16-sessions` 步起就在依赖里了，这一步的写不需要新东西。

### `src/newsletter.rs`：一次写

把两条语句包进事务：`pool.begin()`，两条都对 `&mut *transaction`，然后 `transaction.commit()`。再让数据库
回答"发给谁"这个问题——`WHERE status = 'active'`——而不是在 Rust 里遍历订阅者。

### `src/delivery.rs`：第二种任务

`Job` 变成枚举：`Job::confirmation(subscriber)` 与 `Job::issue(delivery)`，各自指向一行，而不是一条消息
（`mailer/1.15-idempotent-delivery` 步已经为第一种做过这个决定）。worker 按它分派：确认那条路认领某个订阅者
的确认，通讯那条路认领某一行投递。两边重试方式一样——每次认领一次尝试、之间 `backoff`、最多 `MAX_ATTEMPTS`
次、失败就交还——所以两个循环看着相似；把第二个写出来，别为三行策略去发明一层抽象。

### `src/http.rs`：`POST /newsletter`

- 要认证：这是订阅者的一个动作，所以它读 `mailer/1.16-sessions` 步的会话，没有就回 `401`；
- 回 `202 Accepted` 而不是 `201 Created`：*通讯*已经创建，响应写出时它就在那儿；而*发送*只是被接受，
  还没发生；
- body 说明发生了什么：通讯的 id，以及欠了多少份；
- `publish` 提交之后，`fan_out` 把副本交给队列，那儿失败就只记一行日志——不能让发布失败，因为发布才是那份不能
  被撤销的东西。

### 规格判什么

| the test | the claim |
| --- | --- |
| 一次发布 | `202` 带上份数；一期通讯；每个*已确认*订阅者一行，未确认的没有 |
| 没有会话、或者拿着一枚没人被发过的令牌发布 | `401`，什么都没写 |
| 主题为空的发布 | `400` 点名那个字段，数据库里既没有通讯也没有副本 |
| 两个已确认订阅者 | 每人恰好收到一份（见日志），每份都记为已发送，且每人恰好被认领过一次 |

## 完成标准

- `kiln run mailer/1.17-newsletter` — 规格通过
- `kiln check mailer/1.17-newsletter` — 每个 must 闸门都是绿的
- 对运行中的服务发布，回 `202` 带一个数，而这个数等于
  `SELECT count(*) FROM subscribers WHERE status = 'active'`
- `SELECT count(*) FROM issues` 与 `SELECT count(*) FROM issue_deliveries` 同进同退：没有缺副本的通讯，
  也没有无主的副本
- 服务日志里每个已确认订阅者一条 `an email would be sent`，带着这期通讯的主题；从未确认的地址一条都没有

## 陷阱

1. **两条语句假装成一条。** 脚手架的写法：先插通讯，再插副本，然后祈祷。中间一失败就是一期没有收件人的通讯
   ——而通讯本身就是*记录*，已经没东西可用来修它了。这里的事务不是性能决定，它决定的是系统会停在两种状态里的
   哪一种。
2. **队列放进事务里。** `let mut transaction = …` 后面跟一句 `queue.reserve()?`，失败就 `?`，看着整齐，却把
   背压变成了丢数据：队列一满，一期已准备好发出去的通讯就被回滚。更糟的是，提交与入队之间那个窗口，正是崩溃
   *绝不能*造成损失的地方——而把入队提前并不会消掉窗口，只是把失败模式换成了"发布被回滚"。
3. **该写查询的地方写了循环。** 对着刚读出的订阅者列表循环，意味着中间有个窗口（有人确认了，或者退订了）、
   每个订阅者一次往返，以及进程中途死掉时只扇出了一半。`INSERT … SELECT` 是一条语句、一个计划、一份名单
   ——而那份名单是数据库给的答案，不是应用的猜测。
4. **数插入的东西。** `INSERT … SELECT` 不会告诉你它插了几行，除非你问（`rows_affected`）；拿*输入*列表的
   长度去报告的扇出，就是那种在某个订阅者已被 `ON DELETE CASCADE` 删掉之后仍然回"三份"的发布。
5. **看起来对的受众。** 发给 `subscribers` 里的每一行，是脚手架犯的错，而它只在数据库里有人*不是*活跃订阅者时
   才露馅——规格的夹具恰好就是这个状态。确认才让一个地址成为某个人的；越过它发通讯，是在教人别订阅。
6. **干脆忘了扇出。** 一次发布回 `202`、什么都不入队，从外面看完美——通讯在，副本记着——而一封信都不会发出。
   规格里那条日志断言就是观察点，至于生产中这个缺口如何变得可承受，靠的是中继（T3）。
7. **把通讯当成投递。** 每个订阅者一行，才是这张表值得存在的理由：一个"这期已发送"的布尔标记，没有地方记录
   哪个订阅者的那份失败了，也没法在不给所有人重发一遍的前提下重试。

  [concurrency control](https://www.postgresql.org/docs/current/mvcc.html) — `BEGIN` 承诺什么，又不承诺
  什么（长事务就是一把一直握着的锁）

  `ON CONFLICT`，以及 `RETURNING` 能报什么、不能报什么
- [microservices.io: transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)
  — 处理"已记录"与"已入队"之间那个窗口的模式，也正是这一步点名缺失的那个中继
- [The Magical Number Seven](https://en.wikipedia.org/wiki/The_Magical_Number_Seven,_Plus_or_Minus_Two)
  — 跟数据库无关，讲的是为什么把扇出做成批（一条语句、一次入队）胜过循环，以及为什么循环的*失败模式*是相乘而
  不是相加
- [`sqlx::Transaction`](https://docs.rs/sqlx/latest/sqlx/struct.Transaction.html) — 这一步引入的类型，包括
  一个没 `commit` 就被丢弃的事务会发生什么
