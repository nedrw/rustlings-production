# 确认令牌：签发、校验、过期、一次性

## 为什么

注册只是写了一行，等于相信了"敲进这个地址的人"。可还没人证明过自己能读 `ada@example.com` 的信，所以
那一行只算一个*主张*；确认链接才是把主张变成事实的手段：服务发一封，邮箱的主人点一下，那一行从
`pending` 走到 `active`。每一步都简单，可每一种出错方式，都是"这个令牌从来就不算令牌"。

**被篡改。** 猜不到的令牌，是系统随机数生成器给出的 32 字节；它的用法是*查表*，不是验签。这个设计选择
值得停一下：改成签名（HMAC、JWT）意味着服务得保管一把密钥、定期轮换，而且**仍然**要查那一行——签名只
证明"这个令牌是我们发的"，并不说明"它没用过""它没过期"。签名换来的是彻底不用存储，而这个取舍这一步不必
做；它的代价是一把值得别人去偷的密钥，这一步不愿付。

**过期。** 一个永久有效的确认链接，就是收件箱里 2019 年那封旧信里的链接——而那个邮箱此后可能被转发、
共享、甚至泄漏过。窗口在签发时就盖好，而系统里的两个时钟（应用的和数据库的）根本不需要对齐：插入时
`now()` 写下过期时刻，更新时 `now()` 拿它比较。两处都是*数据库的* `now()`，而这是唯一不会跟自己漂移的
时钟。

**被重放。** 这一条才是令牌之所以为令牌：确认订阅者的那条语句**同时拒绝做第二次**——`status = 'pending'`
写在它的条件里，而不是之前某一刻读到的值。同一个链接点两下，或者邮件客户端为了预取发两个请求，都会落到
同一行上；数据库裁决谁改得动，另一个则被告知。反过来写——先读、再判断、再更新——两个请求都读到
`pending`，都更新，都回 200，`confirmed_at` 最终记的是*第二下*点击的时间。插入上的同一课在
`mailer/1.11-signup` 步讲过，这里讲的是更新。

调用方被告知的东西随情况不同，而这个不同就是要点：没人拿到过的令牌是 `404`（没有这样一个链接），过期的
是 `410`（那个链接没了），已经确认过的是 `409`（链接生效过一次，而这个地址不再等待任何东西），而根本
不是令牌的文本是 `400`。对所有这些回同一个状态码的服务，其支持队列就是一群在问「到底发生了什么」的人。

## 任务

脚手架加了 `src/confirmation.rs`（令牌类型、窗口、解析器，以及一个对所有人回答同一个值的 `issue`）和下面
三条语句的 `.sqlx/` 元数据。工作是确认本身，外加一个发出令牌的注册。

### `src/lib.rs`

声明模块：`pub mod confirmation;`。

### `src/confirmation.rs`

`Token::issue` 是脚手架留下的占位，而对所有订阅者都给同一个值的东西不配叫令牌——
`subscribers.confirmation_token` 是 `UNIQUE`，第二个订阅者就会撞上。做成真的：用 `getrandom::fill` 取
`TOKEN_BYTES` 字节（依赖已在 `Cargo.toml` 里），再用现成的 `hex` 助手拼成文本。向系统要不到就老实失败：
这个服务编得出来的令牌，攻击者也编得出来，所以不留回退处理。

然后加上确认。它的形状，也就是路由要调用的东西：

```rust
pub async fn confirm(pool: &PgPool, token: &Token) -> Result<String, Error>
```

1. **一条语句决定它**：

   ```sql
   UPDATE subscribers SET status = 'active', confirmed_at = now() WHERE confirmation_token = $1 AND status = 'pending' AND confirmation_expires_at > now() RETURNING email
   ```

   用"可能没有"的方式取行（`fetch_optional`）：取回一行，说明就是*这次*调用确认了它；没取回，说明不是。
   绑令牌的文本（`token.as_str()`）；文本必须与语句逐字节一致，理由同 `mailer/1.11-signup` 步（那里
   的陷阱 4：`.sqlx` 以语句为键）；
2. **拿到"不"之后，再去问为什么**，用第二条语句把"不"翻译成一句话：

   ```sql
   SELECT email, status FROM subscribers WHERE confirmation_token = $1
   ```

   没有行 → `Error::TokenUnknown`；有行但 `status` 不是 `pending` → `Error::AlreadyConfirmed`，捎上那个
   地址；有行且*仍然*是 `pending` → `Error::TokenExpired`。这个推断靠得住：更新的条件正是
   `pending AND not expired`，一条被它拒绝的 pending 行，只能是被过期挡下的。地址以 `String` 返回：它
   出自表里（能进表的地址都过了解析器），没什么可再验的。

### `src/signup.rs`

插入长出一个令牌和一个过期时间，于是一个订阅者永远不会是一行没人能确认的数据。精确的这段文本：

```sql
INSERT INTO subscribers (email, name, password_hash, confirmation_token, confirmation_expires_at) VALUES ($1, $2, $3, $4, now() + make_interval(secs => $5)) ON CONFLICT (email) DO NOTHING RETURNING id
```

按那个顺序绑地址、名字、哈希、令牌的文本，以及 `CONFIRMATION_WINDOW_SECS`。在插入之前签发令牌，并且
不把它给任何人：201 的 body 和第 1.11 步一样，而令牌是去*邮箱*的东西，不是给调用方的。

### `src/error.rs`

四个变体，全在退出码表里（而退出码说的就是状态码说的那件事）：

| variant | message | exit code | HTTP |
| --- | --- | --- | --- |
| `TokenUnknown` | `no subscriber has that confirmation token` | `2` | 404 |
| `TokenExpired` | `that confirmation token has expired` | `2` | 410 |
| `AlreadyConfirmed { email }` | `` `ada@example.com` is already confirmed `` | `2` | 409 |
| `TokenGeneration { source: getrandom::Error }` | `a confirmation token could not be issued` | `1` | 500 |

三个失败变体里没有一个带令牌，理由与 `InvalidInput` 不带值一样：令牌是密钥，而失败消息最后会进日志行。

### `src/http.rs`

`GET /confirm?token=…`，而状态表长出三条。契约：

| request | answer |
| --- | --- |
| 一个能确认某个等待中订阅者的令牌 | `200` 与 `{"status":"active","email":"<as it was stored>"}` |
| 同一个令牌再来一次 | `409`，点名那个地址 |
| 一个过了过期时间的令牌 | `410` |
| 一个格式正确、但没人拿到过的令牌（包括改了一个字符的） | `404` |
| 不是令牌的文本 | `400` |
| 完全没有 `token` 参数 | `400` |
| 一次确认，但没有配置数据库 | `503` |

三个细节：

- **查询串也要解析**：把 `token` 取成 `Result<Query<ConfirmQuery>, QueryRejection>`（与第 1.11 步的 body
  同一个形状），并让令牌先过 `Token::parse`。"你送来的东西不是链接"和"那个链接不好"是两个不同的答案，
  对应两个不同的错误；
- **200 的 body 与 201 的 body 同形**：把 `SignedUp` 改名为 `SubscriberState`——它不再关于注册，它关于
  一个路由刚刚改动的状态；
- **状态表仍然只有一条规则**：`status_of` 增加三个分支，而 5xx 那一支不变。`TokenGeneration` 是一个
  500，它的原因进日志。

第 1.11 步的 201 body 不多长一个字段。注册响应里的令牌，是任何能看到那个响应的人都能用的令牌——而那恰好
就是确认本该独立于的那个人。

## 完成标准

- `kiln run mailer/1.12-token` — 规格通过（它会起一个 Postgres 容器）
- `kiln check mailer/1.12-token` — 每个 must 闸门都是绿的
- 一次新的注册在行里留一个 64 字符的十六进制令牌、`confirmed_at IS NULL`、过期时间大约在一天之后，而
  201 的 body 不含那个令牌
- `GET /confirm?token=…` 带那个令牌回 `200`，再带一次回 `409`，且 `confirmed_at` 不动
- 通过 `psql` 用一条 `UPDATE` 把 `confirmation_expires_at` 移到过去，确认就回 `410`，而行仍然是
  `pending`
- 同一个令牌的两次确认同时到达，以一个 `200` 和一个 `409` 收场
- `cargo test --lib` 通过：令牌能走完自己的文本往返、两个令牌不同、而 `{:?}` 不会打印出令牌

## 陷阱

1. **读、决定、更新。** 与 1.11 同一个陷阱，穿的是更新那件外衣。它通过每一个顺序测试，并在第一次诚实的
   竞态里输掉：规格的 *"two confirmations of one token have to be decided by the database"* 把它显示成
   `[200, 200]`——两个请求都读到 `pending`，都回答成功，而第二个把 `confirmed_at` 移到了一个没人点过东西
   的时间。
2. **由应用计算的窗口。** 插入时绑 `Utc::now() + Duration::days(1)`，更新时比较 `Utc::now()`：两个时钟，
   而应用的那个是在整个机群上会漂移的那个。规格的窗口断言（*从现在起 23 到 25 小时之间*）说的是数据库的
   `now()`，而两条语句里的 `now()` 是同一个时钟。
3. **每一种失败都用同一个状态码。** 过期回 `404`、被篡改回 `409`、别的都回 `400`：规格逐条检查，而把它们
   分开的理由不是迂腐——它区分的是点了旧链接的人、打错了链接的人，以及在试探令牌的人。
4. **把令牌放进答案里，或放进错误里。** 它作为密钥的程度与密码完全一样：规格断言 201 的 body 里没有令牌，
   也没有任何拒绝把它回显出来。日志行同理——这个类型有意没有 `Display`，所以 `%token` 编译不过，而
   `?token` 打印 `<redacted>`。
5. **一个千篇一律的随机令牌。** 一个计数器（用算术就能猜）、一个时间戳（按日期就能猜）、一个 UUIDv1
   （一个带 MAC 地址的时间戳）、`format!("{:x}", std::process::id())`：它们每一个都是攻击者能*算出来*的
   令牌。`getrandom::fill` 是这一步里唯一知道调用方不知道的东西的那个东西。
6. **用掉之后清空令牌，于是答案也丢了。** `SET … confirmation_token = NULL` 看起来是让令牌一次性使用的
   干净办法；它也让一个被重放的链接与一个伪造的链接无法区分，因为已经没有东西持有那个值了。让它在
   *这里* 一次性的是条件里的 `status = 'pending'`——那一行*留着*，作为发生过什么的记录。
7. **用 `fetch_one` 而不是 `fetch_optional`。** 没有行回来是这个路由每一个失败的*正常*答案；`fetch_one`
   把它们每一个都变成一个 `RowNotFound` 和一个 500。
8. **相信第二条语句。** 那条诊断用的 `SELECT` 不是决定——如果把它写成决定（读状态，然后更新），竞态就
   回来了。它在更新说了"不"*之后*才跑，而且只挑那句话。它的分支顺序同理：过期与不是 pending 是两个不同的
   答案，而两者都是的行拿到的是描述它当下状态的那一个。

- [Postgres: `UPDATE`](https://www.postgresql.org/docs/current/sql-update.html) — `WHERE` 子句就是
  那个决定，`RETURNING` 是调用方听到它的方式，而 `SET` 对每个匹配的行跑一次
- [Postgres: transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html) — 在
  `READ COMMITTED` 下，同一行的两个并发 `UPDATE` 能看到彼此的什么
- [Postgres: random() and friends](https://www.postgresql.org/docs/current/functions-math.html) — 为什么
  SQL 里的 `random()` 不是这里的答案（它不是密码学生成器，而令牌必须活过一次数据库导出）
- [`getrandom`](https://docs.rs/getrandom/latest/getrandom/) — `fill` 在每个平台上保证什么，以及为什么
  一个 `RandomState` 或基于时间的种子不是同一件事
- [OWASP: forgot password cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
  — 同样的三个失败（过期、一次性、不可预测的值），在另一个用邮件发令牌的流程里
- [RFC 6749 §10.5](https://datatracker.ietf.org/doc/html/rfc6749#section-10.5) — 一小串"URL 里的令牌
  必须活过什么"，以及 [RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750)，这一步有意不实现的那个
  bearer 令牌对应物
- [`std::fmt::Debug`](https://doc.rust-lang.org/std/fmt/trait.Debug.html) — 一个密钥类型手写的「已打码」
  `Debug`，以及为什么 `Display` 是要留着不实现的 trait
