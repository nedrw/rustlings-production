# 把错误当作 API 的一部分

## 为什么

一个只是 `String` 的失败只能被打印出来。调用方分不清「端口被占用」和「文件不存在」，于是每个
调用方都在重新发明对同一句话的解析——更糟的是干脆放弃，去重试一件永远不会成功的事。错误类型和
函数一样是 API 的一部分：别的代码（一个测试、第二个二进制、步骤 1.7 里的 HTTP 层）被允许依赖的
就是它。

有两个性质让它值得写下来。一个是**原因链**：「cannot read `mailer.toml`」少了操作系统那句
「No such file or directory」，读者就得自己去猜是哪一半错了。另一个是**退出码**：shell 也是一个
调用方，而一份分不清笔误和读不了文件的部署脚本，要么永远重试，要么在凌晨三点把谁叫醒。

## 任务

脚手架加上了那两个依赖（`thiserror`、`anyhow`），并把失败类型放进 `src/error.rs`：这个服务可能
失败的每一种方式一个变体，还带着某个设置项的值是从哪儿来的。它现在还没有消息、没有原因、也没
有退出码——那就是本步骤要做的事：

- **给每个变体一条消息**（`thiserror` 的 `#[error("…")]`），并且保持上一个步骤的规格已经钉住的措辞：
  调用方可能会把它打印出来，而测试是在比较它的。
- **带上原因。** 那两个配置失败各自保留真正发生了什么——让读取停下来的 `std::io::Error`、拒绝了
  这个文件的 `toml::de::Error`——作为它们的 source，于是 `error.source()` 走的是一条链，而不是被
  消息压扁成一句散文。
- **把服务的其余部分改写到这个类型上。** `mailer::parse` 和 `Config::load` 返回它，各层构造对的
  变体而不是一句话，上一个步骤手写的 `ConfigError`、`Source` 和那些 `Display` 实现被删掉。
- **在 `Error::exit_code` 里把失败映射到退出码**，并且让这张表小而诚实：调用方要了服务没有的东西
  时是 `2`（未知参数、缺失的值、用不了的设置项取值、不认识的设置项）；配置读不了或解析不了时是
  `1`。看见 `2` 的脚本就知道不用重试。
- **`anyhow` 只出现在边界上。** `main.rs` 可以用它：二进制的活儿就是打印然后退出，一个不透明的
  失败盒子正是它想要的。库不行：`anyhow::Error` 没法被 match，所以它当不了服务的失败类型——想要
  对失败做出反应的代码需要的是那些变体。
- **写清会失败的 API 返回什么。** 每个返回 `Result` 的公共函数都要有一节 `# Errors`，点名调用方
  必须处理的那些变体；从本步骤起 `docs:public` 就是一个 must 闸门，而且它拒绝
  `missing_errors_doc`，所以一份写好的签名是「做完了」的一部分。

## 完成标准

- `kiln run mailer/1.5-errors` — 规格通过
- `kiln check mailer/1.5-errors` — 每个 must 闸门都是绿的（包括 `docs:public`）
- `cargo run -- --nope; echo $?` 打印那个未知参数和用法文本，并以 2 退出
- `cargo run -- --config nope.toml --check-config; echo $?` 点名那个文件，保留操作系统给的理由，
  并以 1 退出
- `cargo doc --no-deps` 在 `parse` 和 `Config::load` 上都显示一节 `# Errors`

## 陷阱

1. **把原因压进消息里。** `InvalidConfig { path, message: error.to_string() }` 能编译，打印出来也
   几乎一样——但 `source()` 返回 `None`，于是规格的探题 crate 报出
   *"a failure that carries a cause has to expose it through `source()`"*。链才是调用方能走的东西，
   `String` 不是。
2. **所有失败共用一个退出码。** 配置文件缺失也返回 2，就会让部署脚本把读不了的文件当成笔误：规格
   以 *"the two kinds of failure must not share a code"* 失败。
3. **让 `anyhow` 进了库。** 在 `Config::load` 里用 `anyhow::Result` 是让编译器满意的最短路径，同时
   它把 API 删了：外面再也没法 match 那个失败。于是规格的探题 crate 编不过了，而那个编译错误
   *就是*本步骤的要求——`parse` 和 `Config::load` 回答的必须是 `mailer::Error`。
4. **给变体改名或者改形状。** `src/error.rs` 里的名字是调用方 match 的对象，探题 crate 就是照着
   它们编译的。需要一种新的失败就加一个变体——不要把两种失败并成一种，否则退出码表就丢掉了它
   存在的那个理由。

## 延伸阅读

- [`thiserror`](https://docs.rs/thiserror/latest/thiserror/) — `#[error("…")]`、`#[from]`，以及一个
  叫 `source` 的字段怎么自动变成原因
- [`std::error::Error::source`](https://doc.rust-lang.org/std/error/trait.Error.html#method.source)
  — 调用方要走的是什么，以及标准库自己的错误为什么保得住它们的链
- [`anyhow`](https://docs.rs/anyhow/latest/anyhow/#comparison-to-failure) — 在应用里要一个不透明错误
  的理由，和在库里不要它的理由
- [Rust API guidelines: `C-GOOD-ERR`](https://rust-lang.github.io/api-guidelines/interoperability.html#error-types-are-meaningful-and-well-behaved-c-good-err)
  — 错误类型要有意义、行为良好，并且是 `Send + Sync + 'static`
