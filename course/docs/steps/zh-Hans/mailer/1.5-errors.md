# 把错误当作 API 的一部分

## 为什么

失败如果只是一个 `String`，除了打印出去什么也做不了。调用方分不清"端口被占"和"文件不存在"，只好各自
重新发明对同一句话的解析——更糟的是干脆放弃解析，去重试一件永远不会成功的事。错误类型和函数一样是
API 的一部分：别的代码（一个测试、第二个二进制、第 1.7 步的 HTTP 层）被允许依赖的，正是它。

有两点值得写下来。其一是**原因链**：只写"cannot read `mailer.toml`"、不带操作系统那句
"No such file or directory"，读的人只好自己猜错在哪一半。其二是**退出码**：shell 也是调用方，一个分不清
笔误和读不了文件的部署脚本，要么永远重试，要么在凌晨三点把人叫醒。

## 任务

脚手架加好了两个依赖（`thiserror`、`anyhow`），并把失败类型放进 `src/error.rs`：这个服务可能失败的每一种
方式对应一个变体，还带着某个设置项的值来自哪里。它目前没有消息、没有原因、没有退出码——那正是这一步的活：

- **给每个变体一条消息**（`thiserror` 的 `#[error("…")]`），措辞沿用上一步规格已经钉住的那份：调用方会
  把它打印出来，测试也在比对它。
- **带上原因。** 两个配置失败各自保留真正发生的事——让读取停下的 `std::io::Error`、否掉这个文件的
  `toml::de::Error`——作为 source。这样 `error.source()` 走的是链，而不是被压成一句话。
- **让服务的其余部分改用这个类型。** `mailer::parse` 与 `Config::load` 返回它，各层构造对应的变体而不是
  一句话；上一步手写的 `ConfigError`、`Source` 和那几个 `Display` 实现删掉。
- **在 `Error::exit_code` 里把失败映射成退出码**，让这张表小而诚实：调用方要了服务没有的东西——未知参数、
  缺了值、设置项取值用不了、设置项不认识——是 `2`；配置读不了或解析不了是 `1`。脚本看到 `2` 就知道不必
  重试。
- **`anyhow` 只用在边界。** `main.rs` 可以用：二进制的工作就是打印然后退出，一个不透明的失败盒子正合它
  的意。库不行。`anyhow::Error` 没法 match，当不了服务的失败类型——想对失败作出反应的代码要的是变体。
- **会失败的 API 要写清返回什么。** 每个返回 `Result` 的公开函数都得有 `# Errors` 一节，点名调用方必须
  处理的变体。从这一步起 `docs:public` 是 must 闸门，它拒绝 `missing_errors_doc`——签名的文档也是"做完"
  的一部分。

## 完成标准

- `kiln run mailer/1.5-errors` — 规格通过
- `kiln check mailer/1.5-errors` — 每个 must 闸门都是绿的（包括 `docs:public`）
- `cargo run -- --nope; echo $?` 打印那个未知参数和用法文本，并以 2 退出
- `cargo run -- --config nope.toml --check-config; echo $?` 点名那个文件，保留操作系统给的理由，并以 1 退出
- `cargo doc --no-deps` 在 `parse` 和 `Config::load` 上都显示一节 `# Errors`

## 陷阱

1. **把原因压进消息。** `InvalidConfig { path, message: error.to_string() }` 能编译，打印出来也几乎一样
   ——但 `source()` 返回 `None`，于是规格的探题 crate 报出
   *"a failure that carries a cause has to expose it through `source()`"*。调用方能顺着走的是链，不是一个
   `String`。
2. **所有失败共用一个退出码。** 配置文件缺失也返回 2，部署脚本就会把读不了的文件当成笔误：规格以
   *"the two kinds of failure must not share a code"* 失败。
3. **让 `anyhow` 进了库。** 在 `Config::load` 里用 `anyhow::Result` 是让编译器闭嘴的最短路径，代价是把 API
   删了——外面再也 match 不到那个失败。规格的探题 crate 会编不过，而那个编译错误*就是*这一步的要求：
   `parse` 与 `Config::load` 回答的必须是 `mailer::Error`。
4. **给变体改名或改形状。** `src/error.rs` 里的名字是调用方 match 的目标，探题 crate 照着它们编译。需要
   新的失败就加变体——别把两种并成一种，否则退出码表就失去了存在的理由。

## 延伸阅读

- [`thiserror`](https://docs.rs/thiserror/latest/thiserror/) — `#[error("…")]`、`#[from]`，以及一个叫
  `source` 的字段怎么自动变成原因
- [`std::error::Error::source`](https://doc.rust-lang.org/std/error/trait.Error.html#method.source) — 调用
  方顺着走的是什么，标准库自己的错误又为什么保得住链
- [`anyhow`](https://docs.rs/anyhow/latest/anyhow/#comparison-to-failure) — 应用里要不透明错误的理由，
  和库里不要它的理由
- [Rust API guidelines: `C-GOOD-ERR`](https://rust-lang.github.io/api-guidelines/interoperability.html#error-types-are-meaningful-and-well-behaved-c-good-err)
  — 错误类型要有意义、行为良好，并且是 `Send + Sync + 'static`
