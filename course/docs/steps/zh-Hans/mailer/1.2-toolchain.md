# Pin the toolchain, formatting and lint policy

## WHY

"在我的机器上能编译"是一个没人写下来的版本号。一个用 `stable` 构建的服务下个月会换一个编译器
编译，今天还是警告的 lint 在更新的工具链里会变成错误——于是构建在下一次运行它的人那里坏掉，
而那个提交什么都没改。反过来也一样：一个没有 MSRV 行的公开服务，会接受一次悄悄抬高用户所需编
译器的依赖升级，而坏掉的是他们的构建，不是你的。

格式化与 lint 级别放进仓库是出于同样的理由：每一次评审都把时间花在空白上，或者花在"评审者 A
在乎的那个 `unwrap` 而评审者 B 不在乎"上，其中没有一样是日后有人能查到的决定。写下来之后，
它们就是由工具执行的项目属性。

## TASK

给 `app/mailer` 加三个文件的政策。这里没有任何东西被脚手架：这些是决定，而别人替你做的决定不
是一个决定。

- `rust-toolchain.toml` 把 `channel` 钉到一个具体的三段版本（不是 `stable`），并把 `rustfmt` 和
  `clippy` 列为组件，因为下一步的任务两个都要跑。
- `rustfmt.toml` 把风格设置从评审里拿走：至少 `edition` 和 `max_width`。课程仓库自己的
  `rustfmt.toml` 是一个能用的例子，`cargo fmt --all --check` 是逼你遵守你的那份的门。
- `Cargo.toml` 声明 `rust-version`（用户需要的最低版本）和 `[lints] workspace = true`，而
  `[workspace.lints]` 表拒绝每个目标都必须遵守的东西：

```toml
[workspace.lints.rust]
missing_docs = "deny"
unsafe_code = "forbid"

[workspace.lints.clippy]
dbg_macro = "deny"
todo = "deny"
unimplemented = "deny"
```

只有对*每一个*目标都成立的 lint 才属于那张表。测试可以 `unwrap`，二进制可以打印；那些属于阶
梯的级，门会在命令行上传递它们（第 3 步把它们接进一条命令）。把 `unwrap_used` 或
`print_stdout` 放进 workspace 表是一种有具体症状的错误：第一个断言什么的测试编译不过。

规格检查钉住是真实的——跑测试的编译器报告的就是钉住的版本——声明的 MSRV 被这个钉满足，以及
政策真的咬人。它证明最后一条的方式是往 `tests/` 里写一个小文件，用 `cargo clippy` 编译它，并
要求构建失败。一张从来没有人观察过的 lint 表是装饰。

## DONE WHEN

- `kiln run mailer/1.2-toolchain` — 规格通过
- `kiln check mailer/1.2-toolchain` — 每个 must 闸门都是绿的，包括 `fmt` 和 `clippy@1`
- 在 `app/mailer` 里 `rustup show` 报告钉住的工具链

## TRAP

1. **声明了 lint 却不继承。** `[workspace.lints]` 在包用 `[lints] workspace = true` 选择加入
   之前是惰性的；没有它，夹具干净地编译，`clippy` 一言不发，规格以 *"the lint policy does not
   bite"* 失败而不是一个 lint 错误——这正是这条断言存在要防止的那半小时困惑。
2. **把 `unwrap_used` 放进 workspace 表。** 它于是也作用于测试目标，`cargo clippy` 在测试里第
   一个 `assert_eq!(x.unwrap(), y)` 上失败。阶梯的第 2 级只对生产目标拒绝它，而且门知道这个区
   别；workspace 表不知道。
3. **写 `channel = "stable"`。** 今天什么都不失败，之后一切都失败：构建拿到 rustup 那一刻有的
   任何东西，`rustc --version` 不再与文件相符。规格比较两者，所以这一条立刻被抓住。
