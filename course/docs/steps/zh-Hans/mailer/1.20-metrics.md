# 指标与 SLO 基线

## 为什么

`mailer/1.6-logging` 步给了这个服务一种说清"发生了什么"的方式：一个事件一行 JSON，带字段。日志回答的是
*这一个请求经历了什么*，一次一个请求——而服务还得回答关于自己的另一个问题：**它现在到底怎么样？** 这需要
能廉价相加、形状固定、并且能导出给某个画图并在凌晨三点把人叫醒的系统。那就是指标。

随之而来三个决定，每个都有做错的方式：

1. **名字和标签是 API。** 一块看板、一条告警规则、一份 runbook，全是照着 `http_requests_total{route,status}`
   写的。改个标签名不会弄坏构建，它弄坏的是事故中某人正盯着的那张图——而那是最糟糕的发现时机。所以词汇只住在
   一个文件里（这一步的 `src/metrics.rs`），规格把它当*快照*钉住：改名就是红的构建，而不是无声无息；
2. **基数要有界。** 这一条既费钱，也需要经验才看得见。值来自请求的标签——带 id 的路径、一个地址、一条错误消息
   ——会把一条时间序列变成上千条，把指标库变成一笔昂贵的意外。所以 `route` 是*路由匹配到*的那个模式（对每个
   订阅者都是 `/subscribers/{id}/deliveries`，对每次注册都是 `/signup`），而没有匹配上任何东西的路径，就是它
   匹配到的模式 `/{*rest}`，不是陌生人发来的那个字符串。这也是这一步把 404 处理函数改成一条路由的原因：
   **匹配不上的东西，就数不到**；
3. **一次投递的三种结局是三个数字。** `mailer/1.15-idempotent-delivery` 步把它们分成了三个——消息被收下、
   某次尝试失败但会重试、一条再也没人会发的消息——而一个笼统的"错误"计数器，会让"重试后送达"和"已经放弃"变得
   无法区分。`deliveries_total{outcome}` 这个标签，就是"邮件服务器不太舒服"和"有个订阅者永远不会再收到我们的信"
   这两条告警之间的区别。

**还有这一步坦承没有的那部分**：SLO。指标是原料；SLO 是关于某个数字的协议，而协议需要有人来同意。这一步的完成
标准要的是一份初稿——一个指标、一个目标、一个窗口——但执行属于部署（`alertmanager`、看板、评审），不属于课程
仓库。这里有的是机器能检查的那部分。

## 任务

脚手架加了 `src/metrics.rs`，而洞里装的正是抓取器真正读的那部分：

- 注册表已经在了——按 `(route, status)` 计数、按路由的直方图、按投递结局计数的计数器——`record_request` /
  `record_delivery` 也写好了；
- `render()` 只写每个族的 `# HELP` 与 `# TYPE` 行，**样本一个都没有**：这个进程数到了什么，在这一步写好那些
  行之前是看不见的。

### `src/metrics.rs`：导出

把样本写出来：一条序列一行，`name{labels} value`，排好序（先按名字，再按标签），于是同一状态抓两次得到同样的
字节——规格的快照之所以是一个测试而不是掷骰子，就靠这个。对直方图来说，这就是按递增顺序的桶、一个 `+Inf` 桶，
以及这个族的 `_sum` 与 `_count`。

### `src/lib.rs` 与 `src/http.rs`

- 声明模块（`pub mod metrics;`）；
- `AppState` 持有一个进程级的 `Metrics`，在 `start_with_sender` 里建出来，并与投递队列共享；`metrics()` 把它
  交给端点；
- `GET /metrics` 用 `state.metrics().render()` 作答，内容类型 `text/plain; version=0.0.4`——每个抓取器都认得
  的那个；
- **一个中间件数每个请求**：`middleware::from_fn_with_state(state.clone(), measure)`，包在整个路由外面。两个
  细节就是这一步：
  - `MatchedPath` 是路由*模式*，永远不是具体路径（这就是上面第 2 个决定）；
  - 这一层必须是路由上的**最后一次**调用，因为路由层只包住它被应用时已经存在的路由——在它之后声明的路由，是
    没人数的路由。（规格恰好抓这个：`/metrics` 自己会被数到，而 `/confirm` 不会。）
- 404 处理函数变成一条路由：`.route("/{*rest}", get(not_found))` 而不是 `.fallback(…)`，因为回退处理不经过
  这一层，会成为这个服务唯一数不到的答案。

### `src/delivery.rs`

worker 是唯一知道消息怎么结束的东西，所以由它来数：发送成功记 `Sent`，每次没成功的尝试都记 `Failed`（含重试
——那个数说明邮件服务器不舒服），次数用尽记 `GivenUp`。`Queue::start` 除了发送器和连接池，还要收注册表。

### 规格判什么

| the test | the claim |
| --- | --- |
| 两个请求、两条路由 | `http_requests_total{route="/healthz",status="200"}` 与 `{route="/signup",status="400"}` 分开计数 |
| 两条没人路由的路径 | 两者共用*一条*序列，而那两条路径本身在导出里哪儿都不出现 |
| 词汇 | `# HELP` 的集合恰好是这个服务声明的那三个——改名就会红的快照——外加一个直方图，其 `+Inf` 桶等于它的 count |
| 一条送达的消息 | `deliveries_total{outcome="sent"} 1`，没有任何 `failed` |
| 一台不在的邮件服务器 | `failed` 数下每次尝试，`given_up` 把这条消息数一次：同一次注册，三个和 一个 |

## 完成标准

- `kiln run mailer/1.20-metrics` — 规格通过
- `kiln check mailer/1.20-metrics` — 每个 must 闸门都是绿的
- 对运行中的服务，`curl /metrics` 每条序列一行；隔一秒两次 `curl` 能看到某个计数器动了
- 请求一条没人路由的路径，恰好新增一条序列，名叫 `/{*rest}`——而你请求的那条路径在输出里哪儿都没有
- 一份 SLO 初稿存在于某人会读到的地方：一句话，点名指标（`POST /signup` 上的
  `http_request_duration_seconds`）、目标（例如*99% 在 250 ms 以内*）和窗口（例如*28 天*）。没有东西执行它
  ——那是下一次部署的事——而把它写下来，才让下一条告警规则是推导出来的，不是猜出来的

## 陷阱

1. **值来自请求的标签。** `route=path` 看着有用，而它正是一条指标变成"每个被扫描过的 URL 一条序列"的方式；拿
   `email`、`token` 或错误消息做同样的事更糟，因为那些值既无界*又*敏感。标签是固定词汇，外部来的值要么归进桶里，
   要么丢掉。
2. **层放错位置。** `Router::layer` 只包住它被应用时已存在的路由。把它放在链条中间（这一步第一次尝试就是），
   在它之后声明的每条路由——`/confirm`、`/newsletter`、404 的兜底——对指标都是隐形的：看板不是错的，是*缺了*，
   而缺了更难发现。规格里第二个测试就是那个观察点。
3. **会归零的指标。** 每个请求新建的计数器永远读到 1；每个处理函数克隆一份注册表，就是一堆谁也不共享的数字。
   注册表属于进程，每个要计数的地方拿到的都是*那个* `Arc` 的克隆。
4. **数数得到的东西，而不是要紧的东西。** 请求容易数，却很少是真正的问题；投递结局——订阅者能察觉到的那个
   ——才是这一步真正的内容。一个有着漂亮请求直方图、却不知道有多少消息卡住的服务，是一个有看板没有告警的服务。
5. **平均数。** `_sum`/`_count` 很容易被拿去除；而平均延迟是一个没有任何用户经历过的数字：一千个请求里那一个慢的，
   就这么消失在里面了。从桶里算分位数（PromQL 的 `histogram_quantile`，或者对某个窗口求分位）才是 SLO 该依据的
   东西。
6. **忘了这个端点是公开的。** `/metrics` 不做认证，这是常见的形态（抓取器不是订阅者），也是常见误配置里的泄露
   （一个监听器暴露在公网上的进程）。它该待在一个别的什么都够不着的接口上——`mailer/1.21-container` 步会让这件事
   变成一个真正的决定——而绝不能发生的是"标签带着密钥"，这也是为什么第 1 条陷阱排在第一位。
