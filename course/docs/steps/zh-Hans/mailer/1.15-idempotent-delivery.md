# 幂等投递：每个订阅者只收一封确认信

## 为什么

`mailer/1.14-worker` 步把发送挪出了请求路径，但没让它只发生*一次*：队列会重试，进程会重启，两个 worker 可能
同时握着同一个订阅者的活儿，同一次注册也可能来两遍。每一种都是第二封确认信的机会——而邮件服务器帮不上忙。
它只管收下消息然后发出去；去重是这个服务自己的事，而服务真能做成这件事的地方是数据库。

"恰好一次"是两条朝相反方向拉的主张，诚实的版本是这样的：

- **至少一次**——服务欠下的消息必须发出去，哪怕第一次失败、进程重启、订阅者又来问了一遍；
- **至多一次**——*副作用*每个意图只发生一次，不管中间有多少次尝试、多少任务、多少 worker。

三个决定让它成立，每个都有做错的方式：

1. **键是意图，不是消息。** 不能发生两次的是*通知这个订阅者去确认*。所以状态挂在订阅者身上——不是对消息做
   哈希，也不是拿令牌去重。换过的令牌是一条不同的消息、同一个意图，而消息形状的键恰好就是这样什么也没去重；
2. **认领是一次条件写，它的答案就是事实。** `claim` 不是先读行再判断。先读后写两半之间有窗口（
   `mailer/1.11-signup` 步用唯一约束关上它；这一步用的是同一招，配 `UPDATE ... RETURNING`）：语句自带条件，
   它返回的那一行只属于一个调用方——认领成功的那一个。其余调用方拿到的是*无事可做*；
3. **记录写在发送之后，失败就交还。** `confirmation_sent_at` 只在邮件服务器收下消息之后才写；发送失败就释放
   认领，消息继续"欠着"、继续可被认领，而不是永远卡在"有人在处理"。又因为*尝试次数*也住在行里，"这一条我们
   放弃了"是别人查得到的事实，而不是滚出屏幕的一行日志。

**这一步修不了、但要说出口的那部分**：worker 若在认领与发送之间死掉，会留下一个已认领、却没发出的订阅者。
堵这个洞要么靠清理器（`claimed_at < now() - interval '…'` 把行放回去），要么靠 outbox 让数据库成为唯一的
队列——都是后面的事，也是 T3 存在的理由。这一步换来的是：无论多少次重试、重启、重复请求、并发 worker，同一封
确认信都不会发出两遍。

## 任务

脚手架加了两样东西，而两者的洞都是上面第二个决定：

- `migrations/0002_confirmation_delivery.sql`——在 `subscribers` 上加 `confirmation_claimed_at`、
  `confirmation_sent_at`、`confirmation_attempts`。跑过任何地方的迁移绝不修改：这是 0002，下一次改 schema
  是 0003；
- `src/deliveries.rs`——状态机，其中 `claim` 是一次**读**：问订阅者是否处于 pending 且尚未通知，然后对所有
  来问的人回 `Some`。两个调用方都拿到消息，而那个本该让"放弃"可见的计数，停在零。

### `src/lib.rs`

声明模块：`pub mod deliveries;`。

### `src/deliveries.rs`：让 claim 成为认领

- `claim(pool, subscriber) -> Result<Option<Delivery>, Error>`——一条语句，**边写边判**：

```sql
UPDATE subscribers
   SET confirmation_claimed_at = now(),
       confirmation_attempts = confirmation_attempts + 1
 WHERE id = $1
   AND status = 'pending'
   AND confirmation_sent_at IS NULL
   AND confirmation_claimed_at IS NULL
   AND confirmation_token IS NOT NULL
 RETURNING email, confirmation_token
```

  `None` 不是错误：它只是说确认信已经发过，或者此刻正在别的 worker 手里。一次认领*就是*一次尝试——worker
  每次认领只发一次（见下）——所以 `confirmation_attempts` 数的是这条消息真正递给邮件服务器的次数，而且这个
  数字能扛过重启；
- `mark_sent`——`confirmation_sent_at = now()`，清掉认领。这是此后每个任务都会撞上的写：戳一盖上，`claim` 就
  回 `None`，什么都不发；
- `release`——只清认领，别的都不动。发送失败的消息继续欠着；
- `outstanding(pool, email) -> Result<Option<i64>, Error>`——这个地址所属的订阅者，*前提是服务还欠他一封确认
  信*：未知地址、已确认、已通知过，一律 `None`。这是第二次注册要问的问题。

### `src/delivery.rs`：任务是身份，不是消息

`Job` 不再携带 `Message`，改为携带 `subscriber`；`Queue::start` 除了发送器还要收连接池：该发什么由行决定，在
有人认领它的那一刻决定，永远不由入队的人决定。

worker 的形状随之改变。重试循环现在**穿过**数据库，而不是绕着发送器打转——认领、发一次、记录或交还——于是
每次尝试都是一次认领，尝试计数是真的，而正是"交还"让下一次尝试成为可能：

```rust
let Some(delivery) = deliveries::claim(pool, job.subscriber).await? else { /* nothing to do */ };
let message = confirmation_message(delivery.email.clone(), &delivery.token);
match sender.send(message).await {
    Ok(()) => { deliveries::mark_sent(pool, job.subscriber).await?; /* delivered */ }
    Err(error) => {
        deliveries::release(pool, job.subscriber).await?;
        // …backoff, then claim again; after MAX_ATTEMPTS, log it and move on
    }
}
```

消息从行里重建（`confirmation_message(email, &token)` 是 `mailer/1.13-email-port` 步的函数），令牌因此从来
不必跟着任务走。

### `src/http.rs` 与 `src/signup.rs`：谁能要求投递

- `AppState` 携带 `delivery: Option<Queue>`，它恰好在没有数据库时为 `None`：投递记录住在数据库里，而一个无法
  记录自己做过什么的队列，就是一个会发两遍的队列。`delivery()` 把 `Option<&Queue>` 交给处理函数；
- `/signup` 两者都要——`state.database()` **和** `state.delivery()`——并在插入前预定座位，同
  `mailer/1.14-worker` 步；
- `subscribe(pool, seat, request)` 在插入成功时发出 `Job { subscriber: id }`。插入**输了**的时候，它去问
  `outstanding(pool, &email)`：如果服务仍欠这个订阅者一封确认信，就用这个座位请 worker 再试一次——而回给
  调用方的仍然是 `409`，因为这个地址确实被占了。第二次注册是第二次*投递请求*，它会不会产生一封邮件，由数据库
  决定，不由处理函数决定；
- 处理函数里没有"先读后写"：重复路径的那个问题，是在唯一约束已经裁决*之后*才问的，所以没有可丢的窗口。

### `src/main.rs`

队列现在是可选的，所以关闭序列要在排干之前丢掉那个 `Option`——没有数据库的进程没有东西可排，退出码也不变。

### 规格判什么

| the test | the claim |
| --- | --- |
| 一次注册 | 一封邮件，而行里也这么说：`confirmation_sent_at` 已设，`confirmation_attempts` 为 1 |
| 同一地址再来 | `409`（两种写法各来一次），而邮件仍然恰好一封 |
| 一直失败的发送 | `MAX_ATTEMPTS` 次尝试，行回到未认领、未发送；等发送器恢复、订阅者再来问一次时，消息发出去，只有一封 |
| 多个调用方抢同一地址 | 一个 `201`、七个 `409`、一封确认信：重复请求入队的那些任务，必须被认领去重，而不是靠运气 |

## 完成标准

- `kiln run mailer/1.15-idempotent-delivery` — 规格通过
- `kiln check mailer/1.15-idempotent-delivery` — 每个 must 闸门都是绿的
- `cargo test --lib` 通过：队列的上界与退避策略仍然成立（它们只是离开了投递路径，没有离开这门课）
- 对运行中的服务把同一地址注册两次，
  `SELECT confirmation_sent_at, confirmation_claimed_at, confirmation_attempts FROM subscribers`
  只有一个戳、一个 null、一个计数——日志里只有一封邮件
- 发送器一直失败时，`confirmation_attempts` 达到 `MAX_ATTEMPTS`，`confirmation_sent_at` 保持 null；之后对该
  地址再注册一次，它就发出去了

## 陷阱

1. **先读，再发。** 脚手架的 `claim` 问行"消息还欠着吗"并对所有人回是：两个任务认领同一条消息，它就发了两遍。
   这个窗口和 `mailer/1.11-signup` 步为注册关掉的是同一个，修法也一样：让语句自带条件，相信它的 `RETURNING`
   行，而不是上一次 `SELECT`。
2. **拿消息去重。** 用令牌做投递的键，或者对正文做哈希，看着更整齐，却在第一次换令牌时就坏了：消息变了，意图
   没变，订阅者收到两封确认信。
3. **发送之前写 `sent_at`。** 先盖戳再发，记录就变成了猜测：一次失败的发送留下一个永远无法被通知的订阅者，
   而且再也不会有人重试。戳的含义是*邮件服务器收下了*。
4. **认领了不交还。** 没有 `release`，一次发送失败就让这条消息永远不可认领——行里说"有人在处理"，而那个人早没了。
   进程在发送途中死掉也是同一个洞，这一步写进文档而不是修掉它。
5. **把计数弄丢。** `confirmation_attempts` 只花一列，却是"我们到底多努力过"唯一能留下来的答案。worker 在内存里
   记个私有计数器，一重启就没了；任务里把它重置，会让"已放弃"的消息和"新消息"无法区分。
6. **拿队列当记录。** 一个携带消息的 `Job`，加上一个只活在 worker 脑子里的 `sent` 标记，正是这一步要替换的设计：
   杀掉进程，"那封邮件到底发出去没有"的答案也跟着没了。任务是一个问题，行才是答案。
7. **让答案幂等，而不是让副作用幂等。** 重复注册回 `200` 而不是 `409`，并不会让任何事只发生一次——邮件才是副作用，
   状态码对它说不出什么。`mailer/1.11-signup` 步决定了重复地址回什么；这一步决定它*做什么*，两者互不相干。
8. **在处理函数里认领，在请求里发送。** 趁着请求还开着，把"这个订阅者还需要邮件吗"问清楚很诱人——然后顺手就
   在那儿发了，因为答案已经在手上。那是把 `mailer/1.14-worker` 步撤回去了：调用方又得等邮件服务器，而队列丢掉
   了它唯一持有的东西。
9. **忘了清理器。** 每一次没有交还的认领，都是一次永远不会发生的投递。失败时交还，只覆盖了这个服务看得见的失败，
   覆盖不了那些把它杀掉的失败；真实部署里，被认领的行需要过期时间——上面的正文说了这一点，而不是留给读者去
   生产环境里发现。
