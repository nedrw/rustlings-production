# End-to-end test harness: an app factory on a random port

## WHY

第一个需要服务真跑起来的测试，也是第一个可能时好时坏的测试。固定端口意味着两个测试没法同时跑
——而 `cargo test` 恰恰是同时跑的，所以失败会落在碰巧排第二个的那个测试上。一个只启动一次的
`static` 应用，意味着一个测试的状态就是下一个测试的初始条件。一个靠手工重建路由的装置，意味着
测试验证的东西二进制根本不会提供。

这一步把那些代价一次付清。它之后的每一个测试——有很多，从注册、到订阅邮件、到关停——都启动
自己的服务：端口由操作系统挑，零件和 `main.rs` 造的是同一批，最后再把它停掉。这就是装置的
全部价值：测试之所以能写得短，是因为无聊的那部分在别处；测试之所以能保持诚实，是因为无聊的那
部分就是真的东西。

## TASK

脚手架放好了 `tests/support/mod.rs`：有 `TestApp` 的形状，没有任何行为。那个文件是普通的项目
代码——cargo 不会把 `tests/support/` 下的任何东西当成测试目标，所以规格用 `mod support;` 把它
引进来，规格和你自己写的测试用的是同一个 app 工厂。把它填上：

- **`TestApp::start(config)`** 绑定 `127.0.0.1:0`，问 socket 它拿到了哪个端口，然后用自己的
  监听器把应用跑起来。`config` 里的端口会被忽略：一个能自己挑端口的测试，挑到的很可能是另一个
  测试正在用的端口。
- **提供二进制所提供的那个应用。** 这需要在库里改一处：把 `http::serve` 拆成"先绑定，再在
  监听器上服务"，这样装置就能取走后一半（`serve_on`）；这也正是让端口在第一个请求之前就已知的
  原因。
- **让服务跑在自己的线程里**，配一个自己的 Tokio 运行时。于是测试就是一个普通的阻塞式 `#[test]`，
  而装置拥有那个运行时，永远不会把它嵌进另一个运行时的里面。
- **一个极小的 HTTP 客户端**（`get`、`post`、`request`），通过 `std::net` 说 HTTP/1.1，于是每个
  测试只要三行：启动、请求、断言。`Connection: close` 让每个回答都有尽头。
- **`stop` 和 `Drop`** 把应用关掉并回收它的线程——停下来的应用必须停止*接受*连接，而一个忘了调
  `stop` 的测试也不能漏掉一个线程。
- **不与其他任何测试互相协调**：不用固定端口，不用共享文件，不用 `static`。规格会同时跑三个
  应用，并在中间停掉其中一个，就是为了确认这一点。

## DONE WHEN

- `kiln run mailer/1.8-test-harness` — 规格通过
- `kiln check mailer/1.8-test-harness` — 每个 must 闸门都是绿的
- 加一个一次性的 `#[test]`，启动一个 `TestApp` 并断言 `GET /healthz` 是 `200`，然后连着跑两次
  `cargo test`，两次都通过
- `cargo test -p mailer -- --test-threads=1` 和 `--test-threads=8` 给出同样的结果

## TRAP

1. **固定端口。** 单独跑能过，和别人一起跑就坏：第二个测试会从装置那边收到
   *"Address already in use"* 的 panic，或者——更糟——两个测试轮流回答对方的请求。规格那条
   *"three apps share one port"* 的失败，就是同一个缺陷从内部看到的样子。
2. **整个二进制共用一个应用。** 一个 `static`/`OnceLock` 应用，或者一个存在全局变量里的端口，
   会让每个测试都变成上一个测试的延续。规格以*"stopping one app stopped another"*失败：这个
   承诺是每个测试一个应用，而这个承诺只有装置守得住。
3. **在装置里自己拼路由。** 只拼一个测试需要的那几条路由，是通往"一套全绿、却对服务什么也没说"
   的测试的最短路：规格会在 404/405 那两条断言上失败，报的是*"the factory has to serve the same
   fallbacks as the binary, not a router of its own"*。
4. **运行时里套运行时。** 在测试自己的异步运行时里再建一个 Tokio 运行时，或者从里面调
   `block_on`，都会以*"Cannot start a runtime from within a runtime"*panic。装置拥有运行时，
   在自己的线程里；测试只负责发请求。

- [`tokio::runtime::Builder`](https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html) —
  显式地搭一个运行时，以及为什么一个测试夹具想要自己的一份

  这正是端口号能被提前知道的原因

  `tests/support/mod.rs` 不是测试目标，以及什么才是
- [`std::net::TcpStream`](https://doc.rust-lang.org/std/net/struct.TcpStream.html) — 一个零依赖
  客户端所需要的 socket，仅此而已
