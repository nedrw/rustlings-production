# 每次运行一个关联 id 的结构化日志

## 为什么

一行「starting mailer on 127.0.0.1:8080」没什么毛病——直到有人需要把它再找出来。那一刻它就只是一句话：
主机是其中一个子串，端口是另一个，而想按端口聚合的看板只能去解析别人写的散文。带上*字段*的结构化日志
才是数据：采集器给它建索引，查询按它筛选，而你一旦改了字段名就会弄坏那条查询——这个反馈正是你要的。

另一半是关联 id。一个进程同时服务许多请求，一个请求又会落下许多行；每行里都没有 id 时，"这 40 行哪些是
一起的？"就只能靠猜时间戳。机制是 span：一个带字段的工作单元，它内部的事件继承这些字段。今天这个单元就是
这次运行本身——到 1.7 步，每个 HTTP 请求会被同一个 span 包住，而这一整套装置一行都不用改。

## 任务

脚手架加了依赖，并把入口点放进 `src/logging.rs`：一个能用的 `RunId`，和两个空函数 `init`、`announce`。把
它们填上，再接进二进制：

- **`init` 装上订阅器**，两个设置项都从配置里读（1.4 步）：级别来自 `log.level`（`error`、`warn`、`info`、
  `debug`、`trace`），格式来自 `log.format`——终端用 `pretty`，采集器用 `json`。
- **字段是 `&str`，不是句子。** 这条公告是一个 `info` 事件，字段为 `host`、`port`、`log_format`、
  `database`，消息是 `mailer is starting`。`database` 只说是 `set` 还是 `unset`——密钥有没有配值得知道，
  密钥本身不值得（1.4 步的规矩在这里同样成立）。
- **再加一个 `debug` 事件**，好让级别这个设置项真的有东西可解锁：`info` 是健康服务该跑的级别，而一个连
  自己的内部细节也记在那儿的构建，没人会读。
- **本次运行的 span**：`announce` 跑在名为 `run` 的 span 里，`run.id` 设为这次运行的 id
  （`RunId::of_this_process()`，脚手架给的类型）。有了这个 span，id 会出现在本次运行的每一行上，而不必
  每行重复写。
- **`pretty` 不许给管道上妆。** 终端可以有颜色；`stdout` 是文件、管道或采集器时就给朴素的一行，因为
  `host=127.0.0.1` 必须能在抓到的内容里被找到。
- **日志先于服务的其他一切开始**，而且*只*在服务这条路径上开始：`--help`、`--version`、`--check-config`
  在没有订阅器的情况下作答，配置报告于是仍然是脚本读得懂的东西。
- 接上线：库里写 `pub mod logging;`，二进制负责初始化日志并公告这次运行。装不上订阅器也是一种配置形状的
  失败，和别的没两样：在错误枚举里给它一个变体，配上自己的 `# Errors` 一节和退出码。

## 完成标准

- `kiln run mailer/1.6-logging` — 规格通过
- `kiln check mailer/1.6-logging` — 每个 must 闸门都是绿的
- `MAILER__LOG__FORMAT=json cargo run` 每行一个 JSON 对象，含 `fields.host`、`fields.port`、
  `fields.log_format`、`fields.database`，每个对象里还有一个 `run` span
- `MAILER__LOG__FORMAT=pretty cargo run` 把同样的事实打印给人看，`stdout` 不是终端时没有转义序列
- `MAILER__LOG__LEVEL=debug cargo run` 多出那行 debug；`MAILER__LOG__LEVEL=error cargo run` 什么都不打
- `MAILER__DATABASE__URL=postgres://user:pw@localhost/db cargo run` 说 `database=set`，而那个 URL 在
  输出里哪儿都不出现

## 陷阱

1. **颜色还留着。** `fmt()` 默认上色，抓到的行于是变成
   `\x1b[2mhost\x1b[0m\x1b[2m=\x1b[0m127.0.0.1`：规格报
   *"`host=127.0.0.1` is missing from: …"*，而终端里看着一切正常。上妆之前先问一句：这是终端吗？
2. **把配置本身记进日志，而不是记关于它的字段。** `info!(?config, "…")`，或者不写 `skip_all` 的
   `#[instrument]`，会把每一个设置项——包括数据库 URL——记进那一行或那个 span。规格会因为 URL 出现在
   输出里而失败，而那个 URL 必须轮换。
3. **用一句格式化的话代替字段。** `info!("starting on {}:{}", host, port)` 产出的东西人爱看，采集器却
   建不了索引：规格报 *"this event has no field `host`"*。
4. **那级日志白写了。** 配置写 `debug`，订阅器却停在自己的默认值（`INFO`）上，那行 debug 永远不出现：
   规格报 *"`MAILER__LOG__LEVEL=debug` has to unlock the debug lines this build has"*。
