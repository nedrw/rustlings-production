# 会话与认证：cookie 对 API 密钥

## 为什么

到目前为止服务回答的都是关于*地址*的问题：这个地址空着吗、确认了吗、通知过了吗。这些问题都不涉及某个人。
一旦有哪条路由开始涉及某人自己的数据，服务就需要第二个概念：一张发给"已经验明的人"的凭证，并且能在每个请求上
再验一次。

**会话**就是那张凭证。它是一个随机值，服务只发一次，记住它的摘要直到它结束，然后在两个地方之一接受它：

- `Set-Cookie: session=…` 是浏览器的通道。属性本身就是设计：`HttpOnly` 让脚本看不见这个值，`SameSite` 让它
  不跟别的站点的请求走，`Path=/` 说明发到哪儿，`Max-Age` 说明活多久；
- `Authorization: Bearer …` 是程序的通道：一个头，没有浏览器的那些语义，同一个令牌，服务端同一次查表。

随之而来四个决定，每个都有做错的方式：

1. **令牌是随机的，而数据库只存它的摘要。** 会话令牌是密钥，而待在数据库里的密钥，是全世界的备份、副本和
   支持工单导出都会替你留一份的那种。它用 **SHA-256** 而不是 Argon2 来哈希——和 `mailer/1.11-signup` 步的
   区别正是要点：密码可猜，需要慢哈希；没人猜得到的令牌不需要，而每个请求都跑一次慢哈希，会把认证本身变成
   瓶颈；
2. **会话会结束，而且由*读到它的那条语句*来裁决。** `revoked_at IS NULL AND expires_at > now()` 跟着每一次
   查表走，就像 `mailer/1.12-token` 步的确认窗口一样。数据库的时钟说了算，一条语句说了算，"读它是否还有效"
   和"照着它行动"之间没有窗口；
3. **登录开一个新会话，什么都不继承。** 把这条做错的经典形式是*会话固定*：服务把收到的 cookie 收下，在登录时
   给它祝福。解药不是加一个检查，而是定一个方向——令牌永远由服务端产生；
4. **"已确认"是"放进来"的一部分。** 地址从未被证明过的订阅者，服务还没法认证他；把他放进来，确认这件事就成了
   摆设。

## 任务

脚手架把零件都放好了，洞只有一个函数：

- `migrations/0003_sessions.sql`——`sessions` 表：`token_hash`（唯一）、`created_at`、`expires_at`、
  `revoked_at`，以及带 `ON DELETE CASCADE` 的 `subscriber_id`。跑过任何地方的迁移绝不修改：这是 0003；
- `src/session.rs`——令牌类型、它的摘要，以及三个操作（`open`、`authenticate`、`revoke`）。
  **`Token::issue` 每次都返回零字节**：这个服务开过的每个会话都是同一个令牌，谁学到它，谁就握着全部会话。
  这就是会话固定，而且光读路由是看不出来的——所以规格会登录两次；
- `tests/support/service.rs`——驱动一个*进程*的装置，客户端能发 `Cookie` 或 `Authorization` 头，也能把
  `Set-Cookie` 读回来。之前的夹具在进程内驱动服务，而那恰好是测不了 header 的形状；
- 依赖里的 `sha2`（在 `kiln:scaffold:begin` 块内）：上面的摘要需要一个哈希，这是这门课第一个*快*哈希。

### `src/session.rs`

`Token::issue` 必须向系统要随机数——`SESSION_BYTES` 字节，小写十六进制，与确认令牌同一种写法——要不到就报
`Error::TokenGeneration`。这里有意不留回退处理：这个服务自己编得出来的令牌，攻击者也编得出来。

### `src/login.rs`（新文件）

`Credentials`——一个邮箱和一个原始密码——以及 `log_in(pool, credentials) -> Result<(Token, Email), Error>`，
它：

1. 解析地址和密码（`mailer/1.10-domain-types` 步：解析在前）；
2. 按地址读出订阅者的 `id`、`password_hash` 和 `status`；
3. 用 `Argon2` 拿候选密码去核对存下来的 PHC 字符串——绝不比较字符串；而"没有这个地址"和"密码错了"回同一个
   `401`；
4. 对不是 `active` 的订阅者回 `403`——密码是对的，账号还不能用；
5. 开会话（`session::open`），返回令牌和地址。

### `src/http.rs`

- 三条路由：`POST /login`、`POST /logout`、`GET /me`。`/login` 回 cookie
  （`{SESSION_COOKIE}={token}; Path=/; HttpOnly; SameSite=Lax; Max-Age=…`），body 里是订阅者；`/logout` 把行
  作废*并且*清掉 cookie（`Max-Age=0`）；`/me` 回会话所属的地址；
- 一个 `credential` 助手，从 `Authorization: Bearer …` 或 `Cookie` 头里取令牌——cookie 是一*串 `name=value`
  对*，不是什么恰好含着令牌的字符串——格式对但没人发过的令牌是 `401`，压根不是令牌的文本是
  `mailer/1.12-token` 步那个 `400`；
- 状态表新增：没有可用会话 `401`、凭证对不上 `401`、订阅者从未确认 `403`；`/me` 与 `/logout` 在没有数据库时
  是 `503`，和其他需要数据库的路由一样。

### 规格判什么

| the test | 断言 |
| --- | --- |
| 一次登录 | `200`，`Set-Cookie` 带着 64 个十六进制字符，并有 `HttpOnly`/`SameSite`/`Path=/`，body 里是地址 |
| 一个令牌，两种通道 | cookie 与 `Authorization: Bearer` 在 `/me` 上都回 `200`；什么都没有、以及格式对但没人发过的令牌，都回 `401` |
| 密码错、地址不存在 | `401`，两次都不给 cookie |
| 从未确认的订阅者 | `403`，不给 cookie |
| 一次登出 | `204`，cookie 已过期，之后那个令牌回 `401`——行里的 `revoked_at` 已设 |
| 过期的会话 | 把行里的死线移到过去就够了：`401` |
| 两次登录，以及客户端自带的令牌 | 每次令牌都不同，自带的那枚从不被采纳，也没有哪一行的 `token_hash` 就是令牌本身 |

## 完成标准

- `kiln run mailer/1.16-sessions` — 规格通过
- `kiln check mailer/1.16-sessions` — 每个 must 闸门都是绿的
- 对运行中的服务登录，拿到一个 cookie，手工发回 `/me` 也能用
  （`curl -c jar -d '{"email":…,"password":…}' /login`，然后 `curl -b jar /me`）
- `SELECT token_hash FROM sessions` 里是一个 64 字符的摘要，它*不是* cookie 带的那个值；两次登录留下两行
- 登出之后同一个 cookie 回 `401`，那一行的 `revoked_at` 已设

## 陷阱

1. **令牌不随机。** 一个计数器、一个时间戳、或者从订阅者地址推出来的值，都是能被猜到或预测的令牌——脚手架那个
   固定值是最极端的例子：所有会话共用一个。规格里的两次登录就是抓它的。
2. **把令牌存下来。** 一个存着令牌的 `token_hash` 列，让每一份备份、每一个副本、每一次支持会话里的
   `SELECT *`，都变成一串还活着的会话。摘要把这个值挪到了只有客户端和某一个请求的内存见过的地方。
3. **每个请求都跑 Argon2。** 用密码哈希器去哈希会话令牌，看着像谨慎的选择，结果是每个已认证请求都要付出几十
   毫秒——而会话之所以是令牌而不是密码，理由正在这儿。高熵密钥用快哈希，可猜的用慢哈希。
4. **采纳了送来的东西。** 登录*之前*先读会话 cookie，登录之后拿那一行接着用，就是会话固定：在受害者浏览器里
   埋了一个令牌的攻击者，会随着受害者的登录一起被登进去——因为受害者的登录把攻击者的令牌转正了。登录永远签发。
5. **只在数据库里登出。** 把行作废，值还留在浏览器里，离"再一次生效"只差一次误缓存、一行日志或一次恢复。作废
   和清 cookie 必须在同一个响应里。
6. **忘了检查状态。** 认证是"你是谁"，*授权*是"你能做什么"——但一个把未确认订阅者认证通过的服务，已经把第二个
   问题答错了，因为确认是"这个地址够得着"的唯一证据。
7. **cookie 属性写错。** 没有 `HttpOnly`，一个 XSS bug 就能读走会话；没有 `SameSite`，别的站点一个表单 POST
   就能花掉它（在另一个源上放一份*注册*表单的副本就够了）；没有 `Max-Age`，会话活到浏览器关闭，甚至更久。
   这次构建里 `Secure` 不能设（还没有 TLS，而一个永远送不到的 `Secure` cookie，就是登录不上去）——它是
   `mailer/1.21-container` 步要补的第一件事，这里写进陷阱，是为了让这个省略是一个决定，而不是疏忽。
8. **泄露了错在哪一半。** "没有这个地址"和"密码错了"是同一个 `401`，因为这个差别是关于"谁注册过"的事实。这个
   服务终归还是泄露了*一些*——重复注册是 `409`（`mailer/1.11-signup` 步），未确认登录是 `403`——诚实的规则是：
   想清楚哪些答案值得这份泄露，把它写下来，并且不要不小心泄露。
9. **把令牌写进日志。** 日志文件里的会话令牌，是任何拿到日志的人都能用的会话——同 `mailer/1.13-email-port`
   步对确认链接定的规矩。`Token` 没有 `Display`，`Debug` 会打码，就是为了让这条不容易误犯。
