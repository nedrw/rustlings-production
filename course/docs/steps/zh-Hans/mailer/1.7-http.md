# HTTP 骨架：路由、提取器，以及诚实的 404 和 405

## 为什么

从这一步起，服务真的能在网络上说话了，而它第一层对外接口就是日后一切的基准。这一步里的两个决定，
之后都很难再改。

第一个：*没人应答*的请求长什么样。对任何未知路径都回 200 加个 HTML 页面，或者干脆回空正文的服务，
逼着每个客户端去解析散文才知道出了什么事。反过来，一个说得出有哪些路由的 404，一个点名了本来可用方法
的 405，能把一次集成调试从一下午变成五秒钟。

第二个：`/healthz` 到底代表什么。它回答的是*进程*的死活，不是依赖的死活。因为数据库不在就变红的存活
探针，会把一个正好好干活的进程重启掉——至于那些可能掉线的部分，1.9 步会补上一个就绪应答。

## 任务

脚手架加上了 `axum` 和 `tokio`，并把 `src/http.rs` 放到位，里面有两个桩：`router()` 和 `serve()`。
把它们填上，再接进二进制：

- **`router()` 把整个对外接口当成一个值返回。** 不碰 socket，不需要运行时：测试构造它，往里塞一个请求
  （1.8 步的 app 工厂就建在这上面）。
- **`GET /healthz`** 回 `200`，正文是 `{"status":"ok"}`，除了进程本身不碰任何东西。
- **未知路径回 `404`**，正文是一份说明这件事的 JSON——不是空正文，也不是一个装作 404 处理函数的兜底
  路由。
- **路径存在、方法不对回 `405`**，同样的 JSON 形状，*外加* `Allow` 头。路由自己清楚一条路径有哪些方法，
  兜底路由不清楚——所以这里是在路由自己的答案上补一笔，而不是把它换掉。
- **`HEAD /healthz`** 回 `200` 且没有正文——这就是框架里 `GET` 的含义，它应该保持这样。
- **`serve(config, id)` 绑定配置里的地址**，但记进日志（`address` 字段）的必须是**实际绑上的那个**，然后
  一直服务到进程停下。端口 `0` 的意思是"随便给个空闲的"，于是日志里那个地址是调用方唯一能拿到端口的
  途径——把配置里的 `:0` 写进日志的服务，谁也连不上。
- **绑定失败是一种有类型的失败**，不是 panic：消息里带上那个地址，`Error` 里有它自己的变体，
  退出码表里有它自己的一行，`serve` 上有一节 `# Errors`。
- **二进制跑在运行时上**（`#[tokio::main]`），它原来的 `Idle` 路径现在改为服务，而不是说没事可做。

## 完成标准

- `kiln run mailer/1.7-http` — 规格通过
- `kiln check mailer/1.7-http` — 每个 must 闸门都是绿的
- `MAILER__LOG__FORMAT=json cargo run -- --listen-port 0` 打印一个带绑定地址的 `listening` 事件，
  而 `curl -i <that address>/healthz` 回 `200`
- `curl -i <address>/nope` 回 `404`，正文是 JSON；`curl -i -X POST <address>/healthz` 回 `405`，
  并带上 `allow: GET,HEAD`
- `cargo run -- --listen-port 1; echo $?` 以非零退出码退出，并说出它没能绑上的那个地址

## 陷阱

1. **拿兜底路由顶替回退处理。** 诚实的是 `Router::fallback`；而一个回 404 的 `.route("/{*rest}", ...)`
   把方法也一起吞了，`POST /healthz` 于是得到一句*"没有这样的路由"*——规格在 405 那条断言上失败：路由压根
   没机会说出这条路径认哪些方法。
2. **把配置里的地址记进日志。** 用了 `--listen-port 0`，日志里写 `127.0.0.1:0`，读到它的调用方谁也连不上。
   规格以*"服务必须记下它绑定的地址 … 而它从来没有记过"*失败。
3. **在 `async` 里用阻塞式 socket。** 在 Tokio 任务里调 `std::net::TcpListener::accept` 会堵住工作线程：
   第一个请求答完，第二个永远等不到。规格一直挂到截止时间，报*"服务没有接受连接"*。
4. **404 配空正文。** 状态码没错，但人什么也看不到：规格以*"正文为空的 404 什么都没告诉调用方"*失败。
