# Typed configuration with a documented override order

## WHY

一个服务同时从四个地方读它的设置项：代码里的默认值、二进制旁边的文件、启动它的那个进程的环
境，以及人手动敲的命令行旗标。每一次以「在我机器上是好的」开头的故障，都是在争这四者里究竟谁赢
了。这个覆盖顺序不是留到以后再发现的细节：它就是契约，而一个说不清自己被配置成什么样的服务，
谁也没法运维。

写下来还有第二个理由。一个没有任何来源提到的设置项，*只有*在你本来就知道答案的情况下才有显而易
见的答案——所以像 `MAILER__LISTEN__PROT` 这样的笔误必须被明确拒绝，而不是悄悄换成端口 8080。而
一个在仓库里还带着默认值的密钥并不是密钥：它是一个比泄漏它的那次部署活得更久的密码。

## TASK

脚手架已经把 `src/config.rs` 放到位：设置项和它们的默认值以类型的形式给出、带消息的错误类型，
以及两个还什么都没做的桩（`Config::load`、`Config::report`）。它也加上了这个文件需要的两个依赖。
本步骤的其他一切都归你：

- **覆盖顺序就是契约**：默认值 < 文件 < 环境 < 命令行旗标。每个来源只改动它提到的那些设置项；后
  面的来源没有提到的设置项，保留前面来源给它的值。
- **文件**是工作目录里的 `mailer.toml`，或者 `--config <path>` 指名的路径——后一种情况下默认文
  件*不*读。每个设置项都是可选的；服务不认识的设置项是错误，不是默认值。默认文件缺失是正常
  的；命令行上指名的文件必须存在。
- **环境**：`MAILER__LISTEN__HOST`、`MAILER__LISTEN__PORT`、`MAILER__LOG__LEVEL`、
  `MAILER__LOG__FORMAT`、`MAILER__DATABASE__URL`——前缀是 `MAILER__`，设置项名字的各段之间是
  `__`。带这个前缀却不对应任何设置项的环境变量，会被按名字拒绝。
- **命令行旗标**：`--listen-port <port>`，加上给文件层用的 `--config <path>`，再加上
  `--check-config`。数据库 URL 故意没有对应的旗标：在命令行上敲出来的密钥最后会进到进程列表
  里，也进到每一条 shell 历史里。
- **用不了的值**要被拒绝，并带上设置项、值和它的来源：`log.format = "xml"` 要报出 `log.format`、
  `xml`，以及它来自哪个文件或哪个环境变量。永远以非零退出——被拒绝的配置不能被悄悄降级成默认
  值。
- **`--check-config`** 打印生效的配置并成功退出：`database.url`、`listen.host`、`listen.port`、
  `log.format`、`log.level`，每项一行 `key = value`，按 key 排序。
- **密钥只被标明、从不打印**：`database.url` 在没有任何来源设置过它是 `<unset>`，有来源设置过就
  是 `<redacted>`（已打码）——配置报告是要被人贴进 issue 里的东西。
- **配置在任何其他事情发生之前就被加载**，所以一份坏配置会拦住服务，哪怕它启动时没带
  `--check-config`。`--help` 和 `--version` 是例外：关于这个二进制的问题不该依赖服务的状态。
- **你要提交的是**带占位值的 `mailer.toml.example`；装着真值的那个文件进 `.gitignore`。

## DONE WHEN

- `kiln run mailer/1.4-config` — 规格通过
- `kiln check mailer/1.4-config` — 每个 must 闸门都是绿的
- `cargo run -- --check-config` 打印这五个设置项并以 0 退出
- `MAILER__LISTEN__PORT=9111 cargo run -- --check-config` 显示端口 9111
- `MAILER__LISTEN__PROT=9111 cargo run -- --check-config` 点名那个环境变量并以非零退出
- `MAILER__DATABASE__URL=postgres://user:pw@localhost/db cargo run -- --check-config` 打印
  `<redacted>`，密码在输出里任何地方都不出现

## TRAP

1. **把文件错误吞掉。** `read_to_string(path).ok()` 把「你给我的路径不对」变成「我用了默认值」，
   服务于是带着另一个主机的设置项启动。规格以
   *"the report must mention \"absent.toml\""* 失败——你指名的那个文件，正是报告必须说出来的东西。
2. **按读取顺序而不是生效顺序叠加各层。** 如果环境在旗标之后应用，`--listen-port 9222` 就输给了
   恰好被这次部署设置上的 `MAILER__LISTEN__PORT`，而 `--check-config` 里显示的端口不是那个人要的
   端口。
3. **把密钥打印出来。** `--check-config` 的输出里有 `database.url`，看着挺有用，直到它被贴进
   issue。规格会以 *"the report must mention ..."* 失败，或者输出里出现原始的 URL，而这个 URL
   必须轮换。
4. **放行不认识的环境变量。** 一个带兜底分支的 `match`，那个分支忽略了 `MAILER__LISTEN__PROT`，
   于是服务按默认端口启动；部署看起来一切正常，然后什么都不工作。
