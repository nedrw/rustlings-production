# 授权边界：订阅者只能读到自己的数据

## 为什么

认证回答的是*这是谁*，对*他能看到什么*一个字都没说——而现实世界里的数据泄露，大多就活在这两者之间的缝隙里：
一条路由把认证做得很到位，然后把它收到的那个 id 对应的东西原样奉上。

这一步只加一条路由——`GET /subscribers/{id}/deliveries`，即某个订阅者被欠过哪些消息——而它的全部内容就是
那条边界：

- **路径里的 id 不是身份。** 会话说明谁在问，路径说明在问什么；一个相信路径的处理函数，等于把决定权交给了
  写请求的人。这个比较只有一行，而且必须放在读任何东西*之前*；
- **别人拥有的资源，对这个调用方来说不存在。** 答案是 `404`，不是 `403`。`403` 说的是"这东西在这儿，但它不是
  你的"——那是关于别人数据的事实；一条这么说的路由，就是在替所有来问的人枚举 id。让两个答案*完全一样*才是要
  点，所以这一步的规格连 body 都比；
- **查询本身也要带范围。** 处理函数里那一行比较，是关于这个处理函数的事实；`WHERE subscriber_id = $1` 是关于
  语句的事实。两个都要，因为后者是后来的路由忘不掉的：没有范围的查询加上漏掉的检查就是泄露，而没有范围的
  查询，离它只差一次评审。

`WHERE` 在这里还有第二个理由，而且正是生产里会现形的那个：先全取出来、再在 Rust 里过滤，这份列表*曾经*躺在
进程的内存里——日志行、panic 消息、指标维度，或者下一次重构的响应体。数据库是唯一能把边界一次定死的地方。

## 任务

这一次没有脚手架：一条路由、一个查询、一个错误变体，而 `mailer/1.16-sessions` 与
`mailer/1.17-newsletter` 两步已经给齐了所有牵涉的形状。规格就是契约。

### `src/newsletter.rs`：读

`history(pool, subscriber) -> Result<Vec<DeliveryRecord>, Error>`：某个订阅者被欠的那些副本，最新的在前，
形如 `{issue, subject, sent_at, attempts}` 的列表。有两个细节，值得照这一步的参考解抄，而不是自己再摸一遍：

- 语句里没有 `INSERT`，为拿主题 `JOIN` 了 `issues`，而它唯一的参数是订阅者（来自会话，永远不来自路径）；
- `sent_at` 用 `sent_at::text` 选出。这个服务在 SQL 里读时钟（`now()`），把 `TIMESTAMPTZ` 读进 Rust，就等于
  依赖一个这里别处都用不着的时间 crate。

### `src/http.rs`：路由

`GET /subscribers/{id}/deliveries`，要认证：

1. 照常的就绪检查（要数据库；这条路由别的都不要）以及从 `Cookie` 或 `Authorization` 头取 `identity()`——
   没有会话就 `401`；
2. 把 `identity.subscriber` 和路径里的 `id` 比一比；不一样就回 `Error::NotFound { what: "subscriber" }`
   ——同时把被问的是哪个 id 记进日志，因为那才是有意思的事件；
3. 一样就回 `Json(history)`。

### `src/error.rs`

`Error::NotFound { what: &'static str }`——退出码 `2`、状态 `404`，并且有意让"它不是你的"和"它从来不存在"
共用一个变体。

### 规格判什么

| the test | the claim |
| --- | --- |
| 订阅者要自己的 id | `200`，通讯的主题，以及一封真的投递过的消息的 `sent_at` |
| 别人的 id，以及一个没人有的 id | 两次都 `404`，body 相同——两者无法区分 |
| 没有会话，以及一枚没人被发过的令牌 | 两次都 `401`：是"谁都不是"，不是"是别人" |
| 两个订阅者、两期已发布的通讯 | 每份历史都是调用方自己的列表——一条忘了 `WHERE` 的查询，会以另一个订阅者的行现形 |

## 完成标准

- `kiln run mailer/1.18-authz-boundary` — 规格通过
- `kiln check mailer/1.18-authz-boundary` — 每个 must 闸门都是绿的
- 对运行中的服务，`GET /subscribers/<你自己的 id>/deliveries` 回 `200` 和一个 JSON 列表；把 id 换成*别人的*，
  回 `404`——状态和 body 都跟一个根本不存在的 id 一样
- 服务把这次被拒的尝试连同两个 id 一起记进日志，于是这条边界既看得见，又没法被利用

## 陷阱

1. **相信路径。** `SELECT … WHERE subscriber_id = $path_id` 就是一句话写完的泄露：任何已认证的调用方，随便敲
   一个数字就能读别人的历史。会话里的 id 是处理函数唯一可用的 id。
2. **取回来再过滤。** 先读出所有行、再留下调用方那份，在测试里看不出来，在生产里是错的：别的行进过内存，而内存
   正是日志、追踪和下一次重构会去读的地方。边界该落在语句里。
3. **别人资源回 `403`。** 它看起来是有礼貌的答案，其实是泄露：`403` 等于确认这个 id 存在，把一条受保护的路由
   变成了枚举器。两种情形都 `404`——而且 body 相同，这也是这份规格要比 body 的原因。
4. **读完再比较。** 先把活干了，再看它是谁的，会通过时序泄露、通过副作用泄露（写比读更难收回），也会通过中间写下
   的每一行日志泄露。检查放在最前面，或者查询自带范围——最好两个都做。
5. **只认证、到此为止的路由。** 评审里最常见的那种形状：调了 `identity()`，用了路径里的 id，而会话里的订阅者
   再没被提起。处理函数顶部的认证不是授权，它是授权的输入。
6. **拿错的键去限定范围。** 用调用方能控制的东西来限定范围——查询串里的邮箱、"租户"头、body 里的 id——是同一个
   bug 多绕几个弯。请求伪造不了的那个值，只有会话解出来的那个。
