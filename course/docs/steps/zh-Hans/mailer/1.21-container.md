# 容器化与部署：多阶段镜像、探针、迁移顺序

## 为什么

这条 track 建起来的一切，都是因为*你*启动了它：目录里的一个二进制、shell 里的一个数据库 URL、你自己拉起来的
一台邮件服务器。而部署是同一个服务被别人家的机器启动，那台机器从没见过你的笔记本——这两者之间只隔着一件东西：
**镜像**。镜像里装了什么、监听在哪儿、开始接流量之前先做什么、有多大，都是这一步要做的决定，而每一个都属于
"在你机器上看着挺好、在第一台真机器上就出事"的那一类。

四个决定，每个都有做错的方式：

1. **镜像里有什么，就是有什么。** 单阶段构建会把 `cargo`、`rustc`、`cc`、registry、源码和每一个构建脚本都留在
   你交付的东西里。工具链不是载荷；一个装着编译器的镜像，就带着编译器的漏洞、编译器的体积，以及一片没人审计的
   额外攻击面。所以分两个阶段：一个有全部东西然后消失，一个只有二进制、信任库和一个用户；
2. **它必须小**，而"小"是一个数字。每个镜像都要跨网络 `COPY`、都占节点上的空间，16 MB 和 900 MB 的差别，就是
   "滚动更新期间能部署完"和"不能"的差别。这一步规格里的体积上限不是审美偏好：它是"*运行*阶段真的是运行环境"
   这条断言，而最常见的出错方式，就是把 builder 留在了交付镜像底下；
3. **它必须监听在部署够得着的地方。** `mailer/1.4-config` 步把监听地址做成了设置项，默认 `127.0.0.1`——在笔记本
   上是对的，而一个只监听自己 loopback 的容器，是没人够得着的容器。一个没有东西在后面的发布端口，看起来和坏掉的
   镜像一模一样，而实际上进程健康得很；
4. **它必须说得出自己什么时候活着、什么时候就绪**，而这是两个不同的问题（`mailer/1.9-postgres` 步）：存活是
   这个进程还在，就绪是 schema 已经是最新的。它们在 `Dockerfile` 里的形态是同一个镜像回答两条路由——让它们成真的
   是编排器真的*在用*它们，让它们诚实的是数据库不在时两者会给出不同答案。

**而这一步真正的主张是**：*镜像跑的是你测过的那个二进制*。这是容器对前二十步所有工作许下的承诺——所以这一步的
闸门（`container-repro`）会从你的树重建镜像，问镜像里的二进制和问你宿主机上的二进制同一个问题，而这个比较，
宿主机上任何一次绿灯都替代不了。

## 任务

脚手架放了三个文件，第一个就是那个洞：

- `Dockerfile` 只有一个阶段：`FROM rust:1.98-alpine`、`COPY . .`、
  `RUN cargo build --release --locked`、`ENTRYPOINT` 指向镜像里的二进制。它是一个能用的镜像，而
  `tests/spec_image.rs` 里每一条主张都会在它身上失败；
- `.dockerignore`——没有它，*宿主*的 `target/`（几百 MB）每次构建都会被当作构建上下文送出去，`.git/` 也跟着走；
- `tests/support/container.rs`——规格用的夹具：每次运行构建一次镜像，带着发布端口启动它，从外面问它 HTTP 问题，
  在它里面跑命令，报告它的大小。它从不拉镜像：缺基础镜像是一句指向 `kiln images pull` 的话。它还挂载一个构建
  缓存，并把它的路径作为 `CARGO_TARGET_DIR` 传进去——是"提供"，不是"强加"：忽略这个参数的 `Dockerfile` 正常
  构建，接受它的则复用上次编译的成果（挂载*不能*做什么，见陷阱 3）。

### `Dockerfile`

两个阶段，第二个从空白开始：

```dockerfile
FROM ${BUILDER} AS builder      # the toolchain: build-time only
  ... build the binary ...
FROM ${RUNTIME}                 # alpine + ca-certificates + one user
COPY --from=builder /src/mailer /usr/local/bin/mailer
USER mailer
ENV MAILER__LISTEN__HOST=0.0.0.0
ENTRYPOINT ["/usr/local/bin/mailer"]
```

- **依赖层单独放在最前面**，配一个桩 `src/`：它只在 `Cargo.toml`/`Cargo.lock` 变化时才动，于是改一行代码只需要重编
  一个 crate，而不是整棵树。桩必须能过这个 workspace 的 lint（`missing_docs = "deny"` 是全 workspace 的）；
- **`COPY --from=builder`** 就是让第二阶段变小的那一行：跨过去的是二进制，不是工作区。它*从*哪个路径拷，必须在
  夹具挂载的构建缓存之外（见陷阱 3）；
- **`USER`** 放在入口点之前：不管怎样，进程都是容器里的 pid 1，而一个不需要任何特权的服务就该没有任何特权；
- **`MAILER__LISTEN__HOST=0.0.0.0`** 作为镜像配置，因为那个默认值是部署的决定，而这就是一次部署。别的什么都不
  烘进镜像：数据库 URL、SMTP 主机、日志级别都以环境变量到达，这正是 `mailer/1.4-config` 那套分层存在的理由；
- 镜像**在启动时跑迁移**（二进制自己做的，`mailer/1.9-postgres` 步）——镜像里不带迁移工具，`sqlx-cli` 不在里面。

### 基础镜像来自 `kiln images pull`

这一步声明两个镜像，它们都是构建期输入：`rust:1.98-alpine`（builder）和 `alpine:3.20`（runtime）。
`kiln check mailer/1.21-container` 会在任何构建之前跑 `images` 闸门，缺哪个就点名拉取命令；构建从不为它们上网
（`--pull=never`）。在镜像站后面，同样的镜像住在另一个名字下（`docker.1ms.run/library/rust:1.98-alpine`），
这也是 `Dockerfile` 把两个名字都收作构建参数、夹具传进这台机器引擎实际拥有的那个名字的原因。

### 探针

不用写——从 `mailer/1.9-postgres` 步起就在了。这一步的活是让它们*够得着*：`/healthz` 从容器外回 200，没有数据库
时 `/readyz` 回 503 并说 `no database is configured`，schema 就位之后 `/readyz` 才转 200。规格从进程外面检查这
三件事，而那是唯一能检查探针的地方。

### 规格判什么

| the test | the claim |
| --- | --- |
| `the_image_runs_this_service_and_is_reachable` | 通过发布端口，`/healthz` 回 200；`/readyz` 回 503 并点名缺数据库；未知路径回的 404 body 与宿主机二进制一致；日志说它在监听 |
| `the_image_is_small_because_it_is_not_a_build_environment` | 没有 `cargo`、没有 `rustc`、没有 `cc`、没有 `/src`，二进制在——而镜像小于 25 MB |
| `the_image_does_not_run_as_root` | `id -u` 不是 0，而且那个用户存在 |
| `the_container_migrates_before_it_serves` | 配上数据库后，`/readyz` 转绿，而 schema 就在数据库里 |

## 完成标准

- `kiln run mailer/1.21-container` — 规格通过（第一次构建要几分钟：它要在 builder 里编译整棵依赖树；之后的构建
  是秒级）
- `kiln check mailer/1.21-container` — 每个 must 闸门都是绿的，含 `container-repro`：它从你的树重建镜像，按体积
  预算判它，并把镜像里的二进制给出的配置报告与你宿主机上二进制给出的那份做比较
- `podman run --rm -p 8080:8080 mailer:dev`，然后 `curl -i localhost:8080/healthz` 从你的机器回 200——不是从
  容器里面
- `podman image inspect mailer:dev --format '{{.Size}}'` 是几十 MB，不是几百
- `podman run --rm mailer:dev id -u` 打出一个不是 0 的数
- `podman run --rm mailer:dev sh -c 'command -v cargo'` 失败：工具链没有被打包进去

## 陷阱

1. **监听在容器自己的 loopback 上。** 镜像从 `mailer/1.4-config` 继承了 `listen.host = 127.0.0.1`，发布了端口，
   却不应答任何人。症状是最糟的那一类：容器起来了，日志说 `listening`，容器内部的健康检查也过，而外面看到一条
   石沉大海的连接。容器需要的是 `0.0.0.0`。
2. **依赖层的桩必须能过这个 workspace 的 lint。** 空的 `src/lib.rs` 会在 `missing_docs = "deny"` 上失败，而这个
   失败发生在构建*内部*——整棵依赖树都编译完之后，被 builder 用一行截断的话报出来。修法是两行
   （`printf '//! Stub.\n' > src/lib.rs`），没见过的话就是一个小时。
3. **缓存挂载不是一层。** 夹具挂载一个构建缓存，并把它的路径作为 `CARGO_TARGET_DIR` 传进去，这才让第二次构建便宜
   ——而这也意味着留在 `$CARGO_TARGET_DIR` 里的二进制*不在*镜像里。所以 builder 的最后一步要在同一个 `RUN` 里把
   二进制从挂载路径拷出来，运行阶段再从那儿拷：`COPY --from=builder /src/target/release/mailer` 在 target 目录
   是挂载时会构建成功，产出一个空无一物的镜像。这是 CI 缓存挂载给每个 Rust 项目设的陷阱；这里你是故意遇上它的。
4. **把缓存挂在工具链上。** `/usr/local/cargo` 是镜像放 `cargo` 本体的地方；把 registry 缓存挂到那儿会替换掉它，
   构建死于 `cargo: not found`。缓存路径是 `/usr/local/cargo/registry`。
5. **只在你机器上存在的基础镜像名。** `FROM rust:1.98-alpine` 在能连上 Docker Hub 的地方可行，在镜像站后面就
   失败——那里的镜像是 `docker.1ms.run/library/rust:1.98-alpine`。基础镜像的名字是部署的事实，构建参数才是它该
   待的地方。同一份存储还可能把同一个仓库路径存了*两遍*——如果它是经由不止一个镜像站填的，一个架构一份——引擎
   会在构建进行到好几个阶段时，用 `image not known` 拒掉不属于这台机器的那一份。（夹具挑的是这个引擎实际运行的
   架构，所以该信的那次拉取是 `kiln images pull`。）
6. **手工重建镜像，然后称之为已验证。** `podman build` 绿了只说明文件解析得开；规格里那四条主张是关于镜像*做什么*
   的，而最常失败的两条（体积、可达性）从构建输出里根本看不见。去跑规格。
7. **把配置烘进镜像。** `ENV MAILER__DATABASE__URL=postgres://…:secret@…` 会把一份凭据放进每一层、放进
   `podman history`、也放进它被推到的每一个 registry。镜像声明的是*部署形状*的事实（监听地址、端口）；一切密钥
   都在运行时到达。
8. **打包一个迁移工具，而不是做迁移。** 另一种设计——把 `sqlx-cli` 烘进镜像、在入口脚本里跑 `sqlx migrate run`
   ——在镜像里放了第二份 schema 逻辑，并把启动顺序变成一段 shell 脚本必须做对的事。二进制已经在服务之前做迁移，
   而那就是规格检查的顺序。

## 延伸阅读

- [Docker: multi-stage builds](https://docs.docker.com/build/building/multi-stage/) — 这一步用的模式，包括
  `--from` 与构建参数的写法
- [Alpine Linux: musl and `apk`](https://alpinelinux.org/about/) 与 [`rust:alpine`](https://hub.docker.com/_/rust)
  — 为什么 musl 这条路比 glibc 小，以及它付出什么代价（C 库的差别，和一个要自己加上的链接器）
- [The OCI image specification](https://github.com/opencontainers/image-spec) — 层、manifest、config：
  `podman image inspect` 打出来的东西，以及为什么挂载不属于其中任何一样
- [Kubernetes: liveness, readiness and startup probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)
  与 [the pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination) —
  谁在什么时候调 `/healthz` 和 `/readyz`，以及 `SIGTERM` 该触发什么（`mailer/1.14-worker` 的排干死线才让这
  件事可承受）
- [12factor: backing services](https://12factor.net/backing-services)、[12factor: config](https://12factor.net/config)
  — 数据库 URL 在运行时才挂上去这条规则，也是镜像不带任何凭据的原因
- [Google: distroless images](https://github.com/GoogleContainerTools/distroless) — 这一步之后的下一个台阶：
  没有 shell、没有包管理器，除了二进制和它的库什么都没有
- [Testcontainers](https://testcontainers.com/) — 这一步的夹具手工抄了它的形状，给不想自己维护的项目用
