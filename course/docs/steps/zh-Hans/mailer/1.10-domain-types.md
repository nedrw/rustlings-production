# Domain types: parse, don't validate

## WHY

一个从陌生人那里收文本的服务，一辈子都在判断那些文本能不能用。这件事常见的形状是：一个哪儿都去的
`String`，加上某个在边界上调用的 `validate_email`——然后是处理函数里第二次调用，因为第一次不够，
再然后是第三次，而没有人记得把它加上。类型里没有一句话说这个地址被检查过，于是什么都不可信，于是
一切都要再检查一遍。

这一步用两样东西替换掉它：

- **一个只有解析器能构造的类型**：`Email`、`SubscriberName` 与 `Password` 都持有一个私有的
  `String`，没有公开构造函数，除了 `parse` 什么都不给。一个收 `Email` 的函数，是**被告知**过这个
  地址检查过的——由编译器告知，不是由一句注释。
- **一个回答值、而不是回答判定的解析器**：结果不是"合法"，而是这个服务要存的规范形式。规范化就该
  在这里：`Ada@Example.com` 与 `ada@example.com` 是同一个订阅者，而第 `mailer/1.9-postgres` 步的
  `UNIQUE (email)` 比较的是字节。在这里一次定下来，正是让第 `mailer/1.11-signup` 步不必再去想它
  的原因。

还有第三个决定，更小、也更容易做错：**密码是密钥，而密钥不是一个 `String`**。它不被 trim（空格是
它的一部分），它不会从 `{:?}` 里出来，也没有任何失败消息把它引回去——消息最后会进日志行（第
`mailer/1.6-logging` 步），而日志里的密码是一个必须被轮换的密码。

## TASK

脚手架加了 `src/domain.rs`，三个类型、各项限额，没有任何检查：每个 `parse` 都原样保留它收到的东西，
而 `Password` 带着 derive 出来的 `Debug`。把它们变成解析器，并把这些类型放到其余代码够得着的地方。

### The rules, and the limits

这些值是契约的一部分——规格问的正是这些数字：

| type | accepts | refuses |
| --- | --- | --- |
| `Email` | 至多 `MAX_EMAIL_LENGTH`（254）字节；恰好一个 `@`；本地部分 1–64 字节，由字母、数字、`.`、`_`、`+`、`-` 组成，两端都不是点、也不含 `..`；域由点分隔的标签组成，每个标签由字母、数字与 `-` 组成，两端都不是 `-` | 没有 `@` 或多于一个；本地部分或域为空；域里没有点或含空标签；上面那些集合之外的任何东西（包括空格、控制字符与非 ASCII、带引号的本地部分、IP 字面量形式的域） |
| `SubscriberName` | trim 之后 1–100 个字符；词与词之间单个空格；任何字母，包括非 ASCII | 空或只有空格、控制字符（包括 `\n` 与 `\t`）、超过 100 字符 |
| `Password` | 12–128 个字符，**完全按输入的样子** | 少于 12、多于 128、控制字符 |

解析器产出的是*规范*形式：

- `Email`：trim 过、转成小写——整个地址都转，因为数据库必须只看见一种拼法。
- `SubscriberName`：trim 过，连续的空格压成一个。
- `Password`：不变。`as_str()` 返回的正是调用方输入的东西，空格和所有的一起。

规范意味着解析器是一个不动点：解析它自己产出的东西什么也不改。规格在一个生成的地址集合上检查这条
性质，而不只是在几个样本上。

### The refusal

往 `src/error.rs` 加一个变体，三个解析器都用它：

```rust
Error::InvalidInput { field: &'static str, expected: &'static str }
```

`field` 是 `"email"`、`"name"` 或 `"password"`；`expected` 是这个值本该是什么，写成能进消息的样子
（上表就是来源；规格断言每一条里的一个片段）。消息读起来是 `` the email is not an address with
exactly one `@` ``。

被拒绝的那个值有意**不**放进变体里：它可能是密码。把这个变体也加进退出码表——调用方送来的值该由
调用方去修，那是退出码 `2`（也是第 `mailer/1.11-signup` 步里一个 400 的原料）。

### Where they live

`src/lib.rs` 里的 `pub mod domain;`，因为服务其余部分马上要开始收这些类型。别的地方先什么都不改：
没有路由收 `Email`、没有处理函数返回它——这一步是关于这些值本身，而规格从 crate *外面*判它们，通过
一个按 path 依赖你的项目的探针 crate（和第 `mailer/1.5-errors` 步对错误枚举用的是同一个手法）。

### What the spec does not test, and why

"不存在*别的*构造函数"不是运行时事实：它是代码的形状，检查它的方式是读 `src/domain.rs`，找公开
字段、`pub fn new`、`From<&str>` 与 `Deserialize` 的实现。规格改而钉住一个错误的构造函数会弄坏的
东西——规范化、幂等、那些拒绝、以及打码——而 TRAP 一节列出要保持关着的那些后门。

## DONE WHEN

- `kiln run mailer/1.10-domain-types` — 规格通过（它会编译并运行一个探针 crate，所以第一次跑比之后
  几次久一点）
- `kiln check mailer/1.10-domain-types` — 每个 must 闸门都是绿的
- `Email::parse("Ada@Example.COM").unwrap().as_str()` 是 `"ada@example.com"`，再解析一次得到同一个值
- 规格拒绝表里的每个样本都被拒绝，而消息点名了字段和它期望什么——从不点名那个值
- `format!("{:?}", Password::parse("correct horse battery staple").unwrap())` 不含那个密码
- `cargo doc --no-deps -p mailer` 能过：一个规则只写在步骤正文里的类型，是下一个读者找不到的规则

## TRAP

1. **`Password` 上 derive 的 `Debug`。** 脚手架带着它，而它正是某天有人写下 `info!(?password, …)`
   时把密码送进日志行、panic 消息或一个 `tracing` 字段的东西。规格的 *"`Debug` reaches log lines
   and panics"* 就是那个失败从外面看到的样子。手写这个 impl，只说里面有密钥——连它多长都别说。
2. **对密码做 trim。** `value.trim()` 读起来像在整理，其实会弄坏真实的登录：以空格开头的密码就是一个
   密码。规格的 *"a password is not trimmed, collapsed or lower-cased"* 就是学员做了这个改动之后看到
   的东西。
3. **在失败里引用那个值。** `Error::InvalidInput { value, .. }` 看起来有用——直到一个密码被拒绝、
   而消息落进了日志。规格会在消息里找被拒绝的文本。
4. **第二扇门。** `pub struct Email(pub String)`、`impl From<&str> for Email`、类型上的
   `#[derive(Deserialize)]`，或者一个 `Default`——每一个都是拿到一个从未被解析过的 `Email` 的方法，
   而这个类型的全部要点就是没有这样的方法。如果值必须从 JSON 来（第 `mailer/1.11-signup` 步），
   就反序列化成一个裸字符串*并解析它*：那扇门是一个走 `parse` 的函数。
5. **在错误的地方做规范化。** 在插入点转小写、在处理函数里转、或者在查询里转（"`WHERE lower(email)
   = lower($1)`"），都意味着表里住着两种拼法，唯一约束永远不会触发，而第 1.11 步的竞态有两个赢家。
   在解析器里规范化，一次。
6. **一个接受太多的解析器。** 空字符串不是地址，`ada@example` 不是，`ada@-example.com` 也不是。它们
   每一个都在规格的拒绝表里，而每一行都是某个真实服务出过 bug 的地方。
7. **为此引入一个正则 crate。** 模式不可读、不可维护，而且——对 email 而言——众所周知地在两个方向上
   都错。上面的规则是三十行说明这个服务接受什么的代码，那是一个比 RFC 5322 允许的*更小*的主张，也是
   诚实的那个。
