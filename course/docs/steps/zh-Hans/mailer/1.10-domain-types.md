# 领域类型：解析，而不是校验

## 为什么

一个要从陌生人手里收文本的服务，一辈子都在判断这些文本能不能用。常见的写法是：一个 `String` 到处流
转，边界上有人调一次 `validate_email`——然后处理函数里又来一次，因为上一次不够；再来一次，这次没人
记得加上。类型里没有任何一句话说这个地址验过，于是什么都不能信，于是什么都要再验一遍。

这一步用两样东西替换掉它：

- **一个只有解析器造得出来的类型**：`Email`、`SubscriberName`、`Password` 各自持有一个私有的
  `String`，没有公开构造函数，除了 `parse` 什么都不给。一个收 `Email` 的函数，是**被告知**这个地址验过
  的——由编译器告诉它，不是靠一句注释。
- **一个给值、而不是给结论的解析器**：结果不是"合法"，而是这个服务要存的规范形式。规范化就该放在这
  儿：`Ada@Example.com` 和 `ada@example.com` 是同一个订阅者，而 `mailer/1.9-postgres` 步的
  `UNIQUE (email)` 比的是字节。在这里一次定死，`mailer/1.11-signup` 步才不用再操心这件事。

还有第三个决定，更小、也更容易做砸：**密码是密钥，而密钥不该是个 `String`**。它不做 trim（空格也是
它的一部分），不会从 `{:?}` 里漏出来，也没有任何失败消息把它带回去——消息最终会进日志行（
`mailer/1.6-logging` 步），而日志里的密码，就是一个必须轮换的密码。

## 任务

脚手架加了 `src/domain.rs`：三个类型、各项限额，一点检查都没有——每个 `parse` 原样返回它拿到的东西，
`Password` 还带着 derive 出来的 `Debug`。把它们变成真正的解析器，再把这些类型放到别的代码够得着的地方。

### 规则与限额

这些值是契约的一部分——规格问的正是这些数字：

| type | accepts | refuses |
| --- | --- | --- |
| `Email` | 至多 `MAX_EMAIL_LENGTH`（254）字节；恰好一个 `@`；本地部分 1–64 字节，由字母、数字、`.`、`_`、`+`、`-` 组成，两端都不是点、也不含 `..`；域由点分隔的标签组成，每个标签由字母、数字与 `-` 组成，两端都不是 `-` | 没有 `@` 或多于一个；本地部分或域为空；域里没有点或含空标签；上面那些集合之外的任何东西（包括空格、控制字符与非 ASCII、带引号的本地部分、IP 字面量形式的域） |
| `SubscriberName` | trim 之后 1–100 个字符；词与词之间单个空格；任何字母，包括非 ASCII | 空或只有空格、控制字符（包括 `\n` 与 `\t`）、超过 100 字符 |
| `Password` | 12–128 个字符，**完全按输入的样子** | 少于 12、多于 128、控制字符 |

解析器产出的是*规范*形式：

- `Email`：trim 过、转成小写——整个地址都转，因为数据库必须只看见一种拼法。
- `SubscriberName`：trim 过，连续的空格压成一个。
- `Password`：不变。`as_str()` 返回的正是调用方输入的东西，空格和所有的一起。

"规范"的意思是解析器是不动点：拿它的产物再解析一次，什么都不变。规格对一批生成出来的地址验这件事，
不是抽查几个样本。

### 拒绝

往 `src/error.rs` 加一个变体，三个解析器都用它：

```rust
Error::InvalidInput { field: &'static str, expected: &'static str }
```

`field` 取 `"email"`、`"name"` 或 `"password"`；`expected` 说明这个值本该长什么样，写成能放进消息的
样子（上表就是出处，规格会断言其中一条的片段）。拼出来的消息是 `` the email is not an address with
exactly one `@` ``。

被拒的那个值有意**不**放进变体：它可能是密码。这个变体也要进退出码表——调用方送来的值该由调用方去
修，那是退出码 `2`（`mailer/1.11-signup` 步里那个 400 也是这么来的）。

### 它们住在哪

`src/lib.rs` 里的 `pub mod domain;`，因为服务其余部分马上要开始收这些类型。别的地方先什么都不改：
没有路由收 `Email`、没有处理函数返回它——这一步是关于这些值本身，而规格从 crate *外面*判它们，通过
一个按 path 依赖你的项目的探针 crate（和第 `mailer/1.5-errors` 步对错误枚举用的是同一个手法）。

### 规格不测什么，以及为什么

"不存在*别的*构造函数"不是运行时事实：它是代码的形状，检查它的方式是读 `src/domain.rs`，找公开
字段、`pub fn new`、`From<&str>` 与 `Deserialize` 的实现。规格改而钉住一个错误的构造函数会弄坏的
东西——规范化、幂等、那些拒绝、以及打码——而 TRAP 一节列出要保持关着的那些后门。

## 完成标准

- `kiln run mailer/1.10-domain-types` — 规格通过（它会编译并运行一个探针 crate，所以第一次跑比之后
  几次久一点）
- `kiln check mailer/1.10-domain-types` — 每个 must 闸门都是绿的
- `Email::parse("Ada@Example.COM").unwrap().as_str()` 是 `"ada@example.com"`，再解析一次得到同一个值
- 规格拒绝表里的每个样本都被拒绝，而消息点名了字段和它期望什么——从不点名那个值
- `format!("{:?}", Password::parse("correct horse battery staple").unwrap())` 不含那个密码
- `cargo doc --no-deps -p mailer` 能过：一个规则只写在步骤正文里的类型，是下一个读者找不到的规则

## 陷阱

1. **`Password` 上留 derive 的 `Debug`。** 脚手架就带着它，而哪天有人写下 `info!(?password, …)`，它
   就是把密码送进日志行、panic 消息或 `tracing` 字段的那个东西。规格的 *"`Debug` reaches log lines and
   panics"* 就是这个失败从外面看的样子。手写这个 impl，只说里面装着密钥——连多长都别说。
2. **对密码做 trim。** `value.trim()` 看着像在收拾，其实会弄坏真实的登录——以空格开头的密码，那空格也是
   密码。学员改完之后看到的，就是规格那句 *"a password is not trimmed, collapsed or lower-cased"*。
3. **在失败里引用那个值。** `Error::InvalidInput { value, .. }` 看起来有用——直到一个密码被拒绝、
   而消息落进了日志。规格会在消息里找被拒绝的文本。
4. **另开一扇门。** `pub struct Email(pub String)`、`impl From<&str> for Email`、给类型加
   `#[derive(Deserialize)]`，或者一个 `Default`——每一样都能拿到一个从没经过解析的 `Email`，而这个类型
   的全部意义就是没有这种门。值必须从 JSON 来时（`mailer/1.11-signup` 步），先反序列化成裸字符串，
   *再解析它*：要开也只开一个走 `parse` 的门。
5. **在错误的地方做规范化。** 在插入点转小写、在处理函数里转、或者在查询里转（"`WHERE lower(email)
   = lower($1)`"），都意味着表里住着两种拼法，唯一约束永远不会触发，而第 1.11 步的竞态有两个赢家。
   在解析器里规范化，一次。
6. **一个接受太多的解析器。** 空字符串不是地址，`ada@example` 不是，`ada@-example.com` 也不是。它们
   每一个都在规格的拒绝表里，而每一行都是某个真实服务出过 bug 的地方。
7. **为此拉一个正则 crate 进来。** 模式不可读、不可维护，而且对 email 来说众所周知地两头都容易错。上面
   那些规则不过是三十行代码，说清这个服务接受什么——这个主张比 RFC 5322 允许的*小*得多，也诚实得多。
