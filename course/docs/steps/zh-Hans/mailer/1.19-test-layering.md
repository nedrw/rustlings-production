# 分层测试：接一台真实的邮件服务器容器

## 为什么

此前这门课里的每个测试都跑在假发送器上，那是一个有代价、也有回报的决定。回报：测试能说出*假实现收到了
什么*，于是"每个订阅者一封邮件"是对一个值的断言，而不是对一台邮件服务器的断言。代价，正是这一步要付的：
**假实现在它没有实现的一切上都可能是错的。** SMTP、头部、编码、信封地址——而生产里坏掉的恰恰是这些部分。

所以这一步是在金字塔上补一层，而不是替换掉某一层：

| layer | what it is for | what it cannot see |
| --- | --- | --- |
| 单元（在 `src/` 里） | 跟时间有关的策略（`backoff`、重试次数） | 关于服务的任何事 |
| 假实现（`tests/support/email.rs`） | 服务*决定*发什么，以及发送失败时怎样 | 真邮件服务器会不会收下 |
| 容器（`tests/support/mailpit.rs`） | 协议、实际送达的字节，以及一个真的会失败的依赖 | 几乎看不见什么——所以这一层只有一两个测试 |

让这成为*一层*、而不是"把所有东西再测一遍"的规则是：**假实现留着。** 失败注入——一个拒绝的发送器、一个
永不答复的发送器——是假实现比容器更擅长的活，因为它是确定性的、而且瞬时。容器只挣得三件它独有的事：

1. **送达的那条消息**，逐字节：邮件客户端会显示成什么样，包括那个人该点的确认链接；
2. **一个真实存在**——以及，配上新适配器之后真的*不存在*——**的依赖**：一台不在的邮件服务器，和一台接了连接
   却永远不说话的服务器；
3. **入口**：二进制本身，按部署配置它的方式来配置，而不是测试手工搭出来的状态。

**顺序无关**来自同一套夹具：每个测试起自己的容器、用自己的端口、连自己的数据库，结束时丢掉。没有任何东西被
共享，也就没有东西依赖顺序——下面的完成标准之所以要求多跑几遍，就是为了确认这一点。

## 任务

脚手架把零件放好了，缺的是接线：

- `src/smtp.rs`——T1 自带的适配器：`lettre`、明文 SMTP（`builder_dangerous`，这是这个 crate 给"这条连接不加密"
   起的名字）、每次会话一个死线，发件人是 `no-reply@mailer.invalid`——RFC 2606 保留的地址，保证它不可能是
   一个真实可用的邮箱；
- `tests/support/mailpit.rs`——给一个测试用的 mailpit 容器：SMTP 占一个发布端口，HTTP API 占另一个，加上
  `messages()`、`text_of(id)`，以及一个把容器带走的 `Drop`。它遵循 `tests/support/postgres.rs` 立下的三条
   规矩：引擎要先探测、镜像按仓库路径去查（镜像站会用自己的前缀缓存它）、每条命令都有这个模块自己执行的死线；
- 依赖里的 `lettre`，在 `kiln:scaffold:begin` 块内。

### `src/config.rs`：两个设置项

两个设置项，照 `mailer/1.4-config` 步造其他设置项的方式造——默认值、文件、环境、报告——并且加进
`--check-config`，让部署能看见它们：

```toml
email.smtp_host = …        # a host turns the logging adapter into SMTP; unset keeps the log
email.smtp_port = …        # the port that host listens on
```

测试或部署用 `MAILER__EMAIL__SMTP_HOST` 与 `MAILER__EMAIL__SMTP_PORT` 设置它们；服务不认识的环境变量仍然被拒绝
而不是忽略（这是 1.4 步的规矩，而 `MAILER__EMAIL__SMTP_HOTS` 这种笔误正是它存在的理由）。

### `src/lib.rs`

声明模块：`pub mod smtp;`。

### `src/http.rs`：只在一处决定

`AppState::start` 按配置挑适配器——设了 host 就用 SMTP，没设就用日志适配器——下游全都对着端口写。这正是
`mailer/1.13-email-port` 步的全部回报：加一个真实传输，只花一个函数。

**没配 host 是默认，不是错误。** 此前每一步都在没有邮件服务器的情况下跑二进制，它们的规格从日志里读
`an email would be sent`；一个没有邮件服务器就拒绝启动的服务会把这些全弄坏——还包括一台笔记本。规格里最后那个
测试就是为了守住这一点。

### 规格判什么

| the test | the claim |
| --- | --- |
| 对真实邮件服务器的一次注册 | 消息到达了，收件人是存储的地址、带主题，正文里带着 `/confirm?token=<行里的那个令牌>`——顺着那个链接点下去，订阅者就被确认了 |
| 一台不在的邮件服务器 | `201`，随后 `confirmation_attempts` 到 3，`confirmation_sent_at` 仍为空，订阅者仍是 `pending`，认领已交还 |
| 一台接了却永不答复的邮件服务器 | `SIGTERM` 大约十秒内以退出码 **1** 应答，日志里有 `did not drain before its deadline`，那次在途的发送也被点名 |
| 没配 SMTP host | 日志适配器仍然写一次 `an email would be sent`，带着地址——此前每一步的测试都依赖它 |

## 完成标准

- `kiln run mailer/1.19-test-layering` — 规格通过
- `kiln check mailer/1.19-test-layering` — 每个 must 闸门都是绿的（含 `images`：本地没有那个镜像之前它不会绿）
- `cargo test -p mailer --test spec_integration` 连跑三次都过，再用 `--test-threads=1` 跑一次也过：每个测试
  拥有自己的容器、端口和数据库，所以顺序不是契约的一部分
- 对运行中的服务注册一次，日志出现 `an email is being sent`，而消息能从邮件服务器自己的 API 里读回来——主题、
  收件人，以及正文里的那个链接
- 在它正和一台永不答复的邮件服务器说话时停掉这个服务，会在排干死线内以 `1` 退出，而不是一直挂到被谁杀掉

## 陷阱

1. **把假实现删了。** "我们已经有真邮件服务器了"是对这一步的误读：容器没法被要求恰好在测试关心的那条消息上失败，
   而课里所有失败测试都会变得又慢又不稳。假实现留着做失败注入；容器是为了协议。
2. **什么都拿容器测。** 分层的套件不是"更真实"，它在底层只是更慢、更不精确。一句断言如果能对着假实现做，就该
   留在假实现那儿——金字塔顶端应该只有寥寥几个测试，它们在别处毫无意义。
3. **测试并不拥有的容器。** 固定端口、固定名字、共享数据库，就是两个测试单独过、一起挂的原因，也是一套测试开始
   依赖顺序的原因。`podman run -p 127.0.0.1::1025`（临时宿主端口）加一个把容器删掉的 `Drop`，才是让顺序无关紧要
   的形状——而完成标准要求跑第二、第三遍，因为那是唯一能察觉的方式。
4. **默认镜像已经在本地。** `--pull=never` 把"镜像不在"变成一句学员能照做的话（`kiln images pull`），而不是
   测试里一次漫长的 registry 等待。会挂住的拉取是一套会挂住的测试，而会挂住的测试是一份没人能复现的 bug 报告。
5. **一不小心上了 TLS，或者在该用不了 TLS 的地方上了。** `builder_dangerous` 是"这条连接是明文的"的诚实写法：
   环回地址上的测试容器正是它适用的场景，而部署不是。另一种错法，是给一台只会明文 SMTP 的容器启用 TLS 栈——
   它会以握手错误失败，看起来像邮件服务器的问题。
6. **连接上没有死线。** `lettre` 默认永远等下去，所以适配器给传输设了超时：没有它，一台接了连接却不说话的邮件
   服务器会一直攥着 worker——以及它后面的排干——直到进程被杀。规格里第三个测试就是那个观察点，也是
   `mailer/1.14-worker` 步的排干死线第一次从进程外面被判。
7. **一个可能是真的发件地址。** `no-reply@example.com` 是别人的域名，`no-reply@localhost` 是邮件服务器会拒的
   主机名。RFC 2606 的 `.invalid` 才是"这个地址永远不可能工作"的约定，而占位符就该是这样。

## 延伸阅读

- [The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html) — 这一步补完的
  那个形状，以及为什么分层的依据是*一句断言的成本*，而不是真实程度
- [mailpit](https://mailpit.axllent.org/docs/) — 这个容器、它的 HTTP API，以及 `mailpit` 命令行（想手工读一封
  信时值得一看）
- [`lettre`](https://docs.rs/lettre/latest/lettre/) — `builder_dangerous`、SMTP 传输的超时，以及对一个一次只发
  一条消息的客户端来说"pool"意味着什么
- [RFC 2606](https://datatracker.ietf.org/doc/html/rfc2606) — 保留域名，以及为什么 `mailer.invalid` 是任何
  "绝不能真的送出去"的东西该用的发件人
- [testcontainers](https://testcontainers.com/) — 项目要跑的容器超过两个之后，来做 `tests/support/*.rs` 这里
  那些事的库
- [Flaky tests](https://martinfowler.com/articles/nonDeterminism.html) — 这一步"每个测试拥有自己的容器"背后
  的那篇文章：大多数 flaky 都是共享状态披了层伪装
