# 后台投递 worker：有界队列，退出前排干

## 为什么

`mailer/1.13-email-port` 步把"发一封邮件"变成了一个可以交给别人的值——而且是在**请求里**交出去的。这一步
把那个取舍收回来：

```rust
// src/signup.rs, as step 1.13 left it
if let Err(error) = sender.send(message).await {
    warn!(%error, to = %email, "the confirmation email could not be sent");
}
```

这两行有三个毛病，只有第一个跟速度有关：

- **调用方替邮件服务器买单**：`POST /signup` 现在跟 SMTP 一样慢，邮件服务器一旦不应答，*注册*这条路也跟着
  不应答；
- **没有上限**：没人说清楚这个进程到底揽下了多少活儿。一波注册、一台慢服务器、一次重试风暴——全堆在请求
  路径上，而那是唯一必须保持快的地方；
- **失败无处可去**：试一次，记一行。订阅者存在了，确认信没有，而服务里没有任何东西知道这个差别。

所以消息进**队列**，请求先答复；队列后面一个 worker 任务负责发送。随之而来四个决定，每一个都有做错的方式：

1. **队列有界**（`QUEUE_CAPACITY`）。无界队列根本不是队列，它只是承诺以后某天耗尽内存。有了上限，"我们
   揽的比做完的多"才变成调用方能据以行动的答案：`503`，意思是*回头再来*；而不是 `500`，意思是*这里坏了*；
2. **先占座位，再干活**。处理函数在插入*之前*预定一个座位，等行写完再投递。因为队满被拒的注册什么都没
   写，客户端重试就是一次全新的机会。反过来，先写了行才发现队满，就造出一个永远无法确认的订阅者，而它的
   重试会被那一行回以 `409`——用一个 `503` 挖了个死胡同；
3. **发送失败要重试，且带抖动**。最多 `MAX_ATTEMPTS` 次，每次等一个 `[0, min(cap, base · 2ⁿ))` 内的随机
   延迟。这份随机不是装饰：一台邮件服务器恢复时，整个机群里的 worker 手里攥着同一个失败，它们绝不能同时
   到达；
4. **停止是一个序列**。被要求停下的进程——容器被替换、一次发布、终端前的人——应该先停止*接新*活，把已经
   接下的做完，然后才退出。而且必须在死线内做完（`DRAIN_DEADLINE`）：客客气气请你停的人，手里也握着一个
   `SIGKILL`；在发送途中被杀，正是一封信消失的方式。

**还有一条必须说出口的边界**：这个队列活在内存里，所以它*不是*"还有哪些必须送达"的记录。杀掉进程，它
手里的东西就没了；行才是"还有谁需要被告知"的记录。可靠投递——outbox、逐行认领、投递状态机——是后面的事：
`mailer/1.15-idempotent-delivery` 步把它起步，做法是把"这条消息已经发过了"变成数据库里的事实。这一步换来的，
是一条不依赖邮件服务器的请求路径，以及一个可以被停下、而不必扔掉已接受工作的进程。

## 任务

脚手架加了 `src/delivery.rs`，形状恰好是初稿会写成的那样：一个其实不是队列的 `Queue`（每条消息一个任务）、
一个不花任何代价的 `Seat`、一个永远返回基数的 `backoff`、一个不等待就返回 `0` 的 `drain`。它的模块文档就是
上面那四个决定。任务是把每一条做实，然后从请求、服务器和二进制里用上这个队列。

### `src/lib.rs`

声明模块：`pub mod delivery;`。

### `src/delivery.rs`：一个队列，一个 worker

- `Queue::start(sender: Arc<dyn EmailSender>) -> Self` 建通道，并**起一个 worker 任务**，让它在整个生命
  周期里持有接收端：`while let Some(message) = rx.recv().await`，每条消息按下面的重试策略发送。循环结束时
  ——队列已关闭且为空——worker 记一条 `the delivery queue drained` 并带上投递数量，然后返回它。
- 通道是 `tokio::sync::mpsc::channel::<Message>(QUEUE_CAPACITY)`：有界，因为 `503` 靠它才成立。这里用
  tokio 自带的队列是对的——第三方实现（kanal、flume、crossbeam）赢下的微基准跟这一步的瓶颈（一次密码
  哈希、一台邮件服务器）毫无关系，却会把它们自己的取消语义带进关闭路径；
- `Queue::reserve(&self) -> Result<Permit<'_, Message>, Error>` 就是 `self.jobs.try_reserve()` 映射成
  `Error::QueueFull`。`Permit` 就是那个座位：*位置已经是你的*，所以后面的发送既不会失败也不会等待。它也顺带
  解决一个隐蔽的 bug——在 `select!` 里被取消的 `mpsc::Sender::send(…)` 会丢掉消息（tokio 自己的文档就说
  了），而预定好的 permit 不会。`permit.send(message)` 不是 `async`，这正是要点：等待发生在调用方还有东西
  可失去之前；
- `Queue::drain(self, deadline) -> Result<usize, Error>` 先让 worker 不再接活——worker 选中的 `watch`
  通道，或者 `close()` 加丢弃发送端，哪个能把"不再有新消息"说得更清楚就用哪个——然后在
  `tokio::time::timeout(deadline, …)` 之下等 worker 的 `JoinHandle`。超时是 `Error::DrainTimeout`；worker
  已经不见了是 `Error::WorkerLost`。吃下 `self` 也不是装饰：它是唯一有权等 worker 的句柄，第二个调用方因此
  不可能和它抢；
- 脚手架里的 `Seat` 类型删掉：permit *就是*座位，脚手架里那个只是用来示意座位该放在哪儿；
- worker 会重试：最多 `MAX_ATTEMPTS` 次，中间睡 `backoff(attempt)`。最后一次仍失败的消息用 `error!` 记下
  原因和地址，然后 worker 继续处理下一条——一个够不着的地址不该卡住整个队列；
- `backoff(attempt) -> Duration` 是**纯函数**，这也是个决定：*full jitter* 是
  `random(0, min(RETRY_CAP, RETRY_BASE · 2ⁿ))`，随机数来自 `getrandom`（绝不用时钟——测试必须能在暂停时间
  的情况下跑它，而拿时钟当种子的抖动，是测试永远猜不到的值），生成器失败时退到上界，而不是拒绝重试。

### `src/error.rs`

`Error::QueueFull`——队列满了：部署方的问题，退出码 `1`，HTTP `503`。`Error::DrainTimeout` 与
`Error::WorkerLost`——排干没做完。这几个都不是调用方能修的，所以都不是 `2`。

### `src/http.rs`

- `AppState` 携带 `Queue`（`delivery: Queue`），在 `start_with_sender` 里用调用方选的那个发送器建出来，
  `delivery()` 把队列交给处理函数。`sender()` 删掉：状态里已经没有可以直接够到的发送器，而一个能直接发信
  的处理函数会绕过队列——类型本身就是设计；
- `/signup` **先预定**：`let seat = state.delivery().reserve()` → `subscribe(pool, seat, request)`；
- `serve` 与 `serve_on` 各长出一个带关停 future 的孪生：`serve_with_shutdown(state, id, shutdown)` 与
  `serve_on_with_shutdown(listener, state, id, shutdown)`，建在
  `axum::serve(…).with_graceful_shutdown(shutdown)` 上。不带它的版本保留为一行调用，传
  `std::future::pending()`：测试装置是靠*丢弃* future 来停这个服务器的，装置那边什么都不用改；
- 状态表加一行：`Error::QueueFull` → `503 Service Unavailable`。

### `src/signup.rs`

`subscribe(pool: &PgPool, seat: Permit<'_, Message>, request: SignupRequest)`——座位是一个参数，于是
"先有容量再干活"由类型保证，而不是靠注释。流水线本身一点没变：解析、哈希、插入。然后在插入成功的那一支上，
`seat.send(confirmation_message(email.clone(), &token))`——不 await，因为已经没有什么可等的了。地址已被
占用那一支直接丢掉座位：位置还给队列，因为一封都不发的注册不该占一个名额。

### `src/main.rs`

二进制才是*进程*停下的地方，所以序列放在这里：

1. 等信号——`SIGTERM`（`tokio::signal::unix::signal(SignalKind::terminate())`）或 `ctrl_c`；
2. `serve_with_shutdown(state.clone(), &id, shutdown())`：停止接受，把已经在途的请求做完；
3. 跨过这次调用保留队列句柄，然后 `drop(state)` 并 `drain(DRAIN_DEADLINE)`；
4. 排干完成就退出 `0`——worker 已经记下投递了什么；没完成就 `1`，并用 `error!` 点名剩下了什么。

这些一样都不该进库：信号是进程的属性，而驱动库的测试根本没有信号可等。

### 单元测试：`backoff` 与排干死线

*跟时间有关*的断言该写在 `src/delivery.rs` 的单元测试里，配 `#[tokio::test(start_paused = true)]` 和一个
故意失败的发送器：重试恰好发生 `MAX_ATTEMPTS` 次、等待不超过上界、抖动不是常数、排干到死线就放弃。这需要
tokio 的 `test-util` 特性——加在 `Cargo.toml` 的 `kiln:scaffold:begin` 块里的 `tokio` 那一行，那是脚手架
可以写进去的区域，也就是依赖可以变动的区域。一个要真等上几秒才看得到退避的测试，会让整套测试变慢且时好时坏；
暂停的时钟才是这门课要的注入时钟（authoring.md §6.4）。

### 规格判什么

| the test | the claim |
| --- | --- |
| 一个永不答复的发送器 | 发送还没完成时就已经 `201`——答案来自队列，不是来自发送器 |
| 用注册把队列灌满 | 至少一个 `503`，且 `rows == accepted`：拒绝时什么都没写 |
| 失败一次的发送器 | 消息靠*重试*到达：一次拒绝、一次投递，没有第二个请求 |
| 一直失败的发送器 | 第一条消息被尝试 `MAX_ATTEMPTS` 次，然后*下一条*得到服务：队列往前走，而不是无限重试 |
| 向进程发 `SIGTERM` | 退出码 `0`，日志里有 `the delivery queue drained`，排队的那封确认信在退出前发出 |

## 完成标准

- `kiln run mailer/1.14-worker` — 规格通过
- `kiln check mailer/1.14-worker` — 每个 must 闸门都是绿的
- `cargo test --lib` 通过，包括 `backoff` 与排干死线的暂停时钟测试
- 想直接看规格的话，`cargo test -p mailer --test spec_worker` 通过
- 通过运行中的服务注册一次，确认信的日志出现在 `201` *之后*；对该进程 `kill -TERM <pid>` 后以 `0` 退出，
  日志里有 `the delivery queue drained`
- 灌满队列（发送器挂住，一直注册到被拒）：最后一次回 `503`，`SELECT count(*) FROM subscribers` 停在原处

## 陷阱

1. **无界队列，或者一条消息一个任务。** 脚手架那条每消息 `tokio::spawn` 能编译，能过所有没把服务撑过上限的
   测试，然后在负载下以内存增长的方式失败。规格把它写成 *"a queue that cannot fill up is not a bound"*，
   而且两半都要数：拒绝必须*够得着*，队列还得吸收掉"答案不再等待"的那部分。
2. **`try_send` 丢消息。** 拒绝等待是对的，拒绝答复不是。`try_send` 回 `Err(Full)` 时处理函数只记个警告，等于
   把队满变成默默丢失的注册。座位的作用，就是让请求在损失任何东西*之前*被拒绝。
3. **插入之后再预定。** 先写行再入队，把拒绝推给一个已经存在的订阅者——客户端照着办的 `503`，变成了它修不了
   的 `409`。脚手架自己的形状是同一个 bug 的另一种写法：在请求路径里直接往座位上发，调用方仍在等邮件服务器。
4. **该用 permit 的地方用了 `send()`。** 在 `select!` 里 `sender.send(message)`，或者刚确认有空位就 await
   它，对消息而言不是取消安全的，还会和关闭过程抢。不会丢东西的形状是 `try_reserve()` → 干活 →
   `permit.send(message)`。
5. **队满回 `500`。** 状态表有个默认分支，`Error::QueueFull` 掉进去，就是告诉一个本可以重试的客户端"服务坏了"。
   `503` 才是唯一在说"现在不行"的答案。
6. **先排干再停止。** 服务器还在接请求时调 `drain`，就是在正不断到来的请求脚下关掉队列：容量明明空着，它们
   照样被拒；而一个还挂在途中的请求持有的 permit，可能活得比本该发送它的那个 worker 更久。顺序是：停止接请求
   → 排干 → 退出。
7. **排干没有死线。** 用 `worker.await` 而不是 `timeout(deadline, worker)`：一台永不答复的邮件服务器会把进程
   一直攥住，直到编排器失去耐心把它杀掉，那些*本可以*发出的消息跟着进程一起没了。死线把"卡住"变成一个有人
   可以据此告警的退出码。没有任何规格能通过运行中的服务看到这一条——这次构建的适配器从不阻塞——所以 `drain`
   上的*单元测试*是你和一个必须被杀掉的进程之间唯一的东西：一个 `Hanging` 发送器、一条消息、几毫秒的死线、
   断言排干返回 `Err` 而不是干等。
8. **齐步重试。** 固定延迟，或者不带抖动的 `base · 2ⁿ`，会让整个机群在同一瞬间带着同一份积压回到刚恢复的邮件
   服务器面前。没有规格能抓住它——这一条由 `backoff` 的单元测试决定，这也是为什么随机性写成不接参数的纯函数，
   并且来自 `getrandom` 而不是时钟。
9. **在测试里睡真时钟。** `#[tokio::test] async fn a_retry_waits() { … sleep(300ms) … assert }` 慢、易碎，
   而且断言的东西不对：`start_paused = true` 会把时钟推过去，延迟于是变成测试能读到的值，而不是它必须熬过去
   的时长。
10. **忘了这个队列不是什么。** 把内存队列当成"必须送达"的记录，是进程兑现不了的承诺——它被杀了，记录就没了。
    行才是记录；这一步只让请求路径不再依赖邮件服务器。
