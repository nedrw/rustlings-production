# One command for every check, wired into CI

## WHY

每个项目最后都有两份检查清单：人在推送前跑的，和流水线跑的。它们会漂移，而且漂移永远是同一个
形状——流水线是可以被弄绿的，本地清单里有一条没人记得的步骤，于是提交在本地过、在 CI 里挂。
修法不是纪律，是唯一入口：检查以代码的形式住在仓库里，CI 调这段代码，人调的完全是同一个东西。

还有一个更安静的理由。Rust 里的*任务运行器*是普通代码：它在清单中间失败并以非零退出，可以在
别的工作目录下运行，也可以被测试。YAML 文件里的 shell 胶水这三样都不占，而且 `cargo test` 看
不见它。

## TASK

脚手架已经把形状放好：一个 `xtask` crate、`.cargo/config.toml` 里的 `[alias] xtask`（于是
`cargo xtask <task>` 能用）、以及一个 `ci` 任务还只打印 "not implemented yet" 的桩。

- 填充 `ci` 任务：它跑 `cargo fmt --all --check`，然后 `cargo clippy --workspace --all-targets
  -- -D warnings`，然后 `cargo test --workspace`，并以第一个失败的检查的退出码失败。顺序有讲
  究：最快失败的先跑。
- 把进度打到 stderr，这样以后一个会打印结果的任务仍然可脚本化。
- 加 `.github/workflows/ci.yml`，调用 `cargo xtask ci`——仅此而已。工作流检出仓库并调用这个任
  务；它不自己列 `fmt`、`clippy` 或 `test`，因为第二份清单正是会漂移的东西。
- 不要在工作流里钉 Rust 版本：`rust-toolchain.toml` 已经决定了它。

规格会**运行**你的任务两次。第一次在干净的树上，必须绿。然后带着 `tests/` 里一个未格式化、含
有 `todo!()` 且有一个测试失败、必须红的文件——看你哪个检查先跑。它还会读工作流，反对其中任何
`cargo fmt`、`cargo clippy` 或 `cargo test` 行。

规格必须处理一个细节，你也一样：`cargo xtask ci` 跑 `cargo test`，后者跑本规格，而本规格会把
`cargo xtask ci` 再跑一遍。规格在启动任务时设置 `KILN_CI_NESTED=1`，看到它就立即返回。一个调
用自身的检查是一次挂起，而任务运行器正是它咬人的地方。

## DONE WHEN

- `kiln run mailer/1.3-ci` — 规格通过
- `kiln check mailer/1.3-ci` — 每个 must 闸门都是绿的
- `app/mailer` 里的 `cargo xtask ci` 每个检查打一行，以 `every check passed` 结束
- 故意弄坏格式（在 `src/lib.rs` 里加一个多余的换行），看 `cargo xtask ci` 以 `fmt` 检查的退出
  码失败

## TRAP

1. **把检查也列进工作流。** 看起来无害，而这正是全部问题：YAML 清单和任务清单分头漂移，规格
   以 *"no workflow runs `cargo xtask ci`"* 失败，或者点名那条重新实现某个检查的行。
2. **放任 `cargo test` 递归。** 没有嵌套守卫，任务的第二次调用会启动第三次，运行不会结束——你
   会看到同样四行一遍又一遍，直到你杀掉它。
3. **无论什么失败都从 `ci` 返回成功。** `Command::status()` 给你一个 `Result`，而 `.ok()` 把检
   查过没过扔掉了；规格的坏树那一半会以 *"`cargo xtask ci` stayed green with a file that is
   unformatted, unfinished and fails a test"* 失败——那句话本该是任务自己的退出码。
