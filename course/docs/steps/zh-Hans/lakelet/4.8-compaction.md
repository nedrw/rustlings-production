# 合并重写段，而读取方一直在读

## 为什么

一个只会追加文件的存储会无限长大，而每一个文件，读取方都要付一次代价。`lakelet/4.7-columnar-segments`
给了这个存储一个值得留的文件——记录按列排、压缩、封好——也关掉了"一次刷写*写*什么"这个问题，同时
打开了这一步要回答的那个：一个段装多少条记录，什么时候开始新的段。到目前为止答案是"每次刷写一个
段"，而那道算术就是这一步：

- **每次刷写，都是查询要多打开一个的文件。** 段的头部得先读出来，第一条记录才看得见；一次跨一小时
  的查询，要跨过那一小时产出的每一个段。到这一步自己的工作负载刷了十六次，存储是十六个文件共
  8 112 字节；同样的 2 048 条记录放进一个文件，是 5 700 字节。字节不是问题——*打开次数*才是，
  而每五秒刷写一次的话，一天摄入就是一万七千个文件；
- **两个装着同一序列的段，什么也不共享。** 不共享字典，不共享游程，也不共享 `zstd` 帧：每个段
  各自在边界上付出的那部分，正好是更大的块免费得到的部分。同样的工作负载里，十六个分开的段，
  `bytes_per_sample` 比它们合并成的那一个文件贵大约百分之四十。

合并修的就是这件事，而它要花已经写过一次的字节。这个价钱有个名字——**写放大**——而这一步去量它，
而不是争论它：在预算工作负载上，对十六个段做一趟，写 **12 029 字节**，存储不再持有的部分是
**2 412**，所以这个构建每删一个字节，大约重写 **5 字节**。一次合并两个段，大约是 **10**；每次
调用都整个合并，大约是 **40**。反方向描述起来更省事、活在里头更难受：一个从不合并的策略，让读取
方要付的文件数原地不动。所以"合并*哪几个*段"不是一个循环里的 match 分支——它是一个值，
`src/engine/compaction/plan.rs` 里的 `Policy` 和 `Plan`，不合并任何东西也能评判它。

这一步的另一半，是前一半不许弄坏的东西：**读取方永远看不到一个合并到一半的存储。** 一次合并若重写
了查询正读到一半的那些段，就会把一条记录答两遍，或者两份都不答，而且没有任何计数能告诉任何人。
所以一次合并在恰好一步内可见——写出新段、让它持久化、换掉读取方看的东西，然后才让旧段走——而一次在
换之前开始、换之后结束的读，必须答出与完全在换之前跑完的读一模一样的东西：同样的记录，各一次，
同样的顺序。

这也是存储层的崩溃点拿到第二章的地方。`docs/crash-points.md` 讲的是*日志*：一条记录写下去，机器
死了，一次重放证明一个前缀，并停在第一条它读不了的记录上。这一步是同一条规则往上一层，在那里可能
做到一半的是**一个存储由哪些文件构成**——而那里崩了之后，世界仍然只有两种，靠的是一条必须一次定下
并一直守住的规则：**清单就是存储。** 一个段，当清单点了它的名才算数，按点名的顺序算；段目录里别的
一切，都是崩溃留下的残渣。这一条规则，把五个不同的崩溃阶段收成了一次恢复：读清单，删掉它没点名的
东西。

## 任务

这一步由五条性质组成。其余都是打包。

- **策略是一个值，计划是数据。** 一条**按大小分层**的规则，一句话：*一个计划取最老的一串 `width`
  个连续段，它们的字节大小两两相差不超过 `ratio` 倍。* 要连续，因为合并是在输入所在的位置写出一个
  段，一个跳过了某个段的串，会把那个段的记录挪到它后面那些记录的后面；要最老，因为那是读取方打开
  得最久的文件；大小比较要两头都比，因为只看一头的规则会把一个小文件并进一个大文件。一个计划恰好
  取 `width` 个段——绝不是一个（那重写字节却一个也不删），也绝不是整个层（成本跟着存储跑了多久
  走，是一个没人能给出上界的成本）。这个构建交付**四个段、两倍以内**——`Policy::DEFAULT`，预算
  车道里的基线就是在它上面取的：四个各 `s` 字节的等大段，合并成大约 `3.2 s`，落在它们来的那一串
  之外，于是下一次合并做的是新到的那些段，而不是重写上一次写下的东西；在这个工作负载上，重写比
  保持在个位数（大约五），而一次合并两个的代价大约是十。
- **读取方持有快照，快照点名一个集合。** `Segments::snapshot()` 是查询开始时拿的东西：那一刻构成
  存储的那些段，旁边发生多少次合并都仍然可读，而且仍然*在磁盘上*，直到最后一个点了它们名的读取方
  放手。合并写出的段，在清单点它名的那一刻才是存储，早一瞬都不是。
- **一次合并在一步内可见，存储就是清单点名的东西。** 新段要*先*写好并刷下去，清单才点它的名，这样
  崩溃不可能留下一个指向设备从未留住的字节的索引；清单先写到一个暂定的名字、刷下去、改名到自己的
  名字上、改名之后再刷目录，于是读清单的人看到的是旧的那份或新的那份，绝不会是写了一半的混合。
  合并替换掉的段*退役*：最后一个点过它们名的快照负责删掉它们。
- **在合并的每一个阶段杀掉进程，留下的都是两个世界之一。** 按这个顺序点名各阶段——`planned` →
  `written` → `durable` → `swapped` → `retired`——并说清每个阶段崩了留下什么：磁盘上什么都
  没有；设备已提交的那一部分里的一个孤儿文件；一个完整的孤儿；新的集合（如果某个读取方持有旧段，
  旧段还在）；以及新的集合、什么也不剩。绝不留空洞，绝不让一条记录出现两次；而
  `lakelet/4.4-wal-recovery` 对日志的规则不变，因为合并从不写日志。
- **重写是一个数。** 计数住在 `tests/budget_compaction.rs`，基线住在
  `course/tracks/lakelet/budget/4.8-compaction.toml`：合并了多少次、剩下多少文件、写了多少字节、
  存储不再持有多少字节——还有后两个的比值，它说明一个策略是不是在回本。关系也算在里面：一次
  合并留下的**文件比它找到的少**，删掉的**恰好是它拿走的每一条记录、别无其他**，而且在记录之间有
  结构可共享时，**写的字节比读的少**。

**课程给你什么，什么归你。** 脚手架声明形状，因为装置、规格和后面几步都要读它：

- `src/engine/compaction/plan.rs`——`SegmentInfo`、`Policy`（`DEFAULT` 设成那个诱人的值）、
  `Plan`，以及陈述规则的那段文档注释。`Policy::plan` 归你；
- `src/engine/compaction/mod.rs`——`Segments`、`Manifest`、`Merge`、`MergeReport`、文件名常量、
  `file_of`，以及陈述布局和五个阶段的模块文档。清单自己的字节归你（存储之外没人读它们），
  `seal`、`plan`、`merge`、`install`、`compact` 以及一切私有的东西也归你；
- `src/engine/compaction/snapshot.rs`——`Snapshot` 和它背后的私有集合，文档里写着承诺，退役留给
  你；
- `tests/sim_compaction.rs` 和 `tests/budget_compaction.rs`——课程的装置，也就是 `slow:sim@3`
  和 `slow:bench-budget@10` 跑的东西。它们不是给你改的；
- 项目里别的什么都不变。日志（`4.1`–`4.4`）、批的边界（`4.5`）、队列（`4.6`）和段格式
  （`4.7`）原样不动：这一步在日志旁边加了第二个产物，外加一条关于读取方能看到什么的新规则。

边界在这里也成立：`src/engine/**` 不许点名服务层，代码里不行，散文里也不行
（`lakelet/4.1-ingest-protocol` 会把这些文件当作文本读）；而合并是引擎的事——它会在测试里、
修复工具里、以及一个根本没有配置文件的负载生成器里运行。

## 完成标准

  计划作为值、跨一次换代的快照、每条记录恰一次且顺序相同、文件数和字节关系、五个崩溃阶段、一个
  内容变了但名字还在的段、清单没点名的情况，以及边界。
- `kiln run lakelet/4.8-compaction`——同样的用例，跑课程的副本。
- `kiln check lakelet/4.8-compaction --slow`——每个 must 闸门都是绿的，包括 `slow:sim@3`
  （三个种子、至少两份不同的运行记录，种子 `1` 逐字节重放）和 `slow:bench-budget@10`。
- `cargo test -p lakelet --test budget_compaction -- --nocapture`——原始的 `lakelet-budget`
  行：工作负载的计数、合并、剩下的文件、写入和删掉的字节，以及重写比。

  和段的布局，一个字节都没动。

## 陷阱

1. **在换代的时候就把旧段放走。** 清单易手时删掉它们，会让一个在换代之前开始的读取方拿到一个没人
   点名的文件：规格的
   `a_reader_that_took_a_snapshot_before_the_swap_answers_the_same_after_it` 在记录上失败，
   而模拟的 `files=` 计数显示被替换的段已经没了，却还有读取方点着它们的名。
2. **新段还没持久化就先换清单。** 两者之间崩掉，会留下一个指向设备可能从未留住的字节的索引，而存储
   会答出一个*空洞*：模拟的 `written` 和 `durable` 阶段变红，点名回来时缺了的那部分记录数。
3. **原地写清单。** 往清单后面追加，或者原地覆盖它，而不是写一个暂定文件再改名，意味着写到一半崩掉
   会留下半个索引——而半个索引读成一个段更少的存储，就是之后每个答案里的一个洞。规格故意把一份清单
   切成两半。
4. **读最新的文件，而不是清单点名的东西。** 目录列表不是存储：崩溃之后，最新的文件恰好是合并从未
   装上的那个孤儿，而一个列目录的读取方答的是一个没人写过的世界——那个段的记录还数了两遍。
   `a_store_ignores_what_its_manifest_does_not_name` 就是那个用例。
5. **执行一份过时的计划。** 计划是在某个时刻取下的值。一次合并若不问存储、照计划点名的去拿，就会
   写出一个装着已经合并过的记录的段，而其中每一条都会被答两遍——这就是 `Segments::merge` 拒绝
   一份段已经不在的计划的原因，也是过时计划是 `Error::Invalid` 而不是一次修复的原因。
6. **一次只合并两个（或者每次都合并全部）的策略。** 计数会动，上界会说是哪一项：`merges` 从五变成
   十四，`bytes_rewritten_per_byte_removed_max` 从大约五变成大约十——而每次调用都合并整个存储的
   策略，会把它重写十六遍，却什么都不删（`merges`、`bytes_rewritten_max`、`plan_left_max`）。
7. **去重，或者"每个键保留最新值"。** 这个存储的记录是事件，不是一个键下的值：丢掉一条记录的合并，
   删掉的是字节*和*数据，预算的 `records_lost_max` 之所以是一个零的上界，正是因为这个。
8. **大小按条数比较，或者在 `u64` 里相乘。** 一层讲的是字节——读写它们的成本——记录条数对此什么
   也说明不了。而写成 `size * ratio` 的比较，在大段的存储上会溢出（`u64::MAX` 是合法大小，规格
   就计划了一个）：在 `u128` 里比，或者用除法。
9. **相信索引声明的一个数。** 一个段的记录数和字节长度，是存储对一个文件自己的主张；按声明
   `Vec::with_capacity(stated)`，或者把一个长度不对的文件当成完整的来读，就是一个损坏的存储变成
   *更短*的答案、而不是一次拒绝的方式。
10. **快照存路径而不是集合。** 一串路径名在合并之后，是一串已经不存在的文件。读取方持有的必须是
    集合本身——正是这一点让删除发生在最后一个读取方之后，而不是在换代的时候。
11. **`write_manifest` 排在新段的字节前面。** 顺序就是崩溃点：段的字节、段的刷盘、清单的字节、
    清单的刷盘、改名、刷目录。把刷盘挪到改名之后，就是陷阱 2 再加几个中间步骤。
12. **三个文件里留下一个 `todo!()`。** `no-todo` 会扫每一个目标，包括规格只通过崩溃用例才走到的
    合并路径。

## 延伸阅读

- **现实里的三种合并，以及这一步是哪种。** 分层合并（LevelDB、RocksDB）让每一层的各串互不重叠，
  并为每一层付写放大，换来读放大的下界；
  [size-tiered compaction](https://docs.datastax.com/en/cassandra-oss/3.x/cassandra/dml/dmlConfigStorageEngine.html)
  （Cassandra 的默认，也是这一步的规则）合并大小相同的串，把写成本压得很低，代价是文件数是对数级
  的、而不是常数级；[the RocksDB compaction wiki](https://github.com/facebook/rocksdb/wiki/Compaction)
  描述了混合形态（"universal" 和 "FIFO"），而且对一个策略来说重要的是它的参数：
  `max_bytes_for_level_base`、`level0_file_num_compaction_trigger`、
  `max_background_compactions`。读一遍这些参数名，再读这一步的 `width` 和 `ratio`：形状是一样的，
  名字才是 RocksDB 的东西。
- **这个交易有名字，也有论文。** 写放大、读放大和空间放大互相交换——RUM 猜想
  （[Athanassoulis et al., VLDB 2016](https://arxiv.org/abs/1603.01398)）是它的形式化版本——
  而这一步的数字是其中的一个点：十六个文件变成一个，每删一字节写 5 字节，换来的是一次不再打开其中
  十六个的查询。
- **墓碑，以及为什么保留是另一个问题。** RocksDB 删一个键的办法是写一个*墓碑*，只有合并走到最老的
  层时，那个键的字节才允许消失——所以"删除"是一次删掉数据的合并，而这一步拒绝打破的规则（"合并
  保留每一条记录"）正是有了墓碑之后必须*小心地放弃*的规则。这个存储没有可以被遮蔽的键，所以它接受
  过的每一条记录都还在。它需要的是时间：`lakelet/4.9-retention` 是"删除"获得第二重含义的地方，
  也是某一趟按时间戳删掉*整段*、而不是段内记录的地方，它有一条和这一步一样的读取方持有规则，并证明
  截止点之后的数据一条都没动。
- **业界把清单叫什么。** RocksDB 的 `MANIFEST` 是一串 `VersionEdit` 记录的日志，一次合并的
  "安装"就是其中一条——和这一步"写一整份清单再改名"是同一个想法，只是它用日志，这个构建用一个
  文件。这个想法的另一半在 `DeleteObsoleteFiles` 里：被替换的文件进入一个*列表*，等待引用它所属
  版本的那些读取方，这就是这一步的退役集合加上更多记账。
- **`sync`、`rename` 和目录。** 这一步用的那一条写序惯用法——写暂定文件、刷盘、改名、刷目录——
  正是 [SQLite's atomic commit](https://sqlite.org/atomiccommit.html) 长篇讨论的东西，也让 `rename`
  成为安全原语的，是它在 POSIX 文件系统上是原子的，而 `write` 不是。值得记住的微妙之处是*目录*：
  把一个文件的字节刷下去，并不会让它的名字持久；这就是 `docs/crash-points.md` 的第 4 点，也是
  清单换代要刷两次的原因。
- **按时间分区是同一个形状。** TimescaleDB 的 chunk 及其压缩/保留策略，就是这一步的段加上一个
  时间维度：一个 chunk 一旦比策略的间隔更老，就被封闭并压缩，而丢掉老数据意味着丢掉一个 chunk，
  而不是重写它。`lakelet/4.9-retention` 就是那一步，也是这里的合并保留每一条记录的原因：必须
  *删得便宜*的文件，是整个段，不是段里的一条记录。
- **这一切的下一个读取方。** `lakelet/4.11-query-engine` 接下的是一个 `Snapshot`，走过它点名的
  那些段，并依赖清单里的记录数，在读到任何东西之前说出一次查询会读多少。这一步欠它的，就是刚刚
  许下的承诺：快照点名的集合是完整的、有序的，并且在它脚下不变。
