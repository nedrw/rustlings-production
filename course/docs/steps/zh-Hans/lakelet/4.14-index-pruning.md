# 裁剪是可度量的：一次查询有多少段不必打开

## 为什么

一个靠打开每个文件来回答每个问题的存储是正确的，而遥测存储存在的意义，恰恰是不要成为这种东西。
`lakelet/4.11-query-engine` 给了你一半的修法：一个段在清单里的条目写明了它的记录覆盖的时间 span，
所以范围碰不到这个 span 的查询就不打开那个文件。只是一半，因为清单写的是*计数*——多少字节、多少条
记录、第一条和最后一条各发生在什么时候——而对记录*是什么*只字未提。对一个有两百个段的存储问
`FROM cpu WHERE host = 'h20'`，什么都跳不过：每个段的 span 都碰到查询的范围，每个文件都被打开，最后两百
条记录里才有一条是答案。

这个失败有一个值得在动笔之前先命名的形状，因为它是你的测试抓不到的那一种。答案是对的。没有可写的失败用例，
因为*"这次查询打开了两百个文件，才返回三十条记录"*并不是这个存储任何一个计数器里的 bug：`rows_answered`
是 30，`segments_opened` 是 200，没有任何东西说 200 是错的。**正确而慢没有红灯测试。** 它有的只是一个
*数*，而这一步的工作，是让那个数存在、让它动起来，并且在它不再动的时候让预算失败。

于是存储在每个段旁边得到一个索引——一个 **sidecar**：一个小文件，说明这个段里装了什么，近到足以回答"这个
文件里有没有可能装着我问的东西？"，又从不精确到非得打开段才知道。这个文件的整个设计都从一句话推出来：索引
是**派生状态**。里面的一切都能从它所描述的那个段重建。索引缺失、索引损坏、以及一个段已经不存在了的索引，
都是同一类事件——*这次查询打开了一个本可以跳过的文件*——而永远不会是不同的答案。一个删掉了自己索引目录的
存储，答案和之前分毫不差，只是读得更多；一个索引文件被涂改过的存储也一样。计数器说明发生的是哪一种
（`index_missing`、`index_unusable`），而不是答案变了，这一步就是围绕这个性质来塑造的。

## 任务

三个文件归你，存储是它们要改的东西，装置是课程的。这个划分是故意的：索引才是这堂课，而一条打印你的数字的
车道只是一个装置。

**`src/engine/index/zone.rs`——一个段的两个有序列的边界。** 每一条 `Record` 都有一个时间戳和一个值，两者都有顺序，
所以一个段能说出各自的最小值和最大值。这个类型是一个**值**：由记录构造，之后不再改变，可比较，能以固定的
三十三个字节编码，而且不需要存储就能作答。一条规则贯穿它的每一个方法，也是这一页必须明说出来的一条规则：

- **zone 答的是*可能*，从不是*一定*。** 一个假阳性——关于一个什么都没有的段说"这里的某条记录可能碰到你的
  范围"——代价是一次文件读。一个假阴性代价是**一条记录**：一次没有打开装着它问的那条记录的段的查询，答出
  来的东西里有一个洞，而这个存储里的任何计数都不会说出来。所以没人声明的边界对一切答 `true`，一个完全由
  没有记录构造的 zone 也答 `true`，而一条值是 **NaN** 的记录，会让那一对值处于*未声明*状态，而不是去界定
  一个悄悄把它排除在外的集合——NaN 不高于也不低于任何东西，所以没有任何区间能包含它；
- **单位是清单的单位。** 自 epoch 起的毫秒，无符号，早于它的时间戳算作零：zone 和清单里的段
  条目，是关于同一批记录的两句话，一个两者不一致的存储，会按一个数裁、按另一个数删；
- **范围问题就是 `lakelet/4.11-query-engine` 已经在用的那条半开规则**——一个段的最早记录早于 `to`、最晚
  记录不早于 `from`，就算碰到——只是写在 zone 自己的边界上，而不是清单条目上。两个比较在相反方向上
  各自承重，而规格两端都问；
- **与未声明 zone 的并集仍未声明。** 一次合并写出它各个输入的 zone 的并集（下面的 `merge`），只要有一个输
  入的边界没人写下，合并后的 zone 就什么也不说：这和 `lakelet/4.9-retention` 对合并段的时间范围所说的，是
  同一条规则。

**`src/engine/index/bloom.rs`——一个段可能持有哪些序列。** 一个作用在段的*序列词表*上的过滤器，也是查询
问的第二样东西。它的元素是**词项**：一个序列名，以及一个名字携带的每一个 `key=value` 对。一次查询会点出
这两种形状——`FROM cpu` 点一个指标，`WHERE host = 'h0'` 点一个对——而一个段持有的是完整的名字，所以这些
名字*和*它们的对都要放进去。那个文件里有三个决定比代码更值钱：

- **指标刻意不作为词项。** 存储可以用它来裁剪——一个没有任何 `cpu` 指标的记录的段，答不了 `FROM cpu`——
  而这么做会悄悄改变一个答案：对一个从未持有 `mem` 的存储问 `FROM mem`，今天会被*拒绝*，`Refusal::Unknown`
  由查询读到的记录决定；一旦范围内的每个段都被裁掉，用指标做的探针就会把那次拒绝变成空答案。一个存储是否
  *曾经*持有过某个指标，是关于它整段历史的问题，而 `lakelet/4.18-cardinality-cost` 才是让存储能回答它的那
  一步；
- **大小是固定的，而固定本身就是要点。** 这个构建写出的每个过滤器形状都一样，并且把它自己的形状写进编码
  里，好让解码器能拒绝外来的那一种。这正是**并集**得以可能的原因：一次合并写出各个输入词表的并集，一个
  序列名都不读，而两个过滤器只有在比特表示同样的位置时才谈得上做 OR。大小若是跟着过滤器的名字数量走，
  那次合并就不可能，而把每个名字重新哈希一遍，正是索引存在要避免的那次读；
- **CRC 是校验和，不是哈希。** 项目已有的 crate 是 `crc32fast`，而对于只有最后一个字节不同的消息，CRC 的
  低位是强相关的——而 `% size` 留下的正是低位。在校验和上做一步 `fmix32` 的雪崩，才把它变成哈希；这个差
  别是可度量的，不是理论上的：在这个构建写出的大小下、词表有十六个词项时，没这一步之前，过滤器对它从未见
  过的词项，大约每三十个会答 `yes` 一个，而模块自己的表承诺的是大约七万个里一个。写哈希之前，先读那段话。

**`src/engine/index/mod.rs`——索引作为一个文件。** 每个段一个值、它的编码、它住在哪儿，以及它被询问的
两种方式。

- **它住在段旁边，不在段中间**：`<store>/index/<ordinal>.lki`。清单才是存储
  （`lakelet/4.8-compaction`），一个段只有被清单点名才算数，`segments/` 里别的一切都是孤儿，会在
  下一次打开时被删掉——放在那儿的索引文件，会在它刚派上用场的那一刻被删，而前面有两步都在数那个目录里的
  文件。所以索引有自己的目录、自己的 magic、自己的版本字节和自己的扩展名，两种格式各自独立地演进；
- **封印是让损坏变成拒绝而不是谎言的东西。** 封印之上的每个字节都由 `wal::checksum` 的 CRC 覆盖——日志和
  段用的是同一个函数——所以被翻掉的一位是一个*损坏的*提示（不裁剪，读一次），而不是一个看起来合理的错误
  提示。会撒谎的派生状态比缺席的派生状态更糟，因为缺席会被计数，而谎言不会；
- **`load` 没有错误路径，这就是契约。** 它答 `Found`、`Missing` 或 `Damaged`。"这个存储该去修了"不是
  读者会拒绝回答的那种问题：查询打开那个段，在计数器里说 `index_missing`（或 `index_unusable`），然后返
  回它在一个完美索引下本来也会返回的同一个答案。调用方的数据没有任何一部分，会因为一个提示没了而变成错
  误。

**写的一侧归存储，是三处小改动。** `Segments::seal` 先写文件、*再*写新段的索引，*然后*清单才点名
这个段——这个存储里每一样被安装的东西都遵循这个顺序，所以两者之间发生崩溃，只会留下一个没人会询问的索引。
`Segments::merge` 把合并段的索引写成**它各个输入索引的并集**：不读任何一个序列名，就像为了说出合并段的
时间范围而不读任何记录一样。一个输入索引缺失或损坏，就让合并后的索引*什么都不说*——一个每一位都置位的过
滤器加一个没有边界的 zone，什么也裁不掉——因为一个声称拥有合并文件其实没有的词表的索引，会把它里面确实有
的记录藏起来。`Segments::expire` 完全不用改：已过期段的索引文件作为垃圾留在原地，它们的序号，清单已经
不再点名，而读者只会问清单*确实*点名的那些序号。把这些垃圾变成一个有人管理的数字，是
`lakelet/4.20-capacity-model` 的主题，不是这一步的。

**读的一侧归计划。** `Plan::of` 已经按清单裁剪，现在再裁一次：一个声明的时间 span 碰到查询范围的
段，如果它的 zone 碰不到范围，或者它的过滤器装不下查询点名的一个标签对，仍然会被跳过。一个没有点名任何对
的查询，根本不会被问及词表——没什么可问的时候，就不去问过滤器。两种裁剪分开计数，因为它们是存储不同部分
做出的不同决定：`segments_pruned` 保持 `lakelet/4.11-query-engine` 造出来的原样，`blocks_pruned` 是索引
的那一份，而三个计数合起来就是整个存储——每个段要么被*打开*，要么被*清单裁掉*，要么被*索引裁掉*，
从不同时落在两个里，也从不会哪个都不落。`EXPLAIN` 长出上一页承诺的那一个键（`blocks_pruned`，挨着
`segments_pruned`），而它一直有的十二个键保留它们的名字、顺序和含义。已执行的计数再长四个——`bytes_read`、
`bytes_avoided`，以及说明存储到底能不能裁剪的那两个，`index_missing` 和 `index_unusable`——而
`lakeletq query --json` 把它们全部打印出来，因为一个问"裁剪发生了吗？"的脚本，问的是一次确实发生过的运行。

**而 `OR` 仍然不在语法里，这是这一步要给出的论证。** `lakelet/4.11-query-engine` 拒绝析取，并说明了理
由：一条满足析取任意一半的记录，不能被只匹配其中一半的谓词排除掉。索引改变了这个问题的形状，所以这里是完
整的论证。裁剪一个**合取**是一条规则：查询点名的*任何*一个对不可能在段里，这个段就被跳过，因为一条同时匹
配所有对的记录，必须带上每一个。析取是对偶——只有当*每一个*分支都不可能在这个段里时，段才可以被跳过——而
过滤器也答得出来，所以 `OR` 不是不可裁的。它付出的是*计划*的代价：一张谓词表变成一棵树，计划打印的序列
名不再是名字（`cpu,host=h0` 拼不出 `h0 or h1`），而两个裁剪决定变成一次遍历，它打开的段可能比同一个问题
写两遍还要*多*。那本身是一步——语法、打印器和计划——而这一步的任务，是让索引有能力回答它：对词项的析取由
同一个过滤器回答，一个加上 `OR` 的步继承这条裁剪规则，而不需要自己的索引。

  `may_contain` 在边界上和边界之间、一个未声明的 zone 对一切答是、以及一个什么都不声明的 NaN

## 陷阱

1. **按指标裁剪。** 它是显而易见的第二个探针，也是会改变答案的那一个：对一个从未持有 `mem` 的存储问
   `FROM mem`，今天会用 `Refusal::Unknown` 拒绝，而这是由查询*读到*的记录决定的。把指标加成一个词项，任何
   范围恰好只碰到不带它的段的查询，就会得到空答案而不是拒绝——用例
   `a_selective_query_opens_one_segment_of_many_and_an_unselective_one_opens_them_all` 正是这个形状与上一步
   规格钉住的一次*拒绝*并存的地方，而两者不可能同时成立。
2. **合并给一个读不了的输入写空索引。** `Bloom::of([])` 是一个可能什么都不含的过滤器，于是一个从空词表起
   步、只把读得到的并进来的合并，会写出一个证明合并文件根本不持有任何序列的索引——之后的查询会对一个满是
   记录的存储悄悄返回零行。并集从一个输入起步，而一个没有可读索引的输入贡献 `SegmentIndex::unstated()`。
3. **询问一个清单没有点名的序号。** `merge` 和 `expire` 会留下索引文件，而序号从不复用，所以
   `<store>/index/` 会为一个已经不存在的段积累文件。一个遍历目录而不是走清单的读者，会按一张*过期
   的* zone 图裁剪，跳过一个确实存在的段。规则是清单的顺序与名单：索引只被问清单点名过
   的序号，否则根本不被问。
4. **把 zone 的"不"画在错误的一侧。** `may_meet` 就是那条半开规则，两端各有一个用例：一个正好结束在段的
   第一条记录处的范围**不**碰到它（那条记录属于下一个问题），而一个正好从它的最后一条记录开始的范围则碰
   到。把任何一个比较的方向调反，代价是一条记录且没有任何计数，所以规格两端都问，也所以未声明的 zone 答
   `true`。
5. **大小随词表走的布隆过滤器。** 它看起来慷慨，却会破坏合并：两个形状不同的过滤器不能做 OR，而一个把每
   个名字重新哈希一遍的合并，会去读索引存在就是为了避免读的那些记录。大小是这个构建的常数，解码器拒绝别的
   一切，而固定大小的代价——词表超出它能装下的范围后，它对一切答 `yes`——写在模块里并被断言，而不是被指
   望。
6. **把索引读成第二个真相来源。** 计划一旦用索引里的值去回答清单也声明了的东西，两者就可能不一致
   ——而一个*过期但有效*的文件，或者一个旧版本写下的文件，这时就是一个错误答案，而不是一个缺失的答案。
   索引只被问*它能不能排除某个段*，别的什么都不问。
7. **测量时间的预算。** `slow:bench-budget@10` 比较的是计数，而一条测量毫秒的车道，会在有负载的机器上
   红、在空闲的机器上绿——预算就是这样教会人们重跑它，而不是读它。`tests/budget_pruning.rs` 里的每个指标
   都是一个计数、一个字节总数，或者两个计数的比值。

## 延伸阅读

- `src/engine/index/mod.rs`——布局，逐字节，以及 `Index::load` 给出的三种答案。先读为什么 sidecar 不在
  `segments/` 里的那一节，再把它挪过去。
- `src/engine/compaction/mod.rs`——`seal` 与 `merge`：两者写段和它的索引的顺序，以及合并索引是从什么并集
  写出来的。
- `src/engine/query/plan.rs`——一个循环里的两个裁剪决定，以及计划分开计的是什么。
- `crate::engine::index::bloom` 的表——这个构建写出的大小对应的假阳性率，以及词表超过多大之后过滤器就不再
  省读。
- Apache Parquet 的格式规范，"Column Chunk" → *bloom filter*——同样的 sidecar 思路，出现在一个你多半用
  查询引擎读过的文件格式里，也带着同样那对矛盾：固定大小与不断增长的基数。
- MurmurHash3 的 `fmix32`——模块哈希里的那一步雪崩，以及校验和为什么不是哈希。
- RocksDB 的 wiki，"Partitioned Index Filters" 和 "Bloom Filter"——数据文件旁边的索引，以及一个有数百万个
  段的存储最终会需要的分区。
- ClickHouse 的*数据跳过索引*——`minmax` 与 `bloom_filter` 作为两类跳过索引，正是这一步手工搭出来的那一
  对。
