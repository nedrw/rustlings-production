# 解析器有多可靠，取决于弄坏过它的那批输入

## 为什么

`lakelet/4.1-ingest-protocol` 造了一个解码器，它全部的活就是接过一个不站在你这边的人递来的字节。它的
规格有十二个手写用例，每一个都是*有人想到过*的形状：一整帧、一帧的前缀、超过上限的长度、来自未来的
版本。问题本身就是这个形状。解析器的输入空间是某个对端能发来的每一个字节串，而人写下的用例，是他们
已经怀疑过的那些。真正上线的 bug，是没人怀疑过的那个——差了几个字节的长度、比代码预期更早结束的
缓冲区、含义在一个还没人在跑的构建里变了的取值。

模糊测试是查看没人想到过的输入最便宜的办法：拿*能用*的输入，稍微变异一下，一个个交给解析器，让机器去
找那个栽倒的用例。让它值点钱的是两个性质，两个都在这一页上：

- **它带种子，而且种子算数。** 一次失败必须是一个*用例*：同一个种子在这个进程、下一个进程、另一台
  机器上都得产出同样的输入，否则那个发现就只是一个关于某个星期二的故事，而不是别人能复现的 bug。
  生成器之所以是这里写出来的几十行代码，而不是某个依赖里的 `ThreadRng`，原因就在这里：一个在补丁
  版本里换掉算法的 crate，会悄悄改变一个种子意味着什么；
- **它会留下一份语料库。** 模糊测试器的价值不在于它跑过，而在于它*找到*了东西，而那个发现一年之后
  还能重放。一行一个输入，放在仓库里，每次构建都由装置和规格读一遍——这就是一次回归测试和一篇
  “从前出过这个 bug”的笔记之间的区别。

也是在这里，这个项目从一件你能描述的东西，变成一件事故复盘能用得上的东西。这一步附带的抓包扫描器
（`src/protocol/sniff.rs`）回答的是“这个文件里有哪些帧？”，对象可以是一份 `tcpdump` 转储、一份只
抓到半条连接的日志，或者一个丢了尾巴的存储。它是新代码，解析的是陌生人挑的字节，而解析陌生人挑的字节
的新代码里一定有 bug。下面这趟游走，就是你找出自己那些 bug 的方式。

## 任务

- 写 `src/protocol/mutate.rs`：`walk(seed, iterations, visit)`，一次交给 `visit` 一个变异过的
  输入。它欠四件事——同一个种子游走同样的输入（在任何进程里）、另一个种子游走到别处、这个格式有的
  每一种变异都在游走里（截断、翻转字节、改长度字段、插入垃圾）、以及它产出的不全是垃圾：游走从解码器
  接受的帧出发，并且放过其中一些不动，因为一个解析器*接受*的输入，正是把“拒绝”和一个已经罢工的
  解析器区分开的东西。生成器要手写，并且留在这个模块里。
- 跑装置：`cargo test -p lakelet --test fuzz_protocol -- --nocapture`。它在 `KILN_FUZZ_SEED`
  （默认 `1`）下让 60,000 个输入走一遍 `frame::decode` 和 `sniff::ranges`，重放
  `tests/corpus/**` 下的全部内容，最后打印两个计数器。一次游走在某个输入上栽倒时，它会先按语料库
  自己的格式打印那个输入，再让 panic 穿过去。
- 指望第一次运行就找到点什么。如果第一遍就是绿的，说明你的变异器还没摸到这个格式的边——差几个字节的
  长度、比解析器预期更早结束的抓包、本该是字段的位置上放着的垃圾。
- 把弄坏过解析器的那个输入放进 `tests/corpus/parser/`，一个 `.txt` 文件里一行一个十六进制输入，再
  配一行 `#` 说明它代表哪种失败（格式在那个目录的 `README.md` 里）。先把它最小化：仍然能走到那个
  失败的最小输入，才值得留下，而它也是最能把这件事解释清楚的输入。
- 修的是*解析器*，不是测试。然后把 `course/tracks/lakelet/fuzz/4.2-parser-fuzz.toml` 里的三个
  种子都跑一遍（`for seed in 1 7 20260101; do KILN_FUZZ_SEED=$seed
  cargo test -p lakelet --test fuzz_protocol -- --nocapture; done`），再跑
  `kiln check
  lakelet/4.2-parser-fuzz --slow`，它会重跑这三遍，并对每个种子必须搜到多少、以及必须重放多少语料
  输入设了下限。

## 完成标准

- `kiln run lakelet/4.2-parser-fuzz` — 七个规格用例通过：游走对种子稳定、两个种子游走到不同地方、
  解码器的三种回答都到达过、扫描器在递给它的一切东西下都活着并且仍能找到被垃圾围住的帧、语料库的每
  一条都重放、一行不是十六进制的语料被拒绝时点出它的文件和行号。
- `cargo test -p lakelet --test fuzz_protocol -- --nocapture` — 三个种子各自都是绿的，打印
  `lakelet-fuzz iterations=<n>` 和 `lakelet-fuzz corpus_cases=<n>`。
- `kiln check lakelet/4.2-parser-fuzz --slow` — 每个 must 闸门都是绿的，包括 `slow:fuzz@3`：
  三个种子都跑过，每个都做出来超过 `iterations_min` 个输入，并且至少有 `corpus_cases` 个输入是从
  语料库里重放的。
- 语料库里存着你的游走找到的那个输入，它上面的注释说明那是哪种失败。

## 陷阱

- **一个种子不稳定的生成器。** 读时钟、读地址、读 `HashMap` 的迭代顺序、读某个 crate 的线程本地
  生成器，都会让同一个种子在下一次运行里游走到别处：规格的同种子用例失败，而报告里提到的每个种子也
  都不再意味着任何东西。
- **只会截断的变异器。** 它只找得到被截短的帧，别的什么也找不到：找不到拒绝（每个严格前缀都是
  `Incomplete`），也碰不到在撒谎的长度上的算术。只会翻转字节的变异器有一个镜像的洞——它永远产不出
  一份在一帧中间结束的抓包。规格的三种回答用例会点出你缺的是哪一种。
- **一份不被重放的语料库。** 一个输入如果躺在笔记里、注释里、聊天记录里，或者躺在一个加载器不读的
  文件里（它读的是 `tests/corpus/` 下面的 `.txt`），它就不是一次回归测试：装置会数它重放了什么，
  而课程那一侧的文件写着它欠多少个。规格重放同一批条目，所以一份悄悄空掉的语料库会失败两次。
- **“模糊测试器找到了它，所以我把断言改了。”** panic 在解析器里；削弱规格不是修法，也撑不久
  （`kiln spec restore` 会把课程那份放回来，而 `spec-integrity` 会让被改过的规格失败），删掉那条
  语料，则是删掉了这个 bug 曾经存在过的唯一证据。
- **一趟把发现藏起来的游走。** 一个不点出输入的 panic，会让你手工二分五万个输入。装置按语料库的格式
  打印输入，原因正在于此：一个你复现不了的发现，是你修不了的发现。
- **只为你跑过的那个种子修。** 在种子 `1` 下发生、在 `7` 下不发生的 panic，仍然是 panic；在相信一个
  修复之前，把课程那一侧文件列出的每个种子都跑一遍——闸门做的正是这件事。
- **在这儿去够 `cargo-fuzz`。** 它是生产项目用的东西——libFuzzer、覆盖率引导、带最小化器和语料目录
  ——但它需要一个 nightly 工具链，还有一个这台机器上没装的 crate（`kiln doctor` 会这么说）。课程
  的装置是一道 `must` 闸门能离线运行的替代品：同一个想法，更小的搜索，而计数器就是裁判。

## 延伸阅读

- 在某个允许你用 nightly 工具链的地方跑一次覆盖率引导的模糊测试器：在这个项目的一份拷贝里
  `cargo fuzz
init`，再 `cargo fuzz run ranges`，看它按覆盖到了什么来*挑*变异，而不是按生成器
  说什么。你刚写的语料格式，也是那个工具会留下的东西。
- 读一读生产级模糊测试器跑的变异阶段（AFL 的确定性阶段、libFuzzer 的字典与 havoc）：翻位、翻字节、
  对整数字段做算术、插入与截断，再配上一份这个格式用的常量的字典。`mutate.rs` 里的四种是那张清单的
  小号版本，而长度字段的改写，是一个带长度前缀的格式缺不了的那一种。
- `lakelet/4.4-wal-recovery` 是同一个想法，不靠模糊测试器：一份写好的日志的每一个截断点，都必须
  恢复成已经确认过的内容的一个前缀，因为撕裂的尾部就是一份在记录中间结束的抓包——正是这一步的游走靠
  截短一帧产出的那种输入。
- 在后面的某一步重新打开 `tests/corpus/`，试着不读注释就说出每一条弄坏了什么。一条没人解释得了的
  条目，就该删掉，或者补上解释。
