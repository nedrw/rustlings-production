# 过载必须是一个决定，而不是让内存耗尽杀掉进程

## 回顾

- `async/backpressure@apply — relay/2.14`：界是在它为的那件工作*之前*取的，而负载下增长的数字，是
  别的某个东西扛得住的数字——在那里是每次在途尝试一张许可，过了 `max_backlog` 就是 `503`，增长的
  是表里的行数而不是进程。这一步是同一个论证，落在守护进程自己的内存上：队列住在服务里，它的容量是
  一个部署的数字，而到了界上会发生什么，是一个有名字的策略，而不是分配器怎么决定就怎么算。
- `io/batching@design — lakelet/4.5-batch-writes`：一次 write 调用承载 N 条记录，计数器说明那些
  调用花什么，而**批的边界是 accept 循环的一轮解码出的那些帧**。这个边界正是这一步要给它加上界的：
  一轮能送来比写者写得下的更多的帧，而队列就是站在两者之间的东西。
- `async/backpressure@aware — mailer/1.14-worker`：一个有容量的通道，以及一个给在满的时候到来的
  调用方的回答。这些在这里都不变；变的是那个回答现在是四个*决定*之一，每个都有计数器，而它们谁都不能
  悄悄收回写入路径已经写下的东西。

## 变化

`4.5` 在自己的延伸阅读里留了一句话，它就是这一步的作业：写入路径一次调用写下的，是一轮里到达的全部，
**而没有任何东西限制那是多少**。一个按定时器或按大小阈值工作的批处理器，会写下一个它的调用方已经
答过的批，所以 `4.5` 故意没加。化解这个矛盾的做法，是在写者前面放一个有界的队列，而它的代价一开始
就说清：**没有空位时，生产者被迫等待**——`4.5` 本来得凭空造出来的那个等待，正是这一步明确说出、
并给了一个策略的等待。

新东西有三件，没有一件是队列本身：

- **守护进程在接受与写入之间没有界。** 一轮的帧在一口气里从套接字进了批，所以一条连接能让守护进程
  拿住多少，唯一的限制就是套接字碰巧送来了多少。现在队列最多拿住 `queue.capacity` 个帧，而*生产者
  做什么都不能*让这个数字变大——界就是这个队列作为 deque 的长度，所以别处没有第二个数字能跟它不一致。
- **过载的决定是一个值，而每一个都被计数。** `Block`、`DropNewest`、`DropOldest` 和 `Sample` 是
  同一个问题（“现在怎么办？”）的四个回答，它们摆在一个枚举里看得见，而一个计数器说明每一个花了什么。
  一个宁愿丢帧也不让生产者等的部署，在一个配置键里这么说；默认说的是反面，因为默认不能丢数据。
- **写入仍然是唯一的确认。** `4.1` 承诺过一个被接受的帧是客户端可以相信它是安全的帧，而 `4.5` 在
  写一组帧时守住了这个承诺；两者之间插进一个队列，让这个承诺*更难*守，而不是更容易，因为连接自己
  不再写任何东西。于是答案挪了位置：写者说写了，帧才算写了；调用方通过队列记的那份账，得知自己每个
  帧的下场；而一条连接在队列尘埃落定之前什么都不报。被队列丢掉的帧，永远不会是调用方被告知已存下的
  帧之一——而现在这是一笔规格能查的算术，而不是文档里的一句话。

**为什么容量是一个部署的键，而 `4.3` 的 fsync 策略不是。** 两者看着像，其实不是：一次 append 什么
时候等设备，是这个存储*本身*的属性（一个由间隔策略维持的 WAL，在 ADR 里定一次，随构建交付），而
一个守护进程在套接字和日志之间可以拿住多少，是它*运行*在哪里的属性——同一个二进制服务一台笔记本和
一台 64 GiB 的机器，而一个帧的载荷可以到一兆字节，所以 `queue.capacity = 1024` 是“几百 KiB 的
普通遥测”，还是“协议允许的最大帧的一 GB”，取决于负载。一个含义取决于部署的数字，就该由部署来选；
规则就是这样，而这一步正是它被用上的地方。

这里故意**没有**的东西，好让读者知道下一步从哪儿开始：fsync 的决定（`4.3`）、打开一个存储会恢复
什么（`4.4`）、记录格式和写入成本计数器（`4.5`，没动），以及段与合并（`4.7`、`4.8`）——在那里，
*同一个*问题换了个名词又回来了：合并不都装得下的段，是“两样东西抢一个位置时谁赢”，而那里的答案
也会是一个策略。

## 任务

这一步由五个性质组成。别的都是包装。

- **永远有界。** 队列最多拿住容量那么多的帧，每个策略都如此，哪怕生产者从不停下。界是分层配置里
  一个部署的数字（`queue.capacity`，旁边是 `queue.policy`），它有一个默认值，而一个要零帧队列的
  部署会被拒绝，拒绝的话点名那个键——一个说自己什么都不接受、然后照样启动的守护进程，比一个不启动
  的更糟。
- **丢弃是一个决定，而每一个都被计数。** 四个策略，一个不多一个不少：
  - `Block` 等到有空位再把帧收进来：什么都不丢，感受到过载的是生产者；
  - `DropNewest` 拒绝*正在到达*的那个帧——付账的是刚到的帧，而它被交回给调用方，好让守护进程记的
    那一行能点它的名；
  - `DropOldest` 总是收下到达的帧，丢掉**等得最久**的那个：损失落在更早到达的数据上，而这件事发生
    的时候队列的深度不动；
  - `Sample` **每 `SAMPLE_KEEP` 个到达里收一个**，其余拒绝——它是唯一一个在队列没满时也丢帧的策略，
    因为它是一个*速率*而不是一个界，它保护的是写入路径的吞吐量而不是内存。一个被收下、却发现没有
    空位的到达，用 `DropOldest` 的方式腾出位置。

  一个计数器说明队列丢了多少帧；*决定*说明丢的是哪个帧；而过载会被报告出来：每丢一帧一行日志，
  停止时还有守护进程自己的一份账。
- **确认永远不走在前头，而丢掉的东西永远不被确认。** 那是 `4.1` 的承诺，经由一个第三方守住：写入
  路径说写了（`wrote`，在字节落到文件上*之后*调用，绝不在帧被交出去的时候调用），帧才算写了；
  调用方的那份账在那一刻记账；而 `DropOldest` 只能收回一个仍然**在队列里**的帧——绝不能是写者已经
  取走的，也绝不能是已经写下的。一条连接要等队列尘埃落定，才报告它接受了什么。
- **`offered == accepted + dropped`，以及 `accepted == written + queued`。** 在页面里和代码里都
  写出这两条，并且按策略、在每个检查点上强制它们。它们是同一句话：`accepted` 计的是队列收进来、
  并且没有再丢掉的帧，所以被一次驱逐收回的帧，走的时候也把 `accepted` 带走——一个让它继续被计数的
  实现，是一个两条等式对不上的实现，而抓住它的用例，是在 `DropOldest` 和 `Sample` 下提供超过界的
  帧数的那个。
- **过载之下，调度决定谁被丢掉**——这就是这一步由 `slow:sim@3` 评判、而不是一次运行的原因。三个
  种子，每个种子一份记录，同一个种子逐字节重放，而至少有两个种子不同：装置在任何地方都不打印种子，
  所以摘要不同是因为事件不同。

**课程给你什么，什么是你的。** 脚手架声明表面，因为有三个东西读它——规格、装置，还有守护进程：

- `src/service/backpressure.rs`——`Policy`（带 `as_str`/`parse`，让配置键和日志行用同样的方式
  拼写这四个决定）、`Decision`（一个帧的下场）、`Tally`（一个调用方被告知的东西）、`Stats`
  （四个计数器），以及 `Queue`，连同它的方法签名和 `todo!()` 函数体。**`Queue` 背后的状态是你的**：
  这个文件故意不声明任何字段，因为界住在哪儿是这一步的第一个设计决定。界就是队列自己的长度，而一个
  跟踪同一件事的第二个数字，是一个能跟它不一致的第二个数字；
- `tests/sim_backpressure.rs`——课程的装置，`slow:sim@3` 跑的就是它：四个阶段，每个策略一个，三个
  生产者冲进一个大小为三的界，而守恒律按策略在情景*内部*断言；
- `src/service/mod.rs` 和 `src/service/config.rs`——模块声明和两个 `Config` 字段，插进骨架声明的
  标记区域里。契约文件里每一个 `todo!()` 都是你的，脚手架够不着的部分也是：两个键在四层里的接线
  （默认、文件、环境、旗标——`4.1` 的阶梯，没变）、提供一轮帧的 accept 循环、排干队列的写者任务，
  以及守护进程打印的那两行。

两层计数器，它们回答不同的问题：**队列的** `Stats` 是守护进程看到了什么、对它做了什么，而**一个
调用方的 `Tally`**，是一条连接关于自己那些帧可以说什么。两个都需要，因为一个共享的界可能丢掉一个由
已经走掉的人提供的帧——而那恰恰是一条按连接的日志行猜不到的情况。

**两个键，拼写写清楚。** 名字就是契约——配置文件、环境、命令行和报告都到达同两个设置项，而规格会
一一驱动它们：

| 层 | 容量 | 策略 |
| --- | --- | --- |
| 默认 | `DEFAULT_CAPACITY`——1024 个帧 | `DEFAULT_POLICY`——`block` |
| `lakelet.toml` | `[queue]` `capacity = 8` | `[queue]` `policy = "drop-oldest"` |
| 环境 | `LAKELET_QUEUE_CAPACITY=16` | `LAKELET_QUEUE_POLICY=sample` |
| 命令行 | `--queue-capacity 32` | `--queue-policy drop-newest` |
| 一个部署读回来的东西 | `queue.capacity = 32` | `queue.policy = drop-newest` |

一个没有层能用的值，是携带它的那一层给出的拒绝（`4.1` 的规则：一个认不出的键不能悄悄变成默认值），
而这里要紧的两个，一个是**零帧**的容量——一个永远收不进帧的队列是一次点名它的键的拒绝，而不是一个
照样启动的守护进程——另一个是没人讲得出的策略名，拒绝它的话会列出这个构建有的四个。

守护进程打印两样运维会读的东西：队列每丢一个帧一行，写 `frame dropped by the queue`，带
`policy=<name>` 和 `bytes=<the payload's length>`；停止时一行，写 `queue drained`，带 `policy`、
`capacity`、`offered`、`accepted`、`dropped` 和 `written`。两样里都没有任何时长。

## 陷阱

1. **一个记在别处的界，不在帧上。** 在队列旁边加一加的计数器、许可数不等于 deque 槽位的信号量、
   在 push 之后才检查 `len()` 的 `Vec`：每一个都是能和队列实际拿住的东西不一致的第二个数字，而抓住
   它的用例，是那个从不停下的生产者（对着大小为三的界提供一千个帧，每提供一次就读一次深度）。
2. **一个把自己叫醒的生产者。** `Block` 必须停到有空位为止，所以它得把自己已经交出去的帧告诉写者
   ——而如果它 signal 的正是它马上要 await 的那个对象，它会完成自己的 future（`tokio` 的 `Notify`
   对先创建后检查的写法承诺会这样），然后在一个毫无进展的循环里空转。症状是一个
   `block_waits_for_room_instead_of_dropping` 永远跑不完，同时 CPU 在 100%，那是一个你得认出来的
   挂起，而不是一个你读一读就懂的红测试。
3. **在提供的时候确认。** 队列一收进帧就算作已接受，是这一步存在要防的缺陷，而它在写入迟到之前都
   看不见：帧还在队列里，连接已经打印了它的行，而 `4.1` 的突发用例发现记录比那一行声称的少。在
   `DropOldest` 下它比迟到更糟——帧可以在把它叫作已存下的那一行之后被驱逐，于是守护进程报告了它
   从没写过的数据。
4. **把一个被驱逐的帧还算作已接受。** 把帧从 deque 里收回来却不放 `accepted` 一起走，会让
   `offered == accepted + dropped` 正好差上驱逐的次数：十二个帧在 `Sample` 下进一个大小为 1 的界，
   读出来是 `offered=12 accepted=3
   dropped=11`，而用例会说出那是哪个策略。
5. **会驱逐的 `DropNewest`，或者会拒绝的 `DropOldest`。** 两个策略的区别在于丢的是*哪个*帧，不在于
   丢了多少：`DropNewest` 拒绝正在到达的帧（交回来的载荷就是刚提供的那个），`DropOldest` 收下到达
   的帧，交回等得最久的那个。每个策略一个用例检查这些身份，所以一个丢对了*数量*的实现仍然是红的。
6. **只在满的时候才抽样的 `Sample`。** 那它就是多绕了几步的 `DropNewest`：到达的帧没有被计数，留下
   的不是第 4、第 8 和第 12 个，而那个在 `SAMPLE_KEEP = 4` 下提供十二个帧的用例，会在哪几个活下来
   这件事上失败。
7. **一个拒绝而不等待的 `Block`。** 让测试不再挂起最便宜的办法，就是没有空位时回答 `Refused`——而它
   把唯一一个什么都不丢的策略，变成一个在错误时刻到达什么就丢什么的策略。`dropped == 0` 就是这个
   用例，它在检查点上被检查，而不只在最后。
8. **一个容量为零却照样启动的队列。** `queue.capacity = 0` 必须是一次点名那个键的拒绝，每一个能
   携带它的层都如此；一个带着永远收不进帧的队列启动的守护进程，是一个唯一行为就是丢掉一切的守护
   进程，而一个部署会在生产里发现这一点。
9. **每帧一个批。** 把一轮的每个帧单独提供——或者一个一次只取一个帧的写者——让每个行为用例都保持
   绿，却把计数器推向错误的方向：`4.5` 的守护进程用例报出和记录一样多的调用，而预算的
   `calls_per_record_max` 失败。一轮就是一次提供，写者取走所有等着的，这才让批的大小成为队列的决定。
10. **一个在写之前报告写入的写者。** `wrote` 在字节落到文件上之后才调用，而不是在帧被取走的时候；
    队列自己的 `written` 计数器和每个调用方的账都在那里动，而盯着 `take` 与 `wrote` 之间那个窗口的
    用例，断言此时还什么都没写。
11. **记录里的一个种子。** 在一行 `lakelet-sim` 里打印 `seed=7`，让两个种子在没有任何事件不同的
    情况下也不同，于是 `slow:sim@3` 里“至少两份记录不同”的那一半不再意味着任何东西。在这里把种子
    区分开的，是事件的顺序。
12. **记录里带着时钟或地址。** 格式化一个 `tokio::time::Instant` 会把机器真实的单调时钟基准写进
    记录，同一个种子于是产出两个不同的摘要——`the same seed produced two different transcripts`，
    正是 `docs/handoff-m3-log.md` §6 量到的那个失败。打印情景*观察到*的东西，别的都不打印。
13. **装置里的 `tokio::net::*`。** 真正的套接字类型需要 `enable_tokio_io()`，从那以后地址就变真
    了：一个模拟地址回答 `AddrNotAvailable`，一个共用的端口回答 `AddrInUse`。绑
    `turmoil::net::TcpListener`、按主机名连接，而模拟 DNS 解析的正是主机名。
14. **三个文件里任何一个留下 `todo!()`。** `no-todo` 跑遍每一个 target，包括规格永远不调用的那些
    ——而脚手架状态本来*就该*是红的，所以第一次 `cargo test -p lakelet --test spec_backpressure`
    每个用例都失败，是这一步的起跑线，而不是坏掉的仓库。

## 延伸阅读

- **`lakelet/4.8-compaction`** 是同一个问题回到存储层的地方：两段并不都装得下时做合并，又是一个
  “两样东西抢一个位置时谁赢”，而答案会是另一个策略、另一个计数器。拿这一步的守恒律去对照它：那个
  形状（“进来的每一样，要么写了，要么丢了，要么还在手上”）才是可复用的部分。
- **`tokio::sync::mpsc`** 是这个文件在生态里的版本：`send` 等容量，`try_send` 拒绝，那就是 `Block`
  和 `DropNewest` 在同一个类型里。它*没有*的是 `DropOldest` 和 `Sample`，而理由值得你想清楚——顺序
  归接收端，所以一个发送端看不见等得最久的那个帧。`tokio_util::sync::CancellationToken` 是一条
  排干、而不是丢弃的停止路径的另一半。
- **`tokio::sync::Notify`** 的文档，尤其是关于在条件被检查*之前*就创建 future 的那一句：那条保证
  就是先创建后检查这个写法之所以正确的原因，而 TRAP 2 是同一个对象在两边都用时它的代价。
  `tokio::time::Instant` 在暂停的时钟下（`tokio::time::pause`），是一个确定性的情景会去够的另一件
  工具。
- **OpenTelemetry 的采样器**（`TraceIdRatioBased`、`ParentBased`，以及 SDK 里带 `max_queue_size`
  和 `max_export_batch_size` 的 `BatchSpanProcessor` 队列）是在一份规格里的 `Sample` 加上一个界：
  采样器把流变稀，处理器的队列给内存加上界，而被丢弃的 span 数就是两者都会报告的数字。**Vector 的**
  缓冲区文档是同一个故事，用的是 `buffer.max_events` 和 `when_full: block | drop_newest`；而
  **librdkafka 的** `queue.buffering.max.messages` 配 `queue.buffering.max.ms`，是一个消息代理
  交付的生产者侧版本。
- **内核早就在跑这个文件。** 一个套接字的接收缓冲区（`SO_RCVBUF`）、TCP 窗口和监听积压，是同一个界
  配同一批策略——而内核面对一个满的接收缓冲区，回答是停止确认，那就是替发送方执行的 `Block`。那一层
  的 `drop_newest` 意味着悄悄丢包，这也是为什么一个丢不起帧的协议必须自己给自己的内存加界：不然的
  替代品，是一个没人选过的界。
