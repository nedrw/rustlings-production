# 备份只有恢复过一次才算数

## 为什么

前面每一步都把存储当成*进程*往里面写的地方：打开时重放日志，一次 flush 关掉一个 segment，一次
合并换掉 manifest。磁盘挂掉的那天，这些都不重要——重要的是有人能不能把目录挪到别处，再拿回同一个
存储。那是另一类工作，失败的方式也是早先任何测试都抓不到的。在存储正被写入时取的副本，同时是两个
存储，而直到恢复那一刻才有人发现。某个 segment 在传输中丢了一个字节的副本，是一个看起来和完好目录
一模一样的目录。恢复了一半的目录是个*陷阱*：它不是存储，从里面什么都答不出来，而操作者打开它想看个
究竟，只会看着存储自己的恢复过程把里面的东西删掉。而一份从没人恢复过的副本根本不是备份——它是一个
带着时间戳的希望。

所以这一步讲的是操作者据以做决定的两个数字：**RPO**，副本开始之前崩溃已经丢掉了什么——这是写路径
的策略，不归备份工具管——以及 **RTO**，把存储放回去要花多久。两个都不是这个项目的闸门能判的计数，
所以两个都要*量*出来、写在一页上，再交给一次读者能重跑的演练来让它可查。

## 任务

脚手架造了四个契约文件、一套完整的装置，和那一页的骨架：`src/engine/backup/mod.rs`（副本）、
`src/engine/backup/manifest.rs`（副本自己的 manifest）、`src/engine/backup/restore.rs`（恢复）、
`src/cli/backup.rs`（三个命令）、桩文件 `docs/dr-drill.md`，以及 `tests/sim_backup.rs`——`sim`
闸门跑的那个演练，它是**完整的**，你的活就是由它来判的。它还在 `src/engine/mod.rs` 和
`src/cli/mod.rs` 的标记块里插入了 `pub mod backup;`，并且在 `src/engine/compaction/mod.rs` 的标记
块里给了你两扇门，让一个只*读*存储的工具能进来：**`Manifest::read`**，不开存储就读到它的 manifest；
**`Manifest::load`**，读到那份 manifest，并把里面点名的每个 segment 对着它的文件校验一遍。`copy`
是后者的第一个调用者，而它们存在的理由，正是 `copy` 首先要弄对的那件事：副本只读它的
源，绝不写它，而打开一个存储*就是*一次写。

**`copy(source, destination, interruption)`** 把 `source` 的存储搬到 `destination`，顺序就是模块
文档论证的那个：先是存储自己的 manifest（它就是文件清单——manifest *就是*存储，而 `segments/` 里一个
它没点名的文件，是崩溃留下的孤儿，所以不算存储的一部分），然后是它点名的每一个 segment，按它给的
顺序，最后是重放能证明的那段日志前缀，一个字节也不多。写每个文件，等设备落盘，只有*之后*才追加点名
它的那一条：正是这个顺序，让「副本的 manifest 说清了哪些是完整的」成为代码的性质，而不是一句关于文件
系统的主张。永远不要带上 sidecar 索引（派生状态，`lakelet/4.14-index-pruning`），也永远不要带
`*.pending`。`Interruption::AfterBytes(n)` 在文件内容写满 `n` 个字节后停下副本：被预算切开的文件
**残缺且没有被点名**，副本到此为止。`Report` 是操作者读的那些计数，而拒绝是带类型的：源里没有存储、
目标已经是一个存储，以及存储自己的读取器以什么理由拒绝。

**`backup.manifest` 是一份日志，不是你自己发明的格式。** 副本自己的 manifest 逐字节就是
`lakelet/4.4-wal-recovery` 的格式——第一条用 `wal::segment::introduce`，之后每条用 `encode`——
所以一份在条目中间被打断的副本，恢复起来和存储的日志一模一样：被证明的前缀、没人能读的字节，以及
说明原因的 `Stop`。条目的编解码是显式字节：相对于存储根的名字、一个 kind、字节数、文件给出时的记录
数、文件给出时的首尾毫秒，以及**整个文件的 crc32**（`crc32fast`，日志本来就在用的那族校验和）。
`Manifest::load` 答的是那串条目、被丢弃的字节和 `Stop`——而一份 manifest 根本不在的副本，是一个
带类型的拒绝，从来不是空列表。

**`restore(source, destination)`** 只有一个顺序，而这就是安全论证的全部：加载副本的 manifest，拒绝
已经装着存储的目标，**在写任何东西之前校验每一条**（存在、长度是 manifest 说的、crc32 是它说的），
只有之后才写——存储自己的 `segments.manifest` 放在**最后**，因为那个文件才是提交点
（`lakelet/4.8-compaction`：一个目录之所以是存储，就因为有那个文件）。所以一次被拒绝的恢复会让目标
保持原样，而在最后一个文件之前被打断的恢复留下的目录不是存储——这就是为什么页面上必须说：不要打开
一个恢复了一半的目录去看。损坏是一套带类型的词表，`Display` 会点出文件，凡是有两个数字的地方两个都
点：缺失、偏短、校验和不对、读不出来。

**然后是操作者这边。** `src/cli/backup.rs` 是三个命令，叠加在 `lakelet/4.10-downsampling` 的语法
上，并继续守 `jobq/3.15-cli-contract` 的承诺：`backup --store <DIR> --to <DIR>`、
`restore --from <DIR> --to <DIR>`，以及 `drill [--store <DIR>]`——那次预演，用真实的写路径造一个
存储、模拟一次机器死亡、复制、恢复，再对一份在 segment 内部被打断的副本重做一遍。它们的回答是这个
工具的两种形状（每行一个 `name=value`，或者 `--json` 下的一个对象），失败类别是 `4.10` 那套，没变：
`3` 问的东西不在，`4` 存储拒绝，`2` 调用错了，`1` 一个跑不起来的部署。`drill` 的输出格式写在文件
顶部的 `DRILL_LINES` 里：那是一个页面和脚本都会读的接口，所以要写在一个不会漂移的地方。分发的那一
条、`USAGE` 的几行、每个命令留下的类别，都是 `src/cli/mod.rs` 里的改动。

**`docs/dr-drill.md` 是交付物。** 照着一次运行写，绝不照着意图写：这个存储的副本是什么、它故意不
做什么（它不是一份实时副本——要说清实时副本另需要什么）、操作者的五个步写成的命令、「校验通过」对
每一类损坏分别是什么意思、**量出来的 RPO** 以及解释它的那句话，还有**以墙钟时间计的 RTO，并点名
机器和存储大小**。它钉住的那块是 `lakeletq drill` 的整段输出，逐行不差，而规格会重跑那条命令并
比对——所以那块里不能有钟，计时那一行（`LAKELET_DRILL_TIMED=1`）留在散文里。

不要碰 `src/engine/compaction/**`、`src/engine/wal/**` 或 `src/engine/spool/**`：文件清单、日志的
前缀规则和写路径的持久边界都是早先几步的契约，`lakelet/4.4-wal-recovery` 的规格断言着它们。

## 完成标准

- `cargo test -p lakelet --test spec_backup_restore`（在 `app/lakelet` 里）——二十个用例通过，每个
  一条主张：一份完整副本恰好点名存储的那些文件
  （`a_complete_copy_names_exactly_the_stores_files`）；每个条目的长度和校验和都与文件对得上
  （`every_entry_states_the_bytes_and_the_checksum_the_file_has`）；被撕裂的尾部条目连同它占的字节和
  `Stop` 一起丢掉（`a_torn_tail_entry_is_dropped_with_the_bytes_it_occupied`）；被打断的副本点名一个
  前缀，绝不点名它切开的那个文件
  （`an_interrupted_copy_names_a_prefix_and_never_the_file_it_cut`）；在第一个字节之前就被打断的副本，
  对着一个根本没有副本的目录
  （`a_copy_interrupted_before_its_first_byte_names_nothing_which_is_not_the_same_as_no_copy`）；一次
  完整的恢复得到它复制过的那个存储（`a_complete_restore_yields_the_store_it_copied`）；一次被打断的
  恢复恰好写出它 manifest 覆盖的东西
  （`restoring_an_interrupted_copy_writes_exactly_what_the_manifest_covered`）；缺一个被点名文件的副本
  被拒绝，目标原封不动
  （`a_copy_missing_a_named_file_is_refused_and_leaves_the_destination_as_it_was`）；翻转一个字节和
  切断一个文件是两种不同的拒绝（`a_flipped_byte_and_a_cut_file_are_two_different_refusals`）；恢复
  绝不覆写一个存储（`a_restore_never_writes_over_a_store`）；在记录中间被切断的日志复制到重放能证明
  的前缀（`a_log_cut_mid_record_is_copied_to_the_prefix_a_replay_proves`）；恢复后的存储带着同一份
  series 台账（`a_restored_store_carries_the_same_series_ledger`）；同一个答案从 `4.11` 的执行器里
  出来（`the_restored_store_answers_a_query_the_source_answered`）；两个命令的形状和类别
  （`the_operators_two_commands_answer_on_stdout_and_leave_one_sentence_on_stderr`、
  `the_restore_command_refuses_a_damaged_copy_and_a_destination_that_is_a_store`）；页面与它引用的
  那条命令对得上（`the_page_carries_the_drill_the_command_prints`）；引擎边界
  （`the_step_stays_inside_the_engine_and_does_not_parse_a_segment`）；副本只读它的源，绝不写到存储
  之上（`a_copy_reads_the_store_and_is_never_written_over_a_store`）；一份把崩溃留在源里的孤儿和写了
  一半的 `segments.manifest.pending` 原样留在原地的副本
  （`a_copy_reads_the_source_and_leaves_an_orphan_and_a_half_written_manifest_alone`）；以及一次
  演练：让它指哪个存储就造哪个存储，什么也没指时什么都不留下
  （`a_drill_builds_the_store_it_was_pointed_at_and_leaves_nothing_behind`）。
- `kiln run lakelet/4.19-backup-restore`——同样的用例，跑课程的副本。
- `kiln check lakelet/4.19-backup-restore`——十一个 must 闸门全绿，`links` 也在内：项目的 markdown
  是整体受判的，所以 `docs/dr-drill.md` 上的每个链接都得解析得到。
- `LAKELET_DRILL_TIMED=1 cargo run -p lakelet --bin lakeletq -- drill`——计时的预演，在你自己的机器
  上跑。把它的 RTO 数字抄进页面，并点名机器。
- 对一个大到有意思的存储跑 `lakeletq backup --store <a store> --to <a directory>`
  （`lakelet-load --profile --cycles 200 --store …` 能造一个），然后对副本跑 `lakeletq restore` 到
  第三个目录，再对恢复后的存储跑一次查询。两次都取 `time`。
- `kiln run lakelet/4.18-cardinality-cost` 和 `kiln run lakelet/4.4-wal-recovery`——仍然绿：这一步
  读台账和日志的前缀规则，两者都不改。

## 陷阱

1. **把整份日志都带走。** `cp -r` 会复制崩溃留下的尾巴，而那条尾巴是一条记录的中间：副本于是
   持有重放证明不了的字节，从它恢复出来的每个存储都从同一个字节开始恢复。只取 `Recovered::bytes()`，
   到此为止。
2. **在字节落到设备上之前就点名文件。** 先追加条目，或者把它和写入当成一口气做，会让「manifest
   说清了哪些是完整的」变成一句关于页缓存的主张。在那之后任何地方停下的副本，都有一份 manifest 点名着
   一个不存在的文件，恢复它会被拒绝——或者更糟，在一台会说谎的设备上成功。
3. **先写存储的 manifest。** 先写 `segments.manifest` 的恢复，有一个毫无意义的提交点：下一个失败
   的东西会留下一个按这个项目唯一有的定义*确实是*存储的目录，身后却缺着 segment。把它放到最后写。
4. **边写边校验。** 写每个文件之前才检查它，看着像同一件事，其实不是：第一个失败会落在恢复的半途，
   而目标现在是一个操作者会打开来看的目录。校验整份副本，然后才写。
5. **打开恢复了一半的目录看里面有什么。** 一个有 segment、没有 manifest 的目录，是一个 segment
   全是孤儿的存储，而打开一个存储会删掉它 manifest 没点名的一切。反方向也有同一个陷阱：往一个已经
   装着存储的目标里恢复会合并两个存储，这就是为什么 `Occupied` 是拒绝而不是警告。
6. **副本里不带 sidecar 索引，还说恢复出来的存储是相等的。** 它是相等的——那是 `4.14` 的规则——
   但从一个没有索引的存储重建出来的*台账*，会留下一些 series：存储丢了 segment 之后，再也证明不了
   自己还持有它们。比 series 和它们的计数，并把窗口当作它们本来就有的差异来读。
7. **把 RTO 数字放进规格要比对的那一块。** 墙钟时间会让同一条命令的两次运行打印出不同的字节，而
   `sim` 闸门会判一个种子什么都决定不了的步失败。那一块是没带钟的那次运行；计时那一行住在
   `LAKELET_DRILL_TIMED` 后面。
8. **把拒绝打印到标准输出上。** 一个把这个工具接到解析器上的脚本，绝不能拿到一个答案的一半加一句
   抱怨：stdout 是答案，stderr 是一句话，退出码是类别。`4.10` 的用例和这一步的都断言着它。

## 延伸阅读

- `course/tracks/lakelet/spec/4.19/backup_restore.rs`——那二十个用例，包括从 markdown 里把页面上
  的块读回来、重跑产生它的那条命令的那个。
- `course/tracks/lakelet/scaffold/4.19-backup-restore.patch`——给你的东西：四个契约文件、那一页的
  骨架，以及判整个步的装置。
- `tests/sim_backup.rs`——演练：一个存储、一次机器死亡、一份副本、一次恢复，以及让副本成为备份的
  那次比对。写 `copy` 之前先读它的模块文档。
- `src/engine/wal/replay.rs`——这一步用到目录而不是文件上的前缀规则，也是副本为什么不是 `cp -r`
  的原因。
- `src/engine/compaction/mod.rs`——*就是*存储的那份 manifest，以及那个会删掉它没点名之物的 open：
  恢复的写入顺序背后的两句话。
- [`pg_basebackup`](https://www.postgresql.org/docs/current/app-pgbasebackup.html)——人们在运维的
  数据库里最接近的东西，而它的 `--checkpoint` 正是这一步略去的实时副本机制。
- [`restic check`](https://restic.readthedocs.io/en/stable/045_working_with_repos.html)——一个把
  校验变成动词而不是事后想法的备份工具，这一步的逐文件校验和是它的一个小版本。
- `lakelet/4.3-write-path-adr`（RPO 那个数字就是它策略里的 `Losses`）和
  `lakelet/4.4-wal-recovery`（这一步自己的 manifest 用它的日志格式写）。
