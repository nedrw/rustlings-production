# 从预算到归责：哪个阶段动了，动了多少

## 回顾

- `perf/bench-budget@apply — jobq/3.22`：一个由计数搭成的预算、一道看它们增长形状的守卫，以及装置打印出
  来好让闸门比较的那些名字。那一步立下的规则，正是这一步所立足的：**墙上时钟的阈值是对机器的测量**，忙碌
  的下午红、安静的下午绿，而一个循环留下的数字——检查过的单元、写下的语句——在每台机器的每个进程里都一
  样。这一步不是第二个预算；它是*预算红了的时候*该做什么，因为"有些东西变慢了"是一句任何评审都没法据以
  行动的话。
- `perf/load-testing@apply — relay/2.20`：对整个服务施加的、刻意而可重复的压力，以及容量答案所读取的那
  条曲线——p99 对并发，旁边放着积压。那一步从外面量*服务*，这一步从里面量*查询*，而两个问题是邻居："这个
  跟得上吗"是多次运行连成的曲线，"这次运行里哪一部分慢"是一次运行的剖析。这一步从它那里拿过来的，是一次
  不需要谁去相信的运行该有的纪律：固定的输入、算出来的统计量，以及两个人都能比较的答案。

## 变化

`lakelet/4.14-index-pruning` 让这个存储的一项开销变成了数字。`pruning_rate` 说明一次查询有多少存储不必
打开，而它旁边的计数器——`segments_pruned`、`blocks_pruned`、`bytes_read`、`bytes_avoided`——说明那值
多少。那是*多少*。它不是*哪里*：一个裁剪决定不再裁剪的查询、一个解压变得更贵的段格式、一个保留的记录是
过去十倍的谓词，以及一个按序列把记录走一遍的 `GROUP BY …, series`，是四种不同的缺陷，而每一种都会移动
`rows_scanned` 或 `rows_answered`——或者什么都不动，因为一次读两百个文件才返回三十条记录的查询，答得正
确而缓慢。

所以这一步数一次运行**内部**的工作，并按引擎里付账的那一部分来拆分。七个阶段，按一次查询走过它们的顺序：
对存储做出决定的计划（`headers`）、读到的块（`blocks`）、解压开的块（`decompress`）、解码出的记录
（`decode`）、谓词留下的记录（`filter`）、折进窗口的值（`aggregate`），以及写进答案的桶（`render`）。这些
计数随答案一起走，装置打印对同一个存储的两次查询的剖析，而这一页说明怎么把一次红了的预算读成某个阶段。

有三样东西是故意**不**在这里的，而它们正是这一步长成这个形状的原因：

- **没有时间。** 不是时长，不是速率，不是开始和结束。一个测量机器的剖析，会是一个两台机器各执一词的剖
  析，而 `jobq/3.22-bench-budget` 已经把那个论证了结了——这一步把它下沉一层，用到一次运行的各个部分上，
  而不是整次运行上；
- **没有新的计划键。** `EXPLAIN` 打印的是一次查询*会*做什么，而前面两步按名字和顺序把它钉住了；已执行的
  计数和剖析属于一次发生过的运行，它们进结果和答案的文档。一个往计划里加一行、用来说明这次运行花了多少的
  步，会是一个对自己撒谎的计划；
- **没有存起来的历史。** 一个 trace 描述一次运行，并跟着它一起报告。这里没有任何东西保留过去某次查询的剖
  析，因为一个记得自己过去开销的存储，会是一个数字取决于它什么时候被问的存储——而
  `lakelet/4.20-capacity-model` 才是那个主题所在的地方：一项能从存储的形状*预测*出来的开销，而不是从一
  次运行量出来的。

## 任务

脚手架加了一个模块、一件量具和一个页面：`src/engine/trace/mod.rs` 与 `src/engine/trace/counters.rs`（计数
器的契约，函数体是 `todo!()`）、课程的装置 `tests/attribution.rs`，以及作为桩子的 `docs/perf.md`。
`src/engine/mod.rs` 在它标好的块里声明了这个模块。

**`src/engine/trace/counters.rs`——每个阶段一个计数，作为一个值。** `Phase` 是按查询走过它们的顺序排列的
七个阶段，带着那一张表（`Phase::ALL`）和每个阶段在指标行与 JSON 键里的拼写。`Trace` 是这次运行的自我账
目：在工作发生的地方 `charge`，用 `count` 和 `total` 读回来，`shares` 是占整次运行的整数百分比，而
`merge` 让两次运行能作为一对来报告。那个文件里有四个决定比代码更值钱：

- **一次 charge 是对一件发生过的事的计数**，记在它发生的地方。事后从另一个数推出来的阶段，是唯一一种让
  剖析变得没用的形状，因为推出来的计数说不出它来自哪个阶段；
- **这些阶段是一条流水线，不是七本账。** `decode >= filter >= aggregate >= render`、
  `headers >= blocks >= decompress`，而 `headers` 是计划自己的守恒等式——
  `segments_opened + segments_pruned + blocks_pruned`，把 `lakelet/4.14-index-pruning` 数的那三张
  清单加起来。一个没有用例能证伪的计数器，比没有计数器更糟；
- **`filter` 是谓词，`aggregate` 是范围。** 一条被 `WHERE` 留下的记录，仍然可能在范围之外，而那才是有
  意思的情况：它说明是谓词变宽了，而不是范围变宽了；
- **`shares` 加起来是 100。** 整次运行的整数百分比会留下余数，而一个说 99 的剖析，是一个有人得去解释的
  剖析；余数最大的那些阶段拿走它。

**执行器来记这笔账，结果来携带它。** `query::exec` 是唯一能看见全部七个阶段的地方，所以 trace 在那里记
账，`Outcome` 也在那里长出 `trace()`，挨着 `lakelet/4.11-query-engine` 和 `lakelet/4.14-index-pruning`
加的那些计数器。规则就是阶段表写下的那些：计划检查过的每个段记一个 `headers`（计划的那三张清单合起来就是
整个存储，这正是那个计数可查的原因），每次读的前后是 `blocks` 和 `decompress`，读返回的每条记录记
`decode`，谓词被问的地方记 `filter`，而 `aggregate` 与 `render` 来自窗口处理自己的账目——它折进去的值，
和它写出的桶。`Outcome` 现有的字段不许变：前面四个规格对它们做断言。

**`lakeletq query --json` 打印剖析。** 文本形式的文档长出一个键 `trace`，按阶段运行的顺序每个阶段一个数；
装置的行和那份文档用同样的拼写、来自同一张表。计划的 `EXPLAIN` 输出和旗标形式的桶数组完全不变——
`lakelet/4.10-downsampling` 的数组是脚本已经在读的形状，往里面加一个剖析，会对那种形式并不问的问题给出
第二个答案。

**`docs/perf.md` 是那一页，也是交付物。** 各阶段以及每个阶段数的是什么、那些等式以及每一条能抓住什么、打
印一次剖析的命令、从一份红了的预算走到某个阶段的路径、一个拿这个项目存储真实打印过的数字做的完整例子，以
及这一页立足的两个想法——剖析器的阶段视角，和跨两次运行比较的一个计数器。背后没有计数的断言，不配出现在
上面。

**装置是课程的，基线是内容。** `tests/attribution.rs` 是那件量具：它封印一个存储，问两次查询，并把各自
的剖析和它们之间的差并排打印。别为了让数字好看去改它，也别改课程的基线——闸门读的是课程的副本，而
`kiln reset lakelet/4.15-budget-regression` 会把装置放回去。

## 完成标准

- `cargo test -p lakelet --test spec_budget_regression`（在 `app/lakelet` 里）——十五个规格用例全过，每
  个一个主张：计数器的算术与它分开记的那些阶段（`a_trace_counts_each_phase_on_its_own`）；剖析是整数百分
  比、从大到小、加起来 100（`a_profile_is_whole_percent_of_the_work_that_ran`）；两次运行作为一份报告
  （`a_merge_is_two_runs_in_one_report`）；名字以及它们背后的那张表
  （`every_phase_has_a_name_and_parses_back`）；一个把一切都裁掉的计划只记 `headers`，别的什么都不记
  （`a_plan_that_prunes_everything_away_charges_headers_and_nothing_else`）；一次真实运行上的每一条等式
  （`a_run_charges_the_phases_it_walked_and_the_identities_hold`）；索引省下的那一份作为一个阶段，以及那
  些*没有*动的阶段（`the_phases_move_when_the_index_is_taken_out_of_the_plan`）；一条被范围挡在外的记录
  被过滤、但没被聚合（`a_record_the_range_kept_out_is_filtered_and_not_aggregated`）；同一个问题两次花同
  样的工作（`the_same_question_costs_the_same_work_twice`）；一次什么都没答的查询仍然干过活
  （`a_query_that_answers_nothing_still_worked`）；一个什么都没装的窗口不是一个桶
  （`a_window_that_held_nothing_is_not_a_bucket`）；命令行每个阶段打印一个数
  （`the_command_line_prints_one_number_per_phase`）；答案文档长大了而旗标形式的数组没有
  （`the_answer_document_grew_and_the_flag_forms_array_did_not`）；这一页对着阶段表
  （`the_page_states_the_profile_the_lane_prints`）；以及那条边界
  （`the_trace_is_engine_code_and_counts_work_rather_than_time`）。
- `kiln run lakelet/4.15-budget-regression`——同一批用例，跑课程的副本。
- `kiln check lakelet/4.15-budget-regression --slow`——十个 must 闸门全绿，包括 `slow:bench-budget@10`
  （跑下面那套装置，把它的三十六行与课程的基线比较）。
- 在 `app/lakelet` 里 `cargo test -p lakelet --test attribution -- --nocapture`——读你自己的数字。存储是
  二十四个封印过的段，车道对最近十二小时问两个问题；最先要看的行是 `selective_decode` 对 `wide_decode`
  ——同一个存储、同一个范围，加上一个索引帮不上忙的谓词——然后是那五行 `*_saved`，它们是两份剖析之差落
  在它所处的阶段里的那一份。
- `lakeletq query --store <store> --sql "SELECT count(value) FROM cpu WHERE host = 'h20' AND
  ts BETWEEN … AND … GROUP BY time(1h), series" --json`——答案的文档，`trace` 挨着计数器和桶。然后
  `rm -rf <store>/index`，问同一个问题：答案是同一个答案，`blocks` 和 `decode` 大十二倍，而 `filter`、
  `aggregate` 和 `render` 完全没动——索引省下的是读，不是记录。那次演练值得亲手做一遍，因为它就是一份
  阶段剖析存在的全部意义。
- `kiln run lakelet/4.11-query-engine`、`lakelet/4.10-downsampling` 和
  `lakelet/4.14-index-pruning`——仍然绿：计划打印它原来打印的键，旗标形式的 `--json` 仍然是它原来那个数
  组，裁剪计数器还是原来的意思。

## 陷阱

1. **把交给窗口处理的东西都记到 `aggregate` 上。** 一次 `GROUP BY …, series` 的查询，会把它读到的记录按
   序列各交给窗口处理一遍，于是一个把这一份都记上的运行，会把同一条记录每条序列数一次：在宽查询上就是
   `aggregate` 720 对 `filter` 360，而 `filter >= aggregate` 这条等式，就在车道问的那个存储上失败。真正
   成为某个窗口一部分的才是诚实的计数，而窗口处理自己已经报告了它。
2. **把范围和谓词一起记到 `filter` 上。** 这是两个不同的问题，而剖析正是把它们分开的东西：范围折进过滤
   器之后，每次运行里 `filter` 和 `aggregate` 都是同一个数——等式不再能证伪任何东西——而那个半小时的用例
   会红，因为它正是"谓词留下的一条记录在范围之外"的情况。
3. **给它计时。** 一个用毫秒测量的阶段，是一个会被有负载的机器移动的阶段，而读它的闸门会在别人的构建正
   在跑的时候红。trace 模块里不许有任何东西提到时钟——规格会读源码来确认这一点——理由正是
   `jobq/3.22-bench-budget` 了结的那个。
4. **往 `EXPLAIN` 里加一个键。** 计划打印的是一次查询*会*做什么；剖析讲的是一次发生过的运行。
   `lakelet/4.11-query-engine` 的规格数计划的行数，`lakelet/4.14-index-pruning` 的规格按名字和顺序断言
   它的十三个键，所以第十四个键会让前面两步变红——而读一份红了的预算所用的数字，不是计划的。
5. **事后推出来的计数器。** 在这条车道测量的每一次运行上，`decode = rows_scanned` 和
   `aggregate = rows_answered` 恰好就是诚实的数字，于是一个两个阶段都从结果总数推出来的 trace 能通过整
   个规格——而它仍然是这一页反对的那个失败，因为从一个计数推出来的计数说不出工作来自哪个阶段。让它显形的
   是那次演练：拿掉索引，`decode` 动了，`filter` 却没动；而一个事后拼出来的 trace，根本没有办法量到这一
   点。
6. **加起来不对的份额，或者被漏在剖析之外的阶段。** 整次运行的整数百分比会留下余数；一个打印 99 的剖
   析，或者一个因为某个阶段四舍五入成零就把它漏掉的剖析，是读者得去重建、而不是读的剖析。跑过的阶段就是
   那些行，余数归最大的几个。
7. **两次运行里都是零的指标。** 两次运行都不记的计数器，是闸门在比较、却没有任何缺陷能移动的一行：它让
   一个绿的闸门看起来像证据。一个确实不属于某次运行的阶段，属于这一页的正文，不属于装置的输出。
8. **改装置或基线，而不是改代码。** `tests/attribution.rs` 是课程的文件，基线是闸门读的那份副本：一个
   被改得合适的指标，是一个不再算测量的测量。`kiln reset lakelet/4.15-budget-regression` 会把装置放回
   去，而一个红的闸门，才是对一次真实改动的回答。

## 延伸阅读

- `course/tracks/lakelet/spec/4.15/budget_regression.rs`——那十五个用例，包括那次移动三个阶段、放过三个
  阶段的索引移除。
- `course/tracks/lakelet/budget/4.15-budget-regression.toml`——闸门比对用的那份剖析，在参考解上测得，工作
  负载也写了下来。
- `cargo test -p lakelet --test attribution -- --nocapture`——那件量具：一个存储、两次查询、三十六行。
- `src/engine/trace/counters.rs`——阶段、等式和份额，用这个项目自己的口吻。
- [`perf stat`](https://perfwiki.github.io/main/)——一次运行按计数而不是时长来报告：指令、分支、缓存未命
  中。那里的阶段是处理器的；论证与这一步关于一次查询所说的，是同一个。
- [Prometheus: metric types](https://prometheus.io/docs/concepts/metric_types/)——在每台机器上意思都一样
  的计数器，正因如此，两个样本相减是一个事实而不是猜测。`decode_saved` 就是把这笔算术在一个闸门里做了一
  次。
- `jobq/3.22-bench-budget` 与 `relay/2.20-load-testing`——这一步立足的两步：不会偶发红的预算，以及容量
  答案读自一条曲线的负载运行。
