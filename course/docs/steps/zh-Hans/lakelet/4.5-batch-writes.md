# 写放大：把调用成批，并数清一次刷盘的代价

## 为什么

这个存储接过的每一次 append，都是打开日志、写一条记录、丢掉句柄——这对一次 append *花什么*是诚实的，
也正是这一步存在的理由。那条路上坐着三个调用，而只有最后一个跟磁盘有关：

- 一次**设备刷盘**是毫秒级的。`lakelet/4.3-write-path-adr` 量到的是 4.1 ms，这就是这个构建按间隔
  刷盘、而不是逐记录刷盘的原因——一个逐记录等待的存储，不管磁盘多快，都超不过大约 240 条记录/秒；
- 一次 **open** 走一遍路径、拿 inode 锁、分配一个描述符；
- 一次 **write** 把字节拷进页缓存。

后两个是微秒级的，而它们之所以是预算，恰恰因为这个：它们是按*调用*付的，不是按字节。一次交给内核
六十四条记录，只花一次 open 和一次 write；一条一条交，就花一百二十八个调用，而落到盘上的字节、顺序
都一样。这个比值有个名字——**写放大**，再加上每条记录的调用数——而这一步的要点是，这个比值是写入
路径会数、会打印、也会守住的一个数字，而不是一种得由人去争的印象。

## 回顾

- `store/wal-recovery@apply — lakelet/4.4-wal-recovery`：一条记录是日志头部后面的
  `[length][payload][seal]`，重放在第一条它证明不了的记录处停下，而一个存储靠打开它来完成恢复。
  这一步在一次调用里写下*许多*这样的记录，而格式不允许看出来：一批必须逐字节等于 N 次 append 写下
  的字节，让一个读者或者一次恢复仍然看得见 N 条记录，也让批内部的一刀仍然恢复成它的一个前缀。
- `async/backpressure@aware — mailer/1.14-worker`：一个有界的队列，以及一个关于满了丢什么的决定。
  这一步是那个问题的另一面——它让写入路径每次调用的成本变小，让一轮的帧共用一次调用——并且故意
  **不**限制一轮里到达多少。`lakelet/4.6-ingest-backpressure` 才是那个界和丢弃策略落地的地方，而
  批的大小变成一个有队列挡在前面的决定。

## 任务

这一步由四个性质组成。别的都是包装。

- **一批改变的只是调用，别的什么都没变。** `Spool::append_batch` 把 N 个载荷写成 N 条记录——按给定
  的顺序，用 `wal::segment` 的格式——只花**一次 open 和一次 write**，策略要的话再加一次设备调用。
  `Spool::append` 变成只有一条记录的一批，于是只有一条写入路径，之前每一个承诺都经由它成立。在页面
  里说清哪个系统调用数降了、哪些字节没变：它们是同一条不变式的两半，而规格把同样的载荷写进两个存储、
  比较两个文件，来查这条不变式。
- **一次确认绝不能走在写入前面。** 那是 `lakelet/4.1-ingest-protocol` 的承诺，批量化不会削弱它：
  accept 循环的一轮解码出的帧，在任何一帧被算作已接受*之前*，作为一个批写下。一个先作答、后写入的
  批处理器——按定时器、推到下一轮、从后台任务写——是这一步绝不能引入的缺陷，而它在任何只问文件里
  最后有什么的测试里都看不见。规格正是为此去驱动守护进程：一次写入里一串帧，然后守护进程一说连接
  关闭，就去读日志。
- **计数器就是这一课，而且它们看得见。** `src/engine/flush/batcher.rs` 里放着 `Stats`：写下的记录、
  写下的字节、发生了的**调用**（包括 open）、设备刷盘，以及批数。`Spool::stats()` 回答它们，
  `tests/budget.rs` 把它们打印成 `lakelet-budget
  <name>=<value>` 行，守护进程在停止时打印它们（`store write cost records=… bytes=…
  batches=… calls=… syncs=…`）。计数器**在调用发生的地方**
  记账——`append_batch` 里的 open 和 write，`Spool::sync` 里的刷盘——因为一个由调用方自己加的
  计数器，报的是调用方以为自己做了什么。
- **写放大是一个数字，不是一种感觉。** 每个载荷字节对应的写入字节，以及每条记录的调用数，两个都在
  两种批大小下取，好让一个跟着负载走的成本藏不住。这一步没有任何东西按*时间*评判：预算车道比较的是
  计数（`handoff M2 §1.1`），而一个需要秒表才可信的数字，不是这个项目放进闸门的数字。

**课程给你什么，什么是你的。** 脚手架声明形状，因为计数器是一份别的步骤也会读的契约：

- `src/engine/flush/mod.rs` 和 `src/engine/flush/batcher.rs`——`Batcher`（一起到达的那些载荷、
  它们到达的顺序，以及把它们写下去的那一次调用）和 `Stats`，连同它的访问器，以及写入路径给它记账的
  两种方式；
- `src/engine/spool/batch.rs`——`Spool::append_batch` 和 `Spool::stats`，这一步给写入路径加的两个
  签名。这个文件存在的理由和 `spool/durable.rs`、`spool/recover.rs` 一样：一个学习者要*原地*重写
  的桩，没法靠一次插入交付（`docs/authoring.md` §5 规则 6）；
- `tests/budget.rs`——课程的装置，`slow:bench-budget@10` 跑的就是它；
- `docs/write-amplification.md`——那一页，作为模板：计数器、指标和基线由你来写，而规格会把这一页
  读回去。

那些文件里的每一个 `todo!()` 都是你的，还有两件脚手架交不到你手上的事：`src/service/ingest.rs` 里
的 accept 循环（把一轮的帧写成一个批，并守住上面那个承诺），以及 `src/bin/lakeletd.rs` 里守护进程在
停止时打印的那一行。

## 完成标准

- `cargo test -p lakelet --test spec_batch_writes`（在 `app/lakelet` 里）——十二个规格用例通过，
  包括与 N 次分开 append 的相等、扫过一份按批写成的日志的切点，以及两个驱动守护进程的用例。
- `kiln run lakelet/4.5-batch-writes` — 同样的用例，跑课程那一份。
- `kiln check lakelet/4.5-batch-writes --slow` — 每个 must 闸门都是绿的，包括
  `slow:bench-budget@10`，它把装置的计数和
  `course/tracks/lakelet/budget/4.5-batch-writes.toml` 比较。
- `cargo test -p lakelet --test budget -- --nocapture` — 原始的 `lakelet-budget` 行，两种批大小
  都有，外加把同样的记录每次 append 写一条下来做对照。
- `kiln run lakelet/4.1-ingest-protocol`、`4.2-parser-fuzz`、`4.3-write-path-adr` 和
  `4.4-wal-recovery` — 仍然绿。`Spool::append` 下面长出了一个批，别的东西都没动。
- `docs/write-amplification.md` 点名预算所用的每一个计数器和每一个指标，而 `lakeletd` 在停止时
  打印 `store write cost`，带着这次运行的记录、字节、批、调用和刷盘数。

## 陷阱

1. **一个按 N 次 write 写下的批。** 一次 open，然后每条记录一次 write，能过每一个问文件里有什么的
   用例——字节完全一样——但它输在为它存在的那个计数器上：装置打印 `calls_per_record_max`，闸门报它
   超出了界，而守护进程的 `store write cost` 行报出和记录一样多的调用。
2. **先把这一批答了，稍后再写。** 一个把载荷交给后台任务、定时器或者下一轮的批处理器，让每一个读回
   用例都保持绿，同时破坏 `4.1` 的承诺。抓住它的是读取发生的那一刻：守护进程一说
   `connection closed accepted=8`，规格就去读 `ingest.log`，然后发现不到八条记录。
3. **头部规则在循环里丢了。** 日志的 `LKLT` 头部跟着*第一条*记录走，而且只跟它走。一条每条记录都是
   `segment::encode` 的批，是一个不是日志的文件（`Spool::records` 拒绝它，恢复也证明零条记录）；
   而一条每条记录都是 `segment::introduce` 的批，会把一个头部写进日志中间——下一次重放就在那里
   永远停下。切点扫描对两种都大声失败。
4. **一个重排、分组或者去重的批。** 在写之前给载荷排序（比如为了让写入连续），字节数一模一样，却交给
   每个读者一个不同的序列。`a_batch_keeps_the_order_it_was_given` 就是这个用例，它的消息点名那个
   被挪动的载荷。
5. **一个由调用方记账的计数器。** 从批处理器里调 `stats.charge(n, bytes, 2)`，而不是在两个系统调用
   处记，会让数字撒谎，而存储仍然逐记录 open：预算过了，写入路径却根本没变。在调用发生的地方记账。
6. **一次没东西可写的刷盘。** 一个空批必须什么都不写（不 open、不计账、不成批）。一个照样打开文件的
   实现，会在一个什么都没到达的轮里花掉两次调用，而
   `an_empty_batch_writes_nothing_and_costs_nothing` 把这件事说出来——这一点在 `4.6` 里要紧，因为
   一轮里什么都没有才是常见情况。
7. **按记录去问策略。** 把 write 挪进 `append_batch`，却把 `self.sync()` 留在一个遍历载荷的循环里，
   就把每批一次设备调用变成了每条记录一次：装置的 `fsyncs_per_batch` 于是是 64 而不是 1，而一个
   逐记录等待的存储，正是 `4.3` 花钱避开的东西。
8. **彻底忘了策略。** 一个从不问 `Policy` 的新写入调用，在任何会等待的策略下都会让 `durable_offset`
   落在它写下的字节之后，而 `4.3` 自己的规格会变红——那个失败看起来不会像是这一步的。
9. **不数设备刷盘。** `syncs` 在 `Spool::sync` 里记账，在设备作答之后：一次刷盘的停止和一个等过的
   批都会让它动，而在 `per-record` 下 `syncs` 一直是零，就是这个计数器从来没接过线的迹象。
10. **一行在停止自己的刷盘之后才读计数器的停止行。** 守护进程在它退出路上那次刷盘*之前*打印
    `store
    write cost`，所以 `syncs` 是各次 append 要来的。之后再打印，会报出比写入路径多做的一次
    设备调用，而规格会读这一行。
11. **一份缺了指标的页面。** 规格最后一个用例读 `docs/write-amplification.md`，遇到空白或者一个它
    没点名的指标就失败——文档和基线得用同一套词写，否则评审者只能猜闸门守的是哪个数字。
12. **测量里任何地方的一个时长。** 装置里的时间戳、计数器里的一个 `Instant::now()`、一个以毫秒计的
    指标：预算车道评判的是计数（handoff M2 §1.1），而一行不是 `<name>=<value>` 的装置输出，会被
    报成坏掉的装置，而不是拿去比较。一台有负载的机器和一台空闲的机器给出同样的数字，正是这条车道
    存在的全部理由。
13. **四个文件里任何一个留下 `todo!()`。** `no-todo` 跑遍每一个 target，包括规格永远不调用的那些。

## 延伸阅读

- **组提交**是数据库对同一笔算术给出的答案：PostgreSQL 的 `commit_delay` 和
  `CommitTsControlLock`、InnoDB 的 `innodb_flush_log_at_trx_commit`、MySQL 的 binlog 组提交，都让
  一次设备调用服务许多事务，而它们都让一个客户端等一个同批的伙伴。带着这一步所测的计数器去读其中一份
  实现：它们发布的数字是每事务的调用数和每次提交的字节数，从来不是每次提交多少毫秒。
- **`writev(2)`** 把许多缓冲区交给一次 write 调用，而不用先把它们拼起来。这个项目改为把批建进一个
  缓冲区——批由读到的块约束，所以拷贝也被约束——而 `std::io::IoSlice` 是那个否则会取代这个缓冲区的
  类型。**`O_APPEND`** 是让批那一次 write 落在末尾、而不用我们自己 seek 的东西；**`BufWriter`** 是
  同一个想法往上一层：更少、更大的写入，代价是一次拷贝，以及一些调用方以为已经写下、其实还没写下的
  字节。
- `lakelet/4.6-ingest-backpressure` 是批大小遇见队列的地方：这一步一次调用写下的，是一轮里到达的
  全部，而这里没有任何东西限制那是多少。
- `lakelet/4.7-columnar-segments` 和 `lakelet/4.8-compaction` 是*文件布局*会变的步骤。计数器和
  那一页留着：每个样本多少字节、每条记录多少调用，正是那些步骤用来论证它们的编码和合并花多少的方式。
