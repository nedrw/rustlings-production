# 日志是一个前缀：带校验和的记录、撕裂写入，以及那条已被确认的边界

## 回顾

- `store/wal-recovery@aware — lakelet/4.3-write-path-adr`：写入路径决定一次 append 什么时候等设备，
  而 `Spool::durable_offset` 是那个决定承诺的边界——*机器*死亡拿不走的最后一个字节。
  `docs/crash-points.md` 是每种失败在设备上留下什么的地图，它的第 3 点，撕裂写入，就是这一步的输入：
  一条谁都没写完的记录。
- `time/clock-injection@apply — jobq/3.8-clock-injection`：一个依赖时间的决定，会被交给它允许读的那个
  时钟。这一步的并发那一半是一场*模拟*，在那里时钟是模拟器的：`tests/sim_wal.rs` 里存储的刷盘者在
  模拟时间上睡，因为一次仅仅因为作者机器负载高才发生的刷盘，正是 `slow:sim@3` 存在要抓的那种不确定性。
- `err/typed-errors@design — jobq/3.3-library-errors`：一次失败点名拒绝它的那一层，而调用方从变体里
  做判断，不是从字符串里。在这里，那就是*拒绝*（`Error::Protocol`：这些字节不是这个存储的日志）和
  *恢复*（一个撕裂的尾部，它根本不是一个错误——它是这一步存在的理由）之间的区别。

## 变化

`4.3` 决定了已确认的记录可以在页缓存里待多久，并把那个数字写了下来。它从来不必把日志*读回来*，所以它
承诺的三件事还都只是承诺：

- **`durable_offset` 是一个计数器，不是一份契约。** 没有任何东西拿设备上的字节去对着它量。这一步让
  它变得可执行：一个被杀掉的存储被重新打开，日志被重放，而一次机器死亡留下的东西，被拿去和写入路径
  说过会留下的东西比较。这个边界现在是一个重放要接受评判的东西，每次启动一次，每次启动都如此。
- **“停止接受、刷盘、记 `draining`”是假的。** `bin/lakeletd.rs` 和 `docs/crash-points.md` 的第 6 点
  都描述了一条会刷盘的停止路径，而这个项目里没有任何地方在 append 之外调用过 `sync`。这一步让那句话
  变成真的，而不是去改它：accept 循环返回，无论策略是什么存储都刷一次盘，守护进程打印让这个主张可
  核对的两个数字（`written`、`durable`——一次干净的停止让它们相等）。崩溃点清单的第 6 点也随之更新，
  因为一份仍然写着“一次干净的停止不会自己刷盘”的文档，会变成仓库里唯一一份错的文档。
- **一次重启对自己花了什么只字不提。** 恢复发生在存储被打开的时候，而运维对一次崩溃最便宜的观察，就是
  那一行说明打开时不得不丢掉什么的话。守护进程在启动时记
  `store recovered records=… bytes=… discarded=…`：每次启动一行，字段是收集器读得懂的，没有散文，
  形状就是 `obs/structured-logs@design` 定下的那种（`bin/lakeletd.rs` 和连接计数器本来就是那样读
  的）。存储把这个事实暴露出来（`Spool::recovered`）；守护进程才是决定把它说出口的那一层——引擎没有
  日志格式也没有日志级别，给它一个，就跨过了 `lakelet/4.1-ingest-protocol` 画的边界。

这里故意**没有**的东西，好让读者知道下一步从哪儿开始：

- **一次 append 一条记录，一个存储一个文件。** 批量化是 `lakelet/4.5-batch-writes`，它是逐记录刷盘
  负担不起、而间隔使之可能的东西；
- **一个日志，不是很多个。** 段、合并和保留期是 `4.7` 到 `4.9`；当这个存储长出第二个文件，“恢复从
  哪个文件开始”就成了这一步留下的问题；
- **不修复。** 恢复读设备上有什么、把尾巴切掉。它从不重写一条记录，从不编造一条，也从不去猜一个
  校验封没过的长度字段。

## 任务

这一步由四个性质组成。别的都是包装，而包装值得单独一段，因为课程在这里停下，你从这里开始。

- **一条记录自己声明自己。** `segment` 拥有这些字节：一个头部，说明这是哪个日志（四个字节的 magic
  和一个版本），然后是 `[length][payload][seal]` 的记录，每条有自己的长度和自己的校验和。**校验封
  覆盖长度，也覆盖载荷**，理由在 `src/engine/wal/checksum.rs` 里：这个读者靠它前面的字节找出一条
  记录在哪儿*结束*，而这份文件可能被一次崩溃从记录中间切开，所以长度也是必须被证明的东西之一。
  只盖住载荷的校验封，会让一个被弄坏的长度字段把一条记录的结尾挪到一个校验封仍然盖得住的地方——
  恢复会把别人的一段字节当成一条记录交回来。（`crate::protocol::frame` 只给载荷加校验封，而且它是
  对的：流的读者在需要载荷之前先拿到长度，而不是帧的字节会结束连接。）而一个**不是**这个日志的文件，
  是一个类型化的 `Error::Protocol`，绝不是一个悄悄没有记录的存储：没有头部，`hi!` 和一个第一次
  写入被截在两字节之后的日志是同一串字节，而恢复只能猜它看到的是哪一个。
- **重放在第一件它证明不了的事上停下。** 给一个存储目录，`replay::recover` 回答那些校验封验过的
  记录、那是日志的多少字节、它扔掉了多少字节，以及它*为什么*停下（`Stop`：`End`、`Torn`、
  `Corrupt`）。它从不跳过一条坏记录去找后面一条好的，从不返回一条它没验过的记录，也从不 panic。
  把这件事的论证写在 `src/engine/wal/replay.rs` 里，紧挨着代码：一个日志按构造就是一个前缀，所以
  “坏记录之后的那条记录”是由坏记录的长度描述出来的一个偏移——一个从刚刚被证明不可信的字节里得出的
  结论；一个缺口比一段短日志更糟，因为一个返回记录 1–10、丢掉 11 再返回 12 的存储，已经告诉了
  每一个读者这个序列是连续的；而撕裂之后跟着的东西不是数据，是一条记录的中段。
- **打开一个存储就是恢复它。** `Spool::with_policy` 重放日志，切掉没有任何 append 写完的字节，把
  计数器从恢复到的那个结尾开始，于是下一次 append 从*那里*接着写——绝不盖过它保留下来的记录，也
  绝不落在没人读得了的尾巴后面。`Spool::recovered` 交回这次恢复找到的东西。一个日志被切过的存储
  仍然是一个存储：拒绝启动会同时丢掉数据和这个服务，而丢弃计数，是运维得知前一件事的方式。
- **这个边界经得住一次机器死亡。** `durable_offset` 是存储承诺过的东西，所以把文件截断到它（这是
  `tests/sim_wal.rs` 和规格都用的模型）必须恰好留下已经刷下去的那个前缀——不多一个字节，也不包含
  任何从未刷下去的字节。

第二个性质里穷尽的那一半，是这个里程碑的头号验收项，而它是一个普通规格用例，不是一个 slow 用例：
一份写好的日志的**每一个**截断点，从零字节到整个文件，都恢复成记录的一个前缀，每条都完好，没有错误
也没有 panic。二十条记录也就几千次便宜的调用——这个用例用写者自己的 `segment::encode`/`introduce`
建日志，所以它知道每一个偏移，并在消息里说明这正是它不是一个 slow 测试的原因。镜像的那一个是再往下
的一个用例：一个*被翻转*的字节是损坏而不是截断，校验封抓住它，就在那里结束重放，而不是把那些字节当
成一条记录交回来。同一个主张再往上一层又说了一遍，那里是一个存储而不是一趟游走：
`every_cut_point_of_a_store_opens_to_the_prefix_it_can_prove` 把一个存储的文件在每一个偏移处切开、
打开它，然后问记录、恢复到的结尾、丢弃的字节、打开之后文件的长度，以及存储自己的读者——因为“打开
一个存储就是恢复它”只有在最小的那个撕裂尾部上也成立时才算真：在最后一条完整记录之后一个字节处。

**课程给你什么，什么是你的。** 脚手架声明形状，因为读它的不止这一步：

- `src/engine/wal/segment.rs`——布局（头部、`[length][payload][seal]`）作为文档和常量（`MAGIC`、
  `VERSION`、`HEADER`、`LENGTH`、`OVERHEAD`），外加 `encode`、`introduce`、`scan` 和
  `Stop::name` 的签名；
- `src/engine/wal/checksum.rs`——`seal`、`verifies` 和 `LEN`；
- `src/engine/wal/replay.rs`——`Recovered`（及其访问器）、`recover`、`truncate`；
- `src/engine/spool/recover.rs`——`Spool::recovered`，这一步给写入路径加的唯一一个签名（这个文件存在
  的理由和 `spool/durable.rs` 一样：一个学习者要*原地*重写的桩，没法靠一次插入交付，
  `docs/authoring.md` §5 规则 6）；
- `tests/sim_wal.rs`——崩溃场景装置，它是课程的文件（像 `4.2` 的 `tests/fuzz_protocol.rs`）：
  `slow:sim@3` 每个种子跑它一次，并按打印顺序比较 `lakelet-sim` 的行。它用四种方式死——进程死
  （什么都不丢）、机器死在它的刷盘边界上、机器死在一次进行中的写入里面、以及一个把整次写入写下去却
  改了一个字节的设备——而正是第四种，让*这道*闸门、而不只是规格，能注意到一次跳过了它证明不了的那条
  记录的重放。

那些文件里的每一个 `todo!()` 都是你的，接线也是：`append` 写 `segment` 的字节（一个还不存在的日志
由它的第一条记录声明），`records` 把它们读回来，`with_policy` 做上面的恢复。*格式*没有一点留给猜，
因为规格的偏移依赖它；*行为*的一切——停下意味着什么、这个边界值多少、调用方能得出什么结论——都是
这一步的活。

## 完成标准

- `cargo test -p lakelet --test spec_wal_recovery`（在 `app/lakelet` 里）——十四个规格用例通过，
  包括扫过一份二十条记录的日志的每一个切点。
- `kiln run lakelet/4.4-wal-recovery` — 同样的用例，跑课程那一份。
- `kiln check lakelet/4.4-wal-recovery --slow` — 每个 must 闸门都是绿的，包括 `slow:sim@3`
  （三个种子，至少两份不同的记录，而种子 `1` 逐字节重放）、`slow:mutants@80` 和
  `slow:?coverage@80`。
- `KILN_SIM_SEED=1 cargo test -p lakelet --test sim_wal -- --nocapture` 跑两次——两次是同一份
  记录；`KILN_SIM_SEED=7 …`——是另一份。闸门报告的摘要是证据。
- `kiln run lakelet/4.1-ingest-protocol`、`4.2-parser-fuzz` 和 `4.3-write-path-adr` — 仍然绿。
  `Spool` 的公开 API 是冻结的，它的记录格式不是：前面三个规格通过 `Spool::records()` 把记录读回来，
  从不看那些字节，这正是这一步能改掉它们的原因。
- `docs/crash-points.md` 的第 6 点说的，是停止路径现在的行为，而 `docs/adr/0001-write-path.md`
  仍然点名这个构建交付的策略——ADR 是 `4.3` 的决定，这一步不动它的数字。

## 陷阱

1. **只盖住载荷的校验封。** 它看着对，也能过每一个翻转载荷字节的用例。然后长度字段里一个被翻转的
   字节挪动了记录结束的位置，那个长度指向的字节被拿去和一个从没盖过它们的校验封比较，而——四十亿次
   里有一次——一条从没被写过的记录被交回来。抓住它的用例故意翻转长度字段，它会以
   `the record that changed is not handed back` 失败。
2. **跳过失败的那条记录再重新同步。** “下一条记录从我刚读到的长度之后四个字节开始”，是一个从刚刚
   失败的字节里得出的结论；用例 `a_record_the_replay_cannot_prove_is_not_skipped_over` 的答案是
   `[record 0]`，不是 `[record 0, record 2, record 3, record 4]`。
3. **恢复却不切。** `recover` 读，`truncate` 切，而一个只读的存储把被拒绝的字节留在文件里：下一次
   append 落在它们后面，之后每一次重放都永远停在那里，于是这个存储接受了一些再也没有读者看得见的
   记录。`tests/sim_wal.rs` 在它的 `kind=torn` 重启上让这一条失败（`bytes + discarded != kept`），
   而 `torn` 这种死法存在，就是为了产出这个失败。
4. **挪了 `len`，或者没挪 `durable_offset`。** 计数器从恢复到的结尾开始，不是从文件的大小开始：一个
   把它拒绝掉的字节也算进去的存储，报出一个没人读得回来的长度；而一个 `durable_offset` 落后于恢复
   到的结尾的存储，等于告诉下一次崩溃它可以拿走已经不在的那些字节。
5. **一个回答前缀而不是拒绝的 `records()`。** `Spool::records` 是*严格*的读者——打开一个存储的调用
   方拿到恢复好的前缀，但一个把在记录中间断掉的文件交给它的调用方拿到 `Error::Protocol`，不是一张
   更短的清单。这两个读者故意不是同一个，钉住这件事的用例是
   `a_reader_that_was_not_opened_since_the_cut_says_so_instead_of_answering_a_prefix`。
6. **一份带着挂钟时间的记录。** `format!("{:?}", Instant::now())` 把机器真实的单调时钟基准写进记录，
   于是同一个种子产出两个不同的摘要，`slow:sim@3` 报告
   `the same seed produced two different transcripts`。打印 `Instant::now() - started`，一个*模拟的*
   时长——这个缺陷在 `docs/handoff-m3-log.md` 段 6 里量过，那里有一个种子正是因为这一点产出了两份
   记录。
7. **一份什么也没观察到的记录，或者一份把行排了序的记录。** 闸门按行被打印的顺序比较，所以给它们排序
   就是把调度扔掉，而只打印一份汇总会让每个种子看起来都一样：
   `every seed produced the same transcript`。种子必须决定事件发生的顺序。
8. **装置里的 `tokio::net::*`。** 真正的套接字类型需要 `enable_tokio_io()`，从那以后地址就变真了：
   量到的回答是，一个模拟地址给 `AddrNotAvailable`，一个两次运行共用的端口给 `AddrInUse`。装置绑的
   是 `turmoil::net::TcpListener`，按主机名连接，而模拟 DNS 解析的正是主机名。
9. **一次干净的停止，记了刷盘却没刷。** 那一行的两个数字来自存储（`written` 在 `sync` 之前，
   `durable_offset` 在它之后），所以一次打印 `written == durable` 却没有等过设备的停止，是*更难查*
   的那个谎：检查会读这一对数字，于是这一页和崩溃点清单的第 6 点会一起描述一个没人关上的窗口。
10. **一个对恢复了什么只字不提的守护进程。** 那一行不是装饰：一次丢掉了 4 KiB 却不说一声的重启，会
    让运维在没有解释的情况下比对查询结果；而一次干净的停止上 `discarded=0`，是停止路径有效的最便宜
    的证明。
11. **五个文件里任何一个留下 `todo!()`。** `no-todo` 跑遍每一个 target，包括规格永远不调用的那些。
12. **把一份红的规格读成坏掉的仓库。** 第一次 `cargo test -p lakelet --test spec_wal_recovery`
    十四个用例全在 `todo!()` 处失败——在 `segment`、`checksum`、`replay` 和 `spool/recover.rs` 里。
    那是这一步的起跑线，不是坏掉的仓库；每一个桩都消失之后*仍然*红的那个用例，才是有话要说的那个。
13. **一个只是故事而不是机制的模型。** `tests/sim_wal.rs` 在文件里写明每种死法模拟的是什么、怎么
    做的——丢掉一个 `Spool` 代表进程死，在 `durable_offset` 处 `set_len` 代表机器死，在一条记录
    *内部*切一刀代表一次被打断的写入，在进行中的写入里改一个字节代表一个写下了别的东西的设备。一个
    只说“机器死了”却不说它对文件做了什么的情景只是一段话，而下一个人分不清一次通过的运行和一次其实
    什么都没杀过的运行。

## 延伸阅读

- 这一步的格式是这些小一号的版本：SQLite 的 WAL（一帧是一个头部、一个页和两个校验和，一个*salt*
  让旧 WAL 的帧作废）、LevelDB 的 `doc/log_format.md`（每条记录一个 CRC，根本不要文件头——还有
  `db/log_reader.cc`，它在第一条坏记录处停下）以及 PostgreSQL 的 `xlogreader.c`（`ReadRecord`：
  一个带 magic 和版本的长头部，然后每页一次 `XLogReaderValidatePageHeader`）。同一个问题的三个
  答案，而每一个的恢复代码都是有趣的那一半。
- Kafka 的日志段格式——CRC 是按批而不是按记录算的，而一个段末尾被截断的批，是它的恢复预料之中的
  正常情况；还是同一条“尾部不是数据”的规则，换了一个单位。
- `crc32fast` 的文档，以及为什么是 CRC 而不是哈希：一个能写这个文件的对手也能写下校验和，所以对一份
  字节*草稿*的诚实，和对一个伪造者的诚实是两个不同的问题。一个需要后者的日志需要一个 MAC，而那个
  决定，属于一个已经有对手的步骤。
- `turmoil` 的 `Builder::rng_seed` 和 `enable_random_order`——这一步的装置建在其上的模拟器，以及让
  一份调度可复现的两个旋钮。`docs/handoff-m3-log.md` 段 6 是那个说明种子确实传到了记录里的测量。
- `std::fs::File::set_len` 和 `truncate(2)`：“把文件切到恢复到的结尾”是什么，以及一个做恢复的存储
  为什么必须在再次 append 之前做掉它。
- `lakelet/4.5-batch-writes` 是逐记录刷盘负担不起的东西；`lakelet/4.7-columnar-segments` 和
  `lakelet/4.8-compaction` 是一个日志变成许多文件、而恢复必须知道从哪一个开始的所在。
