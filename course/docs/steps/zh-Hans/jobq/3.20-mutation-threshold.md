# 变异测试：证明规格不是摆设

## 为什么

一次绿的套件说明你写的用例通过了。它对你没写的用例什么也没说，对你写下的那些用例在底下的规则改掉
之后会不会失败，也什么都没说。那是测试里昂贵的那一半，而它是看不见的：一个什么都不断言的套件，跟一个
断言一切的套件有同样的绿勾，而一个读 diff 的评审，只有在那一天真的要紧的时候，才看见前一种。

有一个办法可以问，而它是构建报告里唯一一件衡量*测试*、而不是衡量代码的事：在一个地方改掉规则——一个
比较、一个布尔值、一个常量——构建，然后跑套件。改过的规则如果让套件失败，那就是套件真的在看的一条
规则。套件耸肩放过的那一条，是一个没人写的用例，而改动就躺在树里，所有灯都是绿的。

从那里出来的数字，值多少就看它的分母值多少，而这一步讲分母，跟讲计数一样多：三个变异体的占比，不能
当四十个变异体的证据用；什么都没看的占比根本不是数字；而一个什么都没看的构建，绝不能被报告成一次
失败的构建。

## 回顾

- `test/property-based@apply`——`jobq/3.19-property-invariants`：那台能回答*不*的机器。这一步是那个
  答案之后发生的事：一次变异运行，就是那场游走对准有人故意改过的规则，而分数就是它带回来的那些的
  数量。
- `test/integration-layering@apply`——`mailer/1.19-test-layering`：套件是由什么构成的。**这一步不
  重讲它。** 新的是判决——那个套件里哪些部分会察觉一条改过的规则，以及对于那些不会察觉的该怎么办。

## 变化

到来的是两样东西，而它们是同一个决定的两半：**一个构建被拿来对照的算术**，以及**产出它输入的那次
运行**。

- **规则是一个阈值加一个下限。** 光一个阈值，会被一次把三个变异体判得很好的运行满足，所以策略带着
  两个数字，而判决有三个答案而不是两个：`passed`、`failed`，以及——对于低于下限的运行——`unproven`。
  第三个才是这一步真正讲的决定。"套件不够好"和"证据不足以说"把维护者送去不同的地方，而一个布尔闸门
  必须把其中一个折进另一个，一类缺陷就是这样变成一个下午的错误工作。
- **分数是被判过的那些的占比。** 一个改动位置编不过的变异体，对套件什么都没说，所以它在分数之外，而
  不是作为一个幸存者在分数之内；而一次空的运行根本没有百分比（`None`，不是 `0`），因为一个 `0%`
  会像任何别的数字一样去跟阈值比较，把"什么都没看"报成"最坏的可能"。

`caught` 是两步相遇的地方：`jobq/3.19-property-invariants` 的不变式就是套件，一张改过的模型表就是
变异体，而当一个不变式带着反例回来时，一个变异体就被杀死了。整次运行一个种子，因为两次运行必须可比
——一个分数看天气的套件，是一个谁也没法拿阈值对着它比的套件。

## 作业

脚手架加了一个模块，而**还没有任何东西声明它**：照 `jobq/3.19-property-invariants` 接 `walk` 的方式
去接线 `src/engine/mod.rs`，是你的第一个决定，而在它做成之前规格不编译。五块，而每一块都是一个关于
一个数字*意味着什么*的决定。

### `Score`——多少个，占多少

分母是 `killed + survived`，别的什么都没有：它是被*判过*的那些。一个没编过、或者没跑完的变异体，两个
计数里都不算，因为把它算成幸存者，会让一个项目靠把自己的代码弄成编不过，来提高分数。`percent` 对一次
空运行答 `None`——`checked_div` 就是那个决定的全部，写在它发生的地方——而它截断，因为阈值 80 是一个
关于整数百分比的决定，而四舍五入会让一次差一个变异体才到的运行，读起来像通过。

### `MutationPolicy`——一个阈值、一个下限，三种答案

`judge` 用 `>=` 比较，因为 80% *满足*阈值 80；它在低于下限时答 `Unproven`，而不管配置怎么说，它都
把下限抬到至少一个被判过的变异体：一次什么都没判的运行，什么都没证明，而那不是设置项。`is_satisfiable`
是评审的那一半——"没人能满足这个"恰好有两种形状，阈值高于 100，以及下限为零——而两个方法是故意分开
的：算术是构建做的事，评审是人做的事。

### `Survivor` 与 `Report`——一个能让人行动的分数

一个幸存者带着文件、行、列，以及活下来的那次改写——跟 `kiln` 自己的闸门打印的四样东西一样，于是工具
的报告和这个项目的报告读起来一样。列是其中一部分：一行里可能有两个同一个算子，而只点名了行的报告，
会把同一个地方点名两次。`Report::of` 拿幸存者，而不是从计数推导它们：运行知道哪些变异体活了下来，
而一个从数字重建它们的报告，会藏起两者不一致的情况。

### `caught`——这轮运行本身

每个变异体、每条不变式一场游走，用的是 `jobq/3.19-property-invariants` 的
`walk`/`Model`/`Invariant` 那套机制，而当一条不变式带着反例回来时，一个变异体就被杀死了。这就是变异
测试的全部，而它是三行：一个真正的工具在上面加的一切都是记账——改动往哪儿应用、它编不编得过、要等
多久——而记账正是这个工具值得拥有的原因。

### 有意不改的东西

那场游走和它的模型（`jobq/3.19`）、引擎的那张表，以及每一个更早的套件。如果下面某行 `DONE WHEN`
失败了，那就是这段算术和喂给它的那些游走不一致——而*那个*，正是这一步的形状要抓的缺陷。

## 完成标准

- `kiln run jobq/3.20-mutation-threshold` — 九个用例通过：分数和它的空运行、没人能满足的策略、80%
  遇上 80 的那个边界、那三个词、幸存者所在的地方、一行报告的三种形状、一张埋下缺陷的表，用上一步的
  性质打分，以及那个不会失败的套件得了零分。
- `kiln check jobq/3.20-mutation-threshold` — 每个 must 闸门都是绿的，包括 `clippy@4`。
- `kiln selftest jobq/3.20-mutation-threshold --track jobq`（或者 `kiln verify jobq --slow`）——
  慢路径跑 `slow:mutants@80`，它变异**这一步自己的模块**，并拿这些用例对着它取到的每一个变异体跑：报告
  里的那一行就是分数，而一个幸存者点名那个地方和缺失的断言。一个规则被改掉却没有任何用例察觉的模块，
  就是那个闸门存在要报告的缺陷。

## 陷阱

1. **该用 `>=` 的地方用了 `>`。** 它就是阈值 80 和阈值 81 之间的全部差别，而它通过每一个不恰好落在
   线上的用例：一次恰好杀死它所判的 80% 的运行，被报告成失败，而有人伸手去拿的修法，是调低阈值。
2. **一次什么都没判的运行，分数是 `0%`。** 这个数字于是成了一个仪表盘能画出来的数字，而它把一个从来
   没看过的构建说成"最坏的可能"。`percent` 答 `None`，而报告说明这是两个问题里的哪一个。
3. **两个答案而不是三个。** 把"证据不足"折进"失败"，会让维护者去为一个从没被判过的变异体写用例——
   那跟报告知道的东西正好相反。
4. **没有下限的阈值。** 三个变异体全被杀掉，就是 100%，而接受它的闸门，是一个项目靠少采样就能通过的
   闸门。下限正是让这个百分比成为证据、而不是成为比值的东西。
5. **一个没有地方的幸存者。** "6 个里 1 个存活"是一句谁也没法据以行动的话。报告是变异测试里真会被
   用到的那一半，而它必须点名文件、行、列，以及活下来的那次改写。
6. **在规格里变异代码。** 写一个会改文件、重建 crate、再跑自己的用例，是在测试里装一台编译器：它慢、
   它不稳定，而它做的正是闸门（`kiln check … --slow`）和真实项目里的 `cargo-mutants` 已经在做的
   记账。
7. **一次永远跑不完的变异运行。** 闸门对每个变异体把这一步的用例跑一遍，而一个等条件却没有截止时间的
   用例，会把一个变异体变成一次超时——对每个变异体、在每台机器上、对每个人。有界循环和带截止时间的
   等条件，是 `jobq/3.19` 的规则；它们也是让这一步自己的闸门负担得起的东西。

## 延伸阅读

- [`cargo-mutants`](https://mutants.rs/) — 这一步的生产工具：`kiln doctor` 会报告它有没有安装，而它
  没有的东西，正是这个模块故意留下的记账（构建每个变异体、决定什么算数，以及把一个幸存者写进评审能
  打开的文件）。
- [Mutation testing (survey)](https://doi.org/10.1109/TSE.2010.62) — Jia 和 Harman，讲有哪些变异
  算子、什么是等价变异体，以及这个领域为什么最后落在"一个占比，加一个下限"，而不是落在单独一个数字
  上。
- [`pitest`](https://pitest.org/) — 同一个想法，换了一张算子表，也是一个好例子：这个工具的报告是围着
  幸存者设计的，而不是围着分数。
- `course/tracks/jobq/spec/3.20/mutation.rs` — 九个用例，包括两个拿一张埋下的缺陷表给套件打分的。
- `jobq/3.19-property-invariants` — 这一步打分的那个游走，以及为什么一个变异体可以是一个*模型*，而
  不是一次文本编辑：在这个 crate 里，规则是一个值。
- `course/tracks/jobq/spec/3.14/state_machine.rs` — 下面那些埋下的缺陷所改动的表，按例子来检查；一次
  变异运行，就是拿那张表去问没人写过的用例。
