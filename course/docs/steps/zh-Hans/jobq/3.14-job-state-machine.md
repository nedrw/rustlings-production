# 把作业状态做成类型：不会写错的转移

## 为什么

关于一个作业一生中的每一条规则，都是一条得有人守着的规则。"只有正在跑的作业才能被完成"、"尝试预算花光的
作业就结束了"、"结束了的作业永远不会再发出去"——今天，每一条都住在对它的那条路径里：持久后端里两条了结
语句，内存后端里两个 `if`，SQL 里一个 `case` 表达式。一条散在五个地方的规则，就是一条能在其中四个地方
被改掉的规则，而第五个地方，是凌晨三点在跑的那个。

还有第二笔代价，而它是在评审里现形的那个。一条住在 `if` 里的规则，什么也*问*不了：没有一个函数能交给
性质测试，没有地方能说"四个状态、五个事件，给我看一对会炸的"，也没有一个地方，新来的工程师能从一头读到
另一头，看清一个作业的一生。问不了的东西就查不了，而一个队列的全部价值，就是"结束了的作业永不重跑"这个
承诺。

## 回顾

- `db/transaction-isolation@design`、`db/atomic-claim@design` — `jobq/3.6-transaction-isolation`
  和 `jobq/3.7-leases-and-recovery`：**今天那些转移就发生在这里。** 两个后端的了结路径，就是"为什么"
  里说的那五个地方；而认领，是开启一次尝试的那一个。这里什么也不改它们做什么；改的是规则住在哪里。
- `domain/parse-dont-validate@apply` — `mailer/1.10-domain-types`："做成一个类型"的另一半。那一步
  把值变成*拥有*一个合法邮箱地址的唯一途径，于是一个非法的地址不是你要处理的东西——它是你构造不出来的
  东西。**这一步不重讲它。** 这里新的是，值不是重点：值*之间的移动*才是，而一个转移函数，是跟构造函数
  不同的形状。
- `delivery/dlq@apply` — `relay/2.10-dlq`：两个终结状态是从哪来的。一个尝试次数用完的作业，不是丢了，
  而是*结束了*：队列不再把它发出去，由人来决定接下来怎么办。`succeeded` 和 `failed` 就是这个决定写成
  了状态，而这一步，是把它们写成*吸收*态的地方。
- `sched/delayed-timers@apply` — `jobq/3.11-delayed-timers`：定时器走到一个 `queued` 的作业，让它
  到期。它从不在状态之间移动作业，所以下面的模型里没有"时钟走过了"这个事件——到期是排着队的行的一个
  属性，不是一个状态。

## 变化

**规则变成一个全函数，而列变成它的编码。** 由此引出两件事，两件都查得了，不用争：

- **`transition(state, event) -> Result<JobState, Illegal>` 是全的。** 每个状态对每个事件都有答案，
  一个不被允许的移动，答案是*点名的拒绝*——它原来在哪个状态、到达的是哪个事件、是三种理由里的哪一种
  ——而函数里没有任何东西会 panic。一个性质测试（`jobq/3.19-property-invariants`）能把整件事走一遍，
  因为整件事是一个值：状态和事件都是列表，而答案是一次调用。这就是模型和一段话之间的差别。
- **行里的 `state` 列是模型的编码，从来不是模型本身。** `as_str` 和 `parse` 是它的两个方向；一个这个
  构建不认识的名字，是*按存下来的那段文本*拒绝的，而不是被四舍五入成 `queued`；而 schema 在同一句话
  的下一层也得到它：`migrations/0006_job_states.sql` 用一个点名的 `check` 封住这一列，于是模型里没有
  的状态，存储写不进去，迁移写不进去，一个开着 `psql` 的人也写不进去。

**行为本身并不新。** 一个作业照旧走 `queued → running → succeeded`，一次还有预算的失败照旧回到队列，一次
租约跑完的认领，照旧带着计过数的尝试回来。前面两步的套件必须保持全绿，而它们就是模型没有改动引擎的
证据——它只是把规则挪了个地方。如果下面某条 `DONE WHEN` 失败，那就是模型和存储意见不一，而*那*才是这一步
专门设计来抓的 bug。

## 作业

脚手架加了一个模块和一个占位迁移。**还没有任何东西声明它们**：照
`jobq/3.13-queue-authz-attribution` 接 `authz`、`tenant` 和 `usage` 的方式去接 `src/engine/mod.rs`，
是你的第一个决定，而在它做出来之前，规格编译不过——那就是这一步在告诉你它要什么。

### `src/engine/state.rs` —— 那张表

状态和事件二十四种配对里，有六种是移动。把它们写成一个函数：

| from | event | to |
| --- | --- | --- |
| `queued` | `claim` | `running` |
| `running` | `complete` | `succeeded` |
| `running` | `fail`，还有预算 | `queued` —— 这个作业还欠一次尝试 |
| `running` | `fail`，预算已用尽 | `failed` |
| `running` | `claim lapse`，还有预算 | `queued` |
| `running` | `claim lapse`，预算已用尽 | `failed` |

其余的全都拒绝，而拒绝会说清三种情况里是哪一种：作业已经结束、这个事件要求它在运行、或者这个事件要求它在
等着。那张表里有三个决定，比它们产出的代码更值钱：

- **`retryable` 是预算的回答，不是状态机的回答。** 状态机管的是一个作业*在哪*；它试过几次是那一行的
  事，而数过尝试次数的那个存储，才是说还能不能再试的那个。这就是 `Event` 带的是一个旗标而不是一个计数
  ——也是带旗标的两个事件目的地相同的原因：一次失败和一次失效的认领是两个*故事*（不同的 `last_error`、
  不同的轨迹行、不同的计数器），只有一个状态答案；一个把它们并成一个的模型，会藏起发生的是哪一个。
- **`succeeded` 和 `failed` 是吸收态。** 对它们的每个事件都是同一种拒绝，而 `JobState::is_terminal`
  ——已经在 `domain.rs` 里了——必须跟模型一致，而不是关于模型的第二意见。
- **编码能往返。** `as_str` 在 `domain.rs` 里，跟其余词汇在一起；`parse` 在这里，因为一个模型不认识的
  名字是一次*拒绝*，而这个模块就是拒绝住的地方。这四个名字是一个接口：列存的是它们，`jobqc`
  （`jobq/3.15-cli-contract`）打印的是它们，面板按它们分组。

你写 `transition`、`JobState::parse` 和 `Event::as_str`；模块里其余的东西，都是规格和引擎其余部分已经
在说的词汇。

### `src/engine/store/` —— 模型是存储的答案，不是它的第二意见

两个后端为它们*写*的每一个状态去问模型：

- 内存存储原来用 `if` 决定的地方，现在调用 `transition`：一次认领、一次完成、一次失败，以及
  `release`/`reclaim_expired` 交回来的那一行；
- 持久存储**从模型里绑定目的地名字**（`destination(from, event)`），SQL 里只留*谓词*——
  `state = 'queued'`、`lease_owner = $2`，以及只有那一行知道答案的 `attempts < max_attempts`。
  一个什么都不匹配的谓词，是一条没有答案的查询；一个在 SQL 里发明出来的目的地，是一行处在一个没人叫得
  出名字的状态里；
- `decode_state` 变成 `JobState::parse`，于是读这一列和写这一列，来自同样的四个名字。

*存储*给出的拒绝原样不动：模型拒绝的一次了结是 `Error::Invalid`，那是
`jobq/3.7-leases-and-recovery` 钉住的类别，也是 worker 据以读出自己租约的那个类别。模型自己的拒绝是
`Illegal`，而 `From<Illegal> for Error` 把它映射进那个类别——一次拒绝，一套词汇，没有新的退出码。

### `migrations/0006_job_states.sql`

占位里点名了它必须装下的东西：`jobs.state` 上一个点名的 `check`，写的是这个枚举写的那四个名字。它的决定
里有两个值占位给的那几段话——约束是*点名的*（一个说 `jobs_state_known` 的拒绝，是运维查得到的一个），
而且它*校验*（一个用 `not valid` 加上的约束，会把它本来要找的那些行，原封不动留在表里）。

### 有些东西故意不变

`claim` 的签名和它发放作业的顺序、了结的拒绝和它们所属的类别、`jobq/3.1`–`3.13` 认证过的内存存储
语义，还有端口：没有加方法，没有挪动 `Error` 的变体，而原来写在五个地方的目的地，现在写在一个地方。

## 完成标准

- `kiln run jobq/3.14-job-state-machine` — 五个用例通过：那张表逐对检查、终结态的吸收、编码往返、存储
  把模型走一遍，以及那个自己起一个容器、好让 `psql` 被拒绝的用例。
- 在 `app/jobq` 里跑 `KILN_BACKEND=postgres kiln run jobq/3.14-job-state-machine` — 同样的用例跑在
  持久后端上，那里的目的地是从模型绑定来的，而 schema 执行那套字母表。
- `kiln check jobq/3.14-job-state-machine` — 每个 must 闸门都是绿的。
- `kiln check jobq/3.13-queue-authz-attribution` — 之前那些套件仍然通过：这一步挪的是规则住的地方，
  不是规则本身。

## 陷阱

1. **第二张表。** `transition` 写好了，然后了结路径还是用 `if attempts < max_attempts` 自己决定——
   今天两者一致，等有人改了其中一个，它们就分道扬镳。存储那个用例把*每一个*事件都从端口走一遍，拿行跟
   模型的答案对照，所以这是被抓到的，不是靠评审看出来的。
2. **一个在没人想过的配对上 panic 的全函数。** 在 `queued` + `complete` 那一支里写 `unreachable!()`，
   套件里其他每个测试都能过：*用户*看到的是 `succeeded`，运维看到的是拒绝。规格会把二十四对全调一遍，
   其中任何一对 panic，这一步就是红的。
3. **只写"不允许"的拒绝。** 它是最友善的消息，也是凌晨三点最没用的那条：运维手里已经有作业 id 了，需要
   知道的是这个作业结束了，还是别人正在跑它。规格拿状态自己的名字和事件的名字去断言那条消息，因为那
   正是调用方手里的两个字符串。
4. **把一个不认识的状态往下取整。** 一个带 `_ => Ok(JobState::Queued)` 分支的 `parse`，会把那唯一一行
   在说"这次部署和这个二进制意见不一"的记录，变成一个会再跑一次的作业。拒绝里带着存下来的那段文本，
   因为那段文本是关于哪个版本写下它的唯一线索。
5. **约束不在——或者没有名字。** 没有这次迁移，持久后端会接受 `dead`，而引擎之后会在某次读的时候把它
   当成一次存储失败碰上来；约束没有名字，运维拿到的是 PostgreSQL 自动生成的名字，那个名字在这个仓库里
   什么也指不到。两件事都是通过 `psql` 断言的，那是让*数据库*而不是某个调用方去拒绝的唯一办法。
6. **绑定了目的地，忘了谓词。** 持久存储的语句现在把状态名当参数收，而一个错了一位绑定不是编译错误：
   认领的 `$9`、了结的 `$4`–`$6`、回收的 `$6`/`$7`，各自回答一个不同的问题。在这一步*以及*
   `jobq/3.5`–`3.13` 上都跑 `KILN_BACKEND=postgres`，才是让它们老实的东西。
7. **把模型当作文档。** 一个没人调用的 `transition`，能过规格的头三个用例，第四个一个都过不了：这一步
   的要点就是两个后端都去问它，这才让 schema 的约束和模型成为同一个决定，而不是两个。

  `ADD CONSTRAINT`，以及 `jobq/3.23-online-schema` 之后会需要的 `VALIDATE CONSTRAINT`。
- `course/tracks/jobq/spec/3.14/state_machine.rs` — 那张表作为测试：二十四对的预期答案、那些拒绝，
  以及穿过两个存储的那趟走查。
- `relay/2.10-dlq` — 那一步让"尝试次数用完"变成一个终结状态，以及照着它做事的那些工具
  （`jobq/3.16-dlq-tooling` 是同一个想法，用在这个队列上）。
- `mailer/1.10-domain-types` — 对单个值"解析，不要校验"；也是这一步讲的是移动、不是状态本身的原因。
