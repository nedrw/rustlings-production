# 把公开面写下来，让破坏变成编译错误

## 回顾

- `api/library-design@aware` — `jobq/3.1-engine-boundary`：箭头只朝一个方向，引擎在进程里没有服务器的
  情况下也能跑一个队列，端口的方法返回 `BoxFuture`，因为 trait 里的 `async fn` 不是 dyn 兼容的。那一步
  划出了边界；它没说调用方可以依赖哪些名字。今天 `jobq::engine` 下面的一切都是公开的——连模块布局也
  算在内，于是 `jobq::engine::store::memory::MemoryStore` 和 `Engine` 一样，都是一份承诺。
- `err/typed-errors@apply` — `mailer/1.5-errors`：失败类型是 API 的一部分，变体是调用方拿去匹配的
  东西，原因可以通过 `source()` 一路够到，外壳拿到一个退出码。有一个服务的调用方就是它自己的测试和它
  自己的二进制。这里调用方是别人的程序，而这个差别开始要付代价的地方，就是这一步。

## 变化

新的东西不是一个形状，而是一份**背后有版本号的承诺**。`jobq/3.1` 让引擎在没有守护进程的情况下也能
编译；这一步让引擎的公开面变成一个你**看得见地**破坏的东西。这是两件不同的事，而下面四个动作就是全部：

- **路径不再是 API。** 模块布局是实现细节：`jobq::engine::domain::…` 存在，是因为引擎自己的代码那样
  更整齐，不是因为调用方应该能点出这个名字。把 `scheduler` 拆成两个，
  `jobq::engine::scheduler::Engine` 的每个调用方都得为一次重构重新构建。调用方可以点名的，是
  `jobq::engine` 重新导出的那些东西；这一步之后，那张清单就是整个公开面——挪一个类型从此是 crate
  自己的事，不是调用方的事。
- **增长是声明出来的。** `JobState`、`Error`、`Job` 和 `SubmitRequest` 都会长大：`jobq/3.14` 加状态，
  `jobq/3.3` 给错误枚举一条来源链，`jobq/3.7` 给作业一个租约。`#[non_exhaustive]` 是 crate 在调用方
  的编译器会读的地方说“这个还会长”的方式：在 crate 外面，对这个类型的 `match` 需要一个通配分支，于是
  一个加变体的发布，不会成为破坏每个使用者构建的那个发布。
- **把端口封住。** 存储端口的文档承诺：每个实现的行为都符合 `jobq/3.5-store-port-conformance` 那套一致性
  用例所断言的样子。这个承诺只有跑那套用例的 crate 才守得住——于是这个 trait 从一个私有模块拿到一个超
  trait，而 `impl Store for MyStore` 在别人的程序里不再编译。这是这一步里唯一一处有意*收窄* API 的
  改动，收窄是为了守住一个更宽的版本守不住的承诺。
- **证据不是你的。** 你为自己公开面写的测试，是你自己可以削弱的测试。课程自带一份公开面的见证文件
  （`course/tracks/jobq/api/3.2-public-api-baseline.rs`，编译成 `tests/semver_baseline.rs`）：每个公开
  函数一个函数指针，每个公开变体一个 `match` 分支，每个结构体模式一个 `..`。它能在你的 crate 上编过，
  这一步才算完——而因为它是课程内容，“公开面还成立”就是一句关于这个 crate 的话，而不是关于那个测试
  的话。

这一步真正教的那个习惯，到了发布步 `jobq/3.25-release-artifacts` 才真正花出去：破坏性改动是允许的，
但它得*付出代价*——提升版本号、加一行 changelog，而不是让升级的人吃一惊。

## 作业

- 把引擎的模块收成内部模块：`pub(crate) mod domain;`、`error`、`scheduler`、`store`，以及 `store`
  里面的 `pub(crate) mod memory`。`src/engine` 下不再有任何 `pub mod`。
- 在 `jobq::engine` 重新导出此前公开的每一个名字，让路径可以挪、名字不会消失：`Job`、`JobId`、
  `JobState`、`Queue`、`SubmitRequest`、`WorkerId`、`QUEUE_NAME_MAX`、`DEFAULT_MAX_ATTEMPTS`、
  `Error`、`Engine`、`MemoryStore`、`Store` 和 `BoxFuture`（端口的方法返回它，所以读了端口签名的调用
  方得能点出这个名字）。
- 把端口封住。一个私有模块（`src/engine` 下的 `mod sealed;`）装着 `pub trait Sealed {}`；`Store` 把
  `Sealed` 当超 trait，而这个 crate 认证的每个后端都实现它（`impl Sealed for MemoryStore {}`——编译器
  会坚持这一条，这正是用意）。
- 给 `JobState`、`Error`、`Job` 和 `SubmitRequest` 标上 `#[non_exhaustive]`。标在**类型**上，不是变体
  上，也不是字段上：守护进程自己构造 `Error::Config { detail }`，把 `#[non_exhaustive]` 标在那个变体
  上会挡住它。
- 在 crate 自己的代码里说这个公开面：`src/service/**` 和 `src/bin/jobqd.rs` 点
  `crate::engine::{Error, MemoryStore, Queue}`，而不是私有模块的路径；任何公开文档注释都不链接一个刚
  变成 `pub(crate)` 的模块——`cargo doc --no-deps` 会警告
  `public documentation for … links to private item …`，而一个库的文档，也是它承诺的一部分。
- 让课程的见证文件编过：`cargo test -p jobq --test semver_baseline`（这一步备好时，文件会作为
  `tests/semver_baseline.rs` 到位；`semver@baseline` 闸门就是这个命令）。

## 完成标准

- `kiln run jobq/3.2-public-api-baseline` — 规格的四条主张成立：公开面跑得动一个作业，引擎的模块不是
  公开路径，端口没法从外面实现，而那四个会长大的类型把这一点说了出来。
- `kiln check jobq/3.2-public-api-baseline` — 每个 must 闸门都是绿的，包括 `semver@baseline`。
- 在 `app/jobq` 里跑 `cargo test -p jobq` — 每套用例都通过，包括 `jobq/3.1` 的规格：挪动公开面的一
  步，不能破坏此前对它许下的承诺。

## 陷阱

1. **只重新导出了大部分名字。** 把 `domain` 变成 `pub(crate)`，却在 `pub use` 清单里忘了 `BoxFuture`、
   `QUEUE_NAME_MAX` 或 `DEFAULT_MAX_ATTEMPTS`：在 crate 里编得好好的，到见证文件里就以
   `error[E0432]: unresolved imports …` 失败，并点名消失的那些项。这一步讲的规则是：路径可以挪，名字
   不能消失。
2. **只标了一个枚举，漏了另一个。** 见证文件的通配分支是在 `#![deny(unreachable_patterns)]` 下编译
   的：`Error`（或 `JobState`）上少了 `#[non_exhaustive]`，`cargo test --test semver_baseline` 就会以
   `error: unreachable pattern` 失败，指向那个本该保护调用方的分支。
3. **写成 `pub mod sealed;`。** 封住它的是 `Sealed` 的*不可达*：一个谁都能点名的模块，就是一个谁都
   能在里面给 `Sealed` 写实现的模块，于是 `impl Store for TheirStore` 又编得过。规格按文件和行报出来
   ——“declares the sealed module as a public path”。封了 trait 却忘了
   `impl Sealed for MemoryStore {}`，失败得更早：`error[E0277]`——the trait bound
   `MemoryStore: Sealed` is not satisfied——就在编译器指出的那行 `impl Store for
   MemoryStore`。
4. **把 `#[non_exhaustive]` 标在 `Error::Config` 上而不是 `Error` 上。** 守护进程要构造那个变体，于是
   `src/bin/jobqd.rs` 以 `error[E0639]: cannot create
   non-exhaustive variant using struct expression` 编不过。这个属性属于那个类型：调用方必须为枚举
   长大做准备，而不是为变体的字段做准备。
5. **留下了模块文档里的链接。** `src/engine/mod.rs` 在 `[...]` 链接里点了 `domain`、`store` 和
   `scheduler`，这些链接只在模块公开时才解析得了。`cargo doc
   --no-deps` 于是回答“public documentation for `engine` links to private item `domain`”——每个
   链接一次——而读这个 crate 文档的调用方，顺着一堆哪里也去不了的链接走。这一步没有闸门会构建文档，
   所以这是清单上唯一一条得靠眼睛看出来的。

## 延伸阅读

- [`#[non_exhaustive]`](https://doc.rust-lang.org/reference/attributes/type_system.html#the-non_exhaustive-attribute)
  — 这个属性在每个位置（枚举、变体、结构体、字段）分别做什么，以及它有意不做什么。
- [The Cargo book: SemVer compatibility](https://doc.rust-lang.org/cargo/reference/semver.html) — 这一步
  是它的一份缩小版清单：哪些改动是破坏性的，哪些只是看起来像。
- [`rustc --explain E0603`](https://doc.rust-lang.org/error_codes/E0603.html) — 调用方所用的路径不再
  公开时拿到的错误，也就是要避免的东西，以及一次有意为之的破坏所接受的东西。
- [`rustdoc` lints](https://doc.rust-lang.org/rustdoc/lints.html) — 其中就有
  `private_intra_doc_links`，也就是上面那个陷阱。
- [`cargo-semver-checks`](https://github.com/obi1kenobi/cargo-semver-checks) — 这个检查在生产里长什么
  样；这门课程的 `semver@baseline` 闸门改用 `rustc` 编一份见证文件，于是一步从不依赖一个你未必装了的
  工具。
