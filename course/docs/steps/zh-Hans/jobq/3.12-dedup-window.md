# 去重：去多久，以及窗口的边上会发生什么

## 回顾

- `delivery/idempotency@apply` — `mailer/1.15-idempotent-delivery`：每个订阅者一条确认，靠一次写入
  保住，它自己 `returning` 回来的那一行就是事实，而那一行永不过期。这一步保留的那一半是：回答的是
  *存储*，而答案是第一个请求的答案。T1 从来不必决定的是这个答案什么时候停：订阅者是一个长久存在的身份，
  而生产者的重试是一个并不长久的请求。
- `db/unique-as-concurrency@design` — `jobq/3.6-transaction-isolation`：一条两个调用方能在同一瞬间
  同时违反的唯一性规则，该放在数据库里；`on conflict` 点名那个做裁决的仲裁者，输家会被告知，而不是让
  它自己去重读。这里仲裁者是一对——`(queue, key)`——而输家得到的答案是一个作业，不是一次拒绝。
- `time/clock-injection@apply` — `jobq/3.8-clock-injection`：这个引擎比较的每个时刻，都来自递给它的
  那只时钟。正是这一点，让"窗口已经过去了"变成一个几毫秒就跑完的用例，也是为什么拿来跟键表比较的两个
  时刻都是那只时钟的，而不是数据库的。

另外两个邻居也叫幂等，但都不是这一个，所以边界值得写下来。`api/idempotency-key@apply`
（`relay/2.2-idempotent-ingest`）回答的是*请求*，返回它已经存下的那一行，按租户分键，永不过期。
`delivery/idempotency@apply`（`mailer/1.15`）用同样的方式回答*订阅者*。这一步是"记得"有了尽头的地方，
而这个尽头是接口的一部分。

## 变化

**窗口就是这个决定，而它属于请求。** 一个不带时长的"去重"不算规格：它要么是一张谁都不许清空的表，要么
是一个调用方最多只能信一个进程内存那么久的承诺。所以由请求来说——`with_dedup_window` 紧挨着
`with_dedup_key`，两个都是加在 `SubmitRequest` 上的——引擎的答案以它为界。

由此有三个后果，每一条都是调用方能据以安排的一句话：

- **窗口之内，重复是被回答，而不是被拒绝。** `Engine::submit` 交回那个键已经产生的作业的标识，跟第一个
  请求拿到的是同一个，而重复请求的载荷一个字节都不写。一个拿回*第二个*标识的生产者，分不清自己的重试
  是不是又排了一份它正在重试的工作——而那正是整套机制存在要防的失败。
- **恰好在 `first + window`，这个键又是新的了**，早一个时刻都不行。窗口是半开的：在 `t` 取走的键，在
  `now < t + window` 期间都作答，到 `t + window` 就没了。这条线只写**一次**，在
  `Dedup::expiry`/`Dedup::live` 里，两个存储都从那里读——一个后端差一，就会在整整一个时刻上，要么把
  一次合法的重复去掉，要么把一次重复执行掉。
- **之后调用方能假设什么：什么都不能。** 两个带着同一个键、落在边界两侧的请求，是两个作业，这是对的，
  不是泄漏：窗口是生产者自己关于它的重试能活多久的声明，而它承诺的读法是"每个窗口一件工作"。一个活得比
  自己窗口还久的重试循环，要的就是一个新作业。

窗口也**不会被重复移动**。它从第一个请求起就盖上时间戳，之后待在那里，所以一个要求比第一次更长窗口的
重试——或者一个每秒重试一次、连着重试一小时的客户端——答它的仍然是先打开的那个窗口。一个调用方靠重试
就能往前推的窗口，就是一个调用方说了算的窗口。

**存储为什么留一行来执行它。** 窗口的边界必须在*写入发生的同一刻*、由那条负责写的语句决定，否则两个在
同一个键上赛跑的生产者都会读到"还没有键"，然后都去写。所以这一行就是机制：它带着这个键停止作答的那个
时刻，而取键的那条语句是

```sql
insert into dedup_keys (queue, key, job_id, expires_at) values (…)
on conflict (queue, key) do update
    set job_id = excluded.job_id, expires_at = excluded.expires_at
    where dedup_keys.expires_at <= $now
returning job_id
```

——对一个窗口已过的行是一次**重置**，对一个还活着的行什么也不做。一个对死键*拒绝*、而不是重置它的存储，
会让每个键永远只指向一个作业，那跟没有窗口是同一个承诺。而由于活着的那一半什么都不写，重复的答案就是读
键已经指向的那一行：第一个作业，它现在的样子。

**过期不是删除。** 一个窗口已过的键是死的，是因为它带着的那个时刻，而不是因为有什么东西把它扫走了，所以
清扫只是家务：一个永远不删过期行的存储，回答完全一样；而一次把*活*行删掉的清扫，会放一个重复过去。这就是
这一步机制两半之间的差别——语句是承诺，清扫是磁盘。

## 作业

脚手架加了 `src/engine/dedup.rs`（在你声明这个模块之前它不参与编译）和
`migrations/0004_dedup_keys.sql` 的一个占位。

### `src/engine/dedup.rs`

`Dedup` 是两个存储都去问的那个值，而它模块文档里的四个决定，就是要你做的四个决定：一个键可以长什么样
（`Dedup::new`，可能失败——读它的 `# Errors`）、`first + window` 的哪一边是哪一边（`expiry`、
`live`），以及窗口为零是什么意思（它不是特例：它是一个被取走的瞬间就已经死掉的键）。把那些 `todo!()`
填上。

### `src/engine/domain.rs`

`SubmitRequest` 多了一个键和一个窗口，以及一个 `pub(crate) dedup()`，把这一对变成存储要的
`Option<Dedup>`。三种情况，而第三种是规则、不是遗漏：没有键是 `Ok(None)`（没人指定窗口，就什么也记
不住），有键有窗口是 `Ok(Some(..))`，而**有键没窗口是 `Error::Invalid`**——窗口是问题的一部分，引擎
不会替生产者挑一个时长。

### `src/engine/store/`

- 端口：承诺住在 `Store::enqueue` 的文档里，所以"窗口之内，答案是那个键已经产生的作业"这句话，就写在
  那里，供两个后端遵守；
- 持久后端：整个决定一条语句，键表的那一半
  （`on conflict (queue, key) do update … where expires_at <= $now`）和作业行的那一半都在里面，于是
  一个活着的键**什么都不写**，而赛跑的生产者由数据库来裁决，而不是由早一瞬间发生的一次读来裁决。没有键
  的请求仍然用它原来那条语句；
- 内存后端：在同一条它本来就要拿的锁之下用同一条规则——活着的键在两次写之前作答，过期的那个被重置。这把
  锁就是这个存储的事务（`jobq/3.6-transaction-isolation`），所以这里没有一样东西能只生效一半。

### `migrations/0004_dedup_keys.sql`

这个文件归你。它的决定里有两个是占位里点名的：队列是键的一部分，而这一行带着过期时刻。第三个是
`on conflict` 需要的——一条匹配 `(queue, key)` 的唯一约束或索引，否则迁移能跑过去，而每一次带键的写
都在第一条语句上失败，报
`there is no unique or exclusion constraint matching the ON CONFLICT specification`。

### 有些东西故意不变

`Engine::submit` 仍然回答一个 `JobId`（`jobq/3.2-public-api-baseline` 把它钉住了）：一个需要知道
*自己*的请求是不是第一个的生产者，问的是轨迹，不是队列，而这里多一个答案就是多一份契约。`claim`、租约
和 worker 都不动：一个被去重过的作业，就是一个普通作业。

  后端上，也就是 `slow:conformance@2` 在 `conformance.toml` 里每个后端重复一次的那趟运行。

- `kiln check jobq/3.11-delayed-timers` — 之前那套仍然通过：这一步给 `enqueue` 加了一个问题，没有

## 陷阱

1. **拒绝一个窗口已过的键。** `insert … on conflict … do nothing` 是显而易见的写法，而它让每个键
   *永远*只指向一个作业：于是边界用例在窗口过去一秒后失败，一个合法的后来请求被一个早先窗口的作业回答，
   而表只管变大。过期的行必须被**重置**，`do update … where` 那一半就是干这个的。
2. **`where expires_at < $now` 而不是 `<=`。** 差一个字符，窗口就在错的那一边半开了：恰好在
   `first + window` 时这一行仍然"活着"，于是
   `the_boundary_is_exactly_the_window_after_the_first_request` 在本该产生新作业的地方给出一个
  重复——而且只在那一个时刻，正因如此才有这个专门盯着它的用例。
3. **用到达的那个请求盖窗口的时间戳。** 每个带键的请求都写 `now + window`，连重复请求也写，等于每重试
   一次就把末尾往前推：那个要十分钟窗口的重复请求，通过了边界用例的第一个断言，然后把键又续活了十分钟，
   于是用例里 `first + window` 那一步失败。窗口属于这个键第一次被取走时的样子。
4. **先读键，再写。** `select … where queue = $1 and key = $2`，空了再插，是两个生产者都能穿过去的
   一道缝：`callers_racing_for_one_key_get_one_job` 要么撞在约束上失败（一个竞争者的提交被拒绝），
   要么在队列里找到两个作业。让数据库在一条语句里裁决。
5. **用键被写下那一刻的副本回答重复。** 把 `Job` 存在键旁边看起来干净利落，却会把一个已经了结的作业
   回答成 `queued`：用例先完成第一个作业再问一次，而它读回来的状态，是键被取走那一刻的状态。键指向一个
   作业；状态住在那一行里。
6. **把有键没窗口当成"不去重"。** 请求带了一个名字，所以生产者相信自己给工作命了名；一个忽略这个键的
   存储回答两个作业，看起来还是对的——那个拒绝用例就是不让它过关的地方，而引擎的答案是
   `Error::Invalid`，不是一个没人要的时长。
7. **对整张表去重。** 一个 `key` 列加唯一索引，里面没有队列：
   `a_key_is_a_key_of_one_queue_and_one_window` 会失败，因为同一个字符串在另一个队列里是另一件工作
   （`relay/2.2-idempotent-ingest` 为租户做过这个决定）。两个在不同的队列里都把第一个作业叫 `order-1`
   的生产者，彼此不是重复。
8. **行写完以后，在 Rust 里拿 `self.clock.now()` 去查窗口。** 这次比较总得发生在某处，而如果它发生在
   语句之外，行里的时刻和引擎的决定就可能来自两次不同的读钟：修法不是把比较写得更紧，而是问一次时钟、
   让语句去比较它（绑的是 `$now`，不是 `now()`）。

## 延伸阅读

- [PostgreSQL: `INSERT … ON CONFLICT`](https://www.postgresql.org/docs/17/sql-insert.html#SQL-ON-CONFLICT)
  — `do update … where`、`excluded`、它需要的仲裁索引，以及 update 子句把行压掉时 `returning` 是什么样。
- [PostgreSQL: data-modifying statements in `WITH`](https://www.postgresql.org/docs/17/queries-with.html#QUERIES-WITH-MODIFYING)
  — 为什么一条语句的各个子语句共用一个快照，以及为什么"一条语句"是让一个决定变成原子最便宜的方式。
- [RFC 9110 §13](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods) — 对*方法*
  来说幂等是什么意思，以及为什么键是调用方的声明，而不是服务器的推断。
- `relay/2.2-idempotent-ingest` — 同一个承诺，完全没有窗口，以及它的规格打破它的四种方式：先读后写、
  本该 `do nothing` 的地方用了 `do update`、对一次重试报错，以及一个键没有按它必须按的每一样东西分键。
- `jobq/3.16-dlq-tooling` — 作业被清除时那些键行会怎样，而这是你的迁移用 `on delete cascade` 做的
  决定。
- `jobq/3.8-clock-injection` — 为什么一个带键的 `enqueue` 比较的两个时刻是绑定的参数，而不是数据库的
  `now()`。
