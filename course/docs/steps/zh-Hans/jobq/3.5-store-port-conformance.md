# 一套用例，两个实现：存储端口及其一致性测试

## 为什么

引擎的承诺都挂在它的端口上：一次认领按优先级把到期的工作发出去，绝不把同一个作业交给两个 worker；
worker 拿走一个作业时就计入一次尝试；只有有人正在跑的作业才能被结算；一份没人写过的标识是一个空答案，
而不是一个错误。到今天为止，只有一个实现守着这些承诺，而它们成立，是因为没有什么可以跟它们不一致。

持久化后端把它们变成一份*契约*：两个在不同时间写成的代码库，对着同样的五个方法。它招来的失败不是
崩溃，而是漂移——优先级在新后端上悄悄失去意义，一次重启把同一个作业发出去两遍，一份不存在的标识开始
作为错误回来，而不是一个空答案——而这一切直到队列是那份工作唯一的副本时才露出来。

拦住漂移的不是小心，而是一套一致性用例：一个写满断言的文件，每个后端跑一遍。一个规格文件和一道闸门，
而不是 N 套答法各异的测试；它也是这个项目里唯一一件产物，把“实现这个端口”写成了机器能够反驳的形式。

## 回顾

- `db/migrations@apply` — `mailer/1.9-postgres`：向前编号的文件只应用一次，已应用的那一组记在数据库
  里，服务开始服务之前把 schema 更新到最新——一次可以安全重复的启动。这一步不重教它，而
  `migrations/0001_jobs.sql` 是按那一步留给你的写法写的（`mailer` 和 `relay` 各自编号自己的文件；这个
  项目从 `0001` 开始）。变的是这张 schema 是谁的：不是一个服务私有的表，而是一张表，它只是某个端口的
  *一个*实现，那个端口的另一个实现是一个 map。
- `db/atomic-claim@apply` — `relay/2.5-atomic-claim`：认领是一条语句，里面带 `for update skip locked`，
  因为挑出这些行和给它们盖章必须是一个决定。这条知识可以整块搬过来。新的是它拿来跟什么比：在 `relay`
  里，那条语句是这个服务认领工作的唯一方式；在这里，它是一个端口的两个实现之一，由一份同时还会跑在一个
  根本没有行可锁的存储上的文件来评判。

## 变化

- **新的产物是用例，不是后端。** 一个规格文件，每个后端跑一遍：快跑用 `memory`（夹具的默认值），而
  `conformance@2` 闸门会在 `KILN_BACKEND` 分别设成 `conformance.toml` 声明的每个名字的情况下，重跑
  项目自己的 `run.cmd`。加下一个后端，就是加一个名字和夹具里的一个变体——不是再加一份规格。
- **用例所断言的承诺，必须写在*端口里*。** 认领顺序就是这样一条：从这一步起它写在 `Store::claim` 上，
  因为只由一个后端的文档许下的承诺，是另一个后端守不了的承诺，而用例就会去读它本来该评判的那个实现。
- **不一致是出错的那一方实现的 bug——包括已经交付的那个。** 内存存储拿着一把锁挑出到期的作业，放下锁
  之后再盖章，于是同一瞬间发问的两个 worker 可能都拿到同一个作业。引擎里没有任何东西看得见这件事；用例
  在第一遍跑的时候就看见了，修法是把这个决定的两半放进一个临界区。

## 作业

- 写 `migrations/0001_jobs.sql`：端口承载的那些列，没有一列是调用方看不见的——标识、队列、载荷、
  状态、优先级、它最早能跑的那个时刻、它已经花掉的尝试次数、分给它的预算、它最近一次失败的原因——再给
  认领对着一个大部分都还没到期的表所跑的那个谓词加一条索引。
- 实现持久化后端：`connect`、一个对已经是最新的数据库也能安全跑的 `migrate`，以及端口的五个方法，每个
  都答得和内存存储一模一样。
- 让 `claim` 成为**一条语句**：在给行盖章的 update 里用 `for update skip locked` 挑行，在那里计入
  尝试，并按端口的顺序作答（先优先级，再到期最久的作业，最后标识），而不是按行从表里返回的任何顺序。
- 该拒绝的就拒绝。`complete` 和 `fail` 只碰正在运行的作业：作业处在别的状态就是 `Error::Invalid`，
  没有这一行就是 `Error::NotFound`。`get` 对一份没人写过的标识回答 `Ok(None)`。尝试预算为零是
  `Error::Invalid`，而不是一行谁都跑不了的记录。
- 声明模块：在 `src/engine/store/mod.rs` 里写 `pub(crate) mod postgres;`，类型通过 `jobq::engine`
  重新导出——绝不用 `pub mod`，那会让这个模块变成一条路径，破坏 `jobq/3.2-public-api-baseline` 钉住
  的公开面——再在 `tests/support/mod.rs` 里声明两个新夹具，好让规格够得着它们。
- 内存后端也要保持合规。某个用例在其中之一上失败时，要改的是跟端口不一致的那个实现；放松断言，只会把
  不一致挪进引擎里。

## 完成标准

- `kiln run jobq/3.5-store-port-conformance` — 整套用例在内存存储上全绿，快跑用的就是它。
- 在 `app/jobq` 里 `KILN_BACKEND=postgres kiln run jobq/3.5-store-port-conformance` — 同样的用例，
  对着它自己的一个 Postgres 容器：正是 `conformance@2` 闸门在 `conformance.toml` 里按每个后端重复一遍
  的那次运行。
- `kiln check jobq/3.5-store-port-conformance` — 每个 must 闸门都是绿的，包括 `images` 和
  `semver@baseline`。

## 陷阱

1. **先挑行、再把决定写下来的认领。** 用例的回答是
   `two workers came back with the same job (4 of 16 claims were repeats)`——而且对着
   `KILN_BACKEND=memory` 也会这样回答，因为内存存储交付时就是这个形状：在一把锁下读到期的作业，在
   下一把锁下给它们盖章。修法是结构性的（在同一个临界区里 select 再 stamp），而不是事后加个检查。
2. **用 `format!` 拼语句。** 一份共享的列清单看着像好习惯，而 `sqlx` 0.9 拒绝它：
   `error[E0277]: dynamic SQL strings should be audited for possible
   injections … the trait SqlSafeStr is not implemented for &String`。驱动接收 `&'static
   str`，好让 SQL 在调用点就看得见；每个值都以绑定参数的方式走，所以根本没什么可拼的。
3. **`migrate` 自己跑 DDL。** 用一句光秃秃的 `execute("create table jobs …")` 建表，会让*第二次*运行
   以 `42P07: relation "jobs" already exists` 失败，而第二次运行正是守护进程每次启动都会做的那一次。
   `the_schema_step_can_be_run_again` 就是说这件事的用例。
4. **拿数据库的时钟去解析 `run_at`。** `now()` 是引擎时钟旁边的第二个权威，两者会漂移：一个时钟慢了
   一秒的容器，会让 `a_write_answers_with_the_row_and_the_instant_it_is_due` 失败，消息里带着后端自己
   的名字，而同一条断言在内存存储上却能过。把一只时钟绑定进语句，才是让两个后端回答同一个问题的原因。
5. **`pub mod postgres;`。** 它编得过，用例全绿，而下次评判 `jobq/3.2-public-api-baseline` 时，运行
   会以 `every module under src/engine must be pub(crate)` 失败：一个调用方点得出名字的模块，就是下一
   个发布里会从他们脚下挪走的模块。
6. **忘了那个永远跑不了的请求。** `Store::enqueue` 把尝试预算为零记作 `Error::Invalid`；仍然把行插进
   去的后端会以 `expected Error::Invalid,
   got …` 失败，而它写下的那一行，是任何 worker 都永远完不成的——内存存储本来就在拒绝它，断言之所以
   存在，原因就在这里。
7. **夹具目录自己的死代码。** `clippy@3` 是对每个目标都 `-D warnings`，测试也在内，而夹具是一份菜单：
   `tests/support/postgres.rs` 带着供后面几步用的 `query`、`execute` 和 `stop`，于是第一个不调用其中
   某一个的规格，就会以 `error: struct Postgres is never constructed` 撞上闸门。放宽应该放在写明了
   理由的地方——`tests/support/mod.rs` 顶上一句 `#![allow(dead_code)]`，因为*这个*规格里没人调用的
   夹具，是另一个规格会调用的夹具——而不是撒在今天恰好没被用到的那些函数上。

## 延伸阅读

- [PostgreSQL: the locking clause](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)
  — `FOR UPDATE`，以及把排队的 worker 变成去取下一行空闲记录的 worker 的 `SKIP LOCKED`。
- [`sqlx::postgres::PgPoolOptions`](https://docs.rs/sqlx/0.9.0/sqlx/postgres/struct.PgPoolOptions.html)
  — 连接、`acquire_timeout`，以及 `connect` 会等而 `connect_lazy` 不等的那些东西。
- [`sqlx::migrate!`](https://docs.rs/sqlx/0.9.0/sqlx/macro.migrate.html) — 编进二进制里的迁移，以及
  记录其中哪些已经跑过的表。
- [`tokio::test`](https://docs.rs/tokio/1/tokio/attr.test.html) — 运行时的形态，正是它让那个并发用例
  不再是一次接一次的认领。
- `relay/2.5-atomic-claim` 的 `src/claim.rs`：同一条语句，为单个服务而写，带着这个端口还没有的租约和
  持有者（`jobq/3.7-leases-and-recovery`）。
- 端口本身——`src/engine/store/mod.rs` 是用例读的契约，`tests/support/store.rs` 是 `KILN_BACKEND`
  穿过的那条缝。
