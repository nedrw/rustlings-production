# 特性开关拼出同一个引擎，而不是每个特性一个程序

## 回顾

- `cfg/layered-config@apply` — `mailer/1.4-config`：默认在最底下，其次是一个文件，再往上是环境，旗标
  最后；`--check-config` 打印进程实际决定了什么。这就是一个*二进制*在运行时回答“我有哪些设置项”的
  方式。特性在上一层、也更早地回答同一个问题：到底有哪些代码在那个二进制里。
- `api/library-design@apply` — `jobq/3.2-public-api-baseline`：公开面就是 `jobq::engine` 重新导出的
  东西，存储端口已经封住，而 `jobq/3.3-library-errors` 给了这个公开面一个调用方能据以分支的错误类型。
  特性改的是那个公开面*背后*的东西，而这恰恰是基线看不见的一件事：同一个 `Engine`，里面装的东西少
  一些。

## 变化

服务用一个旗标解决“有些部署要数据库、有些不要”的问题。库做不到：数据库驱动必须在构建里*缺席*，否则它
就在每个只想要内存队列的调用方的二进制里。于是这个 crate 学会被装配，而它跟分层配置的区别，在于决定的
方向：

- **这一层由依赖这个 crate 的人在编译期选定。** `cfg` 不是运行时的 `if`。不想要持久化后端的调用方
  写 `default-features = false`；想要的调用方什么都不做就拿到了。没人需要把一个设置项一路传下去，
  也没有哪个部署会漏掉一个。
- **特性是相加的，这是一条设计约束，不是一句口号。** 任何东西都不能写成“没有”：不能有“关掉
  postgres”，也不能有“停用 metrics”。这条规则是为了让想要不同东西的两个调用方拿到并集——`jobq` 带
  `postgres`，另一个东西也想要 `metrics`，它们不可能落在某个让其中一方悄悄输掉的构建里。
- **一个 crate，几种装配。** 这一步要防的失败模式是分叉：一个 `jobq-memory` 包和一个 `jobq-postgres`
  包，各自漂移，直到两者的 `Engine` 类型不再是同一个类型。这里的每一种装配都是同一个 crate、同一个
  `Engine`、同一个端口——而组合的矩阵是检查出来的，不是信出来的。
- **内存引擎是底线。** 每一种装配都能跑一个作业。这正是 `--no-default-features` 成为一次*有用*的构建
  而不是坏掉的构建的原因，也是规格在每种组合里都会拿调用方去验的那条性质。

闸门*今天*守住的只有一条缝，而且它故意很小：持久化后端还没写（`jobq/3.5-store-port-conformance` 才
写它），所以特性决定的是这个 crate 是哪种构建——而这样一种构建绝不能做的唯一一件事，就是让运维去猜。
现在加第二个特性（`metrics`、`tracing`）会是一个为不存在的代码而设的开关：引擎没有指标可关，而守护
进程的日志不是可选的（`mailer/1.6`），所以这个 crate 今天诚实的特性数量是一。

## 作业

- 给 `Cargo.toml` 加一张 `[features]` 表：`default = ["postgres"]`，`postgres` 写成列表。默认开启，
  因为朴素的 `cargo build`——一个依赖它的 crate、`cargo install` 和这个 track 后面每一步用的那个
  ——必须是完整的引擎。
- 把这张表写进 `kiln:scaffold:begin` / `kiln:scaffold:end` 块里，并让 `postgres` 保持列表形式，一行
  一项。这不是装饰：`jobq/3.5-store-port-conformance` 会把持久化后端的依赖接进那张列表，而脚手架只
  允许往一块有标记的区域里插行（docs/authoring.md §5）。
- 把 `cfg` 放在唯一能碰到持久化后端的地方：`open_store` 把一个持久化 URL 交给一个函数，函数体就是那
  条缝，`#[cfg(feature = "postgres")]` 决定这次构建在有人要后端时给出哪个答案。
- 让答案说清这是哪种构建。不带这个特性的构建必须*点名缺的那个特性*来拒绝一个持久化存储（“rebuild
  with `--features postgres`”），而不是把连接串重复一遍：告诉一个有数据库的运维去用 `memory`，帮不了
  他。
- 别为这个特性改别的任何东西：内存引擎、端口、错误类型和两个二进制在每种装配里都一样，而
  `cargo build --no-default-features` 必须产出一个能排干内存队列的守护进程。

## 完成标准

- `kiln run jobq/3.4-feature-assembly` — 规格通过：清单点名了这个特性并把它打开，每种装配带着自己的
  单元测试都能构建，一个调用方在每种装配里都跑一个作业，而不带这个特性的装配点名拒绝一个持久化存储。
- `kiln check jobq/3.4-feature-assembly` — 每个 must 闸门都是绿的，包括 `clippy@3` 和
  `semver@baseline`（`jobq/3.2` 的公开面没有被这一步改动，见证文件就是这么说的）。
- 在 `app/jobq` 里 `cargo build -p jobq --no-default-features` — 只有内存引擎，然后
  `cargo build -p jobq --all-features`。

## 陷阱

1. **有一个调用点漏了 `cfg`。** 在库里给持久化路径加了门，却在 `src/bin/jobqd.rs` 里留下一处引用：
   `cargo build --no-default-features` 以
   `error[E0433]: failed to resolve: use of undeclared crate or module` 失败，而坏掉的那个构建，
   恰恰是没人会手动跑的那个——这就是规格要在每种组合里都构建守护进程的原因。
2. **用*另一个*构建的说法拒绝持久化存储。** 在一个不带特性的构建里留着旧消息（“use `memory`, or wait
   for the durable backend”）看着像点明了问题——里面的连接串带着 `postgres`——而规格在读这条消息之前
   会把 URL 剥掉，于是它以 *“the refusal has to name the missing feature (`postgres`) as a feature”*
   失败。运维要的是重建时该用的那个旗标，不是把自己写的连接串读回给他听。
3. **一个只能挨着别的特性才编得过的特性。** 守护进程的存储工厂按 `postgres` 加门，它的*调用点*却假定
   这个特性开着，会让 `cargo build --no-default-features` 以
   `error[E0425]: cannot find value … in this scope` 失败，而
   `--no-default-features --features <one>` 更糟：它在作者试过的那一种组合里编得过。这就是规格让每种
   特性各占矩阵一行、而不只构建三种省事的组合的原因。
4. **还是把驱动拖了进来。** 把 `sqlx` 做成普通依赖（“总比可选依赖简单”）会把数据库塞进每个只想要队列
   的调用方的二进制里：构建是绿的，而特性什么也不意味着。
5. **假定默认构建就够了。** 跑一遍 `cargo test -p jobq` 就收工，只证明了一种装配。
   `cargo build --no-default-features` 才能找出漏掉的 `cfg`，而 `--all-features` 能找出那个从未和
   其他特性一起跑过的 `cfg`。

## 延伸阅读

- [The Cargo book: features](https://doc.rust-lang.org/cargo/reference/features.html) — 相加的特性、
  `dep:` 语法，以及 `default-features = false` 为什么是一个*请求*而不是一次减法。
- [`cfg` documentation](https://doc.rust-lang.org/reference/conditional-compilation.html) — 编译期配置
  和运行期配置的区别，说得很清楚，包括为什么特性集合是*构建*的属性，而不是运行中的程序的属性。
- [The Cargo book: optional dependencies](https://doc.rust-lang.org/cargo/reference/features.html#optional-dependencies)
  — `jobq/3.5-store-port-conformance` 用来把持久化后端变成可选的机制：一个可选依赖在某个特性打开它
  之前，不在构建里。
