# 性能预算：慢机器也判不红

## 为什么

"它变慢了"是一条没人能照着行动的评审意见，而它最显然的答法——给那个东西计时——量的是跑它的那台机器。在
共享构建机上，一个墙钟阈值忙的时候红、闲的时候绿，而它教出来的条件反射，是重跑那个作业，直到它通过。没人
相信的闸门，是没人守的闸门。

机器改不了的是*工作量*：一个循环看过多少行、做了多少写入，输入翻倍时这些数字涨了多少。这些数字，评审读得
懂，学习者推到远端之前可以在本地跑出来，闸门也可以拿去和某人特意量出来的基线比——而最后这一条最要紧，因为
小输入会把平方级的算法整个藏住：记得自己位置的排干，为十六行的队列付十六个格子；每行都从头再找一遍的那个
排干，付一百一十二个；而两者都在读者来得及抬头之前就跑完了。

这一步用三样东西搭出这份预算：一个计数器，一道看住计数器形状的守卫，以及装置打印出来的名字和边界——好让
闸门和读者都拿它们去比。

## 回顾

- `test/coverage-policy@apply`——`jobq/3.21-coverage-policy`：证明质量的一半在策略，也是这一步的上一
  步。覆盖率说的是测试套件*够到过*哪些地方；这一步量的是代码在被够到的时候*花掉多少*。两者都是写下来的
  主张，写在评审者能拿数字来争的地方，而且都不是对机器的测量。**这一步不重讲那条策略。** 新的是计数器、
  看住它形状的守卫，以及装置打印出来的那些数字。
- `db/atomic-claim@design`——`jobq/3.7-leases-and-recovery`：队列的活都在 `claim` 里——锁、选取、盖章，在
  同一个临界区——而这台引擎上的预算，讲的就是这个操作。这一步量的排干，就是一次认领交到 worker 手里的
  同一批，顺序是存储给它排的顺序，也就是 `jobq/3.9-priority-fairness` 决定的那个顺序。

## 变化

三个名字，一个文件：

- **`Work`**——两个计数器，不是一个。看过多少格子、写下多少语句，回答的是两个问题，而一个缺陷恰好只会出现
  在其中一个里：把每一行看两遍的排干，格子翻倍、语句不变；把同一行发出去两遍的排干，正好相反。只报一个
  总和，等于只说"有东西变了"。
- **`scale_to`**——守卫。`work(2n) / work(n)`：代价跟着队列走的排干，这个值约等于二；每回都从头重扫的排
  干，每翻一倍约等于四——它的每行格子数随队列增长（256 行时是 97，而另一个是一）——而较小那次运行什么活
  都没做时，答案是 `None`，因为一个没有分母的比较不是一个数。
- **`Row`、`Pull`**——一批，按存储排好的顺序给出，以及记得自己走到哪儿的排干。上面那两个排干之间的全部
  差别就是游标，而它也正是这一步要做的决定。
- **`METRICS`、`SCALE_MAX`、`report`**——预算里属于项目的那一半，而*闸门*拿它来要求这个项目。课程那边
  留着基线（`course/tracks/jobq/budget/3.22-bench-budget.toml`），脚手架送来打印这些行的装置，而名字是一
  张两边都读的清单。

## 作业

脚手架加了一个模块、一个装置和一个页面。**还没有任何东西声明这个模块**：接上 `src/engine/mod.rs` 是你的
第一个决定，在做出它之前，规格和装置都编译不过。

### `Work`——一次操作花了多少

`examine` 每看一行记一笔，`statement` 每发一行记一笔，`total` 是这两个的和。`scale_to` 回答较大的那次测量
多花了多少——没有东西可除时给 `None` 而不是 `0.0`，因为零会像别的比值一样拿去和边界比，从而给一个什么都
没量到的排干报一个 *pass*。

### `Row` 和 `Pull`——一批，以及一个记得住事的排干

一行是交给 worker 的身份，以及它能跑的时刻；`is_due` 用的是 `<=`，因为定在这一刻跑的作业，在这一刻就到
期了。拉取留着它的游标：它发出去的行从此就落在身后，而在问它用的那个 `now` 还没到期的行会被跨过去，而不
是再问一遍——这是排干，不是定时器，而这一批来自一个已经按所问时刻筛过的存储。正因如此，一次排干的代价是
每行一个格子，而不是平方。

### `METRICS`、`SCALE_MAX` 和 `report`——别人读的那些数字

三个指标名、守卫据以判定的边界，以及装置从一对测量里打印出来的行。计数取自两者中较小的那个，守卫取自这
一对，而没有分母的一对只打印两行：读它们的闸门把缺掉的指标当作 `blocked` 而不是通过，而那正是仪器什么都
没量到时的诚实答案。

### `docs/budget.md`——把基线写下来

桩子点了工作负载和它的形状。把它填上：每个指标数的是什么、课程为它带了什么基线、为什么守卫是上界而不是
目标，以及闸门怎么拿它们来比。规格读这一页，并把它和 `METRICS`、`SCALE_MAX` 对起来。

### 哪些东西故意不变

装置（`tests/budget.rs`）是课程的文件：它就是仪器，而学习者改仪器，就是学习者在改测量。工作负载的大小也
是内容——改它，就等于改掉每一条基线的意思，所以它得跟那些数字在同一个提交里动。

## 完成标准

- `kiln run jobq/3.22-bench-budget` — 九个用例通过：两个计数器和总和、一个没有分母的比值、到期边界、一批
  发出去的顺序、四个规模上的计数、排干之后再问一次不花任何代价、守卫用在两个排干上、装置打印的三行，以及
  页面和常量对得上。
- `kiln check jobq/3.22-bench-budget` — 每个 must 闸门都是绿的，`links` 也在内。
- `kiln selftest jobq/3.22-bench-budget --track jobq` — 慢路径跑 `slow:bench-budget@10`，它把装置跑一遍，
  再拿去和课程的基线比。要读的那行是
  `3 metric(s) within ±10% of the course baseline: claim_statements 192, scan_cells 256,
  scale_ratio_max 2`。没装 `llvm-tools-preview` 的机器上，`slow:?coverage@80` 仍然答 `⚠ blocked`；那是
  诚实的答案，不是这一步的失败。

## 陷阱

1. **给它计时。** 用毫秒量的预算，是机器说了算的预算，而读它的闸门会在别人的构建正在跑的时候变红。`Work`
   数格子和语句，正是为了这个：这些数字在每一个进程里、每一台机器上、每一次运行中都是同一个。
2. **一个全部到期的工作负载。** 于是 `scan_cells` 等于 `claim_statements`，排干没有什么可看、可跳：这一
   对数字没有说出任何单个计数没说的事，而守卫量的是一个没有任何判断的循环。四行里有一行没到期，才让这两个
   计数成为两件不同的事实。
3. **队列太短。** 在十六行的一批上，从头再来的排干是 112 个格子，诚实的排干是 16 个，批翻倍时工作量差
   3.7 倍——差别是有，但一个扫一眼绿灯的评审者，在四行的夹具上看不出来：那里两者是 10 和 4。守卫之所以
   存在，是因为比值才是那个*不*需要长队列就有意义的部分。
4. **把 `_max` 指标读成目标。** `scale_ratio_max = 2.2` 是一个上界：变便宜了的排干是通过的排干，而一个把
   参考比值降到 1.9 的改动，不需要去改基线。把它当成"大约 2.2"，就把一道守卫变成了有人去调的目标。
5. **改了工作负载却留着数字。** 基线是 256 行队列、四行里有一行没到期时的计数；在 64 行上量出来的装置会打
   印一个不同的 `scan_cells` 和同一个 `scale_ratio_max`，而拿一个没人重量过的基线做 ±10% 的比较，就是一道
   会因为页面没解释的理由而失败的闸门。
6. **没有分母时打印 `0`。** 对一个什么都没量到的排干，`scale_ratio_max=0` 是*通过*——这是预算绝不能不小心
   给出的那个答案。`scale_to` 答 `None`，`report` 把那一行省掉，闸门把它报成 `blocked`。
7. **改装置或基线，而不是改代码。** `tests/budget.rs` 是课程的文件，
   `course/tracks/jobq/budget/3.22-bench-budget.toml` 是闸门读的那份拷贝——改其中任何一个，改的是仪器，
   而不是它量的那台机器。`kiln reset jobq/3.22-bench-budget` 会把装置放回去。

## 延伸阅读

- [Criterion.rs: analysis](https://bheisler.github.io/criterion.rs/book/analysis.html) — 一个墙钟基准要
  做到什么才可信：预热、样本量、离群点检测，以及一道依赖时间的闸门所需要的那些统计。
- [`iai`](https://github.com/bheisler/iai) — 一个建在指令计数上的装置，理由和这一步数格子一样：它比的是
  代码的两个版本，而不是两台机器。
- [Google SRE book: monitoring distributed systems](https://sre.google/sre-book/monitoring-distributed-systems/)
  — 同一个论证往上抬一层：一个仪表盘画出来的指标，在每一台报告它的机器上都必须意味着同一件事。
- `course/tracks/jobq/spec/3.22/budget.rs` — 那九个用例，包括守卫据以比较的两个排干，以及装置打印的那
  三行。
- `course/tracks/jobq/budget/3.22-bench-budget.toml` — 闸门读的基线，以及它跑的命令。
- `jobq/3.21-coverage-policy` — 证明质量的另一半：测试套件够到过什么，对着这一步的代码花掉多少。
