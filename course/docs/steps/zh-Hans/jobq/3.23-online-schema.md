# 扩展、回填、收缩：在线改队列自己的 schema

## 回顾

- `db/schema-online-evolution@aware`——`relay/2.23-online-schema`：三次部署，以及它们之间的那段窗口。那一步
  决定了，当应用这次变更的进程不是唯一在跑的进程时，一次 schema 变更要付多少代价——扩展只加，不重写；回填
  分批地填，停在*什么都没填*上；**回退处理就是回填所写的同一个表达式**，所以存下来的数字和算出来的数字不可
  能打架。它也在那里决定了中间那个阶段住在哪儿：一条命令，由人来跑，因为这个服务没有队列能把它放下。**这
  一步是那个位置上的 `apply` 一半**，而它唯一改掉的，就是那句话。
- `db/migrations@apply`——`mailer/1.9-postgres`：有一个 schema，进程在对外服务之前把它应用上去，而一个已经
  跑过的迁移什么都不改。这里，schema 归队列自己所有，而这次变更的每一个阶段，都写成一次部署对着一台正在服
  务的数据库执行的语句。
- `db/port-conformance@apply`——`jobq/3.5-store-port-conformance`：一份套件，所有后端。正因为如此，这一
  步讲的可以是一套*流程*，而不是某一个数据库的 SQL；也正因为如此，下面的规格跑两遍——内存存储对
  `migrate()` 答 `Ok(())`，因为它没有 schema，而真正关于 schema 本身的那些用例，归数据库。
- `jobq/3.14-job-state-machine`——把状态列收口的那个迁移，加 `check` 时让它*校验*，而不是写成
  `not valid`，并说了为什么："一个跳过校验的 check，恰好会把它本该找出来的那些行留在身后，而在这条 track
  教过的每一个部署里，这张表都很小。对一个不小的表有答案的那一步，是 schema 那一步。"这一步就是那一步，而
  答案是 `not valid`。

## 变化

四个决定，把这一步和 `relay/2.23` 分开：

- **表归队列所有，而回填是队列里的一个作业。** 中间那个阶段不是某人守在服务旁边跑的一条命令：它是工作，跑
  在正在被改的那张表里的队列上，所以它走同一个端口、同一批认领、同一批 worker、同一条轨迹。分批，因为每批
  一条语句才让一批成为原子的；按 `run_at` 控制节奏，因为一个把所有批次都排成当下到期的计划，会把正在被它
  迁移的那个队列堵住；可续跑，因为这一批的谓词是*值不存在*，而不是一个书签；可取消，因为一个从没跑过的批
  次什么都没填，而一个跑过的批次把自己整批填完了。
- **端口不变。** `Store` 一个方法都没加，这是设计，不是遗漏：引擎欠这一步的，是那个*计划*——下一步是哪个
  阶段、依据系统目录怎么说，以及中间那个阶段花多少、摊成什么样——而端口已经有了一个作业需要的一切。这个后
  果值得读两遍：内存后端连 schema 都没有，却通过同一份套件；而数据库答得出来的那些阶段，就去问数据库。
- **用 `not valid`，因为表不小。** `add constraint … check (…) not valid` 对每一次写入立刻生效，同时告诉
  数据库跳过已经在里面的那些行；收缩阶段里的 `validate constraint`，是后面那次部署，让它真的去检查它们。
  在十行的表上，在扩展阶段就校验，只是舍入误差，`mailer`/`jobq/3.6` 那么做是对的；而在一张就是整个部署队列
  的表上，那是在一次部署取到的锁底下做全表扫描。
- **每个阶段都先问系统目录。** `alter table add column` 不幂等：第二次跑扩展是一个错误，不是空操作。所以
  这个阶段根据数据库已经答出来的东西（`Applied`）来判断，答*没有事要做*，而不是把它的语句再跑一遍。唯一
  的例外是中间阶段自己那条语句，它的谓词就是它可续跑的全部。

## 作业

脚手架加了一个模块、一个装置和一个页面。**还没有任何东西声明这个模块**：接上 `src/engine/mod.rs` 是你的
第一个决定，在做出它之前，规格和装置都编译不过。

### `Change`——一列、一个表达式、一个队列

`Change::new(table, column, computed, queue)` 就是全部描述：队列住在哪张表里、它新加的那一列、算出这个值
的 SQL 表达式，以及回填作业跑在哪个队列上。`batch` 和 `per` 是两个决定*速率*的值：一个作业填多少行，两个
作业之间隔多远。约束名和索引名从列名推出来（`<table>_<column>_known`、`<table>_unfilled_<column>`），而不
是再拼一遍，因为一个在系统目录里看到其中一个的运维，应该能顺着它讲的那一列找到另一个。

`fallback()` 是列还空着的时候读路径的答案：`coalesce(<column>, <computed>)`。它由 `computed()` 拼出来，
而不是另外写一遍，因为存下来的值和算出来的值必须是*分处两地的同一个表达式*——让扩展阶段隐形的全部道理就在
这里，而这是 `relay/2.23` 论证过、这一步照旧保留的东西。

### `Applied` 和 `Step`——数据库说了什么，以及那意味着什么

`Applied` 是系统目录的答案：列在不在、多少行没有值、约束校验过没有。`Applied::before()`、
`expanded(remaining)` 和 `contracted()` 是一次部署走过的三个状态，每个阶段取其中一个，答一个 `Step`：

| `Step` | when |
| --- | --- |
| `Statements(Vec<String>)` | 这个阶段有活：一次部署按顺序跑的语句 |
| `Jobs(Plan)` | 中间阶段：要提交的作业，每批一个 |
| `Nothing(&str)` | 这个阶段已经应用过——以及把理由说清楚 |
| `Blocked(&str)` | 在它之前的阶段还没做完，所以这个阶段会被拒绝 |

真正要紧的是最后两个的区别。`Nothing` 是"这件事已经发生过"，而正是这一点让每个阶段都可以安全地跑两遍；
`Blocked` 是"这件事会被拒绝"，也就是收缩对着还有空值的行执行 `set not null` 时数据库会给的答案——数据库
自己的错误，被挪到了做计划的地方。

### `Plan` 和 `Batch`——中间那个阶段，作为队列来跑的工作

一个计划，是这次变更加上剩下的那些批次：每 `batch` 行一个，`due_at` 彼此相隔一个 `per`，而 `rows()` 的总
和恰好等于缺的那些。`statement(batch)` 是一个批次跑的那一条语句——一条
`update … where … is null … limit <batch>`——而 `is null` 不是一个细节：正是这个谓词让重跑填不进任何东
西，也让一次跑了一半的运行谁都能接着跑完。`requests()` 把计划变成发给正在被改的那个队列的 `SubmitRequest`，
每一个都带着它是哪一批（`migration.batch`、`migration.rows`），因为认领它的 worker 得知道要跑什么。

### `METRICS`、上限和 `report`——这个计划花多少

在线变更的预算也不是一只秒表：它是计划提交的作业数、它保持的速率，以及续跑相对于从头再来要花多少。
`burst()` 是一个间隔里最多有多少批次到期（限流，写成了一道守卫），而 `report(whole, resume)` 打印装置拿去
和课程为这一步带的基线（`course/tracks/jobq/budget/3.23-online-schema.toml`）相比的那三行。一个没有分母的
计划不打印守卫那一行，而不是打印一个零，因为 `0.0` 会像别的比值一样拿去和边界比，从而给一个什么都没量到的
计划报一个 *pass*。

### `docs/migration.md`——把这次变更写下来，给要跑它的人看

桩子点名了三个阶段和三个指标。把它填上：每个指标数的是什么、课程带了什么基线、为什么速率和续跑比值是守卫
而不是目标，以及一次死在半路的运行该怎么办。规格读这一页，并把它和 `METRICS`、`BURST_LIMIT`、
`RESUME_LIMIT` 对起来，方式和 `jobq/3.22-bench-budget` 拿它自己的页面对自己的常量一样。

### 哪些东西故意不变

装置（`tests/backfill_budget.rs`）是课程的仪器，而端口一点没动（`Store` 在这里一个方法都没多）。表是队列自
己的——`jobs`——而列是 `payload_bytes`，一个从这一行本来就带着的载荷算出来的整数：回填要算的那个事实，每
一行里都已经有了，所以这次变更，读者不可能搞错，写者也不用被交代两遍。

### 规格判什么

| the case | the claim |
| --- | --- |
| `the_expand_phase_adds_and_rewrites_nothing` | 这一列可空、没有默认值，约束是 `not valid`，索引是建立在回填所读的谓词上的部分索引，而整个阶段里没有任何 `update` |
| `the_read_path_answers_from_the_expression_the_backfill_writes` | `fallback()` 是 `coalesce(<column>, <computed>)`，批次的语句用的是 `<computed>`，而扩展里没有回退处理 |
| `the_backfill_is_batched_paced_and_atomic` | `ceil(remaining / batch)` 个作业，没有哪一批大于 `batch`，行数对得上，到期时刻彼此相隔一个 `per`，而一批就是一条语句 |
| `the_guard_is_the_rate_and_the_plan_without_it` | 对一个有节奏的计划，`burst()` 是 1；对一个间隔为零的计划，它是批次数——这正是守卫要抓的缺陷——再拿去和 `BURST_LIMIT` 比 |
| `the_plan_is_a_function_of_what_is_left` | 只剩一半的行，就是一半的作业；`report` 打印三行以及拿去和 `RESUME_LIMIT` 比的比值；空计划不打印比值 |
| `running_a_phase_twice_changes_nothing` | 第二次扩展、对一个填满的表做第二次回填、第二次收缩，都答 `Nothing`；而行还空着的时候，收缩答 `Blocked` |
| `the_backfill_jobs_are_jobs_in_the_queue_it_migrates` | 计划的那些请求，在两个后端上都被端口收下，像别的任何工作一样被认领，带着它们是哪一批，并让队列继续服务它里面本来就有的作业 |
| `the_old_release_writes_rows_this_one_serves` | 对着数据库：在一台正在服务的数据库上应用扩展，这一列仍然可空；一行按*旧*版本的写法写进去，落得下来，并通过回退处理被读出来；一个批次把它填上同一个数字；收缩把这一列变成 `not null`——而把收缩跑两遍没问题 |

## 完成标准

- `kiln run jobq/3.23-online-schema` — 上面八个用例在内存后端上通过。
- `KILN_BACKEND=postgres kiln run jobq/3.23-online-schema` 在 `app/jobq` 里 — 同一份套件，跑在持久后端
  上：最后一个用例需要一个数据库来问，那儿才有。
- `kiln check jobq/3.23-online-schema` — 每个 must 闸门都是绿的，`links` 也在内。
- `cargo test -p jobq --test backfill_budget -- --nocapture` 打印 `jobq-budget backfill_jobs=16`、
  `jobq-budget burst_max=1` 和 `jobq-budget resume_ratio_max=0.500`。
- `kiln selftest jobq/3.23-online-schema --track jobq` — 慢路径。要读的行是
  `3 metric(s) within ±10% of the course baseline: backfill_jobs 16, burst_max 1, resume_ratio_max
  0.5`、`2 backend(s) pass the same suite: memory ✓, postgres ✓`，以及没装 `llvm-tools-preview` 的机
  器上 `slow:?coverage@80` 答的 `⚠ blocked`——那是那里的诚实答案，不是这一步的失败。
- 对着你自己一个里面有数据的数据库：手工把扩展跑一遍，看着队列照常服务（`jobqc submit` 照样能用，`jobqd`
  照样认领），然后把回填的批次一直跑到某一批什么都没填——再把它们全跑一遍，看着行数停在原处。

## 陷阱

1. **`add column … not null`。** Postgres 可以带着默认值把它加上而不重写表，而它仍然是错的：**旧版本**的
   insert 点名的是它知道的那几列，而一个数据库不允许留空的列会拒掉那条 insert——失败落在已经在跑的那段代码
   里。schema 要分三次部署往前走，不是一次。
2. **在迁移里做回填。** 一条覆盖整张表的 `update` 和 DDL 处在同一个事务里，在 worker 要认领的那张表上握着
   写锁，于是队列要停多久就停多久——部署的工作暂停一阵，附一条 changelog 记录。扩展阶段的语句里一条
   `update` 都没有，而规格会查这一点。
3. **没有节奏的计划。** 每一批都在 `now` 到期（`burst_max` 等于作业数，而上限是 1），这样的计划把整张表一
   次交给迁移的那些 worker：它正在迁移的队列，就是它消耗容量的那个队列，于是这次扩展变成了一次换了名字的停
   机。间隔是一个决定；零是某人顺手做出来的决定。
4. **一半都做完了，还在计划整张表。** 计划是系统目录说*还剩什么*的函数——`resume_ratio_max` 是 1.0，而
   边界是 0.6，说的就是一次在走到一半时被打断的运行，打算把每一行再翻一遍。已经填好的行数，是数据库一条查
   询就答得出来的数字，所以没有理由靠试着去填它们来重新推一遍。
5. **用书签代替"值不存在"。** `where id > $1`，或者一张 `backfill_state` 表：第一遍没问题，第二遍就得先
   想清楚，而那意味着它不会被跑第二遍，也就意味着一次死在半路的运行，是没人会去收尾的运行。谓词就是可续跑
   的全部，而给一条 `update` 加 `limit`，才让一个批次是原子的。
6. **第二次跑就失败的收缩。** 这个阶段根据系统目录答 `Nothing`，而语句仍然要写得让一次*应用了一半*的运行
   能收尾：`validate constraint` 和 `set not null` 可以再跑一遍，但没有 `if exists` 的 `drop index` 第二
   次是一个错误——收缩里唯一一条天生不幂等的删除。规格把收缩的语句跑两遍来证明它。
7. **还有空行的时候就收缩。** 数据库会用
   `column "payload_bytes" of relation "jobs" contains null values` 拒掉 `alter table … set not null`，
   而跑了它的那次部署，如今在一次滚动发布中间处于半应用状态。那次拒绝就是收缩跑早了，而计划在任何人碰到数据
   库之前就答 `Blocked`：检查的是 `remaining > 0`。
8. **在 Rust 里算这个值。** `payload.to_string()` 对上 `payload::text`：`jsonb` 会规范化键的顺序和空白，
   `serde_json` 不会，于是某些载荷上存下来的数字和回退处理的数字差一个字节，而没人说得清哪个是对的。表达式
   归数据库，只写一遍，写路径和回退处理都从 `computed()` 读它。
9. **读路径没有回退处理。** 一条没有 `coalesce` 的 `select payload_bytes from jobs`，对每一行早于这次变更
   的行都答 `null`——扩展阶段本该是看不见的，而 null 就是它变成一次破坏性变更的方式。`fallback()` 由
   `computed()` 拼出来，于是窗口的两半是同一个表达式。
10. **改装置或基线，而不是改计划。** `tests/backfill_budget.rs` 是课程的文件，
    `course/tracks/jobq/budget/3.23-online-schema.toml` 是闸门读的那份拷贝：改其中任何一个，改的是仪器，
    而不是它量的那个计划。`kiln reset jobq/3.23-online-schema` 会把装置放回去。

## 延伸阅读

- [PostgreSQL: `ALTER TABLE`](https://www.postgresql.org/docs/17/sql-altertable.html) — `ADD CONSTRAINT
  … NOT VALID` 和 `VALIDATE CONSTRAINT`，以及它们各自取什么级别的锁：扩展阶段之所以能应用在一张正在被写
  的表上，全部理由就在这里。
- [PostgreSQL: `CREATE INDEX`](https://www.postgresql.org/docs/17/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)
  — `concurrently`，这个方向上的下一步：一个建起来不阻塞写入的索引，代价是这次构建可能失败，而且得手工清
  理。
- [PostgreSQL: explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) — 一个迁移的
  语句会取什么级别的锁，以及其中哪些会排在一条正在跑的查询后面。
- `relay/2.23-online-schema` — 同样的三个阶段，只是中间那个是一条由人跑的命令，包括读路径的 `coalesce`，
  以及为什么大小要在值被存下的地方算。
- `jobq/3.11-delayed-timers` — `run_at`，这一步的限流所写的那一列：一个还没到期的批次，是认领不会发出去
  的工作。
- `jobq/3.22-bench-budget` — 建在计数上的预算的形状，这一步的装置照着它走。
- `course/tracks/jobq/spec/3.23/online_schema.rs` — 那八个用例写成的测试，包括"安全地跑两遍"的两半。
- `course/tracks/jobq/budget/3.23-online-schema.toml` — 闸门读的基线，以及它跑的命令。
