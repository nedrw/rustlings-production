# 队列即租户：配额、归因，以及那个吵闹的邻居

## 回顾

- `sec/authz-tenant-isolation@design` — `relay/2.16-authz-audit`：权限模型作为*数据*，一个问矩阵
  的层，而不是每个处理函数顶上的一次检查；三种拒绝，三个不同的理由——`401` 给一个没人发过的名字，
  `403` 给一个动作，而别人的行拿到的 `404` 跟不存在的行一模一样。那句话编码的规则，正是这一步保留的：
  **拒绝针对的是动作，从来不是行**，因为对一个确实存在的行回 `403`，已经回答了调用方在钓的那个问题。
  这里新的是模型说的是什么：队列不是一条路由，它是一个*装着工作的东西*，得有人为它负责。
- `sched/fairness@design` — `jobq/3.9-priority-fairness`：认领是资源被拿走的地方，策略决定一个队列
  最多能占住多少，而超过上限的工作留在队列里，尝试次数原封不动。那个策略就是这一步为*租户*拧的旋钮；
  这里没有第二条策略，正文会说它拧的是哪个旋钮、为什么。
- `obs/metrics-slo@apply` — `relay/2.18-delivery-metrics`：一个服务的数字是按*租户*分的，因为"哪个
  租户慢"才是一个共享服务真正会被问到的问题，而一个指标是一个关于别人会照着做什么的决定。这一步留住的
  数字，是做出那个决定所依据的原始计数——通过引擎去读，按队列、按租户，而不是从日志里抠出来。

## 变化

**矩阵说的是能不能，计数器说的是用了多少，而运维要动手，需要的是后者。** `relay/2.16` 能回答"这个
租户能不能做这件事"，回答不了"昨晚是谁把 worker 池吃掉了"。这是两个不同的问题，而它们的差别就是这一步
加的东西：

- **队列属于一个租户，而模型说明别人能对它做什么。** 一个属主，加上一张覆盖三个动作的授权表——`submit`、
  `claim`、`administer`——更宽的授权覆盖更窄的。把模型写成数据，掉出来两条性质：一个"让*某个租户读另
  一个租户的队列*"的授权无处可写，而一个租户能看见的队列，恰好就是模型里点了它名字的那些队列。
- **拒绝给出的答案，跟一个没人声明过的队列给出的答案一模一样。** 这是 T2 那一课，放在它真能放得住的地
  方：过滤在*查询*里，不在一个调用方必须记得做的检查里。租户的句柄是一个值（`Store::scoped`），不是
  每次调用都带的一个参数，所以这个引擎里没有哪条路径会对着请求问"你是谁"——而一个句柄看不见的作业，回
  答起来跟一个没人写过的作业一样（端口给 `Ok(None)`，引擎给 `NotFound`）。
- **计数器由工作顺手写下，而不是事后从工作里重建。** 每个队列五个——`submitted`、`claimed`，以及一次
  尝试结束的三种方式（`succeeded`、`failed`、`reclaimed`）——在**跟状态变更同一个事务**里挪动
  （`jobq/3.6-transaction-isolation` 就是那个模式），于是一次没发生的写，不可能被数进去。`running`
  是从它们推出来的，而不是存下来的：现在正占着 worker 的那些作业，就是"谁吃了池子"的那个数，也是租户
  上限拿来对照的那个数。
- **一次特权变更，跟它的那一行一起提交。** 声明一个队列和记下是谁动的它，是同一个事务，于是一次记不下来
  的变更，就是一次不发生的变更——在这个引擎里，访问模型是唯一一样"静悄悄的变更比拒绝更糟"的东西。

**配额是 `Policy` 的，往上提一层。** `jobq/3.9-priority-fairness` 限的是一个*队列*；
`Policy::with_tenant_cap` 限的是一个*租户*，按这个租户拥有的队列合计，位置一样、规则一样：找不到空位
的认领什么也不拿，工作留在队列里，尝试次数原封不动。它之所以是那条策略上的一个旋钮、而不是第二条策略，
是因为它就是计数器公布的那个数，被当作天花板用——运维按队列读 `running`，而租户的 `running` 正是上限
压住的那个数。吵闹的租户不是一个队列；它是一个*带着好几个队列的租户*，而一个租户之间共享的池子，天花
板得压在后者身上。

## 作业

脚手架加了三个模块——在你声明它们之前都不参与编译——以及 `migrations/0005_queues_and_usage.sql` 的
一个占位。

### `src/engine/tenant.rs`, `src/engine/authz.rs`, `src/engine/usage.rs`

- **租户**是一个引擎能写下来的名字，受的字母表与长度约束跟队列名一样（`Tenant::parse`），而它不是
  一份凭据：这里不对任何人做认证，调用方就是构造出这个句柄的人；
- **模型**是一个值：`QueueDeclaration`（一个队列、一个属主、一张授权表），规则写成两个函数——
  `visible_to`（这个队列是不是*给*这个租户的队列）和 `allows`（它能做这件事吗）——这样一个存储只问
  一件事，而不必自己去比较属主。`QueueAudit` 是轨迹里的一行；
- **数字**是 `Usage`（五个计数，加上推出来的 `running`）和 `QueueUsage`（报告里的一行）。

### `src/engine/error.rs`

两个**新变体**，不是在既有变体上加字段（`jobq/3.3-library-errors` 把这个枚举已有的形状钉住了）：
`NoQueue { queue }`——没人声明过的队列的答案，也是这个调用方看不见的队列的答案——以及
`Forbidden { action }`，它点名动作，别的什么都不说，因为同一个变体还要回答另一种情况：在那里点出队列，
就会泄漏调用方不该看见的东西。两个都要在 `exit_code` 里有一行。

### `src/engine/policy.rs`

`with_tenant_cap` 和 `max_in_flight_per_tenant`，默认是 `None`：上限是部署要来的，跟按队列的那个
上限一样。

### `src/engine/store/`

四个新的端口方法就是这一步的决定住的地方，它们的文档就是规格读的那份契约：

- `declare_queue(&QueueDeclaration)` — 一个带作用域的句柄为它自己的租户声明一个队列，并且不挪动一个
  已存在队列的属主（转让是运维的门，不是被委托者的门）；已存在的队列需要 `Administer`；模型和它的审计
  行一起提交；
- `scoped(&Tenant) -> Box<dyn Store>` — 租户手里握着的句柄。带作用域的存储跑的每一条语句里都有过滤：
  `enqueue`/`claim`（回答 `NoQueue`/`Forbidden`）、作业的读与了结（`Ok(None)`/`NotFound`）、轨迹、
  那些维护调用（一个作用域在自己的队列里续租、交还、回收），以及那两份报告；
- `usage()` — 这些数字，按队列、按队列顺序：带作用域的存储回答它的租户*拥有*的队列（包括零，于是一个
  运维刚建好的队列在用之前就能看见），不带作用域的则回答它可能被问到的每个队列；
- `audit(limit)` — 关于这个句柄能看见的那些队列的特权决定，最新的在前。

`src/engine/scheduler.rs` 多了运维的三扇门（`declare_queue`、`usage`、`audit`）和 `scoped`，而部署
交给每个租户的 worker 的就是它：worker 手里本来就有一个 `Arc<dyn Store>`
（`jobq/3.7-leases-and-recovery`），所以每个租户一个进程，就是一个 worker 握着一个句柄，而引擎里没有
任何一条路径会从请求里读出一个身份。

### `migrations/0005_queues_and_usage.sql`

这个文件归你，占位里点名了它必须装下的东西：归属、授权、计数器，还有轨迹。它的决定里有两个值占位给的那
几段话：授权表是动作字母表合上的地方（一个 `check`，于是一个拼写错误落在迁移里，而不是落在一个什么都
匹配不到的查询里），而那条*规则*——属主拥有一切，一个授权拥有它点名的，`administer` 覆盖更窄的两个
——应该住在一个有名字的地方（`queue_permissions`），因为持久后端的每一条语句都要问它。计数器对归属表
**没有**外键：它们是关于流量的事实，而归属是关于谁该负责的事实。

### 有些东西故意不变

`claim` 的签名、它发放作业的顺序，以及 `jobq/3.5`–`3.12` 认证过的每一个承诺：不带作用域的存储回答得
跟这一步之前一模一样（正是这一点让前面那些规格、以及每一个从不声明队列的项目继续能用），而 `Engine`
已有的方法一个都没动。

- `kiln run jobq/3.13-queue-authz-attribution` — 六个用例通过：模型作为数据、一个租户对自己队列的
  可见范围、一次授权的触达范围、写好的那套工作负载给出的精确数字、轨迹，以及那个自己起一个容器的用例。
- 在 `app/jobq` 里跑 `KILN_BACKEND=postgres kiln run jobq/3.13-queue-authz-attribution` — 同样的
  用例跑在持久后端上，那里的模型是 schema（两张表加一个视图），而不是一个值。
- `kiln check jobq/3.13-queue-authz-attribution` — 每个 must 闸门都是绿的。
- `kiln check jobq/3.12-dedup-window` — 之前那套仍然通过：这一步加的是门，没有挪动端口已经承诺的东西。

## 陷阱

1. **对别人的队列回 `403`。** 友好的答案是"那不是你的"；而规格比较的是租户在队列存在*之前*拿到的那些
   字节，和存在之后拿到的那些字节，一个会变的拒绝就等于回答了"存不存在"这个问题。队列一级的拒绝是
   `NoQueue`，跟没人声明过的队列拿到的是一模一样的变体、一模一样的消息。
2. **在持久后端上用 Rust 做归属检查。** 读出属主、在调用方那边比较，看起来是一样的，直到两个写者赛跑：
   *行级*过滤必须在查询里（`get`、那些了结、轨迹），因为对外来的作业产生 `NotFound` 的那次检查，就是
   本会把它找出来的那条查询。队列一级的门所问的权限问题，是唯一的例外，端口的文档会说明为什么。
3. **把租户做成存储方法的一个参数。** 很诱人，而它是一个调用方会弄错的租户：`scoped` 是一个句柄，所以
   过滤不可能被某个调用点忘掉——而一个方法接收身份参数的存储，就是一个访问模型取决于每个调用方都传对了
   的存储。
4. **计数器写在改了那一行的那个事务之外。** 一个先提交、再给 `succeeded` 加一的 `complete`，会把被拒绝
   的尝试也数进去：写好的那个用例把一个作业了结两次，并断言那五个数字，而留在拒绝路径上的计数器，会以
   多一个计数让它失败。跟 `jobq/3.6-transaction-isolation` 里的轨迹是同一个形状，理由也一样。
5. **计数器记在引擎里，而不是记在存储里。** worker 里的一个 map 看起来等价，直到第二个进程跑起来：
   运维读到的数字必须是存储的，因为造出这些数字的进程死了之后，活下来的是存储。
6. **把 `running` 做成第六列。** 存下来就意味着一个可能跟另外五个不一致的数——而"谁吃了池子"唯一诚实
   的答案，会因此变成两个答案。它是推出来的（`claimed` 减去一次尝试能结束的三种方式），而这个不变量在
   工作负载那个用例里被断言。
7. **审计行在变更之后才写。** 这一行是让一次变更可以被解释的东西，所以这个后端记不下来的变更就不能发生：
   那个把轨迹表丢掉、再要求一次声明的用例，期望声明失败*并且*模型待在原处。事后补写审计行，前半段能过，
   后半段过不了。
8. **在策略旁边另造一个按租户的配额。** 那样就有两个地方决定一个队列能跑多少，它们会打架，而
   `jobq/3.9-priority-fairness` 的承诺（"超过上限，工作等着，尝试次数原封不动"）被其中一个守着，另一
   个没守。租户的旋钮，就是同一个旋钮往上数一层。

## 延伸阅读

- `relay/2.16-authz-audit` — 矩阵、那三种拒绝，以及动作之前就写下的轨迹：这一步的设计那一半，用在一个
  服务的路由上。
- `jobq/3.9-priority-fairness` — 这一步按租户而不是按队列来计的那个上限，以及为什么超过上限的工作是
  等着、而不是失败的论证。
- [PostgreSQL: `CREATE VIEW`](https://www.postgresql.org/docs/17/sql-createview.html) — 这里的访问
  规则为什么是一个视图：一个每条语句都能读的地方，而不是一个五条语句必须保持一致地重复的 join。
- [PostgreSQL: row security policies](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) — 这个
  项目*没有*选的机制，以及它买到了什么（即使有人手写查询，数据库也照样执行过滤），相比一个带作用域的
  句柄买到了什么（引擎根本问不出错的问题）。
- `jobq/3.17-error-budget-alerts` — 这些计数器在哪里变成运维盯着的那个速率，以及为什么是速率需要计数，
  而不是反过来。
