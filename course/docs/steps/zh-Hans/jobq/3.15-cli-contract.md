# CLI 是一套接口：子命令、退出码、机器可读的输出

## 为什么

命令行是一套没有类型的 API。脚本拿 `jobqc` 做的任何事，编译器都不检查：退出码、答案写到哪条流上、
一个旗标怎么拼、输出是一份 JSON 文档还是一行碰巧含 JSON 的日志——全都住在一个只存在于写脚本那个人
脑子里的约定里。其中哪一条错得不太明显，今天什么都不会坏。坏的是*客户*：把一次拼写错误永远重试下去
的 cron 作业，悄悄读到零的仪表盘，把"已经完成"当成"store 挂了"、于是在凌晨三点把某个人叫起来的部署
脚本。

失败的样子总是同一个形状，而这也是这一步为什么是一份契约、而不是一个功能：一个*看起来*机器可读的
工具，比一个明摆着不是的工具更糟，因为建在它上面的脚本会不再检查。先打一条警告的 `--json`、打完错误
再以 `0` 退出的失败、把用法页打到 stdout——每一样都把真问题变成了三个系统以外的解析错误。

## 回顾

- `err/typed-errors@design`——`jobq/3.3-library-errors`：**退出码表是从哪儿来的。** 那一步给了
  `Error` 两个调用方会据以行动的分类器，`is_retryable` 和 `exit_code`，并把两个二进制已经在用的那些
  数字钉死。这一步继承这张表，而不是另发明一张：`jobqc` 从不计算退出码，它去问失败本身。
- `domain/state-machine@apply`——`jobq/3.14-job-state-machine`：四个状态名，以及 `JobState::parse`
  对一个模型里没有的名字给出的拒绝。`--state failed` 之所以能算一个诚实的过滤器，正是因为一次拼写
  错误是用法错误，而不是一次什么都没匹配到、看起来却像好消息的查询。
- `sec/authz-tenant-isolation@operate`——`jobq/3.13-queue-authz-attribution`：每个队列五个计数器。
  它们就是 `usage` 之所以是一个子命令的原因——运维据以行动的那个数字，必须既能被人读，也能被给他们
  发告警的那个脚本读，而在这一步之前，拿到它的唯一办法是对着库写一个程序。
- `api/library-design@apply`——`jobq/3.2-public-api-baseline`：库的表面就是它再导出的东西，而二进制
  没有自己的语法。那是 `jobq/3.1-engine-boundary` 划下的边界，而这一步正是第二个二进制必须守住它的
  地方。

## 变化

**这里没有一件事跟排队有关。** store、租约、调度和计数器都已经在转；这一步加的是它们的答案拿到一个
*程序能消费的形状*，而这个形状是四个决定：

- **stdout 是答案，stderr 是诊断。** 成功时 stdout 拿着答案，stderr 是空的；失败时 stdout **也是
  空的**，stderr 拿着一句话。这些字节只在一个地方决定——`Outcome` 是库用来回答的那个值，二进制只
  负责把它写出去——因为"记得别打那一行"不是一条规则，是一个指望。
- **一类失败一个退出码。** `0` 有答案，`2` 调用写错了，`3` 问的东西不在，`4` store 拒绝了，`1` 这个
  部署坏了。这些类来自 `jobq/3.3`；新的是每一个*调用方的错误*都在打开 store 之前答掉，所以 `2` 走到
  哪里都只说明脚本自己的问题。
- **`--json` 是一种格式，不是第二条命令。** 它改的只是答案长什么样，别的什么都不改：退出码和诊断加不
  加它都一样，而空答案写 `[]`，不是什么都不写。
- **什么都不提示。** 每一个输入都以旗标或者标准输入到达，缺一个的调用会点名缺的是什么，而一个没被要求
  读标准输入的命令永远不碰它——一个会卡在终端上等输入的工具，就是一个会把它本该喂的那条流水线挂住的
  工具。

有一件事引擎没有，而它是这一步诚实的代价：**`Store::list`**。一个回答"这个队列里有什么"的工具，必须
能够去*问*；另一条路——命令行自己拼查询——是一条绕过引擎、直接伸进这个部署碰巧在跑的某个后端的命令
行。端口因此多一个方法，它回答的顺序就是 `claim` 已经写明的那种顺序，而过滤器带着一个上限，因为队列
没有天然的尽头。

## 作业

脚手架加了 `src/cli/mod.rs`（用法文本、`Outcome` 的形状，以及带一个 `todo!()` 的 `run` 签名）和
`src/bin/jobqc.rs`（外壳，写完了）。**还没有任何东西声明这个模块**：`src/lib.rs` 里的
`pub mod cli;` 是你的第一行，而它不在的时候规格不编译——这就是这一步在说它要什么。

### `src/cli/mod.rs`——语法与两条流

下面这张表里的每一行都必须成立，而规格会跑真正的二进制来检查：

| command | stdout (text) | stdout (`--json`) | code |
| --- | --- | --- | --- |
| `jobqc`, `jobqc --help`, `jobqc -h`, `jobqc help` | 用法文本 | 用法文本 | 0 |
| `jobqc --version` | `jobqc <version>` | — | 0 |
| `jobqc submit --queue Q --payload P` | `queued <id>` | `{"id":"<id>"}` | 0 |
| `jobqc submit --queue Q --stdin` | `queued <id>` | `{"id":"<id>"}` | 0 |
| `jobqc inspect <ID>` | `<id> <queue> <state> <payload>` | `{"id":…,"queue":…,"state":…,"payload":…}` | 0 |
| `jobqc list [--queue Q] [--state S] [--limit N]` | 每个作业一行，形如上 | `[{…},…]` | 0 |
| `jobqc usage` | `<queue> submitted=… claimed=… succeeded=… failed=… reclaimed=… running=…` | `[{"queue":…,…}]` | 0 |
| 调用方弄错的任何东西 | *空* | *空* | 2 |
| 一个不在的作业或队列 | *空* | *空* | 3 |
| 一个拒绝了请求的 store | *空* | *空* | 4 |
| 一个坏掉的环境 | *空* | *空* | 1 |

表里有四个细节是会被人争的，而不是照着敲的：

- **载荷是一个 JSON 值，不是一段 JSON 字符串。** `jq '.payload.to'` 不用先 `fromjson` 就得能跑；
  而在文本形状里，载荷是紧凑 JSON（`serde_json::Value` 自己的 `Display`），这样一个含换行符的载荷
  没法把一条作业拆成两行；
- **字段就是上面写的那个顺序**，两种形状里都是。JSON 不定义顺序，而一个每次重构都重排自己字段的金标准
  测试，是一个没人会读的测试；
- **空列表是 `[]`**，而 `list --limit 1` 是一页一条：一个必须特判"没有输出"的脚本，是一个会弄错一次、
  然后就不再信任这个工具的脚本；
- **`--json` 可以在子命令前面，也可以在后面**，因为脚本和人把它放的位置不一样，而一个得在 `--help`
  里解释放哪儿的工具，是一个接口比它所取代的那个还差的工具。

### `src/engine/store/`——一次读，一个指针

`Store::list(&JobFilter)` 是端口上的新方法：这个句柄能看见的作业，顺序是 `claim` 写明的那种（先优先级，
再到期最久的，最后是身份），上限来自过滤器的 limit，而一个作用域看不到的作业干脆不出现——`get` 和
`events` 早就在守这条规则。`JobFilter` 是三个问题合成的一个值（`--queue`、`--state`、`--limit`），
`DEFAULT_LIST_LIMIT` 是没指定 limit 的调用方拿到的默认页。两个后端都实现它：内存里是 map 上的一个
谓词，SQL 里是一个 `where` 加一个 `order by`。

`impl Store for Arc<T>` 是另一半，而它正是*外壳*需要的东西：daemon 和 `jobqc` 在运行时挑一个后端，
拿一个 `Arc<dyn Store>` 握着，而 `Engine<S>` 对端口是泛型的。一个转发的实现（外加给指针的 `Sealed`），
就是从配置而不是从源码里挑 store 的全部代价。

### `src/service/mod.rs`——`open_store` 变为公开

`jobqc` 说话的那个队列，就是 daemon 排干的队列，而要让这件事成为真的、而不只是有意的，唯一的办法是
两者在同一个地方、用同一组设置项搭出自己的 store。这个工具**也不**做迁移：一个每次读都要写的工具，
会需要一个可写的副本，会为回答一个问题去拿锁。

### 有意不改的东西

`jobqd` 的旗标、它的 `--check-config` 报告和 `draining` 那一行（`jobq/3.1`）、settle 的拒绝和它们的
类（`jobq/3.7`）、`jobq/3.5`–`3.14` 认证过的每一个承诺，以及端口已有的所有东西的签名：一个方法是
*加*进一个封闭 trait 的，而这是端口唯一能长大的方式。

## 完成标准

- `kiln run jobq/3.15-cli-contract` — 六个用例通过，包括那个对着真实数据库提交、查看、列出并报告
  状态的脚本。
- `kiln check jobq/3.15-cli-contract` — 每个 must 闸门都是绿的。
- 在 `app/jobq` 里跑 `cargo run -q --bin jobqc -- --help`——打出用法文本，退出 `0`；而带
  `JOBQ__STORE__URL=memory` 跑 `cargo run -q --bin jobqc -- list --json`，打出 `[]`。
- `KILN_BACKEND=postgres kiln run jobq/3.5-store-port-conformance`——多了一个方法的端口，从两个后端
  回答得仍然一样：`Store::list` 是一个有两个证人的承诺。
- `kiln check jobq/3.14-job-state-machine`——更早的套件仍然通过。

## 陷阱

1. **参数错了以后把用法文本打到 stdout。** 打印它是最友善的做法，也正是看不见 `$?` 的脚本会噎住的
   东西：一条等着文档的流水线，拿到的是一页用法。规格里每一次失败都断言 stdout 是*空的*，而不只是
   断言用了 stderr。
2. **把 `--json` 做成第二条代码路径。** 一条命令两条路径，迟早会漂，而漂的永远是失败处理——JSON 那
   一支自己决定"我序列化不了它，退出 1"。规格把每一个会失败的调用跑两遍，带 `--json` 和不带，然后
   比较退出码和诊断。
3. **手工转义载荷。** `format!("{{\"payload\":\"{payload}\"}}")` 是机器可读的，直到载荷里出现第一个
   引号；从那以后，它就是别人进程里的一个解析错误。端到端用例提交一个带引号、反斜杠和换行的载荷，再
   把它当*值*读回来。
4. **没被要求却去读标准输入的工具。** 不带 `--stdin` 的 `submit` 若去读 stdin，在终端上会永远卡
   住——而挂死是 CI 脚本唯一看不见的失败。只有 `--stdin` 才读载荷，其余每一次运行，规格都给它
   `/dev/null`。
5. **第二个打开数据库的地方。** 二进制里写 `PgPoolOptions::connect` 也能用，直到 CLI 的租约、策略或
   启用的功能跟 daemon 的不一样；那时两个进程就在用两套规则排干同一个队列。这个工具拿 `open_store`
   的答案。
6. **每条命令都跑迁移。** 一个会跑迁移的 `list`，是在读上做写：它要拿锁、要一个可写的副本，还会把
   一个只读部署变成一个坏掉的部署。端到端用例通过库把 schema 准备好，然后指望 `jobqc` 看到它已经
   就绪。
7. **没有上限的列表。** `jobqc list` 背后一条 `select * from jobs`，是一个在队列还浅时能用的工具，而
   一旦队列深了，它就是那次故障。过滤器带着上限，CLI 的默认页是 100，而 `--limit` 是一个数字，不是
   一个指望。
8. **在工具里拿文本比较过滤器。** 用字符串比较来读 `--state Queued`，什么都匹配不到，答案是
   `[]`——而那恰好就是"没有失败的作业"的样子。状态由模型来解析（`jobq/3.14`），所以模型没有的名字
   是一个用法错误，并且会点名它有的那四个。

## 延伸阅读

- [Command Line Interface Guidelines](https://clig.dev/)——这一步所主张的那套纪律，用给人看的话写了
  下来：退出码、两条流、`--json`，以及为什么一个提示符是一个 bug。
- [POSIX: exit status](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)——
  为什么退出码停在 125：再往上是 shell 自己的（`126`、`127`、`128+n`）。
- `jobq/3.3-library-errors`——`jobqc` 读而不是重造的那张表，以及 `--json` 为什么改不了退出码。
- `jobq/3.26-dlq-cli`——这套语法往哪儿长：对死信采取行动的那些命令，守着同样的四条规则。
- `jobq/3.13-queue-authz-attribution`——`usage` 打印的那些计数器，以及部署发给每个租户的带作用域
  句柄：命令行走的是运维那扇门，而一个点名租户的旗标，会是从请求里读出来的身份。
