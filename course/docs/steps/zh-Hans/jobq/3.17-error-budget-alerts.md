# 错误预算，以及值得把人叫醒的告警

## 回顾

- `obs/metrics-slo@apply`——`relay/2.18-delivery-metrics`：**一个投递服务导出的那些数字**，以及塑造
  它们的三条规则——用直方图而不是平均值；gauge 在被抓取的那一刻从队列里读，而不是记着；以及一组
  服务*自己挑*的 label，因为每个 label 值都是每个 collector 里的一条序列。这个队列有同样的三个问题，
  却没有那套实现：它有 `jobq/3.13-queue-authz-attribution` 的计数器，没有的是一个决定——它们*叫
  什么*，以及其中一个动了的时候，一个人该做什么。那个决定就是这一步。
- `obs/structured-logs@apply`——`mailer/1.6-logging`：**一行日志是数据，不是一句话。** collector 从
  里面读字段，这一行所属的那次运行是一个 *span*，而不是一个大家要记得传的参数，而唯一永远不会出现的
  东西是密钥。那一步的行写在一条请求路径上，那里 span 是由框架进入的。这里没有框架：行由 worker 循环
  和它派生出来的异步作业写，而 span 不跟着作业走。
- `delivery/dlq@operate`——`jobq/3.16-dlq-tooling`：**运维在一条告警之后用的那个视图。** 一条说
  "这个队列在丢工作"的规则，只有在下个问题——*哪个作业，为什么*——有答案时才有用，而那个答案是死信
  视图和那次尝试自己说的话。这一步正是两半相遇的地方：样本说有多少，日志行说是哪一个，而演练让两者
  都可复现。

## 变化

**一个计数不是信号，而这一步就是两者之间的距离。** `jobq/3.13` 每个队列数五样东西；一个没人命名的
计数器是表里的一个数字，而一个没人商量过的名字，是一块跟读它的人对不上的仪表盘。缺三样东西，而每一样
都是一句 runbook 拿得住的话：

- **那张表。** 有哪些 family、每个是什么形状、叫什么。一个*计数器*是累积的，所以问它的问题是"多快"
  ——答案是两次读数之差，也就是一条规则的窗口。一个 gauge 是一次读数，而问一个 gauge 涨得多快，是一个
  关于抓取的问题，不是关于队列的问题。这两半都是命名那个决定，而名字就是一条规则写下的东西；
- **样本。** 数字住在 store 里（`jobq/3.13`），日志行住在进程里，而让它们成为一个系统的，是日志行的
  字段*就是* family 的名字。这不是表面功夫：collector 从日志行推导序列，所以进程忘了写的一个字段，就是
  一条不存在的序列；而一个告警页为它写了规则的字段，就是一条永远不会触发的规则；
- **规则。** 光一个阈值不是规则。它需要信号、测量它的窗口，以及故意触发它的那个演练——而演练正是让
  另外三者不止是一段话的那一部分。

**一批失败的预算对*这个*队列意味着什么**，是 `relay/2.18` 答不了的那部分，而它是三个决定：

1. **单位是已经 settle 的那次尝试**——不是到达的那个作业，也不是开始的那次尝试。一个生产者停了的
   队列，失败率是零，而且没有工作；预算讲的是 settle，*正在到达*的是另一个信号，而*卡住的*是 gauge；
2. **一次重试是预算在起作用，一次回收是损失。** 一次失败后被交回来的尝试，花掉作业一次尝试，对队列
   则什么也没花——那是引擎在做它被造出来要做的事。一次以 `reclaimed` 收场的尝试，是没人做完的工作：
   一个 worker 拿着它死了，或者它的租约到期了。这个 crate 里没有任何失败计数器会为这两者动一下，而
   一个只读 `failed` 的预算，会在一整个丢掉它认领的每一个作业的部署里读到 **零**。这是这一步最重要
   的一件事；
3. **低于下限的占比，不是关于一个队列的主张。** 一次尝试里的一次失败，是 100% 的失败率，它同时也是
   一个普通的星期二。一条规则在获准告警之前需要一个分母，而那个下限是页面里的一个数字，不是读它的
   人的习惯。

窗口是从第一个决定里自然得出的第四个：一个计数器从队列被创建那天起就是累积的，所以"失败率"不是一次
读数的性质。它是**两次读数之差**，这就是为什么这段算术拿两次读数，也是为什么每条规则都有一列窗口。

**两种颗粒度，以及为什么两个都要。** 样本回答*多少*：每个队列一行、每个 family 一个字段，在任何
事发之前就是零——一条只在第一次失败之后才出现的序列，恰好在有人检查的那段安静时间里报"没有数据"。
尝试那一行回答*哪个*和*为什么*：队列、作业、尝试、worker、结果、处理函数自己说的话，以及花了多久。
两者谁也不替代谁，而从一边到另一边的那条路，正是一个队列可观测性的全部意义：规则按占比触发，而运维
在日志行里找到那些作业和它们的原因。

**运行是上下文，而异步作业是新的上下文。** `mailer/1.6` 把运行做成一个带 `run.id` 的 span，这样
没有哪个调用点需要记得它。这是一个比它看起来更强的承诺，因为这个进程从三个地方写日志：启动它的
daemon、worker 循环，以及每个作业各自派生出来的那个异步作业。daemon 自己的日志行继承那个 span；
那些异步作业是它*启动*的，什么都不继承——`tokio::spawn` 故意给作业一个空上下文，因为作业比造出它的
那次调用活得久。所以 span 必须放在你派生的东西上，而没有它时的失败样子不是一个错误：是一个部署，
它的尝试日志无法归到写下它们的那次运行上，而那正是运维在事故之后会读到的那一行。

## 作业

脚手架加了两个文件，而**还没有任何东西声明第一个**：

- `src/service/signals.rs`——四个函数体，各带自己的论证，类型都已经在位。把 `pub mod signals;` 接
  进 `src/service/mod.rs` 是你的第一个决定，而在它做成之前规格不编译，这就是这一步在说它要什么；
- `docs/alerts.md`——那一页，还是个存根。它有各个小节和表的列，但目标都是占位符：每个目标都能解析
  之前，`links` 闸门是红的；每条规则都点名了真实的东西之前，规格是红的。

### `src/service/signals.rs`

1. **`signals()`**——那些 family。一条规则能写的名字、一个种类、每条序列都带着的 label，以及一句
   帮助文本。label 集合是切分这些数字的轴，而它跟 `relay/2.18` 就一次投递所做的决定是同一种：队列
   的*名字*是有界的、来自配置的，而一个作业 id、一个 worker 或一个载荷，会变成每个作业一条序列；
2. **`Sample::emit()`**——一次运行报告的那行日志：label，然后每个 family 一个字段。字段列表是字面
   写出来的，因为订阅器索引的就是它，所以那个让名字的两种拼法保持相等的测试，是重点而不是形式；
3. **`Attempt::emit()`**——关于一次尝试的那行日志。每种结果上字段都一样（给一个空的原因，而不是缺
   一个字段，因为一个只在某些时候存在的字段，是一个必须应付它的查询），不一样的是*级别*，`took_ms`
   是一个数字而不是格式化过的时长，而载荷根本不是一个字段；
4. **`Budget::burn_between()`**——两次读数进去，一个窗口出来：每个计数器涨了多少、这些涨幅里哪些
   算在预算头上，以及占比是对着什么量的。

### 接线

四个地方，而每一处都是一个决定，不是一行代码：

- **`logging::init`** 在运行的那个 span 里写下装好订阅器的那一行，而 span 必须在订阅器装好*之后*
  建——从一个不存在的分发器那里领来的 span，是一个没人记录的 span，而每次运行的第一行，就会成为
  它唯一缺的那一行；
- **`service::serve`** 就是那次运行：它启动的两个作业被交到那个 span，因为作业不继承 span。它最后的
  动作是样本：这个部署排干的每个队列一行，从 store 里读，而计数器就住在那里——进程报告的是一个读数，
  不是它自己的寿命；
- **`worker::run`** 把 span 交给每个作业派生出的那条异步作业，理由一样，只是低了一层；
- **`worker::handle_one`** 用一个形状写下两种结局，于是两条路径上的字段不可能不一样。

### `docs/alerts.md`

一张规则表，至少每个 family 一行，每行点名它的信号、阈值、窗口、触发它的演练，以及该做什么。它还
写明演练据以衡量的那份预算：文档用 `Budget::standard()`，而规格拿页面的数字跟代码的数字比——一个
页面说一套、演练量另一套，就是一个已经不再为真的页面，而树里别的任何东西都不会发现。

### 有意不改的东西

`jobq/3.1`–`jobq/3.16` 认证过的每一个承诺：`--check-config` 的那些键、`draining` 那一行、信号的
退出码、CLI 的语法和退出码、端口的签名，以及轨迹。这一步给 daemon 已经在写的日志行加字段，并加一个
它原先没有的模块；它去掉一个字段，还说明了为什么：载荷是那一行的，而日志行是 collector 索引的数据。

## 完成标准

- `kiln run jobq/3.17-error-budget-alerts` — 八个用例通过：规则对着表、页面对着预算、一次真实运行的
  样本、每一行日志上的那次运行、关于一次尝试的那行日志、不在那儿的载荷、不构成损失的那次重试，以及
  低于下限的窗口；
- `kiln check jobq/3.17-error-budget-alerts` — 每个 must 闸门都是绿的，包括 `links`，正是它让那一页
  成为一页，而不是一段话；
- 对着你自己的一个队列启动 daemon
  （`JOBQ__STORE__URL=memory JOBQ__WORKER__QUEUES=emails JOBQ__LOG__FORMAT=json cargo run -p jobq --bin jobqd`），
  再用 `SIGTERM` 停掉它：它打出来的每一行都带着同一个 `run.id`，而最后一行是 `emails` 的样本，
  值为零；
- `cargo test -p jobq --test spec_alerts` — 页面点名的那次演练，可以单独跑；
- `kiln run jobq/3.16-dlq-tooling` — 更早的套件仍然通过：这一步读计数器和轨迹，不改它们。

## 陷阱

1. **只数失败的预算。** 直觉的实现是 `failed / claimed`，而这个队列最严重的一次故障从头到尾，它读
   起来都健康：一个 worker 拿着认领死掉的部署，动的是 `reclaimed`，不是 `failed`。演练的第二个窗口
   正是这种情况，而它指望这份预算被花掉。
2. **一条在没有流量的窗口上告警的规则。** 二十次尝试里五次失败是 25%，而它可能是一个没人用的队列上
   糟糕的一分钟。没有下限，每一个安静的钟点都会告警，而最终真正要紧的那条告警，是没人读的那条。规格
   的最后一个用例把下限的两边都走了一遍。
3. **一条只在第一次失败之后才存在的序列。** 只在计数器非零时才把一个 family 写进样本，是一个自然
   的优化，也正是会弄坏仪表盘的那一个：查询在安静时段显示"没有数据"，而这跟队列挂了分不出来。这个
   部署排干的每个队列，每个 family 都会报出来，值为零。
4. **把 run id 当一个字段传。** 它能用——直到有人加了一行日志、一个模块或一个作业，而忘了传它。这个
   失败不是一个编译错误，是一行归不了属的日志，而它会在几个月之后，出现在运维事故之后做的那一次调用
   上。span 是上下文；字段是习惯。规格读一次真实运行的日志行，指望的是那个 *span*，不是一个字段。
5. **一个过不了 spawn 的 span。** 同一个错误的一行版本：`serve` 加了 instrument，而 worker 自己的
   报告里完全没有 run id，因为 `tokio::spawn` 启动一个作业时给它的是空上下文——而缺的那一行，正是
   worker 的。
6. **在订阅器之前建 span。** 把同一课反着读，也是两者中更安静的那个失败：`info_span!` 从它*被创建*
   那一刻装着的分发器那里领 span，所以早建了一行的 span，是一个永远没人记录的 span——每次运行装好
   订阅器的那一行到来时没有上下文，也没有错误。
7. **时长、载荷或原因的形状错了。** `took = ?started.elapsed()` 是一个像 `1.2s` 的字符串，仪表盘
   得去解析它；而载荷是客户自己的记录：它没有上界，它是某个人的地址，它是运维在找别的东西时顺手撞见
   的东西。日志行点名作业；其余的一切都在那一行里。
8. **页面和演练对不上。** 页面是有人在凌晨三点读的东西，演练是触发规则的东西；如果页面写 99%，而
   演练量的是 99.9%，那这个页面错的方式，要花掉一个下午。规格比较这两个数字，谁也不信。
