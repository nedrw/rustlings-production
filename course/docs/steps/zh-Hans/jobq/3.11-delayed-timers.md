# 延迟作业：等待期间不花一分钱的定时器

## 为什么

这个 worker 到目前为止的每一轮，都以同样的方式收场：什么也没找到，睡一个轮询间隔，再来问一遍。这是一个
好默认，也是一个坏习惯——不管有没有安排任何东西，每个队列每一轮都被问一次，永远如此；而一个一秒钟后有
一个作业到期的队列，和一个明年有一百万个作业到期的队列，代价是一样的。

让这件事成为*设计*问题、而不是调参问题的失败模式，是这些工作的形状：一个作业大多在未来的调度器——02:00
的报表、一小时后的重试、每周一次的导出——几乎把每一轮都花在询问还做不了的工作上。加上副本，它还会翻倍：
十个 worker 各自轮询，就是每个间隔每个队列十次查询，而数据库每次的回答都是"还没到"。

另一半才是微妙的地方。显而易见的修法——睡到下一个作业的 `run_at`——好坏全看它睡在上面的是哪个答案，而
那个答案，是某一个进程对一张别的每个进程都在写的表拍下的快照。这一步讲的是记住那个截止时间，同时让轮询
间隔当它的底部，于是唤醒能早就早、能省就省，而且永远不比它取代的那个循环更晚。

## 回顾

- `time/clock-injection@apply` — `jobq/3.8-clock-injection`：这个引擎里的每个时刻都来自递给它的那只
  时钟，正是这一点让"这个作业两小时后到期"变成一个几百毫秒就跑完的用例，而不是一场两小时的测试。
- `db/atomic-claim@design` — `jobq/3.7-leases-and-recovery`：认领、租约，以及把一行放回它的队列的
  回收。这些就是挪动截止时间的事件，也是这里这个结构为什么是存储答案的缓存、而不是真相的来源。

## 变化

`sched/fairness@design`（`jobq/3.9-priority-fairness`）回答的是有好几个作业到期时*谁*先跑，而
`sched/cron@apply`（`jobq/3.10-cron-schedules`）回答的是一个被安排的*时刻*是哪个。两者都没碰这一步的
问题：worker 拿中间那段时间做什么，以及它花多少。

故意**不**放在这里的东西是：sleep 调用不是这一课，一个配置旋钮也不是。这一课是那个*集合*——每个有工作的
队列一条记录，记着这个队列下一次变得可认领的时刻——因为正是它，把"一百万条排到一年后的作业"从一百万次
唤醒，变成六十四条记录、每轮每个队列一次查询。一个存着作业本身的结构，只能靠读那些作业来喂，那不过是多
占些内存的轮询循环。

## 作业

- 给引擎加上 `ReadySet`（`timers` 是一个 `pub(crate)` 模块，跟其他模块一样重新导出）：
  `insert(queue, at)` 记下某个队列的下一件工作在一个时刻到期，并*替换*它之前欠的那条；
  `remove(queue)` 忘掉一个不欠任何东西的队列；`next_deadline()` 回答其中最早的那个；`len()` 数的是
  队列。
- 问存储那个就绪集合唯一需要答案的问题：`Store::next_due(queue)` 返回这个队列**排着队**的行里最早的
  `run_at`，或者 `None`。它要放进端口、而不是某一个后端，因为 worker 手里是一个 `dyn Store`，两个
  后端都得回答它——内存后端是一次扫描，持久后端是在认领已经在用的那个部分索引上求 `min(run_at)`。
- 接上 worker：一轮什么都没找到时，逐个问每个队列下次什么时候有工作，然后等到这些时刻里最早的那个——
  `ReadySet::wait(now, floor)`。让 `WorkerSettings::poll_interval` 当**底部**：截止时间可以让 worker
  更早去看，绝不能更晚，于是一个没人告诉过这个 worker 的队列仍然会被轮询，而一个过时的截止时间，代价是
  一轮，不是一次卡死。
- 把 worker 用来量的那只时钟交给它（`Worker::with_clock`，默认是 `SystemClock`），因为这次等待是两只
  墙上时钟的时刻相减，而一个自带时钟的 worker，就会成为 `jobq/3.8-clock-injection` 专门要消掉的那个
  第二权威。

## 完成标准

- `kiln run jobq/3.11-delayed-timers` — 六个规格用例通过：结构自身的行为、六十四队列上的十万个截止
  时间、等待表，以及两个端到端用例。
- `kiln check jobq/3.11-delayed-timers` — 每个 must 闸门都是绿的，包括 `slow:conformance@2`（规格在
  两个后端上都跑，因为 `next_due` 是一个端口方法）和 `semver@baseline`（表面多了名字）。
- 最该读的是那个端到端用例：轮询间隔十秒的 worker，在 200ms 内了结了一个到期的作业，远在一个纯轮询的
  worker 达不到的截止时间之内。

## 陷阱

1. **每个*作业*一条记录。** 一个装着所有已安排作业的 `Vec<Job>`，就是分配得更大的轮询循环：它得靠读
   那些行来刷新，大小随队列深度变化，而这一步的承诺——代价是队列，不是作业——没了。
2. **只记录截止时间，不应用它们。** 一个队列的下次到期时刻，在它被认领、提交、回收或重试时会被替换；
   一个把每个新答案都塞进去、旧答案还留着的结构，报的是一个已经不归任何人的时刻，于是 worker 为一份没人
   会递给它的工作醒来——而且每认领一次，内存就涨一截。
3. **忘了那个不欠东西的队列。** 存储给的 `None` 必须*删掉*那条记录，而不是把上一个时刻留在那里：留着
   一个过时截止时间的 worker，会睡过一秒钟后才提交的作业。
4. **一觉睡到截止时间。** 截止时间是一张别的进程在写的表的快照，答案两个方向都可能错；底下没有底部，
   一个过时的答案就变成一个一小时不再被问的队列。底部是优化和一种新失败模式之间的差别。
5. **对一个已经到来的截止时间等零。** 到期却没被认领的工作，是被时钟以外的东西按住了——一个按队列的上限，
   或者中间把行取走了的另一个 worker——为它立刻轮询，是一个空闲 worker 在对着存储空转。
6. **读一次存储，然后就永远信它。** 答案缓存进一个 worker 自己的结构里，而缓存的新鲜度只到上一轮为止：
   这个进程之外任何挪动截止时间的事，在底部走完之前都看不见——底部为什么不能谈，原因正好在这里。
7. **用墙上时钟量等待，用单调时钟睡。** 截止时间是一个墙上时钟的时刻，而等待是一个间隔：在两者之间换算
   需要注入的时钟，一个用 `SystemTime::now` 来换算的 worker 又成了第二权威——`clippy@3` 会拒绝这个
   调用，而那是这个陷阱便宜的那一半。

## 延伸阅读

- `tokio::time::sleep` 和 `tokio::time::sleep_until` — 等一段时长和等一个时刻之间的差别，以及这里的
  循环为什么只把其中一个换算成另一个一次。
- `std::collections::BinaryHeap` 和 `BTreeSet` — 这一步在两者之间选一个；先读复杂度表，再读一条被取代
  的堆记录会怎样。
- 哈希时间轮与分层时间轮（Varghese 和 Lauck，*Hashed and Hierarchical Timing Wheels*）— 内核如何拿到
  `O(1)` 的定时器，以及它为此刻意付出的固定分辨率。
- `jobq/3.10-cron-schedules` — 一个不是"现在加重试间隔"的截止时间从哪里来。
- `jobq/3.8-clock-injection` — 为什么这次等待是拿递给 worker 的时钟来量的，以及一个测试拿它能做什么。
