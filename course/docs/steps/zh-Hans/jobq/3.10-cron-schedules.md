# cron 表达式：扛得住夏令时的下次运行推算

## 为什么

"每晚 02:00 跑一次"，是队列被要求得最多的一句话，而它是一句关于*墙上时钟*的话——麻烦正是从这里开始的。
诚实的答案会变：某个政府改了规则，改在一个没人记得的日期，改在一个进程根本不在的时区里。

有两种做错的方式，而且在变贵之前都看不见。第一种是维护一张下次运行时间戳的表：四十条计划变成四十行，
每次部署之后都得有人去更新，而他们忘掉的那一行，就是客户吃早饭时读的那份报表。第二种是每分钟醒一次问
"到点了吗？"：对一条计划来说足够便宜，而对一队大多数时候无事可做的 worker 来说，就是每分钟每条计划
一份固定开销。

能绕开这两者的推算很小——一个问题，问的是一个表达式和一个时刻——而它一年里恰好有两天，答案不细心就会差
一个小时，或者整整少跑一次。这两天就是这一步。剩下的全是语法：一条计划允许说什么、什么会被拒绝，好让一个
拼写错误变成提交时的一条消息，而不是一个在错误的小时上跑了一年的作业。

## 回顾

- `time/clock-injection@apply` — `jobq/3.8-clock-injection`：引擎通过端口读时钟，正是这一点让"下次运行
  是什么时候"成了一个从时刻到时刻的函数，而不是一件测试得等的事。
- `sched/fairness@design` — `jobq/3.9-priority-fairness`：当有好几个*到期*的作业时，下一个跑哪个。

## 变化

上面两个决定的，都是已经到期的作业。这一步说的是那个时刻本身：一个表达式是什么意思，它指出的下一个时刻
又是哪个。有三件事是故意**不**放进来的，每一件都是必须有人大声做出来的决定：

- **你错过了哪几次。** 一条计划回答的是 `next_after(t)`。"我们停了三天，欠了哪些？"是一项策略——每一次
  都补、只补最近一次、补一次外加吞掉了几次——而一个替人回答它的库，等于替那个有上下文的进程（运维、
  面板、事故）做决定。想要补齐的调用方自己去写循环；上限该写在循环里。
- **秒、年和名字。** 五个字段，只要数字，没有 `JAN`，没有 `MONDAY`，没有 `@daily`。一个多接受一点的
  方言，就是一个让每个调用方都得猜引擎到底实现了哪一部分的方言。
- **睡着的那个 worker。** 这些时刻在哪里变成一个唤醒——以及为什么代价是每个*队列*一条记录、而不是每个
  作业一条——是 `jobq/3.11-delayed-timers` 的事。

## 作业

- 一个类型 `Schedule`，由引擎重新导出（`cron` 是一个 `pub(crate)` 模块，跟 `src/engine` 里其他模块
  一样）。用 `Schedule::parse` 读一个表达式，用 `Schedule::in_zone` 指定时区——一个 `Europe/Berlin`
  这样的 IANA 名字；数据库里没有的名字会被拒绝，而不是悄悄取默认。
- `Schedule::next_after(after) -> Option<DateTime<Utc>>` 就是全部 API。答案是一个绝对时刻，严格晚于
  被问的那个时刻；`None` 的意思是"永远没有"——`0 0 31 2 *` 是合法的写法，所以搜索有一个边界，并且
  拒绝假装自己有答案。
- 两个日期字段取并集：`0 0 1 * 1` 在 1 号*或者*每个周一跑，规则看的是两者中哪一个写成了 `*`。crontab
  本来就是这个意思，而这一步的全部用意，就是一条在别处写好的计划，搬过来之后仍然按它作者预期的方式跑。
- 在模块文档里、在规格的消息里，把两条夏令时规则都写清楚，因为没有一个对所有人都对的默认：被时钟**跳过**
  的那一刻，那一天就不发生；被时钟**重复**的那一刻，会发生两次——从这两个里的第一个再问
  `next_after`，回答的是第二个。
- 语法里没有的东西就拒绝，并且说清是哪个字段：不是五个字段、值超出了字段的范围、范围写反了、步长为零、
  一个既不是 `*`、`N`、`N-M`、`*/S` 也不是 `N-M/S` 的项。

## 完成标准

- `kiln run jobq/3.10-cron-schedules` — 十二个规格用例通过，包括两个夏令时的日子，以及依次从每个答案
  再问一次的走查。
- `kiln check jobq/3.10-cron-schedules` — 每个 must 闸门都是绿的，包括 `clippy@3`（新模块是库代码：
  不许 `unwrap`，不许索引，每个可失败的调用都要有一个 `# Errors` 小节）和 `semver@baseline`（表面多了
  名字：`Schedule`、`parse`、`in_zone`、`next_after`）。
- `cargo test -p jobq --test spec_cron` 离线运行，只要几毫秒：没有时钟，没有存储，没有容器，因为一条
  计划就是算术。

## 陷阱

1. **把两个日期字段做 AND。** `0 0 1 * 1` 于是变成每月跑一次而不是每个周一跑，而这个 bug 安静的那个版本，
   是一条客户为别的 cron 写的计划，搬到这个引擎上之后，一年还是只跑十二次。规格正是因此从两边都断言了
   并集。
2. **在 UTC 里做推算，却去别处读时区。** `0 9 * * *` 在每个时区都在 09:00 UTC 触发：代码看起来是对的，
   只用了一个时区的测试通过，而两个时区的那个用例失败。
3. **留偏移量，丢了时区。** 一个固定的 `-05:00` 从十一月到三月是对的，从三月到十一月差一个小时——而那
   正好是没人去看的那段时间。
4. **把被跳过的时刻按"同一时刻，加上那段空档"跑掉。** 在纽约的钟从 02:00 跳到 03:00 的那天，
   `30 2 * * *` 变成在当地 03:30 跑一次：一个表达式从没点过的时刻，由本该避免意外的代码发明出来。
5. **只处理重复的那一小时的一半。** 返回第一个 01:30，然后跳到第二天的，一年会悄悄少跑一次，任何日志里
   都没有一行；而从某个答案再问时返回*同一个*时刻——比较里那个经典的差一——会让一个 worker 永远在
   同一个时刻上触发。
6. **搜索没有边界。** `0 0 31 2 *` 是一个合法表达式，而它指向的时刻根本不存在：一个一直找下去的循环，
   就是一个再也回不来的 worker，而这个 bug 现形的样子，是一个挂着不动的进程，和一个人人都不怀疑的配置
   文件。
7. **把未知的时区默认成 UTC。** `Europe/Berlim` 会让作业一年里都早跑五个小时，而唯一的症状，是一份比
   它的输入先到的报表。
8. **接受 `*/0`。** 步长为零什么也不指向，于是关于这条计划的每个问题都要跑到边界、回答 `None`：一条悄悄
   为空的计划，比一条解析不过的计划更糟。

## 延伸阅读

- `crontab(5)` — 并集规则和"`7` 就是周日"那种写法都出自这份 man page；读它的时候，看看这一步故意拒绝的
  那些部分。
- `chrono` 的 `LocalResult` 和 `TimeZone::from_local_datetime` — 一个本地时间能有的三种答案，包括
  夏令时用例用的那两种。
- `chrono_tz::Tz` 和它背后的 IANA 时区数据库 — 一个时区是一个名字加一部偏移量的历史，所以这一步要的是
  名字，不是数字。
- RFC 5545（`RRULE`）— 同样的问题，语法大得多，夏令时那两天也一样；在任何人把一条计划存成一条规则之前，
  它跟 cron 不一致的那些地方值得先了解。
- `jobq/3.11-delayed-timers` — 这些时刻在哪里变成一个 worker 睡在上面的结构，以及为什么等待的代价是
  队列的数量，而不是作业的数量。
