# 发布：带版本的产物、校验和，以及一份不用别人重新拼的 changelog

## 为什么

这个项目到目前为止被要求做到的一切，问的都是一个已经在跑的进程：一次认领、一份租约、一次状态迁移、一条告
警。**发布**是这个项目第一次把东西交给一个不在这里的人，而传过去的是一个有名字的文件、里面有一个版本号，以
及——如果没人另做决定的话——没有任何东西说明那些字节是不是完好地到了，或者它们里面改了什么。

这些失败写下来很便宜，撞上很贵。`PATH` 上的那个二进制，不是它的 `--version` 说的那个，因为打包进去的是一次
过期的构建，而 tag 说的是一个意图，不是那些字节。一个镜像或者 CI 缓存发出来的，是上个季度用这个名字的那个
文件，因为一个不带版本号的名字就是一个缓存键。一份 bug 报告写着 `0.4.0`，而没人分得清是哪个 `0.4.0`：三个
tag 动过，changelog 是值班的那个人拿 `git log` 拼出来的。一份让人用眼睛去比的校验和文件，是一份没人去查的
校验和文件。

这些没有一件事跟队列有关。它是你做出来的东西和别人能*用*的东西之间的差别，也是这一步为什么是一个工具，而
不是 wiki 里的一段话。

## 回顾

- `ci/pipeline@apply`——`mailer/1.3-ci`：一条流水线是一串命令，要么给出一个绿的结果，要么失败，而这正是这
  一步在一个作业之后下的同一个注。边界是：流水线跑的是*你的代码*，而这里是它末尾的那个作业，发布的是*一个
  文件*。下面那个工具不跑编译器，也不跑测试——它拿到构建产出的东西，判断那是不是 tag 点名的发布。也正因如
  此，它能在任何一个没有 CI runner 的 shell 里彩排。
- `api/library-design@apply`——`jobq/3.2-public-api-baseline`：那一步的见证文件以一句话结尾，而这一步让它
  成真——破坏性变更是允许的，但代价是在 `Cargo.toml` 里抬一个大版本，**外加** `CHANGELOG.md` 里的一行。
  semver 闸门读的是前一半；这一步写的那个文件是后一半，而发布工具会拒绝发布一个版本，如果它的章节缺了、空
  了，或者还挂在 `Unreleased` 底下。
- `cli/contract@apply`——`jobq/3.15-cli-contract`：你在这里加的第三个二进制，受那一步那张表的约束，而不是
  一张新表——每个失败类别一个退出码，答案在 stdout，诊断在 stderr，而一个它看不懂的参数是一个点名那个参数的
  用法错误。退出码是脚本据以分支的承诺；发布工具的拒绝，按 `jobq/3.3-library-errors` 写的那些类别回来。

## 作业

脚手架加了一个模块、一个二进制、一个装置、一个页面桩子和一个 changelog 桩子。**还没有任何东西声明这个模
块**：接上 `src/engine/mod.rs` 是你的第一个决定，在做出它之前，规格和装置都编译不过。

### `VERSION`、`TAG_PREFIX`、`CHECKSUMS` 和 `BINARIES`——那些事实，只写一次

`VERSION` 是 `CARGO_PKG_VERSION`，在编译时读出来：在这个项目里，manifest 是唯一写版本号的地方，而这个字符串
的第二份拷贝，就是会过期的那个拷贝。`TAG_PREFIX` 是 `v`，`BINARIES` 是 `jobqd` 然后 `jobqc`——发布列出它们
的顺序。`CHECKSUMS` 是 `SHA256SUMS`，每个读校验和文件的工具本来就在找的那个名字。

### `digest(bytes)`——SHA-256，因为这个文件是给别人读的

一份校验和文件，是和已经存在的那些工具（`sha256sum -c`、某个包管理器、某个容器 registry）之间的一份约定，
所以算法不是可选的：就是 SHA-256 的 64 个小写十六进制字符。这个 crate 用脚手架特意为此加上的 `sha2` 依赖，
而替代方案——在这个模块里手写一个哈希——是那种错到没人察觉、直到真要紧的时候才现形的代码。规格钉住两个公开
的测试向量（`digest(b"")` 和 `digest(b"abc")`），好让"它算了个哈希"没法冒充"它用 SHA-256 算哈希"。

### `Artifact`——一个名字，以及它为之作保的那些字节

发布里的一个文件，由 `Artifact::of(name, bytes)` 拿着字节本身造出来。`digest()` 是这个文件自己的，`len()`
是它有多重，而模块外面没人能拿一个名字和一个想法造出一个来。字节故意和它住在一起：校验讲的是下载下来的东
西，而一个改成带路径的类型，会让每一次检查都变成第二次文件系统读取，带着它自己的失败模式。

### `Release::of(tag, target)`——tag 就是版本，而名字把两件事实都带上

`Release::of("v0.1.0", "aarch64-apple-darwin")` 给出一个发布：它的 `tag()`、它的 `version()`、它的
`target()`、它写进去的 `directory()`（`jobq-0.1.0-aarch64-apple-darwin`）、它带的 `binaries()`，以及它
随附的 `checksums()` 文件。三种拒绝，按读者会脱口说出的顺序：不以 `v` 开头的 tag 不是这个项目的 tag
（`refs/tags/v0.1.0` 是一个*引用*，不是一个 tag）；版本不是这个 crate 的 tag，是别的东西的发布（在 `0.1.0`
的树上打 `v0.2.0`）；而这两者也都不是一个调用点可以自己拼出来的名字——这就是工具收 tag 而不是收版本号的
原因。

发布目录名里的版本号不是装饰：同一个版本给两个 target 的两次构建是两个文件，而一个只带了这两件事实中一件
的名字，是镜像随时可以拿去和另一个搞混的名字。

### `accepts(name, output)`——二进制得说它就是这次发布

给一个二进制为 `--version` 打印出来的文本，回答它是不是这次发布的版本。版本是**第一行的最后一个词**——
`jobqd 0.1.0`——所以第二行（一条警告、一个构建戳）不算在里面，而一行里没有版本，是拒绝而不是匹配。正是这
项检查抓住了拿过期构建拼出来的发布，也是这个工具为什么要*跑*它即将发布的东西，而不是相信递给它的那个目
录。

### `checksums(artifacts)`——一个文件，不是一个哈希

每个产物一行 `<digest>  <name>`，**两个空格**，按名字排序，每行都以换行结尾，而空集合是一个空文件，不是
一个坏文件。两个空格和排序顺序，是 `sha256sum -c` 读的文件和人读的文件之间的差别：一个 tab，是让
`sha256sum -c` 答 `no properly formatted checksum lines were found` 的文件；一个没排序的文件，让对同一个
发布的两次运行产出两个不同的文件；而缺掉最后那个换行，会让 `while read` 把最后一个产物丢掉。校验和文件
**不是**它自己的产物：一份把自己也包进去的清单，拿来检查不了任何东西。

### `verify(manifest, artifacts)`——两个方向都查，或者都不查

每个产物都必须有一行写着它的摘要，**而且**每一行都必须点名一个就在这儿的产物。后一半是那个没人注意到的：
一份许诺了一个没人构建过的文件的清单，看起来就像一份清单，而消费这个发布的机器，会在很久以后、在别的地方
失败。一个变了的字节是 `ChecksumMismatch`，带着文件名和两个摘要——一份只说"这个发布坏了"的报告，会把读者
打发去手工解开它。一个不在清单里的产物，是一个没人检查过的文件；而一份空清单，不是关于任何东西的证据。

### `changelog_ok(changelog, version)`——关于它自己的交代

三条规则，按读者会注意到的顺序：这个版本有自己的一节（`## [0.4.0]`，或者 `## 0.4.0` 后面跟着任何东西；
而一个 `###` 标题不是一节）；这一节说了点什么——在下一个标题之前，至少有一行既不是空的、也不是注释；而它
上面没有留下任何注记，因为一个仍然*装着*条目的 `## [Unreleased]` 标题，意味着这次发布没有把它们提升上去，
于是它发布的那个版本没有说清随它出去的是什么。顶部一个空的 `## [Unreleased]`，正是发布过的树所保留的样
子。

这条规则讲的是文件的结构，而不是文本：一个在 `Unreleased` 底下的条目里*提到*的版本，不是一节，而一个 grep
`0.1.0` 的检查器，会让一份什么都没说的 changelog 通过。这也是 `jobq/3.2-public-api-baseline` 那句话里闸门
读不到的那一半——"破坏性变更的代价是抬一个大版本、并在 `CHANGELOG.md` 里写一行"是对读者的承诺，而那一行
是这一步的活。

### `Refusal`——那些拒绝，以及它们留下的退出码

一个枚举，装下发布可能被拒绝的每一种方式，配一个点名文件、行或版本号的 `Display`，而不是说
"invalid release"：tag、版本、报告了别的东西的二进制、缺失或读不了的输入、校验和文件的两个方向，以及三种
changelog 拒绝。它叫 `Refusal` 而不叫 `Refused`，是因为 `jobq/3.24-unsafe-budget` 已经把 `Refused` 并进
了 `jobq::engine`，两个名字不能共用一条路径；这个位置的探题（`course/probes/release-artifacts.apply.rs`）
把自己那个独立的枚举拼成 `Refused`，那是夹具里的差别，不是规则里的差别。`exit_code()` 把各个变体映射到
`jobq/3.3-library-errors` 写下的那些类别——`2` 是调用错了（不是这个项目的 tag、另一个版本的 tag），`3` 是
问的东西不在那儿（一个不在发布制作用目录里的二进制），`1` 是这个部署坏了（一个报告了另一个版本或跑不起来的
二进制、一份和它的文件对不上的清单、一份没有交代这个版本的 changelog）。

### `src/bin/jobq-release.rs`——工具

```text
jobq-release --tag v0.1.0 --target aarch64-apple-darwin --from target/release --out dist
```

每个旗标都是必填，除了 `--changelog`，它默认是 `CHANGELOG.md`，按工作目录解析。它按顺序做的事：拒绝一个
不是这个 crate 版本的 tag；拒绝一个缺失的二进制；拿 `--version` 逐个跑那些二进制，拒绝一个没报告这次发布
的；拒绝一份没有交代这个版本的 changelog；然后把两个二进制和 `SHA256SUMS` 写到 `<out>/<directory>/` 里，
并打印校验和文件的那几行，好让一条流水线日志显示发布了什么。它**不**构建任何东西：发布构建是
`cargo build --release`（或者流水线自己的那一步），而一个会编译的工具，是第二次构建、第二套旗标。`--target`
也不去猜，理由和 tag 不让人敲两遍一样：这次发布的名字是一个决定，而一个去推断它的工具，就是一个会悄悄发错
东西的工具。

### `CHANGELOG.md`, `docs/release.md` 和 `tests/release_harness.rs`

changelog 交代的是出去的是什么：顶部是 `## [Unreleased]`，然后每个发布过的版本一节，最新的在前，各自
写着改了什么——这个项目的第一个发布是 `0.1.0`，而它的那一节，是用户遇见的那个项目，不是一列提交。页面是一
个人照着走的流程（`docs/release.md`）：一次发布由什么组成、那些命令、用户怎么检查自己下载的东西，以及这
个作业在流水线里坐在哪儿。装置是课程的仪器（`tests/release_harness.rs`）：它拿这棵树刚构建出来的二进制跑
那个工具，打印下面那些计数，而改它的学习者，就是改测量的学习者——`kiln reset jobq/3.25-release-artifacts`
会把它放回去。

### 规格判什么

| the case | the claim |
| --- | --- |
| `the_tag_is_the_version_and_nothing_else` | `v0.1.0` 是这个项目的 tag，`0.1.0` 不是 tag，`refs/tags/v0.1.0` 是一个引用，而另一个版本的 tag 按那种情况被拒绝 |
| `the_name_carries_the_version_and_the_target` | 目录名把两件事实都带上，两个版本或两个 target 不会撞，两个二进制按发布列出它们的顺序排，而校验和文件不在它们之中 |
| `a_checksum_file_is_the_format_a_tool_reads` | 两个空格、排过序、64 个小写十六进制、末尾有换行、空就是空——以及两个公开的 SHA-256 向量 |
| `verification_is_both_directions` | 一个变了的字节点名文件和两个摘要；一行没有对应文件的清单，是一次不完整的发布；一个没列出来的文件从没被检查过；而一份重排过的清单仍然校验通过 |
| `a_binary_that_does_not_report_the_release_is_refused` | 第一行的最后一个词是版本；第二行不是；不像版本的东西，是拒绝 |
| `the_changelog_has_to_account_for_the_version` | 缺掉的一节、空的一节、还留在 `Unreleased` 底下的注记、正文里提到的版本——对照一次提升过的、能通过的那一节 |
| `the_tool_writes_the_release_the_tag_names` | 真的二进制、真的 changelog：目录、三个文件、一份拿复制过去的字节跑校验的清单，以及工具打印的那些行 |
| `a_from_directory_without_the_binaries_is_refused_and_named` | 缺失的文件被点名，退出码是 `3`，而什么都没写 |
| `the_tool_wants_files_it_can_run` | 该是二进制的地方放了一个目录，以及一个读起来没问题、却跑不起来的文件：两个都按名字被拒绝，退出码 `1` |
| `the_tool_refuses_what_it_cannot_release` | 一个点名那个参数的用法错误、一个缺失的旗标，以及另一个版本的 tag——连同它们留下的退出码 |
| `a_release_that_cannot_be_written_is_this_machine_and_not_the_release` | 一个建不出来的输出目录是退出码 `1`，和一句说明什么没做成的话 |
| `the_project_ships_a_changelog_that_accounts_for_this_version` | 这棵树自己的 `CHANGELOG.md` 说清了 `0.1.0` 是什么，没留下任何占位 |
| `the_page_states_the_release_the_tool_produces` | `docs/release.md` 点了两个二进制、校验和文件、changelog 和 tag 的名，里面没留下 `TODO` |

## 完成标准

- `kiln run jobq/3.25-release-artifacts` — 十三个用例通过。
- `kiln check jobq/3.25-release-artifacts` — 每个 must 闸门都是绿的。要读的是 `links`（页面和 changelog
  都是项目的页面，它们的目标得能解析到）、`semver@baseline`（这一步往表面上加名字，一个都不删）和
  `unsafe-budget@0`（`sha2` 是安全代码；预算仍然是零）。
- `cargo build --release && cargo run --bin jobq-release -- --tag v0.1.0 --target <your target>
  --from target/release --out dist` — 打印每个二进制一行 `<digest>  <name>`，并写出
  `dist/jobq-0.1.0-<target>/`。然后 `cd dist/jobq-0.1.0-<target> && sha256sum -c SHA256SUMS`（macOS：
  `shasum -a 256 -c SHA256SUMS`）说两次 OK，而这就是这个格式的全部要点。
- `cargo test -p jobq --test release_harness -- --nocapture` 打印 `jobq-budget artifacts=2`、
  `jobq-budget checksum_lines=2`、`jobq-budget unverified_max=0` 和 `jobq-budget extras_max=0`。
- `cargo run --bin jobq-release -- --tag v0.2.0 --target <your target> --from target/release
  --out dist` 以 `2` 退出，并说清这棵树是哪个版本——这就是一个发布作业在 tag 和 manifest 对不上时该撞上
  的那次拒绝。

## 陷阱

1. **在调用点拼 tag。** 工具里、流水线的 YAML 里和页面里各一个 `format!("v{version}")`，是一个字符串的三份
   拷贝，而会过期的那份，是 tag 里的那份。版本住在 `Cargo.toml` 里，`VERSION` 在编译时读它，而 tag 是拿去
   和它*核对*的，不是从它拼出来的。
2. **校验和文件里有个 tab。** `sha256sum` 写的是两个空格；编辑器、YAML 块或者格式化工具常常写一个 tab，而
   `sha256sum -c` 随后答 `no properly formatted checksum lines were found`。这个文件是给别人工具用的，不
   是拿来读的。
3. **只查一个方向。** 拿你手上每个文件去对清单，会让一份缺了一行的清单通过，而缺的那一行，正是别人马上要下
   载的那个产物。清单点名一个没人构建过的文件，才是会到达用户那里的失败。
4. **哈希名字，而不是哈希字节。** 对路径、对产物的名字、或者对名字加长度算出来的摘要，是一种改个名就变、
   而一个损坏的下载却照样通过的校验和。摘要是对读到的那些字节算的，而规格的测试向量说的就是这件事。
5. **一份把自己列进去的清单。** `SHA256SUMS` 里的 `SHA256SUMS`，什么都检查不了：这一行写下去的时候，文件
   自己的摘要就变了。两个文件加一份清单，才是那个形状。
6. **用 `starts_with` 读 `--version`。** `jobqd --version` 打印 `jobqd 0.1.0`；检查*名字*的写法，后面跟
   什么版本都通过，而检查 `contains("0.1.0")` 的写法，会放过一个报告 `0.1.0-rc1-broken` 的二进制。版本是
   第一行的最后一个词，别的都是拒绝。
7. **过期的构建。** 在 `cargo build --release` 之后用 `--from target/debug`，打包进去的是昨天的二进制，而
   文件里没有任何东西说这件事：版本检查是 tag 和一个对自己撒谎的文件之间唯一的东西。这也是工具为什么要拒绝
   一个它*跑不起来*的二进制。
8. **靠改标题把 `Unreleased` 提升上去。** 在留在 `## [Unreleased]` 底下的那些注记上面写一个
   `## [0.1.0]`，得到的是一次发布，它的章节是空的，而它的注记属于另一次发布：工具查的是那一节，不是版本字
   符串。
9. **靠 grep 查 changelog。** `changelog_ok` 找的是一个小节*标题*；一份在正文里、或者在 `###` 子节里提到
   版本的 changelog，已经发布了一个数字，却没交代里面有什么。
10. **改装置或者基线。** `tests/release_harness.rs` 是课程的文件，
    `course/tracks/jobq/budget/3.25-release-artifacts.toml` 是闸门读的那份拷贝：改其中任何一个，改的是仪
    器，不是这次发布。`kiln reset jobq/3.25-release-artifacts` 会把装置放回去。
11. **一个只有命令、没有理由的页面。** `links` 查的是目标能不能解析到，规格查的是名字是不是代码里的；两
    者都没法告诉你，这个页面有没有解释*为什么* tag 和清单必须一致。这个页面是写给凌晨三点、眼前摆着一个失败
    作业的发布者的。

  和 `Unreleased` 标题，包括六种变更里读者指望找到哪几种。
- [Semantic Versioning 2.0.0](https://semver.org/) — 一个版本号对表面许下什么，也就是 `semver@baseline`
  和它的见证文件所守住的那一半承诺。
- [GNU Coreutils: `sha256sum`](https://www.gnu.org/software/coreutils/manual/html_node/sha2-utilities.html)
  — 这一步所写的那个格式，包括为什么分隔符是两个空格，以及 `--check` 接受什么。
- [`cargo-dist`](https://opensource.axo.dev/cargo-dist/) — 一个真正的发布工具在这之上还做什么：归档、安装
  器、每个平台一份清单，以及它填好的那个 GitHub 发布。读它是为了清单的形状，不是为了把它加进来。
- [The Cargo book: environment variables](https://doc.rust-lang.org/cargo/reference/environment-variables.html)
  — `CARGO_PKG_VERSION` 和 `CARGO_BIN_EXE_<name>`，这一步的代码和它的规格从构建里而不是从一个字符串里读
  的那两件事实。
- `course/probes/release-artifacts.apply.rs` — 同样的规则做成一个没有依赖的文件，其中的摘要是 FNV，因为
  探题用不了 `sha2`，而那个 tarball 从来不构建。读它是为了看清这一步加了什么：真的字节、真的二进制、真的
  哈希。
- `course/tracks/jobq/budget/3.25-release-artifacts.toml` — 闸门读的基线，以及它跑的命令。
- `course/tracks/jobq/spec/3.25/release.rs` — 那十三个用例写成的测试。
- `jobq/3.22-bench-budget` — 这一步那四个计数所沿用的装置写法，以及它们为什么是计数而不是秒。
- `jobq/3.15-cli-contract` — 第三个二进制沿用的那些退出码，以及关于 stdout 和 stderr 上放什么的规则。
- `mailer/1.3-ci` — 那个流水线作业，而这个工具就是它的载荷。
