# 死信：什么卡住了、为什么，以及再给它一次生命

## 回顾

- `delivery/dlq@apply`——`relay/2.10-dlq`：**这个队列的死信是从哪儿来的。** 那一步决定了什么时候一次
  投递算完了、而不只是迟到了——尝试次数用完，或者订阅者答了某种任何重试都改不了的东西——并且让那一行
  保持可查询，而不是消失。一个作业今天在同一个位置：`failed` 是一个状态，预算就是把它写进去的东西，而
  行不会自己动。**那一步没有定下的是：回去这一步该由谁来决定，而这一步讲的正是这个**——它在回去时重置
  的那个计数，正是两个队列必须给出不同答案的唯一一处，原因在下面。
- `domain/state-machine@apply`——`jobq/3.14-job-state-machine`：**模型在这里故意没有一步可走。**
  `transition` 是全函数，而 `succeeded` 和 `failed` 吸收所有事件：一个作业的生命结束之后，不管到达的
  是什么，它身上什么都不会发生。这不是重放的障碍，它就是重放的形状——事件是发生在生命*之内*的东西，
  而运维的一次重放开启的是另一个生命。这一步不给那张表加一行，而一个因此多出一行的 `transition`，会让
  "我的作业完成了"和"有人又给了它一次机会"变成同一个答案。
- `db/transactions@design`——`jobq/3.6-transaction-isolation`：一次 settle 改那一行、并追加描述它的一
  行日志，**在同一个事务里**，所以重构一次事故的运维，不会遇到一行和一个对不上的轨迹。一次重放就是那个
  形状的一次 settle：持久后端里一个事务，内存后端里一个临界区。
- `time/clock-injection@apply`——`jobq/3.8-clock-injection`：store 的时钟是"现在"的唯一权威。一个被重
  放的作业，**在 store 的时钟读到的那个时刻到期**，而这个时刻是交给决定的，不是在决定内部读的——否则
  一个时钟被固定的部署，重放起来就是非确定性的，而持久后端的 `now()` 会变成第二个权威，那正是上一步
  存在要除掉的东西。
- `sec/authz-tenant-isolation@operate`——`jobq/3.13-queue-authz-attribution`：**句柄就是身份。** 一个
  带作用域的 store，只为它模型里点名的队列作答，而一个它看不见的作业，得到的答案跟没人写过的作业一样。
  一次重放跟别的每一次调用一样走那扇门："我能把谁的死信放回去"这个问题，由调用方握着的那个句柄回答，
  而不是由它传的参数回答。

## 变化

**运维想*读*的一切都已经在端口上了；缺的是回去的那条路。** 引擎放弃的一个作业，是 `failed` 里的一行，
而运维对这样一行会问的三个问题，今天都能回答：哪些行（带状态过滤的 `Store::list`，
`jobq/3.15-cli-contract`），具体是什么死了（`last_error`，尝试计数器），以及它是怎么走到那儿的
（`Store::events`，`jobq/3.6` 的轨迹）。所以要建的不是一个死信 *store*——而是一个给这个视图的名字、
一个关于这次移动的决定，和一个把它兑现的方法。新东西有三样，而每一样都是一句 runbook 拿得住的话：

- **死信队列是一个视图，不是一张表。** 一封死信就是 `failed` 里的一行，别的什么都不是，所以通向这个
  队列的接口，是*同一个 store* 回答一个更窄的问题。把死信拷进一个它们自己的集合——名字暗示的形状，
  也是第一版实现会伸手去拿的那个——会让同一个作业有两行：副本的载荷会变旧，一次重放得同时搬两行，
  而运维读到的是一个不再是那个队列的队列。`dead_letters()` 就是那个视图作为一个值，于是一条命令、
  一块仪表盘和一个测试问的是同一个问题，而不是各自用自己的方言写 `state = 'failed'`。
- **一次重放是第二个生命，而模型说这件事的方式，是它没有对应的一行。** `transition` 拒绝在一个失败的
  作业上 `claim`（`jobq/3.14`），这是对的：这次移动不是发生在作业身上的事，它是关于一个已死作业的
  决定。这就是为什么这里是一段算术、一个值 `revived(job, now)`——*一次重放写什么*——而不是一个
  事件、一条 SQL 语句，或者命令行里的一个分支。它之所以是公开的，理由跟 `transition` 一样：一条调用
  方能*问*的规则，是一条能被证明写错了的规则，而一个工具可以在做任何事之前，回答"这次重放会做什么？"
- **端口多一个方法，而它是唯一的写者。** `Store::replay(&JobId)` 拿重放写下的那一行作答。它在端口上
  而不在某个工具里，是因为两个后端对一次重放必须回答得一样——这正是端口存在的全部理由
  （`jobq/3.5`）——而一个自己拼 `update` 的工具，会是第二份算术，第一次动到其中一份时就会漂。

**一次重放逐字段写下什么。** 一封死信，是计数追上了上限的作业，而一次重放是"再给它一次机会"。下面这
六个决定就是这一步：

| field | after a replay | why |
| --- | --- | --- |
| `state` | `queued` | 作业*出生*时所在的状态：第二个生命从第一个开始的地方开始 |
| `attempts` | **不变** | 计数是这一行的历史，而一次重放不会把一次真的发生过的尝试退回去 |
| `max_attempts` | `attempts + 1` | 动的是上限，因为计数是事实、上限是策略：多一次机会，而且恰好一次 |
| `run_at` | store 的时钟 | 运维要它跑，而做出这个决定的那一刻，属于 store 的时钟 |
| `last_error` | **不变** | 运维第一个问题的答案；让它过时的是*成功*的一次尝试，而清掉它是 `complete` 的事 |
| 租约 | 清空 | "没有哪个第二生命继承一次认领"是重放的性质，而不是作业死在哪儿决定的性质 |

行上其余的一切——身份、队列、载荷、优先级——都还是原来的样子。最后一项值得一句话：一个写进来时紧急的
作业，回来时依然紧急，而一次把优先级重置掉的重放，会是一个没人做过的调度决定。

**动的是上限，而不是把计数重置，而这是 `relay/2.10-dlq` 和这个队列唯一回答得不一样的地方。** 那一步
在回去时把 `attempts` 归零，对它的表来说那是对的：一次投递有一张 *lives* 表，所以它的历史以行的
形式活了下来，而计数是当前这个生命的。一个作业只有一个计数器、一条轨迹。把计数器归零，会是在引擎会读
的一列里撒谎——`may_retry`、列表、一个队列报告的那些数字——而且它还会弄丢一行：一行的身份是
`(job, kind, attempt)`，所以一个从零计数重放两次的作业，会追加第一次重放已经写过的那一行，而历史会说
它只被重放过一次。

**每一次重放都留下一行，别的什么都不动。** `jobq/3.6` 的轨迹是知道这一步会来才写下的——一个事件种类
是 `#[non_exhaustive]`，因为"一次重放、一次清理，以及一次有人取消的运行，都是运维必须能读到的事件"
——所以一次重放追加 `EventKind::Replayed`，点名这个作业被放回来时已经花掉的尝试次数，跟行在同一个
事务里。一次*被拒绝*的重放什么都不追加，因为什么都没发生：这一行在那儿，是为了让"这个之前被重放过
吗？"有个答案，而一个只是被问过一句的作业，正是这条轨迹绝不能由之构成的用例。哪个计数器也不动——队列
的报告数的是工作（submitted、claimed、succeeded、failed、reclaimed），而一次重放不是工作；跟上来的
那次尝试，才是一次认领会数的东西。

**一次重放拒绝什么，又被什么拒绝。** 只有一封死信有第二个生命。别的任何东西回来都是
`Error::Invalid`，点名作业所在的状态，因为一个 `queued` 或 `running` 的作业本来就欠着一次尝试——重
放它，等于在一件还没死透的工作上放第二次认领——而一个被再给一次机会的 `succeeded` 作业，是一个没人
要的重复。另外两种拒绝是端口自己的，在这里是继承来的、不是现发明的：一个句柄看不见的作业，得到的答案
跟没人写过的作业一样（`Error::NotFound`，`jobq/3.13`），而一个句柄看得见、却不能从里面 `claim` 的
队列，是点名那个动作的 `Error::Forbidden`——把工作放回一个你不许从里面取工作的队列，是别人的决定。

## 作业

脚手架加了一个模块：`src/engine/dlq.rs`。**还没有任何东西声明它。** 接线 `src/engine/mod.rs` 是你
的第一个决定——`jobq/3.13` 对 `authz`、`tenant` 和 `usage` 用过的形状，就是该照抄的那个——而在它
做成之前规格不编译，这就是这一步在说它要什么。

### `src/engine/dlq.rs`——视图与决定

两个函数，而上面这段论证就写在模块自己的文档里。

`dead_letters()` 是视图作为一个值：一个状态为 `failed` 的过滤器，于是"什么卡住了"是一条规则、一种
拼法。它的上限是列表的默认页——队列没有天然的尽头，而想要更多的运维会要更多。

`revived(job, now)` 是那个决定：重放要写的那一行，或者说这个作业没有第二个生命的拒绝。它拿时刻，
而不是读时钟，而它回的 `Error::Invalid`，消息**点名作业所在的状态**——运维手上已经有身份了，需要的
是知道它是什么状态，因为"这个作业是 `queued`"和"这个作业是 `succeeded`"是两个不同的错误。这是这个
crate 里唯一决定上表那六个字段的地方，两个后端都调它：内存 store 本来就有那一行，持久 store 在锁下
把它读出来，而两者都不许对答案有什么自己的看法。

### `src/engine/store/`——一个方法，两个承诺

`Store::replay(&JobId) -> Result<Job, Error>` 是端口上的新方法，而让它成为*端口*方法的两个承诺，
就写在它的文档里：**行是在锁下读出来并做出决定的**——持久后端里是 `for update`，内存里是 store 自己
的临界区——所以同一瞬间重放的运维不可能两个都被告知自己搬动了一个作业；以及**状态变化和它的轨迹行是
一个事务**，所以行和日志行一起提交，或者都不提交。两个后端都实现它，`impl Store for Arc<T>` 像其他
方法一样转发它，而 trait 的封闭方向不变：这是一个*加*进端口的方法，而这是端口唯一能长大的方式。

持久实现是更有意思的那一个，它的形状就是 `jobq/3.7` 的 settle：在锁下读那一行，问引擎（通过
`revived`）它该去哪儿，写下行和日志，提交。两种拒绝都按运维会问的顺序问：一个这个句柄看不见的行，用
其他每一次读都带着的作用域过滤器去找，于是它回的是"不在"；而一个不是死信的行，在任何东西被写下*之前*
就被 `revived` 拒绝——一次调用、一句消息，没有任何语句去决定引擎没有决定的事。写本身带着
`state = 'failed'`，这是把决定写成谓词而不是写成一个消息：行已经锁住，所以它匹配不到一个在决定底下
移动过的行，而一次什么都没匹配到的写，是 store 的失败，不是调用方的错误。

### `EventKind::Replayed`

新的种类、它存下来的名字（`replayed`——迁移、查询和某个人的 `grep` 都认的那个字符串，也是
`src/engine/events.rs` 拼出的第四个名字），以及持久后端对它的解码。最后一样是容易忘的那一半，而它
产出的失败正是陷阱 5 讲的那个。

### 有意不改的东西

`jobq/3.5`–`jobq/3.15` 认证过的每一个承诺：settle 的拒绝和它们的类、认领的顺序、内存语义、`jobqd` 的
配置报告和它的 `draining` 那一行、CLI 的语法和退出码，以及端口已有的所有东西的签名。`jobq/3.14` 的
模型不多一行，schema 不多一张表（一封死信是 `jobs` 里的一行），CLI 也不多一条命令：这一步是一个工具
*对着*写的那套接口，而建在它上面的命令必须守住 `jobq/3.15-cli-contract` 的四条规则。

- `kiln check jobq/3.16-dlq-tooling` — 每个 must 闸门都是绿的，包括那个把同一份规格对着两个后端跑的
  一致性闸门。
- `KILN_BACKEND=postgres kiln run jobq/3.5-store-port-conformance` — 多了一个方法的端口，从两个后端
  回答得仍然一样。
- `kiln run jobq/3.14-job-state-machine` — 更早的套件仍然通过：这一步用那个模型，不改它。

## 陷阱

1. **把计数重置。** 重放时 `attempts = 0`，是 `relay/2.10-dlq` 给的答案，也是这一行绝不能给的：
   `may_retry` 于是说一个作业有它从没花过的尝试次数，运维的计数器开始对不上，而同一个作业的*第二次*
   重放，会追加第一次已经写过的那一行——一段关于一个被重放过两次的作业、却说"重放过一次"的历史。规格
   把一次重放走两遍，然后比较尝试次数和轨迹的长度。
2. **把看法留在心里的重放。** 不动 `max_attempts`，会让一个作业下一次失败时，从 `failed` 直接又回到
   `failed`，而什么都没跑：认领的 `attempts >= max_attempts` 不是一个模型看得见的谓词，于是这一行
   干脆再也不会被分发出去。规格认领被重放的作业，并断言它正在跑的那次尝试，比杀死它的那个计数多一；
   再断言第二次失败会花掉新的预算。
3. **第二次重放真做了点什么。** 一个超时之后重试自己命令的脚本，绝不能开启第二个生命。这里一次*幂等*
   的重放，不是一次无声的成功：作业现在已经是 `queued`，所以拒绝点名那个状态，而行和轨迹就停在第一次
   重放留下的地方。规格调它两次，比较整行、整条轨迹和这个队列的数字。
4. **一个不在那儿的谓词。** `update jobs set state = 'queued' where id = $1` 会把一个*成功*的作业
   搬回队列，而唯一拒绝它的是 `and state = 'failed'`——一个写成谓词、而不是写成消息的决定。规格重放
   一个 queued、一个 running 和一个 succeeded 的作业，指望每一个都被它自己状态的名字拒绝。
5. **一行写得进去、却读不回来。** 把种类加进枚举，却没加进持久后端的解码，会留下一条读起来没问题的
   轨迹，直到有人重放了点什么：那时 `events()` 回的是
   `store: replayed is not an event this engine knows`——而且是在事故*之后*运维才做的那一次调用上。
   规格在两个后端上都通过端口把轨迹读回来。
6. **数据库的时钟。** SQL 里的 `run_at = now()` 是数据库对现在的看法，而
   `jobq/3.8-clock-injection` 之所以存在，是因为时间上的第二个权威迟早会跟第一个不一致。规格注入一个
   停住的时钟，停在任何墙上时钟都到不了的时刻，并断言被重放的行在*那个*时刻到期——还断言一次认领
   （它只看 `run_at` 已经过去的行）立刻就把它取走。
7. **先读那一行，再写它。** 事务之外的两条语句——一条 `select` 来做决定，然后一条 `update` 来写——
   是能通过本文件里每一个测试、却在生产里输掉竞态的形状：在两者之间，另一个运维的重放搬动了那一行，
   而第一个人的写，给它加了一个由已经变过的计数算出来的上限。队列于是分发了一次它并不欠的尝试——认领
   会取走任何到期的 `queued` 行，而预算是 *settle* 读的东西——于是作业最后停在 `failed`，花掉的
   尝试次数比给它的上限还多。锁不是装饰；是它让"我先看了一眼，然后我写了"成为同一个动作。
8. **日志行放在第二个事务里。** 一行动了、一行没动，正是 `jobq/3.6` 建这条轨迹要防的那种不一致，而在
   有人从两者重建一次事故之前，它是看不见的。持久后端通过它已经握着的那个事务来追加，那正是 settle
   路径们用的模式。
