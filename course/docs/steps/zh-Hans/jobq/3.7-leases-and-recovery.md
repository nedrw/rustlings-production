# 租约、续租与崩溃恢复：没人会不小心把同一个作业跑两遍

## 回顾

- `db/atomic-claim@apply` — `relay/2.5-atomic-claim`：认领是一条语句，`for update skip
  locked` 就在给行盖章的 update 里面，而被盖章的那一行带着一个持有者和一个时刻。整个形状可以搬过来，
  精神不变：这里的 `Store::claim` 在计入尝试的同一条语句里盖上 `lease_owner` 和
  `lease_expires_at`，而端口的顺序承诺，正是 `jobq/3.5-store-port-conformance` 已经要求两个后端都
  遵守的那一条。新的是项目其余部分拿这个持有者做什么——而这就是这一步的全部。
- `async/graceful-shutdown@design` — `relay/2.15-shutdown-leases`：一次停止是一个*顺序*，而其中有意
  思的部分不是信号。被告知要停的 worker 停止**认领**，在截止时间内做完在途的工作，再把被截止时间截断
  的那些交还回去——一次没人注意的发布和一次看起来像故障的发布，差别就在于那一行是现在就还回去，还是等
  一个租约。这里的顺序一样，进程不一样：没有 HTTP 那一半，整个排干就是一个对着队列的循环。

## 变化

引擎终于能*跑*一个作业了——而推迟到这一步的六件事，就是这一步：

- **worker 循环有了。** `jobq/3.1-engine-boundary` 给了守护进程它的进程形状，
  `jobq/3.5-store-port-conformance` 给了它一个持久化存储，而在此之前，两者之间没有任何东西真的做过
  事：`jobqd` 通告自己在排干，然后等一个信号。这一步就是那个循环——认领、把作业交给一个 `Handler`、
  结算它——而 `open_store` 里那条缝（就是拿一句“循环还没写”拒绝持久化 URL 的那条）因为循环有了而
  消失。
- **一次认领就是一份租约，行上也这么写。** 两个列，而每一次写入都变成以它们为条件。要紧的是*结算*：
  `complete` 和 `fail` 从 `jobq/3.1-engine-boundary` 起就接收一个 worker 名字，却从没看过它。从这
  一步起，它们要求那一行的 `lease_owner` 仍然是这个 worker，而这挡住的正是那个值得一说的意外：一个
  worker 被杀，它的行被回收、被别人认领，然后*第一个* worker 回来了，把它结算掉——它拿着作业 id，
  那一行在运行中，只有租约说这不是它那一次尝试。
- **续租是同一个承诺的另一半。** 一个比租约还慢的处理函数不是 bug；在它身下过期的租约才是。worker 在
  自己的处理函数运行期间续租，用一条语句续它持有的那些行，而租约长度是一个*设置项*
  （`worker.lease_seconds`），因为正确的值是这个部署的取舍：比运维愿意等待的最慢一次尝试更长，比他们
  愿意接受的恢复更短。
- **没人看着的那次尝试照样计入。** 崩溃的 worker 的行带着它的尝试次数回到队列，预算用尽时变成
  `failed`——和 `fail` 用的是同一条规则。不计入它，一个见谁杀谁的载荷就会被永远重试下去：预算是这个
  项目里唯一能结束一个作业的东西。
- **运维那一半是一个数字和一个名字。** `Report` 统计一次运行认领、结算、回收和交还了多少，守护进程在
  退出途中把它们记进日志；行上留着持有者的名字，那是运维凌晨三点会 grep 的东西。这是这个 track 里第
  一步，*对一次事故的回答*是一行记录加上两个设置项，而不是一段 stack trace。
- **时钟偏移，正是由时刻而不是由持有者来裁决的原因。** 租约的结束时刻由引擎的时钟算出，并绑定进语句
  （`jobq/3.8-clock-injection` 会让这只时钟变成可注入的，也是这个文件里的 `Utc::now()` 调用得到一条
  缝的地方）。回收用的谓词是 `lease_expires_at <= now`，于是一个时钟快了一秒的 worker，不会把自己的
  行输给一个时钟慢了一秒的 worker：行上带着*持有者*写下的那个时刻，所有人都对着它比。

## 作业

脚手架加了两个文件，其余都是对你已经拥有的文件的修改。

### `migrations/0003_leases.sql`

`jobs` 上加两列：`lease_owner text` 和 `lease_expires_at timestamptz`，没人持有作业时两者都是
null。文件归你；关于它有两个决定：

- 回收的谓词是 `state = 'running' and lease_expires_at <= now()`，这是每个 worker 每一轮开始时都会
  跑的查询——就是它值得一个索引，而且应该像 `jobs_claimable` 那样是部分索引；
- 别的都别动：租约是一对列，不是一个状态。

### `src/service/worker.rs`

脚手架交来了词汇——`Handler`、`WorkerSettings`、`Shutdown`、`Report`、`Worker`——和一个 `todo!()`：
那个循环。按它描述的那一轮把它实现出来：

1. 从每个配置过的队列**认领**最多 `batch` 个作业，并计入统计；
2. **每个作业在自己的作业里处理**，在它完成的地方结算：成功就 `complete`，失败就 `fail`，带上处理
   函数自己的话。结算走 `crate::engine::retry`，用 `DEFAULT_ATTEMPTS`——结算跑在一个可能被拒绝的
   隔离级别上（`jobq/3.6-transaction-isolation`），而重试是调用方在这一决定里负责的那一半；
3. **续租**这个 worker 持有的租约，在工作旁边起一个定时器（按租约的一半续一次，于是要丢掉两次，认领
   才会失效），并给失败的续租记一笔日志：那是同一个作业跑两遍之前，运维能得到的唯一警告；
4. 每一轮、认领之前，先**回收**一个已经不在的 worker 留下的东西：正是这一行，让一次崩溃变成一次
   延迟，而不是一次丢失的作业；
5. **排干**：信号结束认领；在途的工作拿到 `shutdown` 去完成；被截止时间截断的作废并交还，而报告说明
   各有多少。

### `src/service/handler.rs`

每次尝试一个程序，载荷走标准输入，退出状态就是裁决（零是完成，其他任何值都是一次失败的尝试，原因就是
这个状态）。有两个决定值得说明：程序的输出是*继承*来的，而不是被捕获的（这样处理函数不会因为写满管道
而把守护进程锁死）；而排干截止时间过去时仍在跑的子进程，由一个 `Drop` 杀掉——丢掉一个作业不会运行它
自己的任何清理，所以杀必须发生在值离开作用域的地方。没有设置 `worker.handler` 时，守护进程的默认处理
函数会记录作业，并把它结算为成功。

### `src/engine/store/`

端口长出循环需要的那些方法，而每一个都是两个后端都守着的承诺：

- `migrate`——因为守护进程现在每次启动都会起一个持久化存储，而
  `jobq/3.5-store-port-conformance` 的夹具从那时起就一直在调这个方法的实现。内存存储回答
  `Ok(())`。
- `renew(worker)`——延长*这个* worker 持有的那些租约（别的都不碰：一个能续任何人认领的 worker，能让
  一次不属于它的尝试永远活着）。
- `release(worker)`——把这个 worker 还拿着的东西交回去，尝试次数保留，租约放掉。排干截止时间用的
  就是它。
- `reclaim_expired()`——每一行租约已经用尽的记录都回到 `queued`，预算用尽时回到 `failed`，尝试次数
  保留，轨迹里多一行 `reclaimed` 记录。

持久化后端把后两个各写成**一条语句**（一个修改数据的 `with`，把行搬走、把它们的轨迹记录插进去，一起
完成），理由 `jobq/3.6-transaction-isolation` 已经给过：决定和描述它的那行记录，要么是一次写入，要么
就是谎话。`claim` 在计入尝试的那条语句里盖上租约；`complete` 和 `fail` 在各自的守卫里加上
`and lease_owner = $worker`。

### `src/engine/domain.rs`, `src/service/config.rs`, `src/service/mod.rs`

- `Job` 长出 `lease_owner()` 和 `lease_expires_at()`——那一行必须能通过端口*读得到*，否则这些列
  只有 SQL 看得见（字段清单变长，访问器不改动原有的东西，而 `#[non_exhaustive]` 就是为这个准备的）。
- `worker.lease_seconds`（默认 60，为零拒绝）和 `worker.handler`（一个程序加它的参数；为空拒绝），
  两个都由 `--check-config` 各占一行报告。
- `serve` 用那个租约打开存储，在 `store.migrate` 说该迁移时迁移它，建好处理函数，跑起 worker，并把
  `SIGTERM` 变成 worker 自己的信号。`draining` 那一行和退出码都没有变——
  `jobq/3.1-engine-boundary` 钉住了两者，而且它是在 worker 跑起来*之后*才打印那一行，好让那个词
  名副其实。

## 完成标准

- `kiln run jobq/3.7-leases-and-recovery` — 整套用例在内存存储上全绿：那个循环、交还、一份过期的
  租约、迟到 worker 被拒绝的结算，以及续租。
- 在 `app/jobq` 里 `KILN_BACKEND=postgres kiln run jobq/3.7-leases-and-recovery` — 同样的五个，加上
  需要第二个进程的五个：作业跑到一半时 `kill -9`、被崩溃耗光的预算、带着在途作业的信号、一个排干截止
  时间，以及 `jobqd` 排干一个它真能共享的队列。这就是 `conformance@2` 闸门按每个后端重复一遍的那次
  运行。
- `kiln check jobq/3.7-leases-and-recovery` — 每个 must 闸门都是绿的，包括 `images` 和
  `semver@baseline`。
- `kiln check jobq/3.6-transaction-isolation` 和 `kiln check jobq/3.5-store-port-conformance` — 更早
  的那两套用例在两个后端上仍然通过：这一步往端口上加东西，并把 `migrate` 挪到它上面，没有挪动端口已经
  许下的承诺。
- `JOBQ__STORE__URL=memory JOBQ__WORKER__LEASE_SECONDS=1 cargo run --bin jobqd`，然后
  `kill -TERM
  <pid>`：进程打印排干那一行，以 0 退出，而退出途中的日志行带着一次什么都没做的运行的计数，因为当时
  没有事可做。

## 陷阱

1. **只检查 `state = 'running'` 的结算。** 每个关于正常路径的用例都通过，然后一个被杀、被回收、被
   替换掉的 worker 回来，结算了别人的尝试：那一行在运行中，id 也对得上，守卫里却没有任何东西说“不是
   你的”。`a_late_worker_cannot_settle_a_job_it_no_longer_holds` 以
   `expected Error::Invalid, got
   Ok(())` 失败，而它守住的台账，正是一次投递和两次投递之间的差别。
2. **忘了续租。** 处理函数比租约慢，于是在它还在被处理的时候，行上的时刻已经过去了——下一个 worker
   发现一行“被遗弃”的记录，把它搬回去并认领：一个作业，两次尝试，两个处理函数，日志里没有一行说明这
   一点。续租那个用例以
   `the row went back to Queued while its worker was still handling it` 失败。
3. **续租一切，而不是续租你持有的。** 没有 `lease_owner = this worker` 过滤的 `renew`，会让*另一
   个* worker 的认领永远活着，而这恰恰把这一步要防的崩溃藏了起来——它和没有过滤的 `release` 是同一
   个错误，后者会把一次此刻正在运行的尝试放回队列，让第三个 worker 拿走。
4. **只把行搬回去的回收。** 承诺的一半是尝试计数：一行回来却没有计入它的尝试，就是一个杀掉自己 worker
   的载荷，被一遍遍重试，直到有人注意到。另一半是预算：一次总是回答 `queued` 的回收，永远不会让作业
   死掉，于是一个毒丸载荷长生不死。`a_job_whose_attempts_are_spent_is_not_handed_out_again` 看着
   一个没人让它失败过的作业死掉。
5. **等租约的排干。** 正确，而且慢：每一次发布都把在途的作业藏起一个租约那么久，于是一次本该只花几秒
   的部署看起来像一次故障。退出途中调用 `release`，才能把它变成
   `the job went back to the queue`——`the_drain_deadline_hands_the_job_back` 就是这个用例，而断言
   里*没有持有者*。
6. **排干时还在认领。** 一个等排干时继续转轮次的循环，会揽下自己完不成的工作。信号结束的必须是*认
   领*，不只是这一轮：`a_signal_drains_without_claiming_again` 在信号之后马上写一个作业，并期望它
   仍然是 `queued`，一次尝试都没花。
7. **等待子进程，而不是轮询它。** 守护进程必须能在排干截止时间放弃一个处理函数，所以等待必须可被打断
   （在循环里 `try_wait`，或者一个带 kill-on-drop 守卫的 `tokio` 进程）。处理函数里阻塞式的
   `wait_with_output` 会把排干截止时间变成一句建议：`the_drain_deadline_hands_the_job_back` 随后会
   挂住，直到用例写的那个脚本跑完，于是一个本该两秒的测试要花三十秒。
8. **用两个不同的租约构建存储和 worker。** 存储盖上时刻，worker 在它之前续租；一个把两者分开设置的
   部署，是一个续租总是来得太迟的部署，而唯一的症状就是陷阱 2 的那个。守护进程只有一个设置项
   （`worker.lease_seconds`），并且出于这个理由把它同时传给两边。

## 延伸阅读

- [PostgreSQL: `SELECT … FOR UPDATE SKIP LOCKED`](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)
  — `claim` 建在它上面的那个子句，以及一次不是租约的认领为什么会把一行搁浅。
- [PostgreSQL: `UPDATE … FROM` and data-modifying `WITH`](https://www.postgresql.org/docs/17/sql-update.html)
  — 是什么让 `release` 和 `reclaim_expired` 各自只有一条语句，而不是两次可能互相打架的写入。
- [`tokio::task::JoinSet`](https://docs.rs/tokio/1.53.1/tokio/task/struct.JoinSet.html) — `spawn`、
  `join_next`、`abort_all`：排干就是用这三个调用写成的；中止一个作业，会对它持有的东西做什么（以及
  不做什么）。
- [`std::process::Child::try_wait`](https://doc.rust-lang.org/std/process/struct.Child.html#method.try_wait)
  — 怎么看着处理函数的进程，而不阻塞那个必须随时准备放弃的线程。
- [Kubernetes: pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination)
  — `SIGTERM`、`terminationGracePeriodSeconds`，以及它们背后的 `SIGKILL`：排干正在赛跑的那个截止
  时间，以及租约必须短到能起作用的原因。
- `relay/2.15-shutdown-leases` 的 `src/lease.rs` — 同样的三个操作（回收、交还、那个顺序），为单个
  服务而写，前面还站着一个策略引擎。
- `src/service/worker.rs`、`src/service/handler.rs` 和 `src/engine/store/postgres.rs` — 那个循环、
  两个处理函数，以及租约住在里面的那些语句。`tests/support/service.rs` 是进程级用例用来读守护进程的
  夹具。
