# 把覆盖率当策略：必须走到的分支

## 为什么

每个构建都能打印一个覆盖率数字，而它打印的通常是错的：一个盖住整个 crate 的单一数字，被那些没人
争论的模块主导——接线、为了让某个类型能被命名而存在的适配器、把设置项变成 store 的 `main`。那样的代码
是真的被覆盖了，而它把评审真正针对的那个模块淹掉了。

把百分比读对之后剩下的，才是花钱的那一半：没人走过的分支。一个没有用例触发的错误分支，会让那个函数
的每一条*行*都被覆盖，而它一半的决定没被行使过，编译器分不出这跟一个想过的套件有什么不同。没有人从
仪表盘上发现它；他们是从一次没人写过的告警里知道的，因为活是决定哪些地方必须走到，然后在一个能被
评审的地方把它说出来。

这一步就是那个决定，写在编译器能拿住你的地方：这个项目的引擎有哪些地方、其中哪些必须被一个用例走到、
哪些谁也走不到，以及为什么阈值不是一百。

## 回顾

- `test/mutation@apply`——`jobq/3.20-mutation-threshold`：一个套件*察觉*什么。两个数字互补，谁也不
  替代谁——一个变异体活下来，是因为没有用例*察觉*那个改动；而一个分支保持未覆盖，是因为没有用例*到达*
  它。一个套件可以到达每一个分支、却什么都没察觉；它也可以察觉它到达的一切，而队列三分之一的决定从没
  被行使过。**这一步不重讲那个分数。** 新的是关于哪些地方存在的主张，以及这个主张被拿来对照的阈值。
- `err/typed-errors@design`——`jobq/3.3-library-errors`：错误分支是这份清单主要讲的那些，因为一个
  带类型的错误就是一个决定（一个 `Err` 分支接一个 `Err` 分支），而没人给它写用例的那些分支，恰恰是
  生产最先遇到的。

## 变化

四个名字，而每一个都回答一个百分比回答不了的问题：

- **`Kind`**——行和分支，是关于同一段代码的两个不同问题。只有第二个描述套件。
- **`Inventory`**——那个主张。它讲的是*一个模块*，而它拒绝一个来自别处的地方，而不是长成一张覆盖
  整个库的表。那个拒绝正是这一步存在的全部理由：一个盖住整个库的百分比，是一个关于 `main` 的百分比。
- **`Exempt` 与上限**——有些分支是为编译器或一条 panic 路径存在的，没有用例能走到它们。它们带着某个
  人写下的理由留在清单里，永远不算在一次运行的账上，而 `Inventory::ceiling` 是一个阈值必须装得下的
  上限。
- **`Walked` 与占比**——一次运行是一个地方的*集合*，不是执行次数，而一个模块的运行拿去对着另一个
  模块的清单量时，答的是 `Foreign`，而不是一个数字。

这三种判决是 `jobq/3.20-mutation-threshold` 的，这是故意的：满足、未满足，以及*无法回答*。这里缺的
证据，是清单里没有那种可走的地方；那里缺的，是一次判了太少变异体的运行——而在两种情况下，一个二值的
闸门都必须把"我说不准"叫做失败。

## 作业

脚手架加了一个模块和一页文档，而**还没有任何东西声明这个模块**：照
`jobq/3.19-property-invariants` 接 `walk` 的方式去接线 `src/engine/mod.rs`，是你的第一个决定，而在
它做成之前规格不编译。

### `Site`、`Kind` 与 `Walked`——一个数字数的是什么

一个地方是文件、行，以及那一行回答的是两个问题里的哪一个；一次运行是它到达过的地方的*集合*。同一个
地方访问两次是一个地方，因为一个循环是被走了一千次的一个分支，而一个数执行次数的占比，是一个关于测试
数据的占比。一行和那一行上的分支是两个不同的地方，这就是为什么一个只报单一百分比的套件，回答的是更
容易的那个问题。

### `Inventory` 与 `Foreign`——主张，只关于一个模块

清单记下用例必须走的地方，以及谁也走不到的地方。两个记录器都拒绝一个不在清单作用域下的地方，而一次
运行（`Walked`）也拒绝它：两边对它们描述的东西有分歧的那一刻，下面的算术答 `Foreign`——不是一个
百分比。`src/engine` 是一个模块，不是一个字符串前缀，所以 `src/engineers/queue.rs` 是别处。

### `ceiling`、`share` 与阈值——一个决定的算术

分母是这个模块拥有的*每一个*那种地方，包括豁免的；只有可走的那些能算作已覆盖。所以一次完美的运行，
得分是 `ceiling`——清单允许的最高占比——而不是一百；而 `CoveragePolicy::is_satisfiable` 是评审的
问题：我们写下的规则，是任何人能满足的吗？它故意跟 `judge` 分开，因为算术是构建做的事，而这是一个人
做一次的事。

### `docs/coverage.md`——把策略写下来的那一页

存根写明了作用域和形状，把决定留成空白。把它填上：阈值以及它数的是什么、每个必须被用例走到的分支
一行并带上走它的那个用例、没有用例能到达的分支以及每一个的理由，还有这个数字是怎么量的。规格读这一页，
拿它跟 `CoveragePolicy::standard()` 比，所以一个写着另一个阈值的页面，是一个已经不再为真的页面。

### 有意不改的东西

引擎自己的规则、store 端口，以及每一个更早的套件。变的是这个项目愿意就它们说什么。

## 完成标准

- `kiln run jobq/3.21-coverage-policy` — 十个用例通过：两个问题、两边的拒绝、把一次游走当作集合、
  占比和它的空答案、低于一百的上限、带理由的一次豁免、仍然要走的清单、在边界上恰好满足的阈值，以及
  页面对着代码。
- `kiln check jobq/3.21-coverage-policy` — 每个 must 闸门都是绿的，`links` 也在内：那一页是交付物的
  一部分，而它的目标必须能解析。
- `kiln selftest jobq/3.21-coverage-policy --track jobq` — 慢路径拿 `slow:mutants@80` 对着**这一步
  的模块**跑，拿 `slow:?coverage@80` 对着同一个模块跑。在一台没有 LLVM 工具的机器上，覆盖率闸门答
  `⚠ blocked`，并给出安装那一行（`rustup component add llvm-tools-preview`）：那是诚实的答案，而
  不是失败，而变异体闸门才是必须绿的那一个。

## 陷阱

1. **一个盖住整个库的百分比。** 不带参数的 `cargo llvm-cov` 报一个关于一切的数字，而它会是一个舒服
   的数字：没人怀疑的那些模块被覆盖了，而它们占大多数行。`Inventory::add` 拒绝一个作用域之外的地方，
   `Walked::visit` 也拒绝，所以算术答的是一个点名 `src/main.rs` 和 `src/engine` 的 `Foreign`，而
   不是 78%。
2. **数行，然后管它们叫分支。** `if let Some(cap) = policy.max_in_flight_per_queue() { … }` 只有
   `Some` 那一支被走过，是两行被覆盖、一个决定未被覆盖。一个报前一个数字的套件，报的是编译器早就
   告诉过你的那一半。
3. **在一个有豁免的清单上要 100 的阈值。** 上限于是是可走的地方允许的那个数——十个分支里的九个是
   90——而 100 的策略让每一次运行都失败，包括完美的那一次，而人的条件反射是去跟数字争，而不是跟规则
   争。`is_satisfiable` 就是那个在有人花一星期在这上面之前把它说出来的方法。
4. **没有理由的豁免。** `Inventory::exempt` 把理由作为一个参数，因为评审必须去争的那条记录，是写下来
   的那一条；一页没有理由的地方，开头是"这一个很烦"，结尾是阈值被调低。
5. **拿另一个模块的运行，当这个模块的数字引用。** 一个 `Walked` 带着它量过的那个作用域创建，而
   `share`/`uncovered` 拒绝一个清单没有描述的模块的游走：否则回来的数字，会是关于两个模块的并集的，
   那就是缺陷 1 换了个更绕的走法。
6. **一个数执行次数的占比。** 一个循环跑一千次是一个地方。数*命中*会让一个完全覆盖的模块看起来像
   400%，并让这个数字取决于测试数据有多大，而一个覆盖率闸门就是这样变成对夹具的测试的。
7. **一个会漂的页面。** 作用域、阈值和种类住在代码里（`POLICY_SCOPE`、`CoveragePolicy::standard()`），
   而页面写明它们，所以两者是一起读的：规格比较它们，而它是唯一能做到这件事的东西——一个覆盖率工具对
   一页文档一无所知。
