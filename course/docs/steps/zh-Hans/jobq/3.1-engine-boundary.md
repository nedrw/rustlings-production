# 划出引擎边界：只让守护进程依赖库，绝不反过来

## 回顾

- `repo/workspace-layout@apply` — `mailer/1.1`：一个项目、一个 `[workspace]`，`cargo fmt` 与
  `cargo clippy` 先于其他一切接好。
- `cfg/layered-config@apply` — `mailer/1.4`：默认在最底下，其次是一个文件，再往上是环境，旗标最后；
  `--check-config` 打印进程真正会做什么，而从不打印密钥。
- `obs/structured-logs@apply` — `mailer/1.6`：一个订阅器只装一次，要紧的日志行上带一个 run id。
- `http/service-skeleton@apply` 与 `http/middleware-layering@apply` — `mailer/1.7`、`relay/2.1`：这是你
  第三次搭服务的骨架，也是第一次，搭出来的东西不是服务。

## 变化

项目骨架里你已经会的东西，这里全都在，变的是*依赖的方向*。`relay` 是一个恰好带了个库的服务；`jobq` 是
一个**恰好带了个守护进程的库**。引擎——队列、作业、状态、存储端口——必须能在没有服务器、没有配置文件、
也没有任何进程参与的情况下跑起来，因为它服务的是别人的程序：`jobq` 是引擎，`jobqd` 是套在它外面的一层
壳，而后面的 track 完全可以把另一层截然不同的壳套在同一个引擎上。

今天要为它付的代价，是一条在单个包内编译器给不了你的规则：**箭头只朝一个方向**。`src/service/**` 可以
用 `crate::engine`；`src/engine` 下的任何东西都不许提到 `crate::service` 或 `crate::cli`。规格靠读源码
来检查这一点，这比另开一个 crate 要弱——而这么做的理由就写在规格文件里，好让将来拆分这个包的作者确切
知道该删掉什么。

这一步还把所有后续内容要用到的端口形状定下来。引擎通过引用来持有的那些 trait，方法返回装箱的 future
（`fn claim<'a>(&'a self, …) -> BoxFuture<'a, …>`），而不是 `async fn`：trait 里的 `async fn` 不是 dyn
兼容的（`E0038`），而 worker 是通过引用持有它的存储的，不是通过一个自己点得出名字的类型参数。

## 作业

- 解析一个队列名（`[a-z0-9._-]` 里 `1..=64` 个字节），并说清其余部分错在哪儿。
- 实现内存存储：入队时校验尝试预算并解析出 `run_at`；`claim` 按顺序取到期的作业（先看优先级，再看到期
  最久的，最后看标识），把它们标成运行中并计入这次尝试；`complete` 只结算正在运行的作业；`fail` 记下
  原因，并按预算在 `queued` 和 `failed` 之间选一个；`get` 读一个作业。
- 让 `Engine` 成为唯一的门：`submit`、`claim`、`complete`、`fail`、`inspect`，每一个都委托给存储，并把
  “没有行”变成 `Error::NotFound`。
- 实现守护进程的那些设置项：`Flags::from_args`，以及 `Config::load`——它合并默认值、`--config` 指定的
  文件、`JOBQ__SECTION__KEY` 环境变量和旗标；`report()` 打印结果，并给密码打码。
- 只装一次日志订阅器，并让 `serve` 打开存储、打出 `draining`、等 `SIGTERM`/`Ctrl-C` 然后停下。
  `jobqd --check-config` 不打开任何东西也得能回答。

## 完成标准

- `kiln run jobq/3.1-engine-boundary` — 六个规格用例通过。
- `kiln check jobq/3.1-engine-boundary` — 每个 must 闸门都是绿的（包括 `clippy@2`，它禁止库和二进制
  目标里出现 `unwrap`/`expect`）。
- 在 `app/jobq` 里跑 `cargo test -p jobq` — 上面那套用例，加上你新增的每个单元测试。

## 陷阱

1. 在作业*结束*时而不是被认领时计入尝试 → 一个持有作业时死掉的 worker 把它还回来时 `attempts` 没变，
   于是预算永远用不完，一个毒丸载荷会永远循环下去。规格在 `claim` 之后马上断言这个计数。
2. `claim` 返回作业自己的副本，却不翻转存储里的状态 → 同一个作业又回到下一个 worker 手里：规格那个双
   worker 的用例靠比较标识发现这次重复。
3. 把 `Queue` 做成一个光秃秃的 `String` 别名 → `queue_typo` 就能进数据库。这个名字是看板里的键、指标
   里的标签、表里的一列，所以构造函数是唯一的门。
4. 因为今天只有守护进程一个调用方，就把引擎的逻辑放进 `src/service` → 规格的源码检查失败，而下一个壳
   （一个 CLI、另一个服务、一个测试）想拿到一个队列，就得把守护进程整个抄一遍。
5. 打印配置时把连接串也打出来 → 运维把报告粘进工单，密码就跟着一起走了。`report()` 会打码；
   `mailer/1.4-config` 早就许下这个承诺，这一步把它守住。

  （`rustc --explain E0038` 是简版答案）。
- `docs/handoff-m0.md` §2 — 这门课程据以编写的一组环境事实，其中就包括这一条。
- `tokio::signal` — 一个进程被要求停下的两种方式，以及为什么只有 `Ctrl-C` 不够。
