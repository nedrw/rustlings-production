# 序列化冲突与唯一性竞态：重试，还是预防

## 回顾

- `db/unique-as-concurrency@apply` — `mailer/1.11-signup`：一条两个调用方能在同一瞬间打破的唯一性规则，
  归数据库管，因为应用先做的检查，是一扇两个人都能穿过的窗口——而修法是*利用*这次拒绝
  （`on conflict … do nothing returning id`），不是躲开它。这条知识可以整块搬过来。新的是：被争的
  那一行，不是用户的身份，而是作业自己历史里的一行记录；而且这条规则得先能在一个地方表达出来，才能
  住进索引里。
- `db/transactions@apply` — `mailer/1.17-newsletter`：两次不许做了一半的写入放进一个
  `begin`/`commit`，提交之后跟着做的工作发生在它之后——不在它里面。这里那一对是一次状态改动和描述它
  的那行记录，而你被要求*不要*放进事务的那次写入，是发给网络的那一次；不过隔离级别是前两步都不必做的
  决定，也是这一步的一半。

## 变化

- **一次结算现在是两次写入，而它们是一个提交。** `complete` 和 `fail` 在一个事务里改那一行，*并且*往
  `job_events` 追加一行记录。那条轨迹正是 `jobq/3.16-dlq-tooling` 会列出来、
  `jobq/3.17-error-budget-alerts` 会统计的东西，所以一条可能与它描述的那行不一致的轨迹，比没有轨迹更
  糟：运维一边读到“失败了两次”，一边看到一行写着 `queued`，就有了两个答案，却无从选择。
- **冲突自成一类。** `Error::Conflict` 是持久化后端在数据库因并发拒绝一个事务时抛出的东西——`40001`
  （一个快照被一次它从没见过的提交抢走了一行）和 `40P01`（服务器解开的一次死锁）——而
  `Error::is_retryable` 当初在 `jobq/3.3-library-errors` 里写下来，正是为了让这一步能在它后面放一个
  类别。这里*不*新的是重试这个决定；新的是：重试从此变成对一个引擎点得出名字的类别的正确反应，而不是
  对一条消息的猜测。
- **隔离级别才是那个决定，而它并不免费。** 在 PostgreSQL 的默认级别下，竞态输掉的那一方会*等待*，
  重读那一行，然后要么成功，要么发现无事可做——而且是无声的：引擎分不清“别人把它结算了”和“这一行
  根本没在运行”。在 `repeatable read` 下，同样的写入变成一次调用方能据以行动的拒绝。你是拿一次等待，
  换一个读得懂的答案，代价是得有人去处理这次拒绝。
- **重试有上界，而且它会报告花了几次。** `retry` 是一个套在闭包上的小循环：闭包就是那个事务（所以调用
  方只写一遍），谓词是引擎自己的分类，而答案带着它试了多少次。还没有退避——等待需要一只时钟，而这个
  crate 要到 `jobq/3.8-clock-injection` 把它交给它为止，并不拥有这样一只时钟——所以上界就是策略的全
  部。

## 作业

脚手架加了三个文件，其余都是对你已经拥有的文件的修改。

### `migrations/0002_job_events.sql`

每结算一次一行：`id`、`job_id`、`kind`、`attempt`、`detail`、`at`——每一行对应
`src/engine/events.rs` 里的一行记录。文件归你；其中有两件事是决定：

- 一行记录的身份是 `(job_id, kind, attempt)`，所以同一次结算追加两次，必须是*同一行*记录——而这得由
  数据库来决定，而不是调用方做一次先读后写，因为一个被重试的事务，正是一个来了两次的调用方；
- 持久化后端的追加是 `insert … on conflict (job_id, kind, attempt) do nothing`，PostgreSQL 只有在
  **唯一**索引与这些列完全匹配时才接受它。

参考解还加了运维的问题所需要的那条索引（`job_id` 按 `at` 排序）；规格不强制它的形状，而一个为了计数
去读整条轨迹的步骤（`jobq/3.17-error-budget-alerts`）可以加自己的。

### `src/engine/`

- 声明两个新模块，并重新导出调用方可以点名的东西——`pub(crate) mod events;`、
  `pub(crate) mod retry;`，然后在 `src/engine/mod.rs` 里 `pub use events::{EventKind, JobEvent};` 和
  `pub use retry::{DEFAULT_ATTEMPTS, Retried, retry};`。绝不用 `pub mod`
  （`jobq/3.2-public-api-baseline` 步会读这些声明）：模块仍是 crate 自己的，而*名字*才是公开面。
- `Error::Conflict { source }` 是一个**新变体**，不是 `Error::Store` 上多出来的字段——3.3 的规格会构造
  已有的变体并钉住它们的 `Display`，所以一个长出字段的变体是破坏性改动，不是新增。加上它，扩展
  `is_retryable`（`Store` 和 `Conflict` 都算），再在 `exit_code` 里给它一行（4，和存储一样：外壳能
  据以行动的是“队列不肯收”）。
- 在 `src/engine/retry.rs` 里实现 `retry`：调用闭包，只要 `error.is_retryable()` 为真且还有次数就
  重试，把值和花掉的次数一起返回——上界用尽时，把*最后*一次失败原样交回去。

### `src/engine/store/`

- 给端口加两个方法：`record(&self, &JobEvent) -> Result<bool>`（追加一行记录，回答它是不是新的）和
  `events(&self, &JobId) -> Result<Vec<JobEvent>>`（一个作业的轨迹，最老的在前）。两个方法的文档就是
  用例读的契约：追加是**按行记录的身份**幂等的，而一个没人写过的作业，得到的是一条空轨迹，不是一个
  错误。
- 持久化后端：让每次结算都成为一个 `repeatable read` 的事务
  （`pool.begin_with("begin isolation level repeatable read")`），从 update 自己的 `returning`
  子句里取出这次尝试，追加那行记录，然后提交一次。把驱动的 `40001`/`40P01` 映射成 `Error::Conflict`
  的地方**只有一处**——每条语句的失败本来就会经过的那个函数——这样别的路径都不必记着这件事。
- 内存后端：用它有的东西守住同一个承诺。一把锁同时管住行*和*记录，就是“一个事务”的诚实翻译：一次
  拒绝在两次写入之前就返回，而一次提交了的结算把两样都写下去。

### 有意不变的部分

`claim` 不写记录（一次*已经开始*的尝试在行上），端口已有的五个方法保留签名和行为，而这一步里没有任何
东西替学习者把结算包进重试：存储报告类别，调用方——在这里是规格，下一步是
`jobq/3.7-leases-and-recovery` 的 worker——决定拿它怎么办。

## 陷阱

1. **在事务外面追加。** 一个先提交那一行、再调用 `record(…)` 的 `store.fail(…)`，在每个中途不出错的
   测试里都看着正确——然后一个在两次写入之间死掉的进程，会留下一个作业，没有任何东西解释它怎么到了
   那里，而那正是轨迹本该派上用场的时刻。`a_refused_settle_leaves_nothing_behind` 以相反的方式失败：
   在拒绝的路径上追加，会给一次从未发生的结算留下一行记录。
2. **`on conflict` 子句背后没有唯一索引。** 把 `unique` 从索引上去掉，编得过，迁得动，然后每次结算都
   以 `there is no unique or exclusion constraint matching the ON CONFLICT specification` 失败——在
   第一次追加时，而不是在本该抓住它的那次迁移上。`the_same_line_appended_twice_is_one_line` 就是这个
   用例；断言是第二次 `record` 回答 `false`，而只要数据库还能自由地把这一行写两遍，它就过不了。
3. **停在默认隔离级别。** 结算于是*等*另一个写入方，再重读，
   `a_transaction_the_database_refused_is_a_conflict_with_a_cause` 就以结算回答 `Ok(Queued)` 失败
   ——竞态还在，而调用方仍然没被告知。规格的消息因此指向隔离级别：
   `nothing ever waited for the held
   row` 和 `the loser of the race is refused rather than quietly re-read` 是两个不同的 bug。
4. **用第二条语句读尝试次数。** `update … returning` 把结算那行记录必须点名的尝试交给它；在它之前或
   之后来一句 `select attempts`，可能点出一个中间已经变过的尝试，于是在这一步恰恰关心的那种并发之下，
   记录和行自相矛盾。
5. **一个什么都重试、或者永远重试的包装。** 重试 `Error::Invalid` 会把一个被拒绝的载荷变成一个永远
   不结束的循环；`the_wrapper_retries_what_is_worth_retrying_and_stops_at_its_bound` 用调用计数 1
   检查前一种，用等于上界的调用计数检查后一种。把*第一次*失败又重试一遍，却从不报告试了多少次，同样
   过不了这个用例，因为计数就是断言。
6. **把 `Error::Conflict` 并进 `Error::Store`。** 让整套用例除了一个之外全绿的最便宜做法：冲突的那些
   用例会读 source 链里有没有 `40001`，也会 `matches!(error, Error::Conflict { .. })`。一个
   `Store { detail: "could not serialize…" }` 是一串调用方没法据以分支的字符串，而这个变体存在的
   理由，正是把这件事定下来。
7. **“因为冲突用例要 Postgres”就跳过内存后端。** 七个用例里有两个需要数据库，它们自己也这么说；
   另外五个——轨迹、它的幂等、重试循环——在两个后端上都跑，而一个 `record` 永远回答 `true` 的存储，
   在容器还没启动之前就会在 `KILN_BACKEND=memory` 上让它们失败。

## 延伸阅读

- [PostgreSQL: transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html) — 把
  “等待，然后重读”和 `40001` 分开的那张表，以及为什么在 `repeatable read` 上，一次丢失的更新会变成
  一个你看得见的错误。
- [PostgreSQL: `ON CONFLICT`](https://www.postgresql.org/docs/17/sql-insert.html#SQL-ON-CONFLICT) —
  `do nothing`、它要求的那个仲裁索引，以及它压下一行时返回什么。
- [`sqlx::Transaction`](https://docs.rs/sqlx/0.9.0/sqlx/struct.Transaction.html) — `commit`、
  `rollback`，以及一个两者都没做就被丢掉的事务会怎样。
- [`sqlx::error::DatabaseError`](https://docs.rs/sqlx/0.9.0/sqlx/error/trait.DatabaseError.html) —
  `code()`、`constraint()` 和 `table()`：驱动错误里结构化的那一半，`is_conflict` 读的就是它。
- `relay/2.15-shutdown-leases` 的 `src/lease.rs` — 这个故事的另一半：在那里，一个没人结算的行由租约
  恢复；在这里，恢复是一行记录，说它发生了（`jobq/3.7-leases-and-recovery` 写下这条轨迹的第一条
  `Reclaimed` 记录）。
- `src/engine/events.rs` 和 `src/engine/retry.rs` — 这一步交付的两个模块；它们的文档注释就是论证，而
  `tests/support/store.rs` 是两个后端都对着的那条缝。
