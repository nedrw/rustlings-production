# 命令行上的死信队列：查看、重放，以及带着理由丢弃

## 回顾

- `ops/dlq-tooling@apply`——`jobq/3.16-dlq-tooling`：**这扇门照着写的那个端口。** 那一步点明了队列
  （`dead_letters()`：`failed` 里那些行上的一个视图，不是它自己的一份集合），决定了再给一条命时写什么
  （`revived(job, now)`——计数留着，上限挪到 `attempts + 1`，`last_error` 留着，租约清掉，`run_at` 取存
  储的时钟），并且把这次挪动放上端口，做成 `Store::replay(&JobId)`，一个事务管那一行和那条轨迹。它自己的
  总结说了它没做的部分：*运维工具所做的那些动作*。这一步就是那一半，而 `revived` 一个字都没改。
- `cli/contract@apply`——`jobq/3.15-cli-contract`：**这一步扩展的语法，以及它守住的四条规则。** `jobqc`
  在 stdout 上作答，在 stderr 上诊断；每个失败类别一个退出码；`--json` 是一种格式，不是一个第二命令；而一
  个列表答的是这个句柄看得见什么。`submit`、`inspect`、`list` 和 `usage` 已经在那儿了；死信这一组加入同一
  个解析器和同一张退出码表，而不是在旁边另起一个工具。
- `db/port-conformance@apply`——`jobq/3.5-store-port-conformance`：**为什么这些动作是端口方法，而不是命令
  拼出来的查询。** 端口是那条接缝，它让"同一个问题，两份实现"成为一个有见证的承诺，而一致性闸门每个后端把
  这一步的规格再跑一遍。一个只有内存存储答对了的动作，恰恰就是那道闸门要找的缺陷。
- `db/transactions@design`——`jobq/3.6-transaction-isolation`：**轨迹，以及记录从它那里借来的承诺。** 一
  次结算改那一行，并在同一个事务里追加描述它的那一行。一个*动作*的记录至少要这么强，而这个理由在丢弃上最锋
  利：一次没有记下自己那一行就提交了的删除，是凭空消失、却没人被记下把它扔掉的工作。
- `sec/authz-tenant-isolation@operate`——`jobq/3.13-queue-authz-attribution`：**句柄就是身份，而一个名字
  是一个主张。** 一个带作用域的存储，只为它的模型点名的那些队列作答，而一行它不该看见的，答起来就像一行没
  人写过的——两种情况一个答案，调用方分不出来。这一步要求的 `--by` 不是一份凭据（"我可以吗"是在
  `jobq/3.13` 回答的）；它是记录所保存的东西。

## 变化

**运维要做*决定*所需要的一切都已经在了；缺的是那扇门。** 上一步，端口能点名死信，也能把一条放回去；再上
一步，命令行能 submit、inspect 和 list。这两样都不是凌晨两点有人会对着一个队列拿起来用的东西：前一个是
库，后一个里面根本没有死信这个词。这一步是两者缺的那一半，而它的决定讲的是那些**动作**——这也是它们住在形
状里、而不是住在帮助文本里的原因。

三个决定，每一个都是某人撞上过的失败：

- **动作要签名。** 一个 `Order` 带着接手它那个人的名字，而 `Order::check` 在**存储读到任何东西之前**拒绝
  一个没有名字的动作。`jobq/3.6` 的轨迹记下的是一个作业*发生了什么*——一行 `replayed` 和它点名的那次尝
  试——而事后无论怎么读它，都答不出"是谁把这个作业放回来的"，而对一个别人看得见的动作，这是人人都会问的
  第一个问题。名字是一个*主张*，不是一份凭据（这个存储信任递给它的句柄，`jobq/3.13`），而一份主张的记录，
  仍然是"某个运维重放了它"和压根没人知道有个运维之间的差别。
- **不能撤销的那个动作，必须说清为什么。** 重放是可逆的：作业带着它的载荷和它的计数回到它的队列里，而一次
  错的，就是一个还能再试一次的作业。丢弃不是——工作是扔掉的，作业里剩下的任何东西都说不出它当初是干什么
  的。所以 `Order::check` 在*读那一行之前*，拒绝一个理由空白的丢弃（空的，或者只有空白）；而
  `discardable(job)` 拒绝一个不是死信的作业：一个 `queued` 或 `running` 的作业，还欠着一次即将发生的尝
  试；一个 `succeeded` 的，是某人已经拿到了的工作——把其中任何一个扔掉，都是在对一个并不是被放弃的失败做
  决定。这次拒绝是一道*检查*，而不是一句警告，因为一份里面有一行没法解释的记录，是一份没人信的记录。
- **记录比它讲的那一行活得久。** `jobq/3.6` 的轨迹表随着它所属的作业一起结束（`on delete cascade`），而
  它的注释明明白白地说，一次清理要不要留着它所删掉的东西的轨迹，是写这种清理的那一步的决定。这一步就是那一
  步，而答案是它自己的一份记录，**没有外键**：一次丢弃之后，没有行可问了，而那正是这条记录必须活下来的时
  候。`JobAudit` 就是那一行——作业、队列、动作、操作者、时刻、理由——而 `Store::operate` 在描述这次变更
  的同一个事务里把它写下去。

这扇门自己有四个决定，而有趣的那个是拒绝留下了什么：

- **`dlq list` 是运维的视图，不是一个列表。** `jobqc list --state failed` 问的是同一个问题，答的是整个任
  务，连载荷一起。运维据以做决定的，是每一行已经花掉了多少次尝试，以及它最后一次尝试死掉时说的那句话；载
  荷正是他们*不能*有的东西——不能在滚屏里，不能在工单里，不能在 pastebin 里。一个在事故中间打印客户数据的
  工具，把一次事故变成了两次，这就是那行四个字段为什么是自己的形状，而不是 `list` 上的一个旗标。
- **拒绝是一个类别。** 调用错了是 `2`（不认识的子命令、缺一个旗标、一个空白的理由、一个不是死信的作业），
  身份不在那儿是 `3`，存储拒绝是 `4`，部署坏了是 `1`。这些数字是 `jobq/3.3` 写、`jobq/3.15` 立成契约的
  那张表；这里没有谁发明第五个。
- **没有批量。** `dlq replay <ID> <ID> <ID>` 是 shell 里的一个循环。一个对两个身份动了手、拒绝了第三个的
  命令，没有单一的类别可以留下；而在一个失败旁边打印那两个成功的，会递给脚本一份 `jobq/3.15` 明令禁止的半
  份文档。一个身份，一个动作，一个答案，一个退出码——而运维在 `dlq audit` 里读一个脚本循环做了什么。
- **一个动作的答案，就是记录得到的那一行**，形状和 `dlq audit` 打印的一样，因为那就是刚刚发生的事。一个用
  自己没写下来的东西作答的命令，是一个答案和记录可以对不上的命令。

端口上加了两个名字，`Store::operate(&Order) -> JobAudit` 和 `Store::acts(limit) -> Vec<JobAudit>`，带着
三个承诺：那一行在做决定之前是在锁底下读的（两个运维不可能都被告知自己挪动了它），变更和那一行是同一个事
务，而一个被拒绝的动作什么都不写。一次从这扇门走的重放留下**两行**，这不是重复：轨迹那一行讲的是作业，随
它一起活；记录那一行讲的是动作和人，等作业早就没了，它还在。

## 作业

脚手架加了一个模块、一个页面骨架和一个装置。**还没有任何东西声明这个新模块**：接上 `src/engine/mod.rs` 是
你的第一个决定，在做出它之前，规格和装置都编译不过——而这就是 `kiln run jobq/3.26-dlq-cli` 最先给你看的
那个失败。

### `Act`、`Order`、`JobAudit`——这一步用哪些形状来写

`Act` 是 `Replay`/`Discard`，和这个 crate 公开词汇表里的每一张清单一样带 `#[non_exhaustive]`
（`jobq/3.2`），而 `as_str()` 是迁移的 check 约束、持久后端的解码器和某人的 `grep` 都认的那一种拼法。
`Order` 是一个值，而不是四个参数，因为一个动作可能错的三件事——名字、理由、作业——只在这一处检查，而不
是每个调用点各查一遍；也因为它带的是作业的**身份**，而不是那一行的拷贝：那一行归存储去读，在锁底下读，而
一个带拷贝的 order，会让调用方对一个从那时起已经挪动过的作业做决定。`JobAudit::of(order, job, at)` 定下
的是*记录*（而不是后端）所说的那两件事：操作者的名字去掉首尾空白（一份记录里同一个名字的两种拼法，是一份
没人能数清的记录），而一个只有空白的理由，变成根本没有理由。`stored(…)` 是从列拼出来的同一行，给要把它们
读回来的那个后端用。

### `Order::check` 和 `discardable`——那两种拒绝

`check` 答*动作*本身的第一处错（没有名字；一次没有理由的丢弃），`discardable` 答*那一行*的错（不是
`failed`）。把它们拆开，就是存储所作承诺的形状：一个本身就错的动作，在读之前被拒绝；一个对这一行来说是错
的动作，在写之前被拒绝；而被拒绝的动作不留下任何一行。`discardable` 点名作业所处的状态，因为"还欠着一次
尝试"和"已经做完"，对运维眼前的一行来说是两个不同的答案。

### `Store::operate` / `Store::acts`——端口，以及两个后端

把这两个方法加进 `Store`，实现两遍：

- 内存存储把行追加进一个向量，用的就是挪动那一行的那把锁，并且留一条私有的重放路径（`replay_of`）和一条
  私有的丢弃路径（`discard_of`），好让 `jobq/3.16` 的 `Store::replay` 保住它的签名：同一套算术藏在两扇
  门后面，其中一扇上面没有名字，也不写行；
- 持久存储在那个事务里用 `for update` 读那一行，把谓词写进语句里（删除时是 `state = 'failed'`，这样一行
  自加锁以来挪动过的，就不会被删掉），并在同一个事务里插入那一行；删除会级联到轨迹，于是留下的就是记录那一
  行。

一个接了动作却没写行的存储，是这个 crate 给出答案而不是 panic 的一种情况（`unwritten`）：只要两个后端恰好
在 order 有行的时候写行，它就是不可达的；而它不再不可达的那一天，它就是整整这一步在讲的那个失败。

### `migrations/0008_job_audit.sql`——那张表，号往前排

有四个决定该写进文件里，而不是写在别处的某句话里：**没有指向 `jobs` 的外键**（那一行可能已经不在了，而正
因为可能不在了，这条记录才必须活下来）；**单位是一个动作，不是一个作业**（同一个作业重放一次、后来又被扔
掉，是两行；一个被拒绝的动作，是零行，所以没有一个唯一索引可以推给它）；**队列是反规范化的**（读这行的审
计者不该非得去把作业查出来——而队列正是这次查询的作用域，按 `jobq/3.13` 立下的形状）；**给它们排序的是
`seq`**（两个动作可以共用一个时刻，而记录仍然有顺序：这些行是何时追加的，而不是时钟读到了什么）。

### `src/cli/dlq.rs`——这一组

`dlq list|replay|discard|audit` 挂在 `jobqc` 的解析器上，带 `--queue`、`--limit`、`--by`、`--reason`，
而全局旗标放在子命令任何一边都行。调用方能犯的每一个错误都在这里被拒绝，在任何设置项被读之前、在任何存储被
打开之前，于是 `2` 就意味着"调用错了"，不管数据库最后连不连得上。`parse` 造一个 `Order`（把动作做成引擎
能检查的一个值），而不是把"丢弃要理由、重放不要"这条规则记在一张旗标表里；`execute` 打印存储写下的那一
行。二进制里的帮助文本就是库的 `USAGE`，于是这套语法只有一份。

### `docs/dlq.md`——那一页

脚手架留下一个带着 `TODO` 标记的骨架；为那个刚刚被叫醒的人把它填上。卡在哪儿、怎么看它的一行；那两个动
作，以及各自要付什么；记录；脚本据以分支的退出码表；以及一次事故最初五分钟的先后——包括那一步容易跳过的：
*先修原因*，因为往一个坏掉的处理函数里重放一千个作业，就是十分钟后又多出一千封死信。规格会读这一页，所以
它是交付物，不是关于交付物的注释。

### `tests/dlq_harness.rs`——课程的仪器

它通过 `Order`/`operate`/`acts` 驱动内存存储，打印四个计数——`jobq-budget acts=…`、`record_lines=…`、
`orphans_max=…`、`unattributed_max=…`——`slow:bench-budget@10` 拿它们去和
`course/tracks/jobq/budget/3.26-dlq-cli.toml` 比。是计数，永远不是秒：闸门在一台满载的机器上和一台闲着的
机器上给出同一个答案。装置是课程的文件，不是你的——改它就是改测量，而 `kiln reset jobq/3.26-dlq-cli`
会把它放回去。

### 规格判什么

十一个用例，分四组——作为命令行的这扇门、走端口的那两个动作、它们留下的记录，以及这一步所改的那个端口
——下面每一行都是你能跑的一个主张：

| the case | the claim |
| --- | --- |
| `the_help_text_names_the_commands_that_act_on_a_dead_letter` | 二进制逐字节打印库的 `USAGE`，点名 `dlq`、它的四个子命令、`--by` 和 `--reason`，而 `jobq/3.15` 的那四个命令还在里面 |
| `a_call_the_tool_cannot_understand_is_a_usage_error_that_names_it` | 十次错误的调用，每一次都退出 `2`，stdout 上什么都没有，stderr 上一句话，带不带 `--json` 都是同一个退出码——而那个够不到任何存储的，不管队列连不连得上，答法都一样 |
| `an_operator_walks_the_dead_letters_from_the_command_line` | 整扇门对着一个真的数据库：两封死信按端口的顺序列出，不带载荷；一封被重放，签了名，带着一条注记；一封被丢弃，签了名，带着理由；那一行从表里消失；记录按两种形状读回来；五个拒绝各按类别 |
| `an_act_is_recorded_with_whoever_took_it` | 一个动作一行，最新的在前，一页只取一条时就是最新的那个动作，名字和理由都去过首尾空白，而被重放的作业自己的轨迹仍然在记录旁边 |
| `an_act_that_does_not_hold_changes_nothing` | 四个拒绝（没有理由、只有空白的理由、没有名字、不是死信的作业）都让记录空着，让那些行停在原处 |
| `an_act_is_the_ports_and_not_one_backends` | 重放是随后一次认领取走的第二条命（`attempts` 2，上限 2），一个动作不动任何用量计数，而两个动作都在记录上 |
| `the_handle_decides_whose_dead_letters_are_acted_on` | 一个队列的主人可以对它自己的死信动手，也读得到自己的那一行；另一个租户的那一行根本不在答案里；对别人的行动手，答起来就像一行没人写过的，而且什么都不写 |
| `the_project_has_a_page_an_operator_can_follow` | 页面点了那三个命令，带着脚本据以分支的那些退出码，没留下任何占位 |
| `every_life_the_door_gives_a_job_is_a_line_in_its_trail` | 同一个作业重放两次，中间夹一次失败：轨迹是五行，按它们发生的顺序——死、动作、死、动作、死——而记录装着那两个动作。一行由 `(kind, attempt)` 标识，所以一条把其中两行合并掉的轨迹，会丢掉一条命 |
| `a_replayed_job_waits_for_a_slot_like_any_other_work` | 一个上限为一的队列，收下这扇门放回去的作业（上限数的是*正在跑*的工作，不是排着队的行）；第二个被重放的作业不是被拒绝，是等着；而第一个做完，把座位交出来 |
| `a_replayed_job_ages_like_any_other_work` | 重放让这个作业在动作被做出的那一刻到期，而十个间隔之后，它的优先级高过一个带着更高优先级到达的作业：重放由队列自己的策略收下，而策略正是等待被计数的地方 |

## 完成标准

- `kiln run jobq/3.26-dlq-cli` — 十一个用例通过：帮助文本、十次用法错误、一次穿过真队列的行走、记录、
  那些拒绝、端口的算术、句柄的身份、页面，以及关于这一步所改的那个端口的三个。
- `KILN_BACKEND=postgres kiln run jobq/3.26-dlq-cli` 在 `app/jobq` 里 — 同一份套件配上持久后端：同样的
  拒绝、同样的记录，而那一行是在锁底下读的。
- `kiln check jobq/3.26-dlq-cli` — 每个快闸门都是绿的，而慢的那些就是下面这些行。
- `kiln selftest jobq/3.26-dlq-cli --track jobq`（或者 `kiln verify jobq --slow`）— 要读的行是
  `slow:conformance@2`：`2 backend(s) pass the same suite: memory ✓, postgres ✓`；
  `slow:mutants@80`：`6/6 mutant(s) killed (100%, needs ≥80%) (the walk took 26s)`；
  `slow:bench-budget@10`：`4 metric(s) within ±10% of the course baseline: acts 17, record_lines 12,
  orphans_max 0, unattributed_max 0`；`links`：`41 link(s) in 7 page(s) resolve`；以及没装
  `llvm-tools-preview` 的机器上 `slow:?coverage@80` 答的 `⚠ blocked`——那是那里的诚实答案，不是这一步的
  失败。
- `cargo test -p jobq --test dlq_harness -- --nocapture` 打印 `jobq-budget acts=17`、
  `jobq-budget record_lines=12`、`jobq-budget orphans_max=0` 和 `jobq-budget unattributed_max=0`：十七
  次调用穿过这扇门，其中十二次是真的发生了的动作，而没有一行是关于一个没发生的动作的。
- 在最终的树里跑 `cargo test -p jobq`——**199 passed · 0 failed**（`jobq/3.25-release-artifacts` 的
  187 个，加上这一步的十一个用例和装置），而同样的命令前面加上 `KILN_BACKEND=postgres`——199 passed ·
  0 failed。
- `JOBQ__STORE__URL=memory cargo run -q --bin jobqc -- dlq list` 什么都不打印，以 `0` 退出；而同一条命令
  换成 `dlq discard 4f1c… --by ada`，以 `2` 退出，并在 stderr 上点名 `--reason`。
- `KILN_BACKEND=postgres kiln run jobq/3.16-dlq-tooling` — 这一步所扩展的那个端口，答 `Store::replay` 的
  方式还是原来那样，签名和语义都是。
- `kiln run jobq/3.15-cli-contract` — 早先的那份套件仍然通过：语法长大了，但它没有挪窝。

## 陷阱

1. **一个拿别人递给它的那一行来做决定的命令。** 用 `dead_letters()` 读出死信，然后自己再写第二条 `update`，是
   这一步的短版本，也是它存在所要防的那个 bug：在读到写之间，那一行会动（另一个运维、worker、一次清理），
   于是两个运维都被告知自己挪动了它。动作走 `Store::operate`，它在自己的锁底下读那一行，并在同一个事务里做
   决定——而操作者的名字在 order 上，不在命令上方的一句注释里。
2. **在检查那一行之前就写记录。** 先插入那一行，*然后*才发现这个作业不是死信（或者它已经没了，或者是别人
   的），会留下一行关于一个没发生的动作的记录——审计者唯一用不了的那种东西。顺序是：先是 order 自己的拒
   绝，然后是读，然后是写，而两个后端在碰到任何东西之前就拒绝。规格的
   `an_act_that_does_not_hold_changes_nothing` 断言之后记录是空的，所以一个在检查之前跑的 `record` 调
   用，会一次让五个用例变红。
3. **记录上的外键。** `references jobs (id) on delete cascade` 看着像是在让数据保持诚实，其实正好相反：丢
   弃就是那个删除，于是级联恰好在这条记录成为这项工作的唯一交代时把它移走。持久后端还是按*谓词*而不是按级
   联来删除轨迹（`delete from jobs where id = $1 and state = 'failed'`），理由就是 3.23 讲谓词时给的
   那个：第二条语句可以推理，触发器不能。
4. **接受 `--reason ""`，或者在做出决定之后才去空白。** `is_empty()` 会放过一个只有一个空格的理由，而检
   查之后才 `trim()`，会把没去空白的文本留在记录里；一份同一个名字有两种拼法的记录，或者一次理由只有空白
   的丢弃，是一份"为什么"的计数等于按键次数的记录。检查是名字和理由都做 `trim().is_empty()`，而
   `JobAudit::of` 把要存的东西去了空白。
5. **用新门替换 `Store::replay`。** 把 `jobq/3.16` 的方法路由到 `operate` 上很诱人——然后重放就得有个
   名字，而它没有：`run_at`、`attempts` 和轨迹那一行是一样的，记录那一行不是。两扇门共用 `replay_of`，只
   差一个选项，于是算术只存在一份，而*记录*对那一行不做任何决定。
6. **因为 shell 循环慢，就做一个批量。** `dlq replay a b c` 读起来不错，但对"两个成了、一个被拒了"没有
   答案：退出码没法是同一个类别，stdout 也没法是一份半截的文档。规格的第一个用例断言，两个身份是一个点名第
   二个的用法错误。
7. **`dlq list` 里带上载荷。** 显而易见的实现是给 `jobqc list --state failed` 加一个旗标，而它把客户数据
   送进终端、工单和 pastebin。`dlq list` 是四个字段，其中没有载荷，而 JSON 形状里压根没有 `payload`
   这个键——规格会去要这个键，并指望它不在。
8. **二进制里再放一份语法。** 把 `jobqc` 的帮助文本递到别处、从 `main` 打印出来，第一次加旗标时两份拷贝
   就会漂移：规格逐字节比较二进制的 `--help` 和 `cli::USAGE`。
9. **改装置或者基线，而不是改代码。** `tests/dlq_harness.rs` 是课程的文件，
   `course/tracks/jobq/budget/3.26-dlq-cli.toml` 是闸门读的那份拷贝：改其中任何一个，改的是仪器，而不是
   它量的那个东西。
10. **页面里还留着 `TODO`。** 规格会读 `docs/dlq.md`，拒绝占位，所以一个别的方面都完美的步骤，会一直红
    着，直到这一页写出来——而这正是要点：凌晨三点被叫醒的运维不读源码。

## 延伸阅读

- [PostgreSQL: `SELECT … FOR UPDATE`](https://www.postgresql.org/docs/current/explicit-locking.html) — 持久
  后端那个动作在底下读的行锁，以及它*不*能替你挡住什么。
- [PostgreSQL: sequences and `bigserial`](https://www.postgresql.org/docs/current/datatype-numeric.html#DATATYPE-SERIAL)
  — 为什么 `seq` 对一份动作记录是个好顺序，而对任何会被人引用的东西是个坏顺序，以及为什么它里面的空洞是
  正常的。
- [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339) — 这个项目里每一个时刻被打印时所用的形状，两种答案
  形状都是。
- [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) 和
  [Semantic Versioning](https://semver.org/) — 记录的那一行对一次*事故*（而不是一次发布）意味着什么：一份
  别人能读的交代，按事情发生的顺序。
- [The OpenTelemetry semantic conventions for audit events](https://opentelemetry.io/docs/specs/semconv/) —
  同样的五件事实（谁、做了什么、对着哪个对象、什么时候、为什么）作为一份行业词汇，给这份记录有一天被导出而
  不是被读的时候用。
- `course/tracks/jobq/spec/3.26/dlq_cli.rs` — 那八个用例写成的测试，包括十次用法错误和穿过真二进制的那次
  行走。
- `course/tracks/jobq/budget/3.26-dlq-cli.toml` — 闸门读的基线，以及它那四个计数各自意味着什么。
- `jobq/3.16-dlq-tooling` — 端口那一半：那个视图、`revived`，以及那个已经把作业放回去的方法。
- `jobq/3.15-cli-contract` — 那些退出码、两条流和两种答案形状被定下来的地方。
- `jobq/3.6-transaction-isolation` — 这条记录故意*不*属于的那条轨迹。
- `jobq/3.27-runbook-drill` — 队列坏掉时走这扇门的那个演练，以及和这一页并排写的那一页。
