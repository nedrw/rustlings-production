# 讲优先级，但不让谁饿死：一条你站得住的策略

## 回顾

- `http/rate-limit@apply` — `relay/2.13-rate-limit`：挡在服务前面的一只按租户分的令牌桶，写它是为了
  不让一个调用方把别人的容量花光。
- `db/atomic-claim@design` — `jobq/3.7-leases-and-recovery`：原子地取走一个作业、并为它发一份租约的
  那次认领，以及它发放作业的顺序。

## 变化

`relay/2.13` 决定的是调用方*能不能*进来。这一步决定的是**谁等、等多久**——同一个问题的设计那一半，也是
基准测试里看不出来的那一半。

这个失败模式值得直说，因为它在你最先会去看的每一块面板上都看不见：严格优先级，加上一个不断被高优先级工作
重新填满的队列，就是一个吞吐漂亮、而其他所有人的 p99 没有上限的系统。worker 从不空闲，吵的那个队列深度
看起来很健康，而安静的队列里最老的作业是上周二的。

两个旋钮，回答两个不同的问题：

- **aging** — 一个低优先级作业最多能等多久？过了 `aging_after`，它的排名每个间隔上升一级，于是一个不断
  灌水的队列，最终会跟它正在插队过去的那些工作同场竞争。等待从 `run_at` 量起，也就是作业到期的那一刻：
  一个排到明天的作业，今天并没有被饿着；而从行创建的时刻量起，会把一个还没人要求的作业算成被饿着的。
- **`max_in_flight_per_queue`** — 一个队列最多能占住多少池子？由*认领*来执行，因为资源就是在认领的时候
  被拿走的；超出上限的作业既不失败也不推迟，它们留在队列里，等下一个空位来取。

排序住在存储里——持久后端里是认领的那条语句，内存后端里是那次排序——因为行是在
`for update skip locked` 之下选出来的：事后再对结果排序，只是给已经取走的东西排了个序，并不会改变取走
的是哪几行。

## 作业

- 两个存储都在构造时接收一个 `Policy`（`with_policy`），默认是这一步之前引擎的做法：严格优先级，不设
  上限。公平是要来的，不是自己冒出来的。
- 两个后端把它落实成同一个承诺：顺序里用有效排名（`priority + waited / aging`），选择里用上限——Postgres
  上是一条语句，内存里是一个临界区。
- 守护进程从设置项里接上这两个旋钮（`worker.aging_seconds`、`worker.max_in_flight_per_queue`），在
  `--check-config` 里把它们报出来，默认是开 aging、不设上限。
- worker 每一轮仍然*每个*队列都问：一轮是跨队列公平的单位，而一个只是第二个被问到的队列，并不是一个
  被晾着等的队列。

## 完成标准

- `kiln run jobq/3.9-priority-fairness` — 四个规格用例通过。
- `kiln check jobq/3.9-priority-fairness` — 每个 must 闸门都是绿的，包括 `slow:conformance@2`（套件在
  两个后端上都跑）和 `semver@baseline`（表面只多了名字）。
- `jobqd --check-config` 显示出这两个设置项，默认值分别是 `300` 和 `0`。

## 陷阱

1. 在 Rust 里对认领的结果排序，而不是在语句里给行排序——持久后端取走的是数据库挑出来的那些行，所以这次
   排序改的是报告，不是决定。
2. 从行的创建时刻做 aging，而不是从 `run_at`——一个排到一周后的作业会跟现在就到期的工作竞争；这不叫
   饥饿，这叫一个名字好听的 bug。
3. 用*提交*超过上限就拒绝的方式执行这个上限——上限说的是池子，不是队列的深度：一个队列里等着十万个作业，
   只要有两个在跑，它就是健康的。
4. 把超出上限的作业标成失败（或者可重试）——它们根本没跑过。它们的尝试次数必须原封不动，因为被一个满
   池子花掉的重试预算，是花在空气上的重试预算。
5. 把公平设成默认——那么这一步之前写的每一份规格、每一个依赖严格优先级的部署，都会在升级时改变行为。
   默认是旧行为；*守护进程的*默认才是开着 aging，那是进程的决定，不是引擎的决定。
6. 让 aging 的间隔跟租约用同一个数，于是作业的排名和它持有者的恢复截止时间一起动——两个看起来像一个的
   旋钮，等到其中一个该变的那天，另一个也会跟着变。

## 延伸阅读

- Lamport 的 "scheduling queues"，或者任何一本讲 deficit round robin 的教科书——aging 和 DRR 用不同的
  手段回答同一个问题，而它们之间的取舍，正是这一步设计那一半的内容。
- `jobq/3.8-clock-injection` — 为什么"等得够久了"说的是你能拨动的那只时钟，以及为什么饥饿那个用例是
  确定性的，而不是等五分钟。
- `relay/2.13-rate-limit` — 准入的问题，这一步的上限改在认领时回答。
