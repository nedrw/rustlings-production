# 错误类型也是 API 的一部分：变体、来源，以及你承诺得起的措辞

## 回顾

- `err/typed-errors@apply` — `mailer/1.5-errors`：服务的每一种失败方式对应一个变体，一次失败的原因通过
  `source()` 露出来，而不是被压平成一句话；外壳有一个 `exit_code`；从那时起，每个公开的、会失败的函数
  都带 `# Errors` 段。
- `api/library-design@apply` — `jobq/3.2-public-api-baseline`：公开面就是 `jobq::engine` 重新导出的
  东西，会长大的类型标着 `#[non_exhaustive]`，而课程的见证文件（`tests/semver_baseline.rs`）负责说明
  公开面依然成立。`Error` 就是那一步标记为会长大的四个类型之一——其中一次长大，就发生在这里。

## 变化

在 `mailer` 里，这个类型的调用方就是同一个程序：服务自己的测试、自己的二进制、自己的 HTTP 层。这里调用
方是**别人的程序**，于是一个错误类型能负担得起什么，跟着变了：

- **调用方不共享你的依赖。** 原因写成 `sqlx::Error` 的变体，会让每个调用方都依赖 `sqlx`——而
  `jobq/3.4` 要在这个 crate 完全不带持久化后端的情况下把它构建出来。所以存储的原因被装箱了：引擎把后端
  自己的错误交出去，认得具体类型的调用方用 `downcast_ref` 把它取回来，认不得的调用方拿到它的
  `Display`。驱动留在端口后端那一侧，这正是端口存在的意义。
- **引擎分类，调用方决定。** `is_retryable()` 是**调用方**问的问题，因为策略归调用方：试多少次、用什么
  退避、对着什么截止时间。自己拥有重试循环的服务不需要这个区分；一个被自己从没见过的 worker 调用的库
  需要。
- **措辞是公开的。** `Display` 的文本会进 runbook、看板和工单，所以它由**课程**拥有的一个测试钉住。你
  没打算改却改掉的一句话，就是对接口的改动，而这一步就是这种改动在评审里露出来的地方。
- **增长是加法。** 枚举是 `#[non_exhaustive]` 的，每个调用方都写 `_ =>`，所以加一种失败的兼容做法是
  加一个变体——重塑已有的变体才是破坏性改动，它既会打破 `jobq/3.2` 的见证文件，也会打破每个调用方。

这一步为自己的代码树划下的界线是：**调用方可能要一路走上去的失败带 `#[source]`**——存储的，以及
`Io` 背后的操作系统的。`Invalid`、`NotFound` 和 `Config` 保留一句话，因为它们描述的是这个 crate 对一个
值的判断（“`worker.batch` must be at least 1”），而不是别人的失败被原样传了出去。

## 作业

- 把存储的变体的原因设为后端自己的失败：`Store { #[source] source: Box<dyn
  std::error::Error + Send + Sync + 'static> }`。不是 `detail: String`——规格会 downcast 到它自己
  定义的一个类型，以此证明这条链上带的是后端自己的错误。
- `Io` 的 `#[from] source: std::io::Error` 原样保留，连 kind 一起：`io::Result` 上的 `?` 仍然是通往
  那个变体的最短路径，而按 `ErrorKind` 分支的调用方仍然分得了。
- `Invalid`、`NotFound` 和 `Config` 保持原样：各一句话，不是原因的字段上不要挂 `#[source]`。
- 加上 `is_retryable()`：存储的失败返回 `true`，其他一切返回 `false`，后面步骤新增的任何变体也返回
  `false`，直到有人提出相反的理由——这是决定里安全的那一半，也是这个方法的主体只点名那一个可重试变体、
  而不是罗列其余变体的原因。
- `exit_code()` 完全保持原样。`jobqd` 和 `jobqc` 现在就已经在用这些退出码：调用出错是 2，东西找不到是
  3，存储被拒绝是 4，环境坏了是 1；整理那张表是改动两个二进制的契约，不是一次重构。
- 每个公开项都保持有文档，`# Errors` 段也在内：从 `mailer/1.5-errors` 起，`docs:public` 就是 must
  闸门；而 `clippy@3`——这一步把 track 提到的那一档——在 `clippy@2` 之上拒绝 `missing_errors_doc`
  和一份较小的 pedantic 白名单。

## 完成标准

- `kiln run jobq/3.3-library-errors` — 规格的四条主张成立：每个变体的文本都被钉住，链一路走到真正的
  原因，可重试性按类别判，退出码站得住。
- `kiln check jobq/3.3-library-errors` — 每个 must 闸门都是绿的，包括 `clippy@3` 和
  `semver@baseline`：`jobq/3.2` 的见证文件仍编得过，说明你保留的形状正是当初承诺的那个。
- 在 `app/jobq` 里跑 `cargo test -p jobq` — 每套用例都通过，包括更早几步的规格。

## 陷阱

1. **把原因压平成 `detail`。** 留着旧字段，写 `Store { detail: format!("{error}") }`，编得过，打印出来
   的行*一模一样*——而 `source()` 返回 `None`，于是规格以 “the chain must carry the backend's own
   error” 失败：一个想分清连接被重置和约束被违反的调用方，没有任何东西可走。
2. **点名驱动的类型。** `Store { #[source] source: sqlx::Error }` 是“不装箱”的诱人写法。
   `tests/spec_library_errors.rs` 是在没有 `sqlx` 的情况下编译的，于是它以
   `error[E0308]: mismatched types` 编不过——而且这个 crate 不再*装配得起来*：把它挡在特性开关后面，
   `jobq/3.4` 的 `--no-default-features` 构建编不过；不挡，它就把一个数据库驱动拖进每个只想要队列的
   调用方的二进制里。
3. **对 `is_retryable` 太慷慨。** 给 `Io` 返回 `true`（“一次读可能被打断”），或者对 `Invalid` 网开
   一面（“调用方也许能改好”），听起来都合理，却会在它点名的类别上让规格失败：`Error::Io` 的
   retryable = false——*一块写满的磁盘，不会因为你再问一次就空出来*。
4. **重塑一个变体，而不是加一个。** 给 `Config` 改名，或者把 `Io` 并进去，会改掉 `jobq/3.2` 的见证
   文件所匹配的形状：`cargo test --test semver_baseline` 以
   `error[E0599]: no variant or associated item named …` 失败，这正是基线在履行职责——改动是允许的，
   但它得付代价。
5. **人都已经在文件里了，顺手改句话。** `store: {source}` → `store failure: {source}` 看着像可读性
   修复；它是对一个已发布字符串的改动，规格钉住的文本会因此失败。运维会在凌晨三点 grep 这些行。

## 延伸阅读

- [`thiserror`](https://docs.rs/thiserror/latest/thiserror/) — `#[error("…")]`、`#[source]`、
  `#[from]`，以及一个叫 `source` 的字段不带属性时会怎样。
- [`std::error::Error::source`](https://doc.rust-lang.org/std/error/trait.Error.html#method.source) 与
  [`downcast_ref`](https://doc.rust-lang.org/std/error/trait.Error.html#method.downcast_ref) — 调用方
  怎么走一条链，又从里面把具体类型取回来。
- [`std::io::ErrorKind`](https://doc.rust-lang.org/std/io/enum.ErrorKind.html) — `io::Error` 本来就
  带着的类别，这也是保留整个错误、而不只是它的消息的原因。
- [Rust API guidelines: error types](https://rust-lang.github.io/api-guidelines/interoperability.html#error-types-are-meaningful-and-well-behaved-c-good-err)
  — `C-GOOD-ERR`，那条“错误类型要有意义、行为良好，且是 `Send + Sync + 'static`”的规则。
