# 状态码是 API 的一部分

## 为什么

gRPC 的状态码是一个小而封闭的集合，而客户端按它分支：退避会重试 `UNAVAILABLE`，表单会为
`INVALID_ARGUMENT` 显示消息，而没人会重试 `INTERNAL`，因为它不会自己变对。把一个内部失败映射到
错误的状态码不是装饰——把校验错误报成 `UNAVAILABLE` 是一场永远不可能成功的重试风暴，把数据库宕机
报成 `INVALID_ARGUMENT`，则是一个在"重试是唯一解药"的时候恰好停止重试的客户端。

这个集合小是故意的。六种失败覆盖了服务失败的方式，每一种有一个规范状态码；重试与否由状态码推出，
不由每个调用点各自判断。

## 任务

脚手架加上了 `src/status.rs` 和它的 `pub mod status;` 那一行；两个函数都是桩。

- **[`code_for`]**——内部失败的规范状态码：错误的请求是 `INVALID_ARGUMENT`，查不到的行是
  `NOT_FOUND`，重复是 `ALREADY_EXISTS`，过载的服务端是 `RESOURCE_EXHAUSTED`，程序 bug 是
  `INTERNAL`，依赖不可用是 `UNAVAILABLE`。
- **[`retryable`]**——`UNAVAILABLE`、`RESOURCE_EXHAUSTED`、`DEADLINE_EXCEEDED` 为 `true`；
  `OK`、`INVALID_ARGUMENT`、`NOT_FOUND`、`ALREADY_EXISTS`、`INTERNAL` 永远不是。

## 完成标准

- `kiln run rpc/8.3-status-codes` —— 规格通过
- `kiln check rpc/8.3-status-codes` —— 每个 must 闸门都是绿的
- 过载的服务端与挂掉的依赖可重试；程序 bug 与错误的请求不可重试

## 陷阱

1. **什么都报 `INTERNAL`。** 这个兜底码把每个校验错误变成一次呼叫，把每次可重试的故障变成"服务端
   bug"；规格里的六条映射测试就是抓它的。
2. **重试调用方的错误。** `INVALID_ARGUMENT` 每次尝试都会以同样的方式失败；围着它转的重试循环是一
   场结果固定的压测。
3. **不重试 `RESOURCE_EXHAUSTED`。** 过载恰恰是*停一下再试*能治的那种失败；把它映射成 `INTERNAL` 就把这层价值丢了。
4. **用 HTTP 的词汇发状态码。** `404` 与 `NotFound` 是同一个想法，不是同一个协议：gRPC 客户端按
   gRPC 码分支，而正文里写着 "404" 的状态会被它解析成 `UNKNOWN`。
