# deadline 是绝对的，每一跳都从它里面付

## 为什么

超时是一段时长，而时长从被读到的时刻开始。deadline（截止时间）是一个时间点，而时间点在每一跳上是同一个数字：
客户端算出 `now + budget`，服务端读到的就是那一刻，减去自己花掉的，把剩下的传下去。gRPC 在线上
传 deadline 而不是超时，正是为此——换成时长，三跳的链就有三个时钟，真实预算成了三者之和。

边界才是这一课：一跳可以恰好花掉剩下的全部（调用于是预算为零、已经完成），而需要更多的一跳要在
**跑之前**失败。一个开始做自己完成不了的工作的服务端，花的是下一跳的预算去算一个没人会读的结果，
而客户端最后收到的仍然是 `DEADLINE_EXCEEDED`——更晚，且工作白做。

## 任务

脚手架加上了 `src/deadline.rs` 和它的 `pub mod deadline;` 那一行。`remaining` 是现成的；`call`
是桩。

- **[`call`]**——从 `now` 出发、对着绝对的 `deadline` 走 `hops`，每一跳减去它自己的开销；回答剩下的
  预算，或在第一处装不下的跳上回答 [`Status::DeadlineExceeded`]。
- **已经过去的 deadline 在第一跳之前就失败**，包括根本没有跳要跑的时候。

## 陷阱

1. **跳上写成 `>=`。** "需要全部剩余预算的一跳算失败"会让每一次刚好在预算内完成的调用超时，而一条
   调好的链上，最后一跳永远是恰好装下的那一跳。
2. **每一跳一个时长。** 每一跳重置时钟就是超时模型，链有多长预算就有多长；规格的算术从头到尾只有
   一个 deadline。
3. **跑完再判失败。** 在一跳跑完之后检查 deadline，花掉了预算再报告失败——正是这条规则要避免的
   白工。
4. **忘了起点。** `call(deadline, now, …)` 在 `now >= deadline` 时必须失败，哪怕 `hops` 是空的：
   客户端在开口之前就已经没时间了。
