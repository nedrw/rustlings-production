# 线路上是号码，不是名字

## 为什么

protobuf 的消息在线上是一串 `(号码, 值)` 对。名字存在于 `.proto` 文件、生成的代码和文档里——从来
不在字节里。想清楚这一层，一次改动意味着什么就自己推出来了：

- **改名兼容**——线路从来没有携带名字，按旧 schema 构建的客户端读的是同一个号码；
- **新号码兼容**——旧读取方会跳过它不认识的号码；
- **删掉一个号码会破坏还在发送它的客户端**，而**复用**一个号码换一种类型更糟：旧客户端的字节
  现在被按新类型解析，悄无声息，哪一处都不报错。

这就是 `.proto` 文件里那些 `reserved 3, 5;` 的来处——退休的号码不再发出去，而兼容性检查器就是
在你试图复用时告诉你的那个工具。

## 任务

脚手架放好了 `src/lib.rs`：消息类型在里面；`wire` 是桩。

- **[`wire`]**——旧消息与新消息之间每一处破坏性差异，按号码排序：[`Breaking::NumberRemoved`] 是
  号码没了，[`Breaking::NumberReused`] 是同一个号码换了类型。
- **号码搬家算删除。** 旧号码没了（客户端还在发它），新号码就是新的；这一对不是"改名"。

## 完成标准

- `kiln run rpc/8.1-field-numbers` —— 规格通过
- `kiln check rpc/8.1-field-numbers` —— 每个 must 闸门都是绿的
- 把 `status` 改名为 `state` 兼容；把 `count` 从数字改成文本不兼容

## 陷阱

1. **按名字比对。** 直觉的 diff（`old.name != new.name`）把每次改名都报成破坏，又漏掉一个名字不变、
   类型变了的号码——两个方向都错，而第二个才是危险的。
2. **把号码搬家报成改名。** `(2, "status") → (9, "status")` 是删掉号码 `2`、新增号码 `9`；把它当
   兼容放过，客户端就会把 `2` 发进虚空。
3. **只查旧的那一边。** 新号码上的新字段没问题，但*退休的*号码上的新字段有问题——第二个循环
   （新号码与已删号码相撞）才是 `reserved` 挣工资的地方。
4. **返回一个布尔值。** "兼不兼容"藏起了是哪几个号码坏了；评审者正在改一份 `.proto`，他要的是列表。
