# 流是一个窗口，不是一个缓冲

## 为什么

服务端流式读起来像"把条目产出来"，实际上是"客户端有多少地方就产多少"。地方就是流控窗口：发出去
但还没被确认的条目在途，发送方在窗口处停下。越过窗口继续发送的生产者不是在流式，而是在按生产者
的条件替消费者缓冲内存——2.14 里那条无界队列，低了一层，也更难看见，因为 API 看起来只是一个
`for` 循环。

窗口也让失败模式变得诚实：慢消费者表现为一个满窗口（服务端在等），而不是一个不断增长的堆和一次
看起来像泄漏的 `OOM`。

## 任务

脚手架加上了 `src/stream.rs` 和它的 `pub mod stream;` 那一行。`new`、`in_flight`、`ack` 是现成的；
`send` 是桩。

- **[`Stream::send`]**——在途条目少于 `window` 时给出下一条；窗口满了或条目发完了就是 `None`。
- **满窗口是背压，不是结束**：调用方确认之后再来一次。

## 完成标准

- `kiln run rpc/8.4-server-streaming` —— 规格通过
- `kiln check rpc/8.4-server-streaming` —— 每个 must 闸门都是绿的
- 窗口为二时发两条然后 `None`；一次确认之后第三条通过

## 陷阱

1. **无视窗口。** 没有 `in_flight` 检查的 `self.items.get(self.sent)` 会把全部发出去、替消费者缓冲
   内存——规格里*"窗口被越过了"*就是这条断言。
2. **把 `None` 当流结束。** 调用方不再问；客户端收到一个前缀，还以为那就是全部。窗口重新打开靠的
   是同一次 `send` 调用。
3. **发送时减窗口、确认时不加。** 一个窗口之后流就停住了。
4. **确认比发送的还多。** 夹取是给定的（客户端批量确认时 `ack` 可以超过 `sent`）；题本身不能把它
   重复算进在途。
