# 一条连接，多条流，没有队头阻塞

## 为什么

HTTP/2 做多路复用：一条连接承载所有调用，每条流有自己的流控窗口。多路复用存在的意义是去掉队头
阻塞——一条流上的慢消费者不能拖住别的流——而这只有在窗口**按流**查询时才成立。一条连接级的队列
把 HTTP/2 发明出来要移除的阻塞原封不动地带回来，只是高了一层、更难找：那条快的调用不是被网络堵住
的，是被调度器堵住的。

pump 就是调度器，它的公平规则就是这个设计决定：每轮每流一项，直到整整一轮什么都没发出去为止。
这样一条大流饿不死一条小流，而一条被阻塞的流是**被跳过**的流，不是停下来的 pump。

## 任务

脚手架加上了 `src/multiplex.rs` 和它的 `pub mod multiplex;` 那一行。[`Connection`] 与它的访问函数
是现成的；`pump` 是桩。

- **[`pump`]**——对流做轮转：每轮每流一项，窗口已满的流跳过；整整一轮什么都没发出去就停；按发送
  顺序回答 `(下标, 条目)` 对。

## 完成标准

- `kiln run rpc/8.5-multiplexing` —— 规格通过
- `kiln check rpc/8.5-multiplexing` —— 每个 must 闸门都是绿的
- 下标 0 的流被阻塞，不影响下标 1 的流；每流窗口为二时，两轮以交错顺序发完

## 陷阱

1. **一条连接级的缓冲。** 全部收下来再按顺序发：一个慢消费者拖住所有别的流——正是这一步要讲的
   队头阻塞。
2. **遇到第一个 `None` 就结束这一轮。** 一条被阻塞的流结束了这一遍，它后面的流永远发不出去；规格里
   *"被阻塞的流不影响别的流"*就是这个。
3. **一次只服务一条流。** 把流 0 排干再服务流 1，只有在流 0 很小时才算公平；轮转顺序才是让答案有界
   的东西。
4. **没人能发时不退出。** 没有"没有进展"这个出口的 `loop`，会在所有窗口都满的连接上空转。
