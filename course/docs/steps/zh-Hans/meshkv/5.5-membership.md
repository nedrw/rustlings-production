# 节点加入、节点离开，而没有一条已提交的写入掉出多数派

## 为什么

每个集群都是临时的。机器会被换掉，地域会被加上，节点会为了维护被排干——而在这期间绝不能发生的
一件事，是一条已提交的写入掉出多数派；因为掉出去的已提交写入可以被覆盖，而一个被覆盖的决定，正是
复制日志存在要防的那种失败。

危险的形状写下来就很明显：如果配置能一步改完，就会有一瞬间，旧投票者和新投票者各自以为自己就是
集群。两个不相交的多数派于是可以在同一个 index 上决定两件不同的事，而两件都被自己那一方算作
「已提交」。

Raft 的答案是**联合共识**，这一步实现的正是这个形状：

1. leader 追加一条配置条目，把**两套**成员都写进去。从那一刻起，做一个决定既需要旧集合的多数派，
   **也**需要新集合的多数派——成员关系是*联合*的；
2. 那条条目一提交，每个节点就采用新配置、忘掉旧的。

只要集群是健康的，旧集合的任意多数派和新集合的任意多数派都相交，所以每一瞬间都恰恰只有一个多数派
——这个窗口是靠构造关死的，不是靠时序。

两个细节让它成为 `apply` 级别的步骤，而不是一段话：

- **配置是一条日志条目**，于是它跟那些它不能弄丢的写入之间是有序的。一次抢在一趟在途写入前面的
  变更，就是一次把它弄丢的变更。
- **变更只能由两套集合共同决定**，所以发起变更的 leader，没法靠它正要离开的那个集群的多数派把变更
  做完，也没法在它正要加入的集群拿到那条条目之前做完——而这正是全部的意义所在。

## 任务

- `src/raft/membership.rs`——`Config`（投票者，从 `n1,n2,n3` 解析，拒绝空清单和重名）、
  `Membership::{Stable, Joint}`，带 `is_met`、`targeted`、`voters`、`is_joint`，以及把配置放进
  条目载荷的那两个函数（`encode`/`decode`）。
- `src/raft/state.rs`：
  - `membership()`：这个节点所处的配置，以及有没有一次变更在途；
  - `decided`：一个决定归成员关系来定——稳定时一个多数派，联合时两个都要；
  - `begin_membership(target)`：只限 leader，一次一个，追加配置条目，并把节点推进联合状态；
  - 变更在途期间，`peers()` 是两套集合的并集：要加入的节点得收到它们将要投票的那些条目，要离开的
    节点得一直收到，直到变更提交；
  - 一条已提交的条目如果是一条配置，leader 和 follower 都会采用它——这是联合共识的后一半。一条
    **没有**提交的配置条目，什么都不改变。
- `tests/sim_membership.rs` 是课程内容（由这一步附带）：它把几个状态机当成一个值层面的集群来驱动，
  种子决定谁的选举超时先响、消息按什么顺序到达。

## 完成标准

```sh
cargo test -p meshkv --test spec_membership      # the nine cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_membership -- --nocapture
```

第二条打印出这样一份记录：

```text
meshkv-sim elect leader=n1
meshkv-sim write index=2 committed=1
meshkv-sim change voters=5 joint_before=1 joint_after=0
meshkv-sim write index=4 committed=1 joined=1
```

而另一个种子选出另一个 leader——不管谁赢了，集群都得对同一个答案达成一致。

## 陷阱

- **变更在途时，旧集合的多数派不是一个决定。** 联合阶段存在的意义就是防这种失败：它会让正在离开
  的集群提交一条正在加入的集群能覆盖掉的写入。
- **新节点还没拿到日志之前，新集合的多数派同样不是一个决定。** 它们有的是状态机，不是条目：一个
  决定需要新集合里*持有这条条目*的多数派，而数的是确认，不是名字。
- **配置是一条条目，它的位置要紧。** 它跟一次写入走同一套 `prev`/`match` 机械，正是这一点让变更
  加不到在途写入的前面去。
- **变更不在追加的时候结束。** 它在配置条目*提交*的时候结束——而那次提交，恰恰就是要求两个多数派
  的东西。
- **一个离开的节点不再是对端，它的确认也不再计数。** 一个一直去问已离开节点的集群，会在一台已经
  断电的机器上死锁。
- **一次只做一次变更。** 两条配置条目同时在途，就是两个窗口，而第二个可能被第一个还没达成一致的
  集合提交掉。

## 延伸阅读

- Raft 论文 §6（「Cluster membership changes」）就是这一步，包括为联合阶段给出的论证：两套集合必须
  相交，而保证这件事的唯一办法，就是变更在途期间两个多数派都要。
- `openraft` 把同一对叫 `Membership::{Stable, Joint}`；名字一样，两个 `is_met` 分支也一样，因为协议
  是同一个。
- `5.21` 会同时跑集群的两个*版本*——同一个窗口，只是两套集合的差别不在它们是谁，而在它们说的是
  什么。
