# 延迟与吞吐对节点数：三条轴上的预算

## 为什么

"它能扩展吗？"不是一个用"能"回答的问题。它是一个用**预算**回答的问题：一次写入要花多少条消息、要
多少个确认才能定夺、这些活里每个节点做多少，以及调用方要等几个往返。

三条轴，每一条都是读者算得清的算术：

- **多数派**——`⌊n/2⌋ + 1`，在这个 track 里决定一切的那个数，从成员变更（`5.5`）到分区（`5.14`），
  再到滚动重启（`5.15`）；
- **扇出**——`n − 1`，leader 每笔写入发出的消息数；
- **确认**——`quorum − 1`，leader *等*的就是这个数。扇出和确认是两个不同的数，拿一个顶另一个的
  预算，不是把网络说大了，就是把延迟说大了。

这里的每个数字都是**计数**，从不是时间：计数在忙的机器上和闲的机器上是同一个，这也是这一步的闸门叫
`bench-budget`、而这一步自己的算术就是基线的原因。

## 任务

- `src/budget.rs`——这一步新增的模块：
  - `cost(nodes)`：一笔写入加一次线性一致读的
    `Cost { nodes, quorum, messages, acks, write_hops, read_hops }`；
  - `workload(nodes, writes)` → `Counts { messages, acks, leader_messages, follower_messages, hops }`；
  - `Counts::per_node()`：每个节点平均的消息数——这个数字随集群*上升*，因为 leader 的份额跟着集群涨，
    follower 的不涨。
- `budget/5.17-distributed-budgets.toml` 和 `tests/budget_distributed.rs` 是课程内容：
  `bench-budget` 闸门读的基线和装置。
- `docs/budgets.md`——这一步交付的页面（`links` 判它），带着模型生成的那张表。

## 完成标准

```sh
cargo test -p meshkv --test spec_distributed_budgets     # the five cases
cargo test -p meshkv --test budget_distributed -- --nocapture
```

第二条打印闸门拿来比较的计数：四千条消息、两千条确认、四千条 leader 消息、每个 follower 一千条、
一跳。

## 陷阱

- **扇出不是定夺。** leader 发给每一个同伴，却只等一个多数派；把发送当成等待来数的预算，会把延迟说大；
  把等待当成发送来数的，会把网络说小。
- **加一个节点不是免费的。** 节点每多一个、写入每多一笔，leader 的活就多一条消息；冗余是真的，代价
  也是真的，而每个节点的平均数*升*而不是降。
- **计数，从不计时。** 预算一旦是时长，就成了一个在忙机器上红、在闲机器上绿的预算——它教给人的，是
  哪些改动免费，而教的正好是反的。
- **多数派是一个数，处处都用它。** 如果这一步的模型和 `5.15` 的滚动重启在多数派上说法不一致，其中
  必有一个是错的；它们故意就是同一个 `⌊n/2⌋ + 1`。
