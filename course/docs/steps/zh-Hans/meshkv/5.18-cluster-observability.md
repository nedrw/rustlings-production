# 谁落后，谁在抖：集群的 SLO 页面

## 回顾

- `obs/metrics-slo@aware` — `mailer/1.20`：黄金信号、`/metrics`，以及给一个指标起名，让别人找得到它。
- `obs/metrics-slo@apply` — `relay/2.18`：延迟分位数和每个租户的积压，从计数器上读出来。
- `obs/metrics-slo@design` — `jobq/3.17`：错误预算，花掉预算的告警阈值，以及没有指标时该怎么下判断。

## 变化

三个服务做下来，信号已经眼熟，*失败*却还不眼熟。服务失败，是因为慢或者错；集群失败，是因为彼此意见不
合，而显示这一点的计数器，是服务从来不会有的：

- **落后**：一个 follower，已应用的索引离 leader 的提交越来越远；这样的节点最晚察觉 leader 更替，又最
  先在更替发生时变成问题。
- **抖动**：一个节点一遍遍参选，另一个却一直赢，说明它有钟或者网络的问题；一个节点拒绝写、却一条也没提
  交，说明它落在了分区的错误一侧。

SLO 还是 `jobq/3.17` 那个想法，只是用在*一致*上：一个目标就是关于一个比值的承诺，而错误预算就是这个比
值剩下的部分。新的地方在于，这里的预算是在计数器上做算术——是整数，不是时间——因为一个需要钟的预算，会
跟着机器一起动。这一步不重新推导预算；它把预算放到一个集群上。

## 任务

- `src/metrics.rs`——这一步新增的模块：
  - `NodeMetrics`：各 peer 的索引、参选与当选的次数、拒绝与提交、已应用索引；
  - `lag(peer, commit)`：没见过的 peer，落后量是*未知*，不是零——拒绝时会说出来；
  - `most_behind(commit)`：运维者该先去看的那个 peer；
  - `lost_elections` 与 `is_suspect`：一个故障节点会有的两种形状；
  - `Slo::new(objective_ppm)` 和 `budget_left(commits, attempts)`：比值算术，用整数做。
- `docs/slo.md` 和 `tests/budget_slo.rs` 是课程内容：那一页（`links` 判它）和 `bench-budget` 闸门读的
  装置。

## 完成标准

```sh
cargo test -p meshkv --test spec_cluster_observability     # the five cases
cargo test -p meshkv --test budget_slo -- --nocapture
```

第二条打印落后量、抖动计数器和剩余预算：分别落后十条和五十条，没有丢失的选举，十次失败的预算还剩八次。

## 陷阱

- **未知的落后量不是零。** 一个谁也没听说过的 peer，没有落后量可报；一个答零的计数器，会让最安静的节点
  看上去最健康。
- **跑在提交前面的 peer 不是「负的落后量」。** 落后量下限是零。
- **输掉选举是个信号，而赢下来还不够。** 一个参选九次、只赢一次的节点，就是该去看的节点，哪怕它赢了。
- **只有拒绝、没有提交，是另一种形状。** 一个拒绝了写、却一条没提交的节点，落在了分区的错误一侧——计数
  器会说出那是哪个节点。
- **预算是整数算术。** `attempts × (1 − objective) − failures`，下限为零；用浮点数算出来的预算，换一台
  机器就会差一，而差出来的那一次，正是有人拿来做发布决定的那一次。

## 延伸阅读

- `5.22` 的审计是另一半：这里的计数器，是每个节点关于*自己*的说法，而审计拿各节点的视角互相比对。
- SLO 的形状，是 `lakelet/4.20` 的容量模型用在可用性而不是字节上：一个预测、一次测量，而两者之间的漂移
  才是受判的东西。
