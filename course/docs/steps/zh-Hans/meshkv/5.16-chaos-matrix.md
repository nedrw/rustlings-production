# 一切能坏的东西，故意弄坏，收进一张测试读的表

## 为什么

`5.13` 给了故障一套词汇；`5.14` 和 `5.15` 深入断言了其中两种。这一步问的是 runbook 会问的问题：
**每一种故障，预期行为是什么？**——再把答案写成一张矩阵。

矩阵是数据，而且从两边检查：用例在代码里，同一张表在项目的页面上，规格把两者对起来。这是
`lakelet/4.3` 的戏法（一个决定是一个值加一句话，规格检查两者一致），用在故障清单上——它成立的理由
也一样：一页跟代码走散了的文档，会让运维去相信一种没人实现的行为。

每一行回答三个问题，因为只有三个都答上了，一种故障才算被理解：

| 列 | 问题 |
| --- | --- |
| fault | 注入了什么，用 `5.13` 的词汇 |
| client sees | 调用方能照着行动的那句话 |
| invariant | 无论调度怎样，集群仍必须守住的东西 |

## 任务

- `src/chaos.rs`——这一步新增的模块：
  - `Case { fault, client_sees, invariant }` 和 `MATRIX`，一种故障一行；
  - `covers` 和 `case_for`：runbook 可以用的那套词汇；
  - `check()`：矩阵不许把一种故障写两遍、不许留空格子，也不许两列说同一件事。
- `docs/chaos.md`——这一步交付的页面（`links` 判它）：同一张表，外加怎么读一行、加一种故障要付什么
  代价。

## 完成标准

```sh
cargo test -p meshkv --test spec_chaos_matrix
```

是绿的，尤其是读页面的那个用例：代码里的矩阵和页面上的表，必须一行不差、一字不差地相同。

## 陷阱

- **两列的性质不同。** "节点下线期间写入被拒绝"是调用方观察得到的，拿来做事后断言却毫无用处；"节点从
  日志里追上来"才是演练要检查的东西。两列写着同一句话的表，只有一列。
- **矩阵之外的故障没有预期行为。** 注入它是一次实验，不是演练——`covers` 之所以存在、规格之所以检查
  它，道理就在这里。
- **矩阵与页面逐行比对。** 一边加了一行、另一边没加，就是一页（或一条代码路径）在撒谎；把两者拴在一起
  的，只有规格。
- **重复的一行是一个被忘掉的故障。** `check()` 会拒绝它，因为一种故障写两遍的矩阵，是一张有洞的矩阵。

## 延伸阅读

- `5.22` 的审计把矩阵的最后一行变成可操作的：每一种故障之后，集群提交的东西，就是每个节点最后持有的
  东西。
- `test/chaos-injection@apply — relay/2.17` 在 HTTP 边界注入故障；这一步是同一个想法，换上了集群
  自己的词汇，而矩阵正是让它成为 runbook、而不是一串实验的东西。
