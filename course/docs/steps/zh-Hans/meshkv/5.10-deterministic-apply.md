# 状态机是日志的纯函数，而测试能证明这一点

## 为什么

这条 track 的前九步一直在搬运条目。没有一步说过一个条目*意味着*什么。这一步是日志变成键值存储的地
方，也是那句让复制存储成为可能的话终于必须成真的地方：

> **状态是条目的函数，别的什么都不是。**

两个节点按同样的顺序应用了同样的条目，就持有同样的状态——逐字节相同。正是这一点让 leader 和
follower 意见一致，让重启的节点追上来，也让 `5.4` 的快照成为事实而不是看法。它也是随便一行大意代码
就能打破的那句话，而破碎要等到两个副本各执一词、都坚称自己对，才会露出来。

常见的嫌疑犯都很无聊：

- **哈希表的迭代顺序。** 两个节点插入同样的键，迭代的顺序却不同。如果状态的序列化形式依赖这个顺
  序，两个副本明明持有同样的数据，却对自己的摘要各执一词。
- **时钟。** 读 `now` 的状态机，每次重放都在应用一个不同的函数——而重启后重放日志的 follower，对发
  生过什么会和 leader 意见不一。
- **随机性**（复制函数里没有它的位置）和**浮点数**（只在与自己相同的平台和指令集上与自己一致）。

所以状态是一张**有序**映射，摘要按键的顺序走，而 API 里**哪儿都没有时间参数**。最后这一条是类型层
面的声明：这一步的代码没有地方放一个时钟，这比一句说它不读时钟的注释更硬。

## 任务

- `src/kv.rs`——这一步新增的模块：
  - `Command::{Set, Cas, Delete}`，从条目的载荷解析出来（`set k v`、`cas k expect new`、
    `delete k`，值用十六进制），再编码回同样的字节。解析很严格：格式不对的命令是一个拒绝，不是一
    次猜测。
  - `Kv`：一张从键到值的 `BTreeMap`，加上最后应用的下标。`apply(index, payload)` 拒绝任何不是恰
    好下一个下标的东西——状态机应用的是日志的一个*前缀*，所以缺口、重复、倒退，都被拒绝，而不是被
    猜过去。
  - `Applied::{Written, Removed, Absent, Mismatch}`：一个条目做了什么，包括比较并交换需要的两种情
    形（值对上了，或者这里是它实际装着的值）。
  - `digest()`：按键的顺序，把键和值过一遍 FNV-1a。两个持有相同数据的节点产出相同的摘要，不管表是
    按什么顺序建起来的。
- `tests/sim_kv.rs` 是课程内容：两台机器，一份日志，同一个摘要——种子决定日志，另一个种子就是另一
  份日志。

## 完成标准

```sh
cargo test -p meshkv --test spec_deterministic_apply          # the nine cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_kv -- --nocapture
```

第二条打印整份日志走完之后的摘要，然后是一台*全新的*机器重放同样条目得到的摘要——两者是同一个数。

## 陷阱

- **哈希表的迭代顺序，是破坏确定性的经典手法。** 状态用的是 `BTreeMap`，摘要按键的顺序走；在这里换
  成 `HashMap`，是一个只在某个种子下才现形的正确性 bug。
- **状态机里没有时钟。** 不是“暂时没有时钟”——API 里根本没有，所以没有地方可放。时间是*请求*的属
  性（`5.8` 的窗口），不是 apply 的属性。
- **按顺序应用，其余的一概拒绝。** 接受缺口的状态机，它的状态就取决于哪些条目碰巧到了。
  `index != applied + 1` 是一个拒绝。
- **失败的比较并交换什么也不改。** 它回答 `Mismatch`，带上*确实*装着的那个值，好让调用方去决定；
  照样写下去，等于把 CAS 变成多绕几步的普通 set。
- **摘要算的是内容，不是历史。** 两份日志用不同的顺序写了同样的键，到达同一个状态，就必须得到同一个
  摘要——这才让它成为状态的摘要，而不是日志的摘要。
- **载荷就是命令。** 共识层把一个条目当成字节（`5.3`）；这里是字节第一次被解释的地方，而解释的方式
  就是这一步的全部契约。

## 延伸阅读

- Raft 的论文把它叫作*状态机*：把日志确定性地应用到一个状态上。真正干活的是“确定性”这个词，而
  §5.4.3 解释了为什么 leader 不得提交一个 follower 会以不同方式复现的状态。
- `5.13` 在模拟网络下跑这段代码，段边界就在日志本身里；不确定性的 apply 会让那个装置时好时坏，这
  条规则正是靠这一点一直执行下去。
- `5.22` 的审计把集群提交的状态和每个节点持有的状态做比较——就是这一步算的那个摘要，范围换成整个集
  群。
