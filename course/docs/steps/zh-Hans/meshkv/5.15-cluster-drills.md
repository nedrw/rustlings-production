# 一次一个节点：从不丢掉多数派的滚动重启

## 为什么

`5.14` 把分区变成了断言。这一步是运维的那一半：滚动重启是运维对集群*做*的事，而规则是同一套算术，
只是用在排程上而不是故障上。

> 重启的每一个瞬间，集群里都必须有多数派在线。

三节点的集群可以失去一个节点，五节点的可以失去两个。一个在第一个节点回来之前就拿下第二个节点的
计划，会把集群停掉——而它在电子表格里看起来完全合理。这就是这一步要讲的失败，答案是先把计划做成
一个**值**，在碰第一个节点之前就检查它的多数派。

## 任务

- `src/restart.rs`——这一步新增的模块：
  - `Plan::new(members, order)`：顺序是成员的一个排列，要检查（不缺节点、没有外人、没有重复）；
  - `Plan::majority()`：`⌊n/2⌋ + 1`；
  - `Plan::run(up)`：按顺序走，把每个节点拿下再放回，拒绝那个会让在线节点少于多数派的一步。已经
    下线的节点轮到它时会被放回，而在它之前的每一步里都算下线；
  - `Step { node, was_up, majority_kept }`：runbook 打印的时间线。
- `docs/restarts.md`——这一步交付的页面（`links` 判它）。

## 完成标准

```sh
cargo test -p meshkv --test spec_cluster_drills
```

是绿的，而六个用例说的是：计划是一个排列；三节点集群熬得过一次滚动重启；五个节点可以失去两个，
三个不行；下线的节点轮到它时被放回；会让集群停掉的计划被拒绝；空计划也被拒绝。

## 陷阱

- **顺序不是计划。** 计划的排程由运维来选；让它成为计划的，是每一步的多数派检查，而不是谁写下的那个
  顺序。
- **已经下线的节点要算数。** 轮到它时它会被放回，但在那之前的每一步它都下线；一个忘了这一点的计划，
  会把集群带到两个节点，还以为自己有三个。
- **拒绝是逐步的，而且点出是哪一步。** "这个计划会停掉集群"是一句带着节点名字的话；拒绝里带着那个
  节点、在线的节点数，以及需要的节点数。
- **什么都不改变的重启是个错误。** 中间没有故障，却把同一个节点重启两次，是一个报告了自己没做的工作的
  计划；排列检查会拒绝它。

## 延伸阅读

- 这套算术就是 `5.5` 用在成员变更上的多数派规则：旧的多数派与新的多数派必须相交，而滚动重启是配置
  压根不变的那个特例。
- `5.18` 把重启放上仪表盘：集群的可用性预算就是同一套多数派算术，只是写成了 SLO。
