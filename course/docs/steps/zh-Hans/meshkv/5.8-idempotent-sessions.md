# 重试不是第二次写入：会话，以及让重试成立的那些键

## 为什么

`5.7` 教会了客户端找到 leader。这一步讲的是它找到之后发生的事，因为那个问题的答案常常是
*什么都没有*：请求超时了，而客户端分不清是写入提交了，还是请求根本没到。两者从外面看一模一样，而
客户端唯一安全的动作是再问一次——这没问题，只要再问一次不是第二次写入。

这里防住的失败既不假想，也不微妙。客户端重试一个它已经发过的 `Set`，leader 应用了两次，本该加一次
的值加了两次。写入每次都“成功”；账是错的。在支付系统里，那是钱；在作业队列里，那是同一个作业跑了
两遍。

机制有两半，两半都需要：

- **会话。** 与集群对话的客户端需要一个能挺过重试的身份，而会话同一时刻只能绑到*一个* leader 上：
  一次跨过领导权变更的重试，是一个由别的 leader 必须认出来的请求。
- **幂等键。** 客户端给它只打算做一次的写入带一个键。leader 记住它应用过的键，连同它给出的答案，而
  一个带着它见过的键的请求不会再被应用——它被*再回答一次*，用同一个答案。

心思花在第二半上，而这一步讲的就是它：

- 重复的请求必须回**原来那个**答案，不是新算出来的——问了两遍的客户端，不能为一次写入看到两个不同
  的结果；
- 键必须被记住一个**窗口**，长得足以覆盖客户端的耐心，而窗口必须*有界*，因为它每次写入要花一个条
  目。

## 任务

- `src/idempotency.rs`——这一步新增的模块：
  - `IdempotencyKey` 和 `Session`：带 id 的会话（匿名会话被拒绝——重试时它认不出来），以及
    `key_for(request)`，它从会话和请求推出一次打算做的写入的键；
  - `Answers`：记住的键、它们对应的答案，以及作答的时刻，`expire(now)` 把窗口外的丢掉；
  - `Ledger`：`apply(key, now, apply)`——这一步的心脏。它记得的键*不会*再被应用一次；本该应用一次
    新写入的闭包根本不会被调用，而原来的答案以 `Outcome::Duplicate` 返回。新键会被应用，并以
    `Outcome::Applied` 记住。
  - `default_window()`：课程交付的窗口，长得够一个客户端重试一分钟。
- **失败**的写入不能留下记住的答案——被拒绝的写入不是写入，记住它，会让后来的重试用一个从未应用过
  的失败作答。

## 完成标准

```sh
cargo test -p meshkv --test spec_duplicates
```

通过，而它拿住的用例是：同一个会话里的同一个请求有同一个键，重试用原来的答案作答且只应用一次，键在
窗口内被记住、出了窗口被忘掉，失败的写入不被记住，以及答案的界是窗口，而不是写入的次数。

## 陷阱

- **重复的请求必须被回答，不是被拒绝。** 重试的客户端想要它从没拿到的那个答案；回答“已经应用过
  了”，是客户端还得懂的第二套协议。
- **答案必须是原来那个。** 如果重复的请求被重新回答，客户端就会为一次写入看到两个不同的结果，分不
  清哪个是真的。
- **应用写入的闭包，在重复请求上不得运行。** 规格数调用次数：一个先调闭包再扔掉结果的台账，把这次
  写入应用了两次。
- **失败的写入不留键。** 记住一次失败，会让重试用一个从未应用过的失败作答——而客户端会对一次仍可
  能成功的写入放弃。
- **窗口是一个决定。** 太短，慢客户端的重试就变成第二次写入；太长，内存跟着每次写入增长。规格检查
  课程交付的那个数。
- **键标识的是一次写入，不是一个请求。** 一个会话里两个不同的请求是两次不同的写入，所以键必须既依
  赖请求也依赖会话——否则第二个会被当成第一个的重复吞掉。

## 延伸阅读

- HTTP 世界管它叫*幂等键*，支付 API 管它叫*去重键*；窗口在两边是同一个决定，两边也是同一课：重试需
  要一个能说“这是同一个请求，拜托”的身份。
- `relay/2.2` 在*服务端*教了投递幂等（接收方记住一个投递 id）；这一步是同一个想法的*客户端*一侧，
  两半合起来，才让至少一次投递成为一个可以放心盖东西的地基。
- `5.11` 给客户端一个 SDK，而 SDK 的写入方法就是这一步的 `Session::key_for` 加一个重试循环：SDK 的
  契约是“你可以调两次，存储只会应用一次”。
