# 日志不能永远长下去：快照就是某个 index 上的状态

## 为什么

一份复制的日志是完美的记录，却是糟糕的产品。它按顺序记下每一次写入，能重建任何状态，而它会无界地
长——这意味着一个在集群里待了一年的节点，启动时要重放一年的写入，给一个掉队的节点要运一年的字节，
而要回答一个关于*现在*的问题，得在内存和磁盘上持有一年的条目。

每个复制的存储最后都落到同一个答案：**某个 index 上的状态就够了，产生它的那些条目可以走。** 快照
就是这个状态，加上说明它从哪儿来的两个数——index 和任期。用上它的是合并：快照 index 及以下的一切
都从日志里丢掉，而日志在集群的编号里保住自己的位置。

这一步是 `design` 级别，因为要决定的不是「偶尔拍个快照」，而是一组各有后果的选择：

- **什么时候**可以拍（只拍已提交的状态——别的东西还可能变）；
- 它**被允许替换什么**（它覆盖的那些条目，多一条都不行：一份合并得超过了自己快照的日志，已经失去
  了只靠条目把 follower 追上的能力）；
- 落得太远的节点**怎么**追上来（leader 已经没有的条目发不过去，所以发过去的是状态）；
- **迟到的快照到达时会发生什么**（被拒绝：比节点已经应用过的还旧的快照，会把一个已经在那里的状态
  撤掉）。

载荷仍然不透明。状态*是什么*，以及「在两个节点上应用同样的条目会产出同样的字节」这条规则，是
`5.10` 的主题；这一步关心的是让那个状态能被搬运的记账。

## 任务

- `src/raft/snapshot.rs`——`Snapshot`：它覆盖的 index 和任期，以及那些字节。在 index 0 上构造一个
  会被拒绝，而 `covers(index)` 回答一个给定位置在不在里面。
- `src/raft/mod.rs`——日志知道自己从哪儿开始：
  - `base()`：它不再持有的最后一条条目的 index；
  - `compact_to(index)`：丢掉 `index` 及以下的条目，保住位置（下一条条目是 `index + 1`），并拒绝
    一个日志并不持有的 index；
  - `starting_at(index)`：节点装完一个快照之后有的那份空日志；
  - `at()`、`append()` 和 `truncate_from()` 现在都把基准算进去，于是 index 在每个节点上仍然是同一
    件事。
- `src/raft/state.rs`——`Raft` 学会拍、合并和安装：
  - `take_snapshot(data)`：只针对已提交的状态，什么都没有提交时拒绝；
  - `compact(snapshot)`：拿日志去跟快照对（日志必须持有那个 index、且是那个任期），然后合并；
  - `install_snapshot(snapshot)`：用状态替换日志，同时挪动提交 index；比节点已经应用过的还旧的快照
    会被拒绝；
  - `needs_snapshot(peer)`：某个对端是不是落到了快照后面——是的话，`append_entries()` 发的是快照，
    而不是条目；
  - `InstallSnapshot` 消息、它的编码，以及 follower 的回答。
- `docs/snapshot.md`——这一步附带的那一页（`links` 判它）。
- `tests/budget_snapshot.rs`——`bench-budget` 闸门读的装置：它把一份一千条条目的日志合并成一个 600
  的快照，并打印各项计数。

## 陷阱

- **快照拍的是已提交的状态。** 给一条还没提交的条目拍快照，就是给一个还可能变的状态拍了张照片——
  而装了它的节点，已经应用了一件也许从没发生过的事。
- **合并保住编号。** 合并到 600 之后，下一条条目落在 601，而位置 600 是这个节点记得自己应用过的
  最后一个。一个给自己重新编号的日志，会让其他每个节点上的 `prev` 永远跟它对不上。
- **基准以下的 index 不是条目。** 在合并到 600 的日志上，`at(500)` 回答 `None`，跟一个未来的 index
  一模一样。把「没有」当成「还没有」再重试的代码，会永远等下去。
- **需要快照的对端，就是落在快照后面的那个。** 如果 leader 要把某个对端带到的那条位置在快照 index
  上或更早，通往那里的条目已经没了——发快照。从合并过的位置发条目，就是一个 follower 无声无息永远
  卡在后面的方式。
- **迟到的快照会被拒绝。** 比节点的提交 index 还旧的快照，会撤掉一个已经应用了的状态。拒绝才是
  正确答案，而且必须明说：一声不吭把它忽略掉的节点，是一个永远不知道自己落后的节点。
- **快照的任期要拿去跟日志的任期对。** 同一个 index、不同的任期，意味着另一段历史：这个快照来自
  一条这个节点从没有过的分支。合并到它，换掉的是错的那些条目。

## 延伸阅读

- Raft 论文 §7（「Log compaction」）点名的还是那三个问题：日志留多少、什么时候拍快照、以及怎么把
  一个落在快照后面的 follower 追上来。论文给最后这件事用的说法——「install snapshot」——就是你
  刚实现的那条消息。
- `openraft` 把这一对叫 `(last_log_id, snapshot_meta)`；每个实现都把 index 和任期放在一起，理由
  正是这一步的规格检查的那一条。
- `5.15` 会重启一个离开得够久、必须走这条路回来的节点，`5.22` 则审计快照携带的状态就是集群提交的
  那个状态——正是这两步，把「它编译过了」变成「它活下来了」。
