# 新节点，旧节点，同一个集群：带版本的协议与滚动升级

## 为什么

滚动升级是这个 track 里的第三个「两个真相同时成立」：joint consensus（`5.5`）同时持有两个成员资格，
证书轮换（`5.9`）同时持有两张证书，而这一步同时持有两个**构建**。规则还是同一套算术，只是单位不同——
每一刻，每个节点都得理解其他每一个节点——而两个数字让它可查：

- **major** 是线上格式：major 不同的两个构建无法交谈，所以滚动升级绝不能把它们混在一起。提 major 是
  stop-the-world，而计划拒绝假装不是这样；
- **minor** 在同一个 major 内是兼容的，而这种兼容**不对称**：一个构建能解析直到自己 minor 的每一个
  minor，再远就不行。肯退让的是较新的那个构建，因为可能发出旧构建读不了的帧的，正是它。

这种不对称就是全部的约束：一个升到 `1.2` 的节点，在最后一个节点升级之前，在线上说 `1.1`，而计划的各个
阶段也这么说。

## 任务

- `src/protocol.rs`——这一步新增的模块：
  - `Protocol { major, minor }`，带 `parse`/`render` 和 `can_parse`（那条不对称规则）；
  - `Greeting { node, protocol }` 和 `accept(local, greeting)`：拒绝时点出两个版本，并说明是 major 还是
    minor 谈不拢；
  - `Upgrade::new(order, from, to)`：拒绝空顺序、降级，以及跨 major 的计划；
  - `Upgrade::phases()`：除最后一个之外每节点一个 `Phase::Compat { speaking, built }`，最后一个是
    `Phase::Native { version }`——集群动起来的那一刻。
- `docs/protocol.md`——这一步交付的页面（`links` 判它）：那两个数字、这种不对称，以及运维者读的部署日志。
- `tests/sim_protocol.rs` 是课程内容：按种子的顺序走一遍计划。

## 完成标准

```sh
cargo test -p meshkv --test spec_protocol_evolution     # the six cases
KILN_SIM_SEED=1 cargo test -p meshkv --test sim_protocol -- --nocapture
```

第二条按种子的顺序打印计划的各阶段——除最后一个 `native` 之外全是 `compat`——而每个种子都到达同样的
形状。

## 陷阱

- **兼容规则是不对称的。** 较新的构建读得懂较旧构建的帧；较旧的构建读不了较新构建的帧。一个假定对称的计
  划，会让旧节点解析不了新节点发来的东西。
- **提 major 不是滚动升级。** 两个 major 不能待在同一个集群里，而一个跨了 major 的计划，就是一个让集群
  停下的计划；拒绝时会说明这一点。
- **拒绝会点出两个版本。** 「Protocol mismatch」会把运维者引向错误的构建；一句话里同时有 `1.2` 和 `1.1`
  就不会。
- **最后一步才是动的那一下。** 在它之前，已升级的节点都是兼容模式下的新构建——部署日志该这么说，而一个
  「全都一次升完」的计划说不出这话。
- **计划是一个顺序加若干阶段，而顺序归运维者。** 检查不在乎哪个节点先走；它在乎的是，集群从不混入彼此
  谈不拢的东西。

## 延伸阅读

- `5.9` 的轮换和 `5.5` 的 joint consensus 是同一个形状：一个两个真相共存的窗口、一个关于它能持续多久的
  算术上界，以及一道在改动之前跑的检查。
- `5.22` 的审计是最后一步：在这个 track 计划过的每一次改动之后，集群提交的那个状态，就是每个节点持有的
  状态。
